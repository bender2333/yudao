# Stage 2：三部门 Harness 基线可用

日期：2026-09-15  
性质：Stage 2 重新收敛定义，聚焦"先做出正常可用的 harness"

## 目标

做出一个能日常使用的三部门 harness，质量对标 OMP，但用原生三部门循环 + 新原型界面。进化、记忆、项目接续等推迟到后续阶段。

## 背景

Stage 1 (A-H) 代码已完成，确定性测试全通过，但真实验收因网络连接问题未完成完整流程。当前 Stage 2 原定义（整个"可验证的持续改进"）范围过大，包含离线分析、知识图谱、长期记忆等，与"先做出正常可用的 harness"目标不匹配。

本阶段收敛为：**完成 Stage 1 真实验收 + Provider 配置界面 + Web 原型实施 + OMP 对标补齐 + Prompt 优化**，确保日常可用。

## 范围

### 2.1 Stage 1 真实验收完成

- 真实 Provider 完整流程验收通过（Web 方向调整 + 压缩 + 最终 QA）
- 解决当前 TLS EOF 问题，或更换稳定 Provider
- 补全 F 验收缺口

**依赖**：Stage 1 代码已完成，需网络/Provider 稳定性

### 2.2 Provider 配置界面

- 按原型实现 Provider 管理界面（增删改查）
- 模型目录界面（显示容量、协议、超时）
- 三部门独立绑定界面（Product/Engineering/Quality 各选 Provider+模型）
- 任务创建前验证三部门配置

**依赖**：D18 后端已完成，需前端原型对接

### 2.3 Web 原型完整实施

按 `docs/web-prototype-implementation-plan.md` 完成：

#### Context View（上下文视图）
- 显示当前部门实际输入：developer 指令、部门历史、工具 schema、合同摘要
- 可展开查看摘要来源、原始事件
- 压缩历史可溯源到完整工具回合

#### Trace View（调用链追踪）
- 显示每次模型调用尝试：时间、状态、重试次数
- 失败调用显示错误分类、部分输出
- 链接到对应事件和上下文快照

#### 其他原型功能
- 任务列表优化（状态筛选、搜索）
- 事件卡片交互优化（折叠、高亮）
- 移动端适配（已有基础，需完善）

**依赖**：原型设计已完成，需前端实施

### 2.4 OMP 系统审查

**依赖**：需访问 OMP 代码和文档

### 2.5 Prompt 优化

三部门指令调优，减少无效往返：
- 产品：减少过度澄清，优先形成有效 PRD
- 工程：减少不必要的专家请求，优先自主完成
- 质检：明确验收标准，减少模糊返工

**方法**：
1. 收集真实失败/低效案例
2. 分析无效往返原因（指令不清、权限混淆、默认依据缺失）
3. 调整部门 prompt，补充专业补全依据
4. 回归测试，验证改善

**依赖**：需真实运行数据积累

### 2.6 日常可用性验收

**成功标准**：
1. **真实任务成功率**：连续 10 次真实任务，至少 8 次到达 DONE
2. **失败可追溯**：失败任务可通过 Context/Trace View 定位原因
3. **配置易用**：Provider 配置可通过界面完成，无需手动编辑 JSON
4. **界面流畅**：桌面/手机可正常使用，无明显卡顿或布局错误
5. **OMP 对标**：核心功能不弱于 OMP

**验收方式**：
- 真实场景测试（非 fake provider）
- 桌面 + 手机浏览器测试
- 失败诊断演练（故意触发错误，验证可追溯）
