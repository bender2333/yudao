# Yudao 总体路线图：四个大阶段

> 日期：2026-09-06。
> 性质：根据“扩大每阶段 scope”的要求重新规划；这是架构方案，不表示后续代码实施已经启动。
> 本文作为本轮总体路线入口。此前路线稿中的第二至第五阶段，按本文重新归组；原有运行记录保留各自的时间和证据边界。
> 最新推进顺序：用户要求先完成 Provider 连接及统一管理与部门绑定、第一阶段真实验收、OMP 系统审查、Context/Trace View、按原型完善 Web、Prompt 优化，再启动大功能。工作台与观测原型已完成，Provider 等配置原型预留；当前工作入口见 [第二阶段计划](stage-2-plan.md)。

## 1. 按完整能力划阶段

阶段的单位是研发者能够使用和验证的完整能力。证据采集、评价、控制、记忆等模块可以在同一大阶段内依次交付，模块完成只是内部里程碑。

| 大阶段 | 阶段结束时的系统 | 主要范围 | 整体验收要证明什么 |
| --- | --- | --- | --- |
| 一：可信交付 | 能完成可核验任务的三部门系统 | 当前 MVP、真实模型链路、控制边界、上下文隔离、Web、停止审计与经验候选 | 真实任务能完成，失败能解释和追溯，模型不能绕过交接与质检 |
| 二：可验证的持续改进 | 能从经历中减少后续错误的系统 | 可信经历、独立评价、有界局部控制、语义关联、知识图谱、经验库与长期记忆 | 完成发现问题、形成候选、验证、采用、失效的闭环，在未见任务上证明改善 |
| 三：可持续运行的组织 | 能承担复杂、长时间、并行工作的多部门组织 | 技能、部门内部循环与分型、部门协议、异步与恢复、运维职责 | 交付和运行责任形成闭环，复杂任务可以协作完成，中断可以恢复，成本和质量可比较 |
| 四：受治理的系统演化 | 能改进自身组织方式和日常规则的系统 | 组织与协议变更、基础规则维护、候选实验、版本采用与撤销 | 系统能提出并验证自身改进，在限定范围采用，有反例时能停止使用并恢复有效版本 |

最大的范围调整是：**原第二、第三、第四阶段合并为新的第二阶段**。第二阶段结束时必须看到实际改善，只建立观察报表还没有完成这个阶段。

原 OMP 编排版第一阶段已完成验收。用户随后明确三部门应直接构成 Agent loop，以控制每次上下文的粒度和组装；当前按 [原生循环设计](native-loop-design.md) 重构并重新验收。后续阶段的能力范围不变。

## 2. 第一阶段：可信交付

### 产品结果

研发者通过 Web 提交任务，产品、工程、质检能够围绕有效要求完成真实交付；遇到问题可以 Ask/React 或返工；取消、耗尽和失败有明确记录。

### 范围与完成条件

沿用 [MVP 总设计](loop-system-mvp-design.md)、[原生循环设计](native-loop-design.md)及 [MVP 验收记录](mvp-acceptance.md)，完成真实直达和 Ask/React、工程与质检独立检查、循环与步骤上限、取消与迟到结果、受测快照绑定、逐次模型请求上下文审计及浏览器行为验收。部门历史与自动压缩按最新 [细节清单](requirements/README.md) 实施；provider 用量不参与当前阶段停止判定。

原实施计划 Phase 1-5 都属于这里的内部步骤。最新 Phase 5 只要求从结构化事实记录可审计经验候选，并支持停止后的查询、导出和重放。候选评价、自动采用、独立蒸馏和暂停后继续执行均安排在后续能力中。

原编排版的完整验收和本轮原生循环验收分别记录。历史成功与测试数量不作为新循环的证明，当前状态以对应版本的验收记录为准。

## 3. 第二阶段：可验证的持续改进

### 产品结果

研发者能看到：某类错误如何反复发生，系统据此改变了什么，以及这些改变是否减少了后续任务中的同类错误。经验可以跨任务保留，也可以因反证失效。

首个贯穿场景继续采用已确认的“多轮返工仍重复同类错误”。将它延伸为完整链路：观察返工问题，验证一项改进，在未见任务中使用，再用反例验证经验失效。

### 三层职责

| 层 | 负责什么 | 与其他层的边界 |
| --- | --- | --- |
| 事实与语义层 | 保存各轮要求、完整交付、检查、上下文来源、用量与停止事实；关联问题、工件和经历 | 原始事实可追溯；关系和解释不能自行升级为事实或执行规则 |
| 评价与知识层 | 独立复核、问题轨迹、经验候选、适用范围、反例与有效性管理 | QA 负责当次放行；独立评价判断改善；提炼者不能自行认定候选有效 |
| 任务适应层 | 在既定目标、权限和总预算内调整取证、重试、资源分配，并使用已获准的经验 | 不自行改变用户目标、验收要求、部门责任或组织结构；每次采用可追溯 |

三层是职责边界，不要求建立三个服务或新增三个部门。

### 语义、知识图谱、经验和记忆各做什么

- **语义系统**统一当前任务族中“要求、问题、产物、证据、经验”的身份与含义，处理版本对应、适用范围和冲突。文本相似只能帮助检索，不能证明同一问题或同一根因。
- **知识图谱**组织这些对象及有来源的关系，回答“这条经验依据哪些经历”“要求变化会影响哪些经验”等问题。第二阶段交付围绕这些实际查询的关系模型与查询能力；专用图数据库根据现有存储和查询需求决定。
- **经验库**保存可检验的行为建议，包括支持证据、反例、适用条件和失效状态。经历可以产生候选，候选只有经过评价后才能在限定范围采用。
- **长期记忆**负责跨任务的持久保存、检索、更新与停止使用。持久存在不等于始终注入上下文；每次只装配当前任务需要的有效知识，历史和失效材料供追溯。

关系连接不证明因果，完整记录不证明已经学会。语义提取产生的推断也要保留来源与不确定性，不能回写原始运行事实。

### 内部里程碑

| 里程碑 | 可独立交付的结果 | 后续能力依赖 |
| --- | --- | --- |
| 2.1 可信观察 | 各轮交付可重新取回；独立评价识别持续未解决、修复后复发及有证据的错误放行；形成质量、返工和成本基线 | 控制、经验和研究使用同一份可复核证据 |
| 2.2 单项改进验证 | 对一类已观察到的问题比较固定策略与有界调整；记录原因、动作和结果 | 先知道一项变化是否有效，再扩大采用范围 |
| 2.3 跨任务经验闭环 | 候选提炼、独立验证、语义检索、限定采用、冲突处理与失效停用贯通 | 长期记忆开始影响后续任务，采用过程可以解释 |
| 2.E 原生项目演化 | 同一项目跨 run 接续、继承完整代码、合法需求变化、结果采纳和新会话接续 | 依赖稳定原生接口，不依赖先证明学习收益；与观察和学习分别验收 |
| 2.4 综合验收 | 在未见任务上比较固定基线、仅局部控制、仅经验复用及组合方案 | 区分各项贡献和相互干扰，评价完整学习闭环 |

2.2 与 2.3 在 2.1 形成可靠基线后，可以开展独立实验。知识身份与来源整理可随 2.1 推进；候选取得执行作用必须等对应评价完成。

### 整体完成标准

1. 完整演示“重复问题 -> 经验候选 -> 独立验证 -> 未见任务采用 -> 反例出现 -> 停用”，每一步都能回到当时的要求、交付和证据。
2. 在事先约定的任务族和质量条件下，相比固定基线减少同类错误或无效返工；同时报告实际调用、上下文、评价与知识维护的成本，不能以隐去额外开销换取改善结论。
3. 错误经验和过期要求能够被识别并停止注入；没有合适经验的任务仍能正常执行。评价意见不同先记为分歧，有可复核反例才判定错误放行。
4. 校准任务与未见任务分开，样本选择、最低证据量、质量条件和收益判据在采集前确定。所有失败、缺失和不确定结果都进入报告；不能因阶段范围变大省略独立评价。

现有 [返工观察设计](stage-2-evidence-and-evaluation-design.md)对应 **2.1**。其中“只观察、不自动注入”约束该工作包；第二阶段整体还包含 2.2-2.4 与 2.E。项目接续的目标、基线和采纳边界见 [原生项目演化研究](research/native-project-evolution-design.md)。以上大功能在最新六项前置工作全部完成后再启动。

## 4. 第三阶段：可持续运行的组织

### 产品结果

系统能够对一个需要持续运行的实际交付物承担完整责任：完成需求和开发，发布到明确环境，持续观察，遇到故障后形成修复任务并验证恢复。

同一任务可以跨较长时间、等待外部条件或并行处理局部工作。研发者能看到哪个部门负责、目前在等待什么、哪些结果仍有效，以及发生中断后从哪里继续。

### 范围与边界

| 能力 | 本阶段交付 | 复杂度边界 |
| --- | --- | --- |
| 技能封装 | 把经验证的稳定过程变成可复用单元，保留输入、输出、检查及内部步骤 | 异常时可以展开步骤处理；不能以隐藏过程牺牲审计和质量 |
| 部门内部循环与分型 | 按任务性质采用不同内部组织，允许有界子循环；若采用嵌套分形，外层仍能核验结果 | 产品、工程、质检内部可以不同；子任务继承上级约束，总预算不能逐层重置；深度、调用数和并发有上限 |
| 部门间协议 | 明确交接承诺、澄清、变更影响、责任转移、等待、失败和取消；比较减少无效往返的方案 | 外部责任和有效要求保持清楚，内部私有对话不作为交接合同 |
| 异步与恢复 | 持久记录待办和责任，支持等待、并行、中断续行、取消及迟到结果处理 | 重放状态、恢复订阅和恢复执行分别验收；不默认消息只到一次或外部动作绝不重复 |
| 运维职责 | 平台运行维护与交付物运行维护分别明确责任，接收告警和运行反馈，形成修复与验证闭环 | 运维提供事实和运行约束；产品负责取舍，工程负责修复，质检负责验证 |

“分型”在这里覆盖按任务类型选择不同内部组织；背景资料中的“分形”则指在不同层重复循环原则。两者都不要求每个部门再复制一套三部门。

先由研发者设计并比较有限的技能、部门组织和协议版本。本阶段交付这些组织方式的执行能力；第四阶段再让系统形成自身组织变更的完整流程。

### 内部里程碑与完成证据

1. **可组合交付**：一个复杂任务被分解并由多个内部单元协作完成，外层仍可独立核验；与原三部门方式比较，质量保持，协作或上下文成本下降。
2. **可恢复执行**：在跨部门交接、外部动作确认等边界中断，验证重启、重试、取消、重复和迟到消息。已确认完成的动作不被盲目重复；结果未知的副作用先核实、补偿或交由人处理，再决定继续。
3. **持续运行闭环**：选择确实需要运行维护的交付物，在事先约定的观察窗口内完成发布、观察、故障发现、修复和恢复验证，并核对用户可见状态。

技能与内部协作、异步与恢复可以分别推进，再做集成验收。异步能力依赖可信状态、责任和副作用边界，不依赖系统先学会生成技能；必要的本地恢复也可以更早独立交付。

阶段结束不能只展示多个 Agent 同时运行或一个消息队列已接通，必须看到真实责任、交付、运行反馈和恢复共同工作。规模扩展以真实并发与运行需求为依据，不预先引入分布式平台。

## 5. 第四阶段：受治理的系统演化

### 产品结果

系统能够根据多个任务和持续运行的证据，提出自身协作方式或日常规则的改进，完成实验、评价、限定采用和撤销。研发者可以回答：为什么改变、影响哪里、依据什么、异常时如何恢复。

### 三项职责

| 职责 | 负责什么 | 权限边界 |
| --- | --- | --- |
| 运行与运维 | 执行当前有效版本，提供交付、故障、恢复和成本事实 | 当次任务不自行采用尚未验证的组织或规则 |
| 演化与规则维护 | 识别长期重复问题，提出规则、协议、技能或部门结构候选，组织隔离比较，维护版本和适用范围 | 负责提出与维护，不能自行签发自己的有效性 |
| 独立评价与采用决策 | 按预先约定的标准判断收益、回归、成本及影响，决定采用范围和停止条件 | 被评系统不能修改用户目标、授权边界、独立评价及自己的通过标准 |

基础规则维护部门在这里形成完整工作职责。可调整的是日常执行规则，例如证据要求、上下文组织、部门交接习惯和任务分配策略；用户目标、授权、独立评价权仍由系统外部控制。

这些约束从第一阶段开始就存在。第四阶段新增的是系统提议和验证规则变更的能力。

### 整体完成标准

- 至少贯通一类组织或协议变更，以及一类日常规则变更的完整生命周期：问题证据、候选、隔离比较、独立评价、限定采用、运行观察、撤销验证。
- 使用未见任务比较既有组织、静态改进方案与系统提出的候选；新结构的收益须覆盖其额外协调和维护成本，不能以部门数量或复杂度增长作为进步。
- 用失败候选证明不能自行生效；用采用后的反例证明可以停止新增使用、处理在途任务，并恢复适用的有效版本。
- 语义关系能追踪规则和结构变化对经验、技能和在途工作的影响。规则变化后，相关旧经验须重新判断适用性，不能整体默认有效。

版本证据保留供审计与恢复；淘汰实现和接口直接删除，不建立旧接口兼容层。恢复到已验证版本是运行变更能力，不等于保留过时接口。

## 6. 开放性研究是一条并行路线

第二阶段形成可信经历与独立评价后，即可开展只读测量；观察方法可靠后进入隔离实验。研究可以贯穿第二至第四阶段，不必等待全部组织能力建成。

研究对象包括新任务、新产物、新技能原语及其组合。新颖性与可学习性要绑定具体观察者、历史和评价窗口；固定训练前缀与未见评价部分，保留不利结果。

第三阶段形成有效技能后，可以进一步研究新原语是否打开新的任务或产物空间。研究候选进入实际执行时，仍按其影响范围经过相应评价与采用流程。

主线四阶段的完成不依赖证明无限自我改进。有限实验只支持相应观察窗口内的结论；模型权重更新仍是可选方向，需单独证明其价值。

## 7. 跨阶段保持的架构主线

全系统按三条职责组织：执行负责完成当前任务，知识负责管理可追溯的事实与有效经验，评价负责判断结果及变化是否改善。控制层落实状态、权限、预算和版本选择，界面呈现事实并提交明确命令。

依赖顺序是：**可信执行 -> 可信经历与独立评价 -> 有效控制和经验 -> 可组合的组织能力 -> 组织与规则变更**。这是能力取得执行作用的顺序；设计、只读分析和隔离实验可以并行。

沿用现有 Python 控制层、事件与工件存储；模型接入采用单次调用边界，三部门循环与上下文装配由 Yudao 掌握。OMP 仅作代码级参考。实施前先检查已有依赖是否满足新需求。语义关系、长期记忆、独立评价或新增职责，都不自动意味着新增数据库、服务或 Agent。

成熟模式作为设计依据：沿用回归测试与独立评估隔离校准和验收，沿用知识来源追踪组织经验，沿用持久工作流的等待、恢复和副作用处理，沿用服务运维的监测与事件处理闭环。后续异步选型可比较 Temporal 等现有实现；本规划不提前锁定产品或自研调度引擎。

## 8. 旧规划如何归位

| 原规划或用户方向 | 新位置 |
| --- | --- |
| MVP 实施计划 Phase 1-5 | 第一大阶段内部步骤 |
| 原第二阶段：可信经历与独立评价 | 第二阶段 2.1，保留返工观察场景和证据边界 |
| 原第三阶段：有界局部控制 | 第二阶段 2.2 |
| 原第四阶段：经验复用 | 第二阶段 2.3-2.4，包含语义、知识图谱和长期记忆 |
| 原第五阶段：技能与结构 | 第三阶段的组合执行能力，以及第四阶段的结构变更能力 |
