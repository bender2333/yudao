# Yudao 总体路线图

状态：总图的顺序索引，只写阶段怎么区分、怎么演进，进度看 GitHub 的里程碑与工单；最近一次改动 2026-10-29，总图第一节去掉建设状态。之前的版本归档为 [archive/program-roadmap-2026-10-25.md](archive/program-roadmap-2026-10-25.md)。各次调整的经过与原因见[决定记录](decision.md)。

路线图只回答一个问题：总图 [architecture.html](architecture.html) 按什么顺序变成真的。总图是正本，路线图上的每一项都是总图上的一个方框、一道缝、一个状态或一环；总图上没有的东西不进路线图，先交总架构师。怎么做写在设计说明与需求记录里，不写在这里。总体意图见 [D38 系统意图与基础规则](requirements/system-intent.md)：独立高质量交付、长时间自己运行并自己修复、两层自举。进度看 GitHub 的里程碑与工单。

## 1. 怎么推进

**结构与内容一起长。** 总图把系统分成两种东西。固定的结构：一份事实、写入口与裁决、边界、薄驱动与三道共用的槽位、十三道缝、系统之外的评价、进程之外的看门狗；结构有限，建完就定型。填进结构的内容：部门与角色、轮转方式、工作单元的大小、装配的减法、动作与工具、模型与判定点、画面、观察者、部署形态；内容开放，随运行证据一直加。不设用户看不到东西的纯骨架阶段：每推进一档用户用得到的能力，顺手把碰到的模块边界收成总图第四节的缝，一道缝要有第二种实现（哪怕只是测试用的）接得上才算立住。一切改动守总图第二节的三环。

**阶段、薄片与试用。** 一个阶段是一个 GitHub 里程碑，标题就是阶段名。阶段里按薄片推进，一个薄片回答这个阶段的一个问题（第 2 节的表），做完发一个版本交给你试用，不挡下一个薄片；试用暴露的缺陷排到队列最前面，薄片的先后与细节按试用反馈调整。最后一个薄片的试用就是整个阶段的试用，通过以后关闭里程碑。认为总图缺了什么或错了，交总架构师先改总图；反馈调整的是走法，不增删总图上的东西。里程碑、阶段工单、试用工单与清理单的规矩见 `docs/agents/ticket-spec.md`。

**门：可迭代状态。** 从建结构走到大规模填内容与自己演化，要逐条核对五条判据：有持续的真实负载、能度量（带噪声范围与费用）、改动便宜且可撤回、看得见（循环停在哪一层、为什么）、锚点受保护。第 5 节写每个阶段结束时五条各到哪里。

## 2. 五个阶段

五个阶段的顺序是依赖：没有诚实的单机闭环，自动继续就是把错误继续下去；没有可靠的自转与看门狗，拆开只是把故障分到多台机器；没有独立评价与可撤回的定义，系统自己演化就会失控。

~~~mermaid
flowchart LR
    P1["阶段一：单机诚实闭环，三道槽位立缝"] --> P2["阶段二：可靠恢复、接入真实项目、独立评价"]
    P2 --> P3["阶段三：常驻自转、运维部门、看门狗兜底"]
    P3 --> P4["阶段四：拆开部署、细粒度协作、产品的城"]
    P4 --> P5["阶段五：受治理的演化（第二层自举）"]
~~~

| --- | --- | --- | --- |

| 阶段二：可靠恢复、接入真实项目、独立评价 | 你的一个真实项目接进来、改一处、关掉再开它接着做；对照报告说明比单个 agent 好多少 | 产品、工程、质检、独立的证据、界面、裁决与边界、定义、评价为已建，「模型与工具」本机部分已建；验收表三层（内核、缝、真实场景）都在运转 | ① 真实项目接着做 ② 比单个 agent 好多少 ③ 质检自己核验网页（在 ① 之后）④ 改一处、看得见、能撤回（在 ② 与 ③ 之后：场景 1 与逐条结论用到 ③ 的浏览器核验）⑤ Yudao 做自己的工单（在 ① 与 ④ 之后；试点的做法见[自举需求记录](requirements/self-hosting.md)） |

| 阶段五：受治理的演化（第二层自举） | 系统根据运行证据提出组织定义、流转规则与工作单元降解的候选，经独立评价限定采用，劣化时撤回 | 六节全部方框已建；两层自举与三层验收形成闭环 | 振荡信号进边界与元观察；第二层自举的闭环（提出、独立评价、限定采用、对比与撤回）；稳定工作单元的确定性降解；在楼里铺传送带 |

## 3. 十条内容道

结构建好以后，具体能力的扩充都归入十条并行的道。每条道对应总图上一个槽位、一道缝或一类定义；任何新内容按同一规矩进入：写定义或槽位实现 → 过缝层的契约测试 → 真实场景计分 → 限定采用 → 可撤回。道上「已规划」的项目是总图写明的，都要建；「未知落点」是给没想到的东西留的位置。

| 道 | 总图位置 | 已规划的项目（按先后） | 未知落点 |
| --- | --- | --- | --- |
| 01 部门 | 第一节产品、工程、质检、运维、下一个部门 | 三部门闭环 → 只写声明加运维 → 元观察 | 任何新职能的部门，只写声明 |
| 02 角色与外包 | 第二节「定义」的角色材料；第四节「执行」的缝 | 单循环的部门角色 → 工程的外包角色（ACP） → 部门内多角色与子循环 | 新的角色种类、新的外部代理协议；质检永远不外包 |
| 03 路由与粒度 | 第一节「轮转方式」；第四节「路由」的缝 | 按成果 → 任务池与工作单元的参数化 | 第三种轮转方式、自适应的拆分 |
| 04 装配与语义 | 第四节「装配」的缝 | 减法视图与压缩 → 五层轨迹与七类图谱 → 按依赖与焦点取、提示缓存复用 | 新的减法、跨项目经验的检索与失效重验 |
| 05 动作与工具 | 第一节「模型与工具」；第四节「动作」的缝 | 本机改文件与跑命令（带差异与回执） → 网络取回与 MCP → 浏览器与截图 → 远程执行代理 | 桌面操作（computer use）、技能、降解的脚本 |
| 06 模型与判定点 | 第四节「模型」的缝；第三节的判定点 | 多协议无状态调用与凭据隔离 → 能力表与按部门选模型 → 声明的判定点与校准的决策模型 | 新协议、本地小模型、自适应档位 |
| 07 观察者 | 第一节「观察者」；第四节「观察者」的缝 | 离线的经验候选 → 只读订阅与写入口提案 → 教训发现、振荡检测、降解信号 | 任何只读事实、只出证据与提案的模块 |
| 08 评价与验收 | 第一节「评价」；第四节「评价」的缝；第五节验收表 | 内核重放与契约测试 → 固定回归场景与单 agent 对照 → 操作代理照说明书判分 → 留出场景与发布检查 | 新评测题、变异测试与圈复杂度守卫、新领域的判分器 |
| 09 画面与空间 | 第一节「界面」；第四节「画面」的缝 | 楼与机房基础 → 机房设备与冒烟 → 产品的城与指向式输入 → 铺传送带编辑定义 | 无级缩放的导航、三维（出现需要第三轴的量时） |
| 10 部署与环境 | 第六节「部署是定义」；第四节「定义」的缝 | 单机单进程 → 常驻服务与进程外看门狗 → 控制主机加远程机器与开发板 → 多项目隔离并行 | 按项目拆多个控制核心实例；一个 Yudao 运维另一个 |

**未知的去处**：内容的未知落在道上，按上面的规矩进入；结构的未知（新方框、新缝、内核改动）只走一条路：先交总架构师改总图，第二环向后兼容，第一环经你批准才动工。

## 4. 三个空间：楼、机房、城

画面不是装饰，是一份事实的投影与高带宽的指挥语言（总图第一节「画面 = P_view(事实)」）。所有视觉元素都绑定事件回链，关掉装饰以后看到的全是事实断言。空间的映射（楼、机房、城与七种元件）的依据是调研[游戏世界与代码世界的映射](research/game-world-as-projection.md)与需求记录 [D41 三个空间](requirements/game-world-three-spaces.md)，这张表是它在路线图上的位置。

| 步 | 阶段 | 空间 | 建成的画面 | 绑定的事实 | 你能做的 |
| --- | --- | --- | --- | --- | --- |
| 0 | 一 | 楼与机房 | 部门房间、小人、传送带上的包裹（交接、询问、返工）、大厅决定板、上下文容量刻度、回放 | run 流、项目流、机器流、上下文清单 | 看循环卡在哪一环；拖包裹调优先级；在决定板上批准；倒带回放 |
| 1 | 二 | 全部 | 声明式对照表全覆盖（每种事件、术语、覆盖层都有一行，缺行即测试失败）；检验覆盖的视图 | 事件定义、放行报告与来源回链 | 从任一画面物件点开原始事件、上下文摘要或真实的差异 |
| 2 | 三 | 机房 | 已交付的软件是运行中的设备（版本牌、健康灯、备份柜）；故障冒烟并向楼投递修复包裹 | 运维观察记录、故障记录、部署与回滚事件 | 看生产环境的健康；理解修复为什么插队；批准回滚与恢复备份 |
| 3 | 四 | 城 | 页面、接口、数据表是建筑，模块是街区，依赖是道路，要求是蓝图，验收条件是检查站，证据让蓝图变建筑，试用会话是访客 | 语义图谱、检查回执、浏览器试用记录与截图 | 点一栋建筑直接说话；看哪片街区缺检查站或长期停在蓝图 |
| 4 | 四 | 三空间 | 规则成为物件与物理：可改的规则（模型接线、机器门牌、常设授权牌）是可操作的物件，不可改的（写入口的盖章机、部门的隔离墙）是推不动的边界 | 带版本的定义、项目设置、模型目录流 | 在空间里操作物件下发配置；直观看到安全边界 |
| 5 | 四 | 楼（房间内） | 传送带进房间：中心角色白板上的计划条目、工具角色桌上的任务卡、尝试的草稿堆 | 语义系统的五层轨迹、部门内多角色的事件 | 看部门内多角色与外包角色的瓶颈与重试消耗 |
| 6 | 五 | 楼与定义 | 铺传送带：编辑房间与传送带的连接，生成组织定义的候选交独立评价 | 组织定义候选、第二层自举的通道 | 用空间布局演化组织拓扑 |

| 判据一 真实负载 | 真实小项目闭环 | 接入已有仓库；第一层自举配对试点 | 每周持续的自举工单与运维的自动修复 | 多机多项目并行，自有与外包角色混合承接 | 系统自己提候选并承接演化的验证 |
| 判据二 能度量 | 模型尝试、用量与主机回执 | 回归场景计分、单 agent 对照、噪声范围、费用、检验覆盖比例 | 加留出场景、放行后观察期的故障率、第一次规则复查 | 加判定点准确率、外包与自有对照、任务池粒度对照 | 候选采用前后的隔离对照（含协调与维护成本）与撤回记录 |

| 判据四 看得见 | 楼里的房间、小人、包裹、决定板 | 加循环实例的层、已用边界、收敛状态、来源回链与开环明细 | 加修复循环、机房设备、冒烟、产品依赖底图 | 加产品的城、房间内五层轨迹、规则物件 | 加演化的循环、限定采用的对比视图、传送带编辑 |
| 判据五 锚点受保护 | 写入口事务校验、导入方向与契约版本检查 | 评测材料与被测版本分开，操作代理加确定性代码判分 | 内核清单、路径守卫、已安装实例的发布检查、看门狗演练 | 过网的执行权与派发编号校验、远程工作区从无历史快照重建 | 权威无环与末端独立证据的强制校验、失败候选不生效的演练 |
