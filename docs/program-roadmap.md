# Yudao 总体路线图

路线图把[总图](architecture.html)的意图分解成先后，只写三样：循环分哪几圈、每一圈分哪几个阶段、谁等谁。意图与框架在总图和它展开的[画面总图](architecture-view.html)；三条目的（独立高质量交付、长时间自己运行并自己修复、两层自举）与它们的验收标准在 [D38 系统意图与基础规则](requirements/system-intent.md)；怎么做写在设计说明与需求记录里。进度看 GitHub 的里程碑与置顶的阶段工单，读数看 Discussions 与 `docs/evaluation/`。

## 1. 怎么推进

**循环是主线，分三圈。** 骨架里最核心的是循环：角色围着一份事实轮转，互相询问，核验，打回与返工，接纳或停止（总图第三节）。产品沿着循环一圈一圈长出来：

- **职能之间的循环**：外环与内环。产品 · 工程 · 质检是一般情形，一两个职能直做、以开环完成结束是特例。
- **职能之内的循环**：一个职能里放一个子组织，职能开子事项，子组织自己转完交回上一层。一个职能只有一个角色是特例。
- **看着循环并修改循环**：观察者只读事实，给出证据与提案；系统根据运行证据修改自己的组织与规则（第二层自举）。

每一圈先让一般情形在真实模型下转起来，再围着它长出用得上的功能与体验。特例只验证，不另建：换一份定义就能转，循环本身不改。

**一个阶段是你拿到的一样东西。** 每一圈分成几个阶段，一个阶段结束时你亲手能做成一件新的事。阶段由一次真实运行回答：用从 main 打包安装的版本与真实模型，评价材料在系统之外。运行跑完，读数发在 Discussions，你试用过，由你定这个阶段结束；没做成，按读数修改以后重新运行。读数用来判断和改进，不用来排队：一项读数不好看，不挡别的阶段开始。

**谁等谁只看依赖。** 一个阶段只等它真正用到的东西（第 2 节的图）。互不依赖的阶段同时进行，每一圈同时最多一个进行中的阶段。围绕循环的功能与体验不属于哪个阶段，各自的前提满足就做（第 2 节「不排队的事」）。

**功能沿着骨架实现。** 骨架是一份事实与写入口、裁决与边界、薄驱动与三道槽位（总图第一、二节）。一项功能写成定义或槽位的实现，经骨架的合同接进来；要改骨架才接得进来的，先交总架构师。骨架上的位置就是第 3 节的十条道；每个阶段在每条道上只取它用得到的项。阶段里碰到的模块边界收成总图第四节的缝，一道缝要有第二种实现（测试用的也算）接得上才算立住。一切改动守总图第二节的三环。

**阶段、薄片与试用。** 一个阶段是一个 GitHub 里程碑，标题是编号加阶段名（第 2 节）。阶段里按薄片推进，一个薄片是这个阶段要交到你手上的东西的一部分，做完发一个版本交给你试用，不挡下一个薄片；试用暴露的缺陷排到队列最前面，薄片的先后与细节按试用反馈调整。薄片在进入阶段时切，和父工单、试用工单一起写在置顶的阶段工单里，这里不写工单号。认为总图缺了什么或错了，交总架构师先改总图；反馈调整的是走法，不增删总图上的东西。里程碑、阶段工单、试用工单与清理单的规矩见 `docs/agents/ticket-spec.md`。

**现在在哪。** 路线图不存状态。进行中的阶段，它的阶段工单置顶，开头三行写：现在在哪、下一步、等你什么。

**画面走自己的阶段。** 页面的范围收束在查看状态、回答决定与日常输入，低频配置与日常巡检交给进程外运维代理（[D42](requirements/external-ops-agent.md)）。画面在系统外面，像观察者一样只经接口读事实、发现有的命令（总图第一节「画面」方框，展开见[画面总图](architecture-view.html)）。阶段与薄片的交付只看系统与页面，「看得见」由页面负责；画面有自己的里程碑与第 4 节的步，每一步只画系统已经有的记录，系统不等它，它的测试也不挡系统的合并。

**本体脚手架与阶段检查。** Yudao 自身的本体（`tools/yudao-ontology/`）挂在仓库脚手架层，只读取总图、设计说明、定义与代码事实做一致性推理、封闭完整性核对与存在公理空位推导，不进入运行时。每个阶段结束核对时，除真实运行读数与缝核对外，运行本体检查核对总图、设计说明、定义与代码的一致性。

**未知的去处。** 内容的未知落在第 3 节的道上，按道的规矩进入；结构的未知（新方框、新缝、内核改动）只走一条路：先交总架构师改总图，只能向后兼容的一环要向后兼容，只由你批准的一环经你批准才动工。

### 谁等谁

```
1.1 转实 ──► 1.2 真实项目 ──► 1.3 自己转一周 ──┐
   │                                           ▼
   ├──► 2.1 转起来 ──► 2.2 用起来          3.2 修改循环
   │                                           ▲
   └──► 3.1 看着循环 ──────────────────────────┘
```

- 「职能之间：转实」是所有阶段的前提：循环在真实模型下转不稳，后面每一样都建在不稳的东西上。
- 它结束以后，「职能之间：真实项目」「职能之内：转起来」「看着循环」可以同时开始，互不等。
- 「修改循环」等两样：观察者已经在给出提案，「职能之间：自己转一周」留下了连续运行的记录。没有记录，修改就没有依据。
- 「看着并修改」一圈不等「职能之内」一圈。
- 「职能之间：自己转一周」与「修改循环」开始以前核对第 5 节的五条判据，因为这两段你不在场。

每个阶段进入要成立的条件见[验收证据规则](agents/acceptance-evidence.md)第 6 节。

## 3. 十条内容道

具体能力的扩充都归入十条并行的道，道就是骨架上的位置：每条道对应总图上一个槽位、一道缝或一类定义。任何新内容按同一规矩进入：写定义或槽位实现 → 过缝层的契约测试 → 真实场景计分 → 限定采用 → 可撤回。「哪个阶段用到」一列写每一项第一次被哪个阶段用到；标「不排队」的项前提满足就做（第 2 节「不排队的事」）；标「等」的项哪个阶段都还用不到，由某个阶段的读数、你点名或试用提出时排进来。「未知落点」是给没想到的东西留的位置。

**基础组件跟着道走，不归哪个阶段。** 上下文的压缩、模型调用、工具、执行环境这些组件，位置在道与它对应的缝上；阶段只是从道上取用。一项基础改进什么时候做，看两条：某个阶段的真实运行卡在它上面，它就是那个阶段的工单，放进那个阶段的里程碑；没有哪个阶段卡在它上面，它就不排队，放「围绕循环与阶段总览」，前提是有读数说明它值得做；说不准的先不做，在阶段工单上记下看哪个读数、读到多少就做，真实运行以后按读数定。改进只换缝后面的实现时，按这条走；要动缝的合同或薄驱动推进循环的方式时，是结构的事，先交总架构师改总图。

| 道 | 总图位置 | 已规划的项目（按先后） | 哪个阶段用到 | 未知落点 |
| --- | --- | --- | --- | --- |

| 09 画面与空间 | 第一节「画面」方框；第四节「画面」的缝；[画面总图](architecture-view.html) | 第 4 节的七步，一步一个里程碑 | 走自己的阶段（第 4 节） | 无级缩放的导航、三维（出现需要第三轴的量时）；接别的宿主，只换翻译器 |

## 4. 画面自己的阶段：楼、机房、城

画面是一份事实的投影，也是高带宽的指挥语言（总图第一节「画面 = P_view(事实)」，展开见[画面总图](architecture-view.html)）。所有视觉元素都绑定事件回链，关掉表演以后看到的全是事实断言。楼的形状从事项冻结的定义推出：工程是一间屋，产品 · 工程 · 质检是一层楼，子事项是屋里的一间小屋；没有的东西不画。空间的映射（楼、机房、城与七种元件）的依据是调研[游戏世界与代码世界的映射](research/game-world-as-projection.md)与需求记录 [D41 三个空间](requirements/game-world-three-spaces.md)。

画面是系统外面的一个使用方，有自己的里程碑，按下表一步一步走，不跟第 2 节的阶段绑在一起（步 5 要等「职能之内：转起来」有了子事项的记录，步 6 要等「修改循环」有了候选的通道，这是下表「要等系统先有的记录」一列的意思）；步 0「搬出」改的主要是系统一侧的页面与测试，由系统这边做。每一步的前提只有一条：系统已经有了这一步要画的记录。每一步都先画事实层（屋子、灯、章、刻度，状态直接换上去），表演（走位、气泡、排队）后补；验收看画面合同与诚实性测试，不对照原型的像素。系统加了画面不认识的职能或事件，画面简单画或不画，列进缺口清单，到下一步再补。

| 步 | 空间 | 建成的画面 | 要等系统先有的记录 | 你能做的 |
| --- | --- | --- | --- | --- |
| 0 搬出 | 楼与机房 | 现有的楼、楼层、职能的房间与回放成为单独的应用，经接口接上 Yudao，以单独的页面打开；认不出的事件简单画或不画，列进缺口清单；只在画面上有的事实先补到页面 | 无 | 和现在一样看与回放；点物件到页面看原始事件 |
| 1 跟着定义伸缩 | 楼 | 房间与连接从冻结的定义推出，一间屋到产品 · 工程 · 质检三间屋，认不出的职能画成通用的屋；开环完成与放行用不同的章；检验覆盖的视图；上下文容量刻度 | 冻结的定义与形态、开环完成的记录、放行报告与来源回链、上下文清单 | 一眼看出事项有没有经过独立核验；从任一物件点开原始事件、上下文摘要或真实的差异 |
| 2 机房 | 机房 | 已交付的软件是运行中的设备（版本牌、健康灯、备份柜）；故障冒烟并向楼投递修复包裹 | 运维观察记录、故障记录、部署与回滚事件 | 看生产环境的健康；理解修复为什么插队；批准回滚与恢复备份 |
| 3 城 | 城 | 页面、接口、数据表是建筑，模块是街区，依赖是道路，要求是蓝图，验收条件是检查站，证据让蓝图变建筑，试用会话是访客 | 语义图谱、检查回执、浏览器试用记录与截图 | 点一栋建筑直接说话；看哪片街区缺检查站或长期停在蓝图 |
| 4 规则物件 | 三空间 | 规则成为物件与物理：可改的规则（模型接线、机器门牌、常设授权牌）是可操作的物件，不可改的（写入口的盖章机、职能的隔离墙）是推不动的边界 | 带版本的定义、项目设置、模型目录流、机器流 | 在空间里操作物件下发配置；直观看到安全边界 |
| 5 子事项 | 楼（房间内） | 子事项是屋里的小屋，门框上是余量与层数，远看是一个在转的小盒子、推近进去；屋里的白板、任务卡与草稿堆 | 子事项的事件流、语义系统的五层轨迹 | 看子组织与外包角色的瓶颈与重试消耗 |
| 6 铺传送带 | 楼与定义 | 编辑房间与传送带的连接，生成组织定义的候选交独立评价 | 组织定义候选、第二层自举的通道 | 用空间布局演化组织拓扑 |

## 5. 五条判据

可迭代状态是：改一处，跑真实任务，看到结果，决定保留还是撤回，这个圈能便宜地反复转。它的五条判据在「职能之间：真实项目」结束时逐条核对，都通过才进「职能之间：自己转一周」与「修改循环」：前一段你不在场，后一段系统修改自己。验收标准在 D38 的 N-T1 至 N-T5；核对的做法与记录的位置见[验收证据规则](agents/acceptance-evidence.md)第 6 节。

| 判据 | 读数从哪里来 |
| --- | --- |
| N-T1 有持续的真实负载 | 「职能之间：真实项目」的真实项目上被采纳的事项 |
| N-T2 能度量 | 每个版本的评测结果，与单个 agent 的读数并排的比较 |
| N-T3 改动便宜且可撤回 | 「职能之间：真实项目」里改一处参数、换一次形态：只改定义，每次修改有事件记录，一条命令撤回 |
| N-T4 看得见 | 每个阶段的页面：循环实例的层、已用的边界、收敛状态与停止原因；开环完成与放行分开写 |
| N-T5 锚点受保护 | 评价材料取自运行中的已发布版本；修改内核清单里的路径不会被自动采纳的演练 |
