## 1. 统一阶段名称

| 阶段 | 产品结果 | 当前状态 | 完成依据 |
| --- | --- | --- | --- |
| Stage 1：可信交付 | 产品、工程、质检围绕有效要求完成可核验交付；失败与取消可追溯 | 按原生循环验收记录完成 | [MVP 验收](archive/mvp-acceptance.md)，以及 Stage 2 的 F 收口记录 |
| Stage 2：三部门 Harness 基线及 Provider 补充 | 原日常路径基础上，补无配置启动、统一 Provider 模块和 Go 订阅接入 | 2.1–2.6 按原合同关闭；2.7 于 2026-09-20 关闭 | [历史进度](archive/stage-2-progress.md)、[2.7 计划](archive/stage-2-provider-plan.md)、[2.7 执行报告](archive/stage-2-7-provider-report.md) |
| Stage 3：通用工具、可靠恢复与执行环境 | 能处理实际代码项目，接入已有项目，中断后自动接续；代码在控制主机或登记的远程机器上执行；网络与 MCP 工具、浏览器、技能；不同项目并行；模型管理；桌面客户端与系统首页；与单个 agent 对照；规则与参数可以不发布新版本修改与撤回，内核有清单；Yudao 在自己的仓库上试点完成真实工单 | 进行中：M0 三部门的循环结构与命令执行（#466、#478）优先级最高；M1 网页界面与模型管理的代码已完成，与 M0 一起发布为 0.1.2 交给用户试用（#183、#467；0.1.1 早于网页界面），M0.5 骨架与应用排在 M0 之后、M2 之前（[ADR-0042](adr/0042-skeleton-and-application-two-layers.md)），M2 至 M4 排在 M0.5 之后，M5 技能与 MCP 扩展的需求待讨论（#494）；进度见 GitHub 里程碑与[当前验收基线](current-baseline.md) | [Stage 3 计划](stage-3-plan.md) 的工作包与独立验收 |
| Stage 4：运维部门与长时间运行 | 运维部门在登记的运行环境中部署并观察交付的软件，发现的问题自动进入修复；Yudao 在进程重启、模型服务中断后自动继续；Yudao 自己的工单默认由 Yudao 实例执行；流转由定义驱动 | 后续规划；需求已确认 | 本文第 5.1 节 |
| Stage 5：部门内协作、上下文与界面 | 部门在连续多个事项中只使用当前有效的信息，部门内部围绕中心角色分工，判定点经校准后参与裁决，用户能看清部门内外的运行过程 | 后续规划；语义系统、部门内多角色有设计与工单 | 本文第 5.2 节 |
| Stage 6：受治理的系统演化 | 自举第二层：根据运行证据提出组织或规则变更，独立验证、限定采用并可撤销；部门之间的流转有独立的流程审查 | 后续规划；前置条件见第 6.2 节 | 本文第 5.3 节 |
| 持续改进工作线 | 从重复问题形成经过验证、可停用的跨任务经验，并证明收益；由用户发起的参数对照 | 仅有候选记录和 L1–L3 离线工具；参数对照从 Stage 3 结束时开始；跨任务经验随 Stage 6 进行 | 本文第 4 节 |

同一项目的事项接续、完整成果继承与采纳已有实现和三次变更报告；这不等于长期记忆或学习收益。接入已有代码项目并建档由 3.8 完成（[D33](requirements/existing-project-onboarding.md)）。

1. **已完成的前置工作**：3.2A 本地通用工具；提示词审计补丁与请求结构（#46、#47、#101、#103、#106）；控制核心重构（[#43](https://github.com/bender2333/yudao/issues/43)，[ADR-0010](adr/0010-control-core-drives-role-steps.md)、[ADR-0011](adr/0011-async-control-core.md)）；一份事件日志（[#44](https://github.com/bender2333/yudao/issues/44)，[ADR-0013](adr/0013-event-log-and-single-write-path.md)）；带版本的定义（[#48](https://github.com/bender2333/yudao/issues/48)，[ADR-0014](adr/0014-versioned-definitions.md)）；应用层与接口层的骨架（[#72](https://github.com/bender2333/yudao/issues/72)，[应用层与接口层设计说明](design/app-and-interface.md)）。
2. **用户决定**（[#49](https://github.com/bender2333/yudao/issues/49)）：所有等待用户的事项使用同一种机制（[总体架构](design/architecture/overall-architecture.md)第 7.4 节），第一种是模型引用无法使用时的待恢复；3.1 的核实未知动作与 Stage 4 运维清单以外的动作按同一机制加入。
3. **调用目标每次请求解析**（[#45](https://github.com/bender2333/yudao/issues/45)，2026-09-29 完成）：[ADR-0005](adr/0005-resolve-call-target-per-request.md) 的部分提前到 3.1 之前；控制核心不持有明文凭据，进程重启后按当时的设置与凭据来源继续。
4. **界面工作线**（[D30](requirements/web-game-frontend.md)、[ADR-0015](adr/0015-desktop-client-and-http-contracts.md)、[ADR-0032](adr/0032-interface-served-as-web-pages.md)、[应用层与接口层设计说明](design/app-and-interface.md)）：与 #49、#45、3.1 同时进行。#70 剩下的子工单排在 3.1 之前，然后是界面外壳（#79）与当前档页面（#71），当前档页面通过验收以后删除旧 Web 控制台（#78）。界面由 Yudao 服务以网页提供，有系统首页（待你决定、离开期间的报告、项目列表），在本机打开时用浏览器的系统通知提示新的决定；只在局域网内访问控制主机，认证与加密保留位置并标为 TODO。此后每个工作包（3.1、3.2C、3.4A、3.2B、3.2D、3.8、D24 与 Stage 4 运维）连同界面一起验收，界面工单挂在所属工作包的父工单下。原型依据为 v9（原型设计已结束，[docs/prototypes/v9/design.md](prototypes/v9/design.md)，屏幕清单、页面与决定卡片沿用 [v8 设计说明](prototypes/v8/design.md)）；像素画面按 [ADR-0021](adr/0021-client-pixel-view-follows-v9-structure.md) 用 PixiJS、XState、GSAP 实现 v9 的实体—组件—系统结构。#79 以后是项目页面（#80）、首页页面与决定卡片（#175）和六张像素画面工单（#176、#82、#177、#179、#178、#180）。
5. **评测工作线**（[D32](requirements/comparison-experiment.md)、[评测场景设计](design/evaluation-scenarios.md)）：与界面工作线和后端工单并行进行，不要求排在其他工作之前。按评测场景设计第 10 节建立场景材料、评分器与 OpenCode 运行器，运行 OpenCode 基础分；再建立 Yudao 运行器，在前提满足时运行 Yudao 一侧。设计已由用户逐项审阅（2026-09-30）：评测工具、OpenCode 基础分与场景 2、3 的 Yudao 一侧属于里程碑 M2，场景 1 的 Yudao 一侧属于 M4；版本回归在每个里程碑交给用户试用之前运行。版本比较使用噪声范围，结论是改进、无差别、退化之一；评测结果带费用（用量乘以用户填写的单价）与检验覆盖比例（[规则登记与参数设计说明](design/rules-and-parameters.md)第 4 节）。三个场景是回归场景；不参与调整的留出场景另设，第一次运行在 Stage 4 结束时。Stage 3 结束之前必须完成，没有完成时 Stage 3 不能关闭。
6. **3.1 可靠恢复**：先核对执行权和未完成动作，再继续同一 run。Yudao 启动时自动继续所有中断的 run，只有结果未知的外部动作通过用户决定交给用户。恢复与 replay 分开，恢复不能重置限额或复活已取消任务。进行中的角色任务由步骤驱动从已提交的状态重新装配后继续。执行权在写入口与领域写入一起核对（[ADR-0012](adr/0012-single-control-core-scalable-execution.md)、[ADR-0018](adr/0018-single-control-host-remote-execution.md)）。
7. **3.2C 执行环境服务**（[D29](requirements/remote-execution.md)、[ADR-0018](adr/0018-single-control-host-remote-execution.md)）：执行环境的合同经过 HTTP 加 JSON，提供远程执行代理这种新实现，代码在执行位置上直接运行（[ADR-0022](adr/0022-run-directly-without-containers.md)）；用户在系统中登记机器，在项目中授权使用。依赖 3.1 的动作核实与 #110。
8. **3.4A 不同项目并行**：恢复验收通过后，不同项目、隔离目录中的事项并行执行，执行槽位控制并发数量。同一项目的事项按优先级排队，一次只进行一个。
9. **3.2B 网络与 MCP**（[D36](requirements/network-and-mcp.md)、[设计说明](design/network-and-mcp.md)）：取回与项目设置中的 MCP 服务器固定在控制主机上运行；依赖执行环境的合同（#128），每个新工具单独验收，真实控制主机上的验收是 #495。
10. **3.2D 浏览器**（[D34](requirements/browser-and-computer-use.md)、[浏览器与 computer use 设计说明](design/browser-and-computer-use.md)，#123）：依赖 3.2B 的 MCP 接入与执行环境的合同（#128）。浏览器工具使用 Playwright MCP，每一步把页面的可访问性结构交给模型，模型能看图时附上截图。质检用浏览器操作交付的网页，工程可以使用浏览器做研发自测。质检部门的模型应当能看图：所选模型不支持图像时照常保存并提醒，这时浏览器只给可访问性结构。试用会话的浏览器使用与网络取回相同的拒绝规则，拒绝 Yudao 服务自己的地址，其余按普通浏览器 MCP 的默认做法。质检的逐条结论写明每条验收条件的检验方式，放行附检验覆盖比例与开环的条件（[验证的独立性设计说明](design/independent-verification.md)第 7 节）。评测场景 1 的 Yudao 一侧依赖本项。computer use 是以后阶段的专题（第 5 节）。
11. **3.8 接入已有项目**（[D33](requirements/existing-project-onboarding.md)）：依赖 3.1。产品读取已有代码与文档，写出描述现有行为的初始 PRD；工程写出现有结构的说明；用户确认初始 PRD 以后，它成为当前有效的要求，之后的事项在它的基础上修改。B8 加入采纳写回：按 [ADR-0034](adr/0034-adopted-change-writeback-three-tree-merge.md) 合并事项起点、采纳成果与写回时目标分支三份代码树，核验最终树后生成分支与合并请求；建档材料分类，现有行为以 README、测试与验收基线为准，设计与需求文档作为要求材料。
12. **D24 模型管理**（[#83](https://github.com/bender2333/yudao/issues/83)，[模型管理设计说明](design/model-management.md)）：依赖 #45 与应用层的目录命令（#77）。统一的模型目录与准入、模型能力表、推理档位、每个项目单独选择各部门的模型、部门的建议能力提醒；#96 用真实 Provider 验收三种协议。评测时给质检换用视觉模型、3.2D 的建议能力提醒都依赖本项。增加服务方案按预置表与自定义连接进行（[ADR-0003](adr/0003-versioned-preset-table-no-remote-refresh.md)），不另设工作包。
13. **3.9 组合验收与对照实验**：在 3.8 接入的 openai-agents-python 上对 Stage 3 的各项能力逐项给出结论，浏览器的结论引用 3.2D 的真实验收；在 D32 的三个评测场景上重复与 OpenCode 的对照实验（[D32](requirements/comparison-experiment.md)）；增加共享上下文的一组（[验证的独立性设计说明](design/independent-verification.md)第 6 节）；自举第一层的配对验收并入本项（第 6.1 节）。所有工作包父工单关闭以后进行。
14. **迭代底座**（[D38](requirements/system-intent.md)，父工单 #342）：五条判据中度量、可撤回的改动与锚点的基础，与其余工作包没有阻塞关系。
    - M2：B3 规则登记的四项记录与界限、参数事件与 `parameter.set`、检查时限与建档的单轮上限成为项目级参数（[规则登记与参数设计说明](design/rules-and-parameters.md)）；B6 omp 流程的基线数字（每个工单的审查轮数、合并以后归因到它的集成层失败、搁置的原因、耗时与用量）；B2 已用时间写入事件、边界的核对从流程编排中分出来，挂在 3.1 下（[循环与收敛设计说明](design/loops-and-convergence.md)）；B8 采纳写回与建档材料的分类，挂在 3.8 下。
    - M3：B1 内核清单、六条不变式测试、导入方向与行数的检查；B7 接口的访问令牌、由已安装的实例提供的发布检查（[可信内核设计说明](design/trusted-kernel.md)）。
    - M4（3.9 之前）：B5 可见范围词表的扩充、交付说明分为事实与解释、先判断后看解释（[验证的独立性设计说明](design/independent-verification.md)）。
    - 评测结果的费用、覆盖比例与噪声范围并入评测工作线的 #194、#196、#198；试用浏览器的拒绝规则并入 #149；机器的上线与离线写入机器流并入 #140。
15. **自举工作线**：Yudao 实例把 Yudao 仓库当作普通项目开发，前置条件、试点与验收见第 6.1 节。试点的首批工单是新增的可视化内容：循环实例、收敛状态、事实来源与检验覆盖。

## 3. 跨阶段架构与约束

分层、各层的职责与边界、长期决定、合同与使用的技术见[总体架构：职责分层](design/architecture/overall-architecture.md)：界面、接口层、应用层、控制核心（流程编排、步骤驱动、上下文装配、裁决规则、写入口、事件日志）、定义、知识层、观察层、观察者、执行层（Provider、执行环境、外包 agent 的运行进程）。各阶段的新能力都放进这个结构，不建立第二套事件事实源。

部署形态按 [ADR-0018](adr/0018-single-control-host-remote-execution.md) 与 [ADR-0022](adr/0022-run-directly-without-containers.md)：控制核心、事件日志、工件存储、Provider 模块与观察者在一台控制主机上运行，事件日志使用 SQLite；执行环境可以是本机进程或远程机器上的执行代理，代码在执行位置上直接运行。[ADR-0007](adr/0007-boundaries-for-distributed-deployment.md) 的边界作为执行环境服务的合同继续遵守；同时遵守 [ADR-0010](adr/0010-control-core-drives-role-steps.md) 至 [ADR-0015](adr/0015-desktop-client-and-http-contracts.md)：每次模型请求在控制核心装配；控制核心在一个异步事件循环中运行；控制核心持有执行权；一份事件日志与唯一写入口；组织、角色、动作、本体与规则作为带版本的定义；桌面客户端、FastAPI 接口层，服务之间使用 HTTP 加 JSON。并且遵守 [ADR-0027](adr/0027-trusted-kernel-outside-self-modification.md) 至 [ADR-0031](adr/0031-declared-loop-layers-and-sub-loops.md)：可信内核在自我修改之外，下一个版本由当前运行的已发布版本检查；裁决有三种手段，控制核心的决定只依据已记录的事实；部门由信息的内聚形成，需要独立的是判断；规则是带理由的暂定默认值，参数在界限以内直接修改；循环层写在定义里，角色可以发起子循环，每一层都有边界。

继续遵守 [D09](requirements/execution-limits.md)：运行时间上限是主要的收敛保证，部门激活次数与模型步数的上限保留但默认值放开，单次请求有超时，重试和压缩计入已有额度；等待模型服务、等待机器与等待桌面的时间不计入运行时间上限，每种等待有一个时长上限，超过时发出决定请求并通知用户一次；已用的时间与次数写入事件，进程重启以后连续累计。Provider 用量只读记录；费用等于用量乘以用户填写的单价，没有单价时保持未知；成本进入度量与采用规则，不进入运行中的控制。恢复不清零；并行新增执行槽位控制。不引入 token / 费用硬预算、额度预留系统或通用预算平台。

不引入外部工作流引擎（[ADR-0012](adr/0012-single-control-core-scalable-execution.md)）：控制核心本身就是按事件重放的状态机，会话可以丢弃，恢复时从已提交的状态重新装配。使用 SQLite、官方 SDK 与 HTTPX。

事件分成两类（[ADR-0019](adr/0019-project-stream-across-versions.md)）。项目流记录项目的长期事实：登记的运行环境与常设授权、放行版本历史与当前部署的版本、故障记录、事项队列、当前 PRD 与采纳成果；它跨 Yudao 版本保存，升级时只增加字段或事件种类，已有字段的含义不变。事项在项目流中只记录存在、队列位置、关联的故障记录与最终结果。run 流记录每次 run 的过程，跟随应用版本，不新增旧格式兼容层或迁移：每个版本声明自己的 run 事件版本，升级前后相同时直接重启，按 3.1 自动继续；不同时先排空（停止开始新事项，等正在进行的 run 结束）再升级。用户可以强制升级，正在进行的 run 记为因升级停止，对应的事项用项目的起点重新开始，排在队列最前面；新的 run 不称为恢复了原 run。

### 5.1 Stage 4：运维部门与长时间运行

依赖 3.1、3.2C 与用户决定（#49），以及自举第一层通过验收（第 6.1 节）。进入本阶段时，同步修改 CLAUDE.md、AGENTS.md 与 README 的项目表述，加入运维部门。

**运维部门**（[D27](requirements/operations-department.md)，并入原 3.8）

- 负责交付物（用户项目的软件）的部署、运行观察、性能与故障处理。生命周期跟随项目：项目采纳交付物之后接手，长期存在。按与产品、工程、质检相同的单循环形态建设。
- 观察交付软件的日志、状态与使用者的交互日志。发现的问题作为修复事项自动进入「产品 → 工程 → 质检」流程；用户提出的新要求是另一个来源。同一项目一次只进行一个事项，修复事项排在前面。
- 用户登记运行环境时批准一份常设授权清单：部署质检放行的交付快照、回滚到上一个放行版本、重启服务、读取日志与运行数据。清单以内的动作由运维直接执行并记录，清单以外的动作通过用户决定交给用户。紧急故障时先回滚恢复服务，再排队修复。
- 常设授权还包括部署前备份数据：备份经执行代理复制到控制主机的工件存储，每个运行环境保留最近 3 份。DeliverySpec 声明回滚是否兼容当前数据；兼容时回滚在常设授权以内，需要恢复备份的回滚通过用户决定交给用户。
- 故障记录：运维每次发现问题时提出「新故障」或「已有故障再次出现」，由控制核心记入项目流，每个修复事项关联一条故障记录。修复部署后在观察窗口（项目设置，默认 24 小时）内同一故障再次出现，这次修复记为失败；窗口内出现的其他故障另开故障记录。同一故障连续 2 次修复失败（项目设置）后停止自动修复，服务保持在上一个放行版本，发出决定请求并附上两次修复的证据。
- 运维读取的日志、交互日志与运行数据按外部内容放入请求（与 3.2B 的规则相同），标明来源，只作为数据；修复事项必须引用具体的观察证据，由产品判断是否成立后进入工程。
- 项目登记了运行环境时，产品在 PRD 中加入默认的运行要求：健康检查、结构化日志、交互日志、版本号输出；工程实现，质检逐项核验，运维按约定的格式读取。用户在需求中另有写明的，以用户为准。
- 交付软件使用的密码与服务密钥由用户写在运行环境机器上的指定位置；DeliverySpec 只写需要的密钥名称，执行代理启动软件时读取；事件日志与模型输入中只出现名称。
- 等待用户回答的决定一直等待，界面显示已经等待的时长；这期间紧急故障仍按常设授权回滚，新发现的故障记入故障记录并排队。系统不替用户决定，也不跳过正在等待的事项。
- 运维不修改功能要求，也不代替质检放行。平台与交付物两类运行责任分开，发布成功与运维接收分别记录，见 [运行责任样例](archive/stage-3/operations-responsibility-sample.md)。
- 流转由定义驱动：组织定义只写许可关系（每个部门关注哪些成果、可以询问谁）与边界，开始工作的部门由运行中的事实决定（[ADR-0039](adr/0039-departments-work-from-watched-outputs.md)）；控制代码中没有部门与角色的名称。运维部门只通过定义加入，是「增加一个部门只写声明」的第一次验收（[循环与收敛设计说明](design/loops-and-convergence.md)第 6 节）。

**长时间运行**

- 控制主机使用一台常开的机器（台式机、小主机或树莓派）。
- Yudao 由操作系统的服务管理在崩溃后重新启动，进程卡住时由服务管理的看门狗重新启动，启动时按 3.1 自动继续中断的 run。自举第一层成为常态以后，升级与回退的机械由两层之外的看门狗承担：A、B 两个槽位，存活检查加金丝雀任务，候选失败回退到稳定版，只认健康协议，不依赖 Yudao 的代码，每次修改由用户批准（[骨架与应用设计说明](design/skeleton-and-application.md) 第 10 节；用户 2026-10-23 决定现在只写设计，建设在本阶段）。
- Yudao 定时向外部的报到服务（healthchecks.io）报到；控制主机断电、断网或 Yudao 停止工作时，超过时限没有报到，由该服务通知用户。这项检查不运行在控制主机上。
- 数据保留：事件日志永久保留；事项结束后删除它的工作区与尝试文件；交付快照保留最近 3 个放行版本，以及放行历史中仍被回滚引用的版本；磁盘剩余空间低于设定值时在界面提示。
- 通知与决定请求只在 Yudao 的界面中显示，在本机打开界面时用浏览器的系统通知提示。
- 模型服务中断（[D17](requirements/provider-retries.md)）：按 D17 重试用完以后仍然是连接失败、服务端错误、过载或限流，以及凭据失效、证书校验失败时，run 暂停并进入「等待模型服务」，按间隔重试，服务恢复后自动继续；进入等待时通知用户一次，用户可以取消；等待时间不计入运行时间上限，超过等待的时长上限时发出决定请求。请求内容错误与上下文过长不进入等待，按原有规则处理。

**自举第一层成为常态**

- Yudao 自己的工单默认交给 Yudao 实例执行，omp 留作对照与后备。
- 成果不再经过 omp 的审查流程、由 Yudao 直接采纳，按[可信内核设计说明](design/trusted-kernel.md)第 5 节的级别逐级放开。开始直接采纳之前具备四项条件：路径守卫生效并演练过一次；接口的访问令牌；自举项目的执行位置在控制主机以外的登记机器上；发布检查由已安装的实例提供。
- 圈复杂度与变异测试的研发工具（[D35](requirements/self-hosting.md) 第 4 条）：在 Windows 与 Linux 上直接给出结果与诊断，工程部门用它对自己的交付做检查；在开始直接采纳之前完成，因为那以后审查流程不再检查 Yudao 的成果。阈值、代码位置与工具的形式在设计本阶段时讨论，Stage 3 末的手动检查（#173）的记录作为依据。

**度量与看得见**

- 第一次规则复查与第一次留出场景的运行在本阶段结束时进行。
- 修复循环作为一层出现在循环实例与收敛状态的画面中；被造出来的产品画出底图，底图由主机从代码导出（依赖边由成熟工具经命令导出）。
- 放行以后在观察窗口内由运维发现的故障数，作为质检误放行的外部度量。

完成依据：一个真实软件在登记的 Orange Pi AIpro 开发板上运行，在约定的观察窗口内，运维从可观测数据中发现故障，修复事项经过产品、工程、质检，运维重新部署并确认恢复，全程不需要人参与；观察窗口内的一次 Yudao 进程中断与一次模型服务中断都自动接续；同一项目连续 5 个修复事项中，各部门每次请求的长度不随事项数量增长；只用定义增加运维部门，控制核心的源码没有差异；连续 4 周每周有被采纳的自举事项；规则复查表与留出场景的报告。增加运维部门本身不等于具备运行能力。

### 5.2 Stage 5：部门内协作、上下文与界面

排在 Stage 4 之后，依赖 3.1、3.4A、3.2B 与 D24 模型管理（均在 Stage 3），以及 D32 新增的共享上下文一组的结果。本阶段内各项工作的先后由 D32 对照实验的结果决定。进入本阶段时，D25、D26 与观察者的工单按修改后的设计说明重新拆分；原来的子工单已于 2026-10-19 关闭，保留父工单 #22、#50 与 #98 作为占位。

- **语义系统**（[D25](requirements/semantic-system.md)，[语义系统设计说明](design/semantic-system.md)）：为 Agent 整理轨迹与图谱，并据此组装上下文，承担项目记忆；整理出的知识图谱与语义工程供 Stage 6 系统演化使用。分两部分：
  - **整理**：轨迹记录事项的工作过程，分事项、一轮工作、计划条目、角色任务、尝试五层；图谱由证据、事实、知识、决定、要求、实体、推测七类内容及其关系构成，在其上归纳教训、洞见与画像，其中教训与洞见由教训发现模块找出（待设计）。角色在工作中随时记录，主机按本体校验后写入；记录事实时由 JEV 核对证据是否支持陈述。轨迹与图谱都是事件的投影，重放可以重建。
  - **上下文组装**：每次请求由固定的栏目组成，按常驻栏目、目录、按需取得、接触时附加四种方式放入内容，变更与新到达的输入作为通知追加进历史；各角色按分工得到不同的上下文；组装不调用模型，放入的内容与原因由上下文清单记录。请求长度受工作上限控制，达到压缩阈值时先清理旧工具结果，再压缩，压缩后由轨迹与图谱代替被移出的历史。栏目按变化频率从少到多排列，历史只追加，使提示缓存可以复用。
  - 完成依据：同一项目连续多个事项中，被修改的要求以取代关系出现，被取代的要求不作为有效内容进入请求；数据流核对列出缺失的覆盖；重放事件重建的轨迹与图谱与原记录一致；详细验收见设计说明第 16 节。
- **判定点与决策模型接入**：判定点的通用合同、校准与准入、不确定时的升级、记录与重放（[ADR-0028](adr/0028-three-means-of-adjudication.md)，[总体架构](design/architecture/overall-architecture.md)第 7.2 节）；流转上的判定点各自校准。JEV 的 systemone 接口作为 Provider 模块的新协议接入，ADR-0001、ADR-0004 的结构不变。语义系统的证据核对是第一个判定点，只核对外部文档与需要解读的运行输出。核对用本地中文样本选取阈值，再用另一批样本复核，样本与标注方式见 D25 上下文组装专题第 16 条；校准通过之前，核对结果只记录，不显示给模型，也不改变内容的状态。JEV 的能力边界见 [JEV 决策模型调研](research/jev-decision-model.md)。
- **部门内多角色**：每个部门围绕中心角色协作，中心角色负责规划与判断，经理负责对外沟通，探索者、主程与审查者是中心角色的工具，见 [部门内多角色设计说明](design/department-roles.md)（[D26](requirements/department-roles.md)）。对产品、工程、质检、运维四个部门一起引入。依赖语义系统、3.4A 执行槽位与 3.2B 网络工具（探索者查资料）；决定见 [ADR-0016](adr/0016-center-role-collaboration.md)、[ADR-0017](adr/0017-role-settings-override-department.md)，工单为父工单 #50 与子工单 #51 至 #65。完成依据：在 D32 的任务集上与单循环部门对照，交付质量不低于单循环，并报告模型请求数、用量与耗时；设计第 16 节的反例通过。
- **验证的独立性**：验证密度按记录调节（[验证的独立性设计说明](design/independent-verification.md)第 5 节）；语义系统的可见范围按 D32 新增一组的结果取默认值；审查者能否看到本部门记录的事实作为部门内多角色对照中的一组。
- **子循环**：角色在自己的边界内发起子循环，与部门内多角色的角色任务使用同一个合同（[循环与收敛设计说明](design/loops-and-convergence.md)第 4 节）。
- **外包角色**（[D31](requirements/outsourced-agent-roles.md)）：主程的执行者种类增加外包，经 ACP 接入；在自举的配对工单上对照自有主程与外包主程。
- **同一项目多个写入者**：工作区按事项分开，采纳之前对合并后的结果运行检查定义规定的检查，基线变化以后旧的验证结果不被采用。
- **观察者**：观察者的订阅与提案接口（#98）；教训发现模块作为第一个观察者，只提出提案。
- **规则与参数的界面**：参数的查看与界内修改（`parameter.set`），组织图（部门、角色、观察者、判定点与许可关系）。
- **可观测性**：Yudao 自身的观察视图，包括部门内外的运行过程、角色任务、上下文来源与用量，见 [可观测性详细设计](research/observability-design.md)；数据来自应用层的查询与事件流。
- **界面**：应用层、接口层与网页界面已在 Stage 3 的界面工作线建立（第 2 节）。本阶段在界面中加入部门内多角色、部门账本与语义记录的界面，以及可观测性的深入视图，随对应的后端工单一起验收。

### 5.3 Stage 6：受治理的系统演化

本阶段是自举第二层：Yudao 根据运行证据修改自己的组织与规则。排在最后，前置条件见第 6.2 节，进入时细化需求与设计。按提出者分两步：系统先提出界内参数的候选，由对照与用户决定采用；这一步稳定以后，系统提出结构性定义的候选，经结构校验、隔离对照与用户批准后限定采用。循环方式的界面修改（`definition.propose`）在本阶段加入。内核、评价材料与基础规则不在演化的对象之内。

- **元观察与规则检查部门**（[D28](requirements/meta-observer.md)）：只做流程审查与观察，结果用于系统演化。观察部门之间的流转事实，按规则审查过程，报告不符合项；使用 JEV 决策模型在控制层事先规定的判定点上做带有置信度的判断，判定点用带有标注的中文流转样本校准通过后，控制层才按判断结果自动推进。质检放行、产品取舍、规则修改不交给它；它只按控制核心给出的读取范围订阅事件，不读取作者的工作过程。在组织上是一个部门，运行时是一个观察者加判定点，使用 Stage 5 建立的观察者订阅与提案接口（#98）。
- **扩展接口**：完整的命令行、NDJSON 输出与嵌入（在 CI 中完成事项并导出）。原 3.7 的这一项在本阶段进入时重新写规格。
- **系统演化**：运行提供事实；演化模块提出组织、协议或日常规则候选；独立评价决定是否在限定范围采用。候选不能自行批准，用户目标和授权边界不由被评系统修改。演化使用元观察的审查与观察记录，以及语义系统整理的知识图谱；用于最终判断的隐藏评价材料不进入被评系统可以读取的知识图谱。
- **跨任务经验**：持续改进工作线（第 4 节）中的跨任务经验在本阶段贯通。

完成条件：
- 一类组织/协议变化和一类日常规则变化贯通证据、候选、隔离比较、独立评价、采用、观察与撤销。
- 使用未见任务比较原组织、研发者静态改进和系统候选，收益包含额外协调与维护成本。
- 失败候选不生效；采用后的反例能停止新增使用、处理在途工作并保留恢复依据。
- 规则变化能追踪对经验、技能及事项的影响，不默认旧经验继续适用。

开放性研究仍是独立研究方向；可信观察之后才能开展有解释力的实验。模型权重更新保持可选，不是主线阶段的必做项。

### 5.4 愿景：Yudao 负责自己的运维

Yudao 平台由自己的运维部门负责运维。自举难度大，平台运维目前由人负责。以后可以由一个 Yudao 部署中的运维部门负责另一个部署，健康检查保留一条不依赖被运维平台的外部途径（[组织与持续运行研究](research/organization-runtime-evolution.md)第 7.2 节）。

资源调度与并发的扩展途径见 [ADR-0018](adr/0018-single-control-host-remote-execution.md)：执行能力不够时增加执行环境，模型服务限流时增加连接，一台控制主机容纳不下时按项目分成多个控制核心实例，各有触发条件。

通过 Discord、飞书等消息渠道发送通知、回答决定请求是以后的工作，不排入阶段；在此之前通知与决定只在 Yudao 的界面中显示。

验收（并入 3.9）：

- 任务：6 个真实工单，界面 3 个、控制核心以外的后端 3 个。每个工单由 omp 流程与 Yudao 各实现一次，先后次序轮换；对照一侧的结果不合并。
- 模型：两边从同一组 9router 组合取得模型。omp 保持现在的配置（`oro` 与 `my-small`），Yudao 三个部门都用 `oro`；报告按组合分列请求数与用量。

- 指标：到达审查通过所需的轮数；集成层的结果；架构师核对验收标准时发现的问题数；用户试用时提出的缺陷数；耗时、用量与费用；需要用户介入的次数。

第一层在 Stage 4 成为常态，成果由 Yudao 直接采纳之前具备四项条件：路径守卫、接口的访问令牌、控制主机以外的执行机器、由已安装的实例提供的发布检查（第 5.1 节，[可信内核设计说明](design/trusted-kernel.md)）。
