# Yudao 总体路线图

路线图把[总图](architecture.html)的意图分解成先后的几个阶段，只写先后、每个阶段要回答的问题与回答它的真实运行。意图与框架在总图和它展开的[画面总图](architecture-view.html)；三条目的（独立高质量交付、长时间自己运行并自己修复、两层自举）与它们的验收标准在 [D38 系统意图与基础规则](requirements/system-intent.md)；怎么做写在设计说明与需求记录里。进度看 GitHub 的里程碑与工单，读数看 Discussions 与 `docs/evaluation/`。

## 1. 怎么推进

**循环是主线。** 骨架里最核心的是循环：角色围着一份事实轮转，互相询问，核验，打回与返工，接纳或停止（总图第三节）。五个阶段是同一个循环在越来越难的条件下转：转完一圈，转出来的比单个 agent 好，断了接得上，自己转一周，修改自己。每个阶段的真实运行都用有核验角色的形态，默认是产品 · 工程 · 质检。

**功能沿着骨架实现。** 骨架是一份事实与写入口、裁决与边界、薄驱动与三道槽位（总图第一、二节）。一项功能写成定义或槽位的实现，经骨架的合同接进来；要改骨架才接得进来的，先交总架构师。循环要转，骨架上每个位置都要有东西，位置就是第 3 节的十条道；每个阶段在每条道上只取它的问题用得到的项，所以阶段一是最薄的一圈，后面的阶段各加厚几条道。阶段里碰到的模块边界收成总图第四节的缝，一道缝要有第二种实现（测试用的也算）接得上才算立住。一切改动守总图第二节的三环。

**一个阶段、一个问题、一次真实运行。** 真实运行用从 main 打包安装的版本与真实模型，评价材料在系统之外。运行跑完，读数发在 Discussions，你试用过，由你定这个阶段结束；答案是否定的，按读数修改以后重新运行。阶段里的工单为这次运行服务。

**阶段、薄片与试用。** 一个阶段是一个 GitHub 里程碑，标题就是阶段名。阶段里按薄片推进，一个薄片回答这个阶段的问题的一部分，做完发一个版本交给你试用，不挡下一个薄片；试用暴露的缺陷排到队列最前面，薄片的先后与细节按试用反馈调整。薄片在进入阶段时切，和父工单、试用工单一起写在置顶的阶段工单里，这里不写工单号。认为总图缺了什么或错了，交总架构师先改总图；反馈调整的是走法，不增删总图上的东西。里程碑、阶段工单、试用工单与清理单的规矩见 `docs/agents/ticket-spec.md`。

**画面走自己的阶段。** 画面在系统外面，像观察者一样只经接口读事实、发现有的命令（总图第一节「画面」方框，展开见[画面总图](architecture-view.html)）。阶段与薄片的交付只看系统与页面，「看得见」由页面负责；画面有自己的里程碑与第 4 节的阶段，每一步只画系统已经有的记录，系统不等它，它的测试也不挡系统的合并。

**未知的去处。** 内容的未知落在第 3 节的道上，按道的规矩进入；结构的未知（新方框、新缝、内核改动）只走一条路：先交总架构师改总图，只能向后兼容的一环要向后兼容，只由你批准的一环经你批准才动工。

## 2. 五个阶段

顺序是依赖：循环转不完一圈，就没有可以比较的交付；交付不比单个 agent 好，接进真实项目只多花用量；断了接不上，就转不满一周；没有连续的运行，就没有修改自己所依据的证据。

验收标准在 D38，表里只写编号。

| 阶段 | 要回答的问题（交付验证） | 回答它的真实运行 | 读什么 |
| --- | --- | --- | --- |
| 阶段一：转完一圈 | 默认形态在真实模型下，循环自己把一件小的事从意图转到放行：产品写要求，工程交付，质检独立核验，中间的询问、决定请求、打回与返工都走得通，每次停下的原因都出自清单 | 评测场景里的一个任务，默认形态，运行 3 次；一次 agent 试用 | 走到放行的次数与每次停止的原因；外环的状态各走到几次；每一轮按角色分开的步数、用量与压缩次数 |
| 阶段二：比单个 agent 好 | 同一个模型、同一批任务，循环交付的质量高于单个 agent（OpenCode）；多花的步数、用量与时间是多少 | 全部评测场景，默认形态与 OpenCode 各运行 3 次 | N-G1 的验收标准；两边每次的完成度、正确性、用时与用量并排列出 |
| 阶段三：断了接得上 | 你的一个真实项目接进来，连着做几件事；中途停止服务再启动，循环从停下的地方接着转 | 你选的真实项目，运行中停止服务一次 | 接续以后重做的工作与丢失的工作；需要你出面的次数；第 5 节五条判据的读数 |
| 阶段四：自己转一周 | 你不在的一周，循环做 Yudao 自己仓库的工单；一次进程中断与一次模型服务中断都自动接续，一次故障由运维发现、经循环修复、运维重新部署 | 先做第一层自举的配对试点，再连续运行一周 | N-G2、N-G3 的验收标准；做完的工单、需要你出面的次数、放行以后发现的缺陷 |
| 阶段五：修改自己 | 循环根据运行证据提出组织定义、流转规则与工作单元降解的候选，经独立评价限定采用，变差时撤回 | 一个候选从提出到采用或撤回的全过程 | N-G4 的验收标准；采用前后的隔离对照与撤回记录 |

## 3. 十条内容道

具体能力的扩充都归入十条并行的道，道就是骨架上的位置：每条道对应总图上一个槽位、一道缝或一类定义。任何新内容按同一规矩进入：写定义或槽位实现 → 过缝层的契约测试 → 真实场景计分 → 限定采用 → 可撤回。「哪个阶段用到」一列写每一项第一次被哪个阶段的问题用到；标「等」的项五个阶段的问题都用不到，由某个阶段的读数、你点名或试用提出时排进来。「未知落点」是给没想到的东西留的位置。

| 道 | 总图位置 | 已规划的项目（按先后） | 哪个阶段用到 | 未知落点 |
| --- | --- | --- | --- | --- |
| 01 职能与核验 | 第一节产品、工程、质检、运维、下一个职能、独立的证据 | 产品 · 工程 · 质检闭环 → 核验成为角色的性质，任何形态都能放，发布带一组形态（「工程」「产品 · 工程」「产品 · 工程 · 质检」），职能可以交给外部 agent 做→ 只写声明加运维，运维发现的故障成为事项的来源 | 一：产品 · 工程 · 质检闭环。三：一组形态。四：运维。等：职能交给外部 agent 做 | 任何新职能，只写声明；新的核验方式；新的事项来源 |
| 02 角色与外包 | 第二节「定义」的角色材料；第三节「子组织」；第四节「执行」的缝 | 单循环的职能角色 → 外包角色（ACP），没有下游核验时记开环完成 → 子事项承接职能内多角色与分形 | 一：单循环的职能角色。等：外包角色、子事项 | 新的角色种类、新的外部代理协议；核验角色的结论不外包 |
| 03 路由与形态 | 第一节「轮转方式」；第四节「路由」的缝 | 按成果 → 直做（单 agent 与普通多 agent，开环完成） → 任务池与工作单元的参数化 | 一：按成果。三：直做。等：任务池 | 第四种轮转方式、自适应的拆分 |
| 04 装配与语义 | 第四节「装配」的缝 | 减法视图与压缩（保留失败的尝试） → 五层轨迹与七类图谱 → 按依赖与焦点取、提示缓存复用 | 一：减法视图与压缩。等：轨迹与图谱、按依赖与焦点取 | 新的减法、跨项目经验的检索与失效重验 |
| 05 动作与工具 | 第一节「模型与工具」；第四节「动作」的缝 | 本机改文件与跑命令（带差异与回执） → 网络取回与 MCP → 浏览器与截图 → 远程执行代理 | 一：本机改文件与跑命令。等：网络取回与 MCP、浏览器与截图、远程执行代理 | 桌面操作（computer use）、技能、降解的脚本 |
| 06 模型与判定点 | 第四节「模型」的缝；第三节的判定点 | 多协议无状态调用与凭据隔离 → 能力表与按职能选模型 → 声明的判定点与校准的决策模型 | 一：多协议无状态调用与凭据隔离。等：按职能选模型、判定点 | 新协议、本地小模型、自适应档位 |
| 07 观察者 | 第一节「观察者」；第四节「观察者」的缝 | 离线的经验候选 → 只读订阅与写入口提案 → 教训发现、振荡检测、元观察、降解信号 | 五：全部 | 任何只读事实、只出证据与提案的模块；观察者不做职能 |
| 08 评价与验收 | 第一节「评价」；第四节「评价」的缝；第五节验收表 | 内核重放与契约测试 → 固定回归场景与单 agent 对照（OpenCode） → 操作代理照说明书判分 → 留出场景与发布检查 → 内核的代码质量门槛（[内核的代码质量检查设计说明](design/kernel-quality-gate.md)） | 一：内核重放与契约测试、固定回归场景。二：单 agent 对照。四：留出场景与发布检查、内核的代码质量门槛。等：操作代理照说明书判分 | 新评测题、新领域的判分器 |
| 09 画面与空间 | 第一节「画面」方框；第四节「画面」的缝；[画面总图](architecture-view.html) | 第 4 节的七步，一步一个里程碑 | 走自己的阶段（第 4 节） | 无级缩放的导航、三维（出现需要第三轴的量时）；接别的宿主，只换翻译器 |
| 10 部署与环境 | 第六节「部署是定义」；第四节「定义」的缝 | 单机单进程 → 常驻服务与进程外看门狗 → 控制主机加远程机器与开发板（写入口、动作、模型、接口四道缝过网络验收，质检在另一台机器上检查） → 多项目隔离并行 | 一：单机单进程。四：常驻服务与进程外看门狗。等：远程机器与开发板、多项目隔离并行 | 按项目拆多个控制核心实例；一个 Yudao 运维另一个 |

## 4. 画面自己的阶段：楼、机房、城

画面是一份事实的投影，也是高带宽的指挥语言（总图第一节「画面 = P_view(事实)」，展开见[画面总图](architecture-view.html)）。所有视觉元素都绑定事件回链，关掉表演以后看到的全是事实断言。楼的形状从事项冻结的定义推出：工程是一间屋，产品 · 工程 · 质检是一层楼，子事项是屋里的一间小屋；没有的东西不画。空间的映射（楼、机房、城与七种元件）的依据是调研[游戏世界与代码世界的映射](research/game-world-as-projection.md)与需求记录 [D41 三个空间](requirements/game-world-three-spaces.md)。

画面是系统外面的一个使用方，有自己的里程碑，按下表一步一步走，不跟第 2 节的阶段绑在一起；步 0「搬出」改的主要是系统一侧的页面与测试，由系统这边做。每一步的前提只有一条：系统已经有了这一步要画的记录。每一步都先画事实层（屋子、灯、章、刻度，状态直接换上去），表演（走位、气泡、排队）后补；验收看画面合同与诚实性测试，不对照原型的像素。系统加了画面不认识的职能或事件，画面简单画或不画，列进缺口清单，到下一步再补。

| 步 | 空间 | 建成的画面 | 要等系统先有的记录 | 你能做的 |
| --- | --- | --- | --- | --- |
| 0 搬出 | 楼与机房 | 现有的楼、楼层、职能的房间与回放成为单独的应用，经接口接上 Yudao，以单独的页面打开；认不出的事件简单画或不画，列进缺口清单；只在画面上有的事实先补到页面 | 无 | 和现在一样看与回放；点物件到页面看原始事件 |
| 1 跟着定义伸缩 | 楼 | 房间与连接从冻结的定义推出，一间屋到产品 · 工程 · 质检三间屋，认不出的职能画成通用的屋；开环完成与放行用不同的章；检验覆盖的视图；上下文容量刻度 | 冻结的定义与形态、开环完成的记录、放行报告与来源回链、上下文清单 | 一眼看出事项有没有经过独立核验；从任一物件点开原始事件、上下文摘要或真实的差异 |
| 2 机房 | 机房 | 已交付的软件是运行中的设备（版本牌、健康灯、备份柜）；故障冒烟并向楼投递修复包裹 | 运维观察记录、故障记录、部署与回滚事件 | 看生产环境的健康；理解修复为什么插队；批准回滚与恢复备份 |
| 3 城 | 城 | 页面、接口、数据表是建筑，模块是街区，依赖是道路，要求是蓝图，验收条件是检查站，证据让蓝图变建筑，试用会话是访客 | 语义图谱、检查回执、浏览器试用记录与截图 | 点一栋建筑直接说话；看哪片街区缺检查站或长期停在蓝图 |
| 4 规则物件 | 三空间 | 规则成为物件与物理：可改的规则（模型接线、机器门牌、常设授权牌）是可操作的物件，不可改的（写入口的盖章机、职能的隔离墙）是推不动的边界 | 带版本的定义、项目设置、模型目录流、机器流 | 在空间里操作物件下发配置；直观看到安全边界 |
| 5 子事项 | 楼（房间内） | 子事项是屋里的小屋，门框上是余量与层数，远看是一个在转的小盒子、推近进去；屋里的白板、任务卡与草稿堆 | 子事项的事件流、语义系统的五层轨迹 | 看子组织与外包角色的瓶颈与重试消耗 |
| 6 铺传送带 | 楼与定义 | 编辑房间与传送带的连接，生成组织定义的候选交独立评价 | 组织定义候选、第二层自举的通道 | 用空间布局演化组织拓扑 |

## 5. 五条判据

可迭代状态是：改一处，跑真实任务，看到结果，决定保留还是撤回，这个圈能便宜地反复转。它的五条判据在阶段三结束时逐条核对，都通过才进阶段四：阶段四起你不在场，阶段五起系统修改自己。验收标准在 D38 的 N-T1 至 N-T5；核对的做法与记录的位置见[验收证据规则](agents/acceptance-evidence.md)第 6 节。

| 判据 | 读数从哪里来 |
| --- | --- |
| N-T1 有持续的真实负载 | 阶段三的真实项目上被采纳的事项 |
| N-T2 能度量 | 阶段一、二每个版本的评测结果，与两份结果的比较 |
| N-T3 改动便宜且可撤回 | 阶段三里改一处参数、换一次形态：只改定义，每次修改有事件记录，一条命令撤回 |
| N-T4 看得见 | 每个阶段的页面：循环实例的层、已用的边界、收敛状态与停止原因；开环完成与放行分开写 |
| N-T5 锚点受保护 | 阶段二起评价材料取自运行中的已发布版本；修改内核清单里的路径不会被自动采纳的演练 |
