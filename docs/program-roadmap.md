# Yudao 总体路线图

更新：2026-09-19。本文是当前阶段定义与依赖的唯一入口。最新用户方向：先统一路线图与验收基线，再推进通用工具和恢复，恢复可靠后再加并行。本次更新是设计，不表示新增运行能力已实现。

当前代码核对点为 319d586。能力和证据状态见 [当前验收基线](current-baseline.md)，近期工作见 [Stage 3 计划](stage-3-plan.md)。历史报告保留原编号、版本和结果，不再作为新的执行入口。

## 1. 统一阶段名称

| 阶段 | 产品结果 | 当前状态 | 完成依据 |
| --- | --- | --- | --- |
| Stage 1：可信交付 | 产品、工程、质检围绕有效要求完成可核验交付；失败与取消可追溯 | 按原生循环验收记录完成 | [MVP 验收](mvp-acceptance.md)，以及 Stage 2 的 F 收口记录 |
| Stage 2：三部门 Harness 基线 | 项目与事项、Provider 配置、部门上下文、工具、QA、封存、观测和 Web 日常路径贯通 | 按 2026-09-15 合同关闭；不代表所有复杂任务已验证 | [实施合同](stage-2-implementation-plan.md)、[阶段进度](stage-2-progress.md)、[真实验收](stage-2-real-task-validation.md) |
| Stage 3：通用工具、可靠恢复与持续运行 | 能处理实际代码项目，中断后可靠接续，再支持隔离并行、技能与运维责任 | 设计准备；新能力未实现 | [Stage 3 计划](stage-3-plan.md) 的工作包与独立验收 |
| Stage 4：受治理的系统演化 | 根据运行证据提出组织或规则变更，独立验证、限定采用并可撤销 | 后续规划 | 本文第 5 节 |
| 持续改进工作线 | 从重复问题形成经过验证、可停用的跨任务经验，并证明收益 | 仅有候选记录和 L1–L3 离线工具；学习闭环未贯通 | 本文第 4 节 |

Stage 2 自 2026-09-15 起只指 Harness 基线。原总体路线中的“第二阶段：可验证的持续改进”统一称为“持续改进工作线”，不再使用 Stage 2′ 或与当前 2.1–2.6 重号的名称。长期目标保留，执行顺序采用用户最新选择。

同一项目的事项接续、完整成果继承与采纳已有实现和三次变更报告；这不等于长期记忆或学习收益。接入已有代码项目并建档（B5）仍是后续工作。

## 2. 近期顺序与完成边界

~~~mermaid
flowchart LR
    B["3.0 统一文档与当前版本基线"] --> T["3.2A 本地通用工具"]
    T --> R["3.1 单机可靠恢复"]
    R --> P["3.4 隔离工作区并行"]
    R --> X["3.2B 网络与 MCP 扩展"]
    P --> O["后续技能、组织与运维"]
    X --> O
~~~

编号沿用已有 Stage 3 工作包，执行顺序以依赖为准。3.0 的文档统一可在本轮完成；当前版本的回归和中等压力真实验收是后续执行工作，不能因计划已写完就标为通过。

1. **统一基线**：分清历史验收版本、当前代码和本轮新测；固定场景、限额、检查与证据保存方式。
2. **通用工具**：先完成真实代码项目的搜索、阅读、编辑、本地命令与独立 QA；从一开始记录每次动作及其结果，仍单任务运行。
3. **可靠恢复**：先核对执行所有权和未完成动作，再继续同一 run。恢复命令与 replay 分开，恢复不能重置限额或复活已取消任务。
4. **并行**：恢复验收通过后，先支持不同项目、隔离目录中的独立事项；再处理同一项目的成果竞争与采纳。

Provider 配置页已经完成，不再重复建设。第二协议与推理设置保留在 3.3，但不是本轮工具和恢复的前置。完整技能、MCP、扩展平台、组织分型、运维均有后续位置，不在首个端到端版本一次加入。

## 3. 跨阶段架构与约束

| 层 | 责任 | 边界 |
| --- | --- | --- |
| 用户与观察层 | Web / CLI / API 提交明确命令，呈现任务、动作与恢复事实 | 查询和 SSE 重连不触发任务继续；用户可以看清待核实动作 |
| 业务引擎层 | 项目采纳与事项责任；run 的合同、部门交接、工具准入、QA、停止、恢复 | QA 放行与项目采纳分开；调度不代替部门决定 |
| 基础能力层 | 模型单次调用、工具执行、工作区、SQLite 事件与工件、Git、进程管理 | 工具只回报事实；单次调用不自行决定重试、恢复或交接 |

沿用现有三层，不为新能力建立第二套事件事实源。只在工具执行、恢复协调和项目调度的真实边界提取职责，不预先拆服务，也不先重写整个 Orchestrator。

继续遵守 [D09](requirements/execution-limits.md)：按部门激活次数、模型步骤、单次超时控制执行，重试和压缩计入已有额度；Provider 用量及费用只读记录，未知保持未知。恢复不清零；并行新增执行槽位控制。本次不引入 token / 费用硬预算、额度预留系统或通用预算平台。

成熟依据沿用 [组织与持续运行研究](research/organization-runtime-evolution.md) 对 OMP、Temporal、LangGraph 的审查。现有 SQLite、Python 标准库、OpenAI SDK 和 HTTPX 先满足单机边界；不预先引入工作流服务。若故障实验说明现有实现无法承担要求，再按同一矩阵比较成熟引擎，不能用自研通用调度平台掩盖缺口。

不新增旧运行格式兼容层或迁移。首批恢复只承诺同一受支持应用版本内的进程重启；跨不兼容版本明确拒绝，并可通过现有项目采纳成果新建事项，不能把新事项称为恢复了原 run。

## 4. 持续改进工作线

| 能力 | 已有 | 下一项完成依据 |
| --- | --- | --- |
| 可信观察与独立评价 | 待验证候选、可搬移证据包、清单复核、批次分母 | 固定任务族、独立检查与错误身份；获得真实问题轨迹，缺样本时如实报告 |
| 单项局部改进 | 固定重试等执行规则；尚无证据驱动的比较结论 | 针对已观察问题比较固定策略与一项有界调整，质量不降并报告额外成本 |
| 跨任务经验与记忆 | 候选仅保存，不自动注入 | 候选、独立验证、适用检索、限定采用、冲突处理、反例与停用贯通 |
| 综合比较 | 尚无可比较的控制和经验处理组 | 在未见任务上比较固定基线、仅控制、仅经验、组合方案 |

语义与关系查询服务于具体问题：“这条经验由哪些经历支持”“要求变化后哪些经验需要重验”。已有存储能满足时不新增图数据库或向量库。相似文本不能直接证明同一问题或同一根因。

学习完成要演示“重复问题 → 候选 → 独立验证 → 未见任务采用 → 反例 → 停用”，同时保留失败、无效和缺失结果。训练与校准材料不得混入未见评价。

这条工作线不阻塞通用工具、恢复和初步并行。它是系统自动采用经验及第四阶段自主演化的前置。研发者手写技能依赖稳定过程和独立比较证据，不再机械依赖旧“Stage 2 2.3”编号。

## 5. 后续持续运行与系统演化

Stage 3 后续继续交付技能、部门内部协作、扩展与嵌入接口、运维职责，并做一次真实外部项目的组合验收。发布、告警、修复和恢复验证必须围绕实际交付物与运行环境；不因增加一个“运维部门”就视为闭环。

Stage 4 分三种责任：运行提供事实；演化模块提出组织、协议或日常规则候选；独立评价决定是否在限定范围采用。候选不能自行批准，用户目标和授权边界不由被评系统修改。

Stage 4 完成条件：
- 一类组织/协议变化和一类日常规则变化贯通证据、候选、隔离比较、独立评价、采用、观察与撤销。
- 使用未见任务比较原组织、研发者静态改进和系统候选，收益包含额外协调与维护成本。
- 失败候选不生效；采用后的反例能停止新增使用、处理在途工作并保留恢复依据。
- 规则变化能追踪对经验、技能及事项的影响，不默认旧经验继续适用。

开放性研究仍是独立研究方向；可信观察之后才能开展有解释力的实验。模型权重更新保持可选，不是主线阶段的必做项。
