Stage 3 编号保留。3.0A 文档统一已有；新增 2.7 先交付，随后在新 Provider 基线上完成 3.0B 回归和中等压力真实验收。同一冻结版本的相同检查证据可以引用，不机械重复；计划写完不能标为验收通过。

1. **Provider 补充阶段**：先完成 2.7，所有模型入口通过统一模块，无配置可启动，并支持 Go API Key 与必要三协议。
2. **统一基线**：分清历史验收版本、当前代码和本轮新测；在 2.7 后的冻结版本上补齐场景、限额、检查与证据。
3. **通用工具**：先完成真实代码项目的搜索、阅读、编辑、本地命令与独立 QA；从一开始记录每次动作及其结果，仍单任务运行。
4. **可靠恢复**：先核对执行所有权和未完成动作，再继续同一 run。恢复命令与 replay 分开，恢复不能重置限额或复活已取消任务。
5. **并行**：恢复验收通过后，先支持不同项目、隔离目录中的独立事项；再处理同一项目的成果竞争与采纳。
6. **语义系统**：3.1 通过后进行，同时依赖 D24 模型管理。把被接纳的材料与部门历史分解为带来源与有效状态的语义单元，参与上下文装配、压缩与跨事项延续，并提供数据流核对；设计单独讨论，草案见 [语义系统设计说明](design/semantic-system.md)。
7. **部门内多角色**：依赖语义系统、D24 模型管理、3.4A 执行槽位与 3.2B 网络工具（探索者查资料）。每个部门由部门经理协调固定角色，见 [部门内多角色设计说明](design/department-roles.md)。

已有 Provider 配置页复用；D22 补无配置启动、重载与页面凭据，D23 建独立模块并接 OpenCode Go。Go 必需的 Responses、Chat Completions、Messages 前移到 2.7；其他 Provider/订阅和推理设置留在 3.3。完整技能、MCP、扩展平台、运维均有后续位置。

## 3. 跨阶段架构与约束

| 层 | 责任 | 边界 |
| --- | --- | --- |
| 用户与观察层 | Web / CLI / API 提交明确命令，呈现任务、动作与恢复事实 | 查询和 SSE 重连不触发任务继续；用户可以看清待核实动作 |
| 业务引擎层 | 项目采纳与事项责任；run 的合同、部门交接、工具准入、QA、停止、恢复；部门内的角色任务与部门账本；语义整理与语义视图 | QA 放行与项目采纳分开；调度不代替部门决定；部门经理与语义整理只提交提案，由主机校验后写入 |
| 基础能力层 | 模型单次调用、工具执行、工作区、SQLite 事件与工件、Git、进程管理、语义记录（事件的投影） | 工具只回报事实；单次调用不自行决定重试、恢复或交接 |

沿用现有三层，不为新能力建立第二套事件事实源。只在工具执行、恢复协调和项目调度的真实边界提取职责，不预先拆服务，也不先重写整个 Orchestrator。

继续遵守 [D09](requirements/execution-limits.md)：按部门激活次数、模型步骤、单次超时控制执行，重试和压缩计入已有额度；Provider 用量及费用只读记录，未知保持未知。恢复不清零；并行新增执行槽位控制。本次不引入 token / 费用硬预算、额度预留系统或通用预算平台。

成熟依据沿用 [组织与持续运行研究](research/organization-runtime-evolution.md) 对 OMP、Temporal、LangGraph 的审查。现有 SQLite、Python 标准库、OpenAI SDK 和 HTTPX 先满足单机边界；不预先引入工作流服务。若故障实验说明现有实现无法承担要求，再按同一矩阵比较成熟引擎，不能用自研通用调度平台掩盖缺口。

不新增旧运行格式兼容层或迁移。首批恢复只承诺同一受支持应用版本内的进程重启；跨不兼容版本明确拒绝，并可通过现有项目采纳成果新建事项，不能把新事项称为恢复了原 run。

## 4. 持续改进工作线

| 能力 | 已有 | 下一项完成依据 |
| --- | --- | --- |
| 可信观察与独立评价 | 待验证候选、可搬移证据包、清单复核、批次分母 | 固定任务族、独立检查与错误身份；获得真实问题轨迹，缺样本时如实报告 |
| 单项局部改进 | 固定重试等执行规则；尚无证据驱动的比较结论 | 针对已观察问题比较固定策略与一项有界调整，质量不降并报告额外成本 |
| 项目记忆 | 项目上下文文本随采纳增长，只携带最近一次采纳成果的产品合同 | 由 3.10 语义系统承担：项目内带来源的语义单元跨事项延续，替代长期记忆 |
| 跨任务经验 | 候选仅保存，不自动注入 | 候选、独立验证、适用检索、限定采用、冲突处理、反例与停用贯通 |
| 综合比较 | 尚无可比较的控制和经验处理组 | 在未见任务上比较固定基线、仅控制、仅经验、组合方案 |

语义与关系查询服务于具体问题：“这条经验由哪些经历支持”“要求变化后哪些经验需要重验”。已有存储能满足时不新增图数据库或向量库。相似文本不能直接证明同一问题或同一根因。项目内的语义单元与关系由 3.10 语义系统维护，检索方式在语义系统的单独讨论中确定。

学习完成要演示“重复问题 → 候选 → 独立验证 → 未见任务采用 → 反例 → 停用”，同时保留失败、无效和缺失结果。训练与校准材料不得混入未见评价。

这条工作线不阻塞通用工具、恢复和初步并行。它是系统自动采用经验及第四阶段自主演化的前置。研发者手写技能依赖稳定过程和独立比较证据，不再机械依赖旧“Stage 2 2.3”编号。

## 5. 后续持续运行与系统演化

Stage 3 后续继续交付语义系统、部门内多角色、技能、扩展与嵌入接口、运维职责，并做一次真实外部项目的组合验收。发布、告警、修复和恢复验证必须围绕实际交付物与运行环境；不因增加一个“运维部门”就视为闭环。

Stage 4 分三种责任：运行提供事实；演化模块提出组织、协议或日常规则候选；独立评价决定是否在限定范围采用。候选不能自行批准，用户目标和授权边界不由被评系统修改。

Stage 4 完成条件：
- 一类组织/协议变化和一类日常规则变化贯通证据、候选、隔离比较、独立评价、采用、观察与撤销。
- 使用未见任务比较原组织、研发者静态改进和系统候选，收益包含额外协调与维护成本。
- 失败候选不生效；采用后的反例能停止新增使用、处理在途工作并保留恢复依据。
- 规则变化能追踪对经验、技能及事项的影响，不默认旧经验继续适用。

开放性研究仍是独立研究方向；可信观察之后才能开展有解释力的实验。模型权重更新保持可选，不是主线阶段的必做项。
