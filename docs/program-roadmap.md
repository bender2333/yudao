# Yudao 总体路线图

更新：2026-09-28。本文是当前阶段定义与依赖的唯一入口。最新调整（2026-09-28）：用户确认 Yudao 在可以预见的时间内只有一个人使用，会部署到多台电脑与树莓派一类的板子上；成功标准是能独立高质量交付，以及能长时间自我运行并自我修复（修复 Yudao 交付的软件）。据此阶段按执行顺序重新编号：Stage 3 增加 3.2C 执行环境服务（本机容器与远程执行代理，[ADR-0018](adr/0018-single-control-host-remote-execution.md)），删除 3.4B；运维部门与长时间运行提前为 Stage 4；原 Stage 4 改为 Stage 5；元观察、系统演化与跨任务经验合为最后的 Stage 6，暂时不做；原分布式部署阶段中实际需要的远程执行并入 3.2C，控制核心主备与服务端数据库删除，多个控制核心实例作为扩展途径写在 ADR-0018。与单个 agent 的对照实验（[D32](requirements/comparison-experiment.md)）在 3.9 第一次执行。本次更新是设计，不表示新增运行能力已实现。

长期架构按[总体架构](design/architecture/overall-architecture.md)与 ADR-0010 至 ADR-0018 确定。能力和证据状态见 [当前验收基线](current-baseline.md)；进行中的工作见 [Stage 3 计划](stage-3-plan.md) 与 GitHub Issues；模型管理的已确认设计见 [模型管理设计说明](design/model-management.md)。历史报告保留原编号、版本和结果，不再作为新的执行入口。

2. **用户决定**（[#49](https://github.com/bender2333/yudao/issues/49)）：所有等待用户的事项使用同一种机制（[总体架构](design/architecture/overall-architecture.md)第 7.4 节），第一种是模型引用无法使用时的待恢复；3.1 的核实未知动作与 Stage 4 运维清单以外的动作按同一机制加入。
3. **调用目标每次请求解析**（[#45](https://github.com/bender2333/yudao/issues/45)）：[ADR-0005](adr/0005-resolve-call-target-per-request.md) 的部分提前到 3.1 之前；控制核心不持有明文凭据，进程重启后按当时的设置与凭据来源继续。
4. **3.1 可靠恢复**：先核对执行权和未完成动作，再继续同一 run。Yudao 启动时自动继续所有中断的 run，只有结果未知的外部动作通过用户决定交给用户。恢复与 replay 分开，恢复不能重置限额或复活已取消任务。进行中的角色任务由步骤驱动从已提交的状态重新装配后继续。执行权在写入口与领域写入一起核对（[ADR-0012](adr/0012-single-control-core-scalable-execution.md)、[ADR-0018](adr/0018-single-control-host-remote-execution.md)）。
5. **3.2C 执行环境服务**（[D29](requirements/remote-execution.md)、[ADR-0018](adr/0018-single-control-host-remote-execution.md)）：执行环境的合同经过 HTTP 加 JSON，提供本机容器与远程执行代理两种新实现；用户在项目中登记机器。依赖 3.1 的动作核实与 #110。排在 3.2B 之前，外部内容进入模型输入之前，任意代码已经可以隔离运行。
6. **3.4A 不同项目并行**：恢复验收通过后，不同项目、隔离目录中的事项并行执行，执行槽位控制并发数量。同一项目的事项按优先级排队，一次只进行一个。
7. **3.2B 网络与 MCP、3.7 扩展接口**：每个新工具单独验收。
8. **3.9 组合验收与对照实验**：在真实外部项目上对 Stage 3 的各项能力逐项给出结论；第一次执行与 OpenCode 的对照实验（[D32](requirements/comparison-experiment.md)）。

已有 Provider 配置页复用；其他 Provider/订阅和推理设置留在 3.3，按用户明确的服务推进。

## 3. 跨阶段架构与约束

分层、各层的职责与边界、长期决定、合同与使用的技术见[总体架构：职责分层](design/architecture/overall-architecture.md)：客户端、接口层、应用层、控制核心（流程编排、步骤驱动、上下文装配、裁决规则、写入口、事件日志）、定义、知识层、观察层、观察者、执行层（Provider、执行环境、外包 agent 的运行容器）。各阶段的新能力都放进这个结构，不建立第二套事件事实源。

部署形态按 [ADR-0018](adr/0018-single-control-host-remote-execution.md)：控制核心、事件日志、工件存储、Provider 模块与观察者在一台控制主机上运行，事件日志使用 SQLite；执行环境可以是本机进程、本机容器或远程机器上的执行代理。[ADR-0007](adr/0007-boundaries-for-distributed-deployment.md) 的边界作为执行环境服务的合同继续遵守；同时遵守 [ADR-0010](adr/0010-control-core-drives-role-steps.md) 至 [ADR-0015](adr/0015-desktop-client-and-http-contracts.md)：每次模型请求在控制核心装配；控制核心在一个异步事件循环中运行；控制核心持有执行权；一份事件日志与唯一写入口；组织、角色、动作、本体与规则作为带版本的定义；桌面客户端、FastAPI 接口层，服务之间使用 HTTP 加 JSON。

继续遵守 [D09](requirements/execution-limits.md)：运行时间上限是主要的收敛保证，部门激活次数与模型步数的上限保留但默认值放开，单次请求有超时，重试和压缩计入已有额度；等待模型服务恢复的时间不计入运行时间上限；Provider 用量及费用只读记录，未知保持未知。恢复不清零；并行新增执行槽位控制。不引入 token / 费用硬预算、额度预留系统或通用预算平台。

不引入外部工作流引擎（[ADR-0012](adr/0012-single-control-core-scalable-execution.md)）：控制核心本身就是按事件重放的状态机，会话可以丢弃，恢复时从已提交的状态重新装配。使用 SQLite、官方 SDK 与 HTTPX。

不新增旧运行格式兼容层或迁移。恢复只承诺同一受支持应用版本内的进程重启；跨不兼容版本明确拒绝，并可通过现有项目采纳成果新建事项，不能把新事项称为恢复了原 run。

## 4. 持续改进工作线

| 能力 | 已有 | 下一项完成依据 |
| --- | --- | --- |
| 可信观察与独立评价 | 待验证候选、可搬移证据包、清单复核、批次分母 | 固定任务族、独立检查与错误身份；D32 的任务集与隐藏检查作为固定任务族 |
| 单项局部改进 | 固定重试等执行规则；尚无证据驱动的比较结论 | 针对已观察问题比较固定策略与一项有界调整，质量不降并报告额外成本 |
| 项目记忆 | 项目上下文文本随采纳增长，只携带最近一次采纳成果的产品合同 | 由 Stage 5 语义系统承担：项目内的轨迹与图谱跨事项延续，替代长期记忆 |
| 跨任务经验 | 候选仅保存，不自动注入 | 随 Stage 6 进行：候选、独立验证、适用检索、限定采用、冲突处理、反例与停用贯通 |
| 综合比较 | D32 与单个 agent 的对照实验在 3.9 第一次执行 | 在未见任务上比较固定基线、仅控制、仅经验、组合方案 |

语义与关系查询服务于具体问题：“这条经验由哪些经历支持”“要求变化后哪些经验需要重验”。已有存储能满足时不新增图数据库或向量库。相似文本不能直接证明同一问题或同一根因。项目内的轨迹与图谱由 Stage 5 语义系统维护，作为事件的投影存放在现有 SQLite 中，查询只用结构条件与全文检索，不使用向量检索（[D25](requirements/semantic-system.md)）。

学习完成要演示“重复问题 → 候选 → 独立验证 → 未见任务采用 → 反例 → 停用”，同时保留失败、无效和缺失结果。训练与校准材料不得混入未见评价。

### 5.1 Stage 4：运维部门与长时间运行

依赖 3.1、3.2C 与用户决定（#49）。进入本阶段时，同步修改 CLAUDE.md、AGENTS.md 与 README 的项目表述，加入运维部门。

**运维部门**（[D27](requirements/operations-department.md)，并入原 3.8）

- 负责交付物（用户项目的软件）的部署、运行观察、性能与故障处理。生命周期跟随项目：项目采纳交付物之后接手，长期存在。按与产品、工程、质检相同的单循环形态建设。
- 观察交付软件的日志、状态与使用者的交互日志。发现的问题作为修复事项自动进入「产品 → 工程 → 质检」流程；用户提出的新要求是另一个来源。同一项目一次只进行一个事项，修复事项排在前面。
- 用户登记运行环境时批准一份常设授权清单：部署质检放行的交付快照、回滚到上一个放行版本、重启服务、读取日志与运行数据。清单以内的动作由运维直接执行并记录，清单以外的动作通过用户决定交给用户。紧急故障时先回滚恢复服务，再排队修复。
- 运维不修改功能要求，也不代替质检放行。平台与交付物两类运行责任分开，发布成功与运维接收分别记录，见 [运行责任样例](stage-3/operations-responsibility-sample.md)。
- 流转规则随运维部门改为由定义驱动：阶段按部门与事项种类定义，状态机读取定义。

**长时间运行**

- Yudao 由操作系统的服务管理在崩溃后重新启动，启动时按 3.1 自动继续中断的 run。
- 模型服务中断（[D17](requirements/provider-retries.md)）：按 D17 重试用完以后仍然是连接失败、服务端错误、过载或限流，以及凭据失效、证书校验失败时，run 暂停并进入「等待模型服务」，按间隔重试，服务恢复后自动继续；进入等待时通知用户一次，用户可以取消；等待时间不计入运行时间上限。请求内容错误与上下文过长不进入等待，按原有规则处理。

完成依据：一个真实软件在登记的树莓派上运行，在约定的观察窗口内，运维从可观测数据中发现故障，修复事项经过产品、工程、质检，运维重新部署并确认恢复，全程不需要人参与；观察窗口内的一次 Yudao 进程中断与一次模型服务中断都自动接续。增加运维部门本身不等于具备运行能力。

### 5.2 Stage 5：部门内协作、上下文与界面

排在 Stage 4 之后，依赖 3.1、3.4A、3.2B 与 D24 模型管理（其中调用目标每次请求解析由 #45 在 3.1 之前完成；其余部分是父工单 #83 与子工单 #84 至 #96）。本阶段内各项工作的先后由 D32 对照实验的结果决定。

- **语义系统**（[D25](requirements/semantic-system.md)，[语义系统设计说明](design/semantic-system.md)）：为 Agent 整理轨迹与图谱，并据此组装上下文，承担项目记忆；整理出的知识图谱与语义工程供 Stage 6 系统演化使用。分两部分：
  - **整理**：轨迹记录事项的工作过程，分事项、交接、计划条目、角色任务、尝试五层；图谱由证据、事实、知识、决定、要求、实体、推测七类内容及其关系构成，在其上归纳教训、洞见与画像，其中教训与洞见由教训发现模块找出（待设计）。角色在工作中随时记录，主机按本体校验后写入；记录事实时由 JEV 核对证据是否支持陈述。轨迹与图谱都是事件的投影，重放可以重建。
  - **上下文组装**：每次请求由固定的栏目组成，按常驻栏目、目录、按需取得、接触时附加四种方式放入内容，变更与新到达的输入作为通知追加进历史；各角色按分工得到不同的上下文；组装不调用模型，放入的内容与原因由上下文清单记录。请求长度受工作上限控制，达到压缩阈值时先清理旧工具结果，再压缩，压缩后由轨迹与图谱代替被移出的历史。栏目按变化频率从少到多排列，历史只追加，使提示缓存可以复用。
  - 完成依据：同一项目连续多个事项中，被修改的要求以取代关系出现，被取代的要求不作为有效内容进入请求；数据流核对列出缺失的覆盖；重放事件重建的轨迹与图谱与原记录一致；详细验收见设计说明第 16 节。
- **决策模型接入**：JEV 的 systemone 接口作为 Provider 模块的新协议接入，ADR-0001、ADR-0004 的结构不变。本阶段用于语义系统的证据核对，只核对外部文档与需要解读的运行输出。核对用本地中文样本选取阈值，再用另一批样本复核，样本与标注方式见 D25 上下文组装专题第 16 条；校准通过之前，核对结果只记录，不显示给模型，也不改变内容的状态。JEV 的能力边界见 [JEV 决策模型调研](research/jev-decision-model.md)。
- **部门内多角色**：每个部门围绕中心角色协作，中心角色负责规划与判断，经理负责对外沟通，探索者、主程与审查者是中心角色的工具，见 [部门内多角色设计说明](design/department-roles.md)（[D26](requirements/department-roles.md)）。对产品、工程、质检、运维四个部门一起引入。依赖语义系统、3.4A 执行槽位与 3.2B 网络工具（探索者查资料）；决定见 [ADR-0016](adr/0016-center-role-collaboration.md)、[ADR-0017](adr/0017-role-settings-override-department.md)，工单为父工单 #50 与子工单 #51 至 #65。完成依据：在 D32 的任务集上与单循环部门对照，交付质量不低于单循环，并报告模型请求数、用量与耗时；设计第 16 节的反例通过。
- **技能**：注册、适用性、执行与展开、异常出口与比较。稳定过程有独立证据，封装后质量不降，收益覆盖维护成本。
- **可观测性**：Yudao 自身的观察视图，包括部门内外的运行过程、角色任务、上下文来源与用量，见 [可观测性详细设计](research/observability-design.md)；数据来自应用层的查询与事件流。
- **应用层、接口层与桌面客户端**：按 [ADR-0015](adr/0015-desktop-client-and-http-contracts.md) 与[应用层与接口层设计说明](design/app-and-interface.md)建立命令、查询、事件流、能力清单与认证（父工单 #70），桌面客户端按原型 v7 实现（父工单 #71）；桌面客户端的当前档页面通过验收以后删除旧 Web 控制台（#78）。

### 5.3 Stage 6：受治理的系统演化

用户 2026-09-28 决定暂时不做 Yudao 修改自己的组织与规则。本阶段排在最后，进入时细化需求与设计。

- **元观察与规则检查部门**（[D28](requirements/meta-observer.md)）：只做流程审查与观察，结果用于系统演化。观察部门之间的流转事实，按规则审查过程，报告不符合项；使用 JEV 决策模型在控制层事先规定的判定点上做带有置信度的判断，判定点用带有标注的中文流转样本校准通过后，控制层才按判断结果自动推进。质检放行、产品取舍、规则修改不交给它；它不读取部门私有上下文。在组织上是一个部门，运行时是一个观察者加判定点，使用 3.7 的只读观察接口。
- **系统演化**：运行提供事实；演化模块提出组织、协议或日常规则候选；独立评价决定是否在限定范围采用。候选不能自行批准，用户目标和授权边界不由被评系统修改。演化使用元观察的审查与观察记录，以及语义系统整理的知识图谱；用于最终判断的隐藏评价材料不进入被评系统可以读取的知识图谱。
- **跨任务经验**：持续改进工作线（第 4 节）中的跨任务经验在本阶段贯通。

完成条件：
- 一类组织/协议变化和一类日常规则变化贯通证据、候选、隔离比较、独立评价、采用、观察与撤销。
- 使用未见任务比较原组织、研发者静态改进和系统候选，收益包含额外协调与维护成本。
- 失败候选不生效；采用后的反例能停止新增使用、处理在途工作并保留恢复依据。
- 规则变化能追踪对经验、技能及事项的影响，不默认旧经验继续适用。

开放性研究仍是独立研究方向；可信观察之后才能开展有解释力的实验。模型权重更新保持可选，不是主线阶段的必做项。

### 5.4 愿景：Yudao 负责自己的运维

Yudao 平台由自己的运维部门负责运维。自举难度大，平台运维目前由人负责。以后可以由一个 Yudao 部署中的运维部门负责另一个部署，健康检查保留一条不依赖被运维平台的外部途径（[组织与持续运行研究](research/organization-runtime-evolution.md)第 7.2 节）。

资源调度与并发的扩展途径见 [ADR-0018](adr/0018-single-control-host-remote-execution.md)：执行能力不够时增加执行环境，模型服务限流时增加连接，一台控制主机容纳不下时按项目分成多个控制核心实例，各有触发条件。
