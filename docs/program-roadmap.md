3. **通用工具**：先完成真实代码项目的搜索、阅读、编辑、本地命令与独立 QA；从一开始记录每次动作及其结果，仍单任务运行。
4. **可靠恢复**：先核对执行所有权和未完成动作，再继续同一 run。恢复命令与 replay 分开，恢复不能重置限额或复活已取消任务。执行所有权与激活接口遵守 [ADR-0007](adr/0007-boundaries-for-distributed-deployment.md) 第 1、3 条。
5. **并行**：恢复验收通过后，先支持不同项目、隔离目录中的独立事项；再处理同一项目的成果竞争与采纳。
6. **网络、MCP 与扩展接口**：恢复通过后接入，每个新工具单独验收。3.7 提供的只读观察接口供 Stage 5 的元观察与规则检查部门使用。
7. **组合验收**：3.9 在真实外部项目上对 Stage 3 的各项能力逐项给出结论。

## 3. 跨阶段架构与约束

| 层 | 责任 | 边界 |
| --- | --- | --- |
| 用户与观察层 | Web / CLI / API 提交明确命令，呈现任务、动作、恢复、运行与流程审查事实 | 通过命令入口提交、通过查询接口读取；查询和 SSE 重连不触发任务继续；用户可以看清待核实动作 |
| 业务引擎层 | 项目采纳与事项责任；run 的合同、部门交接、工具准入、QA、停止、恢复；部门内的角色任务与部门账本；语义整理与语义视图；运维部门（生命周期跟随项目）；元观察与规则检查部门（流程审查与观察） | QA 放行与项目采纳分开；调度不代替部门决定；部门经理、语义整理与元观察部门只提交提案或审查结果，由主机校验后写入；判定点上的推进由控制层按事先规定的规则执行；运维的外部动作逐项授权 |
| 基础能力层 | 生成模型与决策模型的单次调用、工具执行（含部署与运行观察工具）、工作区、SQLite 事件与工件、Git、进程管理、语义记录（事件的投影） | 工具只回报事实；单次调用不自行决定重试、恢复或交接；决策模型只给出带有概率的判断 |

沿用现有三层，不为新能力建立第二套事件事实源。服务拆分在 Stage 6 进行；此前各阶段遵守 [ADR-0007](adr/0007-boundaries-for-distributed-deployment.md) 的六条边界：部门与控制层只通过消息往来；继续工作所需的信息全部持久化；执行所有权每次取得都有新的身份，并在写入时核对；部门之间只传递封存快照；界面通过查询接口读取；模型调用只通过 Provider 模块。只在工具执行、恢复协调和项目调度的真实边界提取职责，不先重写整个 Orchestrator。

继续遵守 [D09](requirements/execution-limits.md)：按部门激活次数、模型步骤、单次超时控制执行，重试和压缩计入已有额度；Provider 用量及费用只读记录，未知保持未知。恢复不清零；并行新增执行槽位控制。本次不引入 token / 费用硬预算、额度预留系统或通用预算平台。

成熟依据沿用 [组织与持续运行研究](research/organization-runtime-evolution.md) 对 OMP、Temporal、LangGraph 的审查。现有 SQLite、Python 标准库、OpenAI SDK 和 HTTPX 先满足单机边界；不预先引入工作流服务。若故障实验说明现有实现无法承担要求，再按同一矩阵比较成熟引擎，不能用自研通用调度平台掩盖缺口。Stage 6 的运行方式同样在该阶段按这一矩阵比较后决定。

不新增旧运行格式兼容层或迁移。首批恢复只承诺同一受支持应用版本内的进程重启；跨不兼容版本明确拒绝，并可通过现有项目采纳成果新建事项，不能把新事项称为恢复了原 run。

## 4. 持续改进工作线

| 能力 | 已有 | 下一项完成依据 |
| --- | --- | --- |
| 可信观察与独立评价 | 待验证候选、可搬移证据包、清单复核、批次分母 | 固定任务族、独立检查与错误身份；获得真实问题轨迹，缺样本时如实报告 |
| 单项局部改进 | 固定重试等执行规则；尚无证据驱动的比较结论 | 针对已观察问题比较固定策略与一项有界调整，质量不降并报告额外成本 |
| 项目记忆 | 项目上下文文本随采纳增长，只携带最近一次采纳成果的产品合同 | 由 Stage 4 语义系统承担：项目内带来源的语义单元跨事项延续，替代长期记忆 |
| 跨任务经验 | 候选仅保存，不自动注入 | 候选、独立验证、适用检索、限定采用、冲突处理、反例与停用贯通 |
| 综合比较 | 尚无可比较的控制和经验处理组 | 在未见任务上比较固定基线、仅控制、仅经验、组合方案 |

语义与关系查询服务于具体问题：“这条经验由哪些经历支持”“要求变化后哪些经验需要重验”。已有存储能满足时不新增图数据库或向量库。相似文本不能直接证明同一问题或同一根因。项目内的语义单元与关系由 Stage 4 语义系统维护；语义系统同时整理知识图谱与语义工程，供 Stage 7 系统演化使用。检索与存储方式在语义系统的单独讨论中确定。

学习完成要演示“重复问题 → 候选 → 独立验证 → 未见任务采用 → 反例 → 停用”，同时保留失败、无效和缺失结果。训练与校准材料不得混入未见评价。

这条工作线不阻塞通用工具、恢复和初步并行。它是系统自动采用经验及 Stage 7 系统演化的前置。研发者手写技能依赖稳定过程和独立比较证据，不再机械依赖旧“Stage 2 2.3”编号。

### 5.1 Stage 4：部门内协作、上下文与界面

依赖 3.1、3.4A、3.2B 与 D24 模型管理。

- **语义系统**：关键环节，承担两项职责。一是整理事实与事件，随时进行语义压缩与分发，为各部门与角色装配上下文，并承担项目记忆；二是整理知识图谱与语义工程，供 Stage 7 系统演化使用。草案见 [语义系统设计说明](design/semantic-system.md)，第二项职责尚未写入草案；设计单独讨论（[D25](requirements/semantic-system.md)）。已有的完成依据草案：同一项目连续多个事项中，被修改的要求以更替链出现，旧要求不作为有效内容进入请求；数据流核对列出缺失的覆盖；重放事件重建的语义记录与原记录一致；具体依据在单独讨论后确定。
- **部门内多角色**：每个部门由部门经理协调固定角色，见 [部门内多角色设计说明](design/department-roles.md)（[D26](requirements/department-roles.md)）。依赖语义系统、3.4A 执行槽位与 3.2B 网络工具（探索者查资料）。完成依据：另立任务族，与现有单循环部门在同一组任务上对照，交付质量不低于单循环，并报告模型请求数、用量与耗时；设计第 14 节的反例通过。
- **技能**：注册、适用性、执行与展开、异常出口与比较。稳定过程有独立证据，封装后质量不降，收益覆盖维护成本。
- **可观测性**：Yudao 自身的观察视图，包括部门内外的运行过程、角色任务、上下文来源与用量，见 [可观测性详细设计](research/observability-design.md)。
- **前端优化**：Web 工作台随上述能力扩展；界面的直接读取改为查询接口（ADR-0007 第 5 条）。

跨任务经验仍属于持续改进工作线（第 4 节）。

### 5.2 Stage 5：运维部门与元观察

**运维部门**（[D27](requirements/operations-department.md)，并入原 3.8）

- 负责交付物（用户项目的软件）的部署、运行观察、性能与故障处理。生命周期跟随项目：项目采纳交付物之后接手，长期存在。
- 运行中发现的问题作为新事项进入「产品 → 工程 → 质检」流程。事项进行中，各部门可以向运维询问，运维也可以询问各部门；常见往来是产品（取舍与运行目标）和工程（部署方式与修复）。
- 产品在 PRD 中确定运行目标，运维测量并报告达成情况；工程随交付提供部署说明、健康检查与运行数据输出。
- 部署、回滚、重启都是对真实环境的外部动作，逐项授权。运维不修改功能要求，也不代替质检放行。平台与交付物两类运行责任分开，发布成功与运维接收分别记录，见 [运行责任样例](stage-3/operations-responsibility-sample.md)。
- 依赖 Stage 3 的工具与恢复（结果未知的外部动作）、环境授权与一个真实的发布对象，按 Stage 4 的部门内多角色形态建设。完成依据：一个真实交付物在明确的环境与约定的观察窗口内，完成从故障发现、修复、发布到恢复确认的全过程。增加运维部门本身不等于具备运行能力。

**元观察与规则检查部门**（[D28](requirements/meta-observer.md)）

- 只做流程审查与观察，结果用于 Stage 7 系统演化。观察部门之间的流转事实：交接、询问与回答、缺陷、放行、返工的次数与间隔；按规则审查过程，报告不符合项。质检检查交付物是否符合 PRD，两者分开。
- 使用 JEV 决策模型进行带有置信度的局部判断；发现报告与升级后的判断使用 LLM；循环整体是否有进展由确定的统计与 LLM 分析，不交给 JEV。JEV 的能力边界见 [JEV 决策模型调研](research/jev-decision-model.md)。
- 判定点由控制层事先规定，写明问题、参照材料与三种结果的去向：高置信度通过则推进；高置信度不通过则退回或记录发现；置信度不足则交给 LLM 判断或由用户决定。判定点使用带有标注的中文流转样本选取阈值、再使用另一批样本复核之后，控制层才按审查结果自动推进；未通过的判定点只记录。
- 每次判定记录状态、问题、选项顺序、模型版本、概率与置信度，重放使用记录的结果，并定期抽样复核。
- 质检放行、产品取舍、规则修改不交给它。它不读取部门私有上下文，部门也不能向它分派工作。
- 依赖 3.7 的只读观察接口与带有标注的流转样本。

**决策模型接入**：JEV 的接口作为 Provider 模块的新协议接入，ADR-0001、ADR-0004 的结构不变；准入以判定点为单位，依靠样本校准。

进入 Stage 5 时，同步修改 CLAUDE.md、AGENTS.md 与 README 的项目表述，加入运维部门、元观察与规则检查部门。在此之前，这三份文件只描述当前的三个部门，避免影响当前的工作。

### 5.3 Stage 6：分布式部署

控制层、各部门、元观察与规则检查部门、Provider 与存储部署到不同的服务器和平台上（[D29](requirements/distributed-deployment.md)）。收益：部门靠近所需的环境与权限，凭据保存在各自的环境里；部门在独立容器中执行，隔离任意代码；同一交付快照在多种平台上并行检查；多个事项分散到多台机器。

从现在起遵守 [ADR-0007](adr/0007-boundaries-for-distributed-deployment.md) 的六条边界，本阶段只需把模块移动到不同的机器并加入网络传输，不重写核心。执行所有权在本阶段加入期限与续期。运行方式（是否采用 Temporal 等成熟引擎、事件库使用哪种数据库）在本阶段按故障场景与总成本比较后决定。

依赖 3.1、3.4 与 Stage 5 的完整部门集合。完成依据在进入本阶段时确定，至少包括：任一节点故障后，同一 run 由新的执行者接续，旧执行者的迟到结果被拒收，领域状态不重复推进。

### 5.4 Stage 7：受治理的系统演化

Stage 7 分三种责任：运行提供事实；演化模块提出组织、协议或日常规则候选；独立评价决定是否在限定范围采用。候选不能自行批准，用户目标和授权边界不由被评系统修改。演化使用元观察与规则检查部门的审查与观察记录，以及语义系统整理的知识图谱；用于最终判断的隐藏评价材料不进入被评系统可以读取的知识图谱。

Stage 7 完成条件：
- 一类组织/协议变化和一类日常规则变化贯通证据、候选、隔离比较、独立评价、采用、观察与撤销。
- 使用未见任务比较原组织、研发者静态改进和系统候选，收益包含额外协调与维护成本。
- 失败候选不生效；采用后的反例能停止新增使用、处理在途工作并保留恢复依据。
- 规则变化能追踪对经验、技能及事项的影响，不默认旧经验继续适用。

开放性研究仍是独立研究方向；可信观察之后才能开展有解释力的实验。模型权重更新保持可选，不是主线阶段的必做项。

### 5.5 愿景：Yudao 负责自己的运维

Yudao 平台由自己的运维部门负责运维。自举难度大，平台运维目前由人负责。Stage 6 之后，一个 Yudao 部署可以由另一个独立部署中的运维部门负责运维，健康检查保留一条不依赖被运维平台的外部途径（[组织与持续运行研究](research/organization-runtime-evolution.md)第 7.2 节）。
