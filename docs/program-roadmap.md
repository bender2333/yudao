路线图只回答一个问题：总图 [architecture.html](architecture.html) 按什么顺序变成真的。总图是正本，路线图上的每一项都是总图上的一个方框、一道缝、一个状态或一环；总图上没有的东西不进路线图，先交总架构师。总体意图见 [D38 系统意图与基础规则](requirements/system-intent.md)：独立高质量交付、长时间自己运行并自己修复、两层自举。能力与证据的现状见[当前验收基线](current-baseline.md)。

## 1. 怎么推进

### 1.1 结构与内容一起长

总图把系统分成两种东西。**固定的结构**：一份事实、写入口与裁决、边界、薄驱动与三道共用的槽位、十三道缝、系统之外的评价、进程之外的看门狗。结构是有限的，建完就定型。**填进结构的内容**：部门与角色的声明、轮转方式（按成果、任务池）、工作单元的大小、装配的减法、动作与工具的种类、模型与判定点、画面（楼、机房、城）、观察者、机器的部署形态。内容是开放的，随运行证据一直加。

不设用户看不到东西的纯骨架阶段。每推进一档用户用得到的能力，顺手把碰到的模块边界收成总图第四节规定的缝：先用薄的一层把已有实现包起来、定下契约与版本，等需要第二种实现时再换槽位。一道缝算立住，要有第二种实现（哪怕只是测试用的）接得上，否则只是改了名字。

### 1.2 三环的纪律

一切改动守总图第二节的三环。

1. **可以整体重写**：路由、装配、执行的实现，模型与执行环境的适配，投影，画面，观察者。守住契约，里面整个重写外面看不出来。
2. **只能向后兼容**：三道槽位的契约、骨架事件、对外的合同、定义的格式。带版本，字段只增，旧文件新版本能读。
3. **只由你批准**：写入口、裁决、边界、薄驱动与插件加载、评价材料、看门狗。系统可以提修改的提案，生效要你批准。

### 1.3 走法与门

**薄片发布、真实反馈。** 每个阶段切成用户能装、能用的发布，每个发布只回答一个真实的问题。暴露的缺陷排到队列最前面；切片的先后与细节按试用反馈调整；认为总图缺了什么或错了，交总架构师先改总图。反馈调整的是走法，不增删总图上的东西。

**门：可迭代状态。** 从建结构走到大规模填内容与自己演化，要逐条核对五条判据：有持续的真实负载、能度量（带噪声范围与费用）、改动便宜且可撤回、看得见（循环停在哪一层、为什么）、锚点受保护。第 5 节写每个阶段结束时五条各到哪里。

### 1.4 里程碑与工单

工单在 GitHub 上分三级：**阶段工单**，一个阶段一张，写阶段结束时用户能做什么与结束时总图；**父工单**，一个桶一张，桶是总图第四节的一道缝或第 3 节的一条道，由 `/to-parents` 从阶段拆出；**子工单**，执行者领取的立缝或切片，由 `/to-children` 从父工单拆出。

**里程碑是发布。** 一个 GitHub 里程碑就是第 1.3 节说的一个薄片发布，只回答一个问题；父工单按它交付的问题放进里程碑。进入一个阶段时建它的里程碑，后面阶段的不先建。每个里程碑一张试用工单，里程碑达到后由用户试用、关闭（CLAUDE.md 工作流程第 7 步）。标题写「阶段几 · 序号 名字」。

## 2. 主干：五个阶段

五个阶段的顺序是依赖：没有诚实的单机闭环，自动继续就是把错误继续下去；没有可靠的自转与看门狗，拆开只是把故障分到多台机器；没有独立评价与可撤回的定义，系统自己演化就会失控。

~~~mermaid
flowchart LR
    P1["阶段一：单机诚实闭环，三道槽位立缝"] --> P2["阶段二：可靠恢复、接入真实项目、独立评价"]
    P2 --> P3["阶段三：常驻自转、运维部门、看门狗兜底"]
    P3 --> P4["阶段四：拆开部署、细粒度协作、产品的城"]
    P4 --> P5["阶段五：受治理的演化（第二层自举）"]
~~~

### 阶段一：单机诚实闭环，三道槽位立缝

**目标**：在一台电脑上，产品、工程、质检围着一份事实用真实模型跑通完整的一轮；顺手立住薄驱动与路由、装配、执行三道槽位的契约；点亮办公楼的画面。

1. **薄驱动与三道槽位**（总图第一、二、四节）
   - 流程编排拆成不认识部门名字的薄驱动，和第一个路由实现（按成果：谁关注的成果有了新版本谁开工）。
   - 装配槽位只读事实与定义，从事实减出这一轮要看的，并入你中途的指导；逼近窗口上限时先清旧的工具结果、再压缩成摘要工件；交给模型的那份与上下文清单记进事实。
   - 执行槽位：每一步先问边界（时间、步数、重试上限），再调模型或发工具请求，自己不保存跨步的状态。
   - 骨架事件（只增）与应用事件分开；裁决只读骨架自己折叠的最小投影；测试用的第二种路由能接上，证明缝是真的。
2. **双环与唯一写入口**（总图第一、三节）
   - 外环九个状态全部走通：等待工作、一轮工作中、询问中（嵌在一轮里的另一轮）、等用户（决定请求停在写入口）、核验中、接纳、返工、排空中、停止。
   - 内环六步：路由与边界、装配、模型、工具与环境、裁决与写入口、投影。
   - 写入先过裁决（U ≠ f）：同一事务里核对执行权与期望版本，按消息身份去重（派发编号随阶段二的重派一起核对）；失败的尝试与未获许可的工具调用记为事件备查，不执行、不进有效历史。
   - 质检在信任链末端：工程交快照后，质检在独立重建的公开树副本上跑主机的检查命令，放行必须绑定当前有效的 PRD、交付树与检查回执。
3. **接口、画面合同与楼**（总图第一、四节；第 4 节步 0）
   - 对外唯一的接口缝：带身份的命令、只读查询、按全局位置续接的事件流；关掉页面循环照跑。
   - 画面缝：翻译层把事件变成带来源回链的元件断言交给画面，播放节奏归画面。点亮办公楼（房间、小人、传送带上的包裹、大厅的决定板）。机房的基础视图不在阶段一的工单里，记在原型 v14 的待办（原型变更记录第 12 条），客户端跟不跟、放哪一步在设计时定。

**结束时总图**：一份事实、你、薄驱动、三道槽位为已建；写入口、路由、装配、执行、模型、投影、接口、画面八道缝立住。**交付验证**：你在网页上给一个真实的小项目下意图，三部门写代码、跑命令、回答一次决定请求、放行交付，画面与回放一致。

### 阶段二：可靠恢复、接入真实项目、独立评价

**目标**：解决单机上进程中断与消息乱序；接入已有的真实代码仓库；扩充网络与浏览器核验的动作；在系统之外建起防作弊的评价；启动第一层自举的试点。

1. **单机可靠恢复与重派**（总图第三、六节硬问题二、三）
   - 进程停了又起：控制核心是按事件重放的状态机，重启丢掉内存里的会话，核对执行权后从已提交的事件自动继续；已用时间与次数跨重启连续累计，不清零、不复活已取消的事项。
   - 结果未知的核实：中断时在途的外部动作按动作合同的核实方法查；查不到从最近的封存快照重新装配执行；自动核实不了的通过决定请求交给你。
   - 重派与迟到：重派先经写入口写事件并把派发编号加一；旧编号迟到交回的结果只记录备查，不接纳。
2. **接入已有仓库与写回**（总图第一节「一份事实」的起点）
   - 产品读已有代码、测试与文档写出描述现有行为的初始 PRD，工程写出现有结构的说明；你确认以后它是之后事项的基准合同。
   - 采纳写回合并事项起点、采纳成果与目标分支三份代码树，冲突即停，核验最终树后生成分支与合并请求。
3. **动作缝扩充：网络、MCP 与质检操作网页**（总图第一、四节）
   - 「模型与工具」加入受控的网络取回、MCP 工具服务与浏览器（页面的可访问性结构加真实截图）。
   - 质检自己打开并操作工程交付的网页，试用记录与截图绑定到交付快照；放行附每条验收条件的检验覆盖比例与开环条件明细。
4. **定义成数据与评价的缝**（总图第二、四、五节）
   - 部门与角色、可见范围、检查时限、单轮上限、停止原因清单收进带版本的定义；界内的参数用命令直接改、随时撤回，不发布代码。
   - 评价在系统之外：评测题、用户视角的说明书与确定性的判分脚本与被测版本分开存放；操作代理照说明书与一句话目标操作真实界面，外部的确定性代码查数据库与文件产物判分；与单个 agent 对照，带噪声范围与费用。
   - 第一层自举试点：已发布的 Yudao 实例接入 Yudao 自己的仓库，完成首批画面与非内核工单的配对验收。

**结束时总图**：产品、工程、质检、独立的证据、界面、裁决与边界、定义、评价为已建，「模型与工具」本机部分已建；验收表三层（内核、缝、真实场景）都在运转。**交付验证**：你的一个真实项目接进来、改一处、关掉再开它接着做；对照报告说明比单个 agent 好多少。

### 阶段三：常驻自转、运维部门、看门狗兜底

**目标**：长时间无人值守运行并自己修复；只写声明加入第四个部门（运维）；建成进程之外两个槽位的看门狗；第一层自举成为日常；点亮机房的运行态。

1. **「加部门只写声明」的第一次验收：运维**（总图第一、二节）
   - 不改薄驱动与控制核心的源码，只加组织定义与角色材料，运维部门关注质检放行的交付与运行环境的日志。
   - 常设授权与故障自愈：你登记运行环境时批准常设授权清单（部署前备份、部署放行的快照、紧急故障先回滚到上一个放行版本、读日志与交互日志）。
   - 运维从日志里发现异常，写带观察证据的故障记录进项目流，自动变成排在最前的修复事项进入产品、工程、质检、运维重新部署的循环；同一故障在观察窗口内连续修复失败到定义的上限，保持回滚状态并发决定请求给你。
2. **进程之外的看门狗与两个槽位**（总图第一、四、五节）
   - 看门狗不依赖 Yudao 的代码，维护 A（稳定）与 B（候选）两个槽位。
   - 排空与切换：升级前先向稳定槽发排空命令（不接新事项，等在途的运行结束）；候选槽旁路启动，看门狗做三层健康检查：存活心跳、金丝雀任务的确定性答题、观察期的业务指标对比；任一不过就切回稳定槽。
   - 外部的报到服务看控制主机断电或断网；模型服务限流或中断时自动等待并恢复接续。
3. **第一层自举成为常态与内核守卫**（总图第二、五节）
   - 内核清单、路径守卫、接口的访问令牌、圈复杂度与变异测试的检查、由上一个已安装版本提供的发布检查。
   - Yudao 自己的日常工单默认交给 Yudao 实例开发，成果以合并请求经现有的审查流程；直接采纳（不经审查流程）要等阶段四有了控制主机以外的执行机器再放开。
4. **机房的运行设备与故障冒烟**（第 4 节步 2）
   - 已交付的软件在机房里是运行中的设备（版本牌、健康灯、备份柜）；运维记故障时设备冒烟，修复的包裹滑进办公楼。

**结束时总图**：第四节「看门狗」的缝从未定到已定；第一节看门狗、运维为已建；第五节第一层自举为已建。**交付验证**：你不在的一周里，一次进程中断与一次模型服务中断都自动接续，一次故障由运维发现、经三部门修复、运维重新部署。

### 阶段四：拆开部署、细粒度协作、产品的城

**目标**：跨出单机；不动骨架接入第二种路由（任务池与可调的工作单元）、部门内多角色与外包角色；建语义图谱、判定点与观察者；建成产品的城。

1. **拆开与四道过网络的缝**（总图第六节与硬问题一）
   - 控制主机只有一份：一份事实、写入口、裁决、边界、薄驱动与模型凭据留在这里，不复制、不用分布式锁（写入口在一个事务里核对版本就是锁）。
   - 执行节点与成员多份：定义里登记其他电脑、开发板或容器；写入口、动作、模型、接口四道缝过网络，多出超时与结果未知。
   - 跨机的工作区从封存快照重建：执行代理可以留温热的依赖与编译缓存，每次激活都从控制主机的封存快照建干净的工作区，不带历史；质检在另一个平台重建副本拿错误独立的回执；不同项目隔离并行。
2. **第二种路由：任务池与工作单元**（总图第一、三、四节）
   - 「路由」的缝下接第二个实现：任务池（发布、认领、完成、打回的有环图）。
   - 粒度是定义里的参数：工作单元设为整份正式成果就是按成果轮转，设为拆出的节点就是小粒度双向流转与并行认领；两种路由共用外环的状态词。
   - 各工作单元独立认领与增量核验，放行门仍由质检拿完整交付快照对照当前有效 PRD 做整份核验。
3. **部门内多角色与外包角色**（总图第一、四节）
   - 外包是执行槽位的新实现：只对有下游独立核验的角色（如工程），经 ACP 接外部代理；每次激活用全新的状态目录与无历史的封存快照，模型调用与工具动作走受控的入口；质检不能外包。
   - 部门内围绕中心角色配经理、探索者、主程、审查者；角色在自己的配额与嵌套深度上限内发起子循环。
4. **语义系统、判定点与观察者**（总图第一、三、四节）
   - 语义系统是事件的投影：五层轨迹（事项、一轮、计划条目、角色任务、尝试）与七类图谱（证据、事实、知识、决定、要求、实体、推测），替代被移出窗口的历史，承担跨事项的项目记忆。
   - 判定点：定义声明的判定点（证据核对、上下文初筛、含糊读法的置信度）接经本地样本校准的小模型；判断先写成事件再被使用，重放直接读事件。
   - 观察者：在系统外按读取范围经接口只读订阅事件，产出统计证据、教训候选与振荡信号，都经写入口以提案提交，没有执行权。
5. **产品的城与指向式的输入**（第 4 节步 3 至 5）
   - 从语义图谱与行为记录投影出城：页面、接口、数据表、模块是建筑与街区，依赖是道路，要求是蓝图，验收条件是检查站，绑定证据后蓝图变成建筑，质检的试用会话是访客。
   - 在城里点一栋建筑直接说话，命令带着实体引用进入对应部门的焦点；可改的规则是可操作的物件，不可改的规则是推不动的门禁与墙。

**结束时总图**：第一节轮转方式（含任务池）、模型与工具（含远程与外包）、观察者为已建；第六节变成图上画的样子；「观察者」的缝已建，写入口、动作、模型、接口四道缝过网络验收。**交付验证**：质检在另一台机器上检查；两个项目并行；一个事项由任务池与外包角色承接并整份放行。

### 阶段五：受治理的演化（第二层自举）

**目标**：打通总图第五节的第二层：系统根据运行证据、观察者的信号与图谱提出组织定义、流转规则与工作单元降解的候选，经独立评价限定采用，可以撤回。

1. **振荡信号进边界与元观察**（总图第一、四、五节）
   - 观察者写的振荡信号（指明事项、分支与依据的事件）经写入口进入边界核对，内核按定义停下受影响的分支并转为决定请求交给你。
   - 元观察按读取范围审查部门之间的流转是否合规矩，结合校准过的判定点自动推进或报告偏离。
2. **第二层自举的闭环：提出、独立评价、限定采用、对比与撤回**（总图第二、五节）
   - 交叉演进：谁的定义与角色材料不由谁自己改。先开放界内参数的候选（可见范围、验证密度、配额），稳定以后开放结构性定义的候选（角色分工、关注的成果、轮转方式）。
   - 结构校验与隔离对照：采纳前裁决强制校验权威关系无环、信任链末端有独立证据、目标能追溯到你的意图；在系统外的未见评测集上与基线隔离对照。
   - 限定采用与撤回：通过评价并经你批准的候选只在定义声明的范围（项目类别或事项的比例）内生效；事项建立时冻结定义版本，所以能直接对比限定采用版与基线版；劣化或反例立即撤回那个定义版本，不重启、不回滚代码。
3. **稳定工作单元的确定性降解**（总图第五节）
   - 观察者从轨迹里认出某类工作单元连续成功、零返工，提降解提案：处理者从模型换成确定性的程序，契约与写入口核验不变，走限定采用上线。
4. **在世界里铺传送带**（第 4 节步 6）
   - 开放组织拓扑的编辑：在楼里拖房间与传送带的连接，直接生成组织定义的候选，经独立评价与限定采用生效。

**结束时总图**：六节全部方框已建；两层自举与三层验收形成闭环。

## 3. 十条内容道

结构建好以后，具体能力的扩充都归入十条并行的道。每条道对应总图上一个槽位、一道缝或一类定义；任何新内容按同一规矩进入：写定义或槽位实现 → 过缝层的契约测试 → 真实场景计分 → 限定采用 → 可撤回。道上「已规划」的项目是总图写明的，都要建；「未知落点」是给没想到的东西留的位置。

| 道 | 总图位置 | 已规划的项目（按先后） | 未知落点 |
| --- | --- | --- | --- |
| 01 部门 | 第一节产品、工程、质检、运维、下一个部门 | 三部门闭环 → 只写声明加运维 → 元观察 | 任何新职能的部门，只写声明 |
| 02 角色与外包 | 第二节「定义」的角色材料；第四节「执行」的缝 | 单循环的部门角色 → 工程的外包角色（ACP） → 部门内多角色与子循环 | 新的角色种类、新的外部代理协议；质检永远不外包 |
| 03 路由与粒度 | 第一节「轮转方式」；第四节「路由」的缝 | 按成果 → 任务池与工作单元的参数化 | 第三种轮转方式、自适应的拆分 |
| 04 装配与语义 | 第四节「装配」的缝 | 减法视图与压缩 → 五层轨迹与七类图谱 → 按依赖与焦点取、提示缓存复用 | 新的减法、跨项目经验的检索与失效重验 |
| 05 动作与工具 | 第一节「模型与工具」；第四节「动作」的缝 | 本机改文件与跑命令（带差异与回执） → 网络取回与 MCP → 浏览器与截图 → 远程执行代理 | 桌面操作（computer use）、技能、降解的脚本 |
| 06 模型与判定点 | 第四节「模型」的缝；第三节的判定点 | 多协议无状态调用与凭据隔离 → 能力表与按部门选模型 → 声明的判定点与校准的决策模型 | 新协议、本地小模型、自适应档位 |
| 07 观察者 | 第一节「观察者」；第四节「观察者」的缝 | 离线的经验候选 → 只读订阅与写入口提案 → 教训发现、振荡检测、降解信号 | 任何只读事实、只出证据与提案的模块 |
| 08 评价与验收 | 第一节「评价」；第四节「评价」的缝；第五节验收表 | 内核重放与契约测试 → 固定回归场景与单 agent 对照 → 操作代理照说明书判分 → 留出场景与发布检查 | 新评测题、变异测试与圈复杂度守卫、新领域的判分器 |
| 09 画面与空间 | 第一节「界面」；第四节「画面」的缝 | 楼与机房基础 → 机房设备与冒烟 → 产品的城与指向式输入 → 铺传送带编辑定义 | 无级缩放的导航、三维（出现需要第三轴的量时） |
| 10 部署与环境 | 第六节「部署是定义」；第四节「定义」的缝 | 单机单进程 → 常驻服务与进程外看门狗 → 控制主机加远程机器、开发板、容器 → 多项目隔离并行 | 按项目拆多个控制核心实例；一个 Yudao 运维另一个 |

**未知的去处**：内容的未知落在道上，按上面的规矩进入；结构的未知（新方框、新缝、内核改动）只走一条路：先交总架构师改总图，第二环向后兼容，第一环经你批准才动工。

## 4. 三个空间：楼、机房、城

画面不是装饰，是一份事实的投影与高带宽的指挥语言（总图第一节「画面 = P_view(事实)」）。所有视觉元素都绑定事件回链，关掉装饰以后看到的全是事实断言。空间的映射（楼、机房、城与七种元件）的依据是调研[游戏世界与代码世界的映射](research/game-world-as-projection.md)与需求记录 [D41 三个空间](requirements/game-world-three-spaces.md)，这张表是它在路线图上的位置。

| 步 | 阶段 | 空间 | 建成的画面 | 绑定的事实 | 你能做的 |
| --- | --- | --- | --- | --- | --- |
| 0 | 一 | 楼与机房 | 部门房间、小人、传送带上的包裹（交接、询问、返工）、大厅决定板、上下文容量刻度、回放 | run 流、项目流、机器流、上下文清单 | 看循环卡在哪一环；拖包裹调优先级；在决定板上批准；倒带回放 |
| 1 | 二 | 全部 | 声明式对照表全覆盖（每种事件、术语、覆盖层都有一行，缺行即测试失败）；检验覆盖的视图 | 事件定义、放行报告与来源回链 | 从任一画面物件点开原始事件、上下文摘要或真实的差异 |
| 2 | 三 | 机房 | 已交付的软件是运行中的设备（版本牌、健康灯、备份柜）；故障冒烟并向楼投递修复包裹 | 运维观察记录、故障记录、部署与回滚事件 | 看生产环境的健康；理解修复为什么插队；批准回滚与恢复备份 |
| 3 | 四 | 城 | 页面、接口、数据表是建筑，模块是街区，依赖是道路，要求是蓝图，验收条件是检查站，证据让蓝图变建筑，试用会话是访客 | 语义图谱、检查回执、浏览器试用记录与截图 | 点一栋建筑直接说话；看哪片街区缺检查站或长期停在蓝图 |
| 4 | 四 | 三空间 | 规则成为物件与物理：可改的规则（模型接线、机器门牌、常设授权牌）是可操作的物件，不可改的（写入口的盖章机、部门的隔离墙）是推不动的边界 | 带版本的定义、项目设置、模型目录流 | 在空间里操作物件下发配置；直观看到安全边界 |
| 5 | 四 | 楼（房间内） | 传送带进房间：中心角色白板上的计划条目、工具角色桌上的任务卡、尝试的草稿堆 | 语义系统的五层轨迹、部门内多角色的事件 | 看部门内多角色与外包角色的瓶颈与重试消耗 |
