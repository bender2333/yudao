1. **Provider 补充阶段**：先完成 2.7，所有模型入口通过统一模块，无配置可启动，并支持 Go API Key 与必要三协议。
2. **统一基线**：分清历史验收版本、当前代码和本轮新测；在 2.7 后的冻结版本上补齐场景、限额、检查与证据。
3. **通用工具**：先完成真实代码项目的搜索、阅读、编辑、本地命令与独立 QA；从一开始记录每次动作及其结果，仍单任务运行。
4. **提示词审计补丁与请求结构**（[#46](https://github.com/bender2333/yudao/issues/46)、[#47](https://github.com/bender2333/yudao/issues/47)）：补全工具描述、删除请求中的剩余循环次数、合并质检的检查工具；修正模型只回复文字时下一次请求以助手消息结尾的缺陷；修正两项在本机失败的测试（[#101](https://github.com/bender2333/yudao/issues/101)）；交付工具的描述与拒绝信息写明检查回执来自 `run_check`，登记命令的描述与工程提案合同区分动作回执与检查回执（[#103](https://github.com/bender2333/yudao/issues/103)、[#106](https://github.com/bender2333/yudao/issues/106)）。这些工作都排在控制核心重构之前，使它的事件序列基准包含修改后的行为，并且从全部测试通过的状态开始。
5. **控制核心重构**（[#43](https://github.com/bender2333/yudao/issues/43)）：按 [ADR-0010](adr/0010-control-core-drives-role-steps.md) 与 [ADR-0011](adr/0011-async-control-core.md) 由控制核心驱动每个角色任务的步骤，分出流程编排、异步的步骤驱动、上下文装配（P）与裁决规则（U）的接口，取消部门循环的回调，模型调用与动作使用可以序列化的合同，工具分为主机工具与环境工具；行为不变，现有测试全部通过。它是 3.1 与 Stage 4 语义系统（#22 的子工单）、部门内多角色、外包角色的前置工作。
6. **一份事件日志**（[#44](https://github.com/bender2333/yudao/issues/44)）：按 [ADR-0013](adr/0013-event-log-and-single-write-path.md) 合成一份带全局位置与流版本的事件日志，建立唯一写入口，投影保存并逐步更新。3.1 的执行权核对、3.4B 的原子采纳与语义系统的图谱都建立在它上面。
7. **带版本的定义**（[#48](https://github.com/bender2333/yudao/issues/48)）：按 [ADR-0014](adr/0014-versioned-definitions.md) 把组织、角色、动作、提案合同、限额与停止原因改为带版本的数据，每个事项记录它使用的版本。与一份事件日志并行，语义系统的本体与部门内多角色建立在它上面。
8. **用户决定**（[#49](https://github.com/bender2333/yudao/issues/49)）：所有等待用户的事项使用同一种机制（[总体架构](design/architecture/overall-architecture.md)第 7.4 节），第一种是模型引用无法使用时的待恢复；3.1 的继续执行与核实未知动作按同一机制加入。回答命令与决定请求的查询通过应用层的骨架（[#72](https://github.com/bender2333/yudao/issues/72)，[应用层与接口层设计说明](design/app-and-interface.md)）登记，骨架排在用户决定之前。
9. **调用目标每次请求解析**（[#45](https://github.com/bender2333/yudao/issues/45)）：D24 中 [ADR-0005](adr/0005-resolve-call-target-per-request.md) 的部分提前到 3.1 之前；控制核心不持有明文凭据，进程重启后按当时的设置与凭据来源继续。
10. **可靠恢复**：先核对执行所有权和未完成动作，再继续同一 run。恢复命令与 replay 分开，恢复不能重置限额或复活已取消任务。进行中的角色任务由步骤驱动从已提交的状态重新装配后继续。执行权在写入口与领域写入一起核对（[ADR-0012](adr/0012-single-control-core-scalable-execution.md)）。
11. **并行**：恢复验收通过后，先支持不同项目、隔离目录中的独立事项；再处理同一项目的成果竞争与采纳。
12. **网络、MCP 与扩展接口**：恢复通过后接入，每个新工具单独验收。3.7 提供的只读观察接口供 Stage 5 的元观察与规则检查部门使用。
13. **组合验收**：3.9 在真实外部项目上对 Stage 3 的各项能力逐项给出结论。

已有 Provider 配置页复用；D22 补无配置启动、重载与页面凭据，D23 建独立模块并接 OpenCode Go。Go 必需的 Responses、Chat Completions、Messages 前移到 2.7；其他 Provider/订阅和推理设置留在 3.3。技能在 Stage 4，运维在 Stage 5。

## 3. 跨阶段架构与约束

分层、各层的职责与边界、长期决定、合同与使用的技术见[总体架构：职责分层](design/architecture/overall-architecture.md)：客户端、接口层、应用层、控制核心（流程编排、步骤驱动、上下文装配、裁决规则、写入口、事件日志）、定义、知识层、观察层、观察者、执行层（Provider、执行环境、外包 agent 的运行容器）。各阶段的新能力都放进这个结构，不建立第二套事件事实源。

从现在起遵守 [ADR-0007](adr/0007-boundaries-for-distributed-deployment.md) 的六条边界，以及 [ADR-0010](adr/0010-control-core-drives-role-steps.md) 至 [ADR-0015](adr/0015-desktop-client-and-http-contracts.md)：每次模型请求在控制核心装配；控制核心在一个异步事件循环中运行；控制核心逻辑上一份并持有执行权，执行层与观察者可以扩展；一份事件日志与唯一写入口；组织、角色、动作、本体与规则作为带版本的定义；桌面客户端、FastAPI 接口层，服务之间使用 HTTP 加 JSON。

继续遵守 [D09](requirements/execution-limits.md)：运行时间上限是主要的收敛保证，部门激活次数与模型步数的上限保留但默认值放开，单次请求有超时，重试和压缩计入已有额度；Provider 用量及费用只读记录，未知保持未知。恢复不清零；并行新增执行槽位控制。本次不引入 token / 费用硬预算、额度预留系统或通用预算平台。

不引入外部工作流引擎（[ADR-0012](adr/0012-single-control-core-scalable-execution.md)）：控制核心本身就是按事件重放的状态机，会话可以丢弃，恢复时从已提交的状态重新装配。单机使用 SQLite、官方 SDK 与 HTTPX；Stage 6 的服务端数据库在该阶段按故障场景与总成本比较后选定，事件日志的接口不变。

不新增旧运行格式兼容层或迁移。首批恢复只承诺同一受支持应用版本内的进程重启；跨不兼容版本明确拒绝，并可通过现有项目采纳成果新建事项，不能把新事项称为恢复了原 run。

## 4. 持续改进工作线

| 能力 | 已有 | 下一项完成依据 |
| --- | --- | --- |
| 可信观察与独立评价 | 待验证候选、可搬移证据包、清单复核、批次分母 | 固定任务族、独立检查与错误身份；获得真实问题轨迹，缺样本时如实报告 |
| 单项局部改进 | 固定重试等执行规则；尚无证据驱动的比较结论 | 针对已观察问题比较固定策略与一项有界调整，质量不降并报告额外成本 |
| 项目记忆 | 项目上下文文本随采纳增长，只携带最近一次采纳成果的产品合同 | 由 Stage 4 语义系统承担：项目内的轨迹与图谱跨事项延续，替代长期记忆 |
| 跨任务经验 | 候选仅保存，不自动注入 | 候选、独立验证、适用检索、限定采用、冲突处理、反例与停用贯通 |
| 综合比较 | 尚无可比较的控制和经验处理组 | 在未见任务上比较固定基线、仅控制、仅经验、组合方案 |

语义与关系查询服务于具体问题：“这条经验由哪些经历支持”“要求变化后哪些经验需要重验”。已有存储能满足时不新增图数据库或向量库。相似文本不能直接证明同一问题或同一根因。项目内的轨迹与图谱由 Stage 4 语义系统维护，作为事件的投影存放在现有 SQLite 中，查询只用结构条件与全文检索，不使用向量检索（[D25](requirements/semantic-system.md)）；语义系统同时整理知识图谱与语义工程，供 Stage 7 系统演化使用。

学习完成要演示“重复问题 → 候选 → 独立验证 → 未见任务采用 → 反例 → 停用”，同时保留失败、无效和缺失结果。训练与校准材料不得混入未见评价。

这条工作线不阻塞通用工具、恢复和初步并行。它是系统自动采用经验及 Stage 7 系统演化的前置。研发者手写技能依赖稳定过程和独立比较证据，不再机械依赖旧“Stage 2 2.3”编号。

### 5.1 Stage 4：部门内协作、上下文与界面

依赖 3.1、3.4A、3.2B 与 D24 模型管理（其中调用目标每次请求解析由 #45 在 3.1 之前完成；其余部分是父工单 #83 与子工单 #84 至 #96）。

- **语义系统**（[D25](requirements/semantic-system.md)，[语义系统设计说明](design/semantic-system.md)）：关键环节，为 Agent 整理轨迹与图谱，并据此组装上下文，承担项目记忆；整理出的知识图谱与语义工程供 Stage 7 系统演化使用。分两部分：
  - **整理**：轨迹记录事项的工作过程，分事项、交接、计划条目、角色任务、尝试五层；图谱由证据、事实、知识、决定、要求、实体、推测七类内容及其关系构成，在其上归纳教训、洞见与画像，其中教训与洞见由教训发现模块找出（待设计）。角色在工作中随时记录，主机按本体校验后写入；记录事实时由 JEV 核对证据是否支持陈述。轨迹与图谱都是事件的投影，重放可以重建。
  - **上下文组装**：每次请求由固定的栏目组成，按常驻栏目、目录、按需取得、接触时附加四种方式放入内容，变更与新到达的输入作为通知追加进历史；各角色按分工得到不同的上下文；组装不调用模型，放入的内容与原因由上下文清单记录。请求长度受工作上限控制，达到压缩阈值时先清理旧工具结果，再压缩，压缩后由轨迹与图谱代替被移出的历史。栏目按变化频率从少到多排列，历史只追加，使提示缓存可以复用。
  - 完成依据：同一项目连续多个事项中，被修改的要求以取代关系出现，被取代的要求不作为有效内容进入请求；数据流核对列出缺失的覆盖；重放事件重建的轨迹与图谱与原记录一致；详细验收见设计说明第 16 节。
- **决策模型接入**：JEV 的 systemone 接口作为 Provider 模块的新协议接入，ADR-0001、ADR-0004 的结构不变。本阶段用于语义系统的证据核对，只核对外部文档与需要解读的运行输出。核对按 [D28](requirements/meta-observer.md) 的规则校准：用本地中文样本选取阈值，再用另一批样本复核，样本与标注方式见 D25 上下文组装专题第 16 条；校准通过之前，核对结果只记录，不显示给模型，也不改变内容的状态。JEV 的能力边界见 [JEV 决策模型调研](research/jev-decision-model.md)。
- **部门内多角色**：每个部门围绕中心角色协作，中心角色负责规划与判断，经理负责对外沟通，探索者、主程与审查者是中心角色的工具，见 [部门内多角色设计说明](design/department-roles.md)（[D26](requirements/department-roles.md)）。依赖语义系统、3.4A 执行槽位与 3.2B 网络工具（探索者查资料）；决定见 [ADR-0016](adr/0016-center-role-collaboration.md)、[ADR-0017](adr/0017-role-settings-override-department.md)，工单为父工单 #50 与子工单 #51 至 #65。完成依据：另立任务族，与现有单循环部门在同一组任务上对照，交付质量不低于单循环，并报告模型请求数、用量与耗时；设计第 16 节的反例通过。
- **技能**：注册、适用性、执行与展开、异常出口与比较。稳定过程有独立证据，封装后质量不降，收益覆盖维护成本。
- **可观测性**：Yudao 自身的观察视图，包括部门内外的运行过程、角色任务、上下文来源与用量，见 [可观测性详细设计](research/observability-design.md)；数据来自应用层的查询与事件流。
- **应用层、接口层与桌面客户端**：按 [ADR-0015](adr/0015-desktop-client-and-http-contracts.md) 与[应用层与接口层设计说明](design/app-and-interface.md)建立命令、查询、事件流、能力清单与认证（父工单 #70，其中骨架 #72 排在 3.1 之前），桌面客户端按原型 v7 实现（父工单 #71）；桌面客户端的当前档页面通过验收以后删除旧 Web 控制台（#78）。

跨任务经验仍属于持续改进工作线（第 4 节）。

### 5.2 Stage 5：运维部门与元观察

**运维部门**（[D27](requirements/operations-department.md)，并入原 3.8）

- 负责交付物（用户项目的软件）的部署、运行观察、性能与故障处理。生命周期跟随项目：项目采纳交付物之后接手，长期存在。
- 运行中发现的问题作为新事项进入「产品 → 工程 → 质检」流程。事项进行中，各部门可以向运维询问，运维也可以询问各部门；常见往来是产品（取舍与运行目标）和工程（部署方式与修复）。
- 产品在 PRD 中确定运行目标，运维测量并报告达成情况；工程随交付提供部署说明、健康检查与运行数据输出。
- 部署、回滚、重启都是对真实环境的外部动作，逐项授权。运维不修改功能要求，也不代替质检放行。平台与交付物两类运行责任分开，发布成功与运维接收分别记录，见 [运行责任样例](stage-3/operations-responsibility-sample.md)。
- 依赖 Stage 3 的工具与恢复（结果未知的外部动作）、环境授权与一个真实的发布对象，按 Stage 4 的部门内多角色形态建设。完成依据：一个真实交付物在明确的环境与约定的观察窗口内，完成从故障发现、修复、发布到恢复确认的全过程。增加运维部门本身不等于具备运行能力。

**元观察与规则检查部门**（[D28](requirements/meta-observer.md)）

- 只做流程审查与观察，结果用于 Stage 7 系统演化。观察部门之间的流转事实：交接、询问与回答、缺陷、放行、返工的次数与间隔；按规则审查过程，报告不符合项。质检检查交付物是否符合 PRD，两者分开。
- 使用 JEV 决策模型进行带有置信度的局部判断；发现报告与升级后的判断使用 LLM；循环整体是否有进展由确定的统计与 LLM 分析，不交给 JEV。JEV 的能力边界见 [JEV 决策模型调研](research/jev-decision-model.md)。
- 判定点由控制层事先规定，写明问题、参照材料与三种结果的去向：高置信度通过则推进；高置信度不通过则退回或记录发现；置信度不足则交给 LLM 判断或由用户决定。判定点使用带有标注的中文流转样本选取阈值、再使用另一批样本复核之后，控制层才按审查结果自动推进；未通过的判定点只记录。
- 每次判定记录状态、问题、选项顺序、模型版本、概率与置信度，重放使用记录的结果，并定期抽样复核。
- 质检放行、产品取舍、规则修改不交给它。它不读取部门私有上下文，部门也不能向它分派工作。
- 依赖 3.7 的只读观察接口、Stage 4 接入的 JEV 协议与带有标注的流转样本。

**决策模型**：元观察使用 Stage 4 接入的 JEV 协议。JEV 的模型访问定义按模型测试准入（[ADR-0002](adr/0002-candidates-need-test-to-admit.md)）；判定点在本阶段设计，每个判定点用带有标注的中文流转样本校准通过后，控制层才按判断结果自动推进。元观察在组织上是一个部门，运行时是一个观察者加判定点（[ADR-0012](adr/0012-single-control-core-scalable-execution.md)）。

进入 Stage 5 时，同步修改 CLAUDE.md、AGENTS.md 与 README 的项目表述，加入运维部门、元观察与规则检查部门。在此之前，这三份文件只描述当前的三个部门，避免影响当前的工作。

### 5.3 Stage 6：分布式部署

执行层（执行环境、Provider、外包 agent 的运行容器）、观察者（元观察、教训发现模块、演化模块）与存储部署到不同的服务器和平台上，控制核心逻辑上一份并做主备（[D29](requirements/distributed-deployment.md)、[ADR-0012](adr/0012-single-control-core-scalable-execution.md)）。部门的身份与每一步的控制留在控制核心；部门需要的执行环境与 Provider 部署到靠近环境与权限的机器上。收益：凭据保存在各自的环境里；执行环境在独立容器中运行，隔离任意代码；同一交付快照在多种平台上并行检查；需要时按项目把 run 分给多个控制核心实例。

从现在起遵守 [ADR-0007](adr/0007-boundaries-for-distributed-deployment.md) 的六条边界与[总体架构](design/architecture/overall-architecture.md)第 7 节的合同，本阶段只需把执行层与观察者移到不同的机器并使用 HTTP 加 JSON 传输（[ADR-0015](adr/0015-desktop-client-and-http-contracts.md)），不重写核心。执行权在本阶段加入期限与续期。事件日志与工件换成服务端数据库与对象存储，数据库产品在本阶段按故障场景与总成本比较后选定。

依赖 3.1、3.4 与 Stage 5 的完整部门集合。完成依据在进入本阶段时确定，至少包括：任一节点故障后，同一 run 由新的执行者接续，旧执行者的迟到结果被拒收，领域状态不重复推进。

### 5.4 Stage 7：受治理的系统演化

Stage 7 分三种责任：运行提供事实；演化模块提出组织、协议或日常规则候选；独立评价决定是否在限定范围采用。候选不能自行批准，用户目标和授权边界不由被评系统修改。演化使用元观察与规则检查部门的审查与观察记录，以及语义系统整理的知识图谱；用于最终判断的隐藏评价材料不进入被评系统可以读取的知识图谱。

Stage 7 完成条件：
- 一类组织/协议变化和一类日常规则变化贯通证据、候选、隔离比较、独立评价、采用、观察与撤销。
- 使用未见任务比较原组织、研发者静态改进和系统候选，收益包含额外协调与维护成本。
- 失败候选不生效；采用后的反例能停止新增使用、处理在途工作并保留恢复依据。
- 规则变化能追踪对经验、技能及事项的影响，不默认旧经验继续适用。

开放性研究仍是独立研究方向；可信观察之后才能开展有解释力的实验。模型权重更新保持可选，不是主线阶段的必做项。

### 5.5 愿景：Yudao 负责自己的运维

Yudao 平台由自己的运维部门负责运维。自举难度大，平台运维目前由人负责。Stage 6 之后，一个 Yudao 部署可以由另一个独立部署中的运维部门负责运维，健康检查保留一条不依赖被运维平台的外部途径（[组织与持续运行研究](research/organization-runtime-evolution.md)第 7.2 节）。
