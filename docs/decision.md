## 2026-09-30 - 圈复杂度与变异测试在本阶段末手动进行；工具放到下一阶段

- 背景：2026-09-29 定下变异测试与复杂度检查做成研发工具以后，讨论当前阶段怎样先用上。
- 用户原话：

  - 「为啥说omp方便？因为现在omp是自动推进开发的执行者」

- 决策：

  - 工具放到下一阶段，目标形式是可执行工具与 skill 加 MCP，首要使用者是自主推进模式中的执行者 omp，以后由 Yudao 集成。
  - 以后要做的事情写进 [D35 自举](requirements/self-hosting.md)。
  - #158 继续暂缓。
- 影响：路线图的调整，修改内容先经用户确认。

## 2026-09-29 - 自举作为核心目标；单一写入角色是短期取舍；质量检查按部门分为工序；变异与复杂度做成研发工具

- 背景：讨论圈复杂度与变异测试怎样进入项目，以及测试与流程做成框架还是 Yudao 的内置模块。架构师的分析是：现在的开发流程就是用文字规则运行的三部门循环，应当放进 Yudao，并按编译器自举的做法由固定版本的 Yudao 承载自身的开发；同时指出按现行设计，一个项目同一时刻只有一个角色编写代码。
- 用户原话：「按 Yudao 的设计，一个项目在同一时刻只有一个角色编写代码，这是当前短期的取舍，因为简单。未来肯定是要打破这种方式的，利用worktree并发。或者结合不同执行主机通过branch进行。自举这个事情，其实就是我的目的，但是我没有把握完成。所以暂时没有推进，现在重新拿出来作为一个核心目标。如果说刚才的测试分层，做成命令，我建议作为一道工序融入到部门内，比如工程部门对单元测试和圈复杂度、变异测试进行自我保证。 验证部门做大的验证。另外，我关于变异测试，圈复杂度测试是想要一个类似微服务或者MCP的工具，可以在windows或者linux上直接给出相关的结果和诊断，供研发使用。」
- 决策：
  - 自举（用 Yudao 开发 Yudao）是核心目标。
  - 同一项目同一时刻只有一个角色编写代码，是当前阶段为了简单作出的取舍；将来支持多个写入者：同一执行主机上用 worktree 并发，不同执行主机之间通过分支进行。
  - 测试与质量度量作为部门的工序（交出检查）：工程部门对单元测试、复杂度与变异测试作自我保证，质检部门做大的验证。
  - 变异测试与复杂度检查做成类似微服务或 MCP 的工具，在 Windows 与 Linux 上直接给出结果与诊断，供研发使用。
- 影响：需求写进 [D35 自举](requirements/self-hosting.md)；自举的 ADR，以及路线图、D27、D16、D31 与部门内多角色设计说明第 12.6 节的调整，修改内容先经用户确认。

## 2026-09-29 - 3.8 与 3.2C 的设计决定；机器流；远程验收等树莓派

## 2026-09-25 - 语义系统：整理与上下文组装分开，轨迹与七类图谱内容

- 用户声明：语义系统不是 RAG，也不是长期记忆；它参照 Semantica，是带有知识、事实、证据等内容的知识图谱，给 Agent 做上下文用。Agent 最重要的是上下文管理，语义系统分为整理与上下文组装两部分；上下文组装列为重点 TODO，专题讨论。
- 用户决定（整理部分）：轨迹分事项、交接、计划条目、角色任务、尝试五层，只有一份，部门账本是它在部门这一层的视图；轨迹的上面几层由主机从事件生成，尝试由角色在任务结束与压缩之前整理；图谱内容分证据、事实、知识、决定、要求、实体、推测七类，事实必须附证据；角色在工作中随时记录图谱内容，主机校验后写入，压缩之前补录；轨迹与图谱只由事件生成；要求类条目带稳定编号，主机校验引用，质检放行要求每条有效验收条件都有通过的检查结果与证据。
- 用户决定（第三轮）：轨迹最低一层称为「尝试」，与「调用尝试」在术语表中区分；证据出现新版本、要求被修改或废止时，主机把受影响的内容标为待复核，矛盾的新事实必须写明取代哪一条或记录为冲突；所有部门可见事项层与交接层的轨迹、要求类条目、主机接纳的材料内容与实体名称，计划条目以下的轨迹与部门记录的内容只有本部门可见；知识只在本项目的本部门内使用，跨项目复用属于持续改进工作线；用户可以查看轨迹与图谱、把部门记录的内容标为失效或写入更正，轨迹只能查看；第二项职责中演化使用轨迹与决定，语义工程包括项目术语表以及教训、洞见等语义。
- 用户决定（第四轮）：抽象层包括教训、洞见、画像，必须关联依据；教训随时记录，复盘在成果被接纳后与事项结束时由中心角色进行；教训是参考内容，主机不强制执行，需要强制的成为规则候选；抽象层属于部门私有，画像按部门各自编写，跨项目复用属于持续改进工作线；Semantica 不作为依赖，借用 PROV-O 对应、四个时间字段、决定与因果、本体加约束形状、冲突类型，轨迹与图谱是存放在现有 SQLite 中的事件投影；本体由系统定义，实体类型为固定清单，领域概念作为术语类实体；关系分八组；不记录模型给出的置信度。依据见 [Semantica 参照调研](research/semantica-reference.md)。

## 2026-09-21 - 压缩在推理型模型上的失败形态与待决方向

- 事实：`mimo-v2.5`（推理型）在真实运行中多次进入 `FAILED / compaction_failed`，两种形态：`Compaction summary exceeds its output limit`（12000 窗两次，场景 C）与 `Compaction returned an empty summary`（32000 窗一次，3.2A 登记命令验收 `run_4280c207b68248cd`）。压缩调用在上游侧记录为 success，但正文为空或超限；两次压缩调用分别耗时 47s / 23s。
- 机制：`harness/compaction.py` 的 `response_reserve` 取 `max(窗口 15%, min(模型声明输出上限, 窗口/2))`；32000 窗且声明输出上限 4096 时预留 4800、摘要上限 4096。推理模型的 reasoning 与摘要正文共享该预算。
- 现状与设计一致（压缩失败 fail-closed，不静默截断），因此不按缺陷直接修改。
- 待决方向（需人确认，涉及 D10 压缩语义与 D17 重试边界）：
  1. 提高模型声明的 `max_output_tokens`。本机 4096 是验收发送上限而非服务商标称；需确认模型真实上限，不猜容量。
  2. 把"空摘要"归为可重试的模型输出畸形，走现有每次激活的重试额度（与"未声明工具却返回 function_call 归为可重试"同类先例）。
  3. 压缩请求抑制推理，需要协议或服务商级参数支持，属能力变更。
  4. 摘要改用非推理模型。部门绑定为单模型，属设计变更。
- 推荐：先做第 2 项（最小改动，不改变 fail-closed 与重试类别），同时确认第 1 项的真实上限；若仍不足以覆盖长工程会话，再评估第 3 或第 4 项。

## 2026-10-02 - 结果未知的动作自动核实与自动重新执行

- 背景：3.2B 讨论中留下的专题 6。长时间无人值守运行时，Yudao 进程被终止、电脑重新启动或远程执行代理超时，都会让进行中的动作结果未知；现在的实现对每一个这样的动作都发出决定请求，只读的读取也是这样，运行停下来等用户。恢复契约第 4 节原先写着读取以新尝试重读、写入按快照核实，实现时简化成了全部询问。2026-10-02 用 grill 讨论两轮，用户回答「采纳建议」并确认修改清单。
- 决策（[恢复契约](design/recovery-contract-and-fault-matrix.md)第 4 节开头的三步）：
  1. 契约声明可以重复的动作（读取与搜索、检查、网络取回、登记时声明「可以重新执行」的命令与 MCP 工具），结果未知时以同一个逻辑动作的新尝试自动重新执行，不询问用户，也不另外通知；动作记录与房间的动作显示里看得到两次尝试与依据。
  2. Yudao 自己的文件工具（写入、编辑、删除、移动）按动作前的快照自动核实：工作区与快照相同时重新执行；只有目标路径变成参数中的内容时确认已完成；其他情况交给用户。
  3. 同一个逻辑动作只自动重新执行一次（「动作没有发生」的重新执行也计入）；新的尝试仍然未知时发出决定请求，材料写明连续两次结果未知，提醒可能是动作本身导致中断。
  4. 登记的命令增加「可以重新执行」，默认为否，`command_configured` 增加字段，旧事件为否，事项创建时固定。MCP 工具的「可以重新执行」同样表示结果未知时自动重新执行。
- 同日处理 #135 登记的两条架构问题：项目流与机器流允许给已有字段增加取值（ADR-0019 与规则 1 修改，清单写入路径由 #241 实施）；仓库自身的 `.git` 不算宿主私有路径。
