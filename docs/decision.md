## 2026-10-30 - 模型管理：填写地址与 Key，选择模型即可使用

- 事实：用户 2026-10-29 试用 0.2.0 卡在模型配置：「填写了key以后，保持为灰色」「模型不能自动去填写上下文窗口信息」「获取模型会获取到所有的模型，非常乱」「点击测试也没反应」「模型能力表没有任何用，我需要的是自动填写」。用 0.2.0 加一个返回 104 个模型的上游复现：添加模式下三个凭据按钮永远灰着；候选卡片的窗口与输出上限全是空输入框；候选不能搜索筛选，「加入」到结果所在的表格相隔 9088 像素；「测试」的结果写在别处（编辑表单里的连接测试写在上方的卡片里，新加行的模型测试被服务端拒绝后只在页面最顶写一句）。
- 决定：页面主路径只有服务地址与 API Key，勾选模型以后系统补全参数、做模型测试、通过即启用（V14 原型定为模型管理页的定稿，其余页面仍以 v13 为准）。
  - Key 的存法看 OpenCode（提交 7ab721a97f）：随连接保存，始终写进数据目录的 .env，系统支持文件权限时只有所有者可读写，明文保存，没有「只在本进程有效」的选择，环境变量是另一种来源。（用户 2026-10-30：「key 怎么存，你看下opencode就行」）
  - 容量来源次序是上游模型列表、能力表、用户填写。能力表扩到 models.dev 的全部服务商，只在连接地址识别出的服务商之内按上游模型 ID 精确查找：2026-10-30 的快照里，出现在多个服务商下的 1174 个型号中有 752 个的窗口或输出上限不一致，按型号名称跨服务商借用值会给出错的容量。
  - 模型测试加工具往返（D24 原来的「工具能力检查暂不加入」改为加入）：三部门每一步都靠工具调用，页面主路径上没有手工声明「是否接受要求调用工具」的地方，只能由测试测出。
  - 第一个启用的模型自动成为还没有部门默认的部门的部门默认，已有的选择不被覆盖。
  - 容量未知的模型保持不可用，用户填写窗口与输出上限（来源标手动）以后继续；列表里没有的模型用「手动添加」。
- 记录：设计见模型管理设计说明第 4.1 至 4.5、5.1、9.1、14 节与应用层和接口层设计说明的模型管理命令；需求见 D24；工单 #1264 改写为父工单。

## 2026-10-30 - 模型能力表：按接入包登记协议，不排除记录；协议预填改回能力表优先

- 事实：#1296 用 2026-10-30 15:19 取回的 models.dev（SHA-256 `4e9ba4423a35cc60d18b9aa5bda8a67895090a814d496ee5bc6248716d5a7d97`，233 个服务商、8923 个模型）生成能力表时，有 25 个接入包不在映射表里。其中预置服务方案对应的 `opencode-go` 有两个模型（`gemini-4-argon`、`gemini-4-argon-contributor`）自己声明 `@ai-sdk/google`；官方源码 `vercel/ai@dfed8e8234` 的 `packages/google/src/google-language-model.ts` 向 `models/<模型>:generateContent` 发请求、`google-provider.ts` 用 `x-goog-api-key` 认证，三种协议都不是。原设计只能整个服务商排除，而定义加载要求预置服务方案在能力表里有条目，两条不能同时满足。另外有 8 个服务商的接入包映射不到，但其中部分模型自己声明了能映射的接入包（例如 `azure` 下 24 个、`google-vertex` 下 20 个）。
- 决定（被唤醒的架构师，用户可以推翻）：
  1. 登记的单位是接入包。映射表每一行登记为三种协议之一，或「没有对应的协议」；登记为某种协议要有官方源码的依据（请求路径、认证方式与请求体），依据写在这一行旁边。映射表里没有的接入包仍使脚本以错误结束，逐条列出服务商、模型与接入包，不写出能力表。
  2. 不按服务商、也不按模型排除记录。接入包没有对应协议的模型照常收录，调用协议为空，接入包、容量与输入方式保留。理由：models.dev 给出的窗口与输出上限是这个服务商下的真实值，与 Yudao 能不能说那个接入包的协议无关；排除只会丢掉真实数据、让用户手填，还会与预置服务方案的条目要求冲突。协议为空的模型选用时协议按默认预填，能不能用由模型测试测出，不需要新的状态。
  3. 能力表记录服务商的接口地址与接入包、模型自己声明的接入包，以及来源文件的 SHA-256；映射表的登记与依据在提取脚本里，与生成的能力表同一次提交修改。原来的命令行「排除服务商」不再需要：命令行上的决定在提交里留不下记录。
  4. 协议预填改回能力表优先：内置服务方案也先取能力表中这个模型的协议，查不到或为空时取方案的默认协议，其余取 Chat Completions。设计说明第 4.3 节 2026-10-30 改写时写成了「内置服务方案取方案的默认协议」，与 D24 用户 2026-10-07 的决定、第 4.1 节自身和 #1296 正文第 4 条都不一致，#1293 按那一句把候选的协议次序改成了方案默认优先；这是一致性修正，按冻结规则只更新依据与任务评论。
- 记录：模型管理设计说明第 3、4.1、4.3、10、14 节与文末变更记录；`CONTEXT.md` 的「模型访问定义」「模型能力表」；#1296 正文与任务评论，#1295 任务评论。

## 2026-10-30 - 核验是角色的性质，固定结构只剩循环、边界、裁决

- 背景：用户要让同一套底下的层能退化成单 agent、普通多 agent，往上是三部门，再往上是部门内子组织与观察者，并且「确保抽象、层、复用」，不是追求内核更薄。方案出处：分支 `plan/verification-as-node` 的 `docs/plan-verification-as-node.md`。
- 决策（[ADR-0044](adr/0044-verifier-role-and-open-loop.md)，[形态与核验角色设计说明](design/forms-and-verifier-role.md)）：
  1. 固定结构改为三样：循环、边界、裁决；独立的证据由核验角色取得。
  2. 分四层：事实与裁决、循环、路由、组织；任何形态都不改前两层。内核只认通用的成果，PRD、交付、质检结论与检验方式归成果驱动与核验。
  3. 核验是角色身上可声明的性质，只有一套，所有路由共用（用户看了两种放法的对照图后选定）。
  4. 新路由「直做」承接单 agent 与普通多 agent；没有核验角色的事项交完成按流程采纳、不发决定请求，记为开环完成。
  5. 外包不要求下游有核验，最差退化成调用 OpenCode，Yudao 仍守快照、上限、写入口与开环完成的标记。
  6. 部门内多角色与分形只用子事项；观察者不做部门。
  7. 方案里「内核过关自动采纳」的分级拆出去，以后单独定。
- 排期：内核只认通用成果、核验角色、直做与开环完成、形态随事项冻结进阶段二；子事项与观察者写入留在原来的道。
- 改动：总图第一、二、三、四、五节；`CONTEXT.md` 新增核验角色、开环完成、直做；基础规则 3 下一行（用户授权）；D38 追加用户原话；`CLAUDE.md` 项目表述；循环与收敛设计说明的外包判据。
