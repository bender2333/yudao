## 2026-09-29 - 原型 v8 的方向；机器在系统中登记、在项目中授权

- 背景：开始 v8 原型的讨论（/grill-with-docs），三轮问题。
- 用户原话：「采纳推荐」（三轮相同）。
- 用户决定：
  - v8 首先回答用户回来时哪些事需要决定、离开期间发生了什么、能不能放心再离开；首页顶部一排来自事实的状态项，不给汇总结论。
  - 机房属于系统这一层：首页画一栋楼，每个项目一层，地下室是共用的机房；项目楼层只画通往机房的门与本项目正在使用的机器。
  - 机器在系统中登记（名称、地址、用途），项目中授权使用（登记的目录、可以执行的操作、是否作为运行环境），授权范围按项目分开。
  - 部门之间的交接经过管道，询问与回答走传信管；决定请求在首页的卡片中就地回答；离开期间只回放关键事实；质检房间增加试用台并显示真实截图；同一项目排队中的用户新要求可以调整顺序，修复事项始终在前。
  - 原型档位按 Stage 3 的工作包细分，再加 Stage 4、Stage 5；评测结果不进入客户端。
- 决策：新建 [v8 设计说明](prototypes/v8/design.md)；D30 增加「原型 v8 的方向」；ADR-0018、D29、路线图、Stage 3 计划、总体架构、阶段需求总览改为在系统中登记机器、在项目中授权；应用层与接口层设计说明增加 `work_item.reorder`、`machine_authorization.save`、需要恢复备份的回滚、首页状态项与关键事实列表，删除候选相关的两个命令与 `ops.accept_responsibility`；Stage 3 计划第 5.3 节写明凭据被上游拒绝在 Stage 4 起进入等待模型服务；CONTEXT.md 增加「机器」。

## 2026-09-28 - 3.2D 浏览器与 computer use；质检的模型不能看图时提醒；评测模型由用户提供

- 背景：评测要在 Stage 3 结束之前完成，场景 1 需要质检操作网页，而质检工具的路线位置未定。用户要求参考 Codex。调研（[浏览器与 computer use 调研](research/browser-and-computer-use.md)）发现 Codex 的浏览器与桌面操作是一个常驻 JavaScript 运行环境加 `js(code)` 工具，实现不开源，内置模型全部支持图像；Playwright MCP 用可访问性结构操作网页，OpenCode 官方示例采用它；桌面程序的操作都依赖截图。
- 用户原话：「这里应该是computer use和浏览器工具，这里可以参考codex」「评测规定两边都用 DeepSeek V4.1 Flash，这个不成立。可以用gemini 3.8 flash」「我们会要求质检部门必须有vision能力」「Q4，安全的事情先放低优先级，跟着正常的浏览器mcp一致就行。 Q7，我会单独提供有视觉能力的模型，你无需再操心」「其他采纳建议」「这样吧，质检部门设置的时候，只进行提醒就行，不必强行要求支持图像。」
- 用户决定：
  - 新增 3.2D 浏览器与 computer use，依赖 3.2B 与 3.2C，排在 3.9 之前（[D34](requirements/browser-and-computer-use.md)）。浏览器使用 Playwright MCP，每一步给可访问性结构，模型能看图时附截图，截图保存为证据；computer use 在容器的虚拟屏幕中通过截图、点击与输入操作桌面程序。
  - 安全放低优先级，按普通浏览器 MCP 的默认做法运行。
  - 质检两个工具都可以使用，工程可以使用浏览器做研发自测，运维在 Stage 4 决定。
  - 部门定义写明建议能力，质检为图像输入；所选模型不具备时照常保存并提醒用户，请求时按模型实际具备的能力提供工具，不能看图时不提供 computer use，浏览器只给可访问性结构。
  - 评测模型由用户单独提供，有视觉能力，两边相同。
- 决策：新增 D34 与调研记录；路线图、Stage 3 计划、D32、评测场景设计、模型管理设计说明（第 5.6 节部门的建议能力）、需求与设计索引、阶段需求总览按这些决定修改；`CONTEXT.md` 增加「建议能力」。

## 2026-09-28 - 一台控制主机加远程执行；阶段按执行顺序重新编号；启动时自动继续

- 背景：架构师问 Yudao 在可以预见的时间内给谁用、运行在哪里，以及判断「做成了」的标准。用户回答只有自己一个人使用，会部署到多台电脑与树莓派一类的板子上；成功标准是能独立高质量交付，以及能长时间自我运行并自我修复（修复 Yudao 交付的软件）。
- 用户决定：
  - 控制核心、事件日志（SQLite）、工件存储、Provider 模块与观察者在一台控制主机上运行；执行环境是一个服务，有本机进程、本机容器、远程执行代理三种实现，用户在项目中登记机器；控制核心只有一个实例、不做主备、不换用服务端数据库，执行权没有期限与续期；以后的扩展途径是增加执行环境、增加模型连接、按项目分成多个控制核心实例，各有触发条件，部门不作为拆分单位（[ADR-0018](adr/0018-single-control-host-remote-execution.md)，取代 ADR-0012 中的两项与 ADR-0007 第 3 条中的期限一句；[D29](requirements/remote-execution.md)）。
  - 阶段按执行顺序重新编号：Stage 3 改名「通用工具、可靠恢复与执行环境」，新增 3.2C 执行环境服务（本机容器与远程执行代理），排在 3.1 之后、3.2B 之前，依赖 3.1 的动作核实与 #110；Stage 4 运维部门与长时间运行；Stage 5 部门内协作、上下文与界面；Stage 6 受治理的系统演化，包括元观察与规则检查部门（D28）与跨任务经验，暂时不做。原分布式部署阶段中的远程执行并入 3.2C，其余不做。
  - 同一项目一次只进行一个事项，按优先级排队，运维发起的修复事项排在用户的新要求之前；3.4B 同项目并行采纳不做。
  - 3.1 的恢复在 Yudao 启动时自动继续所有中断的 run，只有结果未知的外部动作通过用户决定交给用户；Yudao 由操作系统的服务管理在崩溃后重新启动（Stage 4）。
  - 模型服务中断：按 D17 重试用完以后仍然是连接失败、服务端错误、过载、限流，或凭据失效、证书校验失败时，run 暂停进入「等待模型服务」，按间隔重试，恢复后自动继续；进入等待时通知用户一次，用户可以取消；等待时间不计入 D09 的运行时间上限；请求内容错误与上下文过长不进入等待（Stage 4，[D17](requirements/provider-retries.md)、[D09](requirements/execution-limits.md)）。
  - 运维部门：观察交付软件的日志、状态与使用者的交互日志，发现的问题作为修复事项自动进入「产品 → 工程 → 质检」；用户登记运行环境时批准常设授权清单（部署质检放行的交付快照、回滚到上一个放行版本、重启服务、读取日志与运行数据），清单以外的动作通过用户决定交给用户；Yudao 修改自己的代码与规则暂时不做（[D27](requirements/operations-department.md)）。
  - 与单个 agent 的对照实验：Yudao 与单独运行的 OpenCode 通过 OpenCode Go 调用同一个能力一般的模型，任务集由架构师设计、用户审阅，每个任务两边各运行 3 次；3.9 组合验收时第一次执行，之后每个阶段结束时重复；结果决定 Stage 5 内各项工作的先后（[D32](requirements/comparison-experiment.md)）。
  - 部门内多角色在 Stage 5 对产品、工程、质检、运维四个部门一起引入。
- 决策：[总体路线图](program-roadmap.md)、[Stage 3 计划](stage-3-plan.md)、[总体架构](design/architecture/overall-architecture.md)、[恢复契约](design/recovery-contract-and-fault-matrix.md)、[应用层与接口层设计说明](design/app-and-interface.md)与各需求记录按这些决定修改；D29 的需求记录改名为 `remote-execution.md`。

## 2026-09-26 - 长期架构：十项决定与 ADR-0011 至 ADR-0015

- 背景：用户要求结合路线图、最近的架构讨论、原型与全部需求，从整体重新思考架构，至少保证很久够用。架构师核对了路线图各阶段、31 份需求记录、10 份 ADR、原型 v7 与现有代码，发现 #43 没有考虑 ADR-0007 的边界、恢复契约的同一事务、D24 的逐次解析、并发方式与后续阶段；文档之间有 18 处冲突。
- 用户决定（对 Q7 至 Q11 回答「采纳推荐」）：
  - 控制核心在一个异步事件循环中运行（[ADR-0011](adr/0011-async-control-core.md)），#43 的步骤驱动写成异步。

- 本条取代 2026-09-21 两条压缩记录中的「摘要输出上限固定 4096」与「摘要请求不带推理参数」。摘要为空或超限时本次压缩不生效，这一步的工作请求按未压缩的历史照常发送，下一步再次尝试压缩（参照 opencode）；未压缩的历史放不进窗口时事项失败结束。完整规则见[模型管理设计说明](design/model-management.md)。

## 2026-09-22 - 运行时间限制替代计数限制作为主要收敛保证

- 用户指令：「不用限额。进行时间限制即可，尽可能放开限制，确定收敛即可」。
- 事实：真实验收运行因计数限制（`max_cycles=12`、`MAX_MODEL_STEPS=32`）在模型提交前被暂停（`PAUSED / model_steps_exhausted`、`PAUSED / max_cycles`），无法完成交付。
- 决策：
  - 新增 `run_time_limit_sec`（默认 7200 秒）作为运行级挂钟时间限制，使用单调时钟在每次激活准备和每步之间检查，达到上限进入 `FAILED`（停止原因为 `time_limit`）。
  - `max_cycles` 默认值从 8 放宽至 999999，`MAX_MODEL_STEPS` 默认值从 32 放宽至 999999，实际运行中不再成为有效约束。
  - 保留计数限制的完整机制：调用方仍可显式配置较小值以恢复旧行为，达到上限时仍进入 `PAUSED`。
  - 终态选择 `FAILED` 而非 `PAUSED`：时间限制是系统强制停止，与取消、provider 错误等同类，不属于「暂停后可继续」的语义。
- 变更文件：`harness/models.py`、`harness/engine.py`、`harness/orchestrator.py`、`harness/projection.py`、`harness/projects.py`、`harness/web/server.py`、`harness/tests/test_run_time_limit.py`、`harness/tests/test_orchestrator.py`、`README.md`、`docs/requirements/execution-limits.md`。

## 2026-09-21 - 压缩在推理型模型上的失败形态与待决方向

- 事实：`mimo-v2.5`（推理型）在真实运行中多次进入 `FAILED / compaction_failed`，两种形态：`Compaction summary exceeds its output limit`（12000 窗两次，场景 C）与 `Compaction returned an empty summary`（32000 窗一次，3.2A 登记命令验收 `run_4280c207b68248cd`）。压缩调用在上游侧记录为 success，但正文为空或超限；两次压缩调用分别耗时 47s / 23s。
- 机制：`harness/compaction.py` 的 `response_reserve` 取 `max(窗口 15%, min(模型声明输出上限, 窗口/2))`；32000 窗且声明输出上限 4096 时预留 4800、摘要上限 4096。推理模型的 reasoning 与摘要正文共享该预算。
- 现状与设计一致（压缩失败 fail-closed，不静默截断），因此不按缺陷直接修改。
- 待决方向（需人确认，涉及 D10 压缩语义与 D17 重试边界）：
  1. 提高模型声明的 `max_output_tokens`。本机 4096 是验收发送上限而非服务商标称；需确认模型真实上限，不猜容量。
  2. 把"空摘要"归为可重试的模型输出畸形，走现有每次激活的重试额度（与"未声明工具却返回 function_call 归为可重试"同类先例）。
  3. 压缩请求抑制推理，需要协议或服务商级参数支持，属能力变更。
  4. 摘要改用非推理模型。部门绑定为单模型，属设计变更。
- 推荐：先做第 2 项（最小改动，不改变 fail-closed 与重试类别），同时确认第 1 项的真实上限；若仍不足以覆盖长工程会话，再评估第 3 或第 4 项。

## 2026-09-21 - 压缩请求输出预算固定为 4096，空/超限摘要不终止任务

- 参考实现：`sst/opencode` `packages/core/src/session/compaction.ts`（commit `70a24697ea0028e19f22712fd63059538cb4bee7`）。
- 新策略：
  - `SUMMARY_OUTPUT_TOKENS = 4096`：摘要请求的 `max_output_tokens` 固定为 4096，与模型声明的输出上限无关。推理模型的 reasoning 输出与摘要正文共享该预算，固定上限避免摘要被 reasoning 挤占。
  - 摘要请求发送 `tools: []`，不携带推理/provider 特殊参数（已确认 `assemble_compaction` 和 provider 适配器层均不发送）。

  - 预检：估算的摘要提示词 token 数超过 `context_window - SUMMARY_OUTPUT_TOKENS` 时不发送请求，返回"未压缩"。
  - 空摘要或超限摘要不终止任务（返回 None），部门继续工作，后续激活重试压缩。
