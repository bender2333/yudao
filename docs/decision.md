## 2026-10-25 - 用户只定走向、规则与试用结论；solo 跨 harness 一份规矩；内核工单事前批准

Argon 的工作流建议（四条）对照仓库后的取舍：

1. **用户的参与方式**写进 `CLAUDE.md`：不写代码、不逐张确认、不审不合 PR；平时看总图、对照表与一两个契约文件，与子架构师定走向，与总架构师定规则；里程碑或阶段结束时亲自试用。要用户决定的只有走向、规则、试用结论。
2. **solo 跨 harness**：规矩已经在 `AGENTS.md`「Solo 模式」，但它与 `/solo` 循环的工人契约（`.claude/skills/solo/worker.md`、`docs/agents/triage-labels.md`）对设计问题的处理相反（前者让执行者自己改设计，后者交回架构师）。统一成交回：工单太大、设计冲突、连续三次没过都标 `needs-triage` 交子架构师分诊，执行环境挡住才 `ready-for-human`。标签沿用 `needs-triage`，不用 Argon 建议的 `needs-architect`：那个标签在本仓库的含义是派发者启动架构师，solo 范围没有派发者，脚本与正在跑的循环也都用 `needs-triage`。
3. **内核工单事前批准**：原来 `/to-children` 把需你批准环的子工单一律标 `ready-for-human`，solo 做不了换骨架的活。改成批准在拆单时给：用户在场时同意「只改」清单，正文写批准行、加 `kernel-approved`、标 `ready-for-agent`；执行者只改清单内的文件，要改清单外的就交回，CI 过了按各自流程合并。审查者与 solo 合并前核对都认这个标签。总图第二节「只由你批准」的环没有变，变的是批准的时点。没有采用「内核行数守卫」的说法：CI 里没有这样的检查，不编。
4. **三个技能**交子架构师写：`/module-sync`（子架构师带用户看一屏体检卡，衔接 `/to-parents`、`/to-children` 与事前批准）、`/solo-worker`（单张工单的跨 harness 工人协议，从 `worker.md` 抽出，只留一份）、`/trial-intake`（试用前导游卡、试用后把口语反馈定位到代码与缝再分流建单）。

## 2026-10-01 - 网络取回与 MCP 工具

- 背景：用户 2026-09-30 把 3.2B 列为用 grill 讨论的专题。2026-10-01 在 Stage 3 待讨论的专题中选择专题 4，用 grill 讨论两轮共十二项，每轮回答「采纳建议」，随后确认修改清单。调研 OMP、OpenCode、Claude Code、Codex 的做法，官方 MCP Python SDK，以及国内可用的搜索类 MCP 服务器（[调研](archive/research/network-and-mcp-references.md)）。
- 决策（[ADR-0025](adr/0025-network-and-mcp-run-on-control-host.md)，[D36](requirements/network-and-mcp.md)，[设计说明](design/network-and-mcp.md)第 14 节）：
  1. 搜索经 MCP 提供，Yudao 不内置搜索工具；Yudao 自带的 MCP 服务只有 3.2D 的 Playwright MCP。
  2. 网络取回与登记的 MCP 服务器固定在控制主机上运行，与 run 的执行位置无关，执行代理不实现它们；凭据只在控制主机。
  3. 每个项目各自登记（项目流，带版本，事项创建时固定版本）；凭据按名称引用，使用与 Provider 相同的凭据来源。
  4. 登记就是常设授权；登记之外的取回与「使用前询问」的 MCP 工具经一次性批准，批准在本事项内对同一个主机或同一个工具有效，重启以后仍然有效；MCP 工具有三种处理方式，新读取到的默认「不提供」；项目没有登记时部门没有这两类工具。
  5. 评测期间两边都不联网（OpenCode 的运行配置关闭取回与搜索）。
  6. 取回只发 GET，不带凭据与 Cookie；拒绝回环、内网与链路本地地址并在解析以后检查，198.18.0.0/15 不在拒绝范围内（这台电脑的虚拟网卡代理把域名解析到这个范围）；Yudao 服务自己监听的地址与端口永远拒绝；明确登记的内网来源允许。
  7. MCP 登记：stdio 与 streamable HTTP，不支持 SSE 与 OAuth；只使用工具；读取工具清单后保存快照，模型看到的是快照；每个工具有处理方式与「结果未知时可以重新执行」两项。
  8. 每个 run 的每个服务器一个实例，第一次调用时启动；启动时限 60 秒、调用时限 120 秒、输出上限 20000 个字符；失败不停止事项；遗留进程在启动时结束。
  9. 取回结果未知时直接以新的尝试重新取回；MCP 结果未知时发出决定请求，调用超时先取消再发出决定请求。
  10. 取回与 MCP 的结果保存为外部来源工件，工具结果分页返回，可以作为「外部文档」证据；HTML 转文本，PDF 与图片不支持。
  11. 界面不做新原型：项目设置新增「网络与 MCP」一节，系统「工具与扩展」页只读汇总，批准卡片与调用显示沿用 v9 的房间动作。
  12. M3 试用与验收使用 Exa 官方 MCP（不填 Key）；登记的 MCP 服务器（#236）的验收使用 `mcp-server-time`（stdio）与 Exa（HTTP），MCP 客户端模块（#69）的验收使用 `mcp-server-time` 与 SDK 写的本机测试服务器。
- 核对的事实：
  - OMP 与 OpenCode 在 Windows 上退出时都不结束 MCP 服务器的整个进程树，也没有找到对回环与内网地址的拦截；官方 MCP SDK 在 Windows 上用作业对象结束进程树（实测）；官方 fetch 服务器可以读到 127.0.0.1。
  - 官方 `mcp` 2.2.0 在超时与取消时发送取消通知；Windows 上子进程只继承 12 个基础变量（上游 issue #3335）。
  - 这台电脑上所有域名解析到 198.18.0.0/16，Python 的 `is_private` 把它算作私有地址。
  - Claude Code 与 Codex 都有逐个工具的批准方式，批准可以只在一个会话内有效；取回按域名批准，跨主机重定向重新批准。
- 遗留：声明可以重复的动作，结果未知时是否自动重新执行（3.1 的规则，影响所有动作），记入需求概览第 6 节的待讨论清单。（2026-10-02 已确定，见下一条）

## 2026-10-02 - 结果未知的动作自动核实与自动重新执行

- 背景：3.2B 讨论中留下的专题 6。长时间无人值守运行时，Yudao 进程被终止、电脑重新启动或远程执行代理超时，都会让进行中的动作结果未知；现在的实现对每一个这样的动作都发出决定请求，只读的读取也是这样，运行停下来等用户。恢复契约第 4 节原先写着读取以新尝试重读、写入按快照核实，实现时简化成了全部询问。2026-10-02 用 grill 讨论两轮，用户回答「采纳建议」并确认修改清单。
- 决策（[恢复契约](design/recovery-contract-and-fault-matrix.md)第 4 节开头的三步）：
  1. 契约声明可以重复的动作（读取与搜索、检查、网络取回、登记时声明「可以重新执行」的命令与 MCP 工具），结果未知时以同一个逻辑动作的新尝试自动重新执行，不询问用户，也不另外通知；动作记录与房间的动作显示里看得到两次尝试与依据。

## 2026-10-07 - 原型 v10 的四项决定：来源的着色、步骤循环的取值、run 层只计有主机证据的条件、按字段的来源

## 2026-10-19 - 后台命令的记录随 Yudao 进程存在，按会话归属（#549，被唤醒的架构师）

- 背景：PR #615 的审查交回两个问题。一是 `read_output`、`stop_job` 没有加进任何部门的工具清单（`roles.json`、`work_items.json` 不在工单的「只改」里）；二是每次激活新建 `LocalEnvironment`（`orchestrator.py` 的 `_environment_for(..., refresh=True)`），后台命令记在环境实例上，下一次激活读不到也结束不了，进程继续运行。架构师在 main f0fba2bb 上核对，两条都属实。另外查出：检查工作区在激活开始时删除重建（`_new_inspection_environment`），里面有后台进程时，Windows 上删除会因为句柄占用失败，POSIX 上进程在删掉的目录里继续运行。
- 决策：
  1. 后台命令的记录属于执行环境一层，随执行环境的进程存在，与激活无关：本机是 Yudao 进程内一份，由会话的管理者 `SessionFactory` 建立并持有，编排器每次建立 `LocalEnvironment` 时把它和使用这个环境的会话身份交进去；远程是执行代理进程内一份。重新启动以后记录是空的，旧编号回答「已经结束」。
  2. 编号只对启动它的会话有效，别的会话用这个编号得到「已经结束」：部门的可见范围对 Yudao 提供的工具有效。
  3. 结束有三个时机：会话结束、事项暂停或取消（都经过 `SessionFactory.close_run`），以及删除工作区，包括检查工作区重建之前。
  4. 三个部门在每一处有 `bash` 的工具清单里都加上这两个工具。
  - 执行环境服务设计说明第 4.1 节增加「结束会话的后台命令」，读取与结束带会话身份，删除工作区一行写明先结束其中的后台进程；第 4.6 节的路径同步。本地通用工具设计说明的命令一行已经写明会话结束、暂停、取消时结束，这次不改（它是 #616 的依据）。
- 没有采纳的：模块级的全局表（测试里几个编排器共用一张，模拟不了重新启动）；记在 `DepartmentSession` 上（会话一层不持有进程，3.2C 以后后台进程在执行代理进程里）。
- 影响：`docs/design/execution-environment.md` 第 4.1、4.6 节；#549 的任务评论（「只改」加 `roles.json`、`work_items.json`、`orchestrator.py`）；#550 的正文（是否运行中以后台命令的记录为准，「只改」加 `harness/environment.py`）；#558 加 `touches-core`。

## 2026-10-21 - 询问分支的时间上限在安全节点检查（#553，被唤醒的架构师）

- 背景：PR #641 第 3 次要求修改，达到上限搁置。第 3 轮审查的三条：集成层的 `test_ask_branch_exhausted_by_run_time_limit_ends_with_unable` 用 1 秒的运行时间上限与阻塞的等待，分支之前的步骤一慢就在询问之前用完时间，CI 上失败；`min(declared_time, remaining_time)` 的剩余时间一侧没有用例能区分；`_recover_run_usage` 改成取最大值，没有用例能区分。在 d08d54f6 上核对：分支的时间上限用 `asyncio.wait_for` 给步骤驱动加硬期限，超时把取消传进步骤驱动的任务，然后吞掉等待结果时的全部异常；分支的安全节点本来就检查事项的运行时间（`_stop_requested` 的 `time_used_up`）。
- 决策：
  1. 分支的时间上限和事项的运行时间用同一种做法：分支的激活带上期限（分支开始的时刻加声明值），安全节点在期限到了时回答停止，模型回应里没有执行的工具按现有的跳过记录。依据：ADR-0031 规定停止在安全节点由代码保证、单次请求与单个动作各有时限；`StepDriver.cancel` 的取消落在正在进行的这一项上，记录与没有取消时走同一条路径。硬期限让步骤停在记录的中途，还要靠吞掉异常收尾，违反共同规则的 fast-fail 一条。
  2. 事项剩余时间这一侧由安全节点已有的运行时间检查负责，不另算剩余时间，也去掉时间为 0 时不开分支的提前结束：提问方的运行时间用完时，提问方在执行询问之前的安全节点就停止。分支实际的时间上限仍是声明值与事项剩余时间中较小的一个。步骤一侧不变。
  3. 分支交回回答就记为已回答：回答能交回，说明执行回答工具之前的安全节点已经放行。没有回答时，期限到了或事项运行时间用完，原因写时间上限。
  4. `_recover_run_usage` 取最后一个 `activation_finished` 的累计值（main 的写法）。分支结束事件改写累计值以后，一个事项里的累计值按写入先后不减，最后一个就是最大的。
  5. 运行时间的用例改用 3 秒上限与 4 秒的分支等待，与 `kernel/test_limits_survive_restart.py` 的 3 秒相同；分支之前的步骤在本机约 0.17 秒。架构师在临时 worktree 上按以上做法改过一次（已删除）：询问分支、动作恢复、用量恢复、引导中断与事件序列基准的用例全部通过，基准没有变化；去掉期限检查时，声明时间的用例失败。
- 没有采纳的：保留硬期限，用流式的假模型回应拉开用例的余量（第 3 轮审查的建议）。这样两种停止方式并存，硬期限的问题留在控制核心里。
- 影响：工单 #553（任务评论，标签改为 `ready-for-agent`）。设计说明、ADR 与定义不改。分支的期限只在进程内存中：现在部门没有声明时间上限，生产上分支的时间上限就是事项的运行时间，它跨重启累计；部门的声明加入定义时，分支已用时间跨重启的累计一起设计。

## 2026-10-22 - 查看交付时不再重算核对 Git 材料（用户）

- 事实：查看一份正式事件的版本（`event.detail` → `git_version_detail`）时，代码按事件日志用当前代码重新拼出全部材料，与 Git 里存的逐字节比对，对不上就报错。#637 删掉 `ProductDecision.request_id` 以后，之前写下、带产品决定的 run，之后的交付都读不出来（#714、#722）。
