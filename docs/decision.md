# 决策记录

## 2026-09-26 - 总体架构：每次请求在控制核心装配，教训由独立模块发现，反复退回时提醒用户

- 背景：架构师把语义系统设计说明与总体架构草案（[职责分层](design/architecture/overall-architecture.md)、[控制核心与可替换的材料](design/architecture/core-and-materials.md)）及 [Loop System 原理](archive/native-harness/loop-system-principles.md)核对，发现草案第 4 节「会话内的上下文由执行者用同一份装配器代码演变」与 D25 的栏目规则冲突，D25 让刚失败的角色写出教训与原理中的 Distiller 冲突，D26 在同一计划条目反复退回时没有处理。
- 用户决定：每次模型请求由控制核心装配；自有角色不设单独的会话执行者，控制核心驱动每个角色任务的步骤；执行层只有 Provider、执行环境与工具、外包 agent；控制核心的边界是裁决不使用模型（[ADR-0010](adr/0010-control-core-drives-role-steps.md)）。
- 用户决定：语义系统分布在知识层（本体、投影、状态推导、核对、查询）、控制核心的 P（栏目、目录、接触时附加、通知、清理与节录）与 U（按本体校验、安排整理与复盘），以及观察层（证据核对作为一种判定点），见[职责分层](design/architecture/overall-architecture.md)第 3 节。
- 用户决定：教训由另一个模块产生，这个模块单独审查事件与事实、找出教训，可能与元观察结合，考虑使用主动推断与自由能原理，待设计；角色不写出教训（[D25](requirements/semantic-system.md)）。
- 用户决定：同一计划条目反复被审查退回时提醒用户，角色不从新的历史开始（[D26](requirements/department-roles.md)）。
- 用户决定：洞见也由教训发现模块找出，只能通过查询取得；复盘写出或更新画像、合并重复的实体（D25 已确认第 28 条）。
- 用户决定：ADR-0010 的控制核心重构单独立一张行为不变的重构工单，排在 3.2A 之后、3.1 的 #16 之前；#22 中依赖它的子工单在工单建立后补上原生依赖（[总体路线图](program-roadmap.md)第 2 节）。工单为 [#43](https://github.com/bender2333/yudao/issues/43)。
- 用户决定（#43 的重构计划）：第一个提交加入事件序列对照，此后每个提交的事件序列必须与基准一致；并发不在这次重构范围内；测试只从 `LoopSystem` 驱动或调用新模块的公开接口，重试与步数改为参数；smoke 的上下文审计改用 P 的接口重新装配。流程编排与步骤驱动之间除开始、取消、取得结果之外，只有一个由流程编排提供的安全节点接口，新输入的分派在其中完成。
- 决策：控制核心内部分为流程编排、步骤驱动、上下文装配、裁决规则、事件库与运行状态投影，流程编排只调用步骤驱动的开始、取消与取得结果；工具分主机工具与环境工具，查询范围由控制核心按角色身份填入；投影随事件写入逐步更新并保存，从头重放只用于重建与核对。依赖方向与分层表分开写明。
- 决策：architecture-docs-on-main 合并进主分支；worktree-docs-research-frontend-libs 的内容已被它包含，只并入提交历史；两份 Loop System 文档纳入版本管理。

## 2026-09-25 - 语义系统：整理与上下文组装分开，轨迹与七类图谱内容

- 用户声明：语义系统不是 RAG，也不是长期记忆；它参照 Semantica，是带有知识、事实、证据等内容的知识图谱，给 Agent 做上下文用。Agent 最重要的是上下文管理，语义系统分为整理与上下文组装两部分；上下文组装列为重点 TODO，专题讨论。
- 用户决定（整理部分）：轨迹分事项、交接、计划条目、角色任务、尝试五层，只有一份，部门账本是它在部门这一层的视图；轨迹的上面几层由主机从事件生成，尝试由角色在任务结束与压缩之前整理；图谱内容分证据、事实、知识、决定、要求、实体、推测七类，事实必须附证据；角色在工作中随时记录图谱内容，主机校验后写入，压缩之前补录；轨迹与图谱只由事件生成；要求类条目带稳定编号，主机校验引用，质检放行要求每条有效验收条件都有通过的检查结果与证据。
- 用户决定（第三轮）：轨迹最低一层称为「尝试」，与「调用尝试」在术语表中区分；证据出现新版本、要求被修改或废止时，主机把受影响的内容标为待复核，矛盾的新事实必须写明取代哪一条或记录为冲突；所有部门可见事项层与交接层的轨迹、要求类条目、主机接纳的材料内容与实体名称，计划条目以下的轨迹与部门记录的内容只有本部门可见；知识只在本项目的本部门内使用，跨项目复用属于持续改进工作线；用户可以查看轨迹与图谱、把部门记录的内容标为失效或写入更正，轨迹只能查看；第二项职责中演化使用轨迹与决定，语义工程包括项目术语表以及教训、洞见等语义。
- 用户决定（第四轮）：抽象层包括教训、洞见、画像，必须关联依据；教训随时记录，复盘在成果被接纳后与事项结束时由中心角色进行；教训是参考内容，主机不强制执行，需要强制的成为规则候选；抽象层属于部门私有，画像按部门各自编写，跨项目复用属于持续改进工作线；Semantica 不作为依赖，借用 PROV-O 对应、四个时间字段、决定与因果、本体加约束形状、冲突类型，轨迹与图谱是存放在现有 SQLite 中的事件投影；本体由系统定义，实体类型为固定清单，领域概念作为术语类实体；关系分八组；不记录模型给出的置信度。依据见 [Semantica 参照调研](research/semantica-reference.md)。
- 用户决定（第五轮）：压缩不再生成文字摘要，由角色整理的尝试（进行中的尝试写明目标、已完成的部分、下一步、正在处理的文件与未完成的操作）与补录的图谱内容代替被移出的历史，整理失败按模型管理设计第 8.7 节处理，D10 中「摘要」的含义随之修改；实体身份由「类型 + 名称」确定，在第一次被引用时建立，文件的移动与删除由主机按工作区变化记录，其他重复实体在复盘时合并。用户另外提出惊讶值：模型固有的认识或动作得到的结果与预期不符时，记录这次事件并记住相关的知识与教训。
- 用户决定：语义系统只保留由惊讶得出的知识、教训等内容，并标明来源；惊讶怎样发现、怎样与基础的事件系统结合，单独专题讨论，参考主动推断与自由能原理。整理部分的讨论至此完成。
- 用户决定：惊讶机制以及随之而来的事件系统整理是复杂的演化系统，放到后面进行；当前的设计必须让它们以后能正常接入。
- 用户决定（上下文组装专题）：参考 OMP 与 opencode 的实现；术语只使用「上下文组装」，每次请求由固定的栏目组成，每个栏目写明来源、上限与重新计算的时机，放入的内容由上下文清单记录。
- 用户决定（上下文组装第二轮）：主机只主动放入有效与待复核的内容，冲突成对显示，事实与知识附证据种类，不计算综合可靠分数；记录事实时用 JEV 核对证据是否支持陈述，只用于外部文档与需要解读的运行输出，按 D28 的规则校准通过后才显示并可以使事实变为待复核，JEV 的协议接入由 Stage 5 提前到 Stage 4；常驻栏目、目录、按需取得、接触文件时附加四种方式配合使用；组装只按结构关系与固定规则，不调用模型，清单记录每条内容的放入原因；栏目按变化频率从少到多排列，历史只追加，当前状态栏目放在末尾、每次重新计算且不写入历史，工具定义在一次任务中不变，按协议设置缓存断点或缓存键；压缩阈值不超过工作上限 100000 token；达到阈值时先把最近 40000 token 之外的工具结果换成带取回地址的占位，节省不足或仍超过阈值时再压缩。依据见 [上下文组装：参照调研](research/context-assembly-reference.md)。
- 用户决定（上下文组装第三轮）：变更与新到达的输入由主机在下一个安全节点作为通知追加进角色历史，送达对象沿用 D26，图谱状态变化由主机直接通知受影响的角色，当前状态栏目只放当前状态；目录列出与焦点（中心角色的进行中计划条目、工具角色的分派说明引用）一步相连的内容，上限 2000 token；各角色的上下文按 D25 专题第 11 条分配，审查者只附加知识与教训，看不到部门记录的事实、决定、推测与画像；压缩后历史开头放主机按轨迹节点生成的轨迹节录，上限 13107 token，接触时附加的记录清空；查询只用结构条件与 SQLite FTS5 trigram 全文检索，不用向量检索，工具分查询图谱、查询轨迹、读取来源、读取材料四个；画像每份 2000 token 并在写入时校验，常驻教训合计 4000 token，接触时附加每个实体 2000 token，规则、intend 原文与当前有效要求不截断。
- 用户决定（上下文组装第四轮）：项目上下文文本只保留项目名称、长期目标、当前采用的成果与本事项，已采纳事项列表与仍有效的决定由项目画像与事项层轨迹提供；未采纳事项中知识与教训继续有效，事实、决定、推测与画像只能查询并标注来源；进行中的其他事项的内容在结束前不可见；JEV 校准样本属于系统，按固定版本校准，两批各 200 条，强 LLM 给出参照标注，分歧样本与 10% 抽样由用户裁定，「不支持」的精确率达到 0.9 才启用；界面按栏目显示来源、用量与放入原因，点击角色查看焦点、目录与已附加的实体，增加「上下文」覆盖层。
- 用户决定（上下文组装第五轮）：常驻栏目中的当前有效要求只包括本事项 ProductSpec 的要求、验收条件与约束；项目中其他有效要求通过接触时附加（关联在所接触文件上的要求与验收条件）、目录与查询取得，产品架构师起草时用查询分页取得项目的全部有效要求；部门账本在中心角色与经理的当前状态栏目中显示，进行中与未开始的计划条目完整显示，已完成的每条一行，经理只看到未通过的数据流核对项，上限 4000 token。
- 决策：路线图中 JEV 的协议接入由 Stage 5 移到 Stage 4；模型管理设计说明第 8.3 节的压缩阈值、第 8 节的工具结果处理，在语义系统设计说明改写时一起修改。
- 决策：语义系统设计草案原先的「语义单元、检查点事后整理、检索」思路被取代，整理部分讨论完成后按 [D25](requirements/semantic-system.md) 改写；检索方式、语义视图上限与各角色看到的内容移入上下文组装专题。术语写入 [CONTEXT.md](../CONTEXT.md)。

## 2026-09-25 - 部门内部：中心型协作，审查者、交出条件与预测性探索

- 用户决定：三个部门都采用中心型协作，中心角色分别是产品架构师、工程架构师、测试工程师；探索者、主程（原「开发者」）与审查者是中心角色的工具，由它分派任务、安排审查与返工，中心角色不做工具角色的写入工作；经理负责对外沟通，在中心角色认为完成后按主机检查提交部门成果，并关注部门进度与数据流转、发现问题时提醒中心角色，不分派部门内的工作。三个部门都设审查者（产品审查者、工程审查者、质检审查者），每次从新的上下文开始；部门向外层提交的每份成果都要通过主机按部门规定的检查，其中包括针对该版本的审查通过记录；外层返工从部门账本接着做；部门对外只有经理一个接口。可以同时进行的工作包括探索者的多项查证、审查与作者的下一项工作、设计与实现分段进行、质检提前设计检查；PRD 被接纳后各部门可以做预测性探索（只读查证并起草草案，有空闲槽位时进行，PRD 更新后全部作废）。一次性角色不设同时任务数与请求数上限；连续 3 轮没有进展时重新规划；角色设置优先于部门设置；角色历史不跨事项延续。画面上部门内由小人走到工位递卡片，部门之间经过管道。

## 2026-09-22 - 运行时间限制替代计数限制作为主要收敛保证

- 用户指令：「不用限额。进行时间限制即可，尽可能放开限制，确定收敛即可」。
- 事实：真实验收运行因计数限制（`max_cycles=12`、`MAX_MODEL_STEPS=32`）在模型提交前被暂停（`PAUSED / model_steps_exhausted`、`PAUSED / max_cycles`），无法完成交付。
- 决策：
  - 新增 `run_time_limit_sec`（默认 7200 秒）作为运行级挂钟时间限制，使用单调时钟在每次激活准备和每步之间检查，达到上限进入 `FAILED`（停止原因为 `time_limit`）。
  - `max_cycles` 默认值从 8 放宽至 999999，`MAX_MODEL_STEPS` 默认值从 32 放宽至 999999，实际运行中不再成为有效约束。
  - 保留计数限制的完整机制：调用方仍可显式配置较小值以恢复旧行为，达到上限时仍进入 `PAUSED`。
  - 终态选择 `FAILED` 而非 `PAUSED`：时间限制是系统强制停止，与取消、provider 错误等同类，不属于「暂停后可继续」的语义。
- 变更文件：`harness/models.py`、`harness/engine.py`、`harness/orchestrator.py`、`harness/projection.py`、`harness/projects.py`、`harness/web/server.py`、`harness/tests/test_run_time_limit.py`、`harness/tests/test_orchestrator.py`、`README.md`、`docs/requirements/execution-limits.md`。

## 2026-09-21 - 压缩在推理型模型上的失败形态与待决方向

- 事实：`mimo-v2.5`（推理型）在真实运行中多次进入 `FAILED / compaction_failed`，两种形态：`Compaction summary exceeds its output limit`（12000 窗两次，场景 C）与 `Compaction returned an empty summary`（32000 窗一次，3.2A 登记命令验收 `run_4280c207b68248cd`）。压缩调用在上游侧记录为 success，但正文为空或超限；两次压缩调用分别耗时 47s / 23s。
- 机制：`harness/compaction.py` 的 `response_reserve` 取 `max(窗口 15%, min(模型声明输出上限, 窗口/2))`；32000 窗且声明输出上限 4096 时预留 4800、摘要上限 4096。推理模型的 reasoning 与摘要正文共享该预算。
- 现状与设计一致（压缩失败 fail-closed，不静默截断），因此不按缺陷直接修改。
- 待决方向（需人确认，涉及 D10 压缩语义与 D17 重试边界）：
  1. 提高模型声明的 `max_output_tokens`。本机 4096 是验收发送上限而非服务商标称；需确认模型真实上限，不猜容量。
  2. 把"空摘要"归为可重试的模型输出畸形，走现有每次激活的重试额度（与"未声明工具却返回 function_call 归为可重试"同类先例）。
  3. 压缩请求抑制推理，需要协议或服务商级参数支持，属能力变更。
  4. 摘要改用非推理模型。部门绑定为单模型，属设计变更。
- 推荐：先做第 2 项（最小改动，不改变 fail-closed 与重试类别），同时确认第 1 项的真实上限；若仍不足以覆盖长工程会话，再评估第 3 或第 4 项。

## 2026-09-21 - 压缩请求输出预算固定为 4096，空/超限摘要不终止任务

- 参考实现：`sst/opencode` `packages/core/src/session/compaction.ts`（commit `70a24697ea0028e19f22712fd63059538cb4bee7`）。
- 新策略：
  - `SUMMARY_OUTPUT_TOKENS = 4096`：摘要请求的 `max_output_tokens` 固定为 4096，与模型声明的输出上限无关。推理模型的 reasoning 输出与摘要正文共享该预算，固定上限避免摘要被 reasoning 挤占。
  - 摘要请求发送 `tools: []`，不携带推理/provider 特殊参数（已确认 `assemble_compaction` 和 provider 适配器层均不发送）。
  - 摘要仅从可见文本 delta 收集；reasoning 类型的输出被忽略。
  - 预检：估算的摘要提示词 token 数超过 `context_window - SUMMARY_OUTPUT_TOKENS` 时不发送请求，返回"未压缩"。
  - 空摘要或超限摘要不终止任务（返回 None），部门继续工作，后续激活重试压缩。
  - 序列化历史时，工具输出截断为 `TOOL_OUTPUT_MAX_CHARS = 2000` 字符。
  - 真正的"无法容纳"场景（固定原文与当前工作超出窗口）仍然明确停止。
- 变更文件：`harness/compaction.py`（新增常量、截断、预检、非致命空/超限）、`harness/orchestrator.py`（`_finish_compaction` 处理 None 返回值）。
- 现有 `test_three_undeclared_tool_calls_fail_compaction` 测试不变：适配器级的协议畸形（未声明工具却返回 function_call）仍走引擎重试→耗尽→FAILED 路径，与 `finish_compaction` 的非致命处理是不同的错误路径。
