# 恢复契约与故障矩阵

总图位置：第六节三个硬问题的第二、三个；第四节「动作」的缝里的核实方法。依据：[ADR-0038](../adr/0038-function-first-commands-without-registration.md)（结果未知的动作在自动核实以后交还发出它的会话，由模型决定是否重新执行，第 4 节与故障矩阵）；[组织与持续运行研究](../research/organization-runtime-evolution.md) 第 6、10 节。

范围：研究原表标题沿用“十二项”，实际列了 13 行，本说明按 13 个具名场景核对，避免漏掉“恢复与取消/撤销并发”。

## 1. 四种能力分别验收

| 能力 | 目标 |
| --- | --- |
| 事实重建 | 新增恢复事实也可重建，查询不调用模型和工具 |
| 观察恢复 | 页面重连补事实；区分运行中、中断、待恢复（机器离线时显示等待机器）和四种结束方式——已完成、已暂停、已取消、已停止（结束的方式分开，正常完成不是「已终止」） |
| 控制恢复 | Yudao 启动时自动继续所有中断的 run：run 事件版本相同时单机取得唯一执行权，从一致边界继续同一 run；不同时旧 run 不恢复，按强制升级处理：记为因升级停止，对应的事项用项目的起点重新开始（[项目的起始文件夹设计说明](project-initial-files.md)第 2 节）并排在队列最前面 |
| 动作恢复 | 分清未发出、已完成、部分完成和未知；按动作契约继续或停止核实 |

调用目标在每次模型请求时按项目部门设置与部门默认解析（[模型管理设计说明](model-management.md)第 5.4 节），恢复后的下一次请求同样按当时的设置解析，凭据按引用从宿主重新解析；恢复不依赖事项创建时的模型快照。

## 2. 最小恢复依据

恢复读取以下持久事实，不依赖模型总结或进程内存：
- 项目、事项、run 的身份，当前责任、有效意图/合同/计划及输入版本。
- 当前应用版本声明的 run 事件版本（[ADR-0019](../adr/0019-project-stream-across-versions.md)）；每次模型请求记录的调用目标、选择来源与部门 Prompt 版本（[模型管理设计说明](model-management.md)第 6 节）。
- 执行所有权、每次重新取得执行权的身份、停止/取消决定。
- 已消耗的激活次数、模型步骤和重试尝试，以及已用的运行时间（在每个安全节点写入事件，进程重启以后从事件恢复，连续累计；等待期间不计入）；压缩也计入原有限额。
- 每个逻辑动作的身份、输入依据、执行尝试、派发意图、已知结果及结果未知的原因。
- 已保存的完整模型响应、已执行工具及尚未执行部分；有效部门历史与压缩来源。
- 工作区一致边界、已确认交付与检查、Git/封存身份和项目采纳状态。

只增加当前恢复需要的事实，不提前设计通用等待 DSL、技能版本平台或 token/资金预留系统。Provider 用量是事实记录，缺失不是零。

## 3. 执行权与一致边界

恢复的触发：Yudao 启动时重建状态，然后自动继续所有因进程中断而未结束的 run，不等待用户操作；结果未知的动作按第 4 节自动核实，核实不出确定结果时交还发出它的会话，由模型决定。模型引用无法使用时 run 进入待恢复，用户修复配置后经命令继续。等待模型服务、等待机器、等待桌面、等待桌面解锁各有时长上限，超过时发出决定请求并通知用户一次；等待用户的决定没有上限，由用户结束。Yudao 进程由操作系统的服务管理在崩溃后重新启动，属于 Stage 4 长时间运行。

同一 run 同时只有一个有权推进的执行者。取得/变更执行权与相关领域提交在同一 SQLite 事务序列内核对。执行权由控制核心持有，没有期限与续期（[ADR-0018](../adr/0018-single-control-host-remote-execution.md)）：控制主机上只有一个控制核心，执行权编号用于进程重启与两个进程同时恢复的情况。锁定与释放不能仅依赖线程对象；两个进程同时恢复最多一个成功。

每次模型/工具分派和领域接纳都核对当前权利与有效合同。旧结果可以被记录为迟到事实，已发生的用量保留，但旧执行者不能接纳提案、推进阶段或发出新的合法动作。

这仍不能让已发出的子进程消失。因此，接管前必须核实旧进程树和未完成写动作：
- 旧执行者仍有效时，恢复请求被拒绝。
- 旧执行者失联但可能继续写入同一工作区时，暂停新冲突动作，先终止/隔离并确认，再核对工作区。
- 只在持久层拒绝旧结果、却放任它继续改同一目录，不算恢复可靠。
- 单机进程锁、进程树和数据库事务的组合须实测；不预先引入分布式租约服务。

一致边界包含领域事件及其所引用的完整工件。工具部分效果不因缺少完成事件就回到“没发生”。崩溃中留下的 PRD/PLAN、代码、封存或 Git 对象，按正式接纳事实及工具前后依据核实；不得只看磁盘存在就沿用为正式结果。

恢复过程中仍可收到输入或取消。它们在同一持久控制顺序中决定合法行为；已取消任务不可恢复，恢复先开始也不能阻止后来取消停掉后续分派。

## 4. 动作分类与处置

结果未知的动作按以下顺序处理：

1. 先按动作的核实方法自动核实。Yudao 自己的文件工具（写入、编辑、删除、移动）把动作前的快照、动作参数与工作区现在的状态对比：只有这个动作要改的路径变成参数中的目标内容、其他都没变时，记录核实记录确认已完成，依据是这次对比，不补造原来的成功回执；工作区与动作前的快照相同时，确认动作没有发生。核实出确定结果时交回这个结果。run 的工作区只有持有交接的工程写入，这个对比可靠。
2. 其余作为工具结果交还发出它的会话，写明执行被中断、结果未知，附上已经收到的输出，由模型检查以后决定是否重新执行。

| 动作 | 中断后核实什么 | 可以怎样继续 | 不允许的做法 |
| --- | --- | --- | --- |
| 只读搜索/阅读 | 当时材料版本和输出是否完整 | 已完整则复用；否则在有效材料上以新尝试读取 | 静默把变化后的内容冒充旧读取结果 |
| 写入/编辑/删除/移动 | 动作身份、前置内容、预期效果、实际树、其他写者及动作回执 | 按上面第 1 步自动核实：能证实已完成则记录核实依据；其他情况按第 2 步交还发出它的会话 | 单凭“文件恰好等于目标”补造原执行成功回执，或覆盖未知人工修改 |
| 本地命令与检查 | 进程树是否仍在，输出/退出记录是否落盘，执行副本和结果是否匹配 | 仍在则等待或取消；已完成则复用有效证据；其余按第 2 步交还发出它的会话，附上已经收到的输出；检查在全新的检查副本中运行，结果未知时由模型决定是否重新运行；后台命令在重新启动以后记为已经结束 | 把超时当作未执行；把重复尝试当两次独立检查 |
| 模型请求/压缩 | 完整响应与工具调用是否保存，尝试是否占用，摘要是否已接纳 | 完整响应从未执行动作继续；未知尝试保留未知用量，按 D17 分类和剩余次数处理 | 自动重试所有解析错误，执行半截工具参数，重置步骤或重复已接纳摘要 |
| 领域提交/项目采纳 | 已接纳事件、合同/计划/代码树和采纳基线 | 已完成则跳过；缺少正式接纳则按当前依据重新校验；采纳幂等补齐 | 只因工具返回成功就认为正式成果的提交或采纳已完成 |
| 网络取回（3.2B） | 这次尝试有没有完整结果与外部来源工件 | 按第 2 步交还发出它的会话，由模型决定是否重新取回；重新取回是同一个逻辑动作的新尝试，两次尝试分别记录（[网络取回与 MCP 工具设计说明](network-and-mcp.md)第 8 节） | 把没有完整结果的尝试当作已完成；把两次取回当作同一个结果 |
| MCP 工具（3.2B） | 动作记录；没有可以验证的查询 | 按第 2 步交还发出它的会话，由模型决定是否重新调用；调用超时先发取消通知并结束 stdio 服务器的进程树，再按同样规则处理 | 自动重试；把服务器标注的只读、幂等提示当作真实无副作用保证 |
| 发布（Stage 4） | 对方是否有动作身份、查询、去重、取消与核实能力 | 在 Stage 4 运维部门单独给出处置契约 | 把 GET/工具名称或幂等标签当作真实无副作用保证 |
| 采纳写回（3.8 B8） | 采纳与命令身份、三份代码树、最终树摘要与检查回执、远端分支提交、合并请求身份 | 按 [ADR-0034](../adr/0034-adopted-change-writeback-three-tree-merge.md) 核实：远端已有对应结果时记录核实事实；明确未发生且前提仍满足时继续；无法确认时保持待核实。目标分支推进后重新合并并核验 | 冲突时覆盖一侧、核验前推送、未知时重复创建分支或合并请求、把原快照的放行用于合并后的树 |
| 试用会话、浏览器与屏幕动作（3.2D） | 按尝试身份查询执行代理的动作记录与会话记录；试用会话是否仍然存在 | 只读动作以新尝试重做；改变页面或程序的动作在会话仍然存在时按当前实际状态继续，依据是新取得的页面结构与截图，会话不存在时记为中断，桌面会话中断时结束被测程序并恢复被最小化的窗口；桌面锁定时屏幕动作不发出，等待解锁；所在试用用例不能以通过结束（[浏览器与 computer use 设计说明](browser-and-computer-use.md)第 5.1、9 节） | 重做改变页面或程序的动作；把含结果未知步骤的试用用例作为放行证据 |

每类动作契约必须回答：谁有权做、作用于什么、怎样识别同一动作与不同尝试、成功证据是什么、结果未知时向哪里查、何时可重复、取消能否确认停止、谁负责未解决结果。副作用没有可验证恢复方法时，部门发出的动作按第 2 步交还发出它的会话；主机发起的动作（例如采纳写回）保持结果未知，等待下一次核实；不自行发明补偿动作。

核实可以产生新的核实记录，不能改写原始观察。恢复页展示最后已确认位置、重新启动时结果未知的动作及其处理（核实确认或交还会话）、核实依据；等待机器时另外展示机器名称与已经等待的时长。

## 5. 角色任务的恢复

[部门内多角色](department-roles.md)中，角色任务是执行与恢复的单位。进程重启后，先按第 3、4 节核实未完成的动作，核实结束后再继续角色任务。

| 对象 | 恢复方式 |
| --- | --- |
| 连续角色的任务（主程） | 从原历史继续同一任务 |
| 一次性角色的任务（探索者、审查者） | 一次性角色不写入文件，重新运行该任务：从新的上下文开始，分派说明不变。每个任务只有一份被接纳的角色结果：结果已被接纳的任务不再运行，旧执行者迟到的结果只记录、不接纳 |
| 预测性任务 | 按当前 PRD 版本决定：依据的仍是当前版本时，按所属角色的方式继续；PRD 已更新时作废，已有结果一起作废（部门内多角色设计说明第 11.2 节） |
| 中心角色与经理 | 等待继续：等待角色结果、回答或槽位的状态从事件中恢复，两者都从原历史继续 |
| 进行中的步骤 | 由步骤驱动从已提交的状态重新装配后继续：下一次模型请求按当时的设置解析调用目标（第 1 节）并重新装配；已保存的完整模型响应从尚未执行的工具调用继续（第 4 节） |

- 执行权编号在写入口与领域写入一起核对（第 3 节）；旧执行者的角色结果、提案与动作回执只记录，不接纳。
- 恢复不重置限额与已用运行时间（第 2 节），不复活已取消的角色任务（第 3 节）；等待执行槽位的任务保持排队。

## 6. 故障矩阵

以下每行都须有版本、注入位置、持久证据与预期结果。3.1 只关闭适用行，明确后置的行在 3.2C、3.4A 与 Stage 5 部门内多角色补齐；不能把“不适用”写为通过。

| # | 故障场景 | 必须成立的结果 | 验收归属 |
| --- | --- | --- | --- |
| 1 | 事项或部门关注的成果已接收、部门尚未开始工作 | 重启找到未完成责任；run 未创建时补建或明确失败，不能丢任务或重复创建 | 3.1 |
| 2 | 分派意图已保存但无接收/结果 | 用同一动作身份关联核实；未知发送不等于没执行 | 3.1 |
| 3 | 文件/命令/模型已完成，本地确认未保存 | 核实真实效果后复用或受控重试；无盲目重复副作用 | 3.1；远程执行代理上的动作在 3.2C 重验；新增网络动作在 3.2B、外部动作在 Stage 4 运维部门重验 |
| 4 | 两个进程同时争取同一 run | 最多一个可以推进；事务中校验执行权，旧结果不能改变领域状态 | 3.1 |
| 5 | 旧执行者失权后仍有动作/子进程 | 拒绝新分派；对已经发出的动作核实，不与未知旧写者同时改同一目录 | 3.1 |
| 6 | 并行的一项失败 | 已成功的独立事项不重跑，失败事项单独恢复；整体状态如实呈现 | 3.4A；父子节点在 Stage 5 部门内多角色补验 |
| 7 | 模型输出不完整或无法解析 | 原输出和已知用量保留；沿用现有错误分类与次数限制，不添加通用自动重试 | 3.1 |
| 8 | 数据库/工件/封存/Git 写入失败 | 没有持久接纳就没有成功确认；残留文件不能伪装成正式成果 | 3.1 |
| 9 | 页面/SSE 断开 | 重连只补观察；不新建 Worker、不重发模型或工具 | 3.1 |
| 10 | 应用版本变化，或模型引用无法使用（定义被移除、准入已作废、窗口未知、凭据缺失） | 按 [ADR-0019](../adr/0019-project-stream-across-versions.md)：项目流跨版本读取；run 事件版本相同时直接继续；不同时旧 run 不恢复，排空期间由用户发起的强制升级与启动时发现版本不同的未结束 run 同样处理：把 run 记为因升级停止，对应的事项用项目的起点（有采纳成果时是采纳成果，没有采纳成果时是项目的起始文件夹，都没有时是空树）重新开始并排在队列最前面，不发决定请求；模型引用无法使用时待恢复，写明部门、模型与具体问题，修复配置后继续执行；上游拒绝凭据与证书校验失败按 D17 进入等待模型服务（Stage 4），等待有时长上限（`wait.model_service.max_sec`，暂定默认值）；角色的模型失败时系统不自行改用其他模型或 Prompt，不热解释旧状态 | 3.1 |
| 11 | 用量/费用缺失、评价分母为空 | 显示未知或证据不足；不记零费用、成功率或“改善” | 3.0/3.1 |
| 12 | 取消后子进程/执行者失联 | 停新分派并记录取消；在确认进程已停前展示动作「等待机器」（远程）或继续结束本地进程树 | 3.1 本地进程；3.2C 远程执行代理上的进程；3.4A 独立事项；Stage 5 部门内多角色的父子传播 |
| 13 | 恢复与取消/撤销并发 | 按持久控制顺序处理，先已生效的取消或版本禁用不能被恢复越过 | 3.1 取消/不支持版本；Stage 6 完整撤销 |

还需覆盖：同一次模型响应中途只执行部分工具、压缩摘要确认前后、步骤/激活次数临界值、交付完成但项目尚未采纳、恢复时新输入令旧合同失效。这些是上表的具体注入位置，不另建立一套阶段定义。

## 7. 最小实验与通过条件

先在与生产数据隔离的目录，用真实本地进程验证三个窄场景：
1. 工具效果已经写入，完成确认前杀进程；恢复不会盲目重做。
2. 旧执行者失联/滞留时尝试接管；无法确认旧写者结束前不能并发冲突写入。
3. QA/交付已接纳、项目采纳前杀进程；恢复只补一次合法采纳。

通过后再完成整个适用矩阵，并在真实 Provider 任务上分别覆盖正式成果的提交、工具、QA/采纳边界的进程终止与续行。受控故障不称自然服务故障，模型成功不代替宿主故障验证。

通过意味着可安全继续的任务确实回到最终 QA，未知效果的动作交还发出它的会话，由模型负责后续处理。只把所有情况都转人工，或者只在内存中抛异常，没有证明可靠恢复。

首批针对当前 Windows 宿主验证进程树、文件替换和 SQLite 行为；其他平台在同矩阵验证后才声明支持。数据全留在原 run 的事实链中，独立导出后可重建与核验。

## 8. 决策与非目标

单机恢复使用现有 SQLite、事件与工件。不引入外部工作流引擎（[总体架构](architecture/overall-architecture.md)第 3 节）：控制核心本身是按事件重放的状态机，会话可以丢弃，恢复时从已提交的状态重新装配；Temporal 与 LangGraph 的成熟模式用于划分执行历史、动作与检查点的边界。控制核心在逻辑上只有一份，持有每个 run 的执行权，执行权编号在写入口与领域写入一起核对；执行权没有期限与续期（[ADR-0018](../adr/0018-single-control-host-remote-execution.md)）。

不承诺 exactly-once 外部副作用、不为 run 流加跨旧格式兼容、不做持久日历/消息队列、不引入费用预算、不为次数耗尽提供无限继续。完整远程副作用、父子取消、运行版本撤销分别在对应后续包验收。

文档提交不能关闭 3.1；通过与否以完整故障证据和真实任务结果决定。
