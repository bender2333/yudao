## 2. 各层的职责与边界

| 层 | 职责 | 边界 |
| --- | --- | --- |
| 客户端 | 展示与操作 | 只通过接口层读写 |
| 接口层 | 路由、合同、事件流、能力清单、认证 | 不含业务规则，只调用应用层 |
| 应用层 | 命令处理（按身份去重、核对基准版本）、查询与读取模型（循环画面、流转、回放、报告） | 修改只经过控制核心；读取只读投影；查询不写入事件 |
| 控制核心 | 身份与裁决：流程编排、步骤驱动、上下文装配（P）、裁决规则（U）、写入口、事件日志 | 裁决不使用模型；是唯一写入事实的地方；在控制主机上只有一份（[ADR-0012](../../adr/0012-single-control-core-scalable-execution.md)、[ADR-0018](../../adr/0018-single-control-host-remote-execution.md)） |
| 定义 | 组织、角色、动作、提案合同、本体、判定点、技能、限额、停止原因、服务方案预置表 | 带版本；只在发布新版本或经用户批准采用时改变；运行中不可修改（[ADR-0014](../../adr/0014-versioned-definitions.md)） |
| 知识层（[D25 语义系统](../../requirements/semantic-system.md)的整理部分） | 由事件派生轨迹、图谱与全文索引，推导内容的状态，计算要求链与数据流核对，提供查询 | 只由事件生成，不调用模型，不写入事实；派生内容是否进入上下文由 P 决定 |
| 观察层（[D28](../../requirements/meta-observer.md)） | 在判定点给出判断；语义系统的证据核对与元观察的判定都是判定点 | 只在编排器预先规定的判定点被调用，判断是编排器的输入 |
| 观察者 | 教训发现模块、元观察、Stage 6 的演化模块、校准抽样 | 按读取范围订阅事件，只以提案形式提交结果；读取范围由控制核心确定 |
| 执行层 | Provider、执行环境、外包 agent 的运行容器 | 只交回模型输出、动作回执、提案与证据；不持有领域状态 |

各部门（产品、工程、质检，以及 Stage 4 的[运维部门](../../requirements/operations-department.md)）的身份在控制核心：权威位置、装配规则、私有历史，写在定义中。自有角色的每一步由控制核心驱动，模型调用与动作在执行层运行；外包角色（[D31](../../requirements/outsourced-agent-roles.md)）由控制核心派发给外部 agent。元观察在组织上是一个部门，运行时是一个观察者加判定点。

## 3. 十项长期决定

1. **一份事件日志与唯一写入口**（[ADR-0013](../../adr/0013-event-log-and-single-write-path.md)）：每条事件有全局位置、所属的流与流内版本；所有写入只经过写入口，在同一个事务中核对执行权编号与流版本、接收 U 的裁决、追加事件、更新投影；投影保存下来，随写入逐步更新。
2. **异步执行**（[ADR-0011](../../adr/0011-async-control-core.md)）：控制核心在一个异步事件循环中运行，事项与角色任务都是可以取消的任务；模型调用、动作的进程与事件推送都以异步方式等待。
3. **部署形态与执行权**（[ADR-0012](../../adr/0012-single-control-core-scalable-execution.md)、[ADR-0018](../../adr/0018-single-control-host-remote-execution.md)）：控制核心、事件日志（SQLite）、工件存储、Provider 模块与观察者在一台控制主机上运行；控制核心只有一份，持有每个 run 的执行权，执行权没有期限与续期；执行环境可以分布到用户登记的其他电脑与树莓派上；部门不单独部署成服务；不引入外部工作流引擎。
4. **合同**（第 7 节）：模型调用、动作、外包派发、判定点、观察者订阅与提案，以及客户端的命令、查询与事件流，都是可以序列化、带身份的 pydantic 类型。
5. **调用目标每次请求解析**（[ADR-0005](../../adr/0005-resolve-call-target-per-request.md)）：每次模型请求之前由 Provider 模块解析；控制核心不持有明文凭据，凭据在执行调用的地方按引用读取。实施排在 3.1 之前。
6. **动作契约与执行环境**（第 7.3 节）：所有环境工具都是动作，每类动作有契约；执行环境是一个服务，合同经过 HTTP 加 JSON，有本机进程、本机容器、远程执行代理三种实现（3.2C），从封存快照建立；控制核心不直接读写工作区文件。
7. **带版本的定义**（[ADR-0014](../../adr/0014-versioned-definitions.md)）：组织、角色、动作、本体、判定点、技能、限额与停止原因作为带版本的数据；每个事项记录它使用的定义版本，每次请求与裁决记录所用的版本。
8. **用户决定**（第 7.4 节）：所有等待用户的事项使用同一种机制，决定请求与回答都写成事件。
9. **观察者**：需要调用模型的派生工作（教训发现、元观察、演化、校准抽样）按读取范围订阅事件，结果作为提案经过 U；Stage 6 隐藏的评价材料放在任何 agent 与观察者都读不到的存储中。
10. **应用层与界面**（[ADR-0015](../../adr/0015-desktop-client-and-http-contracts.md)）：接口层使用 FastAPI；命令、查询与一条按范围筛选的事件流；能力清单；只在局域网内使用期间认证保留位置、标为 TODO；客户端是 Electron 桌面程序，后端不提供界面文件。

## 4. 语义系统在各层中的位置

| 位置 | 语义系统的部分 | 边界 |
| --- | --- | --- |
| 知识层 | 本体；轨迹、图谱、全文索引这三种投影；状态推导（有效、待复核、取代、失效）；要求链与数据流核对；查询 | 只由事件生成，不调用模型，不写入事实 |
| 控制核心 · P | 栏目、目录、接触时附加、通知送达、旧工具结果清理、压缩之前的整理请求、轨迹节录、上下文清单 | 只读取知识层、材料与事件 |
| 控制核心 · U | 按本体校验记录、尝试、复盘的产出 | 校验与写入在写入口的同一个事务里完成，并行角色同时新建同名实体时只有一个成功 |
| 控制核心 · 流程编排 | 在成果被接纳后与事项结束时安排复盘，由中心角色通过一次单独的请求完成 | 复盘的产出作为提案经过 U |
| 观察层 | 证据核对，作为编排器事先规定的一种判定点；JEV 的结论交给编排器，写成事件 | 只能让事实变为待复核 |

需要调用模型的整理工作（压缩之前的整理请求、复盘）由角色自己的请求完成，产出作为提案经过 U。教训与洞见由教训发现模块找出，它是一个观察者。细节见[语义系统设计说明](../semantic-system.md)第 4 节。

## 5. 依赖方向

- 定义 ← 事件日志 ← 知识层与运行状态投影 ← P 与 U ← 步骤驱动 ← 流程编排 ← 应用层 ← 接口层 ← 客户端。
- 步骤驱动向上只通过流程编排提供的安全节点接口（依赖倒置），在每个安全节点得到继续或停止；新输入的分派与通知的送达在这里完成。接口有四个操作：继续判断在每个安全节点调用（每一步开始、尝试失败以后、工具前后、重试等待中），分派新输入并判断是否停止；开始新工作之前的核对在准备每一步、开始请求、安排重试与工具开始之前调用，另外关闭依据已经改变的协作请求，并核对角色任务的工作依据（合同、计划、协作请求）；重试等待可以被新输入、指导与取消唤醒；结束运行写入终态时核对作出停止判断时的流版本，此后有用户命令或输入写入时按写入以后的状态重新判断。取消由发起的一方写入；激活与运行循环交回的运行状态包含已经开始的取消，取消还没有写入时等它写入以后再交回。
- 控制核心只通过合同调用执行层与观察层；执行层不依赖控制核心的内部。
- 观察者只通过应用层订阅事件与提交提案，不依赖控制核心的内部。
- 职责分层表按「谁有权做什么」划分，依赖方向按本节写明。原架构文档（[Loop System 架构](../../archive/native-harness/loop-system-architecture.md)第 2 节）的 L0 至 L4 把两者合在一起，L1 的 ContextAssembler 读取 L2 的 StateStore，与它自己「只允许向下依赖」的规则矛盾；本架构采用它的不变量与原理，层次按本节的依赖方向确定。

## 6. 控制核心内部

### 6.1 模块

| 模块 | 职责 | 现在的代码位置 |
| --- | --- | --- |
| 流程编排 | 事项与交接、角色任务状态、执行槽位、放行、复盘的安排、停滞与反复退回的提醒、用户决定、判定点请求、外包 agent 的派发；提供安全节点接口 | `orchestrator.py`（运行生命周期、激活的准备与收尾、安全节点接口的实现、提案接纳后的流转） |
| 步骤驱动 | 一个角色任务内部的步骤循环：取得调用目标、取得请求、模型调用、重试、工具许可、执行动作、记录 | `engine.py` 的 `StepDriver`；`recording.py`（记录接口 `StepRecorder`） |
| 上下文装配（P） | 第 4 节表格中 P 那一行的全部内容，以及按调用目标的窗口计算阈值 | `assembly.py`（部门历史、每一步的装配、压缩完成后的检查点）；`context.py`、`compaction.py` |
| 裁决规则（U） | 提案校验、记录与尝试按本体校验、工具许可；许可规则可以增加，只能收紧 | `adjudication.py`（工具许可、提案校验与提交判断的入口）；`validation.py` |
| 写入口与事件日志 | 执行权与流版本的核对、追加事件、更新保存的投影、通知订阅方 | `write_path.py`（写入口 `WritePath`：同一事务中读取保存的投影、判断并追加，期望版本、命令身份与执行权编号的核对）、`event_store.py`（一份事件日志、按全局位置与范围读取、订阅）、`projection.py`（保存的投影、重放核对） |

执行层中，执行环境在 `environment.py`（本机实现 `LocalEnvironment` 与只读查询 `FactsQuery`），动作合同在 `actions.py`，模型调用合同在 `providers/call.py`。定义层在 `harness/definitions/`：限额、停止原因、组织、角色、工具、提案合同与服务方案预置表七个 JSON 文件，加载与 pydantic 校验在 `__init__.py`，版本由全部文件的内容摘要确定。应用层与接口层在 `harness/app/` 与 `harness/api/`。

- 流程编排只调用步骤驱动的开始、取消与取得结果，不接触步骤内部。
- 步骤驱动只通过 P 与 U 的接口取得请求与裁决结果。
- 所有写入只经过写入口。
- 控制核心同时驱动多个角色任务，等待模型、动作与网络时不占用其他任务。

### 6.2 一步的顺序

```mermaid
sequenceDiagram
  participant O as 流程编排
  participant S as 步骤驱动
  participant PM as Provider
  participant P as 上下文装配
  participant U as 裁决规则
  participant E as 执行环境
  participant W as 写入口
  O->>S: 开始角色任务
  loop 每一步
    S->>O: 安全节点：继续或停止
    S->>PM: 取得调用目标（按设置解析）
    PM-->>S: 调用目标或失败原因
    S->>P: 取得请求（按调用目标的窗口）
    P-->>S: 装配好的请求与上下文清单
    S->>W: 记录请求
    S->>PM: 模型调用
    PM-->>S: 流式输出与结果
    S->>W: 记录模型输出
    S->>U: 工具调用
    alt 环境工具
      U-->>S: 允许
      S->>E: 动作
      E-->>S: 回执
    else 主机工具
      U-->>S: 由控制核心执行的结果
    else 不允许
      U-->>S: 拒绝原因
    end
    S->>P: 取得接触时附加的内容
    P-->>S: 附加内容
    S->>W: 记录工具结果与附加内容
  end
  S-->>O: 角色结果被接纳，角色任务结束
```

### 6.3 两类工具

- **主机工具**：提交、记录、查询、读取材料、分派。由控制核心执行，读取知识层；查询范围由控制核心按角色身份填入，模型给出的参数不能扩大这个范围。
- **环境工具**：读写文件、运行检查与命令，以及以后的网络、MCP 与外部动作。每次调用是一个动作（第 7.3 节），经过工具许可以后在执行环境中执行，回执回到控制核心，由 P 附加内容。

外包 agent 的工具调用走同一套工具，工具许可、接触时附加与查询范围对它照样有效。

**工作区的事实。** 控制核心不直接读取工作区。U 需要的工作区事实（公开树的清单与摘要、路径在工作区中的规范形式与种类、检查回执）由执行环境的只读查询提供：步骤驱动在工具许可之前取得，流程编排在提案判断之前取得，作为输入交给 U；U 只根据投影、事件与交给它的事实判断。判断所依据的摘要写进承载判断结果的事件（工具开始、提案接纳或拒绝），重放时从事件读取，不再查询。动作合同的前置条件（树摘要、文件版本）使用同一个查询。执行环境是本机容器或远程执行代理时，这个查询与动作一样经过合同。

## 7. 合同

所有合同都是 pydantic 类型，可以序列化，不含进程内的对象；跨进程时按 [ADR-0015](../../adr/0015-desktop-client-and-http-contracts.md) 使用 HTTP 加 JSON。

### 7.1 身份

- 项目 > 事项 > run > 交接 > 计划条目 > 角色任务 > 步骤。
- 一次模型调用是一个逻辑调用，下面有一次或多次调用尝试（D21）。
- 一个动作是一个逻辑动作，下面有一次或多次动作尝试。
- 协作请求、决定请求、判定、提案各有自己的身份。
- 每条往来带身份，接收方按身份去重，旧执行权编号的结果只记录、不接纳。

### 7.2 五种合同

| 合同 | 双方 | 内容 |
| --- | --- | --- |
| 模型调用 | 步骤驱动与 Provider | 身份（run、角色任务、步骤、逻辑调用、尝试）；调用目标的选择；装配好的输入、工具定义与缓存断点或缓存键；流式输出；结果与用量；按尝试取消 |
| 动作 | 步骤驱动与执行环境 | 逻辑动作与尝试的身份；动作类别；输入；前置条件（树摘要、文件版本）；预期效果；授权依据；回执（结果、证据、执行以后的树摘要）；结果未知时的核实方法 |
| 外包派发 | 流程编排与外包 agent 的运行容器 | 角色定义与版本、任务说明、资料引用、工作区快照摘要、工具入口、模型入口；工具请求（转为动作合同）；提案与证据；续期与取消 |
| 判定点 | 流程编排与观察层 | 判定点与版本、问题、参照材料、选项；概率、模型版本与选项顺序；重放使用记录的结果 |
| 观察者 | 观察者与应用层 | 从某个全局位置开始按读取范围订阅事件；提案（教训、洞见、发现、演化候选）带身份与依据 |

客户端的合同：命令带身份与基准版本，返回接受或拒绝；查询返回快照与对应的全局位置；事件流按全局位置推送与补齐，发现缺口时重新同步快照；能力清单列出当前部署提供的查询、命令与覆盖层。

### 7.3 动作契约

每类动作的契约回答[恢复契约](../recovery-contract-and-fault-matrix.md)第 4 节的问题：谁有权做，作用于什么，怎样识别同一动作与不同尝试，成功证据是什么，结果未知时向哪里查，何时可以重复，取消能否确认停止，谁负责未解决的结果。没有可以验证的恢复方法时，结果保持待核实，不自行补偿。

| 动作类别 | 执行环境 | 授权 | 出现时间 |
| --- | --- | --- | --- |
| 读取、搜索 | 本机、容器或执行代理 | 角色的工具许可 | 已有 |
| 写入、编辑、删除、移动 | 本机、容器或执行代理 | 角色的工具许可与工程计划的范围 | 已有 |
| 登记的本地命令 | 本机、容器或执行代理 | 登记表 | 3.2A |
| 检查 | 检查副本 | 质检角色 | 已有 |
| 网络取回、MCP 工具 | 本机、容器或执行代理 | 用户决定 | 3.2B |
| 浏览器（Playwright MCP）与 computer use（容器中的虚拟屏幕） | 容器 | 角色的工具许可；按普通浏览器 MCP 的默认做法运行，不另加限制；computer use 只提供给模型能看图的部门（[D34](../../requirements/browser-and-computer-use.md)） | 3.2D |
| 外部动作（部署、回滚、重启、读取运行数据） | 登记的运行环境上的执行代理 | 常设授权清单以内由运维直接执行；清单以外由用户决定 | Stage 4 |
| 外包 agent 的文件与命令请求 | 外包 agent 的容器 | 与自有角色相同 | D31 |

执行环境是一个服务，合同经过 HTTP 加 JSON，有三种实现（[D29](../../requirements/remote-execution.md)、[ADR-0018](../../adr/0018-single-control-host-remote-execution.md)）：
- 本机进程：在控制主机上运行登记的命令。
- 本机容器：在控制主机上隔离运行任意代码（3.2C）。
- 远程执行代理：运行在用户登记的其他电脑或树莓派上的一个小服务，在登记的目录中读写文件、启动进程并交回动作回执（3.2C）。用户在项目中登记机器，写明地址、用途与授权范围；只在局域网内使用期间，连接的认证与加密保留位置并标为 TODO，离开局域网之前加入访问令牌与 TLS；模型凭据只保存在控制主机。执行代理在动作进行期间按时发送心跳，超过时限没有心跳时动作结果记为未知，按恢复契约第 4 节核实；之后到达的回执按动作身份记为迟到事实。

执行环境从封存快照建立，依赖缓存与编译缓存可以保留；工作区内容每次从快照重建。本机进程只运行登记的命令；运行外来代码使用容器实现。

进程类动作（检查、登记的命令）以异步方式启动与等待。超时或取消时结束整个进程树，回执记为超时或已取消，带截至结束时的输出，取消能够确认停止；取消在动作开始之前到达时不启动进程。

### 7.4 用户决定

凡是等待用户的事项，都由流程编排发出决定请求：身份、阻塞范围（一个动作、一个角色任务、一个 run，或不阻塞）、由合同给出的选项与说明。用户通过命令回答，请求与回答都写成事件，重放时使用记录的回答。

| 决定 | 来源 |
| --- | --- |
| 授权网络取回、MCP 工具，以及常设授权清单以外的外部动作，一次性批准 | 3.2B、D27、原型 v7 |
| 核实结果未知的动作：重新执行、接受当前结果、停止 | 恢复契约第 4 节 |
| 模型引用无法使用时的待恢复 | 模型管理设计说明第 5.5 节 |
| 进入等待模型服务的通知（只通知一次，用户可以取消 run） | Stage 4、D17 |
| 判定点置信不足时的裁定 | D28 |
| 证据核对的校准样本裁定 | D25、#41 |
| 采用 Stage 6 的定义候选 | Stage 6 |
| 反复退回的提醒（只通知，不阻塞） | D26 |

中断的 run 在 Yudao 启动时自动继续，不经过用户决定；其中结果未知的外部动作按上表第二行交给用户。
