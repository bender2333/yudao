# 上下文装配：把视图当作事件日志上的纯函数

状态：设计（2026-10-29 子架构师按 #912 写出，未实施）。依据：#912；回放读数在 [docs/evaluation/context-assembly-2026-10-29.md](../evaluation/context-assembly-2026-10-29.md)、[context-assembly-replay-2026-10-29.md](../evaluation/context-assembly-replay-2026-10-29.md)、[context-assembly-counterfactual-2026-10-29.json](../evaluation/context-assembly-counterfactual-2026-10-29.json)；规则清单的机器可读版本是 [evals/context/rule-set.json](../../evals/context/rule-set.json)。路线位置：路线图第 3 节「装配与语义」道，阶段未定（#912 的评论：暂不挂里程碑）。总图位置：第四节「装配」缝（装配契约：执行实现 ↔ 装配实现，`ContextAssembly` 的四个方法），第一节「装配实现」方框（第 3 圈「可以整体重写」）。

## 1. 问题、现状与方法

### 1.1 要解决的问题

每一步发给模型的上下文的用量在涨，而用量就是费用与时间。系统的做法一直是「把部门历史整段重放」：`ContextAssembler.assemble` 把固定材料与全部部门历史拼成一个请求（`harness/context.py:411`），`plan_compaction` 只在请求要超出「窗口 − 预留」时摘要一段前缀（`harness/compaction.py:118-121`）。于是三件事同时成立：

- 窗口很宽（这批运行全部是 1,000,000 token）时，压缩从不触发，历史一路全量重放；
- 「旧工具结果清理」（[语义系统设计说明](semantic-system.md)第 11.2 节：最近 `context.tool_result_keep_tokens` 之外的旧结果换成占位）**没有实现**：`harness/` 里没有任何代码读这一条；
- 规则登记里 `context.work_limit_tokens`、`context.tool_result_keep_tokens`、`context.tool_result_clear_min_tokens`、`context.history_keep_tokens` 四条 `kind: parameter` 的条目都没有读者（`grep -rn "tool_result_keep_tokens" harness/` 无命中）。

所以本设计不是从零发明，而是：**把「视图」写成事件日志上的纯函数，先用真实运行记录量清楚什么被用到、什么是浪费，再从测量里提减法规则，并把已经写进设计却没有实现的那几条接到这条路径上。**

### 1.3 方法：四步，都是离线

1. **重建**：`model_request_serialized` 事件指向的工件是这一步真正发出去的请求体，`context_assembled` 是同一步的上下文清单。两者相加，不需要重跑装配、不需要模型，就能得到每一步的视图。
2. **测量**：真值集合来自这一步模型的输出（见第 2 节），据此算每一步的召回与浪费，再按步序、部门、窗口大小分组看分布。
3. **重放**：把同一条日志喂给纯函数 `view(events, rules)`，得到新请求，用**同一套**真值集合重新算召回与浪费；再逐条关掉一条规则，看它各自的贡献（消融）；再逐段核对材料里的每一段。
4. **扫描**：只改一个参数的取值，看「省量 × 召回」的曲线，参数默认值从曲线的拐点取。

**回放忠实性**（`python -m evals.context verify`）：规则全关时，`view()` 必须一字不差地还原记录下来的请求。646/646 步逐字节一致（`messages` 与 `tools` 两部分；`max_tokens`、`model`、`stream` 由执行层填，不属于装配）。这条通过以后，第 3 节的数字才有意义。

## 2. 「用到了什么」：真值集合与这个启发式的误差

从这一步模型的输出里抽四类引用：文件路径、长标识符与散列、反引号与引号里的片段、工具调用编号。这一步的请求给出的回答用到了哪些记号，就是这一步的**真值集合**。

- **召回**：真值里那些「此前已经出现过」的记号，有多少还在这一步的视图里。模型在这一次输出里新造的记号（自己写的命令、变量名）不进分母，否则召回被人为压低。
- **浪费**：视图里**此后**（这一步及之后）从未被引用的记号所在的条目，它们的用量合计。记号记给视图里最早持有它的那一条。

四类误差，方向一致：**浪费是上界、召回是下界**。

1. 词面共现不等于因果。同一个记号可能同时出现在多条里（意图、多次读取的文件内容、后来的输出）。归属记给最早的一条，于是后来的重复条目会被计成浪费——这一条让浪费偏高。
2. 改写与会话不算。模型用了某条内容但换了措辞、换算成结论，词面不重合，会被记为浪费——同样让浪费偏高。
3. 指令类材料永远不会被「引用」。`current_work` 这类材料是照着做的，不是照着抄的：它 92.4% 的用量「从未被引用」，并不说明它没用。**凡是「按引用率减材料」的结论都不能用在指令类材料上**（第 3.5 节）。
4. 只看到写出来的那一部分依赖。模型没写出来的依赖（例如按已有内容决定不再读取）不进真值集合。

还有一条不是误差而是事实：这是**一个模型、一批短任务**（每 run 平均 29 步、最长 77 步）。策略在这批数据上成立的减法规则，换个模型或更长的任务要重新量一遍。

## 3. 现状：每一步的召回与浪费

### 3.1 用量都在哪里

| 条目种类 | 条目数 | token | 占比 | 此后从未被引用的 token | 占该类 |
| --- | --- | --- | --- | --- | --- |
| 部门材料（`pinned`） | 646 | 2,503,978 | 30.1% | 2,771 | 0.1% |
| 工具结果（`tool`） | 6,245 | 2,469,095 | 29.6% | 1,776,519 | 72.0% |
| 部门输入（`input`） | 830 | 1,813,796 | 21.8% | 1,676,082 | 92.4% |

**窗口这一维在这批数据上只有一个取值**，所以「按窗口大小看分布」只能给占用率：中位 1.03%，p90 2.45%，最大 5.02%。32,000 窗口的样本只有 `fake` 协议的 13 步（没有请求原文），不能算进分布。结论是：窗口是硬上限，但在这批运行里**离上限还有两个数量级的距离**，任何「等窗口快满再处理」的策略都不会被触发——这正是现状全量重放且从不清理的原因。

小结果大多用不上但几乎不花 token（≤200 的 2,850 条合计 229,385 token）；大结果一旦用上就用得多。**折叠的单位要按 token 算，不按条数算。**

### 3.5 三类浪费，只有一类可以直接减

1. **可减且已验证**：被后来取代的旧内容。同一路径 `read_file` 最多读到 418 次（`README.md`）、256 次（`textstats.py`）；同一编码工具，结果里 72% 的 token 此后从未被引用。折叠它有实测的召回代价（第 6.1 节）。
2. **可减但要按材料分**：引证类材料。每步都装的 `current_product_spec`（813,971 token，9.8%）、`project`（606,169）、`proposal_contract`（252,524）、`current_delivery_spec`（208,534）。被引用记号覆盖的字符占比分别只有 4.1%、2.2%、5.6%、6.3%。逐段核对（第 4 节 R5）表明其中 8 段换成摘要**一个记号都不丢**，`project` 一丢就丢 311 个记号（36 步），所以 `project` 不在门控之列。
3. **不能按这个数字减**：指令类材料。`current_work` 92.4%、`collaboration_rules` 0% 的引用率是「照着做」的自然结果。它们的浪费只能通过**减少重复装入**（同一种输入只留最新一份）来省，不能通过「引用率低就不装」来省。

### 3.6 其他三个可以量的点

- **同一步内的完全重复**只有 41,774 token（0.5%），所以「同一次调用重复装两遍」不是问题；问题是**同一条内容在后续每一步都重新发一遍**。
- **失败结果** 355 条、10,076 token（0.12%），词面引用率为 0——错误文字短且通用，模型用了也不复述。所以「失败结果不折叠」这条按「便宜且承载状态」定，不按引用率定。
- **部门输入的重复**：830 条输入、103 种不同正文；`[current_work]` 一种输入占了全部输入的 21.8%。

## 4. 规则清单（七条）

每条写：名字、输入、输出、默认值、是定义还是参数（沿用规则登记的 `kind` 与 `form`）、从哪组数据来。机器可读版本是 `evals/context/rule-set.json`，字段与代码里的 `Rules` 一一对应，测试核对两者不漂移。

### R1 `input_single_copy`（定义，`form: admission`）

- **输入**：部门历史里的输入条目与它们的种类（`[current_work]`、通知）。
- **输出**：同一种输入只留最新一份原文，旧的换成一行占位。
- **默认值**：开。占位写法：`（第 N 步的旧输入已折叠：同一部门输入只保留最新一份原文）`。
- **数据**：830 条输入、103 种正文、1,813,796 token（21.8%），92.4% 的用量此后从未被引用；消融省 295,030 token（3.5%），召回 −0.0006。
- **为什么是定义不是参数**：判据是「同一种输入的新版本取代旧版本」，没有可以调的数值。

### R2 `superseded_read_collapse`（定义，`form: admission`）

- **输入**：工具结果、它的工具名与调用参数里的路径。
- **输出**：同一路径的 `read_file`/`read_range` 结果只留最新一版原文，旧的换成一行占位（保留 `tool_call_id`，配对不破）。
- **默认值**：开。写与改的结果不在此列（它们承载「文件已经改成什么」，不是同一条内容的新旧关系）。
- **数据**：同一路径重复读取 15 个热点（README.md 418 次、textstats.py 256 次）；消融省 119,944 token（1.4%），召回 −0.0025。节省小于预期，是因为一步之内通常只有一两份同路径副本——重复主要发生在**跨步**，跨步由 R3 的预算管。

### R3 `tool_result_keep_tokens` + `tool_result_clear_min_tokens`（参数，`form: boundary`）

- **输入**：历史工具结果按新到旧累计的用量。
- **输出**：超出保留量时，从最旧的一轮开始折叠成占位；一轮折叠省下的量不足 `clear_min` 时不做。
- **默认值**：`keep = 16000`、`clear_min = 4000`。两条都已在规则登记里（`context.tool_result_keep_tokens` 暂定 40000、`context.tool_result_clear_min_tokens` 暂定 20000），**但装配实现没有读它们**；本设计把默认值按下面的曲线改掉，并接上。
- **数据**：工具结果占 29.6% 的用量、72% 从未被引用；步龄表说明不能按步龄切，只能按预算切。扫描（其余规则固定）：

  | `keep` | 省 | 召回 现状 → 新视图 | 召回下降的步 |
  | --- | --- | --- | --- |
  | 40000 | 9.2% | 0.9548 → 0.9520 | 5 |
  | 16000 | 11.1% | 0.9548 → 0.9504 | 8 |
  | 8000 | 15.8% | 0.9548 → 0.9353 | 18 |
  | 4000 | 19.3% | 0.9548 → 0.9334 | 23 |
  | 2000 | 20.6% | 0.9548 → 0.9295 | 28 |

  拐点在 16000：从 40000 降到 16000 多省 1.9pp 只丢 0.0016 召回；再降到 8000 多省 4.7pp 却丢 0.015（三倍代价）。`clear_min` 的扫描：20000 → 11.1%、12000 → 13.5%、6000 → 15.8%、2000 → 16.9%；取 4000（省量曲线已平，召回下降的步数不再明显增加）。
- **注意**：40000 那个暂定值在这批数据上**从不触发**（中位请求 13k token、最大 52k），所以「已经登记了」不等于「已经起作用」。

### R4 `error_result_keep`（定义，`form: permission`）

- **输入**：工具结果的 `ok`/`error` 字段。
- **输出**：失败的结果不折叠，也不计入保留量。
- **默认值**：开。
- **数据**：失败结果 355 条、10,076 token（0.12%），词面引用率 0（见第 2 节误差 1：短而通用的文字不会被复述）。保留它的代价实测 6,432 token（打开这条规则后总用量多 6,432），换来召回 +0.0002——用 0.08% 的用量换「部门不会重复同样的失败」，值得。

### R5 `pinned_reference_gate`（定义 `form: admission` + 参数 `pinned_stub_chars`）

- **输入**：部门材料的各段、这一次的工作引用（`current_work` 段里点名的来源）。
- **输出**：契约段整段装入；门控清单里的段在工作引用没有指向它、并且换成摘要确实更省时，换成「未装入 + 原文长度 + 怎么查」加前 `pinned_stub_chars`（默认 400）字符。
- **默认值**：开；门控清单 = `current_delivery_spec`、`prior_delivery`、`existing_overview`、`causal_chain`、`binding_refs`、`prior_structure`、`prior_initial_prd`、`current_product_decisions`。**`project` 不在清单里。**
- **数据**：逐段核对（一段一段单独换成摘要，看会不会丢掉只在这一段里的记号）：

  | 段 | 步数 | 省下的 token | 丢掉的记号 | 丢记号的步 |
  | --- | --- | --- | --- | --- |
  | project | 646 | 557,018 | 311 | 36 |
  | current_delivery_spec | 172 | 191,334 | 0 | 0 |
  | prior_delivery | 29 | 29,990 | 0 | 0 |
  | existing_overview | 132 | 18,480 | 0 | 0 |
  | causal_chain | 646 | 16,329 | 0 | 0 |
  | binding_refs | 646 | 15,588 | 0 | 0 |
  | prior_structure | 6 | 8,430 | 0 | 0 |
  | prior_initial_prd | 5 | 4,605 | 0 | 0 |
  | current_product_decisions | 23 | 2,047 | 0 | 0 |

  `project` 是「仓库里有哪些文件、路径怎么排」的地图，模型每 18 步就要引用一次（311 个记号、36 步）。把它门控掉的整版回放（那一次连 `project` 一起门控）召回从 0.9548 掉到 0.9066——**这是这批判量里唯一被数据否掉的减法**，所以它留在常驻一侧。八段合计省 259,715 token（3.1%），召回不降。
- **未决**：`project` 的 557,018 token 是最大的一块。它能不能「按部门、按工作阶段」装（产品部门只在建档与改 PRD 时需要，质检与工程要得更多），需要按部门分别核一遍，本批数据里产品只有 97 步，样本太薄（见第 8 节）。

### R6 `round_fold_granularity`（定义）

- **输入**：历史按轮切分（一次模型输出与它的工具结果为一轮）。
- **输出**：折叠以整轮为单位，调用与结果成对折叠成一条注记；不拆开一对。
- **默认值**：开。
- **数据**：工具调用条目占 18.5%、45.9% 从未被引用；聊天协议要求 `function_call` 与它的结果成对出现，按条折叠会留下配不上的调用（性质测试 `test_tool_calls_stay_paired_with_their_results` 守这一条）。这条规则本身不省用量（消融为 0），它是 R3 能安全折叠的前提。
- **与既有设计一致**：[语义系统设计说明](semantic-system.md)第 11.3 节早已写明「分界只在步骤边界上，工具调用与它的结果不分开」。

### R7 `work_limit_tokens`（参数，`form: boundary`）

- **输入**：装配出来的请求的估算用量。
- **输出**：超过工作上限就继续折叠更旧的一轮，直到低于上限；窗口减预留是更硬的上限（`ModelLimits`）。
- **默认值**：100,000（规则登记里已有，装配实现没有读它）。
- **数据**：这批运行里请求最大 52,316 token、中位 13,031，所以这个上限在当前数据上不触发；它的作用是**在长任务上兜底**（第 5 节）。这也是一个「登记了但没有实现」的参数，接上以后才能说它有效。

## 5. 装入顺序与截断

窗口是硬上限，但**硬上限不等于目标**：请求越短，费用越低、注意力越集中。所以装入分三层，从硬到软：

1. **必须装（不进折叠预算）**：部门材料里的契约段（`intend`、`current_work`、`current_product_spec`、`current_contract`、`department_rules`、`allowed_tools`、`proposal_contract`、`input_handling`、`input_progress`、`professional_completion`、`collaboration_rules`、`pending_inputs`、`validation_feedback`、`qa_defects`、`pending_ask`、`pending_request`、`latest_response`、`request_results`、`department_guidance`、`guidance_results`、`revision_note`、`engineering_explanation`），工具定义，最新一份部门输入，失败的工具结果，模型的文字回答。
2. **按引用取舍（R5）**：引证段落只有被这次工作引用点名、或不在门控清单里时整段装入；否则一段摘要加查询方式。
3. **按预算折叠（R2、R3、R6）**：工具结果按新到旧累计，超过 `tool_result_keep_tokens` 的轮次从最旧的开始成对折叠成一行注记；同路径的旧读取先折叠（R2）。

**截断规则**：

- 顺序是**先折叠、后压缩**。折叠不调模型、不改内容、原文留在事件日志里；只有折叠到 `tool_result_clear_min_tokens` 都省不出来、请求仍然超过「窗口 − 预留」时，才走现有的压缩路径（`plan_compaction`，本设计不重写它）。
- 折叠从**最旧**的一轮开始，不从「引用率最低」的条目开始：引用率是事后才知道的量，装配时不能读它（读了就是把未来的信息用进来）。装配能用的只有「新到旧 + 一轮 + 失败结果除外」这三个确定性判据。
- 任何一步的用量一旦超过 `work_limit_tokens`，继续折叠直到低于它；仍然超过窗口减预留时压缩。
- 每一步的视图都写进 `context_assembled` 清单（每段的来源、版本、估算用量、折叠了哪几轮），重放时按同一份规则版本复原。

## 6. 三项证明

### 6.1 确定性（通过）

- **性质测试**：`evals/tests/test_context_view.py` 10 条，200 份随机日志上同事件同规则给出逐字节相同的请求；不修改输入；配对完整；材料恒在首位；存活条目的顺序是日志顺序的子序列；保留量越大留得越多（单调）；同路径只留一份原文；失败结果从不折叠；规则文件与代码字段一致。
- **回放忠实**：规则全关时 646/646 步与记录逐字节一致（第 1.3 节）。
- **规则版本**：`Rules.version()` 是规则取值的规范散列（本版 `sha256:6d66cca8e0935b18…`），请求与清单记版本，重放才能核对「同一份规则」。
- **不用 hypothesis**：项目开发依赖里没有它，CI 用 `uv sync --frozen` 装依赖；性质测试用固定种子的生成器，失败可复现。要引入 hypothesis 是另一张工单。

### 6.2 反事实回放（做了，但这批模型上**没有区分力**）

做法：按部门分层、按步序分桶抽 16 步，温度 0，同一模型分别回答旧视图与新视图；顺手把**旧视图再问一次**作为基线（这一步是原工单没写、但不做就判断不了的）。

| 判据 | 旧对新 | 旧对旧（同一请求重复） |
| --- | --- | --- |
| 动作（工具名 + 参数）完全相同 | 1/16 = 6.3% | 1/16 = 6.3% |
| 工具名的集合相同 | 11/16 = 68.8% | 12/16 = 75.0% |
| 参数里的路径集合相同 | 3/13 = 23% | 2/13 = 15% |
| 动作种类（调用 / 只回复文字） | 16/16 | 16/16 |

**结论与它为什么不够**：这个模型在温度 0 下并不确定——同一个请求问两次，动作完全相同的只有 6.3%，工具名集合相同 75%。旧对新与旧对旧的差值（工具名 −6.2pp、路径 +8pp，n=16）都在噪声之内，**这条判据既证明不了「不丢该留的」，也否证不了**。所以：

- 这条证明记「未通过（判据没有区分力）」，不记为通过。放宽成「工具名集合一致率」也一样：基线本身只有 75%，说明这个模型的动作在第 16 步以后本来就在漂。
- 唯一能从这次抽样里读出的正向证据是**上游回报的输入用量**：16 步合计 201,030 → 185,943 token（−7.5%，抽样偏向早期步，全量是 −16.8%）。用量是确定量，不受模型随机性影响。
- 要恢复这条判据的区分力，只有两条路：换一个温度 0 下逐字确定的模型（同一请求重复问必须 100% 一致），或者把判据从「动作相同」换成「动作引用的材料在新视图里都在」——后者其实就是 6.1 的召回，只是换成模型输出来当输入。两条都写进第 8 节，需要总架构师定。

### 6.3 端到端（**未做**，说明原因与判据）

三个固定回归场景（场景 1、2、3）用 `evals/scorer` 打分、比隐藏检查分数与费用，这条现在**跑不了**：新视图还没有在 `harness/` 里实现，而架构师不改 `harness/`。场景 3 的最近一次读数（2 次运行、总用量均值 114,151 token、费用未知——模型服务没有上报用量与单价）只能当对照的起点。

所以端到端不写成「通过」，而是写成**实现工单的验收**（第 9 节的 C 张）：实现以后在要发布的提交上跑三个场景，判据是「隐藏检查的通过条数不下降，模型请求与用量下降」。这批 646 步的读数给出的预期是输入用量 −16.8%，场景 3 只有 5 至 7 个请求一步，预期收益更小（第 3.2 节：步序 1 的省量 20.9% 主要来自 R5，后面才来自 R3），不承诺具体的数。

## 8. 未决问题

1. **反事实回放的判据失效**（6.2）。需要总架构师定：换确定性模型重做，还是把判据改成「动作引用的材料都在新视图里」。这一条不解决，原工单「三项证明」的第二项就没有合格的证据。
2. **端到端证明要等实现**（6.3）。在 C 张工单实现以后跑；在此之前，不得以「回放省了 16.8%」代替它。
3. **`project` 段 557,018 token**：按部门、按阶段分别装能省多少，产品部门只有 97 步样本，不够定。要等更多运行记录（尤其是产品与质检的建档类工作）。
4. **`call` 条目 45.9% 从未被引用**：折叠一轮时调用参数随结果一起消失是安全的（R6）；但「保留调用、只折叠参数」这种做法在聊天协议里不允许（配对要完整），所以没有别的减法空间。如果改用 responses 协议，可以再量一次。

## 9. 工单草案

三张，都可以独立验证。**都不挂里程碑**（#912 的评论：路线图第 3 节未给本项指定阶段，等总架构师定落点）；成立为真工单时按子工单模板写正文，标 `ready-for-agent`。

### A. 把视图写成纯函数并接上装配契约（立缝 + 切片）

把 `view(events, rules) → request` 作为装配实现的内核：规则集带版本、读规则登记的 `context.*` 条目、`context_assembled` 清单记录折叠了哪几轮、规则版本与折叠计数进清单。现有 `assemble` 改成「取视图 → 造请求」，不改装配契约的四个方法，不改压缩路径。

- 独立验证：`evals/tests/test_context_view.py` 的确定性性质测试在 `harness/` 侧另有一份等价测试；同一事件重放两次请求逐字节相同；`context_assembled` 里有规则版本与折叠计数；规则全关时与当前行为逐字节一致（用 `evals/context/verify.py` 的判据在真实日志上核一遍）。
- 判据（结束条件）：`check` 通过；内核清单与总行数不涨（不改内核）；现有的 `harness/tests/test_context.py`、`test_compaction.py`、`test_assembly.py` 一条不删。

### B. 接上 R1、R2、R5 三条减法规则

在 A 的视图上实现三种取舍：同一输入只留最新一份、同路径只留最新读取、引证段按工作引用与逐段清单门控。

- 独立验证：三条规则各有一条能区分「实现正确 / 未实现」的测试（构造带重复输入、重复读取、引证段的日志，断言折叠与保留）；回放同一批事件，用量下降且召回不下降（用 `evals/context/replay.py` 的同一判据，允许 ±0.005 的波动）。
- 判据：改动前后在同一份导出上跑 `replay` 的召回读数不下降超过 0.005，用量下降不低于 7%（A 之后 B 的实测贡献：R1 3.5% + R2 1.4% + R5 3.0%）。

### C. 接上 R3、R4、R6、R7 的折叠与预算，并跑端到端

按 `tool_result_keep_tokens` / `tool_result_clear_min_tokens` / `work_limit_tokens` 做按轮折叠，失败结果不折叠；参数默认值改为 16000 / 4000 / 100000（`harness/definitions/rules.json` 的条目与四项记录一起改）。交付时在要发布的提交上跑场景 1、2、3。

- 独立验证：单元层有折叠与配对的测试；模组层有一条「超过预算的请求会折叠最旧的一轮」的测试；端到端在三个固定场景上隐藏检查通过条数不下降、模型请求的输入用量下降（`evals/runner/yudao_metrics.py` 的读数）。
- 判据（这是本设计的 6.3）：三个场景的隐藏检查分数不降；场景 3 的 `total_tokens` 均值下降；不达标的写清是哪个场景、差多少，不放宽。
- 依赖：A、B 先合并。

**归属**：三张都在路线图第 3 节「装配与语义」道，`touches-core` 不适用（不改内核：`assembly.py`、`context.py`、`compaction.py` 是应用层的装配实现）。
