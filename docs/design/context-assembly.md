# 上下文装配：把视图当作事件日志上的纯函数

总图位置：第四节「装配」缝（装配契约：执行实现 ↔ 装配实现），第一节「装配实现」方框（第三环「可以整体重写」）；第三节「上下文逼近上限 → 压缩」（保留意图、有效合同、失败尝试与近期回合）。依据：回放读数与成本核对在 [docs/evaluation/context-assembly-2026-10-29.md](../evaluation/context-assembly-2026-10-29.md)、[context-assembly-replay-2026-10-29.md](../evaluation/context-assembly-replay-2026-10-29.md)、[context-assembly-counterfactual-2026-10-29.json](../evaluation/context-assembly-counterfactual-2026-10-29.json)；规则清单的机器可读版本是 [evals/context/rule-set.json](../../evals/context/rule-set.json)。

## 1. 问题、现状与方法

### 1.1 要解决的问题

每一步发给模型的上下文的用量在涨，而用量就是费用与时间。系统的做法一直是「把部门历史整段重放」：`ContextAssembler.assemble` 把固定材料与全部部门历史拼成一个请求（`harness/context.py:411`），`plan_compaction` 只在请求要超出「窗口 − 预留」时摘要一段前缀（`harness/compaction.py:118-121`）。于是三件事同时成立：

- 窗口很宽（这批运行全部是 1,000,000 token）时，压缩从不触发，历史一路全量重放；
- 「旧工具结果清理」（[语义系统设计说明](semantic-system.md)「旧工具结果清理」：最近 `context.tool_result_keep_tokens` 之外的旧结果换成占位）**没有实现**：`harness/` 里没有任何代码读这一条；
- 规则登记里 `context.work_limit_tokens`、`context.tool_result_keep_tokens`、`context.tool_result_clear_min_tokens`、`context.history_keep_tokens` 四条 `kind: parameter` 的条目都没有读者（`grep -rn "tool_result_keep_tokens" harness/` 无命中）。

所以本设计不是从零发明，而是：**把「视图」写成事件日志上的纯函数，先用真实运行记录量清楚什么被用到、什么是浪费，再从测量里提减法规则，并把已经写进设计却没有实现的那几条接到这条路径上。**

| 可回放的 run | 22 个（另有 1 个 `fake` 协议与若干没有请求记录的 run，不计） |
| 部门会话 | 64 个（产品 97 步、工程 311 步、质检 238 步） |
| 工作请求 | 646 个（`purpose = work`；压缩请求不计） |

| 输入用量 | 8,331,638 token（按装配实现同一条估算公式：4 字符 1 token） |
| 时间跨度 | 2026-10-21 至 2026-10-22 |

`docs/evaluation/scenario-3-qwen38flash-2026-10-20/` 那份导出是报告级读数（每次运行 5 至 7 个请求、总用量均值 114,151 token），没有请求原文，所以**分布只从事件库算**，报告级数字只用来对照量级。

### 1.3 方法：四步，都是离线

1. **重建**：`model_request_serialized` 事件指向的工件是这一步真正发出去的请求体，`context_assembled` 是同一步的上下文清单。两者相加，不需要重跑装配、不需要模型，就能得到每一步的视图。
2. **测量**：真值集合来自这一步模型的输出（见第 2 节），据此算每一步的召回与浪费，再按步序、部门、窗口大小分组看分布。
3. **重放**：把同一条日志喂给纯函数 `view(events, rules)`，得到新请求，用**同一套**真值集合重新算召回与浪费；再逐条关掉一条规则，看它各自的贡献（消融）；再逐段核对材料里的每一段。
4. **扫描**：只改一个参数的取值，看「省量 × 召回」的曲线，参数默认值从曲线的拐点取。

**回放忠实性**（`python -m evals.context verify`）：规则全关时，`view()` 必须一字不差地还原记录下来的请求。646/646 步逐字节一致（`messages` 与 `tools` 两部分；`max_tokens`、`model`、`stream` 由执行层填，不属于装配）。这条通过以后，第 3 节的数字才有意义。

## 2. 「用到了什么」：真值集合与这个启发式的误差

从这一步模型的输出里抽四类引用：文件路径、长标识符与散列、反引号与引号里的片段、工具调用编号。这一步的请求给出的回答用到了哪些记号，就是这一步的**真值集合**。

- **召回**：真值里那些「此前已经出现过」的记号，有多少还在这一步的视图里。模型在这一次输出里新造的记号（自己写的命令、变量名）不进分母，否则召回被人为压低。
- **浪费**：视图里**此后**（这一步及之后）从未被引用的记号所在的条目，它们的用量合计。记号记给视图里最早持有它的那一条。

四类误差，方向一致：**浪费是上界、召回是下界**。

1. 词面共现不等于因果。同一个记号可能同时出现在多条里（意图、多次读取的文件内容、后来的输出）。归属记给最早的一条，于是后来的重复条目会被计成浪费——这一条让浪费偏高。
2. 改写与会话不算。模型用了某条内容但换了措辞、换算成结论，词面不重合，会被记为浪费——同样让浪费偏高。
3. 指令类材料永远不会被「引用」。`current_work` 这类材料是照着做的，不是照着抄的：它 92.4% 的用量「从未被引用」，并不说明它没用。**凡是「按引用率减材料」的结论都不能用在指令类材料上**（第 3.5 节）。
4. 只看到写出来的那一部分依赖。模型没写出来的依赖（例如按已有内容决定不再读取）不进真值集合。

还有一条不是误差而是事实：这是**一个模型、一批短任务**（每 run 平均 29 步、最长 77 步）。策略在这批数据上成立的减法规则，换个模型或更长的任务要重新量一遍。

**窗口这一维在这批数据上只有一个取值**，所以「按窗口大小看分布」只能给占用率：中位 1.03%，p90 2.45%，最大 5.02%。32,000 窗口的样本只有 `fake` 协议的 13 步（没有请求原文），不能算进分布。结论是：窗口是硬上限，但在这批运行里**离上限还有两个数量级的距离**，任何「等窗口快满再处理」的策略都不会被触发——这正是现状全量重放且从不清理的原因。

### 3.5 三类浪费，只有一类可以直接减

1. **可减且已验证**：被后来取代的旧内容。同一路径 `read_file` 最多读到 418 次（`README.md`）、256 次（`textstats.py`）；同一编码工具，结果里 72% 的 token 此后从未被引用。折叠它有实测的召回代价（第 6.1 节）。
2. **可减但要按材料分**：引证类材料。每步都装的 `current_product_spec`（813,971 token，9.8%）、`project`（606,169）、`proposal_contract`（252,524）、`current_delivery_spec`（208,534）。被引用记号覆盖的字符占比分别只有 4.1%、2.2%、5.6%、6.3%。逐段核对（第 4 节 R5）表明其中 8 段换成摘要**一个记号都不丢**，`project` 一丢就丢 311 个记号（36 步），所以 `project` 不在门控之列。
3. **不能按这个数字减**：指令类材料。`current_work` 92.4%、`collaboration_rules` 0% 的引用率是「照着做」的自然结果。它们的浪费只能通过**减少重复装入**（同一种输入只留最新一份）来省，不能通过「引用率低就不装」来省。

### 3.6 其他三个可以量的点

- **同一步内的完全重复**只有 41,774 token（0.5%），所以「同一次调用重复装两遍」不是问题；问题是**同一条内容在后续每一步都重新发一遍**。
- **失败结果** 355 条、10,076 token（0.12%），词面引用率为 0——错误文字短且通用，模型用了也不复述。所以「失败结果不折叠」这条按「便宜且承载状态」定，不按引用率定。
- **部门输入的重复**：830 条输入、103 种不同正文；`[current_work]` 一种输入占了全部输入的 21.8%。

## 4. 规则清单（七条）

按第 6.4 节的成本核对，实现的只有 R3、R4、R6、R7，并且 R3 与 R7 只在本节末「开启条件」成立时生效；R1、R2、R5 不实现，留在清单里作为测过、不采纳的记录（用户确认）。

每条写：名字、输入、输出、默认值、是定义还是参数（沿用规则登记的 `kind` 与 `form`）、从哪组数据来。机器可读版本是 `evals/context/rule-set.json`，字段与代码里的 `Rules` 一一对应，测试核对两者不漂移。

### R1 `input_single_copy`（定义，`form: admission`）

- **输入**：部门历史里的输入条目与它们的种类（`[current_work]`、通知）。
- **输出**：同一种输入只留最新一份原文，旧的换成一行占位。
- **默认值**：开。占位写法：`（第 N 步的旧输入已折叠：同一部门输入只保留最新一份原文）`。
- **数据**：830 条输入、103 种正文、1,813,796 token（21.8%），92.4% 的用量此后从未被引用；消融省 295,030 token（3.5%），召回 −0.0006。
- **为什么是定义不是参数**：判据是「同一种输入的新版本取代旧版本」，没有可以调的数值。

### R2 `superseded_read_collapse`（定义，`form: admission`）

- **输入**：工具结果、它的工具名与调用参数里的路径。
- **输出**：同一路径的 `read_file`/`read_range` 结果只留最新一版原文，旧的换成一行占位（保留 `tool_call_id`，配对不破）。
- **默认值**：开。写与改的结果不在此列（它们承载「文件已经改成什么」，不是同一条内容的新旧关系）。
- **数据**：同一路径重复读取 15 个热点（README.md 418 次、textstats.py 256 次）；消融省 119,944 token（1.4%），召回 −0.0025。节省小于预期，是因为一步之内通常只有一两份同路径副本——重复主要发生在**跨步**，跨步由 R3 的预算管。

### R3 `tool_result_keep_tokens` + `tool_result_clear_min_tokens`（参数，`form: boundary`）

- **输入**：历史工具结果按新到旧累计的用量。
- **输出**：超出保留量时，从最旧的一轮开始折叠成占位；一轮折叠省下的量不足 `clear_min` 时不做。
- **默认值**：`keep = 16000`、`clear_min = 4000`。两条都已在规则登记里（`context.tool_result_keep_tokens` 暂定 40000、`context.tool_result_clear_min_tokens` 暂定 20000），**但装配实现没有读它们**；本设计把默认值按下面的曲线改掉，并接上。
- **数据**：工具结果占 29.6% 的用量、72% 从未被引用；步龄表说明不能按步龄切，只能按预算切。扫描（其余规则固定）：

  | `keep` | 省 | 召回 现状 → 新视图 | 召回下降的步 |
  | --- | --- | --- | --- |
  | 40000 | 9.2% | 0.9548 → 0.9520 | 5 |
  | 16000 | 11.1% | 0.9548 → 0.9504 | 8 |
  | 8000 | 15.8% | 0.9548 → 0.9353 | 18 |
  | 4000 | 19.3% | 0.9548 → 0.9334 | 23 |
  | 2000 | 20.6% | 0.9548 → 0.9295 | 28 |

  拐点在 16000：从 40000 降到 16000 多省 1.9pp 只丢 0.0016 召回；再降到 8000 多省 4.7pp 却丢 0.015（三倍代价）。`clear_min` 的扫描：20000 → 11.1%、12000 → 13.5%、6000 → 15.8%、2000 → 16.9%；取 4000（省量曲线已平，召回下降的步数不再明显增加）。
- **注意**：40000 那个暂定值在这批数据上**从不触发**（中位请求 13k token、最大 52k），所以「已经登记了」不等于「已经起作用」。

### R4 `error_result_keep`（定义，`form: permission`）

- **输入**：工具结果的 `ok`/`error` 字段。
- **输出**：失败的结果不折叠，也不计入保留量。
- **默认值**：开。
- **数据**：失败结果 355 条、10,076 token（0.12%），词面引用率 0（见第 2 节误差 1：短而通用的文字不会被复述）。保留它的代价实测 6,432 token（打开这条规则后总用量多 6,432），换来召回 +0.0002——用 0.08% 的用量换「部门不会重复同样的失败」，值得。

### R5 `pinned_reference_gate`（定义 `form: admission` + 参数 `pinned_stub_chars`）

- **输入**：部门材料的各段、这一次的工作引用（`current_work` 段里点名的来源）。
- **输出**：契约段整段装入；门控清单里的段在工作引用没有指向它、并且换成摘要确实更省时，换成「未装入 + 原文长度 + 怎么查」加前 `pinned_stub_chars`（默认 400）字符。
- **默认值**：开；门控清单 = `current_delivery_spec`、`prior_delivery`、`existing_overview`、`causal_chain`、`binding_refs`、`prior_structure`、`prior_initial_prd`、`current_product_decisions`。**`project` 不在清单里。**
- **数据**：逐段核对（一段一段单独换成摘要，看会不会丢掉只在这一段里的记号）：

  | 段 | 步数 | 省下的 token | 丢掉的记号 | 丢记号的步 |
  | --- | --- | --- | --- | --- |
  | project | 646 | 557,018 | 311 | 36 |
  | current_delivery_spec | 172 | 191,334 | 0 | 0 |
  | prior_delivery | 29 | 29,990 | 0 | 0 |
  | existing_overview | 132 | 18,480 | 0 | 0 |
  | causal_chain | 646 | 16,329 | 0 | 0 |
  | binding_refs | 646 | 15,588 | 0 | 0 |
  | prior_structure | 6 | 8,430 | 0 | 0 |
  | prior_initial_prd | 5 | 4,605 | 0 | 0 |
  | current_product_decisions | 23 | 2,047 | 0 | 0 |

  `project` 是「仓库里有哪些文件、路径怎么排」的地图，模型每 18 步就要引用一次（311 个记号、36 步）。把它门控掉的整版回放（那一次连 `project` 一起门控）召回从 0.9548 掉到 0.9066——**这是这批判量里唯一被数据否掉的减法**，所以它留在常驻一侧。八段合计省 259,715 token（3.1%），召回不降。
- **未决**：`project` 的 557,018 token 是最大的一块。它能不能「按部门、按工作阶段」装（产品部门只在建档与改 PRD 时需要，质检与工程要得更多），需要按部门分别核一遍，本批数据里产品只有 97 步，样本太薄（见第 8 节）。

### R6 `round_fold_granularity`（定义）

- **输入**：历史按轮切分（一次模型输出与它的工具结果为一轮）。
- **输出**：折叠以整轮为单位，调用与结果成对折叠成一条注记；不拆开一对。
- **默认值**：开。
- **数据**：工具调用条目占 18.5%、45.9% 从未被引用；聊天协议要求 `function_call` 与它的结果成对出现，按条折叠会留下配不上的调用（性质测试 `test_tool_calls_stay_paired_with_their_results` 守这一条）。这条规则本身不省用量（消融为 0），它是 R3 能安全折叠的前提。
- **与既有设计一致**：[语义系统设计说明](semantic-system.md)「压缩与轨迹节录」早已写明「分界只在步骤边界上，工具调用与它的结果不分开」。

### R7 `work_limit_tokens`（参数，`form: boundary`）

- **输入**：装配出来的请求的估算用量。
- **输出**：超过工作上限就继续折叠更旧的一轮，直到低于上限；压缩阈值是更硬的上限（`ModelLimits`）。
- **默认值**：100,000（规则登记里已有，装配实现没有读它）。
- **数据**：这批运行里请求最大 52,316 token、中位 13,031，所以这个上限在当前数据上不触发；它的作用是**在长任务上兜底**（第 5 节）。这也是一个「登记了但没有实现」的参数，接上以后才能说它有效。

### 开启条件：只对缓存命中低的调用目标折叠

- **为什么**：上游按前缀缓存计价（第 6.4 节）。不折叠时请求只在末尾追加，上一步的请求整段命中缓存；折叠一次，从折叠处起后面全部按未缓存重发。所以缓存命中高的调用目标折叠反而更贵，命中低的才省。
- **判据**：同一个会话最近 3 次上游报告了用量的模型回复，缓存读的 token 之和占输入 token 之和的比例低于 `context.fold_below_cache_hit`（参数，`form: boundary`，默认 0.5，范围 0.1 至 0.9）时，这一步按 R3、R7 折叠；否则这一步不折叠，请求只在末尾追加。用量取自事件日志里已经记下的模型回复，所以判据仍是事件日志上的纯函数，重放得到同样的视图。
- **不够 3 次或上游没有报告缓存读时**：按命中高处理，不折叠。这时的费用最多等于现在的做法；误开折叠在命中高的服务上会贵 6% 至 40%。
- **窗口快满时**：不管命中高低，请求达到压缩阈值时压缩（[模型管理设计说明](model-management.md)「预留与阈值」）。命中高的调用目标因此只在窗口快满时整理一次历史。
- **不会来回切换**：命中低时折叠，折叠又让命中保持低；命中高时只追加，命中保持高。一个会话换了调用目标（模型）以后，按新目标的回复重新累计。
- **记录**：`context_assembled` 清单写明这一步是否开启折叠和算出的命中比例。

## 5. 装入顺序与截断

窗口是硬上限，但**硬上限不等于目标**。请求越短、注意力越集中；费用是否随之下降取决于缓存命中（第 6.4 节）。所以装入分三层，从硬到软，第 3 层只在第 4 节「开启条件」成立时生效：

1. **必须装（不进折叠预算）**：部门材料里的契约段（`intend`、`current_work`、`current_product_spec`、`current_contract`、`department_rules`、`allowed_tools`、`proposal_contract`、`input_handling`、`input_progress`、`professional_completion`、`collaboration_rules`、`pending_inputs`、`validation_feedback`、`qa_defects`、`pending_ask`、`pending_request`、`latest_response`、`request_results`、`department_guidance`、`guidance_results`、`revision_note`、`engineering_explanation`），工具定义，最新一份部门输入，失败的工具结果，模型的文字回答。
2. **引证段整段装入**：R5 不实现，引证段落照现在的做法装入。
3. **按预算折叠（R3、R6）**：工具结果按新到旧累计，超过 `tool_result_keep_tokens` 的轮次从最旧的开始成对折叠成一行注记。

**截断规则**：

- 顺序是**先折叠、后压缩**。折叠不调模型、不改内容、原文留在事件日志里；只有折叠到 `tool_result_clear_min_tokens` 都省不出来、请求仍然达到压缩阈值时，才走现有的压缩路径（`plan_compaction`）；压缩生效以后，请求里另放一段失败清单（下面「压缩以后保留失败的尝试」）。
- 折叠从**最旧**的一轮开始，不从「引用率最低」的条目开始：引用率是事后才知道的量，装配时不能读它（读了就是把未来的信息用进来）。装配能用的只有「新到旧 + 一轮 + 失败结果除外」这三个确定性判据。
- 任何一步的用量一旦超过 `work_limit_tokens`，继续折叠直到低于它；仍然达到压缩阈值时压缩。
- 每一步的视图都写进 `context_assembled` 清单（每段的来源、版本、估算用量、折叠了哪几轮），重放时按同一份规则版本复原。

### 压缩以后保留失败的尝试

目的：压缩以后，角色不再犯压缩以前已经犯过的错。上下文逼近上限压缩时保留四样东西（总图第三节）：

| 保留什么 | 在哪里 | 由谁保证 |
| --- | --- | --- |
| 意图 | 事项原文的全部版本，常驻栏目 | 不进入压缩（[语义系统设计说明](semantic-system.md)「常驻栏目」） |
| 有效合同 | 当前有效要求、提案合同与第 5 节第 1 层的契约段 | 不进入压缩，同上 |
| 失败的尝试 | 失败清单，本节 | 主机从事件生成 |
| 近期回合 | 分界之后的原始记录 | [模型管理设计说明](model-management.md)「旧工具结果清理、分界位置与保留」 |

失败要单独规定，原因有两个。整理请求由角色自己写，写的是进展，失败的经过在摘要里最容易被省掉；再压缩一次，就成了摘要的摘要。轨迹节录超过上限时从最早的条目开始合并，早先的失败也会被合并掉。所以失败清单由主机从事件生成，不交给模型整理，也不受节录的合并规则约束。

**什么算失败。** 只取这个角色在本事项里自己的历史，全部从事件读出，判据确定：

1. 失败的工具结果（与 R4 是同一种）；
2. 被写入口或裁决拒绝的提案、被工具许可拒绝的调用，带拒绝原因；
3. 主机运行的检查没有通过的回执；
4. 角色整理尝试时记为没有达到目的、换用其他方法的尝试（语义系统设计说明「尝试的整理」）。

核验角色的打回意见与缺陷不在清单里：它们是部门输入，属于第 5 节第 1 层必须装的契约段，压缩不移出。

**每条写什么。** 做了什么（工具与参数摘要、提案种类、检查名称或尝试的目的）；怎么失败的（错误原文、拒绝原因或失败输出的开头，截到下面的单条上限）；事件编号，角色用读取来源或查询取回全文；这件事后来有没有做成。「后来做成」的判法是确定的：同名的检查后来在较新的快照上通过，同一种提案后来被接纳，同一工具以同样的参数后来成功。做成的标「后来已解决」。

**放在哪里。** 压缩生效以后，失败清单放在历史开头的轨迹节录之后，自成一段。每次压缩都从事件重新生成，覆盖这个角色在本事项里从开始到当前分界的全部失败，所以连续压缩几次，最早的失败仍按原文出现。分界之后的失败照常留在近期回合里，不重复列。没有压缩过的会话不生成这一段：失败原文还在历史里，折叠也不动它们（R4）。失败清单计入用量，不进折叠预算。

**常量。**

| 常量 | 默认值 | 范围 | 理由 |
| --- | --- | --- | --- |
| 失败清单的上限 | 4000 token | 1000 至 13107 token | 这批运行里失败结果 355 条、共 10,076 token，平均每条约 28 token；一条一行时 4000 token 装得下一百多条，多于单个会话的失败数。上限不超过轨迹节录的上限 |
| 单条失败原文的上限 | 400 字符 | 100 至 2000 字符 | 错误文字短而通用（第 3.6 节），开头几百字符已经写出失败的种类与位置；更长的输出用事件编号取回 |

超出清单上限时，先把「后来已解决」的合并成一行「另有 N 条失败后来已解决，可以查询」；仍然超出，从最早的未解决失败开始合并成一行「另有 N 条更早的失败，可以查询」。最新的失败最可能被再犯，所以先留新的。

**边界。**

- 只给这个角色自己。失败的经过属于作者的过程（[验证的独立性设计说明](independent-verification.md)「共享的与隔开的」），核验角色与其他部门的请求里没有它。
- 只在本事项内。跨事项的经验由教训发现与常驻教训承担（语义系统设计说明「抽象层与复盘」）。
- 子事项的失败清单留在子事项里；子事项的结果回到上一层时是一份普通提案，上一层只看到它被接纳还是被拒绝。
- 失败清单是事件上的纯函数：同样的事件与规则版本得到同样的一段，上下文清单记录这一段列了哪些事件。

**验收。**

1. 一个角色的会话里有一次失败的工具调用、一次被拒绝的提案、一次没有通过的检查，压缩生效以后的下一次请求里，失败清单逐条列出这三件事的做法、失败原因与事件编号；用事件编号取回的原文与事件里的相同。
2. 同一会话连续压缩两次，第一次分界之前的失败在第二次压缩以后的请求里仍按原文出现。
3. 后来做成的失败标「后来已解决」；超出上限时按上面的顺序合并，最新的未解决失败留在清单里。
4. 删除投影重放，失败清单逐字节相同，重放不发出模型请求。
5. 核验角色的请求里没有被核验方的失败清单。
6. 在会触发压缩的长任务样本上，评测报告列出压缩以后重复清单里已有失败的次数：同一工具以同样参数得到同样的错误，同一检查因为同样的原因失败，同一种提案因为同样的原因被拒绝。目标是 0。出现时逐条核对清单有没有装入这一条：没有装入是缺陷；装入了仍然重复的，记进评测，作为修改整理规则或角色材料的依据。

## 6. 三项证明

### 6.1 确定性（通过）

- **性质测试**：`evals/tests/test_context_view.py` 10 条，200 份随机日志上同事件同规则给出逐字节相同的请求；不修改输入；配对完整；材料恒在首位；存活条目的顺序是日志顺序的子序列；保留量越大留得越多（单调）；同路径只留一份原文；失败结果从不折叠；规则文件与代码字段一致。
- **回放忠实**：规则全关时 646/646 步与记录逐字节一致（第 1.3 节）。
- **规则版本**：`Rules.version()` 是规则取值的规范散列（本版 `sha256:6d66cca8e0935b18…`），请求与清单记版本，重放才能核对「同一份规则」。
- **不用 hypothesis**：项目开发依赖里没有它，CI 用 `uv sync --frozen` 装依赖；性质测试用固定种子的生成器，失败可复现。要引入 hypothesis 是另一张工单。

### 6.2 反事实回放（做了，但这批模型上**没有区分力**）

做法：按部门分层、按步序分桶抽 16 步，温度 0，同一模型分别回答旧视图与新视图；顺手把**旧视图再问一次**作为基线（这一步是原工单没写、但不做就判断不了的）。

| 判据 | 旧对新 | 旧对旧（同一请求重复） |
| --- | --- | --- |
| 动作（工具名 + 参数）完全相同 | 1/16 = 6.3% | 1/16 = 6.3% |
| 工具名的集合相同 | 11/16 = 68.8% | 12/16 = 75.0% |
| 参数里的路径集合相同 | 3/13 = 23% | 2/13 = 15% |
| 动作种类（调用 / 只回复文字） | 16/16 | 16/16 |

**结论与它为什么不够**：这个模型在温度 0 下并不确定——同一个请求问两次，动作完全相同的只有 6.3%，工具名集合相同 75%。旧对新与旧对旧的差值（工具名 −6.2pp、路径 +8pp，n=16）都在噪声之内，**这条判据既证明不了「不丢该留的」，也否证不了**。所以：

- 这条证明记「未通过（判据没有区分力）」，不记为通过。放宽成「工具名集合一致率」也一样：基线本身只有 75%，说明这个模型的动作在第 16 步以后本来就在漂。
- 唯一能从这次抽样里读出的正向证据是**上游回报的输入用量**：16 步合计 201,030 → 185,943 token（−7.5%，抽样偏向早期步，全量是 −16.8%）。用量是确定量，不受模型随机性影响。
- 要恢复这条判据的区分力，只有两条路：换一个温度 0 下逐字确定的模型（同一请求重复问必须 100% 一致），或者把判据从「动作相同」换成「动作引用的材料在新视图里都在」——后者其实就是 6.1 的召回，只是换成模型输出来当输入。

**通过条件**：反事实回放不作为这套装配的通过条件，理由就是上面那张表——旧对旧只有 6.3%，判据在这批模型上没有区分力，不为了这一条去换一个确定性模型。通过条件是下面两条：

1. **引用材料可及性**（确定性，不调模型）：在这 16 步上，把每一步实际动作里引用的材料（工具调用编号、文件路径、引用片段）逐条对新视图核对，要求全部仍在视图里；有不在的，逐条写清是哪一条、为什么可以丢，或者补哪一条规则。它等于把 6.1 的召回换成模型输出来当输入，18 步召回下降的那份清单逐条复核（11 步措辞、4 步路径清单、3 步状态名）：属于启发式噪声的排除，真丢材料的写进规则调整。
2. **端到端**（第 6.3 节）：由实现工单在要发布的提交上跑三个场景，隐藏检查通过条数不下降、模型请求与用量下降。

**引用材料可及性的核对结果**：

- **16 步抽样**：对照回放报告的 18 步召回下降清单（[context-assembly-replay-2026-10-29.json](../evaluation/context-assembly-replay-2026-10-29.json) 的 `losses`），16 步里有 15 步不在清单中，新视图相对现状没有少任何此前出现过的引用。唯一在清单里的是 `run_d50eaf60623e42d6` 工程第 7 步（缺 10 条记号），逐条对照反事实回放里这一步的三份回答（[context-assembly-counterfactual-2026-10-29.json](../evaluation/context-assembly-counterfactual-2026-10-29.json)，空白折叠以后比较）：10 条里 8 条在新视图下的动作中原样出现；另外 2 条没有原样出现，其中一条在旧视图再问一次的回答里出现、旧视图第一次回答里没有，另一条三份回答里都没有。三份回答的调用、`end_line` 与 `expected_text` 完全相同。结论：这一步的下降是模型自己撰写的文字措辞不稳定造成的，没有丢材料，不补规则。
- **18 步清单的逐条复核**：只做完上面这一步。其余 17 步（`run_487814ceab394396` 2 步、`run_22dfbdc3050c4b8a` 1 步、`run_062b44be06ff46bc` 1 步、`run_11cbb348bbb54e93` 12 步、`run_7be8a0074290452c` 1 步）要对照原视图，才能判断每个记号在哪个条目里、被哪条规则折叠。这要用当时的事件库与工件库（回放报告的数据目录是 `C:\code\yudao` 那台机器上的 `%LOCALAPPDATA%\Yudao`，本机同一路径下只有 927 个事件、12 个运行，不是同一份）。拿到以后用 `python -m evals.context replay --db <events.sqlite>` 重放，逐条写进本节。
- **新数据上的复核**（三份试用事件库，产品与工程部门用 deepseek-v4.1-flash，trial-data-e28ea596 里的质检部门用另一家的模型；`verify` 核对 840 步逐字节一致）：新视图丢引用的步明显比原来那批多，几乎全部来自 R3（逐条规则的消融里只有 R3 的召回贡献不为 0）。

  | 数据 | 步数 | 省 | 召回 现状 → 新视图 | 召回下降的步 |
  | --- | --- | --- | --- | --- |
  | 原 22 个运行（2026-10-21、22） | 646 | 16.8% | 0.9548 → 0.9448 | 18（2.8%） |
  | trial-data-1016 | 188 | 46.7% | 0.9391 → 0.8767 | 26（13.8%） |

  | trial-data-e28ea596 | 477 | 51.1% | 0.9329 → 0.8984 | 23（4.8%） |

  丢的记号里代码标识符最多，其次是文件路径与措辞。R3 的保留量在三份新数据上的扫描（召回下降的步数合计 840 步里）：40000 为 6 步、24000 为 41 步、16000 为 68 步；省量依次是 11% 至 18%、30% 至 37%、45% 至 51%。从 16000 降到 8000，每多省一个百分点丢的召回是 16000 以上的 2 到 3 倍，拐点仍在 16000。所以召回的口径下，16000 是这条曲线上效率最高的点，但它要付出 3% 至 6% 的召回，丢引用的步占 5% 至 14%。这些记号是不是真的让模型做错事，召回回答不了；费用有没有降下来，见第 6.4 节。

### 6.3 端到端（**未做**，说明原因与判据）

三个固定回归场景（场景 1、2、3）用 `evals/scorer` 打分、比隐藏检查分数与费用，这条现在**跑不了**：新视图还没有在 `harness/` 里实现，而架构师不改 `harness/`。场景 3 的最近一次读数（2 次运行、总用量均值 114,151 token、费用未知——模型服务没有上报用量与单价）只能当对照的起点。

所以端到端不写成「通过」，而是写成**实现工单的验收**：实现以后在要发布的提交上跑三个场景，判据是「隐藏检查的通过条数不下降，模型请求与用量下降」。这批 646 步的读数给出的预期是输入用量 −16.8%，场景 3 只有 5 至 7 个请求一步，预期收益更小（第 3.2 节：步序 1 的省量 20.9% 主要来自 R5，后面才来自 R3），不承诺具体的数。

### 6.4 成本：按前缀缓存计价（新增，**未通过**，折叠规则要改）

前几项证明用 token 数代表费用。上游按前缀缓存计价：一步的请求与上一步的请求从头起相同的那一段命中缓存，按缓存读的单价（取十分之一）算；从第一处不同起的全部内容按未缓存的价格算。不折叠的历史只在末尾追加，上一步的请求整段命中；折叠把旧的一轮换成占位，从那一处起之后的内容都按未缓存重发。所以 token 数下降不等于费用下降。

**方法**：`python -m evals.context cost --db <events.sqlite>`（`evals/context/cost.py`）。对每个会话按步序重放，逐条比较相邻两步的请求，算命中缓存的 token；费用 = 命中 × 0.1 + 其余 × 1。每条规则单独开（其余关掉）各算一遍。

**校验**：基线（记录下来的请求）反推的缓存命中占比，与上游回报的 `cache_read_tokens / input_tokens` 对照：trial-data-1016 为 91.5% 对 91.2%，trial-repro 为 94.7% 对 97.0%，trial-data-e28ea596 为 63.5% 对 60.6%。这个折算在基线上与上游的回报吻合。它只模拟前缀命中，不含缓存过期、命中的块粒度与写缓存的加价。

**结果**（折算费用，现状 = 100%；报告在 `docs/evaluation/context-assembly-cost-*-2026-10-29.md`）：

| 变体 | token 数 | trial-data-1016 | trial-repro | trial-data-e28ea596 |
| --- | --- | --- | --- | --- |
| R1 部门输入只留最新 | 98% 至 100% | 315% | 101% | 133% |
| R2 同路径读取只留最新 | 99% 至 100% | 100% | 104% | 101% |
| R5 引证段按引用门控 | 99.5% 至 100% | 100% | 99% | 100% |
| R3 保留 16000 / 最少省 4000 | 51% 至 56% | 106% | 138% | 58% |
| R3 保留 40000 / 最少省 20000 | 89% 至 98% | 123% | 105% | 73% |
| 全开 | 49% 至 55% | 152% | 142% | 66% |

按部门看，决定费用的是这个部门的缓存命中：工程部门（deepseek）三份数据里命中 92%、97%、92%，R3 的 16000 / 4000 让它的费用到 107%、136%、127%；质检部门在 trial-data-e28ea596 里命中只有 43%（用另一家的模型服务），同一条规则把它的费用降到 43%，而它占了那份数据 57% 的 token，所以整体降到 58%。

**结论**：
- R1 费用持平或更高（101% 至 315%），省的 token 只有 2%：它把旧输入改成占位，改动落在请求的前部，后面全部失去缓存。没有收益。
- R2、R5 费用持平（99% 至 104%），没有收益。
- R3 的费用取决于这个调用目标的缓存命中：命中在九成以上，折叠让费用升高 6% 至 40%；命中低，折叠省一半以上。
- 第 5 节「请求越短，费用越低」这句话只在缓存命中低的调用目标上成立。

第 6.1、6.2 的证明没有变。按这些结论定的取舍写在第 4 节开头与「开启条件」：实现以后，用同一个方法在这三份数据上核对开启条件下的 R3、R7，三份的折算费用都不高于现状。
