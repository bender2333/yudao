# 本地通用工具设计说明

状态：工具边界已实施，3.2A 于 2026-09-26 验收（[3.2A 验收报告](../stage-3/3.2a-registered-commands-e2e-report-2026-09-26.md)）；已有代码的进入方式改为 3.8 的建档，未实施（#124）。本文写明工程与质检使用的本地工具的边界，3.2B 网络与 MCP、3.2C 执行环境服务与 3.2D 浏览器与 computer use 新增的工具同样遵守这些边界。

## 1. 使用过程

1. 已有项目经 3.8 的建档进入：`project.onboard` 只读采集源目录的一份确定代码快照，用户确认建档写出的初始 PRD 以后，快照成为项目的第一次采纳；之后的事项在 Yudao 管理的独立工作区中从采纳成果开始。源项目不被直接改写，变化由可核验的交付提供；建档以后源目录的修改不进入项目。
2. 产品确认本次变更，工程制定计划，然后搜索、阅读、编辑、执行项目登记的本地构建与测试命令。
3. 模型可以看到命令退出状态和输出；成功退出只证明该命令成功，任务是否完成由独立质检判断。
4. 工程提交确定的完整代码树；质检在独立副本上运行公开检查并给出结论；项目按已有规则采纳。

代码快照接入只包含来源、版本与摘要、文件清单、初始基线和隔离副本，由 `project.onboard` 使用；`work_item.create` 没有代码快照来源。建档事项、初始 PRD 与基线采纳见[接入已有项目设计说明](existing-project-onboarding.md)（[D33](../requirements/existing-project-onboarding.md)）。

## 2. 工具边界

| 能力 | 设计要求 | 验收反例 |
| --- | --- | --- |
| 公开树 | 工作区中按项目的忽略规则（项目中的 `.gitignore` 与 Git 的排除文件）排除之后的全部文件与目录；忽略规则由 Git 命令行判断，做法参照 OpenCode 的快照（`0027387`，`packages/opencode/src/snapshot/index.ts` 第 172 至 270 行）。被忽略的路径（例如依赖目录与构建产物）不进入快照、封存与交付，部门的工具也看不到。其余部分出现链接、特殊文件等无法表示的条目时，运行以 `workspace_unrepresentable` 暂停（[D09](../requirements/execution-limits.md)） | 依赖目录中的链接不影响快照；未被忽略的链接使运行暂停，停止原因与说明写明相对路径 |
| 搜索、目录与区间阅读 | 限在公开项目材料范围；返回来源和位置；大结果明确截断，并能继续取回 | 私有部门目录、Git 元数据、路径逃逸和链接绕行不能变成跨部门材料 |
| 区间编辑 | 针对已读取版本或可唯一核对的原文；不匹配时拒绝覆盖，让模型重新读取 | 文件已变、重复匹配、不存在目标、编码差异不能静默改错 |
| 本地命令 | 项目登记的命令及参数范围，固定工作目录、最小环境、时限、输出限制和进程树管理 | 未登记命令、超时、取消、子进程遗留、输出过量及退出失败均有真实状态 |
| 动作回执 | 执行前记录动作身份与输入依据；结果绑定命令、快照、退出状态、输出及尝试 | 执行完成但确认没有保存时，不能记为未执行 |
| 独立质检 | 检查绑定最后提交的完整树，检查中的修改不能成为已测试的交付 | 修改检查副本、复用旧回执、改树后沿用通过结论均被拒绝 |

所有工具结果、拒绝原因与停止说明中的路径都写成工作区内的相对路径，主机上的绝对路径不进入模型看到的内容。

本地命令只执行项目登记的命令，不提供任意 shell 字符串、安装软件或发布权限。专用文件工具负责可审计的编辑，工程的命令结果不能代替质检回执。

工作目录和环境白名单不是操作系统沙箱，项目脚本本身也能执行任意代码。本地进程只用于可信本地项目与经过审阅的构建和测试入口。任意代码的隔离执行由 3.2C 执行环境服务的本机容器提供（[D29](../requirements/remote-execution.md)），不能靠命令名匹配或 Prompt 声称实现隔离。

## 3. 使用的依赖与成熟实现

- 文件、进程、SQLite、临时目录和归档先使用 Python 标准库与项目已有实现，不另建文件工具体系。
- 搜索使用 ripgrep，声明为运行前置并验证平台可用性，不静默改用另一套语义。
- 网络取回由 3.2B 使用已有的 HTTPX；MCP 使用官方 Python SDK，不自写协议客户端。模型调用使用官方 OpenAI SDK 与统一 Provider 模块（[Provider 层设计](provider-layer.md)）。
- 进程超时不等于整棵进程树已经停止。Windows 和 POSIX 分别验证，使用成熟的进程管理能力；尚未验证的平台不标为支持。
- OMP 的工具与会话审查用作接口和证据模式的参考，不引入 OMP 运行时接管 Yudao 的部门循环。
