# 本地通用工具设计说明

总图位置：第四节「动作」的缝；第一节「模型与工具」方框。依据：[ADR-0038](../adr/0038-function-first-commands-without-registration.md)、[架构与需求诊断](../research/architecture-diagnosis-2026-10-19.md)。

本文写明三个部门使用的本地工具的边界，3.2B 网络与 MCP、3.2C 执行环境服务、3.2D 浏览器与以后阶段的 computer use 新增的工具同样遵守这些边界。

## 1. 使用过程

1. 已有项目经 3.8 的建档进入：`project.onboard` 只读采集源目录的一份确定代码快照，用户确认建档写出的初始 PRD 以后，快照成为项目的第一次采纳；之后的事项在 Yudao 管理的独立工作区中从采纳成果开始。源项目不被直接改写，变化由可核验的交付提供；建档以后源目录的修改不进入项目。
2. 产品确认本次变更；工程在它的一轮工作中，在运行工作区中搜索、阅读、编辑，用 `bash` 运行任意命令，例如安装依赖、构建、启动服务、运行测试。其他会话在自己的检查工作区中做同样的事情。
3. 模型可以看到命令的退出状态和输出；成功退出只证明该命令成功，任务是否完成由核验角色判断（三部门里是质检）；定义里没有核验角色的事项，指定角色交了完成就以开环完成结束（[形态与核验角色设计说明](forms-and-verifier-role.md)「开环完成」）。下面写到的工程与质检，在其他形态里是有写入范围的角色与核验角色。
4. 工程提交确定的完整代码树，交付引用在交付快照上运行的检查；质检在交付快照的全新副本上运行检查，包括自己按 PRD 写的测试，然后给出结论；项目按已有规则采纳。

代码快照接入只包含来源、版本与摘要、文件清单、初始基线和隔离副本，由 `project.onboard` 使用；`work_item.create` 没有代码快照来源；`project.create` 的起始文件夹用同一条采集路径，见[项目的起始文件夹设计说明](project-initial-files.md)。建档事项、初始 PRD 与基线采纳见[接入已有项目设计说明](existing-project-onboarding.md)（[D33](../requirements/existing-project-onboarding.md)）。

## 2. 工作区

| 工作区 | 谁使用 | 从哪里建立 | 生命周期 |
| --- | --- | --- | --- |
| 运行工作区 | 工程的一轮工作：读取、写入与命令 | 封存快照 | 每个 run 一个，随 run 存在 |
| 检查工作区 | 其他每个会话：质检、产品、在询问分支里回答的工程；会话的文件工具与 `bash` 都在这里执行 | 当前快照，在这个部门的检查位置上建立；质检的从它当前面对的快照建立：最新的封存交付，还没有交付时是事项开始时的项目起点 | 每个会话一个，会话第一次使用文件工具或命令时建立，会话结束时删除；质检的会话进行中有新的交付封存时，在质检的下一步从这份交付重建 |
| 检查副本 | 一次 `run_check` | 被检查的快照；质检的检查另外放入质检的测试材料 | 每次检查一个，检查结束时删除 |

- 每块内容只有一个写入者（[三部门的循环结构](department-loop.md)「同时运行的条件」）：运行工作区只由工程的一轮工作写入；检查工作区里的改动只留在这个会话中，不进入运行工作区与交付。
- 质检的测试材料：质检在检查工作区中的一个固定目录里写测试，这个目录不进入公开树与交付快照，只出现在质检的检查工作区与检查副本中。主机在会话中保存这个目录的内容作为质检的材料，每次保存是一个版本；新的检查工作区（包括交付到达后重建的）与每个检查副本放入当前版本。交付之前写的测试因此进入之后每一份交付的检查。
- 依赖目录与构建产物被项目的忽略规则排除，不进入快照；每个工作区与检查副本中由命令重新生成，下载的内容来自执行位置上的依赖缓存（[执行环境服务设计说明](execution-environment.md)「执行位置上的程序与依赖缓存」）。

## 3. 工具边界

| 能力 | 设计要求 | 验收反例 |
| --- | --- | --- |
| 公开树 | 工作区中按项目的忽略规则（项目中的 `.gitignore` 与 Git 的排除文件）排除之后的全部文件与目录；忽略规则在进程内用 pygit2（libgit2）判断（[ADR-0024](../adr/0024-git-in-process-with-pygit2.md)），做法参照 OpenCode 的快照（`0027387`，`packages/opencode/src/snapshot/index.ts` 第 172 至 270 行）。被忽略的路径（例如依赖目录与构建产物）不进入快照、封存与交付，部门的文件工具也看不到。其余部分出现链接、特殊文件等无法表示的条目时，运行以 `workspace_unrepresentable` 暂停（[D09](../requirements/execution-limits.md)）。捕获期间别的部门正在写的文件变了，快照这一侧重读：短暂等待以后重新捕获，有界次数用完后才以 `TreeError` 交出文件与原因；判据不改，一次并发写入不结束整个事项（2026-10-29 试用 Tc1f7185a-02）。捕获的身份比对只比路径与句柄两侧都取得到的字段（设备、inode、种类、链接数、大小、mtime），权限位不参与：Windows 上 `Path.lstat()` 会按 `.cmd`/`.bat`/`.exe` 后缀把权限位补成可执行，而 `os.fstat()` 拿到的是句柄、不补，拿 `st_mode` 当身份会让工作区里只要有一个这类文件就每次捕获都报 `TreeError`（2026-10-29） | 依赖目录中的链接不影响快照；未被忽略的链接使运行暂停，停止原因与说明写明相对路径；两个部门同时读写同一个工作区时，捕获照常成功；工作区里有 `.cmd`、`.bat`、`.exe` 这类文件时捕获照常成功 |
| 搜索、目录与区间阅读 | 限在会话所用工作区的公开树；返回来源和位置；大结果明确截断，并能继续取回 | 私有部门目录、Git 元数据、路径逃逸和链接绕行不能变成跨部门材料 |
| 区间编辑 | 针对已读取版本或可唯一核对的原文；不匹配时拒绝覆盖，让模型重新读取 | 文件已变、重复匹配、不存在目标、编码差异不能静默改错 |
| 质检的文件工具（M2 起） | 质检会话有写文件与区间编辑的工具，作用在它自己的检查工作区：写在测试材料目录里的内容按测试材料保存，其余改动随检查工作区在会话结束时删除；写不到运行工作区，也不进入交付快照。此前质检只能经 `bash` 的 heredoc 写测试，转义出错时要反复修补（[架构与需求诊断](../research/architecture-diagnosis-2026-10-19.md)第 2.3 节） | 质检的写入出现在运行工作区或交付快照中，被拒绝 |
| 命令（`bash`） | 三个部门都可以使用。接受任意命令字符串，在会话所用工作区的根目录用 bash 运行，每次调用启动一个新进程，不保留 shell 状态。时限由模型在调用时给出，缺省值与最长值是规则登记中的暂定默认值（缺省 300 秒，最长 3600 秒）；超时或取消时结束整个进程树；命令自己退出时仍留着的子进程随这次调用一起结束，回执写明留下过进程、已经结束，并提示长期运行的服务用后台运行（一次调用就是这棵进程树的一段生命）；输出超过上限时，完整输出保存为工件，模型看到截断的部分并能继续取回。进程得到 Yudao 进程（远程为执行代理进程）的全部环境变量；输出中已知密钥的值替换成名字。可以后台运行：立即返回一个编号，输出持续收集，模型用编号读取新的输出或结束进程；会话结束、事项暂停或取消时，这个会话启动的后台进程全部结束；Yudao 或执行代理重新启动以后，后台进程记为已经结束 | 超时、取消、子进程遗留、输出过量、退出失败、会话结束后仍在运行的后台进程、执行位置上找不到 bash，均有真实状态 |
| 检查（`run_check`） | 三个部门都可以使用。接受任意命令字符串，在检查副本中用 bash 运行，时限与 `bash` 相同（缺省 600 秒，最长 3600 秒）；运行前后核对副本的公开树，回执绑定快照与质检测试材料的版本。交付与放行只认检查回执；`bash` 的结果是动作回执，不能当作检查 | 修改检查副本、复用旧回执、改树后沿用通过结论、测试材料改变后沿用旧回执，均被拒绝 |
| 动作回执 | 执行前记录动作身份与输入依据；结果绑定命令、所用工作区、退出状态、输出及尝试 | 执行完成但确认没有保存时，不能记为未执行 |
| 结果未知 | 文件工具按动作前的快照自动核实，核实出确定结果时交回这个结果；其余结果未知的动作作为工具结果交还发出它的会话，写明执行被中断、结果未知，附上已经收到的输出，由模型检查以后决定是否重新执行（[恢复契约与故障矩阵](recovery-contract-and-fault-matrix.md)「动作分类与处置」） | 重新启动时正在运行的命令以「执行被中断、结果未知」交还模型，附上已经收到的输出；不等待用户回答 |
| 独立质检 | 质检在交付快照上检查：检查工作区从封存的交付建立（还没有交付时从事项开始时的项目起点建立，不读取运行工作区），检查副本绑定交付快照；检查中的修改不能成为已测试的交付 | 修改检查副本、复用旧回执、改树后沿用通过结论均被拒绝 |
| 网络取回 | 三个部门都可以使用，在控制主机上执行；任何 http 与 https 地址都可以取回；只发 GET，不带凭据与 Cookie；拒绝 Yudao 服务自己的地址与端口；下载大小、时限与重定向次数有上限；完整内容保存为外部来源工件，大结果分页返回并能继续读取；评测期间不联网（[网络取回与 MCP 工具设计说明](network-and-mcp.md)「网络取回」） | Yudao 服务自己的地址、超出大小与时限、请求中的凭据与 Cookie，均有真实状态 |
| MCP 工具 | 项目设置中写明的 MCP 服务器提供的工具，全部直接提供给可以使用的部门，在控制主机上执行；结果未知时按上面「结果未知」一行处理；凭据只写名称，不出现在事件、工件与日志中（[网络取回与 MCP 工具设计说明](network-and-mcp.md)「MCP 服务器」与「恢复契约」） | 调用超时、取消、进程遗留与结果未知均有真实状态；凭据值不出现在保存的内容中 |

所有工具结果、拒绝原因与停止说明中的路径都写成工作区内的相对路径，主机上的绝对路径不进入模型看到的内容。

交给模型的工具结果条目只有回执的三项：是否成功、输出、错误（带图像的结果另加一组工件引用，见[浏览器与 computer use 设计说明](browser-and-computer-use.md)「请求中的图像」）。回执上的其他字段（例如被拒绝的标记与原因）留在回执上，不进这一条。事件载荷里记下的结果就是模型看到的结果：按事件重新装配请求得到的条目与当时发出的逐字相同，所以要让模型看到新字段，先把它记进事件载荷。

代码在执行位置上直接运行，拥有所在账户的全部权限，Yudao 不提供操作系统层面的沙箱（[执行环境服务设计说明](execution-environment.md)「代码的权限、认证与加密」）。`bash` 与检查运行的命令能读写这个账户能访问的全部文件，包括别的部门的材料；部门的可见范围对 Yudao 提供的工具有效。来源不明的仓库，把项目的执行位置设到另一台登记的机器。

## 4. 使用的依赖与成熟实现

- 文件、进程、SQLite、临时目录和归档先使用 Python 标准库与项目已有实现，不另建文件工具体系。
- 搜索使用 ripgrep，声明为运行前置并验证平台可用性，不静默改用另一套语义。
- bash 是执行位置上的运行前置：Linux 使用系统的 bash；Windows 使用 Git for Windows 的 bash，查找顺序参照 OMP（oh-my-pi@e3106be，`packages/utils/src/procmgr.ts:135-180`：Git 的安装目录，然后是 PATH 上的 `bash.exe`）。找不到时工具结果写明原因，不改用 cmd 或 PowerShell。git 本来就是执行位置上的必需程序（[执行环境服务设计说明](execution-environment.md)「执行位置上的程序与依赖缓存」），Windows 上安装 Git for Windows 时同时带有 bash。
- 后台运行与时限的做法参照 OMP 的 bash 工具（`packages/coding-agent/src/tools/bash.ts:335`、`:900-1000` 的 `async` 参数与任务管理，`packages/coding-agent/src/tools/tool-timeouts.ts:11` 的缺省 300 秒、最长 3600 秒）。
- 网络取回由 3.2B 使用已有的 HTTPX；MCP 使用官方 Python SDK，不自写协议客户端。模型调用使用官方 OpenAI SDK 与统一 Provider 模块（[模型管理设计说明](model-management.md)「统一调用、取消与观测」）。
- 进程超时不等于整棵进程树已经停止。Windows 和 POSIX 分别验证，使用成熟的进程管理能力；尚未验证的平台不标为支持。
- OMP 的工具与会话审查用作接口和证据模式的参考，不引入 OMP 运行时接管 Yudao 的部门循环。
