# 部门指导的处理设计

日期：2026-09-06 设计；2026-10-12 按 [ADR-0036](../adr/0036-concurrent-departments-and-nested-asks.md) 修改送达与处理结果，用户采纳；2026-10-13 补充放行等发给产品的输入处理完（第 2 节、第 4 节第 8 条），用户确认；2026-10-14 按 [ADR-0039](../adr/0039-departments-work-from-watched-outputs.md) 修改：指导是接收部门关注的成果，等待工作的部门以它开始一轮工作，不再开以用户为提问方的询问分支，用户确认。对应 [D20](../requirements/department-guidance.md)，循环结构见[三部门的循环结构](department-loop.md)第 6 节。已实现：命令 `guidance.send` 接收指导，`harness/interactions.py` 的 `receive_guidance` 保存原文并写入接收事件；指导记录由 `department.workspace` 查询读取（[应用层与接口层设计说明](app-and-interface.md)第 7.1 节）；第 2 节表里四种送达已实现（#1009）。2026-10-26 补定三件事：一轮工作怎么回答用户（第 3 节）、什么叫处理完（第 3 节）、放行怎么等（第 2.1 节），由 #1037、#1038、#1039 与 #561 按这个顺序实现。 总图位置：第三节外环「你中途的指导」那条规矩；第一节「你」方框。

## 1. 三类职责

| 职责 | 负责的结果 | 不承担的责任 |
| --- | --- | --- |
| 原文与接收 | 保存事项、接收部门、原文及顺序，返回可追溯的接收记录 | 发送成功不表示模型已看到或处理 |
| 送达与处理 | 按接收部门的状态把指导作为通知加入它的历史，或让它以这段指导开始一轮工作，保存回答 | 不创建独立的聊天运行器，不让页面直接推进部门或修改 PRD |
| 界面与观察 | 显示草稿、接收、进入模型输入与回答，能够回到对应的工作 | 不按计时器模拟处理，不把一个部门收到的原文自动发给其他部门 |

## 2. 送达

| 接收部门的状态 | 处理 |
| --- | --- |
| 正在一轮工作中 | 在它的下一步作为通知加入它的历史；正在进行的模型调用与工具照常结束，下一步的请求包含这段指导 |
| 一轮工作停在一次询问上等待回答 | 加入它的历史，它收到回答、继续工作的那一步看到 |
| 等待工作 | 指导是它关注的成果，控制核心让它以这段指导开始一轮工作，其他部门照常运行；这一轮可以读取、写入（工程写运行工作区）、运行检查、询问与提交正式成果，以提交正式成果或回答用户结束，回答交给用户 |
| 事项已结束 | 拒收，保留用户的草稿 |

发给产品的指导就是新输入，原文保存进 intend。同一个部门收到的几段指导按接收的顺序处理：一轮工作正在进行时，后一段作为通知在它的下一步送达。取消优先于新的工作，已经发生的工具结果保留。

新输入不打断任何部门，但放行要等它处理完：质检提交放行时，发给产品的输入还没有处理完（还没进入产品的模型输入，或者收到它的那一轮工作还没结束），这次提交等到处理完再裁决。产品修订了 PRD，放行因交付依据的是旧版本被拒绝；产品没有修订，放行被接纳（[三部门的循环结构](department-loop.md)第 6 节）。

### 2.1 放行怎么等

等待的做法是：**这一次提交留在步骤驱动里等，不返回给模型。**

1. 质检提交放行（`qa_review` 的结论是 `release`）时，如果有发给产品的输入还没有处理完，工具许可这一步不给出结果，步骤驱动在安全节点上等。等的是同一个等待点：等待模型服务重试用的就是它，取消、暂停、运行时间用完照常生效；产品的那一轮工作结束、提交以后，提交方唤醒它。这一次调用不返回给模型，不写事件，不占步数。只有放行等；质检提交缺陷记录不等，缺陷记录送到工程，PRD 有变化时工程与质检本来就会重新看自己的工作。
2. 醒来以后重新做一遍提交判断，用的是此刻的 PRD 与交付：PRD 有了新版本，提交因交付依据的是旧版本被拒绝，拒绝的结果交回质检，它下一步看到新版本的通知；PRD 没有变，提交被接纳，事项结束。
3. 等待必须发生在「工具开始」事件写入之前。这样重新启动以后，会话恢复时这条模型已经发出、还没有处置的工具调用会照常重新执行（`engine.py` 的 `_unexecuted_calls`），重新进入同一个等待。「等待期间重新启动，提交仍在等待」靠这一条成立，不新增事件种类，也不把「在途的放行」写进事实。
4. 等待期间其他部门照常工作，包括产品询问质检：质检的主线会话在等，被询问时在分支里回答（循环结构第 3.2 节第 1 条），两边不互相等。

为什么不用拒绝或推迟：被拒绝以后质检没有可以等的工具，模型每一步重试一次，把步数烧光，事项因上限暂停，这正是 2026-10-13 要避免的。为什么不把在途放行记成新的事件：重启以后未处置的工具调用已经能恢复它，新增事件种类要提高 run 事件版本，只为一件事实记两遍。


## 3. 处理结果与来源

接收、进入模型输入、回答分别写成事件，界面据此显示指导的状态。指导作为通知送达正在进行的一轮工作时，后续的工具调用与提交就是处理的结果，没有单独的回应；以指导开始的一轮工作以正式成果或回答用户结束。接收部门以后再工作时，它的历史里有这段指导与它的处理。

**处理完只有一个说法：收到这条输入或指导的那一轮工作结束了。** 「收到」是它进入了这一轮的模型输入（部门输入事件），「结束」是这一轮的主线会话正常结束（轮结束事件）。指导的「已回答」和放行等的「发给产品的输入处理完」是同一件事的两个读法，读同样的事实。取消、暂停、上限不算处理完：取消和上限让事项结束，指导停在「已进入模型输入」，界面按事项已结束显示；暂停以后继续的是同一轮，结束时才算。

**已回答由主机写。** 一轮工作正常结束时，主机为这一轮收到的每条指导写一条回答事件，部门不提交，也没有状态词、结果事件的绑定与核对。事件里记是哪一轮、怎么结束的：提交被接纳，或者用文字回答。

**用文字回答用户。** 以指导开始的一轮工作，如果它开始时关注的成果里只有指导（没有新的 PRD、交付或缺陷记录），模型不调用工具的文字回复就是对用户的回答，一轮就此结束；回复的文字已经记在模型消息里，部门页本来就显示。其他的轮仍然要求调用工具，没有工具调用的回复照旧提醒，次数用完事项停止。这条规则只放宽「一轮怎么结束」，不给指导任何额外的权限（见下）。

原文准确保存；部门在询问或回答里转述时引用原文与来源，不以模型改写后的描述冒充用户原话。其他部门只能看到接收部门在询问或回答里引用的部分。

指导不授予额外的权限：工程不能据此直接修改 PRD，质检不能据此修改交付；需要改变要求时询问产品，需要修改代码时由工程在它的一轮工作中修改（质检提交缺陷记录，或用户把指导发给工程）。

## 4. 必验反例

1. 模型调用进行中收到指导，这次调用照常结束，下一步的请求包含指导。
2. 写入工具进行中收到指导，已写入的内容保留，下一步看到真实的工作区与指导。
3. 接收部门在等待工作时收到指导，以它开始一轮工作，其他部门不停止；发给等待中的工程的修改要求，在这一轮里直接改运行工作区并交付，或者回答用户。
4. 发给产品的指导修订了 PRD，正在工作的部门在下一步收到通知；质检正在核验时，放行因交付依据的是旧版本而被拒绝。
5. 同一个部门连续收到两段指导，按接收的顺序处理。
6. 取消与指导同时到达时，取消立即生效，已经接收的指导保留可查。
7. 事项结束以后发送的指导被拒收，草稿保留；切换部门、刷新、断线或重复发送时，不改变接收部门，不重复形成同一接收事实。
8. 质检提交放行时，产品正在一轮工作中处理用户的新输入：放行等到这一轮结束再裁决。产品修订了 PRD 时放行被拒绝，没有修订时放行被接纳；等待期间取消，事项取消，没有放行。

## 5. 界面对应

部门页继续采用冻结原型的主消息区与右侧检查区。输入区写明接收部门，接收记录、进入模型输入与回答沿消息显示。等待、拒收和查询失败使用真实状态；发送中的对象固定，切换查看对象不改写已发的命令。
