# 部门指导的处理设计

日期：2026-09-06 设计；2026-10-12 按 [ADR-0036](../adr/0036-concurrent-departments-and-nested-asks.md) 修改送达与处理结果，用户采纳；2026-10-13 补充放行等发给产品的输入处理完（第 2 节、第 4 节第 8 条），用户确认。对应 [D20](../requirements/department-guidance.md)，循环结构见[三部门的循环结构](department-loop.md)第 6 节。已实现：命令 `guidance.send` 接收指导，`harness/interactions.py` 的 `receive_guidance` 保存原文并写入接收事件；指导记录由 `department.workspace` 查询读取（[应用层与接口层设计说明](app-and-interface.md)第 7.1 节）。本文第 2、3 节的送达与处理结果未实施。

## 1. 三类职责

| 职责 | 负责的结果 | 不承担的责任 |
| --- | --- | --- |
| 原文与接收 | 保存事项、接收部门、原文及顺序，返回可追溯的接收记录 | 发送成功不表示模型已看到或处理 |
| 送达与处理 | 按接收部门的状态把指导加入它的历史，或开询问分支处理并保存回答 | 不创建独立的聊天运行器，不让页面直接推进部门或修改 PRD |
| 界面与观察 | 显示草稿、接收、进入模型输入与回答，能够回到对应的工作 | 不按计时器模拟处理，不把一个部门收到的原文自动发给其他部门 |

## 2. 送达

| 接收部门的状态 | 处理 |
| --- | --- |
| 正在工作 | 在它的下一步作为通知加入它的历史；正在进行的模型调用与工具照常结束，下一步的请求包含这段指导 |
| 在询问链上等待回答 | 加入它的历史，它收到回答、继续工作的那一步看到 |
| 不在工作 | 控制核心立即开一个询问分支处理，提问方是用户，回答交给用户，其他部门照常运行；回答的限制与询问相同，产品可以修订 PRD，工程与质检只读取文件与运行检查 |
| 事项已结束 | 拒收，保留用户的草稿 |

发给产品的指导就是新输入，原文保存进 intend。同一个部门收到的几段指导按接收的顺序处理，前一段还在询问分支里处理时，后一段等它结束。取消优先于新的工作，已经发生的工具结果保留。

新输入不打断任何部门，但放行要等它处理完：质检提交放行时，发给产品的输入还没有处理完（还没进入产品的模型输入，或者收到它的会话还没结束），这次提交等到处理完再裁决。产品修订了 PRD，放行因交付依据的是旧版本被拒绝；产品没有修订，放行被接纳（[三部门的循环结构](department-loop.md)第 6 节）。

## 3. 处理结果与来源

接收、进入模型输入、回答（在询问分支里处理时）分别写成事件，界面据此显示指导的状态。部门在自己的历史里处理指导时，后续的工具调用与提交就是处理的结果，没有单独的回应。接收部门以后再工作时，它的历史里有这段指导，在分支里处理过的还有它的回答。

原文准确保存；部门在询问或回答里转述时引用原文与来源，不以模型改写后的描述冒充用户原话。其他部门只能看到接收部门在询问或回答里引用的部分。

指导不授予额外的权限：工程不能据此直接修改 PRD，质检不能据此修改交付；需要改变要求时询问产品，需要修改代码时按交接处理。

## 4. 必验反例

1. 模型调用进行中收到指导，这次调用照常结束，下一步的请求包含指导。
2. 写入工具进行中收到指导，已写入的内容保留，下一步看到真实的工作区与指导。
3. 接收部门不在工作时收到指导，在询问分支里处理，持有交接的部门不停止；回答交给用户，接收部门的历史增加一条指导与回答的记录。
4. 发给产品的指导修订了 PRD，正在工作的部门在下一步收到通知；质检正在核验时，放行因交付依据的是旧版本而被拒绝。
5. 同一个部门连续收到两段指导，按接收的顺序处理。
6. 取消与指导同时到达时，取消立即生效，已经接收的指导保留可查。
7. 事项结束以后发送的指导被拒收，草稿保留；切换部门、刷新、断线或重复发送时，不改变接收部门，不重复形成同一接收事实。
8. 质检提交放行时，产品正在询问分支里处理用户的新输入：放行等到分支结束再裁决。产品修订了 PRD 时放行被拒绝，没有修订时放行被接纳；等待期间取消，事项取消，没有放行。

## 5. 界面对应

部门页继续采用冻结原型的主消息区与右侧检查区。输入区写明接收部门，接收记录、进入模型输入与回答沿消息显示。等待、拒收和查询失败使用真实状态；发送中的对象固定，切换查看对象不改写已发的命令。
