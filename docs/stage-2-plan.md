## 1. 用户确定的顺序

1. 解决 Provider 连接问题，并支持统一 Provider 管理与部门独立绑定，最高优先级。
2. 补齐真实验收，完成第一阶段。
3. 审查 OMP，系统性借鉴。
4. Context/Trace View，作为可观测性核心。
5. 按已完成原型完善 Web 功能和产品体验，Provider 等配置原型预留。
6. 优化 Prompt，提升质量。

上述全部完成，再开始较大的功能。第 2 项仍是第一阶段的最终验收，不通过阶段改名把它留成历史欠项。第 3-6 项的改动也需验证受影响行为，不能用第 2 项改动前的成功记录代替新版本验证。

## 2. 每项交付与完成条件

| 顺序 | 解决的问题 | 应交付的结果 | 完成依据 |
| --- | --- | --- | --- |
| 1 Provider 基础 | 间歇连接中断仍影响真实长流程；部门独立绑定已接入本地验证 | 连接诊断、有界恢复、取消及尝试记录；统一 Provider/模型目录和部门绑定，详见 D18 | 慢响应、重试耗尽、取消及新输入经过验证；不同部门实际使用至少两个 Provider 完成流程，压缩及重试归属正确。增加等待、修改展示名称或一次探针成功不单独算解决 |
| 2 第一阶段真实验收 | 局部成功尚未覆盖实际用户的完整操作 | 冻结版本的真实 Web 与小窗压缩流程、最终 QA、交付及输入来源审计 | 持续输入形成新要求和计划，真实交付按最终合同通过独立 QA；压缩后继续到最终交付；Git、封存、事件及实际输入互相对应。失败样例保留 |
| 3 OMP 系统审查 | 原生运行时需要系统吸收成熟实现的经验 | 固定版本的源码审查、机制对照、借鉴/不采用理由及独立的小改进清单 | 每项判断可追到实际源码；选中的必要改进完成独立验证，其他研究项明确归档，不留下不清楚的待处理清单 |
| 4 Context/Trace View | 研发者需要看清每次请求实际读到什么、发生了什么、为什么接续或停止 | 按已完成观测原型查看真实 Context、请求/响应、尝试、事件及用量，见 D21 | 失败、重试或压缩可回到对应输入输出；缓存及尝试不重复计数，缺失不冒充零；历史、实时和导出一致 |

## 3. 第一优先级的当前事实

以本轮读取的 [D17](requirements/provider-retries.md)、[原生设计](native-loop-design.md)和[验收记录](mvp-acceptance.md)为准：

- 当前使用原生三部门内核和官方 Responses SDK，OMP 是参考，不是运行依赖。
- 已记录的主要故障是约数秒后出现的 TLS EOF/连接中断；同配置也有成功响应。不能把它误记为正常一分钟响应触发超时，也不能据此确定是模型配置、远端或本机哪一方的根因。
- H 的有界重试已提交为 `7c720e1`，默认单次 600 秒、最多 3 次尝试和失败输出隔离已有定向验证。真实 Web 与小窗仍因连续三次连接失败而未最终放行，机制已实现不等于连接问题和第一阶段整体已完成。
- 当前继续复用 H 及其验收证据，不另开重试运行器；本轮 Web 工作只规划与归档原型。
- [D18](requirements/department-providers.md) 的统一目录、三部门绑定和任务冻结已接入原生循环。本地 HTTP/SSE 捕获用于验证实际连接、模型、认证、协作和异常边界；真实跨 Provider 最终 QA 仍未完成，配置 UI 继续等待原型。

近期应在当前 H 实现上完成独立审查和故障复现，区分网络、适配、流式协议及内核行为。重试是恢复措施，诊断仍需保留原始失败与实际等待。认证、额度及不可恢复协议错误不靠反复请求掩盖。

真实验收要使用用户当前指定的 provider 和模型，配置变更、重试次数和使用版本均可核对。没有完整流程证据时保持待验收；若证据指向尚未解决的外部依赖，记录具体阻塞，不以别的服务成功代替。

用户最新明确继续使用 `provider.md` 指定模型和专用测试密钥。当前先完成该服务下的真实 Web、小窗压缩和最终 QA，三部门仍显式通过统一目录绑定；第二套服务不再作为启动此次验收的等待条件。本地多连接验证、单服务真实验证及后续真实跨服务验证分别记录，不混为同一种证据。服务商最大能力未公布时，本次试验显式登记并验证运行限制，不将其冒称标称能力或加入隐式运行默认。

第一项内部继续完成连接恢复与审查，并独立接入 D18 的目录、部门绑定、调用归属和只读观察。Provider 配置与绑定选择界面按用户补充预留，等对应原型再细化；底层验收使用明确的宿主配置。选定跨 Provider 验收配置后，完整真实验收覆盖新基线；此前单 Provider 的结果分别保留。OMP 的 Provider/角色绑定源码核对属于本项设计依据，第三项仍负责更广的系统审查。

## 4. OMP 审查的范围与方法

审查回答“哪些已验证的机制能改善 Yudao 当前原生内核”，不把 OMP 全套运行时重新引入项目。

| 机制 | 重点核对 | 对 Yudao 的适用问题 |
| --- | --- | --- |
| Provider 与流式协议 | 统一目录、角色与模型绑定、多协议适配、连接、错误分类、终态和用量来源 | 部门独立使用 Provider，准确区分提供方与应用失败，可靠处理部分响应 |
| 历史与上下文压缩 | 原始历史、摘要范围、近期回合、容量估计、摘要失效与继续执行 | 同部门工作是否连续，摘要能否追源，实际请求是否完整 |
| 工具与循环 | 调用/结果配对、取消、失败、中间状态和接续 | 不重复执行工具，不接纳失效结果，不绕过部门与合同责任 |
| 观察与交互 | 事件、trace、状态、等待及错误呈现 | 用户能否区分准备、发出、部分返回、完成、失败与重试 |
| Prompt 与专业基础 | 指令结构、规则来源、工具说明和任务材料分层 | 哪些写法改善清晰度，哪些依赖 OMP 特有机制而不适用 |

固定所审查的源码版本，先整理模块与实际调用链，再按上述问题阅读对应路径。结论分为已有等价能力、值得采用的机制及不适用项。先核对项目已有库的能力，再决定最小改动；每个采用项单独验证、提交、推送。文章摘要或产品名不能代替源码依据。

## 5. Context/Trace 的核心使用过程

研发者选中一次部门工作，看到该次采用的原始意图、有效合同与计划、Prompt 版本、本部门历史视图、压缩摘要与来源、工具定义。继续沿时间线查看实际模型尝试、流式输出、工具结果、交接和停止原因。

每次请求同时显示当时部门绑定、Provider 配置身份、协议、请求模型和实际返回模型，以及有效上下文容量。配置来源来自任务快照；失败时没有返回模型就保持未知，不从当前系统配置或其他成功调用回填。

一条逻辑请求的多个尝试放在一起，明确区分已准备、已发送、部分返回、失败、退避及完整成功。失败输出保留为证据，不显示成有效部门历史；调用次数来自实际请求事实，不从准备记录或步骤编号推算。

“实际输入”必须来自当次保存的输入工件；装配清单、摘要及展示都是它的说明，不能根据当前状态临时拼出一份看起来合理的历史输入。Prompt 编辑显示作用范围、待生效和实际采用版本。

视图只查询事实，用户命令仍交给现有内核。支持从摘要和错误回到来源、查版本差异、固定时点回看和完整导出；不展示凭据，不把内部不可见推理当作可获取内容。任务切换、断线和迟到响应不会混用不同任务的数据。

整体布局现以已完成的工作台与观测原型为准，按 [D19](requirements/web-workspace-prototype.md) 和 [D21](requirements/request-observability.md) 实施；复用当前 Web、事件、输入审计和工件查询，不建设另一套事实来源或独立管理后台。部门定向指导作为 [D20](requirements/department-guidance.md) 单独设计，Provider 等配置区域仍预留。

| --- | --- | --- |

| 2.3 跨任务经验 | 候选、验证、适用检索、采用与失效贯通 | 可信来源、独立评价及实际使用边界 |
| 2.E 原生项目演化 | 同一项目跨任务增量开发、合法改方向、成果采纳及新会话接续 | 稳定原生内核、完整代码基线和项目采纳合同；不依赖先证明学习收益 |
| 2.4 综合比较 | 分别比较基础、仅控制、仅经验和组合方案 | 冻结控制与经验版本、独立未见任务与完整成本 |

2.E 区分项目、一次变更和执行 run，也区分目标改变、QA 通过、项目采用与外部发布。来源材料提出的“三次变更文本 CLI”可以作为未来设计案例，目前不开始实现。

领域知识支持日常专业补全；新学习经验仍须验证。项目知识按需提供，不能用后续检索设计替代当前同任务部门完整历史及有来源的压缩要求。运行限制沿用最新确认，不自行恢复任务 token 预算。
