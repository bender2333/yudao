## 2. 每项交付与完成条件

| 顺序 | 解决的问题 | 应交付的结果 | 完成依据 |
| --- | --- | --- | --- |
| 1 Provider 连接 | 间歇连接中断阻止长流程完成，正常等待和故障处理需要可靠 | 能定位失败发生在哪一层的诊断、有界恢复、明确的永久失败与取消处理、完整尝试记录 | 慢响应、瞬时失败后继续、重试耗尽、取消及新输入处理经过验证；真实当前 provider 能支持后续完整流程。增加等待或一次探针成功不单独算解决 |
| 2 第一阶段真实验收 | 局部成功尚未覆盖实际用户的完整操作 | 冻结版本的真实 Web 与小窗压缩流程、最终 QA、交付及输入来源审计 | 持续输入形成新要求和计划，真实交付按最终合同通过独立 QA；压缩后继续到最终交付；Git、封存、事件及实际输入互相对应。失败样例保留 |
| 3 OMP 系统审查 | 原生运行时需要系统吸收成熟实现的经验 | 固定版本的源码审查、机制对照、借鉴/不采用理由及独立的小改进清单 | 每项判断可追到实际源码；选中的必要改进完成独立验证，其他研究项明确归档，不留下不清楚的待处理清单 |
| 4 Context/Trace View | 研发者需要看清每次请求实际读到什么、发生了什么、为什么接续或停止 | 按任务、部门、激活和步骤查看真实输入来源、历史/摘要、调用尝试、工具、交接和错误 | 能从一次失败、重试或压缩回到实际输入及对应输出；实时、历史回看、切换任务与导出一致，无假完成或失效来源冒充当前输入 |
| 5 Web 完善 | 完整操作流程和可扫描、可理解的界面 | 按用户原型完成任务输入、状态、材料/差异、Prompt 和观察入口的产品流程 | 桌面与移动端真实交互验收，包括等待、失败、重连、取消、历史回看与长文本；原型未到时不自行确定新布局并宣布完成 |
| 6 Prompt 优化 | 提高需求、计划、专家协作与 QA 的任务质量 | 有版本、与部门职责一致的 Prompt 改进及效果比较 | 使用固定任务和评价方法核对意图保持、要求覆盖、计划执行、协作、回归与错误放行，同时记录成本；不能只用模型自评或一条成功案例证明改善 |

主实施顺序遵循 1-6。资料整理、验收案例准备可以在不占用最高优先级关键资源的前提下进行；不会因此启动大功能。Web 等待原型的状态明确保留，不能把等待当作默认批准某个新设计。

## 3. 第一优先级的当前事实

以本轮读取的 [D17](requirements/provider-retries.md)、[原生设计](native-loop-design.md)和[验收记录](mvp-acceptance.md)为准：

- 当前使用原生三部门内核和官方 Responses SDK，OMP 是参考，不是运行依赖。
- 已记录的主要故障是约数秒后出现的 TLS EOF/连接中断；同配置也有成功响应。不能把它误记为正常一分钟响应触发超时，也不能据此确定是模型配置、远端或本机哪一方的根因。
- D17 要求允许足够的单次等待，由内核安排最多 3 次尝试，实际尝试占用既有步骤；取消和新输入仍优先，失败的部分输出不进入有效历史或工具执行。这是待实现及验收的目标行为。
- H 批次的 Provider 重试仍有未提交实现。本任务只导入资料并安排后续设计，不把这批在途实现一并提交，也不另开一套重试运行器。

近期应在当前 H 实现上完成独立审查和故障复现，区分网络、适配、流式协议及内核行为。重试是恢复措施，诊断仍需保留原始失败与实际等待。认证、额度及不可恢复协议错误不靠反复请求掩盖。

真实验收要使用用户当前指定的 provider 和模型，配置变更、重试次数和使用版本均可核对。没有完整流程证据时保持待验收；若证据指向尚未解决的外部依赖，记录具体阻塞，不以别的服务成功代替。

## 4. OMP 审查的范围与方法

审查回答“哪些已验证的机制能改善 Yudao 当前原生内核”，不把 OMP 全套运行时重新引入项目。

| 机制 | 重点核对 | 对 Yudao 的适用问题 |
| --- | --- | --- |
| Provider 与流式协议 | 连接、超时、错误分类、断流、终态、协议保真和用量来源 | 提供方失败与应用失败能否准确区分，部分响应能否可靠处理 |
| 历史与上下文压缩 | 原始历史、摘要范围、近期回合、容量估计、摘要失效与继续执行 | 同部门工作是否连续，摘要能否追源，实际请求是否完整 |
| 工具与循环 | 调用/结果配对、取消、失败、中间状态和接续 | 不重复执行工具，不接纳失效结果，不绕过部门与合同责任 |
| 观察与交互 | 事件、trace、状态、等待及错误呈现 | 用户能否区分准备、发出、部分返回、完成、失败与重试 |
| Prompt 与专业基础 | 指令结构、规则来源、工具说明和任务材料分层 | 哪些写法改善清晰度，哪些依赖 OMP 特有机制而不适用 |

固定所审查的源码版本，先整理模块与实际调用链，再按上述问题阅读对应路径。结论分为已有等价能力、值得采用的机制及不适用项。先核对项目已有库的能力，再决定最小改动；每个采用项单独验证、提交、推送。文章摘要或产品名不能代替源码依据。

## 5. Context/Trace 的核心使用过程

研发者选中一次部门工作，看到该次采用的原始意图、有效合同与计划、Prompt 版本、本部门历史视图、压缩摘要与来源、工具定义。继续沿时间线查看实际模型尝试、流式输出、工具结果、交接和停止原因。

一条逻辑请求的多个尝试放在一起，明确区分已准备、已发送、部分返回、失败、退避及完整成功。失败输出保留为证据，不显示成有效部门历史；调用次数来自实际请求事实，不从准备记录或步骤编号推算。

“实际输入”必须来自当次保存的输入工件；装配清单、摘要及展示都是它的说明，不能根据当前状态临时拼出一份看起来合理的历史输入。Prompt 编辑显示作用范围、待生效和实际采用版本。

视图只查询事实，用户命令仍交给现有内核。支持从摘要和错误回到来源、查版本差异、固定时点回看和完整导出；不展示凭据，不把内部不可见推理当作可获取内容。任务切换、断线和迟到响应不会混用不同任务的数据。

这里先确定需要表达的事实与操作，具体整体布局随第 5 项原型对齐；复用当前 Web、事件、输入审计和工件查询，不建设另一套事实来源或独立管理后台。
