# 第二阶段 Prompt 改善与验证

日期：2026-09-07。对应 [第二阶段计划](stage-2-plan.md) 的第 6 项。本文准备实施与比较方法；当前真实 Provider 验收仍使用原 Prompt，尚未替换默认内容，也没有得出质量提升结论。

## 依据与边界

现有 `department_prompts.py` 保存三部门默认规则，创建任务时形成原文工件与版本；每次激活固定所用版本。`ContextAssembler` 分开用户原文、当前工作、规则、合同、计划、历史及工具定义。代码负责权限、接纳和 QA 放行，Prompt 负责让模型准确理解和使用这些约束。

采用 [OMP 固定版本审查](research/omp-stage2-system-review.md) 中的来源分段与工作顺序原则。规则只有出现完整重复段落时才做精确去重，不做语义相似删除，不增加通用 Prompt 引擎或新的配置层。Context/Trace 和已有原型 Web 的必需行为先完成，再实施本项应用变更。

## 已观察到的问题

以下材料已经公开给开发过程，不能再作为未见验证样本：

| 来源 | 实际事实 | 候选改善方向 |
| --- | --- | --- |
| `run_8b6983a76419465e`，seq70 | 更换合同后的新计划缺少变更理由，被主机拒收 | 明确本任务已有历史计划时，新计划需要说明变化，即使旧计划已失效 |
| 同一 run，seq81 | 在新计划未接纳时尝试写文件，被主机阻止 | 根据实际接纳回执继续工作，被拒后先处理反馈 |
| 同一 run，seq92 | 调整计划引用旧有效合同，被主机拒收 | 区分历史依据和当前绑定，引用当次输入提供的有效合同身份 |

这些事实支持设计一个有针对性的候选，不证明单纯改 Prompt 已足以解决问题。失败请求、压缩、网络异常和被主机拒绝的工具也需要保留成本，不能只比较最终成功部分。

## 三层职责

| 层次 | 要交付的结果 | 验证方式 |
| --- | --- | --- |
| 部门说明 | 以职责、有效依据、工作顺序和提交结果组织简洁规则 | 核对实际源码规则，不创造不存在的工具、身份或权限 |
| 输入与版本 | 原文、版本、hash、下次激活生效关系及实际请求可核对 | 复用 Context/Trace 与 Prompt 版本测试；当前调用不被保存动作改写 |
| 独立比较 | 固定基线与候选在登记任务上的结果及成本 | 相同执行限制、公开要求和外部主机检查，保留所有任务及失败 |

产品继续负责完整目标和合法变更；工程继续先形成有效计划，再修改、检查并交付；质检继续独立核对完整有效合同和受测交付。不能用压缩后的历史决定覆盖当前合同，也不能把模型自述当作主机接纳。

## 比较安排

1. Web 联调结束后固定应用提交、三部门基线 Prompt hash、Provider/模型目录与实际返回模型、运行限制及工具集合。
2. 使用上述已公开运行及独立的公开校准材料编写一个候选。校准覆盖要求变更、计划被拒后的纠正、专业协作和 QA 返工，先检查说明是否准确反映运行合同。
3. 候选内容和评价方法固定后，再登记确认任务。确认材料与候选开发材料分开，具有完整公开要求；保留检查输入只能验证公开规则，不能增加隐藏业务要求。
4. 同一任务的基线与候选使用独立工作区和原始起点，按任务交替执行先后顺序。网络与服务限制保持一致，不替换模型或对其中一组额外重试。
5. 对封存后的实际交付运行固定主机检查，逐任务比较质量、错误放行、无效提交与成本。工程自检、Yudao 内部 QA、外部复核分开记录。
6. 根据登记结果决定采用、缩小范围或保留原版本。查看正式结果后发生的 Prompt 修改属于下一版，需要新的确认材料。

任务族至少覆盖带方向变更的文本处理、结构化数据处理、需专家澄清的要求，以及有公开回归检查的修复。具体任务登记与数量依据校准结果形成，在正式执行前冻结。当前不填没有观测依据的样本量、提升幅度或统计显著性承诺。

## 结果口径

| 指标 | 依据 | 不能替代它的内容 |
| --- | --- | --- |
| 意图与要求保持 | 原文、完整有效合同、合法改变与保留内容、独立检查 | 模型对自己的评分 |
| 计划合规 | `plan_accepted`、拒收原因、实际文件及工具回执 | 计划写得更长或使用更多术语 |
| 纠正与重复错误 | 同条件下的拒收、纠正和后续复发轨迹 | 只统计最后一轮 |
| 协作正确性 | 实际请求、回应、职责内接纳及返回工作 | 自然语言说已经咨询或完成 |
| 交付与错误放行 | QA 受审绑定、独立恢复的完整交付、外部反例 | 自检通过或 QA 的自然语言结论 |
| 成本与可靠性 | 每次实际模型请求、输入含缓存口径、输出、工具和经过时间 | 准备记录数、成功子集或把缺失费用填零 |

同一任务内的多轮尝试不充当多个独立样本。基础流程已经包含正常专业知识，不能刻意削弱对照。样本不足时展示逐任务事实和限制，不把没有发现回归写成已经证明没有回归。

## 交付与提交

实施者提交一份与真实工具和合同一致的候选、版本与适用范围说明，以及独立比较报告。应用变更只覆盖部门说明和实际发现的必要精确去重；评价脚本复用现有目录、封存、主机检查和观测接口。

主代理负责固定比较约定、独立审查及采用结论，子代理负责候选与测试实现。默认 Prompt 仅在比较支持采用后更新并独立提交；不因本项需要比较就提前建设 2.1 的正式学习管线。完整成本和未解决项保留在第二阶段进度中。
