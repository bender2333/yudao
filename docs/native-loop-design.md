# 原生三部门循环设计

## 目标与授权

用户于 2026-09-06 明确要求重构：三部门构成 Agent loop 本身，目的是让未来上下文的选择粒度、组装时机和策略由 Yudao 控制。OMP 仅作代码级参考，例如 provider 封装、流式协议和工具结果处理，不作为运行依赖。

用户随后确定 Web 持续输入、部门 prompt 展示与编辑、原文 `intend.md`、产品 `PRD.md` 及研发先计划后实施。完整需求与待决交互见 [已确认需求清单](confirmed-requirements.md)；这些能力依赖本轮的逐次上下文所有权，不能仅凭重构完成就声称已经实现。

此前 MVP 验收证明外层三部门编排能够完成任务。本轮改造循环执行边界，需要重新验证真实任务；此前验收不能替代本轮结果。

## 三层职责

| 层次 | 职责 | 边界 |
| --- | --- | --- |
| 任务与观察 | Web 命令、进度、合同、证据、上下文与用量展示 | 创建和取消交给内核；查询来自事件和投影 |
| 三部门循环内核 | 部门职责、当前合同、逐步上下文装配、工具调度、交接、预算和停止 | 产品、工程、质检分别保有上下文边界；模型输出经过普通代码校验 |
| 基础执行 | 单次模型请求、流式解析、错误与取消；受限的文件和检查工具 | 模型适配器不执行工具、不访问工作区、不选择部门、不管理对话历史 |

状态机与调用驱动在同一内核中各有职责：前者校验并提交权威状态，后者安排模型和工具执行。网络请求不占用状态提交临界区。

## 循环推进

1. 依据当前状态选择产品、工程或质检，建立本次部门激活。
2. 每次模型请求前装配 intend 原文、当前工作、有效要求、同部门完整历史和工具定义，检查上下文容量及循环次数。
3. 基础适配器完成一次模型响应，将内容、工具请求和实际用量返回内核。
4. 内核执行允许的工具并保存结果；需要继续时，由上下文装配器重新构造下一次请求。
5. 部门提交形成后立即交还合同校验和状态机，决定继续修正、交接或停止；不等待另一个 Agent 运行时宣布结束。

部门可以连续进行多个工具步骤，不要求每个工具后轮换三部门。自然语言中的完成声明没有完成权；没有提交的重复响应受明确的步骤与循环次数约束。provider 用量不参与任务停止判定，单次调用仍有超时。

## 上下文所有权

- 当前有效要求与产品决定、交付有效性、返工依据仍由投影决定。
- 每步输入先呈现 intend 原文和当前工作，再结合有效合同与本部门完整历史。模型适配器接收已经装配好的完整输入，不追加隐式系统提示。
- 同一任务内按部门保存完整模型输出和工具结果，跨激活继续使用；工具调用和结果关系必须完整。其他部门不能取得该部门完整私有历史。
- 请求中的推理协议项和工具关联信息需要保真，不能通过丢弃必要项使下一次调用失效。保存协议项不等于取得模型不可见的内部推理。
- 当前版本不遗忘本部门历史、不自动摘要或截断；待语义分解、洞见和数据流形成后，再优化上下文管理。长期记忆检索不在本轮增加。
- 上下文容量检查覆盖完整请求的指令、部门历史与工具定义，并在每次请求前执行；超限明确停止。provider 实际用量只作可选观测，不形成任务 token 预算。
- 每次请求保存可核对的内容工件、来源、摘要及 run、department、activation、step 的绑定。密钥、认证头不属于上下文工件。

## 基础能力的选择

现有 Python 项目没有模型 SDK 依赖。使用官方 OpenAI Python SDK 连接已经验证可用的 Responses provider，借用 SDK 的请求、流式协议解析和取消能力，不再经 OMP RPC。

Provider 每次只处理一个响应。请求显式提供完整输入，关闭服务端持久会话和 SDK 自动重试，不通过 previous_response_id 等远端状态继续对话。连接失败明确失败，不自动切换 provider 或使用 fake。

Fake 与真实 provider 使用相同的单次响应边界。Fake 只能生成模型输出及工具请求；文件修改、检查与证据仍由同一个内核和宿主工具执行。

OMP 源码只读参考。本轮删除 Yudao 中的 OMP 进程启动、RPC、自动发现隔离配置和旧入口，不保留兼容适配器或旧环境变量回退。旧运行证据保留为历史事实，不将其标注为原生循环的验收证据。

## 必须保持的能力

三部门合同、Ask/React、独立质检和回执绑定、交付失效、停止记录、经验候选、事件与工件、重放和 Web 命令保持有效。取消与预算停止后不接受迟到提交，不继续下一次模型或工具调用；已经完成的响应、检查和用量保留供审计。

检查仍在可丢弃工作副本中执行。该机制不是操作系统沙箱。当前运行不增加长期记忆、暂停恢复、额外部门或分布式服务。

## 实施与验收

1. 原生内核与 fake 跑通直达、Ask/React 和返工；证明提交即可交接、工具由宿主执行，以及上下文确实每步重建。
2. Responses 适配器通过本地请求捕获验证：指令与输入符合装配记录、工具往返完整、无远端会话、用量不重复、静默连接可取消。
3. CLI、Web、查询与导出接入原生循环；检查每步上下文可以从界面和事件回查。
4. 独立复测取消交错、预算耗尽、上下文增长、检查证据、合同失效与经验候选，不以删除旧适配器为理由丢失行为覆盖。
5. 使用既有主 provider 跑新的直达与 Ask/React，核对真实交付、工程与质检回执、实际请求与事件重放；浏览器验证创建、实时观察和取消。

每个可验证的工作包单独提交和推送。Codex 负责设计、审查与验收，应用代码由实现子 agent 完成。
