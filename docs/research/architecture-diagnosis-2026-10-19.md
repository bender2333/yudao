# 架构与需求诊断：M0 以后先把投入放在哪里

日期：2026-10-19 至 2026-10-20。诊断的提交：main `909deda6`（结构、演化与追溯）；评测运行见第 2.1 节，Yudao 的 3 次读数分属 `909deda6` 与 `ffb099c7` 两个提交。第 9 节的提议由用户确认以前不执行。

## 0. 决定与结论

这次诊断只服务一个决定：M0 完成以后、M2 开始之前，先把投入放在哪一处，才能最快让 Yudao 进入可迭代状态（`CLAUDE.md` 第 49 至 56 行的五条判据），并拿到「三部门交付质量高于单个 agent」的第一个可信读数。

结论：**先投在评测这一处，让场景 3 的 Yudao 对 OpenCode 在对等的条件下、在质检能给出结论的时间里跑出来；M2 的恢复与建档排在它后面。**

依据是今天的读数（第 2 节）：

- 同一个模型（`qhub/Qwen3.8-Flash`）上，Yudao 工程部门一个部门交出的东西已经和单个 agent 在同一水平：完成度 0.857、0.841、0.841，OpenCode 是 0.841、0.841、0.530。
- 三部门能比单个 agent 多出来的，只能来自质检：发现问题、退回、工程修好。这一段在 90 分钟里一次也没有走到：Yudao 在第 70、80、75 分钟交付，质检只剩 10 到 20 分钟，三次都没有给出结论，也没有运行过一次检查。到今天为止，场景 3 上 Yudao 的 7 次真实运行（10-06 的 3 次、今天原样的 1 次、带数据的 3 次）没有一次走到质检的结论。
- 所以「高于」这个假设现在**没有读数**，不是读数为负。要拿到它，缺的是让循环在评测窗口里走完一圈，以及一把对等、能分辨「高于」的尺子。
- 第二条目的（长时间自己运行）在今天的运行里已经够用：2 次单次请求超时、2 次连接失败，都没有等人，自己恢复了。M2 的恢复与建档服务的正是这一条，可以往后排。

先做的事，按顺序（都写成了提议，第 9 节）：

1. 现在就能做，只改 `evals/`，和 M0 的核心工单不冲突：放出 #324 并加上几处运行器修复；把场景 3 的对照从 #198 拆出来（发现 1）。
2. 在 M0 完成的那个提交上，按今天带数据文件的条件重跑 3 + 3，作为 M0 前后的第一次版本比较；M0 的 #557（质检在交付之前按 PRD 起草测试）能不能让质检在窗口里给出结论，用这次读数回答（发现 2，预测 P2）。
3. 由你定两件事：「高于」怎样判；评测的时间上限要不要从 90 分钟改到 Yudao 默认的 120 分钟（发现 3、发现 2）。
4. 第一次参数对照之前，把 9 个读初值的参数接到现值上（发现 4）。

## 2. 核心假设的读数

### 2.1 怎样跑的

- 场景 3（材料 `scenario-3@2`，评分器 `scorer-3@2`），被测模型 `qhub/Qwen3.8-Flash`，经 9router；两边同一个模型，Yudao 三个部门都绑定它。准入记录里服务方报告的模型名是 `auto`。每次 90 分钟上限（运行器的值，属于评价标准，只由用户修改）。
- 事先告诉用户：每边 3 次，最坏约 4.5 小时；用户选择两边同时运行。实际经过：

### 2.4 读数说明了什么

- 工程交付这一段：Yudao 0.857、0.841、0.841，OpenCode 0.841、0.841、0.530。配对随机化检验在这 6 个数上的单侧 p 值是 6/20 = 0.30，分辨不出高低。可以说的只有两点：Yudao 三次都不低于 OpenCode 最好的一次；Yudao 没有出现 OpenCode 第 3 次那种「没做完就停」，它的交付要先经过主机运行的检查，这是结构上的差别。
- 三部门多出来的那一段（质检）没有读数。
- 代价：Yudao 用时约 3 倍，用量 1.2 到 3.7 倍。基础规则第 5 条说成本是目标的一部分，这一项现在对 Yudao 不利。

「模块→层」映射取自[总体架构](../design/architecture/overall-architecture.md)第 2、5、6.1 节与内核清单 `harness/definitions/kernel-manifest.json` 的 `paths`：定义（`definitions`）、可信内核（清单里 13 个模块）、执行层（`environment`、`providers`）、P（`assembly`、`context`、`compaction`）、步骤驱动（`engine`、`recording`）、流程编排（`orchestrator`）、应用层（`app`）、接口层（`api`）、命令行（`__main__`）。依赖方向按第 5 节：层号小的不导入层号大的，内核只导入内核。

| 结果 | 条数 | 内容 |
| --- | --- | --- |
| 一致 | 93 | 已归属模块之间的依赖全部符合第 5 节 |
| 多出 | 0 | 没有向上的导入，内核没有导入内核以外的模块 |

## 7. 发现（按对这次决定的影响排序）

### 发现 1：评测工具让两边的条件不同，读数先量到的是工具的缺口

现象：
- Yudao 一侧的工作区没有题目的数据文件，事项文字要求工程「按接口约定自己写出这份文件」（`evals/runner/yudao.py:93-97`），OpenCode 一侧拿到了真实文件（附件）。原样的那一次 72 分钟没有交付，58% 的时间花在编数据与两次请求时限上（第 2.3 节）。
- OpenCode 一侧的运行器遇到被测模型留下的 `nul` 文件就中止整组（`run_eval.py:90`）。
- Yudao 的单次输出上限是 8192（`yudao.py:37`），OpenCode 用模型的默认值；本次 OpenCode 单步最多输出 15165 个 token。
- Yudao 的运行器在全部运行结束时才读一次提交号（`run_yudao_eval.py:209`），工作区中途被切换时，报告里的提交号就错了（第 2.1 节第 4 条）。
- 让 Yudao 带上数据文件的 #324，后端（#321）10-07 就已合并；运行器这边从 10-06 起被推迟 4 次：10-08 加了对 #194 的依赖，10-13 加了对 #486 的依赖，10-16 因为派发机器没有评测变量改为 `needs-triage`、同时排到 M0 之后，10-19 改为 `waiting`（工单时间线）。
- 第一份 Yudao 对 OpenCode 的对照报告 #198 把场景 2、3 绑在一张工单上，被 #195（场景 2 要先建档，M2）阻塞。

原因链：工单写法与排序。测量工具的修复被当作「评测工作线」的一部分，跟着里程碑排；设计里「两边同一份输入」（评测场景设计第 3 节「输入」「隔离」两行）没有对应的运行器检查，起点不同只写进报告的说明，不让这次运行作废。

对照案例：同一个模型、同一套运行器，只把数据文件带进去，带数据的 3 次都在第 70 到 80 分钟交付，完成度 0.841 到 0.857；原样的那次到第 72 分钟还没有交付。

可以被推翻的预测（P1）：#324 与这几处运行器修复不在 M0 完成之前合并，M0 完成时的读数里，Yudao 的工程在 3 次中至少 2 次又自己写地铁数据，这些步骤占到工程时间的 20% 以上。检验：交付里有没有自写的数据文件，相关步骤的用时。

最小的处理：#324 照原文放出（运行器经 `initial_directory` 带入数据文件，删去事项文字里的那一段），同一张工单加三项：复制交付时跳过 Windows 保留名；Yudao 的输出上限取模型访问定义的值并写进报告；每次运行在服务启动时记下提交号。把场景 3 的对照从 #198 拆出来，不等建档。这些只改 `evals/`，现在就能做。不处理的代价：每一次读数都要人工判断「这次差在哪」，第二条判据（能度量）一直不成立。

### 发现 2：三部门的循环在评测的时间上限里走不完一圈，质检的作用从来没有被量到

现象：带数据的 3 次，交付在第 70.1、80.4、75.2 分钟，质检剩 20、10、15 分钟，三次都被时间上限结束，没有结论，没有运行过检查（第 2.3 节）。Yudao 交付以前的模型调用是 OpenCode 全程步数的 4 到 6 倍。质检写测试的方式也慢：它没有 `write_file`，经 `bash` 的 heredoc 写，start-1 约 4 分钟花在修被转义弄断的行上。

原因链：设计、执行环境与评价标准三层。
- 设计：现在的 main 上三个部门依次工作，质检在交付到达以后才开始准备测试。M0 还没有合并的 #474 与从它拆出的 #557（三个部门同时运行；PRD 被接纳以后质检就按 PRD 起草测试用例）针对的正是这一点，效果还没有测过。
- 执行环境：同一个模型，Yudao 的工程拆成很多小步，每次请求都带着部门历史与 PRD；在一个慢模型上，次数直接变成时间。
- 评价标准：90 分钟是运行器的上限，Yudao 自己的默认运行上限是 120 分钟，评测设计第 3 节写明「不为评测调整」。

对照案例：smoke 的 happy 场景（`harness/smoke.py:55-61`，echo 程序）用真实模型走完产品、工程、质检并放行，10-18 在 `6d23c555` 上 101 秒通过。循环结构本身能走完，走不完的是中等大小的任务。

可以被推翻的预测（P2）：只合并 M0、不处理质检的写文件方式与单次请求的步数，M0 完成时在同样条件下（带数据文件、同一模型、90 分钟）再跑 3 次，至多 1 次在上限以内出现质检结论（`qa_submitted`）。检验：3 次中出现 `qa_submitted` 的次数。今天是 0 / 3。

最小的处理：M0 完成时，在完成的那个提交上按今天的条件重跑一次，作为 M0 前后的第一次版本比较；读数分开报告「工程交付的完成度」与「质检是否在上限以内给出结论、结论与评分器是否一致」。质检的写文件工具与时间上限是要你决定的两项提议（第 9 节）。不处理的代价：「高于单个 agent」这个目的的唯一证据来源，一直停在工程交付这一段。

### 发现 3：「高于」在需求里变成了「不低于」，现在的次数也分辨不出「高于」

现象：用户原话是「质量高于直接使用单个 agent」（`system-intent.md:25`），需求 N-G1 写成「不低于单独运行的 agent」，验收是「判定为不劣于 OpenCode」（`system-intent.md:129`），`CLAUDE.md:46` 仍写「高于」。规则与参数第 4 节的主要指标是质检误放行，规则是不劣于、余量 0；OpenCode 没有质检，这个指标对它没有意义。Yudao 对 OpenCode 的比较没有代码。今天的 6 个数上，配对随机化检验的单侧 p 值是 0.30（第 2.4 节）；一个场景、每边 3 次，只有 Yudao 3 次全部高于 OpenCode 3 次才能到 0.05（20 种排列里的 1 种），而 OpenCode 自己 3 次之间就差 0.31。按 N-G1 现在的写法，今天的读数已经算「不劣于」；按用户的原话，回答不了。

原因链：需求层。校准时把「目的」改写成了能验收的门槛，「不劣于」容易验收，却回答不了「是否高于」；对照规则只为版本对版本写了，Yudao 对单个 agent 的比较方法没有写。

对照案例：待定。

可以被推翻的预测（P3）：不改写判定，M2 试用（#184）时 Yudao 对 OpenCode 的对照报告给出「无差别」或「受阻」，不给出「高于」。检验：#198（或拆出的场景 3 那张）报告的结论字段。

最小的处理：由你定「高于」怎样判（第 9 节给了三种写法），写回 N-G1 与评测场景设计；在那之前，报告把两边的逐次完成度并排列出，不下「高于」的结论。不处理的代价：做完 M2 也拿不到你要的那个读数，只能拿到「不比它差」。

### 发现 4：参数能改的范围比写的窄，「改动便宜」只对 4 个限额成立

现象：规则登记 66 条，`parameter.set` 接受其中 57 个参数并写事件。运行时跟随现值的只有 `max_cycles`、`run_time_limit_sec`（`projects.py:380-387`）、`check_timeout_sec`（`orchestrator.py:272`）与 `onboarding.round_time_limit_sec`。`tool_call_required_limit`、`max_model_steps`、三个重试参数、两个 bash 时限、`check_timeout_max_sec` 与 `tool_output_limit` 由 `DEFINITIONS.rule_value` 读定义文件里的初值（`engine.py:90-98`；`definitions/__init__.py:400-402` 的注释写「现值」，读的是文件值）。另外 44 个参数代码不读，其中三条 `roles.*.visibility` 正是 N-T3 验收里举的「角色的可见范围」：`context.py:90` 从 `roles.json` 读，改参数不生效。

原因链：代码层。迭代底座 B3 把登记、界限、事件与查询做完了，只把建 run 时冻结的几个限额接到了现值上；其余条目的读取没有改。

对照案例：`max_cycles` 与 `run_time_limit_sec` 经 `projects._limit_values` 读现值，建 run 时冻结，修改以后的新事项按新值运行，这条路是通的。

可以被推翻的预测（P4）：对 9 个读初值的参数中任何一个做第一次对照，新事项的行为不变；例如把 `tool_call_required_limit` 从 3 改为 1，模型仍要连续 3 次不调用工具才暂停。检验：暂停之前连续不调用工具的次数。

最小的处理：9 个读初值的参数改为读建 run 时冻结的参数版本；`rules.registry` 的结果标出哪些条目接入了运行，没接入的不接受 `parameter.set`。不处理的代价：拿评测做的第一批对照（可见范围、质检重新检查的比例、上限以外的边界）都得改代码，「改一处、跑一次、留或撤」只对 4 个数成立。

### 发现 5：单次请求的时限按整段回复的累计时间算，模型还在输出也会被切断重来

现象：原样那次的事件 #39、#59 各在 600 秒时以 `provider_timeout` 失败，重试从头开始。原样重放事件 #56 的请求：模型服务连续输出 583 秒（21476 行流数据，相邻两段最多间隔 3 秒），正常结束。时限的走法写在 `providers/responses.py:123-126`：读取回复体的每一段都计时，累计到时限就超时；默认 600 秒（`providers/store.py:24`）。D09 的用户原话是「尽可能放开限制，确定收敛即可」（`execution-limits.md:7`）。

原因链：设计层。「一定会停」已经由运行时间上限保证，单次请求的时限再按总时长算，挡住的其实是「回复太长」。

对照案例：带数据的 3 次没有一次超时：工程不再一次写出整份数据文件，单次回复都短。用普通的流读取重放同一个请求，583 秒正常结束：模型服务本身没有问题。

可以被推翻的预测（P5）：M0 以后同样条件的读数里，每一次 `provider_timeout` 的请求按原样重放都能不中断地正常结束（相邻两段间隔小于 30 秒）；如果重放出现长时间没有数据，说明是模型服务停住，这条归因就错了。检验：重放的总时长与最大间隔。

最小的处理：单次请求的时限改为「多久没有收到新数据」，总时长交给运行时间上限。这是设计修改，写成提议（第 9 节）。不处理的代价：在慢模型与大文件上，每次多花 10 分钟，而且重试不保证这次回复会短一些。

诊断完成以后，派了一个只读的 gemini 子任务（omp，`9router/gemini`，2026-10-20 13:54 至 14:08 本地时间），在单独检出 `909deda6` 的工作区里运行，只给原始材料、方法与运行条件，不给本报告的结论。任务说明在 [gemini-prompt.md](architecture-diagnosis-2026-10-19/gemini-prompt.md)，它的报告原文在 [gemini-independent.md](architecture-diagnosis-2026-10-19/gemini-independent.md)。运行中只有读取与 `gh issue view`，工作区没有改动。

两边的前三条：

| 名次 | 本报告 | gemini |
| --- | --- | --- |
| 1 | 评测条件不对等，读数先量到工具的缺口 | 质检没有验证的脚手架，循环走不到放行 |
| 2 | 循环在评测窗口里走不完一圈，质检的作用没有被量到 | 工程步数膨胀、上下文累积，吃掉八成时间 |
| 3 | 「高于」变成了「不低于」，现在的次数分辨不出「高于」 | 编排器过大、高频共变，妨碍规则与参数的演化 |

一致的地方：两边都认为读数的关键是三部门在 90 分钟里走不到质检的结论；gemini 的第 1、2 条是本报告第 2 条的两半（质检一段与工程一段）。两边的结论相同：M0 以后先投在循环走完一圈与评测上，M2 的建档与远程执行往后排。

不一致的地方：

1. 起点缺口的位置。gemini 把它排第 4，并写成 Yudao 产品的缺口：「`initial_directory` 是私有参数」「被测系统无法通过公开标准 API 接纳初始数据文件」「D37 没有实现」。这一点核对下来不成立：`initial_directory` 在 `project.create` 的公开合同里（`harness/app/project_commands.py:26-31`，#321，10-07 合并），缺口在运行器（#324）。gemini 也没有提到 `nul`、输出上限与提交号这几处运行器问题。本报告保持第 1 条。
2. 「高于」的判法。gemini 没有指出需求里「高于」变成了「不低于」，也没有算次数够不够；它写「只要循环跑通……就能立即拿到具有统计显著性的读数」。按配对随机化检验，每边 3 次时，只有 Yudao 3 次全部高于 OpenCode 3 次才能到单侧 0.05；今天只算工程交付是 0.30。本报告保持第 3 条。
3. 处理办法。gemini 建议给质检设「最多 8 步」、给工程设「最多 30 到 40 步」的硬上限，并限制质检只写单个脚本。本报告不采纳：用户的约束是「尽可能放开限制，确定收敛即可」（`execution-limits.md:7`）与「不能为了可控而失去 agent 的能力」（`system-intent.md` 第二节第 4 条），基础规则也要求先反复观察到失败再定规则；一个场景、3 次运行不够定这样的规则。本报告的办法是先让质检有写文件的工具、用 M0 的预测性探索让质检在交付之前准备测试，再看读数。
4. 编排器过大。gemini 排第 3；本报告放在第 8 节「这次不修」，因为它不挡读数，M0 还在删阶段状态机与协作请求，等 M0 完成以后再量。
5. 被结束的那次运行的原因。gemini 写成「工程大量写文件，内存未回收，被宿主机杀死」。事实是 Claude Code 在会话空闲、系统内存不足时结束了它启动的后台命令，没有证据表明是 Yudao 的进程占用了内存。任务说明里「被宿主机的内存回收结束」的写法不够清楚，是这处误读的来源。
6. 方法 1。gemini 找到了两处导入扫描看不出来的问题：`harness/environment.py:613、655` 在执行层里写死了 `if action.department == "quality"`；编排器直接建立与打开检查工作区（`harness/orchestrator.py:438-446`）。核对属实，前一处与总体架构第 2 节「执行层……不持有领域状态」不一致。与这次的决定关系不大，补进第 8 节。

gemini 另外给出的数字：工程每次请求的上下文中位数约 7.7 万至 8.3 万 token、最高约 10.9 万（本报告核对属实）；它据此认为上下文累积是变慢的主要原因。OpenCode 每步的上下文更大（约 25 万至 28 万），总用量与 Yudao 同一量级，所以本报告认为主要原因是步数，上下文大小不是。
