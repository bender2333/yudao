# Raven（渡鸦）：它做了什么，Yudao 能用什么

> 日期：2026-11-07。状态：调研，未安装、未运行 Raven，未复现任何数字。
> 用途：回答三件事：外部报告（argon 的《Raven 调研与建议》）里关于 Raven 的说法哪些站得住；Raven 能不能当开发 Yudao 的过渡脚手架；它的哪些做法值得 Yudao 借。支持 [D35 自举](../requirements/self-hosting.md)「第二层的前置条件与完成条件」、[语义系统设计说明](../design/semantic-system.md)第 8、15 节（教训发现模块，待设计）、[外包角色设计说明](../design/outsourced-roles.md)第 4.3 节，以及共同规则第 5、8 条（先用成熟的库、先看成熟产品）。
> 阅读范围：仓库 README 全文（main 分支）；技术报告《Raven: The Harness of Harnesses for Composable Agentic Intelligence》的引言、第 2、3 节与第 5、6 节的一部分读到原文，第 4 节（Evolver）与第 7 节大部分只读到摘要，第 8、9 节与附录没有读；`tech-report-v1` 发布页全文。新闻稿只用来找一手来源。详见第 8 节。

## 1. 结论

Raven 是 EverMind 开源的多 agent 框架（Apache-2.0，技术报告发布时最新的版本是 v0.2.3）：一个主 agent（Host Agent）用模型把目标拆成一张无环的依赖图，派发前先校验这张图，再把节点交给内置的四个专长 agent（Research、Code、Design、Oncall）或经 ACP、命令行、OpenAI 兼容接口接入的 13 种外部 agent，最后由主 agent 自己整合交付。旁边有长期记忆（EverOS）、技能检索（SkillForge），以及一个在框架之外改框架的演化器（Evolver）。

**自进化这一块确实扎实，值得借做法；分布式部署在一手来源里没有，argon 报告里「联邦化调度」说的是一台机器上调用多家 agent，不是拆到多台机器上。** Raven 不适合当开发 Yudao 的过渡脚手架：Yudao 的开发现在卡在交接点没人接，不卡在拆单与写代码；多加一层编排还会在 GitHub 工单之外多出第二份事实。

| 问题 | 判断 |
| --- | --- |
| 分布式部署做得好吗 | 一手来源里没有。README 只写了一台机器上的 Docker Compose；产物存在按会话只追加的账本里；没有找到多机、按身份去重、执行权、重放与重启恢复。这方面 Yudao 总图第六节与 [ADR-0018](../adr/0018-single-control-host-remote-execution.md) 想得更完整 |
| 自进化做得好吗 | 演化器这一块好：在框架之外运行，从失败的轨迹诊断原因，把候选改动做成真实的 git 提交，先在训练子集上筛、再全量、最后在封存的留出集上给出泛化数字，只采用统计上胜过基线的。撤回在两份来源里都没找到 |
| 能不能当开发 Yudao 的过渡脚手架 | 不建议，理由见第 5 节 |
| 能不能复用它的 13 种 agent 适配 | 不需要。Yudao 的外包角色已定走 ACP 标准，每家用 ACP 生态现成的适配程序；Raven 的适配长在它自己的运行时里。可以拿它的预设清单查哪些 agent 能经 ACP 接 |
| 值得借的 | 演化器的三级评测与「失败轨迹 → 候选」；SkillForge 技能带支持案例的结构；派发前五组校验；Oncall 的「战役」记录（目标、测量、允许的动作、预算） |
| 不借的 | 主 agent 用模型生成调度图；主 agent 自己整合并宣布交付；运行中的 Curator 边干活边改自己 |

## 2. 外部报告的说法逐条核对

argon 报告里关于 Raven 的事实性说法，按一手来源核对。「原文」指读到了原文，「摘要」指只读到那一段的摘要，措辞没有核对。

| 报告的说法 | 核对结果 |
| --- | --- |
| Apache-2.0 | 成立（原文） |
| 仍处于 v0.2.x 的 Pre-Alpha 阶段 | 一半成立。v0.2.3 是技术报告发布（2026-09-27）时最新的版本；README 里没有 pre-alpha 字样，只写了 Curator 是实验性的；pre-alpha 的说法来自二手来源。今天的最新版本没有查 |
| Host Agent 动态生成 DAG | 成立（原文）：从要求的交付物倒推出依赖图；派发前做格式、图结构（含无环）、能力、状态、环境五组校验，第一条不过就停；不做语义校验 |
| DAG 单向推进，不能局部打回 | 不准确。图本身无环，但一个节点被判否以后挂起，主 agent 可以带消息续做、放弃或重新规划（续做、放弃、重新规划只读到摘要） |
| 13 种终端 agent 预设 | 成立（原文）：Claude Code、Codex、OpenCode、Hermes Agent、OpenClaw、MiroThinker、GitHub Copilot、Qwen Code、CodeBuddy、Qoder、Grok Build、Kimi Code、Pi |

| SkillForge 把成功轨迹提取为可执行函数或脚本 | 不成立。从经验得出的技能不带脚本（原文）；只有技能目录里的现成技能可以带 `scripts/` |

| 追加避坑指南（Pitfalls） | 没找到 |
| EverOS 内化 agent 自身的执行经验 | 成立（原文）：案例记录任务意图、尝试的做法、可复用的心得与估计的质量分，按意图归组生成或修订技能。「哪个子 agent 易超时」这类具体例子没找到 |
| 超图聚类与衰减，长周期 token 开销降到 1/10 | 没找到。HyperMem 是 EverMind 的另一个项目；「降本 90%」在两份来源里都没有 |
| 旁路 Evolver 与基准回归 | 成立（README 原文，评测流程是摘要）：演化器把 Raven 当库调用，「开发 agent 而不是在 agent 里面运行」；改提示词、知识、运行时、配置四类位置，内核不改 |
| Live Waterfall 实时瀑布流 | 只是 README 的声明，附一段视频，技术报告里没有描述，未核实 |

报告里关于 Yudao 的说法有三处不对：Yudao 没有「阶段五」，稳定工作单元的确定性降解在阶段四（[路线图](../program-roadmap.md)第 2 节）；「置信度连续达标直接触发降解」与第二层自举相反，降解与别的候选一样要经观察者提案、独立评价、限定采用，候选不能自己批准自己（[D35](../requirements/self-hosting.md)）；「重裁决、轻装配」的痛点报告没给依据。另外，总图写的是核验角色的结论不外包，不是「质检部门永不外包」。

## 3. 它到底做了什么

### 3.1 一轮工作怎么走

- 主 agent 从用户要的交付物倒推出一张依赖图，节点是交给某个专长 agent 的子任务。路由不用单独训练的分类器，由主 agent 的模型决定。
- 图在派发前过五组校验：格式、图结构（含无环）、能力（有没有接得住这个节点的 agent）、状态、环境；不过就退回主 agent，这一轮不启动任何节点。图可以要求某些节点先经用户批准再派发。
- 节点跑完交给一个完成判定。技术报告明确把「客观上对不对」与「agent 或判定说完成了」分开记。节点被判否时挂起，等主 agent 决定。
- 主 agent 整合各节点的交付物，交给用户。部分专长 agent 内部有独立审查：例如 Research 用不带作者上下文的另一次模型调用审查，Design 把没检查过的幻灯片交给空上下文的第二个审查者（摘要）。

### 3.2 记忆与技能

- EverOS 是本地优先、以 Markdown 存储的长期记忆，存经历、事实、画像、案例与技能。写入在一个会话内串行，存储失败会重试。
- 案例提取器记下任务意图、尝试的做法、可复用的心得与估计的质量分；同一意图的案例归组，用来新建或修订技能，技能链接回它的支持案例。评测某个案例时，它自己不进支持池。

### 3.3 两种「自己改自己」

- **演化器（Evolver）**：在框架外面，用配置文件一条命令跑，可以从断点续跑。读失败的轨迹，诊断反复出现的失败原因，生成候选改动（真实的 git 提交），先在训练子集上筛，再在完整训练集上跑，最后在封存的测试集上给出一个泛化数字；只留下在可复现的评测里胜过基线的改动。可改的是提示词、知识、运行时、配置四类，内核不改（后两句是摘要）。EverMind 另一份工作报告：固定一个 27B 模型、只演化框架，AppWorld 的一次通过率从 41.3% 升到 56.7%（二手来源，未核）。
- **Curator**：在运行中边干活边改 agent，可以换工具与外部服务、技能与做法、它自己的判断代码；装进去之前先校验，不过就退回（原文）。README 标为实验性，随仓库提供，不在安装包里。

### 3.4 数字

技术报告引言写编排基准上的完全匹配比最强的基线高 10.4 与 10.5 个百分点（原文）；Raven-Code 在 DataAgentBench 上一次通过率 0.8762（README 原文）。其余数字（Oncall 对 Claude Code、技能检索的提升、每题费用）只读到摘要。多层嵌套的额外开销没有找到分项数字，报告只说费用包括规划、执行者、交接、运行时校验与重试。

## 4. 和 Yudao 总图逐项对照

| 总图的东西 | Raven 里对应的 | 关系 |
| --- | --- | --- |
| 一份事实（只追加，跨重启） | 产物存在按会话只追加的账本里 | 相通一半：只追加一致；它的账本按会话，没找到跨会话的重放与恢复 |
| 裁决与写入口（U ≠ f） | 派发前的五组校验是确定性的；完成判定由模型做；主 agent 自己整合交付 | 一半相通：校验先于派发一致；「谁说了算」不同，Yudao 的放行只来自核验角色的独立证据 |
| 路由槽位（读事实与冻结的定义） | 主 agent 用模型生成依赖图 | 冲突：Yudao 的路由不调模型、重放读事件；要模型判断的小问题走判定点，答案先写成事件 |
| 核验角色与开环完成 | 「客观上对不对」与「宣布完成」分开记；部分专长 agent 内有空上下文的审查 | 思路相通，位置不同：它的审查在专长 agent 内部，Yudao 的核验是定义里的一种角色，任何形态都能放 |
| 执行的缝与外包角色（ACP） | 13 种外部 agent，Claude Code、Codex、OpenCode 经 ACP | 方向一致：Yudao 也走 ACP，适配用生态里现成的程序；Yudao 多了每次从封存快照建工作区、模型与工具走受控入口 |
| 装配的缝 | 上下文吃紧时由记忆提议缩小窗口（摘要） | 不同：Yudao 的装配是从事实减出、交给模型的字节记进事实，同样的事件重放出同样的请求 |
| 教训发现模块（待设计） | 案例提取 + 按意图归组 + 技能链接支持案例 | 可借鉴结构，见第 6 节 |
| 第二层自举 | 演化器在框架外面跑、三级评测、只留胜过基线的 | 相通，可借鉴评测流程；Yudao 多了限定采用（只在某类事项或某个比例生效）、撤回不回滚代码、评价材料只由你改 |
| 运维部门与常驻（阶段三） | Oncall 的「战役」 | 可借鉴记录的结构，见第 6 节 |
| 拆开部署（第六节） | 没有找到 | Raven 在这方面没有可借的 |
| 画面与页面 | 实时瀑布流（未核实） | 以后多成员并发时可以参考 |

## 5. 不当开发 Yudao 的过渡脚手架

argon 报告建议先用 Raven 开发 Yudao：主 agent 拆单、多家 agent 并发写代码、Oncall 盯评测与走查。不建议，三条理由：

1. **它解决的不是现在卡住的地方。** 阶段二最近一次诊断（2026-11-07 的架构师日记）：solo 循环停在「0 可派」，主因是父工单验收、交回分诊、到期放回这些交接点只在有架构师会话时发生，架构师循环 10-31 以后没开过；分解上的毛病是依赖挂错、工单建得太早。主 agent 拆图解决的是「拆单慢」，并发写代码解决的是「写得慢」，两样都不是瓶颈。对症的做法是让架构师循环定时跑起来（同日已做成 `architect-loop` 技能，由定时任务唤醒），并修掉诊断里的分解问题。
2. **会多出第二份事实。** Yudao 的开发以 GitHub 工单与标签为事实（[工作方式](../agents/workflow.md)第 1、4 节），拆单写依据、「只改」与环，验收写证据评论。主 agent 的依赖图有自己的状态，不认识这些；两份状态对不上时，谁为准没有答案。
3. **会搅乱阶段二的对照。** 第一层试点要拿已发布的 Yudao 与外部执行者逐张配对比较，外部执行者现在是 solo 执行者，基线数字要先导出（[D35](../requirements/self-hosting.md)「第一层试点的配对验收约定」）。半途把执行者换成多层嵌套的 Raven，基线就变了。

真想试 Raven-Code 写代码，最便宜的试法是把它当成又一种 solo 执行者：照 `solo-worker` 技能做一张界面工单，事实仍在 GitHub，不用主 agent。这和 Hermes、OpenCode 当执行者是同一条路，不用改流程。

## 6. 值得借的四个做法

按价值排序，都落在外圈或第二层，不碰内核。

**① 演化器的三级评测与「失败轨迹 → 候选」（第二层自举，阶段四；道 08 评价与验收）。**
Yudao 已定候选要在系统外、被测方没见过的评测集上与基线隔离对照（[D35](../requirements/self-hosting.md)，[实验规约](experiment-protocol.md)）。演化器补的是两样具体做法：候选先在训练子集上便宜地筛、再全量、最后才动封存的留出集，留出集只用来给一个泛化数字，不参与挑选；候选从失败轨迹里诊断出的原因出发，一个候选对一个原因。Yudao 比它多的要保留：限定采用、撤回不回滚代码、评价材料只由你改、候选不能自己批准。它没有写撤回，这正是 Yudao 要守的一条。

**② 技能与教训带支持案例（教训发现模块，语义系统第 8、15 节）。**
Yudao 已定教训必须关联依据、依据失效时变为待复核、跨项目复用要经独立验证（[语义系统设计说明](../design/semantic-system.md)第 8 节）。SkillForge 补的是案例的结构与用法：一条案例记任务意图、尝试的做法、可复用的心得、质量分；同一意图的案例归组，生成或修订一条技能，技能按「质量、再按时间」链回支持案例；评测某个案例时它自己不进支持池，免得自己证明自己。教训发现模块设计时，把这几样当输入。不借的：argon 说的「置信度达标就直接触发降解」。教训是参考内容，主机不强制执行；要强制的走定义候选的流程（[规则登记与参数设计说明](../design/rules-and-parameters.md)「采用与撤回」）。

**③ 派发前的五组校验（任务池，道 03 路由与形态）。**
任务池阶段如果允许角色提出「拆成几个工作单元」的提案，裁决前的结构校验可以参照它的五组：格式、图结构（无环）、能力（定义里有没有接得住的角色）、状态、环境（登记的机器在不在）。Yudao 定义加载时已经校验「谁能拒绝谁无环」等，这一条是把同样的思路用到运行中的拆分提案上。

**④ Oncall 的「战役」记录（运维部门与常驻自转，阶段三）。**
一次长时间无人值守的工作有一份持久记录：目标、测量、允许的动作、预算；算力请求按剩余预算截断；等待、终止、重交的决定要引用最近一次测量；没有基线的报告被拒。这和 Yudao「判断要有证据」一致，运维部门写设计说明时可以作为事项与上限怎么写的参考。

实时瀑布流：画面与页面以后到了多成员并发时可以参考，现在只是 README 的声明，先不排。
