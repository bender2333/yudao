## 现象

现在后台命令只能轮询：模型得自己记着编号，再去调 `read_output`。作业结束了没有人接，一轮结束时作业也跟着停（`harness/environment.py` 里的 `BackgroundJobTable` 放在内存，按会话结束）。自动驾驶配置因此把后台命令关了（`docs/agents/autopilot-runtime.md`：「关闭后台命令，命令都在前台运行，测试结果能交回」）。路线图阶段三「断了接得上」、阶段四「自己转一周」，以及道 05、道 10 上的远程执行代理（现在标「等」）都会碰到这个问题：命令更慢，网络会断，进程会重启。

用户定的方向是：底下只做一套异步，同步就是「发出去，在同一步里等结果」这个特例；作业结束不打断角色。

## 要定什么

总图没有写一轮交掉以后，这一轮起的后台动作结束时结果怎么回来。建议照第三节「中途的指导」那条规矩办：内核不动，不加模块，不加缝，也不加「等后台」这个状态。具体补下面四处：

1. **第三节，两环的关系。** 现在的原文是：「你中途的指导是职能关注的成果：职能在等待时，指导让它开始一轮；在一轮工作中时，指导在下一步作为通知加入。」建议在后面加一句：「后台动作的结束同理：它是发起它的角色关注的东西，角色在等待时让它开始一轮，在一轮工作中时作为通知加入，不打断正在走的一步。自有角色在下一步加入；职能由外部 agent 做时，什么时候加入跟中途的指导一样，按外包设计说明里那条未决问题的结论办，没定之前等这一轮交回再带上。」
2. **第四节「动作」卡，加两条：**
   - 「动作可以在后台跑：回执晚于发起它的一轮到达时，照常写成事实，不作为那一轮的结果接纳。」第三节已有「重派与迟到的结果：旧编号只记录」，第六节已有「旧编号交回的结果只记录不接纳」，这一条是把这两条规矩用到后台动作上。
   - 「后台动作属于事项与执行权，事项停止或执行权转走时一并结束；时间上限来自定义。」作用是让第一节「保证一定会停」对一轮之外还在跑的进程也成立。边界的代码不用改，结束进程由执行实现负责。
3. **第四节「装配」卡。** 「待并入的指导」改成「待并入的通知（指导、后台动作的结束）」，规矩那一行和「交换」那一行各改一处。按「字段只增」算，这是向后兼容的改动。再补一句边界：外部 agent 做的职能，装配只给这一轮开头那一份；中途的通知怎么送进外部会话，归外包派发，不归装配。
4. **第二节「定义」那一格。** 不用改，后台动作的时间上限算在「上限」里。

**和「总图里的细则移到设计说明」那份清单的关系**（11-10 的决定记录，九项，还在等用户定）：如果第四节各道缝的规矩移到设计说明，第 2、3 条就跟着落到对应的设计说明里，分别是执行环境设计说明（动作）和 `docs/design/context-assembly.md`（装配），意思不变。第 1 条说的是循环怎么接住外来的结果，属于框架，建议留在总图第三节。

## 依据（总图原话）

- 第二节：「四层……单 agent、普通多 agent、产品 · 工程 · 质检、子组织都只换下面两层，任何一种要改上面两层，就是抽象没立住。」第一节的方程每次只处理一条进来的东西，里面没有「等」。一轮结束是一条事实，作业结束是后来的另一条事实，所以异步不用动内核。
- main 上内核清单（`harness/definitions/kernel-manifest.json`）列出的 13 个模块里，没有一个提到 background 或 job。
- 第六节：「没有事件库之外的第二份事实」。所以不另做通信模块或消息总线：角色之间经事实，系统和外面经接口，跨机器走四道过网的缝，传输适配放在外圈。

## 一条推断，设计说明里没有直接写，请一起确认

子组织里起的后台作业，结束时叫醒的是子事项里发起它的那个角色，不越过层级去叫上一层；「后台动作跟着事项和执行权走」用的是子事项自己的执行权。这是从第三节「子事项有自己的事件流、冻结的定义与边界」推出来的。

## 相关，归子架构师

- 外包设计说明里的未决问题「外部 agent 中途怎么收指导」，建议放宽成「中途怎么收通知（指导、后台动作的结束）」，一次定清。ACP v1 没有规定运行中再发 prompt 怎么处理；v2（草案）规定任何状态下都能发。
