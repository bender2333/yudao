# 离线证据、复核与批次分析详细设计

> 日期：2026-09-06。设计对象：第二阶段 2.1-A/B 的下一批独立交付。
> 状态：开发设计，本文新增能力尚未实现。当前可运行入口仍只有 `python -m harness.analysis demo`。
> 上位依据：[第二阶段计划](../stage-2-plan.md)、[总体架构](../system-architecture.md)。调研依据见[证据与评价](evidence-evaluation.md)。

## 1. 要交付的完整使用过程

研发者准备各轮本地交付、有效要求、固定行为检查和原 QA 材料，发起一次离线复核。工具保存完整交付，在独立副本实际检查，形成可搬移的证据目录。关闭程序、修改原交付或将证据目录移到其他位置后，仍能只读核验并重建问题轨迹。研发者可以汇总多个目录，也可以从一个结论追到具体原始输出。

这一过程沿用现有封存、检查和分析逻辑。输出用于材料复核与观察工具校准；真实执行来源、正式任务身份和系统版本齐备前，不能据此建立正式质量基线。

当前不接入第一阶段事件库、控制器、OMP、上下文或 Web。当前固定运行可信本地 Python 文本程序，不接受命令模板、依赖安装或输入材料提供的插件。

## 3. 三层职责

```mermaid
flowchart LR
    M[本地材料清单] --> I[输入核验与复核编排]
    I --> S[封存与固定执行]
    S --> P[完整证据目录]
    P --> V[只读核验与记录重建]
    V --> A[纯轨迹分析]
    A --> R[单份报告与批次报告]
    V --> Q[结论来源定位]
```

| 层 | 负责什么 | 不能做什么 |
| --- | --- | --- |
| 采集与执行 | 解释明确输入、封存交付、发起固定检查、保存主机回执 | 不能把输入清单中的“已通过”当成自己的执行结果 |
| 证据存取与核验 | 保存原始记录、解析目录、核对完整性和引用、重建已观察事实 | 读取不能启动检查、导入交付模块或访问历史路径 |
| 分析与呈现 | 计算轨迹、QA 对照、覆盖、成本及批次汇总 | 不能补造缺失观察，不能通过重写原 QA 制造一致性 |

这三层继续属于 `harness.analysis`，使用本地模块调用。近期不新增服务、数据库或通用执行框架。

## 4. 四类身份必须分别保存

| 对象 | 解决的问题 | 不能替代的对象 |
| --- | --- | --- |
| 材料/任务声明 | 提供者称这些轮次属于哪个任务、哪个任务族 | 不证明真实任务身份，不证明样本独立 |
| 一次复核 | 区分何时、用什么评价器对材料做了哪次实际检查 | 不能当作新的任务；只读重生成不创建新的复核 |
| 内容标识 | 识别要求、检查、交付、输出及证据记录内容 | 同内容不意味着同一次执行，不同内容也不必然是不同任务 |
| 来源依据 | 说明身份和 QA 决定来自人工声明、固定校准还是可信采集 | 一个自由文本标签不具有可信采集的证明力 |

本地清单必须明确材料来源，提供稳定的材料标识和有序轮次。任务族、执行系统版本或原始任务身份无法核对时保留未知，不从目录名、修改时间或源码内容猜测。

同一份材料重新执行检查得到新的复核；移动目录、重新渲染报告仍然是原复核。即使输入文本相同，真实运行的多次执行也需分别记录，不按文本哈希直接删除其成本。

## 5. 证据目录的逻辑组成

以下是存储职责，不是要求实现者建立一组插件或通用对象注册表。

| 组成 | 必须包含 | 读取规则 |
| --- | --- | --- |
| 目录入口 | 协议版本、材料来源、复核身份、有序轮次及完整文件清单 | 只接受当前明确版本；重复身份或缺少引用报错 |
| 要求与检查 | 当轮完整有效要求、版本、固定输入、预期行为和复现条件 | 重新计算内容标识；检查必须指向当轮有效要求 |
| QA 与辅助意见 | 原决定、受审要求、交付对应、来源依据；辅助意见另存 | 缺少受审依据时仍保存，但不能确认错误放行 |
| 完整交付 | 普通文件字节、隐藏文件、二进制及空目录清单 | 校验文件集合，不能只检查已列出的几个文件 |
| 实际观察 | 每次检查的结束类型、退出码、耗时、原始输入输出、环境、前后交付标识 | 状态是历史回执；需要与可核验字节及比较规则一致 |
| 分析约定 | 评价器身份、文本比较规则、分析方法版本及适用范围 | 原执行环境与本次读取环境分别记录 |
| 派生报告 | 问题轨迹、QA 对照、Markdown 和批次结果 | 可以重新生成；不是读取器接受事实的依据 |

先使用目录与 JSON、原始文件。压缩归档、云对象存储、签名服务和跨语言标准互操作不属于近期需求。借鉴 BagIt 的完整文件核验和 PROV 的来源职责，不声明已实现相应标准。

### 5.1 包内定位与历史来源

包内交付及 stdin/stdout/stderr 使用相对于证据根目录的路径。搬移只改变读取根目录，不改变证据内容、复核身份或历史环境标识。

原交付路径、当时 Python 路径、当时工作副本位置和执行参数作为历史文字保存，明确不可导航或执行。读取器不能因为找不到原路径而使用当前目录同名文件，也不能将本机解释器信息覆盖到原环境中。

执行后的工作副本可作为诊断附件保留。对于执行中修改文件的案例，核心证据至少包含封存交付、前后标识、变更回执与原始输出；缺少可取回的执行后字节时，报告只能说“记录了内容变化”，不能声称读者已经独立重建变更内容。

### 5.2 内容标识与真实性

逐个原始文件按字节计算标识；结构化事实使用固定的项目序列化约定。沿用并明确现有 `fingerprint` 的约定，不把排序 JSON 自动称为跨语言规范化标准。协议变化时直接切换当前实现，不增加旧协议分支。

证据整体标识覆盖来源声明、有序轮次、要求、检查、QA 依据、环境、实际观察及原始文件清单。派生报告和本次渲染时间不参与该标识，避免同一事实换一种展示就变成新证据。

核验有三个不同层次：

1. 文件完整性：内容是否与给定清单一致。
2. 记录一致性：要求、检查、交付、回执与结论是否相互支持。
3. 来源可信性：是谁在何种可信执行边界采集了它，有什么独立依据。

前两项通过不自动得到第三项。拥有整份证据写权限的人可以同时改文件和清单；没有外部可信内容标识或可信采集依据时，不能承诺发现这种整体重写。近期本地工具报告前两项及声明来源，不引入签名基础设施来制造未经验证的真实性保证。

## 6. 保存过程及中断处理

1. 先检查完整输入合同、输出位置及引用关系；在任何交付开始执行前报出清单结构错误。
2. 创建一个新的工作目录；输出不能位于任何输入交付内部，也不能覆盖已有证据目录。
3. 保存规范化的输入及来源，逐轮封存交付，执行固定检查。已完成的实际回执尽快保存；不同轮次使用独立副本。
4. 执行前后核对交付；运行后保存原始字节和结束事实，不能先写“通过”再补证据。
5. 在同一父目录下完成核验后发布最终目录入口。发布前的残留工作目录不能被批次统计当成完成材料。

这是本地目录发布协议，不承诺断电时文件和数据库的跨系统原子性。文件系统异常、磁盘满或进程退出会留下可识别的未完成材料；默认不自动续跑未完成检查。用户再次发起复核时创建新身份，旧残留保留用于诊断。

输入合同合法后发生的超时、无法启动、交付丢失或交付变化属于观察结果，必须保留。结果未知与明确失败分别记录；输出写入本身失败时，本次工具执行也不能宣布证据包完成。

## 7. 只读加载与重新核验

读取必须是一个闭合过程：所需文件都在证据目录内，所需比较规则由当前工具提供。读取不调用模型、不执行 `main.py`、不调用记录中的命令，也不安装依赖。

### 7.1 读取顺序

1. 以结构化 JSON 解析入口，检查当前协议、字段类型、有序轮次和唯一身份。
2. 解析全部包内路径，拒绝越界、绝对路径、盘符相对路径、UNC、父级跳转、链接及重解析点。
3. 校验核心文件集合、字节数与内容标识，发现缺失、替换和未声明交付文件。
4. 重建要求、检查、QA、环境与观察记录，检查每个引用的对象和版本。
5. 从真实 stdin/stdout/stderr 字节恢复文本。stdout 严格 UTF-8 解码失败才允许无逻辑文本；成功则按既定换行规则比较。
6. 对正常退出的检查重新计算该字节与退出码支持通过还是反例，核对重复次数、稳定性及受测内容对应。超时或启动失败的发生原因仍属于历史主机回执，不会因读取字节就被再次实证。
7. 重算轨迹与 QA 对照，输出新的核验回执。原派生分析即使存在也不作为依据；可记录旧展示与重算不一致。

当前 `trajectory._validate_round` 对非通过/失败状态的检查较少，且无逻辑文本分支仍需读取真实字节验证。实施者必须补齐读取边界，不能只将 JSON 转回 dataclass 后就认为可被信任。

### 7.2 JSON 与 Windows 文件规则

Python 标准库 JSON 默认接受重复键并保留最后一个，也默认接受 NaN/Infinity。[P01](#p01-python-json) 说明了这些行为。输入协议应拒绝重复键、非有限数字、错误类型、负耗时与非法重复次数；布尔值不能充当检查次数。有效 JSON 也需要领域校验。

中文要求和文件名合法，输入输出统一 UTF-8；文件字节保持原样，不对交付文本进行换行转换。输出比较仍沿用现有 CRLF/CR/LF 归一化，只作用于比较，不修改原始字节。

面向 Windows 的证据读取还要检查大小写碰撞、尾点/尾空格别名、设备名及冒号形成的不同路径含义。对无法在当前平台无歧义表示的路径明确拒绝，不悄悄改名。目录检查需在解引用之前完成，不能先 `resolve` 再遗漏根链接。

本批以可信本地材料和稳定目录为前提。加载时防止误指向包外文件，但不声称在恶意并发替换文件、特权进程干预或不可信程序逃逸条件下提供安全隔离。限制输入大小和文件数是可操作边界，具体上限在编码前以校准材料和失败样例确定并记录，不能静默截断。

## 8. 本地材料清单的使用合同

清单承载研发者提供的事实和检查约定，不承载执行代码。近期使用 JSON，复用标准库，按实际合同校验；不为单一输入新增 schema 服务。

| 输入组 | 必须说明 | 不允许隐含推导 |
| --- | --- | --- |
| 整份材料 | 材料标识、来源、是否校准、轮次顺序 | 不能从文件名推断真实运行来源 |
| 每轮交付 | 本地目录或明确缺失、交付来源、轮次身份 | 未指定不等于复制上一轮交付 |
| 有效要求 | 完整文字、身份、版本、合法变化来源 | 要求变了不能只复用旧文字的标识 |
| 固定检查 | 所属要求、文本输入、预期 stdout/退出行为、超时与重复约定 | 不接受任意 shell、入口或依赖安装请求 |
| QA | 原决定、来源、受审要求、已提供的交付依据 | 不能自动把未知 QA 对应到刚封存的新交付 |
| 可选上下文 | 原始任务或系统版本的来源依据，独立文字意见 | 缺失不填成本地工具版本或新的模型判断 |

清单中的相对交付路径以清单目录为基准，允许研发者显式引用该目录外的本地交付；它与证据包内部禁止越界是不同边界。输入路径在复制时进行验证，执行永远使用已封存的独立副本。

QA 明确由人工声明“审阅本轮材料”时，可以保留这一声明并关联封存内容；来源仍是人工声明，不能升级成已验证的历史 QA 绑定。来源证据缺失时，工具仍能发现当前交付反例，但不能宣称真实模型错误放行。

未知字段与版本明确报错，避免拼错字段后工具以默认值执行。先完成所有轮次的语法及引用检查再开始运行；执行期间后来消失的输入保留缺失事实，不跳过轮次。

### 8.1 拟定操作面

| 操作 | 输入 | 输出 | 会不会执行交付 |
| --- | --- | --- | --- |
| 本地复核 | 显式清单和新输出位置 | 自包含证据目录、报告、过程结果 | 会，固定可信程序 |
| 核验 | 一个证据目录 | 完整性与一致性回执 | 不会 |
| 重生成报告 | 已核验目录和新的展示输出位置 | JSON/Markdown 派生报告 | 不会 |
| 批次分析 | 有序材料位置列表和输出位置 | 提交清单、分层统计、来源索引 | 不会 |

具体命令名称在实现时集中确定；本文不把尚不存在的 CLI 写成当前使用说明。工具正常完成复核与被测交付通过是两种结果：一个记录完整的失败交付也可以成功生成证据目录。自动化消费方必须分别检查工具结果和领域结果。

## 9. 材料批次统计

### 9.1 先保留提交清单，再形成可比较组

输入列表逐项记录提交位置、可读性、核验状态、是否重复、材料来源、复核身份和分组依据。坏包、缺失包、重复提交都保留这一行。

精确复制的同一复核只参与一次观察统计，但提交次数仍如实显示。同一交付重新执行形成不同复核，检查成本全部保留；它们不增加独立任务数。对于只修改声明身份的相同内容，不自动认定独立样本，显示同材料或身份待核验。

先按校准/本地声明/可信采集分开，再按要求、检查、环境及评价方法划分可比较范围。不同范围可以并列显示覆盖与各自结果，不能合成一个质量收益百分比。

### 9.2 分母与计算单位

| 报告项目 | 分子与分母/单位 | 未知怎样处理 |
| --- | --- | --- |
| 材料可用性 | 完成核验的提交项 / 全部提交项，同时给出去重后包数 | 缺失和损坏留在提交分母；重复项单列 |
| 检查完成覆盖 | 有可判定观察的声明检查 / 全部声明检查 | 坏包无法获知检查总数时，标明此分母仅覆盖已读材料 |
| 要求覆盖 | 至少有检查的有效要求 / 全部有效要求 | 仅表示已配置检查，不代表所有输入行为覆盖 |
| 复发 | 同比较区段内可复核的复发点数，另列涉及材料数 | 缺失与口径变化不跨越连接；不能称根因复发率 |
| QA 反例对照 | 有同要求及同交付依据的反例放行轮次 | 同时列全部放行轮次、可比较轮次和来源层级；不能仅报告已核验部分的比率 |
| 独立任务结果 | 具有可核对任务身份、预定采样和任务终点规则的任务 | 近期身份不够时不发布正式任务成功率 |
| 复核成本 | 实际检查次数、累计检查秒数、复核经过时间 | 历史执行/模型/价格缺失记未知，不记零 |

每轮失败次数不能代替返工次数：原 QA 的返工是当时决定，外评失败是后续发现。当前材料无法证明“无效返工”的原因，近期只展示已观察轨迹和已声明返工。

累计检查时间不是端到端耗时；未来并行时二者尤其不同。批次去重不抹除真实重复执行成本，展示层重生成的耗时单列为分析成本。只要有成本缺失，求和就标明“已知部分”及记录覆盖；它至多是总成本下界，不能仍命名为完整总成本。

### 9.3 一组固定统计校准材料

提交六项：A、A 的完整复制、A 的新一次复核、B、一个损坏目录、一个不存在的位置。前四项通过核验，得到四个有效提交项、三个不同复核和两个已声明材料身份；后两项身份未必可恢复。

期望报告：提交总数六，有效提交四，重复提交一，损坏一，缺失一；去重后的复核三。即使两个已声明材料都检查通过，也不能写成“六个任务中四个通过”，更不能据此宣称两个独立真实任务全通过。

若损坏项带有可以读取但尚未核验的身份，只作为未核验声明展示，不能将它与另一有效项合并后从损坏分母消失。

## 10. 一个结论怎样回到来源

报告中的问题轨迹点必须能定位到：材料与复核、轮次、有效要求、固定检查、封存交付、环境、每次原始 stdout/stderr 和原 QA 依据。文字解释与这一串来源并列保存。

先用表格及明确链接完成查询，不建设通用图谱编辑器。后续 Web 可以使用相同的定位结果，并由服务端核验可访问对象；不能将证据中任意路径变成浏览器可访问文件接口。

“修复后复发”的来源包含支持这一判断的失败、通过、再次失败三个观察，不能只链接最终失败。口径变化需能定位是哪一份要求、检查或环境发生改变。

## 11. 开发分批与文件责任

| 批次 | 完整结果 | 主要边界 | 独立验收后提交 |
| --- | --- | --- | --- |
| L1 | 当前复核能保存、搬移、只读加载并重算轨迹 | 持久存取、核验和记录合同；报告格式集中调整 | 搬移、原材料删除、篡改与禁止执行 |
| L2 | 外部清单能驱动多轮复核 | 输入解析与编排，复用 L1 和既有执行器 | 真实本地三轮、缺失、超时、QA 依据不足 |
| L3 | 多份材料可按诚实分母汇总并追溯 | 只消费 L1 的已核验对象，不另写加载器 | 重复、重评、损坏、缺失、混合来源和口径 |

L1 的存取合同先形成可审查的小结果。L2 可并行完成清单验证，但实际写包依赖 L1。L3 可先准备统计校准材料，实际汇总依赖 L1。CLI、共享记录与 `report.py` 由同一实施者整合，避免多代理同时改动。验收编号 A/B/C 分别对应这三份离线续批，不与第二阶段 2.1-A/B/C 的完整工作包编号混用。

主代理维护设计、审查和验收；实现由 Codex 子代理承担。每批完成后 commit、push，仍不合入第一阶段分支。

## 12. 验收场景

| 编号 | 输入或故障 | 应观察到的结果 | 不接受的结果 |
| --- | --- | --- | --- |
| A01 | 三轮已知固定材料 | 失败、修复、复发与另一检查的新问题正确 | 只判断最终一轮 |
| A02 | 退出进程，修改/删除原目录，再搬移证据 | 核验与轨迹不变；报告定位新的包内文件 | 依赖原绝对路径 |
| A03 | 核验时拦截子进程启动和交付导入 | 全过程没有执行 | 发现缺失后自行重跑 |
| A04 | 改 stdout 字节但不改清单 | 完整性失败 | 使用 JSON 中缓存文本继续通过 |
| A05 | 合法 UTF-8 字节却记录为无逻辑文本 | 记录一致性失败 | 无文本分支绕过比较 |
| A06 | 改要求/检查/环境或 QA 绑定而保留原观察 | 引用或内容标识不一致明确失败 | 沿用旧派生结论 |
| A07 | 加入未列出的交付文件、删除空目录 | 完整交付核验失败 | 只验证已列文件 |
| A08 | 包内 `..`、盘符、链接、junction、路径碰撞 | 在读取对象前拒绝并说明位置 | 读取到包外真实文件 |
| A09 | NaN、重复键、布尔重复次数、重复轮次 | 清单/包结构错误，无执行 | 默默采用最后值或转换类型 |
| A10 | 同时声称超时和正常退出完成，或与重复回执矛盾 | 按终止事实的合法组合校验；无法核实原因则保留限制 | 非通过状态完全不校验，或只因 stdout 符合预期就否定超时 |
| A11 | 篡改派生 `analysis`，核心证据不变 | 重算真实派生结果并提示旧展示不一致 | 信任原 analysis |
| A12 | 同时重写全部核心记录及哈希，无外部锚点 | 只能核验自洽性，来源仍未获证明 | 宣称能检出所有伪造 |
| B01 | 清单后三轮之一的字段/引用有误 | 任何程序启动前返回完整输入错误 | 前两轮已执行后才发现静态错误 |
| B02 | 合法输入中途丢失、程序超时或环境失败 | 保留所在轮次、尝试和不确定性 | 从材料序列删除失败项 |
| B03 | QA 放行但缺少受审交付依据 | 可报告当前反例，不能确认真实错误放行 | 自动补成刚生成的交付哈希 |
| B04 | 本地模块导入、中文文本、Windows 换行 | 沿用既有固定 Python 与文本约定 | 改用隔离参数破坏本地导入 |
| B05 | 输出目录已存在或位于交付内部 | 无覆盖、无递归封存输出 | 覆盖旧证据或复制自己 |
| B06 | 完成部分检查后进程退出/磁盘写满 | 未完成材料明确，不算完成证据 | 有 report 就算成功 |
| C01 | 六项统计校准材料 | 输出第 9.3 节的提交、重复和复核数 | 按目录数声称任务成功率 |
| C02 | 校准、人工 QA、真实采集材料混合 | 来源分层，逐项可追溯 | 一起算真实模型错误放行率 |
| C03 | 要求/检查/环境改变，或中间缺失 | 分段比较，缺失可见 | 跨段推断修复/复发 |
| C04 | 同包重复汇总、重渲染、重新执行 | 前两者不增复核数；后者保留新执行成本 | 任何新报告都变成新任务 |

代码验证集中覆盖这些行为边界，复用现有 pytest；文档自身只做链接、结构、来源和一致性检查。没有代码变化时不以重跑旧测试充当本设计已实现的证据。

## 14. 本文直接核验的实现依据

所有访问日期为 2026-09-06。以下为官方原文的相关章节核验，未安装或运行外部产品。

### P01 Python JSON

- 来源：[Python 3.14 JSON 文档源文件](https://github.com/python/cpython/blob/3.14/Doc/library/json.rst)；[官方文档](https://docs.python.org/3/library/json.html)。
- 阅读范围：解析限制、`object_pairs_hook`、`parse_constant`、非有限数字和 Repeated Names Within an Object。
- 直接依据：默认解析器容许重复键及非有限数；可用标准库明确拒绝。采用的是结构化解析和领域验证，不需要为此新增服务。
- 限制：文档介绍解析行为，不证明我们的输入校验已经正确实现。

### P02 RFC 8259

- 来源：[RFC 8259 原文](https://www.rfc-editor.org/rfc/rfc8259.txt)。
- 阅读范围：第 4、6、8、9 节的对象名称、数字、UTF-8 和解析限制。
- 直接依据：重复键影响互操作；Infinity/NaN 不属于 JSON 数字；实现可限制输入长度、深度和数字范围。
- 项目决定：协议要求比“默认解析成功”更严格。RFC 的 SHOULD unique 不等于规范要求所有解析器必须报错。

### P03 SQLite 使用范围

- 来源：[Appropriate Uses For SQLite](https://www.sqlite.org/whentouse.html)。
- 阅读范围：本地存储、网络文件系统和 High Concurrency。
- 直接依据：SQLite 面向本地应用存储，单个数据库同一时刻只允许一个写者；高并发和网络共享需另评估。
- 项目决定：近期证据目录无需增加数据库；后续来源索引优先评估现有 SQLite。多个进程/机器并发写与长期运维需求出现后再作选型实验。
- 限制：这是适用性依据，不是本项目吞吐量测试，也不承诺文件工件与数据库共同事务。
