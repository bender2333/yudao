# 原生模型重试的设计核对

日期：2026-09-06。本轮读取第一阶段 `95ba279` 后正在实施的改动、D17 与 D09，并结合两份并行实施回执复核。本文是架构和验收建议，不是 H 批次已经实现或通过的证明；不修改第一阶段业务代码。

## 1. 当前有效要求

第一阶段 `D:/codes/yudao/docs/requirements/provider-retries.md` 记录了用户新要求：瞬时模型失败应重试，正常响应约一分钟不应误判失败。一分钟是用户观察值，不是截止时间。D17 已取代旧的连接失败立即终止设计；历史无重试运行及其失败仍按当时版本保存。

以 D17 当前实施选择为准：原生内核控制重试；适配器负责单次请求和错误分类；最多 3 次尝试，通常等待 1 秒、2 秒，Retry-After 等待上限 60 秒；单次请求默认 600 秒且可配置。每次实际请求使用新步骤编号，计入既有 32 次调用上限，工作与压缩一致。SDK 内置重试保持关闭。

因此，早期“适配器内部自行重试”“失败尝试不计模型步骤”“仅成功用量入账”等建议不作为当前合同。无需新增独立重试平台、可配置的策略组合或额外任务总时限配置。

## 2. 保持三层责任

| 责任 | 应负责什么 | 为什么 |
| --- | --- | --- |
| 模型适配器 | 一次网络请求、流读取、单次输出与可判断的失败原因 | 不掌握当前需求是否变化，也不独立决定是否继续旧工作 |
| 原生执行与状态控制 | 下一次尝试、等待、步骤限制、取消、新输入、结果接纳 | 每次发起请求都需服从当前任务的控制顺序 |
| 事件、查询与 Web | 保存每次尝试，派生当前等待状态、历史与审计结果 | 失败事实可追溯，看到部分输出不等于请求已经成功 |

等待不占状态锁；等待前后和请求实际开始前均核对取消、新输入及执行依据。新输入已经接收时终止旧工作重试，由产品处理。prompt 按 D02 的下一次目标部门激活生效，不能因为同一次激活内重试就提前采用新 prompt。

每次尝试拥有自己的实际请求记录与步骤编号，通过关联标识说明它重试哪次请求。界面可以显示“本次第几次尝试”，但不因此制造额外部门激活。第 32 步失败后没有第 33 次实际请求，也不先显示一个必定不能执行的重试等待。

重试前重新装配当前上下文并完成请求准入，不能直接重用锁外保存的旧请求。流式观察从注册时就绑定具体尝试，不能在回调到达时借用“当前请求”的身份；旧流迟到的消息和用量仍属于原尝试，只保存对应审计事实，不混入新尝试或恢复旧工作。

## 3. 失败事实与有效历史分别处理

失败尝试的输入、已收到内容、停止原因和用量应按来源保存。部门有效历史及摘要只能消费允许接续的完整回合；失败流中的残缺 function call 不进入下一次模型输入，也不能假造工具成功结果补齐协议。原始完整历史仍可查询，不删除失败尝试。

`request.observe` 的职责是记录模型观察，不直接执行主机工具；当前实施版增加了观察缓冲，具体持久化时机仍需核验。工具由 `engine.run_department` 在适配器返回完整响应、协议检查与动作准入后执行。需要防止的是重试引入后混合两次输出或再次进入动作执行路径，不能把现有 observer 误描述成已经发生了重复工具执行。

只有明确的完整响应及允许的后续处理才能成为有效回合。仅“未找到失败标记”不足以证明成功；部分输出到达、进程中断或失败标记持久化失败时，查询和审计不能默认已完成。成功识别应共享明确来源，避免运行时、审计和 Web 分别猜测。

同一规则覆盖部门对话、压缩来源和最终部门记录。原始记录若包含失败片段，必须保留所属尝试及状态；作为已接纳工作依据的记录只能包含有效回合。不能只修复下一次请求的历史过滤，却让最终记录把失败片段与成功输出拼成一份无区分的结果。

审计应能区分已装配但未发出、已发出且成功、已发出且失败，以及终态未知。已安排的重试最终需要对应实际请求或明确的取消、输入变化及停止原因。进程中断留下的未完成记录可以如实保留，但不能因此取得完整验收通过；也不要求仅为了消除悬空记录而继续发送已取消的请求。

失败输出不进入有效历史，不意味着失败消耗不存在。提供方已经上报的失败用量仍按实际尝试保存并去重累计；成功尝试同样计入。未收到用量标为未上报，不能填零或推断不收费。只读用量不重新成为任务预算或重试条件。

提供方已经返回完整成功响应后，工具、工件、数据库或提交失败应按对应主机失败处理，不能归为可重试网络错误而重发模型。客户端至多一次执行工具不等于提供方只计算或只计费一次；断线时远端是否已处理可能未知。

## 4. 错误与等待的必要细化

| 情况 | 建议口径 |
| --- | --- |
| 临时连接中断、TLS EOF、读取超时或没有终态的传输中断 | 在尝试及步骤限制内重试；每次保留独立事实 |
| 正常长响应 | 沿用当前配置的单次等待，不能因超过一分钟额外中止 |
| 401/403、参数错误、上下文容量、模型或协议内容错误 | 明确停止，不靠相同请求反复尝试 |
| 429 临时限流、临时服务器过载 | 读取明确原因和有效 Retry-After，并受有界等待约束 |
| 429 余额、支出或配额耗尽 | 不能靠退避恢复访问，不按临时限流重试 |
| 证书验证失败、固定认证或配置错误 | 与间歇 TLS EOF 分开，不因同属 APIConnectionError 就一律重试 |
| Retry-After 超过允许等待范围 | 明确说明超出本次等待策略并停止；不将其截短后提前请求服务 |

首批不因其他状态码“看起来可能临时”就无依据扩展白名单；兼容服务未提供明确错误语义时，保留未知分类与有限停止。异常正文和请求头不直接展示，诊断只保存需要的类型、状态与已校验的错误码，不泄漏密钥。

OpenAI 官方 [Error codes](https://developers.openai.com/api/docs/guides/error-codes) 已实际打开阅读：明确区分临时限流与余额/支出/配额类 429，后者重试不会恢复访问；超时、临时服务器错误可短暂等待后再试。该文档不规定 Yudao 的事件结构、步骤预算或 penguinapi.org 的全部行为。SDK 流迭代的内部重试细节以对应安装版本源码为准，本文不以搜索摘要证明该实现。

## 5. 当前事件对接与待核验项

最新主树已在 `ModelRequest`、失败与重试计划事件中采用 `attempt / root_step_id / retry_of_step_id`，等待采用 `delay_sec`；smoke 和 Web 查询也已读取这套字段。本文据实际实施更新，上一版建议的失败事件 ID 关联与毫秒单位不再作为对接要求。保持一个清楚的合同即可，不因不同字段命名重新改造已对齐的结构。

Web 可以直接从已有事件计算重试状态，不必增加独立可写状态。应区分请求中、退避中和终止；首个部分 MODEL_MESSAGE 不清除尚在进行的尝试，最终成功、取消、新输入转交和失败耗尽的状态必须与控制层一致。

以下是当前对接口径及需要补齐的要求，不是 H 批次已经验收通过的证明：

| 项目 | 统一含义 |
| --- | --- |
| 实际尝试 | 以 `MODEL_REQUESTED` 为客户端发起尝试的记录，按 `(activation_id, step_id)` 唯一关联已装配输入；它不证明提供方已经收到或成功处理 |
| `attempt` | 同一逻辑请求的尝试序号，从 1 开始，最大 3；失败事件及紧随的计划事件均记录触发重试的失败尝试序号，计划中的下一次请求使用 `attempt + 1` |
| `retry_of_step_id` | 首次请求为 `null`，重试请求指向同一激活中前一次失败的步骤；失败和计划事件携带它们所属请求的该字段 |
| `next_step_id` | 只用于重试计划，表示待发的目标步骤；对应实际请求出现前不增加实际调用计数 |
| `root_step_id` | 同一逻辑请求第一次尝试的步骤，在重试链中保持不变；连同激活身份验证，不能仅凭一个整数跨激活关联 |
| `max_attempts` | 失败与重试计划事件显式记录 `3`，审计验证字段存在且等于当前上限，不能靠默认值掩盖生产端遗漏 |
| 等待 | 统一使用 `delay_sec`；不增加毫秒字段的兼容读取 |
| 数量 | `attempt_count` 只统计已记录的实际尝试；`retry_count` 只统计其中 `attempt > 1` 的尝试；`prepared_count` 按装配记录单列，不能把已准备未发送的重试计为调用 |

装配事件仍核验实际输入及来源，并按重试计划的目标步骤关联；元数据若写入装配事件，应在持久化前准备完毕，不事后补写不可变事件。计划事件的 `step_id` 指触发它的失败步骤，`next_step_id` 与 `next_attempt` 才指下一次待发请求。不能仅凭重试计划就认定请求已发出；已统一步骤关联后，审计里残留的旧 `retry_of` 兼容判断应移除。

Web 现有 `projection.request_count` 表示部门间协作请求，模型尝试统计不能覆盖其含义。模型尝试、模型重试和上下文准备使用明确的独立统计；准备数直接来自装配记录，不能在异常记录中用最大步骤编号推测数量。查询层提供一致的展示数据，前端不从事件序号猜测尝试次数。

本次读取时，`_record_attempt_failed` 和 `_record_retry_scheduled` 尚未写入 `max_attempts`，smoke 使用缺失时默认 `3` 的读取。应补生产事件和缺字段反例；显示默认值不能替代审计证据。

`engine.RETRY_BUDGET_SEC = 1805.0` 当前参与是否重试的判断，是额外的逻辑请求总耗时限制，并非单次请求超时。单次超时可配置时，这个固定限制可能提前拒绝尚未耗尽的尝试。按当前 D17 边界清理这一额外停止条件，沿用最多 3 次、每次激活 32 次、单次超时和有界退避；无需引入新的总时限配置。

## 6. 验收证据

1. 首次连接失败或临时 503 后成功，实际调用数量准确，成功回合只进入一次部门历史、工具只执行一次。
2. 已产生部分输出后断流，重试成功；失败内容仍可审计，但不进入下一次请求、工具回合或摘要。
3. 重试耗尽时明确失败；压缩调用遵守相同规则，失败摘要不能被当作新检查点。
4. 失败尝试已上报用量、未上报用量及成功用量分别核对，不能漏记或重复累计。
5. 等待中取消、新输入到达、请求开始边界交错时，不能发起过时尝试；第 32 次调用后不再发起下一次。
6. 永久错误和不同 429 原因分类正确；有效等待、过长等待及取消使用可控时间验证，正常一分钟级响应不误失败。
7. 模型成功后的主机提交失败不重发模型；缺少成功结束证据的 partial 不能在历史、审计或 Web 冒充完整成功。
8. 旧请求的迟到消息及用量仍归原尝试；最终部门记录、下一次有效历史和压缩来源均不会误采用失败片段。仅装配未发出、已安排后取消及进程中断的情况能准确区分。
9. 固定条件通过后，在新目录用当前 provider 完成真实 Web 方向调整和真实小窗至最终 QA，保留新旧策略及失败尝试，不能覆盖旧 run。

重试增强与 [第一阶段独立验收](../stage-1-acceptance-2026-09-06.md) 中确认的“封存损坏仍可放行”分别验收。重试成功不能消除该 P2，封存修复也不能替代真实完整流程成功。
