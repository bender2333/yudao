## 1. 结论

文档一致性分成两条线，按**事实的种类**分，各有自己的目标、规则、命令和验收，可以单独开关：

- **规则事实线（新，先做）**：管给 LLM 读的规则文件。谁加标签、谁写证据、什么算交回理由、谁有什么权限。正本表格里写一次，别处引用或用句式复述，工具比对。
- **图谱与概念线（已有的部分加设计线）**：索引、死引用、待核对、阅读范围，和以后的概念模型与取值比较。

第一步只读、不改文档：把 `workflow.md` 与验收证据规则的正本表格读成事实，在 main 上数出要迁移的句子。

## 2. 两条线怎么分

原来按文件分「设计线」和「脚手架线」（方案第 1 节）。现在改按事实分：脚手架线里确定性的那半（死引用、待核对、阅读范围）归图谱线；原来写着「矛盾主要在文字里，判断仍靠读」的那半，归规则事实线。设计线不动，归图谱与概念线。

| | 规则事实线 | 图谱与概念线 |
| --- | --- | --- |
| 目标 | 同一条规则只有一个出处；复述与出处一致；同一角色读到的规则唯一 | 引用不失效；上游改了下游被提醒；设计文档复述的取值与总图一致 |
| 管的事实 | 谁做、谁加、谁写、谁给；是不是某个清单的一员；谁有权限；冲突时以哪份为准、守不守某类文件（比如这里让守 ADR、那里让走新规则） | 文件、小节、边、hash；以后加概念、取值、代码事实 |
| 正本 | `workflow.md` 第 4、5、7 节与权限表，`acceptance-evidence.md` 证据表 | 总图、`CONTEXT.md`、对照表 |
| 范围 | 脚手架文件：`CLAUDE.md`、`AGENTS.md`、`docs/agents/**`、`.claude/skills/**` | 全仓 `.md`、`.html`（现有范围） |
| 写法约束 | 有：引用或五种句式 | 只有「数字加量词」，以后加词条结构块 |
| 读 `.doc-index/` 吗 | 不读，直接读文件 | 读写 |
| 依赖概念模型吗 | 不依赖 | 设计线依赖 |
| LLM | 不用 | 定向提取另行验证 |
| 状态 | 没建 | 第 1、2 步已合入 |

两条线共用的只有三样：Markdown 解析库（markdown-it-py）、clingo、脚手架文件的范围清单。代码、规则、数据、命令、测试、提醒钩子都分开：

| | 规则事实线 | 图谱与概念线 |
| --- | --- | --- |
| 代码 | `doc_consistency/rulefacts/` | 现有模块 |
| 规则 | `rules/rulefacts/*.lp` | `rules/*.lp` |
| 数据 | `data/canon.json`（正本表格与列的性质）、`data/patterns.json`（句式） | 现有 `data/*.json` |
| 结果 | `.doc-index/rulefacts/`（基线与确认，只追加） | 现有 `.doc-index/` |
| 命令 | `doc-consistency rules <子命令>` | 现有命令不变 |
| 测试 | `tests/rulefacts/` | 现有 |
| 钩子 | 单独一个入口 | 以后接 |

规则事实线不读索引，所以图谱线的口径怎么改（比如 11-02 收窄待核对）都不影响它；关掉其中一条，另一条照常跑。

### 固定句式只管第一条线

两条线对写法的要求不同，这是分开的主要理由：

- **规则文件是给 LLM 的 prompt**。它的内容本来就是一条条「谁在什么时候做什么、以什么为准」，词汇封闭（角色、标签、前缀、文件种类），几种句式就能写全，句式不会损失表达力。
- **设计与代码要表达的东西多得多**：结构、数据流、取值、约束、为什么。硬套几种句式写不全，所以第二条线不约束正文写法，靠概念模型（`CONTEXT.md` 词条结构块）、总图的结构和代码事实，只把能读成事实的那部分（数目、名字、状态、阶段、代码名）拿来比。

### clingo、Z3 与形式化证明放在哪

- 两条线判断矛盾都用 clingo。它是封闭世界的逻辑程序：没写的就当没有，能一次列出全部矛盾，同样的输入同样的结果。第一条线的五类结论和「以谁为准」的成环都是它最擅长的有限关系推理。
- 「证明」只对写进模型的事实成立，模型以外的东西证明不了。所以这里的结论是「这些事实之间没有矛盾」，不说「文档是对的」。
- Z3 管的是数值与约束的可满足性（比如参数之间的不等式），只在第二条线出现多变量的取值约束时才用，方案第 12 节已经这样定。第一条线用不到。

## 3. 规则事实线

### 3.1 正本：每条事实只归一张表的一列

`data/canon.json` 写清哪张表的哪一列是哪种事实、单值还是多值、值从哪个词表来。文档里一个字不加。

```json
{
  "tables": {
    "docs/agents/workflow.md#4. 状态与标签 > 表1": {
      "key": "状态",
      "columns": {"谁改成它": {"fact": "由谁改成", "many": true, "vocab": "角色"}}
    },
    "docs/agents/workflow.md#5. 证据评论 > 表1": {
      "key": "前缀",
      "columns": {"谁写": {"fact": "由谁写", "many": true, "vocab": "角色"}}
    },
    "docs/agents/workflow.md#7. 出问题往哪交 > 表1": {
      "key": "卡在",
      "columns": {"交给": {"fact": "交给", "many": true, "vocab": "角色"}}
    }
  }
}
```

**现成的一处要先定归属**：`needs-triage` 的交回理由在 `workflow.md` 里写了两次。第 4 节状态表写「设计问题、规则矛盾、验收做不到、冲突两边都丢行为、连续三轮没过；新报告的问题」，第 7 节「卡在」写「设计、规则矛盾、验收做不到、连续三轮没过」，少了「冲突两边都丢行为」，用词也不同（「设计问题」对「设计」）。同一个正本里一条事实有两处出处，这条线第一个要报的就是它。理由清单归哪一张表，由总架构师或 用户 定；另一处改成引用。

### 3.2 句式

正本以外，规则事实只能这样写：

| 句式 | 例子 | 读成 |
| --- | --- | --- |
| 引用 | `` `needs-triage` 谁改成它，见 `docs/agents/workflow.md`「状态与标签」 `` | 只查出处在不在 |
| 由谁 | `` `needs-triage` 由执行者加上 `` | `says(键,由谁改成,执行者)` |
| 只由谁 | `` `needs-architect` 只由派发者加上 `` | 再加 `only(...)` |
| 谁不 | `` 架构师循环不加 `needs-architect` `` | `says_not(...)` |
| 是或不是清单一员 | `` 文件超上限不是 `needs-triage` 的理由 `` | `member` / `not_member` |
| 以谁为准 | 设计说明与 ADR 冲突时以设计说明为准 | `prevails(节点,设计说明,ADR)` |

角色只能写 `workflow.md` 角色表里的名字和 `data/roles.json` 的别名；键只能是正本表格的首列；清单条目只能是正本那一格里的条目名。句式用 Lark 写成一份文法文件（共同规则第 5 条：用成熟库，不手写解析）。

### 3.3 规则

```
canon(K,F,V) :- cell(T,K,F,V), canon_table(T).
% 一条事实只归一处
dup_canon(K,F,T1,T2) :- cell(T1,K,F,_), cell(T2,K,F,_), T1 < T2.
% 复述多说了正本没有的值
extra(N,K,F,V) :- says(N,K,F,V), not canon(K,F,V).
% 说「只由」，正本里还有别人
only_wrong(N,K,F,V) :- only(N,K,F,_), canon(K,F,V), not only(N,K,F,V).
% 说「不」，正本里有
denied(N,K,F,V) :- says_not(N,K,F,V), canon(K,F,V).
% 说不是理由，正本里是
not_member_wrong(N,K,X) :- not_member(N,K,X), canon(K,理由,X).
% 两处说的「以谁为准」方向相反，或者绕成一圈
above(A,B) :- prevails(_,A,B).
above(A,C) :- above(A,B), above(B,C).
precedence_cycle(A,B) :- above(A,B), above(B,A), A < B.
```

「以谁为准」这一类没有在 10-29 的 46 条里单列，但它就是 用户 说的那种「这里让守 ADR，那里让走新规则，agent 啥也干不成」。它是一张偏序，规则能判方向相反和成环。

多值事实复述时只说一部分，不报。

### 3.4 提醒

粗筛（封闭词表的键加角色加动作词，引导句的命中带到它下面的列表与续行）找出「像在复述规则」的句子。这样的句子既不是引用、也不合句式，就提醒一次，给出它像哪一行正本。只在改动的行里报，存量记成基线。钩子单独一个入口，照 `.claude/hooks/state-doc-dates.mjs` 的做法，不撤回写入；`check` 永远以 0 退出。

## 7. 为什么走这条路：写法评审

开放提取输在主语不封闭，规则分不清单值、多值与范围（概念模型方案第 13 节）。规定写法从源头补这两处：主语只能用封闭词表里的名字，单值多值由正本表格的列声明，文档里不加标记。11-02 不采纳隐藏标记的理由是「标记要作者主动写」；这里作者照句式写的是普通中文，想不起来由钩子提醒，和 11-01「不靠 agent 自己想起来」一致。

### 规则类句子有多少

粗筛口径：一句话里同时有封闭词表的名字、角色名和动作词。窄口径的词表只用标签快照与七个证据前缀，宽口径再加脚手架文件所有表格的首列。数字由评审时的临时脚本得出，脚本没有入库。

| 提交 | 文件 | 句子与表格行 | 窄口径命中（其中表格行） | 宽口径命中（其中表格行） |
| --- | --- | --- | --- | --- |
| 35cc686e（10-29 试验语料） | 33 | 3282 | 76（9） | 280（37） |
| aae86d9c（11-02 的 main） | 35 | 3642 | 62（26） | 243（68） |

11-01 把流程收进 `workflow.md` 以后，落在表格里的变多、散文变少。今天要过一遍的散文在约 36 到 175 句之间，第 2 步实数。T42 两边、T40 的表格一侧、T44 的 4 句粗筛都抓到；T43 的 `AGENTS.md` 一侧是「下面这些不是交回的理由：」引出的一串条目，单句粗筛漏了，所以第 3.4 节要把引导句带到列表。

### 比过的路线

| 路线 | 结论 |
| --- | --- |
| 完整受控语言（Attempto ACE、Grammatical Framework） | 不做：中文没有现成的受控语言，全部规则文件写成受限语法人读不动 |
| 句式模板（EARS 那类样板句） | 采用，作为复述的写法 |
| 正本表格加引用或句式 | 采用，就是本方案 |
| 可见行内字段（Dataview `键:: 值`、Semantic MediaWiki） | 不做：规则文件读起来像配置 |
| 文件头 front matter | 留给图谱与概念线：阶段归属、实施状态、状态行缺字段是「这份文件」的属性 |
| 单一来源，复述由生成产生 | 不做：生成区要起止边界，只能写成注释，等于隐藏标记 |
| 需求追踪工具（sphinx-needs 9.1、StrictDoc 0.30、Doorstop 3.2，都在维护） | 不搬：它们管追溯与审阅，不判断正文矛盾，要换文档格式；「上游变了下游可疑、看过盖章」已是现有的待核对与确认记录 |
| 写作时 lint（Vale、textlint、zhlint） | 用自带的：词表在 `CONTEXT.md` 与共同规则里，外部工具要另抄一份，抄的那份又会走样 |
| 定向提取 | 降成辅助：句式定下以后，LLM 最多帮作者把一句改写成句式；这条线先不用 |
