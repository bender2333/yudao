## 1. 结论

文档一致性分成两条线，按**事实的种类**分，各有自己的目标、规则、命令和验收，可以单独开关：

- **规则事实线（新，先做）**：管给 LLM 读的规则文件。谁加标签、谁写证据、什么算交回理由、谁有什么权限。正本表格里写一次，别处引用或用句式复述，工具比对。
- **图谱与概念线（已有的部分加设计线）**：索引、死引用、待核对、阅读范围，和以后的概念模型与取值比较。

规则事实线保证三件事，给两类人：

- **一致**（给 agent）：同一条规则只有一处正本，复述与正本一致。靠 clingo 比对。
- **完整**（给 agent）：每个角色读到它该读的全部规则。不靠复述，靠正本所在的文件在被点名角色的必读范围里；工具已经算得出必读范围，只差一条规则（第 3.3 节）。`workflow.md` 与验收证据规则是总架构师、子架构师、架构师循环、solo 执行者、审查者五个角色都必读的文件，所以正本放在这两份里，不另开一份。
- **可看**（给用户）：用户不读 clingo 的输出，这条线做得对不对，用户看图判断。图从同一份事实生成，不手画（第 3.5 节）。

第一步只读、不改文档：把 `workflow.md` 与验收证据规则的正本表格读成事实，生成一页图，在 main 上数出要迁移的句子。

## 2. 两条线怎么分

原来按文件分「设计线」和「脚手架线」（方案第 1 节）。现在改按事实分：脚手架线里确定性的那半（死引用、待核对、阅读范围）归图谱线；原来写着「矛盾主要在文字里，判断仍靠读」的那半，归规则事实线。设计线不动，归图谱与概念线。

| | 规则事实线 | 图谱与概念线 |
| --- | --- | --- |
| 目标 | 同一条规则只有一个出处；复述与出处一致；同一角色读到的规则唯一 | 引用不失效；上游改了下游被提醒；设计文档复述的取值与总图一致 |
| 管的事实 | 谁做、谁加、谁写、谁给；是不是某个清单的一员；谁有权限；冲突时以哪份为准、守不守某类文件（比如这里让守 ADR、那里让走新规则） | 文件、小节、边、hash；以后加概念、取值、代码事实 |
| 正本 | `workflow.md` 第 2、4、5、7 节与权限表（含用户的权限），`acceptance-evidence.md` 证据表 | 总图、`CONTEXT.md`、对照表 |
| 范围 | 脚手架文件：`CLAUDE.md`、`AGENTS.md`、`docs/agents/**`、`.claude/skills/**` | 全仓 `.md`、`.html`（现有范围） |
| 写法约束 | 有：引用或五种句式 | 只有「数字加量词」，以后加词条结构块 |
| 读 `.doc-index/` 吗 | 不读，直接读文件 | 读写 |
| 依赖概念模型吗 | 不依赖 | 设计线依赖 |
| LLM | 不用 | 定向提取另行验证 |
| 状态 | 没建 | 第 1、2 步已合入 |

两条线共用的只有三样：Markdown 解析库（markdown-it-py）、clingo、脚手架文件的范围清单。代码、规则、数据、命令、测试、提醒钩子都分开：

| | 规则事实线 | 图谱与概念线 |
| --- | --- | --- |
| 代码 | `doc_consistency/rulefacts/` | 现有模块 |
| 规则 | `rules/rulefacts/*.lp` | `rules/*.lp` |
| 数据 | `data/canon.json`（正本表格与列的性质）、`data/patterns.json`（句式） | 现有 `data/*.json` |
| 结果 | `.doc-index/rulefacts/`（基线与确认，只追加） | 现有 `.doc-index/` |
| 命令 | `doc-consistency rules <子命令>` | 现有命令不变 |
| 测试 | `tests/rulefacts/` | 现有 |
| 钩子 | 单独一个入口 | 以后接 |

规则事实线不读索引，所以图谱线的口径怎么改（比如 11-02 收窄待核对）都不影响它；关掉其中一条，另一条照常跑。

### 固定句式只管第一条线

两条线对写法的要求不同，这是分开的主要理由：

- **规则文件是给 LLM 的 prompt**。它的内容本来就是一条条「谁在什么时候做什么、以什么为准」，词汇封闭（角色、标签、前缀、文件种类），几种句式就能写全，句式不会损失表达力。
- **设计与代码要表达的东西多得多**：结构、数据流、取值、约束、为什么。硬套几种句式写不全，所以第二条线不约束正文写法，靠概念模型（`CONTEXT.md` 词条结构块）、总图的结构和代码事实，只把能读成事实的那部分（数目、名字、状态、阶段、代码名）拿来比。

### clingo、Z3 与形式化证明放在哪

- 两条线判断矛盾都用 clingo。它是封闭世界的逻辑程序：没写的就当没有，能一次列出全部矛盾，同样的输入同样的结果。第一条线的五类结论和「以谁为准」的成环都是它最擅长的有限关系推理。
- 「证明」只对写进模型的事实成立，模型以外的东西证明不了。所以这里的结论是「这些事实之间没有矛盾」，不说「文档是对的」。
- Z3 管的是数值与约束的可满足性（比如参数之间的不等式），只在第二条线出现多变量的取值约束时才用，方案第 12 节已经这样定。第一条线用不到。

## 3. 规则事实线

### 3.1 正本：每条事实只归一张表的一列

`data/canon.json` 写清哪张表的哪一列是哪种事实、单值还是多值、值从哪个词表来。文档里一个字不加。

```json
{
  "tables": {
    "docs/agents/workflow.md#4. 状态与标签 > 表1": {
      "key": "状态",
      "columns": {"谁改成它": {"fact": "由谁改成", "many": true, "vocab": "角色"}}
    },
    "docs/agents/workflow.md#5. 证据评论 > 表1": {
      "key": "前缀",
      "columns": {"谁写": {"fact": "由谁写", "many": true, "vocab": "角色"}}
    },
    "docs/agents/workflow.md#7. 出问题往哪交 > 表1": {
      "key": "卡在",
      "columns": {"交给": {"fact": "交给", "many": true, "vocab": "角色"}}
    },
    "docs/agents/acceptance-evidence.md#1. 记录身份与结论 > 表1": {
      "key": "结论",
      "columns": {"负责角色": {"fact": "由谁负责", "many": true, "vocab": "角色"}}
    },
    "docs/agents/workflow.md#2. 角色 > 表1": {
      "key": "角色",
      "columns": {"做什么": {"fact": "做", "many": true, "vocab": "事", "open": true},
                  "不做什么": {"fact": "不做", "many": true, "vocab": "事", "open": true}}
    },
    "docs/agents/workflow.md#6. 四个循环 > 权限表": {
      "key": "事",
      "columns": {"用户在场": {"fact": "在场可否", "many": false, "vocab": "可否"},
                  "用户不在场（架构师循环）": {"fact": "不在场可否", "many": false, "vocab": "可否"}}
    }
  },
  "vocab": {
    "载体": ["总图", "基础规则", "设计说明", "ADR", "需求记录", "术语表", "CLAUDE.md", "AGENTS.md", "共同规则", "工作方式", "工单规范", "验收证据规则", "技能", "工单正文"]
  }
}
```

表的键写工具的节点名（`doc-consistency nodes 状态与标签` 能查到）。词表有三类：角色（`workflow.md` 角色表加 `data/roles.json` 的别名与合称）、键（正本表格的首列）、载体（「以谁为准」的对象是规则的载体，不在任何正本表的首列里，所以在 `canon.json` 单独登记）。

第 1 节「事实放在哪」表的「谁改」一列也是正本（由谁改），复述里「只由总架构师改总图」这类句子和它比。

用户的权限也是正本事实，而且是最要紧的一类：「只由用户修改基础规则」「用户不逐张批工单」「不审也不合 PR」划的是 agent 不经用户能做到哪里。它们的正本是角色表（第 2 节）的「做什么」「不做什么」两列，读成「做」「不做」，与权限表（第 6 节用户在场与不在场）的两列，读成「在场可否」「不在场可否」。做与不做的对象是「事」，这份词表现在没封闭：第 1 步先把表里的短语原样列出来，第 5 步随写法约定一起封闭。封闭时动词分三类：定（决定）、确认（放行）、改（动手：改、建、删、写、推送、合并）。用户不亲手改代码、规则与文件，只与角色沟通、让角色去改，所以用户的事实只有「定」与「确认」两种；规则里写用户改、建、删、写的，都是走样，第 3 步作为一类矛盾报出。例子：`CLAUDE.md` 写基础规则「只由用户修改」，真实的流程是用户定意图、架构师改（在场告诉用户，不在场记录），第二层自举不碰，这正是权限表那两行，所以那句该写成「意图只由用户定」加引用权限表。用户不读规则文件（看总图与对照表），完整性那条规则不对用户算；矩阵里用户一列只标点名。

格子怎么读成事实：「架构师」是总架构师、子架构师、架构师循环三者的合称，「任何角色」是角色表里的全部角色，都登记在 `data/roles.json`，读的时候展开成各个角色；一格里用「或」「、」「与」分开的是多个值；括号里的话与「领取时」「之前」这类限定不进事实，当附注单独列出来给人看。读不出来的格子原样报出，不猜。

**现成的一处要先定归属**：`needs-triage` 的交回理由在 `workflow.md` 里写了两次。第 4 节状态表写「设计问题、规则矛盾、验收做不到、冲突两边都丢行为、连续三轮没过；新报告的问题」，第 7 节「卡在」写「设计、规则矛盾、验收做不到、连续三轮没过」，少了「冲突两边都丢行为」，用词也不同（「设计问题」对「设计」）。同一个正本里一条事实有两处出处，这条线第一个要报的就是它。理由清单归第 4 节状态表：标签的意思就是它的触发条件，第 7 节是路由表，管交给谁、怎么交。第 7 节那一格与 `AGENTS.md`「请架构师处理」的四种情形到第 5、6 步改成引用或句式。

### 3.2 句式

正本以外，规则事实只能这样写：

| 句式 | 例子 | 读成 |
| --- | --- | --- |
| 引用 | `` `needs-triage` 谁改成它，见 `docs/agents/workflow.md`「状态与标签」 `` | 只查出处在不在 |
| 由谁 | `` `needs-triage` 由执行者加上 `` | `says(键,由谁改成,执行者)` |
| 只由谁 | `` `needs-architect` 只由派发者加上 `` | 再加 `only(...)` |
| 谁不 | `` 架构师循环不加 `needs-architect` `` | `says_not(...)` |
| 是或不是清单一员 | `` 文件超上限不是 `needs-triage` 的理由 `` | `member` / `not_member` |
| 以谁为准 | 设计说明与 ADR 冲突时以设计说明为准 | `prevails(节点,设计说明,ADR)` |

| 在场可否 | 用户在场时总架构师可以改意图 | `may(节点,角色,事,在场)` |
| 交给 | 执行环境的问题交给用户 | `handoff(节点,卡在项,角色)` |
| 穷尽清单 | 只有设计问题、规则矛盾、验收做不到、连续三轮没过是 `needs-triage` 的理由 | `only_members(节点,键,{…})` |

后三种是第 2 步盘点补的：权限表的复本、路由的复本、「只有四种情形」这类清单，五种句式写不出。

写法的几条约束：主语必须写出来，「不自己加方框」「你」这样的祈使句不算句式；「在场」「之前」这类限定进附注，不进事实；「以 X 为准」只认载体词表里的 X（规则的载体），「以账本为准」「以 main 的现状为准」这类数据与运行状态的优先级是流程，不进这条线；陈述加指路的句子（「阶段工单由总架构师建，模板见某某」）按句式比对，引用只免除纯指路的句子。「规则」一词两义：系统里的规则登记（复盘与试用产生的提议，由用户定）与开发流程的规则文件，词表里分开写。被点名的执行者不只是角色：CI、脚本、钩子登记成「机器」，能被点名，没有阅读范围。

角色只能写 `workflow.md` 角色表里的名字和 `data/roles.json` 的别名与合称；键只能是正本表格的首列；清单条目只能是正本那一格里的条目名。句式用 Lark 写成一份文法文件（共同规则第 5 条：用成熟库，不手写解析）。

### 3.3 规则

```
canon(K,F,V) :- cell(T,K,F,V), canon_table(T).
% 一条事实只归一处
dup_canon(K,F,T1,T2) :- cell(T1,K,F,_), cell(T2,K,F,_), T1 < T2.
% 复述多说了正本没有的值
extra(N,K,F,V) :- says(N,K,F,V), not canon(K,F,V).
% 说「只由」，正本里还有别人
only_wrong(N,K,F,V) :- only(N,K,F,_), canon(K,F,V), not only(N,K,F,V).
% 说「不」，正本里有
denied(N,K,F,V) :- says_not(N,K,F,V), canon(K,F,V).
% 说不是理由，正本里是
not_member_wrong(N,K,X) :- not_member(N,K,X), canon(K,理由,X).
% 两处说的「以谁为准」方向相反，或者绕成一圈
above(A,B) :- prevails(_,A,B).
above(A,C) :- above(A,B), above(B,C).
precedence_cycle(A,B) :- above(A,B), above(B,A), A < B.
```

合称在比对前展开：复述写「由架构师」就是三条 `says`，正本只有总架构师时，另两个按 `extra` 报出；正本写「架构师」而复述只写「由总架构师」，是多值只说一部分，不报。

完整性，用阅读范围规则算出的 `reads(角色,文件)`：

```
% 正本点名的角色读不到正本所在的文件
unreachable(R,T) :- canon_table(T), in_file(T,F), named(T,R), role(R), not reads(R,F).
```

`named(T,R)`：表 T 的角色列里出现了角色 R。

「以谁为准」这一类没有在 10-29 的 46 条里单列，但它就是 用户 说的那种「这里让守 ADR，那里让走新规则，agent 啥也干不成」。它是一张偏序，规则能判方向相反和成环。

多值事实复述时只说一部分，不报。

## 6. 已定与待定

已定（2026-11-03，用户）：

1. 正本以外允许用固定句式复述。规则文件是 agent 一次读完照做的，处处跳去正本会断；句式是普通中文，又能比对。
2. `needs-triage` 的理由清单归第 4 节状态表，第 7 节与 `AGENTS.md` 改成引用或句式。
3. 钩子的提醒和图谱线的提醒分开输出，各自能关。
4. 可视化提前到第 1 步，从同一份事实生成，不手画。
5. 「以谁为准」的对象是规则载体，在词表里单独登记；合称在比对前展开，复述比正本多出来的角色按 `extra` 报。

待定：

1. 第 5 步的正本形状：「事 × 角色」权限表当谁做什么的正本，角色表改成复述；「事」的词表从第 2、3 步的候选句里收，由用户定（这是规则）。
2. 设计文档里也有规则事实时（比如测试分层设计说明说谁跑集成层），进不进这条线。第 6 步以后再看，先只管脚手架文件。

## 7. 为什么走这条路：写法评审

开放提取输在主语不封闭，规则分不清单值、多值与范围（概念模型方案第 13 节）。规定写法从源头补这两处：主语只能用封闭词表里的名字，单值多值由正本表格的列声明，文档里不加标记。11-02 不采纳隐藏标记的理由是「标记要作者主动写」；这里作者照句式写的是普通中文，想不起来由钩子提醒，和 11-01「不靠 agent 自己想起来」一致。

### 规则类句子有多少

第 2 步 `rules scan` 在 2026-11-03 的分支上实数（35 个脚手架文件，3443 个句子，表格一格一句，正本表格的行不算）：

| 项 | 数 |
| --- | --- |
| 候选（一句里同时有键、角色与动作词） | 312，其中表格格子 81、代码块 10、靠引导句带条目才命中 23 |
| 已是引用 | 8（纯指路 3，陈述加指路 4，错分 1） |
| 能改成句式 | 52 |
| 不是规则事实 | 252 |
| 窄口径（只认标签快照与证据前缀） | 49 |
| 抽样 40 条人工核对 | 规则事实 23，噪音 17：噪音率 42.5%（区间约 27% 到 58%）；23 条里五种句式能写 19 条，覆盖 82.6% |
| 漏筛探针：不是候选但合句式形状 | 49（由谁 26、以谁为准 18、只由谁 3、谁不 2），主语不是角色（CI、脚本）或「以 X 为准」的 X 是数据 |

迁移量约 180 条（区间 130 到 230）。

第 3 步 `rules check` 在同一天的分支上：候选 368 条（补漏后），解析成功只有 4 句，矛盾 2 条（都是 `AGENTS.md`「只有四种情形交回」与第 4、7 节理由清单逐字不同：条目用词不同，又少「连续三轮没过」）。第 2 步抽样里按正则分到「能改成句式」的 10 条，真文法一句也解析不了：6 条的键不在词表里（「缝的已定、未定」「处理工单」「守着这些行为的用例」），2 条缺主语，2 条动词不在映射里。结论：文法与规则立住了，瓶颈在键的词表。真实规则大多以「事」为键（谁可以改什么、谁不做什么），这类事实的正本现在是角色表的两列散文、词表没封闭，所以第 5 步要做的不只是写法约定，还要给「事」一张正本：「事 × 角色」的权限表（行是事，列是谁可以、只由谁、谁不），角色表改成它的复述。迁移量因此更依赖先补正本与词表，不是逐句改写。粗筛的噪音不大，弱点有两处：三类分法里「不是规则事实」一类的召回差（23 条规则事实只有 10 条被分到「能改成句式」）；主语不是角色的句子漏掉一半。五种句式写不出的四条是权限表与路由的复本，所以加了第 3.2 节后三种句式。11-02 的临时脚本数字（窄 62、宽 243）口径不同，不可直接比。

### 比过的路线

| 路线 | 结论 |
| --- | --- |
| 完整受控语言（Attempto ACE、Grammatical Framework） | 不做：中文没有现成的受控语言，全部规则文件写成受限语法人读不动 |
| 句式模板（EARS 那类样板句） | 采用，作为复述的写法 |
| 正本表格加引用或句式 | 采用，就是本方案 |
| 可见行内字段（Dataview `键:: 值`、Semantic MediaWiki） | 不做：规则文件读起来像配置 |
| 文件头 front matter | 留给图谱与概念线：阶段归属、实施状态、状态行缺字段是「这份文件」的属性 |
| 单一来源，复述由生成产生 | 不做：生成区要起止边界，只能写成注释，等于隐藏标记 |
| 需求追踪工具（sphinx-needs 9.1、StrictDoc 0.30、Doorstop 3.2，都在维护） | 不搬：它们管追溯与审阅，不判断正文矛盾，要换文档格式；「上游变了下游可疑、看过盖章」已是现有的待核对与确认记录 |
| 写作时 lint（Vale、textlint、zhlint） | 用自带的：词表在 `CONTEXT.md` 与共同规则里，外部工具要另抄一份，抄的那份又会走样 |
| 定向提取 | 降成辅助：句式定下以后，LLM 最多帮作者把一句改写成句式；这条线先不用 |
