## 1. 结论

**这份本体为两件事服务**（用户 2026-11-03 说明）：

1. **按规格查一致**：总图完整映射到代码和测试，查出没映射到的、映射错的，也查出总图自己内部的缺口与矛盾。第 3 至 5 节、第 8 节讲这一件。
2. **给 agent 装上下文**：在本体上长出来的语义网络（知识图谱）替 agent 挑上下文，因为光靠记忆和 RAG 不够。第 6 节讲这一件。

两件事读同一份事实。第一件保证图是对的，第二件用这张图；图里的关系错了，第二件就会给 agent 装错东西。所以第一件也是第二件的质量保证，不是两套工程。

把 Yudao 的本体按 MOF 的元层次分开，写法一份，内容分层：

| 层 | 是什么 | Yudao 里对应 | 正本 |
| --- | --- | --- | --- |
| M3 写法 | 怎么写一个本体：种类、关系、属性单值或多值、层、状态 | 规则事实线 `canon.json` 的列声明；概念线计划的「词条结构块」字段表 | 工具里的一份元规则，用自己的格式描述自己 |
| M2 Yudao 本体 | 软件工程本体：事项、事件、提案、回执、一轮工作、轮转方式、核验角色、部门、角色、形态；从意图、需求、总图、设计说明到模块、代码名、测试、守卫的整条链；产品工件（模块、接口、页面）；领域建模的元概念 | `CONTEXT.md` + 总图 + `harness/definitions/` 的格式 + 语义系统第 5 节 + 规则事实线的词表 | 和规则事实线重叠的概念以 `canon.json`、`roles.json` 为正本，不另抄一份；其余概念哪条规则要用才加（第 10 节第 1 条，已定 C） |
| M1 产品领域模型 | 一个产品自己的概念，比如笔记本的「笔记、笔记本、标签」，按 DDD 写成限界上下文、聚合、实体、值对象、领域事件、不变量 | 今天只有 ProductSpec 里的「术语」实体 | 产品部门在 ProductSpec 里定义 |
| M0 事实 | 运行中的具体东西：这个事项、这条事件、这份定义里的「质检」部门 | 事件库、定义 JSON 里的实例 | 事实 |

表示用 clingo 事实，不上 OWL：闭世界（没写就算没有）正是两条一致性线都依赖的。检查分四类：本体自检、实例符合、分层、演化只增；跨设计、代码、测试再加一组链上的检查（第 5.2 节）。

代码与测试也在同一份模型里，不另起一套：它们的事实大多已经有正本，对照表、测试分层登记表、导入方向合同、内核清单，只是各管一块、没连起来。连起来以后，`seam-diff` 技能里靠人检索的几步就变成规则。

自举的关键一句：**Yudao 开发 Yudao 时，产品「Yudao」的领域模型就是 Yudao 本体本身。** 所以 M3 写法只要一份，检查 Yudao 文档的工具，和以后语义系统为任何产品检查领域模型的能力，是同一件事的两个用法。

## 1.1 业界怎么做，这份方案在哪

用户 2026-11-03 问：最初的目的是让架构一路一致到代码和测试，这样想是不是太窄，业界有没有更好的做法。业界把这件事拆成几类工具，各管一段：

| 做法 | 代表 | 管什么 | Yudao 里已有的对应 |
| --- | --- | --- | --- |
| 反射模型（reflexion model） | Murphy、Notkin、Sullivan 1995；SAVE | 人写高层模型，再写高层模型到源码的映射，工具从源码算出依赖，报出一致、背离、缺失三类 | 对照表就是映射，`seam-diff` 就是手工算的反射模型 |
| 代码查询语言与代码事实库 | CodeQL（.QL，Datalog 语义）、Meta 的 Glean（带 schema 的代码事实，逻辑查询语言 Angle）、jQAssistant（代码扫进 Neo4j，规则写成 Cypher，查到东西就让构建失败） | 把代码变成可查询的事实，规则写成查询 | CodeGraph 索引；ast 现算的事实；clingo |
| 架构规则写成测试 | ArchUnit（Java）、import-linter（Python） | 导入方向、分层、命名 | 5 条 import-linter 合同、`test_thin_driver_names.py`、`test_layers.py` |
| 依赖结构矩阵 | Lattix | 模块之间的依赖矩阵，看分层有没有被打穿 | 没有 |
| 可追踪模型 | Eclipse Capra（可以自定义追踪元模型，例子里的链接种类就是「实现」「测试」）；功能安全领域要求需求、设计、代码、测试双向可追踪 | 需求 → 设计 → 代码 → 测试的链，查断链与没覆盖 | 语义系统的要求链（细化、实现、验证），只给产品设计、没给 Yudao 自己 |
| 模型驱动、代码生成 | MOF、EMF | 模型是正本，代码从模型生成 | 不走这条路：代码由 agent 写，模型用来查，不用来生成 |

Passos 等 2010 年比较了反射模型、依赖结构矩阵与代码查询语言三类静态做法：推荐反射模型做系统化的架构一致性检查，代码查询语言表达力最高；也写明任何一种静态做法都查不出全部违例。

**定位**：用户的想法不窄。它正好是上表前五类的合并：反射模型（总图对代码）加可追踪（需求到测试）加规则（clingo），放在同一套概念和同一个闭世界里。业界通常是几样工具各管一段，词汇互不相通。这份方案多出来的有三点：

1. 一套词汇管到底：脚手架规则、设计文档、代码、测试用同一份概念与关系，不是每个工具一份。
2. 自举：同一套写法和规则以后由语义系统给产品用，产品的代码与测试按同样的方式查。
3. 本体可以演化，演化本身也能查（「只增」规则），这一点业界的架构检查工具一般不管。

**比它更宽的方向有两个，都不建议现在做**：

- **行为**：上面都是静态的。业界在静态检查之外还看运行时：按测试记的覆盖、调用 trace。仓库的[游戏世界调研](game-world-as-projection.md)第 4 节已经把代码的本体分成机器、语义、行为、模型四种，这份方案管的是语义与模型；行为的事实（检查回执、测试结果、事件日志）Yudao 本来就有，以后可以按同一套概念接进来，见第 10 节第 6 条。
- **生成**：模型驱动从模型生成代码。Yudao 的执行者是 agent，模型拿来查比拿来生成合适，这一条倾向不做。

更大的风险是反方向：一开始就建得太宽。所以仍按「哪条规则要用才加哪个概念」长。

## 3. Yudao 本体里装什么

### 3.1 分层照总图的「四层」

总图第二节已经给了本体的骨架：事实与裁决只认事项、事件、成果的某一版及其依据、提案、回执、写入范围、上限与决定请求；循环只认一轮工作；路由写轮转的规矩，核验从核验角色取；组织（定义）往里填部门与角色。总图的判据是「任何一种要改上面两层，就是抽象没立住」。

这句话本身就是一条本体规则：**上层的代码和文档不许点名下层概念的实例。** 部门是组织层的概念，「产品、工程、质检」是部门的实例，住在定义里。10-30 架构排查的根因（核心写死部门名）就是破了这一条。

所以每个概念至少要标两件事：

- **层**：事实与裁决、循环、路由、组织。另外标三环（可重写、只向后兼容、只由用户批准），演化规则要用。脚手架的概念标「脚手架」，表示它在 Yudao 之外、给开发 Yudao 的 agent 用。
- **是概念还是实例**：「部门」是概念，「质检」是实例。实例只能出现在定义和它所在层以下。

### 3.2 借 Essence 的「内核加实践」

OMG Essence（SEMAT）是最接近「软件工程本体」的标准。它有一个所有软件工作都有的内核，七个 alpha：机会、利益相关者、需求、软件系统、工作、工作方式、团队；每个 alpha 有一串状态，每个状态有一张检查单；实践是可选、可组合的模块，叠在内核上，可以加自己的 alpha。

对 Yudao 的用处不是照搬，而是三点：

1. **内核加实践对应「核心固定、外环可变」**。Yudao 的形态（三部门、一个角色直做、外包直做）和 ADR-0045 的「形态加本项目的改动」就是实践的组合。新的轮转方式进来，是加一个实践，不改内核。
2. **alpha 的状态加检查单**对应外环状态、停止原因和判定点。可以把「什么条件下进入某状态」写成本体里的状态与迁移，clingo 能核对文档和定义有没有写出不存在的迁移。
3. **拿七个 alpha 对一遍 Yudao 本体，找缺口**。粗对照：需求 ↔ ProductSpec 与要求链；软件系统 ↔ 交付与交付快照；工作 ↔ 事项与一轮工作；团队 ↔ 部门与角色；工作方式 ↔ 定义、组织、形态；利益相关者与机会 ↔ 用户与意图。这是起草时的对照，没有逐条核过。

### 3.3 产品领域模型的元概念放在 M2

DDD 的元概念（限界上下文、聚合、实体、值对象、领域事件、不变量、通用语言）作为 Yudao 本体的一个子块，挂在语义系统的「术语」之下或取代它。每个产品在 ProductSpec 里填自己的 M1。

和现有设计的接法：

- **要求链**：验收条件可以写它关于哪个聚合或哪个不变量，质检的检查就能按领域元素归组。
- **代码对照**：产品的模块对应限界上下文，做法和 Yudao 自己的「总图的词与代码名对照」一样。
- **笔记本的例子**：M1 写「笔记本」上下文有聚合「笔记本」，包含实体「笔记」，值对象「标签」，不变量「一条笔记只属于一个笔记本」（单值）。clingo 就能查：交付里某处让一条笔记属于两个笔记本，报冲突。

DDD 只是默认的一种 M2 子块；别的产品可能更适合别的建模方式（第 10 节第 2 条）。这一层现在用不上，排在最后。

### 3.4 代码与测试：从意图到测试的整条链

把 Yudao 当成一个产品看，它自己的「要求链」从意图一直走到测试。链上每一环都已经有正本，缺的只是把它们读成同一套概念与关系：

| 概念 | 是什么 | 正本（已有） | 今天的量（8c979df） |
| --- | --- | --- | --- |
| 意图 | 目的、判据、基础规则 | D38、基础规则 | |
| 需求记录 | 一条需求与验收标准 | `docs/requirements/` | 40 份 |
| 总图元素 | 缝、方框、状态、内环步、四层、三环 | 总图 HTML 的结构 | 13 道缝 |
| 缝的规矩 | 一道缝要守的一条规矩 | 总图每道缝的 `<li>` | 40 条 |
| 设计说明 | 一个方框或一道缝怎么做 | `docs/design/`，开头「总图位置」一行 | 28 份 |
| 模块 | 一个 Python 或 TypeScript 文件 | 代码本身（ast） | |
| 代码名 | 模块里的公开定义：类、函数、常量 | 代码本身（ast） | |
| 总图的词与代码名的对应 | 一个总图的词由哪些代码名实现，一致与否 | 对照表 `name-map.md` 第 1 至 3 节 | 102 行：一致 58，不一致 30，代码里还没有 14 |
| 导入方向合同 | 哪层不许导入哪层 | `pyproject.toml` 的 `[tool.importlinter]` | 5 条 |
| 内核清单条目 | 只由用户批准那一环的文件 | `kernel-manifest.json` | 12 个模块 |
| 测试文件 | 一个测试文件与它的层 | `harness/tests/layers.toml` | 242 个：集成 123、模块 77、单元 42 |
| 守卫 | 守一道缝的某几条规矩的测试文件 | 对照表第 4 节「每道缝的守卫」 | 每道缝 0 到 6 个 |
| 工单、PR、证据 | 改代码的工作单与它的证据 | GitHub、`workflow.md` 第 4、5 节 | |

关系，名字沿用语义系统第 5.3 节的要求链（细化、实现、验证），不另起：

| 关系 | 起点 → 终点 | 单值或多值 | 事实从哪来 |
| --- | --- | --- | --- |
| 细化 | 需求记录 → 意图；设计说明 → 总图元素 | 多值 | 需求记录与设计说明开头的依据行、总图位置行 |
| 属于 | 规矩 → 缝；模块 → 缝（两侧）；模块 → 层；模块 → 环 | 规矩、层、环单值；模块的缝多值 | 总图结构；对照表第 4 节「两侧在代码里」与「四层」「三环」两行；内核清单 |
| 实现 | 代码名 → 总图的词 | 多值 | 对照表第 1 至 3 节 |
| 导入 | 模块 → 模块 | 多值 | ast，每次现算 |
| 守 | 守卫 → 规矩 | 多值 | 对照表第 4 节，现在是散文，见第 10 节第 5 条 |
| 在层 | 测试文件 → 单元、模块、集成、桌面 | 单值 | `layers.toml` |
| 验证 | 测试文件 → 模块 | 多值 | 静态：测试导入了哪些模块（ast）；动态：按测试记的覆盖（以后，见第 10 节第 6 条） |
| 来自 | 测试文件 → 工单 | 单值 | 文件名 `test_issue_N`，33 个 |

**这里也是自举的不动点**：语义系统给产品记的实体类型（模块、文件、接口）和要求链关系（细化、实现、完成、验证、违反），和上表给 Yudao 自己用的是同一套。今天用它查 Yudao 的代码与测试，以后语义系统用同一套规则查产品的代码与测试。

**粒度**：到模块与公开定义为止，不建调用图。概念模型方案第 9 节已经写了「不做：调用关系」；要查调用时仓库已有 CodeGraph 索引，不进本体。

## 4. 表示：用什么写、为什么不用 OWL

| 选项 | 世界假设 | 适不适合 |
| --- | --- | --- |
| OWL / RDF | 开放世界：没写的事实不算假 | 不适合当检查用。两条线都依赖「没写就算没有」：走不到、没人认领、缺核对、没列的就是不做 |
| SHACL | 闭世界验证 | 思想合适（语义系统已经借了「约束写成形状」），但要整套 RDF 工具链 |
| clingo / ASP | 闭世界，一次列出全部违例，确定 | 合适。两条线已选，工具已在用 |
| Alloy | 有界模型查找 | 适合探索设计，不适合日常检查（第 7 节） |

Siemens 的 OOASP 是现成的参照：它把面向对象模型（类、关联两端的基数、属性）写成 ASP 事实，再派生「约束违例」原子来核对一份配置。Yudao 照这个路数，不必引入它。

### 4.1 设计概念写在哪

概念模型方案已定在 `CONTEXT.md` 词条下加结构块。本方案只在那份草稿上加几个字段：

```
#### 部门
（原有的定义段落与 _Avoid_ 行不变）
- 层：组织
- 是：概念
- 属性：显示名 单值；角色 多值；关注的成果 多值
- 定义在：`docs/architecture.html`「全局总图与方程」

#### 核验角色
- 层：路由
- 是：概念
- 属性：核验谁 多值
```

## 5. clingo 查什么

### 5.1 本体本身

四类规则，前三类是确定性的：

1. **本体自检**：名字和别名唯一；关系两端的种类存在；「定义在」的小节存在；每个概念有层；实例的种类是登记过的概念。M3 用同一组规则检查自己，这就是最便宜的「自描述」：MOF 的 M3 也是「符合它自己」的。
2. **实例符合**：单值属性出现两个值就报（LLM 开放提取试验里缺的就是这一块）；关系连接的种类不对就报。文档说法、定义 JSON、代码事实都当实例来查。规则事实线的 `compare.lp` 已经是这一类在脚手架上的实现。
3. **分层**：上层代码或文档点名下层实例就报，见第 8 节的原型。
4. **演化只增**：新旧两版本体比较，只许加种类、关系、字段，已有的不许删、不许改层、不许把多值改单值。这是「保守扩展」的一个简化版：描述逻辑里判断一个扩展是否保守代价很高，但 Yudao 的本体没有推理公理，只比结构就够。

```
% 演化只增：旧版有、新版没有，或层变了
removed(K) :- old_kind(K,_), not new_kind(K,_).
relayered(K) :- old_kind(K,L1), new_kind(K,L2), L1 != L2.
narrowed(K,P) :- old_prop(K,P,multi), new_prop(K,P,single).
```

### 5.2 跨设计、代码、测试的检查

整条链连起来以后多出来的检查。右列的「现在怎么做」大多是 `seam-diff` 技能第 2、3 步里靠人跑、靠人检索的部分。

| 检查 | 规则的意思 | 现在怎么做 |
| --- | --- | --- |
| 规矩没有守卫 | 总图的一条规矩，没有任何守卫守它 | 对照表第 4 节写「没写进这一栏的就是没有守卫」，靠人对 |
| 守卫丢了 | 对照表列的守卫文件不在 `layers.toml` 里，或本次 junit 里没出现 | `seam-diff` 第 2 步人工核对 |
| 守卫失败 | 守卫在本次 junit 里失败，报到它守的缝与规矩上 | `seam-diff` 第 2 步 |
| 守卫层太高 | 内核的规矩只有集成层守卫 | 测试分层设计说明第 5 节「往下层移」，靠人看 |
| 分层 | 上层模块点名下层实例（第 8 节） | `seam-diff` 第 3 步部门名检索；`test_thin_driver_names.py` 只查 `orchestrator.py` |
| 导入越层 | 模块的层与导入方向矛盾：标在内核的模块导入了应用层 | import-linter 只按包名查，不知道对照表给模块标的层 |
| 对照表走样 | 对照表写的代码名在代码里没了；内核新加的公开定义没有总图的词认领 | 概念模型方案第 4 节已列，未做 |
| 已定的缝没有代码 | 总图里「已定」的缝，对照表还有「代码里还没有」的行 | 靠人看。这不一定是错：总图写应当如此，代码可以落后，报成「待建」而不是矛盾 |
| 链断了 | 需求记录没有任何设计说明细化它；设计说明的总图位置指向的缝没有守卫 | 没有人查 |
| 测试没挂上 | 测试文件不是任何缝的守卫，也不验证任何标了层的模块 | 没有人查；33 个按工单号命名的测试最可能落在这里，只是提醒，不算错 |

规则的样子：

```
% 规矩没有守卫
unguarded(S,R) :- rule(S,R), not guarded(S,R).
guarded(S,R) :- guards(F,R), guard(S,F), test_layer(F,_).
% 守卫丢了：对照表列了，登记表没有
lost_guard(S,F) :- guard(S,F), not test_layer(F,_).
% 内核的规矩只有集成层守卫
guard_too_high(S,R) :- rule(S,R), kernel_seam(S), guarded(S,R),
    not low_guard(S,R).   % kernel_seam：两侧有内核清单模块的缝
low_guard(S,R) :- guards(F,R), guard(S,F), test_layer(F,L), L != integration.
% 导入越层：内核模块导入了层更低的模块
import_up(A,B) :- imports(A,B), module_layer(A,LA), module_layer(B,LB),
    layer(LA,NA), layer(LB,NB), NA < NB.
% 已定的缝还有没建的词：报待建，不报矛盾
pending(S,W) :- seam(S,set), word(W,S,missing).
```

和代码有关的结论都只提醒，不拦提交，同两条一致性线的约定；需要拦的仍由已有的守卫测试与 CI 拦。

## 6. 用途二：同一套事实给 agent 装上下文

### 6.1 记忆加 RAG 缺什么

RAG 按字面或向量相似去找，记忆按以前写下的话去找。改代码的 agent 真正要守的东西，很多和手里的文件并不像：

| 缺口 | 例子 | 本体怎么补 |
| --- | --- | --- |
| 不像但相关 | 改 `adjudication.py` 时，该守的是总图上它那道缝的规矩和 ADR-0044「核验是角色的性质」，它们的字面里没有这个文件名 | 沿关系走：模块属于缝，缝有规矩，设计说明细化缝并引用 ADR |
| 旧的和新的一起来 | 相似检索会把已被取代的决定一起捞回来；语义系统第 1 节说的就是这个问题 | 状态与取代本身是关系，只放有效的；取代的只在查询时要了才给 |
| 漏了不知道 | 检索返回前几条，漏掉的看不出来 | 闭世界：该附的是规则算出的全集；上限装不下就写「另有 N 条」，不静默丢 |
| 说不清为什么放进来 | 相似度分数不是理由 | 每条带上走过的关系作理由，就是语义系统第 10.11 节上下文清单里的「放入原因」 |
| 不能重放 | 向量库或嵌入模型一换，结果就变 | 同一份事实、同一份规则，结果一字不差，同上下文装配设计说明「视图是事件日志上的纯函数」 |
| 谁能看什么靠提示词 | 检索不管角色的范围 | 可见范围也写成规则；规则事实线的 `scope.lp` 已经是脚手架上的这一块 |

RAG 不是没用。没有实体可挂的开放问题（「以前有没有人讨论过 X」）仍然要全文检索，语义系统选的是 FTS5 trigram，不用向量。本体管有锚点的那部分，而改代码时这部分占大头。

### 6.2 语义系统本来就是这么设计的

语义系统第 10 节的上下文组装只按结构关系与固定规则选，不用向量检索：焦点与一步相连的目录（第 10.4 节），角色读或改文件时附上关联在这个文件实体上的要求与内容（第 10.5 节），各角色看得到的不同（第 10.8 节），每条的放入原因记进上下文清单（第 10.11 节）。它挂的本体是第 5 节：内容种类、实体类型、要求链关系。

缺的是两样：

1. 这套本体只给产品用，Yudao 开发自己时没有图。第 3.4 节那条链（意图、需求、缝、规矩、设计说明、模块、守卫、测试）就是 Yudao 自己的那张图。
2. 语义系统第 5 节的本体是文档里的几张表，没人查过它自洽。用途一的检查（第 5 节）放到同一份本体上，就是「图对不对」的保证。

[上下文装配设计说明](../design/context-assembly.md)管的是另一半：历史怎么折叠、旧工具结果怎么清、装入顺序与截断。它回答「历史里留什么」，本节回答「历史之外再附上什么」。两者都是事件与事实上的纯函数，接在总图第四节同一道「装配」缝上。

### 6.3 选上下文写成规则

接触时附加写成 clingo 规则。用的就是第 4.2、4.3 节那些事实，不另记一份：

```
% 焦点：本次任务读或改的文件
focus(M) :- touched(M).
% 走一步：文件所在缝的规矩、守卫、细化它的设计说明
attach(rule(S,R),  seam(M,S)) :- focus(M), module_seam(M,S), rule(S,R).
attach(guard(F),   seam(M,S)) :- focus(M), module_seam(M,S), guard(S,F).
attach(design(D),  seam(M,S)) :- focus(M), module_seam(M,S), refines(D,S).
% 再走一步：设计说明引用的有效 ADR
attach(adr(A),     design(D)) :- attach(design(D),_), cites(D,A), adr_status(A,valid).
% 文件里的代码名实现的总图的词，带上状态（不一致、代码里还没有都要提醒）
attach(word(W,St), name(M,N)) :- focus(M), defines(M,N), implements(N,W), word(W,_,St).
% 内核模块：提醒不许点名下层实例（第 3.1 节）
attach(layer_rule(kernel), layer(M)) :- focus(M), module_layer(M,kernel).
% 角色范围
show(X,Why) :- attach(X,Why), visible(X).
```

`attach` 的第二项就是放入原因，原样写进上下文清单。排列与上限照语义系统第 10.5 节：冲突与待复核在前，然后是规矩与要求、有运行验证的内容、其他；每个文件有上限，超了写「另有 N 条，可以查询」。

这条规则和规则事实线计划里的写入时钩子是邻居：那个钩子提醒「这句话像在复述哪条规则」，这条给出「这个文件该守什么」。两者读同一份事实，可以并成一个入口。

### 6.4 先给谁用

- **现在：开发 Yudao 的 agent。** 改一个文件之前，钩子或技能按上面的规则附上它那道缝的规矩、守卫、设计说明、有效 ADR 与对照表状态。这相当于把 `seam-diff` 第 3 步那类事后人工检索提到事前：不是改完再查，是改之前就告诉它。
- **以后：Yudao 运行时的部门角色。** 就是语义系统第 10.5 节，同一套写法与规则，换成产品的图。第一层自举时，这两者是同一件事：Yudao 开发自己时，附给角色的就是第 3.4 节那张图。

先做哪个，见第 10 节第 9 条。

### 6.5 业界怎么挑上下文

下面三项这一轮只读了搜索结果里的介绍，没有逐篇读原文。

| 做法 | 怎么挑 | 和这里比 |
| --- | --- | --- |
| Aider 的 repo map | tree-sitter 抽出定义与引用，按文件之间的引用建图，按图排名，挑进固定的 token 预算 | 也按结构、不按相似；但图里只有代码符号，没有需求、规矩、决定 |
| Microsoft GraphRAG | 用 LLM 从文本抽实体与关系建图，再分社区写摘要，回答全局性的问题 | 图是开放抽取的；仓库 11-02 的开放抽取试验（召回 1/4，100 条里 98 条误报）说明这条路在 Yudao 的文档上不稳 |
| Zep 与 Graphiti | 带时间的知识图谱给 agent 当记忆，事实有成立区间，被新事实作废；向量、全文、图关系混合召回 | 语义系统第 2 节已经借了它的四个时间；向量召回不借 |

## 9. 怎么接两条一致性线和自举

**规则事实线**：它的 `canon.json` 已经是一个小本体，按已定的 C 当本体的第一块，接法见第 10.1 节。

**概念线**：本方案就是概念模型方案第 3 步（定写法）和第 4 步（合并模型）的内容，多加了「层」「是概念还是实例」两个字段（单值多值那份草稿已有）。LLM 开放提取失败的两个原因（主语不封闭、不知道单值多值），本体都补上：定向提取的主语只能来自本体，规则只比单值属性。

**第一层自举**（Yudao 做自己的工单，阶段二薄片 ⑤）：Yudao 把自己当普通项目开发时，产品「Yudao」的 M1 领域模型就是 Yudao 的 M2 本体。所以只要 M3 一份，开发 Yudao 用的一致性工具，和语义系统给产品用的领域模型检查，长成同一个东西。像能编译自己的编译器。

**第二层自举**（阶段四）：系统提出的定义候选里，凡是改本体的，先过两道确定性检查再进隔离对照：演化只增（第 5 节第 4 类）、分层不破（第 3 类）。本体里「只由用户批准」那一环的概念，候选一律不许碰。这样「候选不能自行批准」有一部分是规则保证的，不只靠评价。

**C 要分清一件事：共用的是概念，不是实例。**

| 概念（M2，共用一份） | 脚手架里的实例（规则事实线） | Yudao 运行时的实例 |
| --- | --- | --- |
| 角色 | 总架构师、子架构师、架构师循环、solo 执行者、审查者、agent 试用者（`workflow.md` 第 2 节、`roles.json`） | 产品、工程、质检的角色（`organization.json`） |

「审查者」和「质检」是同一个概念（核验角色）的两个实例，不是同一个东西。吸收那天要做的是把脚手架的实例搬进定义，概念不用改。这也是第 3.1 节分层规则管的事：实例只住在它的来源里。

**`canon.json` 在本体里是什么**（对照 8c979df 上的文件）：

| `canon.json` / `roles.json` 的写法 | 在本体里是什么 |
| --- | --- |
| 表的 `node`（事实、角色、标签、证据前缀、卡在项、结论、测试层）与 `key` | 种类（概念） |
| 正本表首列的每一行（某个标签、某个前缀、第 1 节的十七件事） | 这个种类的实例 |
| 列的 `fact`（由谁定、由谁改、由谁改成、由谁写、交给、由谁负责、理由、在场可否、以谁为准） | 关系 |
| 列的 `many` | 关系单值或多值 |
| 列的 `vocab` 与 `key_vocab`（角色、可否、机器、载体） | 关系终点的种类，取值清单在 `vocab` 或 `roles.json` |
| 列的 `edge`（角色→键、键→角色） | 关系的方向 |
| `aliases`、`roles.json` 的别名与 `groups` 合称 | 别名；合称是实例的集合，比对前展开 |
| `rulefacts-patterns.json` 的动词（定、确认、改……） | 关系的叫法，不是新关系 |

**共用的那部分放哪**：就放在规则事实线现有的 `canon.json` 与 `roles.json` 里，它们是重叠概念的正本。本体不另存一份，用的时候编译成事实（下面第 3 条）。重叠以外的概念不进这两个文件，哪条规则要用才加，写法见第 4.1 节。

C 的接法（已定，按这个做）：

1. **规则事实线已做的第 1 至 6 步不用改**，它的文件归它自己的方案管，本方案不碰。
2. **只约定一件事**：`canon.json` 里种类和关系的名字就是本体里的正名，概念线以后不另起名字。比如概念线要用「角色」，就用 `canon.json` 那个「角色」，不在 `CONTEXT.md` 另写一份角色清单。
3. **编译成本体事实是一个很小的脚本**：只读 `canon.json` 与 `roles.json`，生成 `kind(角色)`、`rel(由谁改成, 标签, 角色, multi)` 这样的事实，格式同第 4.2 节，跑第 5 节的本体自检。
4. **加概念只有一个时机**：某条规则要用它。概念线以后要查缝、部门、事项时再加，用同一套写法，加的时候标层。
5. **吸收进 Yudao 时**：概念的层从「脚手架」改到 Yudao 的某一层，实例搬进定义。这是第 5 节「演化只增」规则唯一的例外，要当一次决定记进决策记录，不让候选自己做。
