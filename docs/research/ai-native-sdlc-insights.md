## 1. 总体判断

文章将软件生命周期表述为 Plan、Design、Build、Test、Deploy、Maintain 六个非线性环节，AI 参与每个环节，接纳的产物触发后续工作，维护反馈再成为新意图。核心与 Yudao 的循环方向相符：保留交付和责任要求，通过自动交接、检查和反馈推进。

一致的是控制思想，不能据此认定当前三部门已完成文章的全部生命周期。Yudao 当前主要实现单次任务的产品、工程和质检流转；跨任务项目接续、项目采用成果及部署维护外循环仍需明确交付。

该来源是供应商应用实践指南，不是证明某种架构优于其他架构的实验论文。以下区分原文建议、本项目现有基础和我们推导的新设计；原文效果预期、经验数字和演示配置均不作为本项目验收证据。

## 2. 六个环节与三部门是两个维度

| 原文环节 | 回答的问题 | Yudao 的责任映射 |
| --- | --- | --- |
| Plan | 为什么做、想得到什么、边界是什么 | 产品保留原始意图和有效变化；领域补全协助理解 |
| Design | 采用什么产品方案、技术方案与约束 | 产品负责用户与业务选择，工程负责技术设计，重要跨界取舍经 Ask/React 解决 |
| Build | 怎样在现有系统上形成可验证增量 | 工程计划、实现、必要重构和局部自检 |
| Test | 什么证据说明改变符合要求 | 工程持续反馈与 QA 独立复核；循环外评价另行衡量系统改善 |
| Deploy | 哪份交付可以进入哪个运行环境 | 工程与后续运维执行，按已定义的环境权限和发布约定核验；QA 放行不等于发布成功 |
| Maintain | 实际运行的问题怎样进入下一轮 | 第三阶段运维保留观察与影响，形成关联到项目和版本的新工作 |

三部门定义谁对结果负责，六个环节定义工作要覆盖什么。设计、自检和维护反馈可以分布在各部门和多次变更中，不需要按文章标题机械增加六个部门，也不能把三部门做成互不交流的文档流水线。

## 3. 值得吸收的六点

### 3.1 优化单位应是一项变化的完整交付

原文开头指出，生成代码加快后，需求准备、审查、发布与人工等待会成为新的瓶颈；并行章节也用审查承载能力限制同时推进的工作数量。

对 Yudao 的推导是：不能只优化工程 token、代码产量或部门并发数。观察一项变更从提出到采用、到实际使用反馈的全程，找出等待发生在哪里、由谁接续、缺少何种输入。之后依据证据改善职责与交接，避免工程吞吐增加而 QA 队列持续增长。

近期落点是第二阶段的变更时间线、等待原因和返工分类；第三阶段再根据真实容量限制在途任务与并行度。不根据文章的“两三个会话”建议预设 Yudao 固定并发数。

### 3.2 用可追溯产物接续项目

原文在六环节总览、Plan 和 Build 中强调意图、要求、计划、代码与检查、审查和事故记录的版本关联；下一步读取上一环节的产物，执行偏离计划时同步更新计划。

Yudao 已有 ProductSpec、DeliverySpec、QAReview 和事件引用，但还缺少跨 run 的项目归属及实施方案与实际差异。需要增加项目和变更责任，使一次交付成为下一次工作的明确起点，历史决定和实际成果能够关联。

这里采用的是产物的语义与来源关系，不要求强制生成六份 Markdown 或每步新建 PR。模型写下文件只是提案，控制层接纳并核验实际版本后才推进；Git 提交也不单独证明工具运行或发布发生。完整方案见[原生接入设计](native-project-evolution-design.md)。

### 3.3 工程内部反馈与独立质检同时存在

原文 Test 区分贯穿实现过程的反馈循环和使用独立上下文的终检。代码需要可运行检查，界面需要实际浏览器或截图证据，缺陷修复先确认反例。

Yudao 可以保持工程在职责内反复修改和自检，QA 从当前要求、公开合同和真实交付独立判断。工程内检查不必每次触发跨部门返工，独立 QA 也不能仅复述工程检查摘要。

进一步的演化要求由我们明确：QA 同时核对本次变化和仍有效的既有合同。用户合法改变行为时同步改变相应检查，旧语义退出当前要求。既不能只验证新增功能，也不能把旧测试永久固定为阻止演进的规则。

### 3.4 知识、程序约束与评价承担不同责任

原文将项目说明用于必要上下文，将 skills 用于一致应用专业知识，将 hooks 用于执行时的确定性限制，将配置 eval 用于发现模型、提示和技能变化造成的退化。

这与我们的领域补全形成直接对应：行业知识解释如何完成未定义部分，项目约定确定当前适用选择；真正必须保持的权限、预算、版本和证据要求由主机控制实现。增加一句提示或加载一个 skill，不构成系统已经强制执行该要求的证明。

新增落点是把知识与上下文装配的版本纳入系统配置评价。改变一条默认、部门提示或历史筛选方法，也可能改变交付质量，不能因没有修改生成代码就跳过相关校准。普通开发回归与正式未见任务比较各有用途，前者通过不代表后者已经证明收益。

### 3.5 上下文是持续维护的项目产物

原文的项目说明面向“新人第一天所需”，要求短、可审查、随实际错误和代码变化更新；独立子任务使用各自的上下文和工具范围。

选择性上下文和历史分层已在我们的设计中存在。新的实施含义是：Yudao 要自动维护这种接续能力，让每次进入项目的执行者取得当前代码、差异、适用约束与相关理由。用户不需要每轮重写背景材料。

短摘要只是一种派生表示。源决定、实际实现和验证仍分别核对；旧理由可查，旧命令不会因此重新生效。项目、工作树和任务范围限制优先于相关性排序，模型适配器追加的实际输入也在管理范围内。

### 3.6 维护反馈回到同一个变更流程

原文 Maintain 用确定性监测发现异常，再按权限分配只读诊断、修复提案或既有处置流程；问题重新成为意图，修复后保留事故回归材料。

Yudao 的用户要求、公开缺陷和未来运行反馈应共用项目变更入口，并保留各自来源与授权。明确的小修复可以缩短方案准备，复杂方向变化需重新分析影响，二者仍经过相应要求与独立检查。

这带来清楚的三种反馈：当次工程与 QA 返工；跨任务的项目持续迭代；对 Yudao 控制、知识和组织的独立改善评价。线上问题不自动成为全局学习经验，外评隐藏材料也不能直接进入被评项目的修复上下文。公开事故材料成为开发回归后，不继续当未见评价样本。

## 4. 需要结合项目调整的建议

| 原文做法或示例 | Yudao 的取舍与原因 |
| --- | --- |
| 各环节示例中的产品审核、工程审查和发布签批 | 保留相应责任与明确权限，范围内日常工作自动推进；用户已授权事项不重复确认，必要人工取舍集中在实质问题 |
| 第二次犯错就将修正规则写入项目说明 | 可追加有来源的问题记录或纠正已明确规范；系统推导的新经验仍须判断适用范围、验证与失效，次数不是普适性证据 |
| 以 Build 开始后的 spec 提交数衡量需求返工 | 区分用户主动演化、合理发现、误解遗漏及未知原因；提交次数可描述活动，不能直接代表需求质量差 |
| 修复任务禁止修改测试 | 保护本次缺陷的有效反例和独立评价；用户合法改变合同后允许更新对应检查，明确取代关系 |
| 选取 20-50 个任务、使用 1/2/3 个标准差的监测层级 | 作为文章的启动示例；实际样本量、阈值和时间序列方法依据任务、波动、成本与错误代价校准 |
| Shell 字符串匹配的部署 hook 和环境变量授权示例 | 说明动作前控制的位置，不能当作完备授权或隔离实现；实际动作、目标、版本与已授权范围由可信执行边界核验 |
| Git 与现有工单系统可用相互链接过渡 | 本项目每类事实只有明确权威来源；Markdown、图和索引是可读表示或引用，不新增双向互相覆盖的状态 |
| 跨 worktree 并行避免文件冲突 | 保留工作副本隔离，同时检查共享接口、目标和项目基线；不同文件仍可能有语义冲突 |

文章列举的商业产品、托管配置和示例不是本项目依赖选择。使用已有维护中的库和本地能力，具体工具选型在对应实际接入时验证，不照搬供应商工具栈。

## 5. 对阶段计划的实际改变

| 阶段 | 吸收后要交付或明确的内容 |
| --- | --- |
| 第一阶段 | 沿用原生三部门骨架，补齐已确认的持续输入、有效 PRD、事前计划、相互咨询与动作请求、部门历史压缩和 prompt 编辑；最新评审建议补完整交付封存与重构工具，不增加项目生命周期平台 |
| 第二阶段 | 增加 2.E 原生项目演化：项目、变更、完整基线、增量交付、原因查询、选择性上下文、项目结果采纳和跨变更视图；与观察及学习工作并行 |
| 第二阶段评价 | 将领域默认、提示、上下文与知识版本列入配置变化校准；区分工程自检、QA 与独立改善评价；度量全程等待及正常演化和缺陷返工 |
| 第三阶段 | 发布与维护反馈进入既有变更流程；依据审查与执行容量控制并行；运行恢复、部署回执和副作用责任分别验证 |
| 第四阶段 | 系统自己提出的组织和规则修改继续走有证据的比较、限定采用与撤销；不把日常项目调整推迟到这里 |

生命周期环节不是我们四个大阶段的编号，也不要求每项任务按顺序完整经过六步；具体执行仍遵守产物和检查的前置依赖。研究、校准和独立准备可以提前，真实执行接入按照接口与证据前置条件推进。

## 6. 新设计怎样证明有用

第一项验收是同一项目连续完成三次真实变更，新会话可继续工作，仍有效的行为保持，合法旧要求退出，旧原因可以定位，未采用的候选不会覆盖当前项目。该验收先证明功能可靠，不冒称已获得统计收益。

之后在同类、事先明确的任务条件下比较：是否减少人工重复补背景，是否减少失效上下文导致的错误，是否缩短变更到可用交付的时间，是否把等待从工程转移到了 QA 或用户。质量、成本、未完成、失败和未知结果共同报告。

规范符合、交付行为、实际使用效果和系统自身改善是不同判断。产品准备时记录问题与期望结果，QA 检查约定行为，未来运行观察提供实际使用反馈。单纯 spec 符合或一次测试通过，不能证明产品解决了用户的全部真实问题。
