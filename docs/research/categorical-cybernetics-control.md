## 1. 开放过程的接口

Capucci、Gavranović、Hedges 与 Rischel 的 optic 范畴用一对对象 `(X, X′)` 表示正向与反向接口。以集合的直积为例，从 `(X, X′)` 到 `(Y, Y′)` 的过程用正向映射 `X → M × Y`、反向映射 `M × Y′ → X′` 及中间信息 `M` 表示。Vagner、Spivak 与 Lerman 将带类型的端口作为接线范畴的对象，把连接、并置和反馈表达为端口之间的接线。[1 §3–4][2 §2–3]

Yudao 采用离散时间解释：一步是一次接纳事件，时间上相邻的反馈通过已提交事实连接。用 `(用户意图, 澄清请求)`、`(当前合同, 合同异议)`、`(封存交付, 返工意见)` 表示相邻接口；`M` 保存提案的依据版本、角色与激活身份。一次角色工作可能调用模型或进程。写入口只接纳满足合同的提案，反馈通过提交后的事件传播。这里实现的是这一解释下的控制组合，无须在运行时引入一般的 optic 或连续动力系统求解器。

令 `E*` 为有限事件序列，`S` 为已接纳事实决定的运行状态。事件折叠定义作用 `F : E* → End(S)`：

```text
F(空序列) = id
F(p ++ q) = F(q) ∘ F(p)         其中 q 接在 p 之后，保留执行权与派发身份
```

状态包含判定新旧派发所需的事实。重放只重算状态，不再运行模型、工具或检查；同一条事件序列的结果与折叠时的分组方式无关。独立角色在各自的可见范围与检查副本中工作，其并置不授予跨角色读写的权限。

## 2. 核验反馈的组合

对一个封存交付 `v`，冻结的定义给出要核验其作者及成果种类的角色集合 `Qv`。坐标 `(v, q)` 对应一位核验者对这一版本的结论。每个坐标使用有限序 `未提交 < 无法核验 < 通过 < 打回`；这里的顺序定义合并优先级。不同角色组成直积 `∏q∈Qv Signal`，在每个坐标上取最大值。没有接纳的报告时用「未提交」作为单位元；非本版或非声明角色的结论不进入直积。因此这一组合满足结合律、交换律和幂等律，分批处理、不同角色先后提交或同一结论重复读入均不改变结果。报告进入组合前仍要经过写入口、身份和版本核对。

| 组合结果 | 控制动作 |
| --- | --- |
| 核验角色集合为空 | 依照运行创建时冻结的标记，记录开环完成 |
| 存在打回 | 这一版不能继续放行；缺陷记录按冻结的关注关系返回交付作者 |
| 角色集合非空且全部通过 | 采纳最后一份结论的事务才可以记录事项放行 |
| 其余情况 | 继续未完成的核验；「无法核验」经既有决定请求处理 |

`harness/feedback.py` 实现该直积与读取规则。`direct.py`、`watched_outputs.py`、`tightening.py` 分别接入已有的通用成果事件、成果驱动投影与收紧检查，使用同一套组合。不同交付有不同摘要，新版核验从一组新的「未提交」开始；回执仍绑定当前 PRD、合同、交付快照与本次激活。定义条件 `$issuer` 指向提交角色自身；指定固定职能的旧条件含义不变。检查材料从该角色最近的已接纳保存事件导出，读写的是各自的副本；独立判断的所有者同样从事件信封读取。页面进度和离开期间的报告按照事项终态区分单个核验结论与放行。

## 3. 活性、停机和恢复

上述组合律用于安全性：相同事实给出相同的反馈，旧版结论及其他角色的结论不能替代当前坐标。活性需要独立的条件：反馈路径中的下一步已准备好、定义保留了相应的关注关系、模型与执行环境能工作且尚有额度。运行上限保证停止，无法保证以放行收敛。

`harness/thin_driver.py` 在准备记录无新工作时按写入事务的事件版本重查路由。期间有新输入、指导或成果产生可启动工作时，持续运行入口回到排程；发生流版本冲突时，通过写入口用新版本重新判断。询问本身也是已记录的工作来源：`RunProjection.pending_ask_departments()` 按发起它的主线会话恢复全部根询问，路由在列出可工作职能和开始事务中使用同一事实。

验收区分正负两方面：已有输入不被空闲停止覆盖；没有工作时仍可记录明确的停止原因；两个核验角色使用真实主机断言，只有一个通过时继续，打回后工程交付新版本，两位都核验新版本才放行。已有取消、上限、开环、定义改名和重放用例继续承担各自的约束。

## 4. 从原始意图到核验证据

对已记录的显式要求集合 `I`，在关系范畴 `Rel` 中取 `R : I → A`、`T : A → K`、`H : K → W`。`A` 是合同验收条件，`K` 是检查或其他独立证据类型，`W` 是绑定当前版本且已核对的回执。复合关系 `H ∘ T ∘ R` 的定义域必须覆盖 `I`，才能声称每个登记要求都有证据路径。若一条要求包含多项必要条件，须按验收条件逐项核对，任何一条路径的存在都不足以代替其余条件。

结构覆盖与语义验证有不同的证据。系统需要独立核对已登记集合是否遗漏了用户明确要求；检查的辨别力要用对应的可复现违规样本判定，例如相同长度的原顺序与反序输出、同一行为通过内部调用而公共入口未接线。命令检查的基线对照只验证这一条命令能否区分基线与交付。多个角色都通过同一种不充分的检查，仍可产生误放行。

工单 #1841 保留「来源遗漏、歧义、证据不足」的设计决定。需要定义谁核对原始要求的分解、谁接纳映射证据、缺项应回产品还是工程、证据不足何时请求用户。分支只执行已有核验权限、独立性和当前版本规则。待设计确认后，用公开对照样例验证三种去向，再按固定材料、同一模型及同一评分器复验。真实评测的结果与本地确定性回归分开记录。

## 5. 后续校验与实施边界

- 路由继续从冻结的定义和事件事实选择下一步；任务池与职能内子循环按各自已定契约接入。无效接线在加载定义时报告，不能运行到半途才靠模型补足。
- 时间、预算、无动作暂停、依赖恢复分别观测。按真实事件定位循环中止原因，再验证每种中止是否符合当时的状态与界限。
- 候选结构与发布版本在相同输入、材料、模型和评分器下单独复测。重点读返工是否重新核验、错误停机比例、误放行率、完成率、用量，以及用户待决定的数量与时长。
