# 范畴论作为 Yudao 循环架构的理论依据与后续方向

本文是调研，不是设计说明，也不提出新功能。它用范畴论的语言，把 Yudao 已经立住的骨架——循环、边界、裁决，以及写入口、事件日志、最小投影、薄驱动与路由契约——重新叙述一遍，目的是给后续的架构与控制系统设计提供约束和组合规则。凡涉及现状，都以当前代码与文档为准；类比严格的地方写明，只是启发式的地方也写明。

控制论描述循环「怎么转」：感知、比较、执行、再感知。Yudao 的外环就是这一套：职能按关注的成果开工，主机执行并留下回执，路由判断一轮与事项如何结束。范畴论描述「转出来的东西为什么合法」：对象之间的箭头怎样组合、极限与伴随给出什么唯一性、一条射改变状态时还要满足哪些方程。它能约束「拼起来的零件不要走样」，但不能代替对具体方案好不好、快不快的判断。把范畴论写进运行时，或指望它从自然语言意图直接推出合法形态，都不在本文的主张里。

依据的主要材料：`harness/write_path.py`、`harness/event_store.py`、`harness/adjudication.py`、`harness/minimal_projection.py`、`harness/thin_driver.py`、`harness/routing_contract.py`、`harness/watched_outputs.py`、`harness/direct.py`、`harness/engine.py`（`StepDriver`）、`harness/orchestrator.py` 的 `busy()`、`harness/definitions/` 与 `harness/definitions/forms/`、`harness/app/read_models.py`、`harness/definitions/kernel-manifest.json`、[ADR-0044](../adr/0044-verifier-role-and-open-loop.md)、[ADR-0019](../adr/0019-project-stream-across-versions.md)、[总体路线图](../program-roadmap.md)第 3 节道 03 与道 10，以及代码里仍称作「3.4A」的执行槽位约束。

## 1. 单子：把「结果交给下一步」写成可组合的箭头

**概念是什么。** 单子 `T` 给类型 `A` 一个「带上下文的计算」`T A`，并提供三个操作：`unit`（把纯值放进上下文）、`bind`（把上一步的结果交给下一步）、`join`（把嵌套的上下文压平）。常见实例是：出错短路（`Either`）、把状态穿过去（`State`）、以及「先做完这件事再做下一件」（`Cont` / 顺序合成）。定律要求组合不依赖于你怎样加括号：`bind` 结合律，`unit` 是左右单位。

**为什么对 Yudao 有用。** 一轮工作本来就是「上一步的事实成为下一步的输入」。若每一步都自行决定怎样写日志、怎样处理失败、怎样把状态交给下一轮，组合就会在缝上走样。单子把「结果怎么往下传、错误在哪一层停下、状态由谁线程化」收成同一套箭头，便于检查：失败有没有被悄悄吞掉、投影有没有在中途分叉、重试是不是在同一套上下文里重新判断。

**对应现有架构哪部分。** 现有实现并没有一个名叫 Monad 的类型类，但流水线已经按这个形状接线：

- `unit`：命令被 `harness/app/application.py` 的注册表接受之后，经 `WritePath.transact`（`harness/write_path.py`）把新事件放进日志。事件信封由 `harness/kernel_events.py` 给出；提交在 `harness/event_store.py` 的同一个 SQLite 事务里核对流版本、执行权与命令身份。
- `bind`：`ThinDriver.run_until_stop`（`harness/thin_driver.py`）问路由「谁能开工」，再按执行契约把一轮交给 `StepDriver`（`harness/engine.py`）。`StepDriver` 装配请求、调用模型、经 `adjudication.tool_permission` 取得许可后再 `perform` 动作；一轮的 `RoundResult` 交回薄驱动，再经写入口写回。
- `join` / 状态穿行：裁决不读应用投影，只读 `MinimalProjection`（`harness/minimal_projection.py`）。它由骨架事件纯函数折叠而成，可以重算；已用时间与次数跨重启连续（内核清单 `kernel-manifest.json` 的规则「已用的时间与次数跨重启连续」）。写入口判断期间不持有锁，版本冲突则按写入后的状态重新判断，最多 `MAX_JUDGMENTS` 次——这是把「并发下的状态」重新 `bind` 一次，而不是另开一条账。
- 出错：停止原因是封闭清单（`harness/definitions/stop_reasons.json`，基础规则 6）。不可重试的 provider 错误、重试耗尽、取消、时间上限等进入 `FAILED` 或 `PAUSED`，不靠模型口头说「完成」。

把默认形态的协作写成单子管道，只是复述，不是新设计：用户意图 `bind` 产品提案（`submit_product_spec`），提案被裁决接纳后 `bind` 工程交付，交付被质检在独立副本上核验后 `bind` 放行；任一步的合法失败走清单里的停止原因，而不是在管道外另写终态。

**落地方向。** 适合用来约束新槽位的接线（新路由、新执行实现、外包角色），检查它们是否仍经写入口、是否仍把停止原因写进封闭清单、是否仍按最小投影做裁决。不建议为此引入一套范畴论运行时或重写编排器。性能（压缩次数、墙钟）和方案好坏（质检有没有误放行）仍要靠评测与试用，单子定律管不到。

## 2. 极限：三个职能围着同一份日志，相遇点应当唯一

**概念是什么。** 极限是一张图的「最佳相遇点」：从极限对象出发，有一组射分别落到图里的每个对象，而且任意另一种落法都唯一地经过这个相遇点（万有性质）。乘积是最简单的极限：同时看到 A 和 B 的那个对象，由两个投影唯一确定。

**为什么对 Yudao 有用。** 「角色围着同一份事实工作」若只是口号，每个角色都可以私下另记一份真相。极限要求：产品、工程、质检作为对象，它们共同依赖的不是彼此的私有历史，而是同一份日志上的锥。相遇点唯一，意味着不该再出现第二条「也算事实」的写入通道。

**对应现有架构哪部分。** 日志是这个锥的底：`EventStore`（`harness/event_store.py`）是只追加的事实库，流分为 `run:<run_id>`、`project:<project_id>`、`catalog:main`，每条事件有全局位置与流内版本。写入口是锥的顶点：内核清单写明「事实只经写入口写入」，对应测试 `harness/tests/kernel/test_single_write_path.py`。三个职能在定义里不是三个独立宇宙，而是同一组织上的对象：默认形态 `harness/definitions/organization.json` 规定产品关注 `user_input` / `guidance` / `baseline_review`，工程关注 `product_spec` / `defect_record` / `guidance`，质检关注 `delivery` / `guidance` / `structure` / `product_spec`；`sources` 把用户输入与建档交给产品。路由 `watched_outputs`（`harness/watched_outputs.py`）按「关注的成果有了新版本」决定谁开工——这是从同一份日志投影出来的，不是部门之间点对点传话。

查询侧的 `harness/app/read_models.py` 明确：调用尝试表与流转记录写在 `read-models.sqlite` 里，「不写事件日志与保存的投影」，删了以后从事件重放重建。它是锥上的只读投影，不是第二个顶点。

万有性质在这里是设计规范，不是已经机器证明的定理：今天靠分层合同（`pyproject.toml` 的 import-linter）和内核测试守「只有一个写入口」。若将来出现绕过 `WritePath` 的写入，极限解释就破了。

**落地方向。** 换形态、加职能、加观察者时，先问：这个新对象是否仍只通过写入口落到同一份日志，只读是否只经投影。观察者「只读事实、给出证据与提案」（路线图 3.1）应当是锥上的射，不能成为第二个顶点。角色怎么划分，首先服从「共同依赖的是日志，不是对方的私有会话」；私有历史本来就不进入跨职能上下文，这与极限的投影方向一致。

## 3. 余代数与余递归：每一步是函子作用于已有状态，「完成」要结构可核对

**概念是什么。** 代数是「把结构折进去」（`F X → X`），余代数是「从状态展开观察与下一步」（`X → F X`）。余递归按这个展开一直走，直到结构上的终止条件，而不是靠运行后凭感觉说「大概完了」。

**为什么对 Yudao 有用。** 事项的状态不该是内存里一份可变对象，而该是日志上可重放的折叠。更关键的是「完成」：若完成只是模型说了一声，或某次试用碰巧放到了行，它就只是经验结果。余递归要求终止条件写在结构里：停止原因在封闭清单中，放行与开环完成是两种不同的结束原因，而不是同一种「DONE」的口语。

**对应现有架构哪部分。** 最小投影是典型的折叠（代数）：`fold_events` / `fold_more` 把骨架事件折成当前版本、执行权、已用量、正式成果、运行状态与待回答决定。每追加一条事件，就是在已有状态上再作用一次。应用投影（`harness/projection.py`、`harness/project_projection.py`）与读取模型同样从事件重算。薄驱动的循环（`run_until_stop`）则更像余代数的展开：看当前视图，问 `ready_departments`，开一轮或问 `item_end`，把结果写回后再展开。

终止已经部分结构化合。`stop_reasons.json` 里 `released` 的标签是「已完成并放行」，`open_loop` 是「开环完成」，两者 `outcome` 都是 `done`，但含义不同。[ADR-0044](../adr/0044-verifier-role-and-open-loop.md) 规定：固定结构只剩循环、边界、裁决；没有核验角色的事项交完成就按流程接纳，记为开环完成，记录与页面不写放行。这落在直做路由 `harness/direct.py`（`recorded_open_loop`、`completion_reason`）和两份形态定义 `harness/definitions/forms/single_role_direct/`、`harness/definitions/forms/several_roles_direct/` 上。默认形态则要求核验角色（质检）绑定当前有效合同、交付和代码树后才能 `released`。内核规则「每个 run 以封闭清单里的原因结束或进入等待」守的就是这种结构性终止。

需要诚实的界限：结构可核对的是「以哪种合法原因停下」，不是「放行的交付一定通过隐藏检查」。后者仍是经验与评测问题（过程检查点 `no_false_release` 评的是质检有没有误放行）。余递归不取代评价。

**落地方向。** 新的结束方式必须先进入封闭清单与路由的 `item_end` / `completion_reason`，再出现在页面文案里。不要让应用层或模型另发明一种「也算完成」。任务池若作为第三种路由进来，也要给出同样可核对的终止射，而不能只在运行记录里口头标注。

## 4. 伴随：自由构造出候选，遗忘映射压回合法子集

**概念是什么。** 伴随是一对方向相反的函子 `F ⊣ U`（自由—遗忘是典型例子）：`F` 从较薄的数据生成较丰的结构，`U` 忘掉多余结构回到较薄的那一层。它们满足万有性质：从意图生成的「最自由」对象，到任何一个合法对象，都有唯一的中介箭头。由此常常推出「这种分工在某种意义上是最优的」。

**为什么对 Yudao 有用。** 产品与工程的工作像自由构造：从意图、材料与决定生成合同、计划与交付候选，候选可以比最终合法集更宽。质检与写入口的裁决像遗忘映射：不看作者自我解释的优先权（内核规则「验证者提交独立判断之前看不到作者的解释」），把候选压回「可核验、可绑定版本、工具许可允许」的子集。若这个类比成立，换角色时不应改底下的层，而应改「自由生成什么、遗忘掉什么」。

**对应现有架构哪部分。** 严格对应到「已实现的伴随函子」并不成立，这是启发式。能对上的部分是：

- 生成在应用与执行一侧：`StepDriver` 让模型提议工具与提案；提案种类与部门工具集来自定义（`harness/definitions/tools.json`、`roles.json`、`proposal_contracts.json`）。
- 压回在内核一侧：`adjudication.py` 与 `validation.py` 做工具许可、提案校验与提交前复核；写入口是唯一入账处；质检在独立检查副本上跑主机签发的检查，模型自报 `exit_code` 不是证据（基础规则 1）。
- 换形态不换骨架：[ADR-0044](../adr/0044-verifier-role-and-open-loop.md) 把核验从「第四样固定结构」改成角色可声明的性质。发布带的三份形态（`LoopSystem` 的 `FORM_REGISTRY`：默认 `three_departments`，以及 `single_role_direct`、`several_roles_direct`）共用写入口、薄驱动与契约，只换定义与路由/收紧检查。没有核验角色时，遗忘映射变薄，终止落到 `open_loop`，这与「遗忘得更少、合法集更宽」一致，但仍必须显式标记开环，不能装成放行（基础规则 2）。

万有性质「因此可推出最优角色分工」这一步，今天推不出来。系统并没有从意图范畴到合法交付范畴的形式化伴随，也没有证明三职能是唯一最优分解。它实际保证的是：角色分工是定义里可替换的内容，骨架（循环、边界、裁决）保持不变。这是可组合性，不是最优性定理。

**落地方向。** 用伴随作检查清单，而不是推导引擎。加职能、外包角色或观察者时问两句：生成是否仍只产生提案与记录；压回是否仍只由内核与核验角色（且核验结论不外包，ADR-0044）完成。若某一侧既生成又裁决自己，就违背基础规则 3，类比也立即失效。不要把「最优分工可形式推导」写成近期目标。

## 5. 光学 / 透镜：从「整个系统是一个大对象」转到「每个事项是一个焦点」

**概念是什么。** 透镜（以及更一般的 optics）描述「大结构上的一个焦点」：`get` 取出焦点，`put` 把更新写回整体。三条定律约束组合：`get-put`（取出再放回等于不变）、`put-get`（放回的值再取出就是它）、`put-put`（两次放回等于只留最后一次，或在带交换律的变体里规定冲突如何合）。多个透镜可以同时对准同一份整体，只要焦点的读写范围与定律被遵守。

**为什么对 Yudao 有用。** 当前控制核心在概念上仍常被当成「一个大对象、一个执行槽」。要并行多个事项，真正需要的不是再复制一套内核，而是：每个事项是日志上的一个焦点，独立读写自己的 `run:` 流，共享的 `project:` / `catalog:` 流有明确的冲突规则。透镜定律给出这些规则该长什么样。

**对应现有架构哪部分。** 今天的焦点几乎是「整份数据目录同一个槽位」。`Orchestrator.busy()`（`harness/orchestrator.py`）注明「3.4A 之前只有一个执行槽位」：槽位是否占用只按事件日志里未结束的 run 以及正在开始的事项判断，不看进程内任务表；已有事项在执行时，`work_item.create` 以 `busy` 拒绝（`harness/app/project_and_work_item_commands.py`）。这是全局互斥，不是按焦点的并行。

与透镜已经同构的部分：日志按流分区；一个 run 的投影是该流上的折叠（`get`）；写入口按流版本提交（`put`），冲突则重新判断——这是 `put-put` 在单流上的乐观并发，而不是静默覆盖。保存的投影与最小投影都应能从事件重建（`get-put`：重放与当前保存一致）。`read_models.py` 是另一个只读焦点，约定不回写日志。

路线图里，多事项并发仍标为「等」：道 03 的「任务池与工作单元的参数化」，道 10 的「多项目隔离并行」（[总体路线图](../program-roadmap.md)第 3 节）。代码与术语表仍把这项工作包称作 3.4A（`CONTEXT.md`：「3.4A 不同项目并行」）。归档需求曾写过暂定默认：不同项目可并行、槽位默认 3 个且可配置、同一项目一次只进行一个事项。这些是历史口径，不是已实施的行为；实施前要以当时有效的设计说明为准。

**落地方向。** 思考并发时先划分焦点，而不是先加线程：

- 应当互不相交：各事项的 `run:` 流、工作区、任务内 Git（`<data-dir>/git/<run_id>.git`）、检查副本。
- 可能冲突、必须经写入口与流版本解决：同一 `project:` 流（采纳、形态、目标）、`catalog:` 流（模型目录、排空）、进程级 Provider 与本机执行资源。
- 同一项目内是否仍串行，是产品取舍，不是透镜定律能替你决定的；定律只要求：一旦允许两个焦点写同一流，就要有可叙述的 `put-put` 规则，而不能靠「谁快谁赢」却不留下冲突记录。

任务池路由若出现，应是路由契约的又一种实现（`routing_contract.py` 已为「任务池那一种」留了可选方法），不应另开写入口。光学是设计这层并发的语言，不需要先引入 optics 库。

## 6. 拓扑斯：把日志看成带内部逻辑的宇宙——但只解决形式化之后的自洽

**概念是什么。** 拓扑斯是一个「足够像集合」的范畴，带有内部逻辑和子对象分类子。可以在里面写命题、取子对象（满足命题的那些元素），逻辑不必是经典的二值：可以有「尚未判定」这类真值。

**为什么对 Yudao 有用。** 事项状态、角色公约、工具许可能否写成日志宇宙里的命题，并且由系统自己计算，而不是只在外部用自然语言互相解释。对「进行中 / 等待决定 / 排空 / 开环」这类非二值状态，子对象分类子比硬塞成 true/false 更贴切。

**对应现有架构哪部分。** 今天没有内部逻辑引擎。接近的原料是：事件种类与骨架事件登记、定义里的规则条文（`harness/definitions/rules.json`、组织里的 `rules` 字段）、路由与裁决已经在计算机上可判定的那些谓词（谁能开工、工具是否许可、提案能否接纳、事项以何原因结束）。`read_models` 与查询把其中一部分编成可检索的表，但表不是分类子。

必须写清两道界限。第一，拓扑斯解决的是形式化之后的自洽：「这些命题在同一宇宙里会不会互相打架」。它不解决「自然语言意图如何变成范畴里的对象」。意图解析、建档、`ask_user` 与产品合同仍然需要现在的那一层，不能跳过。第二，这与外部形式验证（在系统之外用另一种工具证明性质）不同：外部证明可以给内核清单里的规则做补充证据，但运行中的事实仍只经写入口进入 Yudao 自己的日志；把证明当事实写入，也要走同一条缝。

**落地方向。** 排在后面。若要做，应先挑一块已经形式化的碎片——例如停止原因清单、工具许可、开环与放行的互斥——写成可机器核对的内部命题，再考虑真值是否多于二值。不要从「用拓扑斯理解需求原文」起步。

## 7. 米田引理：对象由它发出和接受的箭头决定

**概念是什么。** 米田引理说，一个对象被它到所有其他对象的射族（以及从所有其他对象射进来的族）完全决定。工程上的推论是：不要先问「这个角色内部是什么」，而要问「它向谁发出什么、接受什么、与谁交换什么」；重构时改关系，而不是先改实现细节。

**为什么对 Yudao 有用。** 形态要可替换，内核就不能认识「产品」「工程」这些专名的内部心理学。角色应当由它可调用的工具、可提交的提案、关注的成果、核验关系来定义。这正是换形态时只换定义与路由、不换写入口的原因。

**对应现有架构哪部分。** 这是七条里与现状对得最直的一条。

- `harness/definitions/roles.json`：每个角色列出 `tools` 与 `visibility`，再加职责说明；产品没有写交付代码的工具，也不能放行。
- `harness/definitions/organization.json` 与形态目录：部门、关注的成果、`sources`、`verification.verifiers`（谁核验谁的哪种成果）和写入范围。换一份形态就是换一组箭头。
- 工具许可：`adjudication.py` 按定义中的部门工具集与路径规则判断，不按模型自称的身份。
- 路由契约（`harness/routing_contract.py`）：薄驱动只问「谁能开工、一轮以何结束、事项以何结束、询问分支如何接」，不认具体路由类名。`watched_outputs` 与 `direct` 是两种不同的射族，由 `register` / `select` 按组织里的 `routing` 名称接上。
- 内核事件与提案字段是通用说法（事项、成果的某一版及其依据、提案、回执），不认部门种类——ADR-0044 的分层与米田方向一致。

**落地方向。** 继续把「新能力」写成新的箭头（新工具、新提案种类、新核验声明、新路由问题），而不是在薄驱动或写入口里写死部门名。重构时先改定义与契约测试，再改实现。米田给出的是定义风格，不是把角色 Yoneda 嵌入搬进运行时的理由。

## 建议的采用顺序，以及过度形式化的风险

当前仍是骨架阶段：固定的是循环、边界、裁决，职能与轮转是填进结构的内容，并发与任务池还在路线图的「等」。采用范畴论，应按「先能约束下一步会改到的缝，再谈更强的内部逻辑」来排，而不是按理论的漂亮程度来排。

1. **光学与极限，优先。** 下一道会碰到的结构问题就是多事项 / 多项目并发（代码中的 3.4A，路线图道 03、道 10）。先用焦点、互不相交的流、以及共享流上的 `put-put` 规则把槽位设计说清楚，并且继续守「日志只有一个写入口」。
2. **米田，保持。** 角色与路由已经按关系定义。新形态、外包角色、观察者沿这条路走即可，不必另起一套理论工程。
3. **余递归的终止，巩固。** 放行与开环完成已经分记。新路由必须交出同样可核对的结束原因；不要让「完成」重新变成经验口头语。
4. **单子，作为讨论与审查用语。** 用来检查新实现有没有绕过 `bind` 该经过的写入口与停止清单。不值得为此改运行时形态。
5. **伴随，只作启发式检查清单。** 用来发现「生成者裁决自己」，不用来证明角色分工最优。
6. **拓扑斯，最后。** 只在一小块已经形式化的规则上试验内部逻辑；不承担意图理解，也不替代评测。

主要风险是把隐喻写成定理。一旦把「应当像极限」说成「已经证明唯一」，或把「像伴随」说成「因此三职能最优」，后续设计就会被虚假的必然性锁死。范畴论在这里的正当用途是：给出组合时必须守住的方程与唯一性要求，并标明现状离这些要求还有多远。判断一个具体形态好不好用、一次放行有没有误判、压缩会不会把时限吃满，仍然要靠设计质量、试用和评测，不是靠把更多数学符号写进仓库。
