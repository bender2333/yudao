## 0. 一句话

楼就是 Yudao 自己。它由两半构成：一半是 Yudao 这台机器（一份事实、裁决、循环、路由、组织，以及把它们隔开的缝），另一半是这台机器加工的软件工程对象（意图、要求与验收条件、设计、计划任务、交付、检查与证据、缺陷、放行，以及被谈论的模块、文件、接口）。本体就是这两半的种类和关系，每个种类以总图为准、对到代码、标在四层中的一层。脚手架（`workflow.md`、`canon.json`、`roles.json`、技能、工单与标签）是现在盖楼用的架子，不进本体。

第一步：把下面第 2、3 节的种类与关系写成一份手写的数据，再从现成的结构化来源（name-map 的表、定义文件、骨架事件）编译出实例，跑三条检查，看它能不能复现已知的问题、并找出至少一条 name-map 里还没写的。等你点头再做。

## 1. 放在哪一层

| 层 | 是什么 | 例子 |
| --- | --- | --- |
| M3 | 写本体用的格式 | clingo 的事实与规则（第一版第 4 节） |
| M2 | **Yudao 本体**（本方案） | 事项、事件、回执、部门、核验、成果种类、要求、缺陷、模块 |
| M1 | 某个被开发的项目的领域模型 | 笔记本应用的 DDD：笔记、标签、同步；自举时就是 Yudao 仓库自己 |
| M0 | 一次运行里的具体事实 | 第 1832 号事件、某个事项的第 3 版交付 |

脚手架不在这四层里。它是开发 Yudao 的人和 agent 现在用的流程，属于规则事实线（main 上已经做完的那条）。

自举在这里有一个直接的落点：Yudao 开发 Yudao 时，那个项目的 M1 写的正是 Yudao 的模块、文件、接口，而这些东西的意义由 M2 说明。同一个名字会出现在两层（M1 里的术语「事项」、M2 的种类「事项」），两层之间只用一条「对应」关系连起来，不合并（第 5.2 节）。

## 2. 种类

每个种类写：它是什么、出自总图哪里、对到哪段代码、属于哪一层。代码一栏的状态照抄 name-map：一致、不一致、未建。四层用总图第一节的分法：事实与裁决（内核）、循环、路由、组织。另有两组不归某一层：缝与环（结构本身）、加工对象（软件工程的对象）。

### 2.1 事实与裁决（内核）

总图说内核只认这几样：事项、事件、某种成果的某一版及其依据、提案、回执、角色的写入范围、上限、决定请求。本层的种类就从这句话来。

| 种类 | 是什么 | 总图 | 代码 | 状态 |
| --- | --- | --- | --- | --- |
| 事件 | 事实的唯一载体，带序号，只追加 | 第一节「一份事实」、方程 | `kernel_events.py` 的 `SkeletonEventType`、`event_store.py` | 一致 |
| 流 | 事件的分组：项目流、事项一次执行的流 | 第四节投影 | `run_stream`、项目流 | 一致 |
| 事项 | 一件要做成的事，系统的工作单位 | 第一、三节 | 项目流里叫 `work_item`，一次执行叫 `run` | 不一致（两个名字并存） |
| 执行权 | 此刻由谁推进这个事项 | 方程「执行权」 | `claim_execution_right` | 一致 |
| 派发编号 | 一次派发的编号，防止旧的派发写进来 | 方程「派发编号」 | 事件 `dispatch_number_acquired`、`event_store.py` 的 `dispatch_number` | 一致 |
| 提案 | 模型的输出，只能提议，不能宣布状态已改变 | 第一节、基础规则 3 | 事件 `proposal_submitted`、`proposal_rejected`；`proposal_contracts.json` | 一致 |

| 快照 | 封存的一份工作区，起点和终点 | 第一节「一份事实」；第四节动作 | `snapshot.py`、`workspace.py` 的 `WorkspaceSnapshot`、`SnapshotRef` | 一致 |

| 裁决 | 接纳或拒绝一个提案，三种手段按顺序：规则、判定点、升级 | 第一节「裁决」；D38 N-J1 | `adjudication.py`；判定点没有 | 部分未建 |

## 4. 怎样服务两个用途

### 4.1 用途一：规格驱动的一致性

总图、意图、术语表、代码、测试五样东西都描述同一座楼，本体是它们共同对的那份名单。能查的分三类：

1. 总图对代码。每个种类要么有「实现」关系，要么标未建。name-map 已经是人工维护的这份对照，本体把它变成可以算的事实，再从代码里直接读一遍去复核它。这一步现在就有用：写方案时对照 main，发现 name-map 有两行已经过时。写入范围一行还写着裁决按部门名 `quality` 写死，其实 #1390 已经改成读声明；成果种类一行还写着放在路由定义里，其实 #1456 已经移成定义里单独一项。人工维护的对照会落后于代码，这正是要机器核对的地方。
2. 分层。内核层的代码不应该提到外层的实例名（某个部门名、某个成果种类名）。这正是你说的「不变的放内核，变的放外圈」。11 月 4 日还有两处（`definitions/__init__.py` 里固定的 7 个成果名、`adjudication.py` 里的 `quality`），#1456 与 #1390 合并后，按名字搜已经找不到。这条检查的用处变成守住它，以后谁再写死一个部门名就报出来。第一版写过扫描的代码（`layering.py`），但当时拿脚手架的词去比，现在改成拿第 2.3、2.4 节的实例去比。
3. 总图自身的矛盾与缺口。例如：每个被关注的成果种类必须有部门产出它；每个被核验的成果种类必须有核验者；核验关系无环；每个新增部门写了目标函数与证据来源（D38 N-I6）；每条需求编号引用的总图位置存在；总图在内核清单里列的词，`CONTEXT.md` 都有词条。最后一条现在就不满足：术语表没有事项、提案、回执、成果、执行权、上限、停止原因、PRD、交付、缺陷、放行的词条。
4. 代码对测试。每条内核规则对应一个测试名称（D38 N-K4），每个验收条件有检验或标开环（N-K2）。这一类等要求链建出来才能做全，第一步不做。

### 4.2 用途二：AI 上下文装配

两处用得上同一份本体。

一处是 Yudao 运行时给部门装配上下文。[语义系统](../design/semantic-system.md)第 10 节的「焦点与目录」「接触时附加」需要知道一条内容是什么种类、关于哪个实体、和谁在要求链上相连。第 2.6 节和第 3 节的要求链就是它要的那份类型表。这里要统一一件事：组织定义里的成果种类（`product_spec`、`delivery_spec`、`qa_review`）和语义系统的内容种类（要求、交付、缺陷）现在是两套名字说同一些东西。本方案的处理是：成果种类是「部门交出来的那一版」，内容种类是「图谱里拆出来的条目」，两者用「产生于」相连（主机从接纳的 `product_spec` 生成要求条目，语义 5.1 已经这样写了），不另起第三套名字。

另一处是 agent 在开发 Yudao 本身时取上下文，也就是自举第一层。一张工单碰到路由，按本体就能取齐：总图第一节「轮转方式」、name-map 路由一节、`routing_contract.py` 与 `watched_outputs.py`、它们的测试、D38 的 N-A1 至 N-A5。这比按文本相似度检索准，因为连线是写下来的，不是猜的。

两处是同一份 M2：运行时用它给项目的 M1 内容分类，自举时 Yudao 仓库的 M1 恰好就是这座楼的实例。

## 5. 边界

### 5.1 和脚手架

脚手架里有一批词和楼里的词同名，本体只取楼里的意思，脚手架的那份只标出来、不建模：

| 词 | 楼里的意思（进本体） | 脚手架的意思（不进） |
| --- | --- | --- |
| 审查者 | 部门里的一种运行时角色 | `roles.json` 里开发流程的审查角色 |
| 检查 | 项目的检查定义与检查回执 | CI、文档一致性这些开发用的检查 |
| 提案 | 模型的输出，等裁决 | 开发流程里提一个 ADR 或改动 |
| 证据 | 回执、跑一遍、换模型、人 | 工单与 PR 里贴的证据 |
| 交付 | 成果种类 `delivery_spec` 的一版 | 一张工单交出的东西 |
| 放行 | 质检结论 `release` | 合并、发布脚本 |
| 子事项 | 运行时的子循环 | 子工单 |
| 设计说明、总图 | 不是种类，是本体的来源文档 | 同左 |

只属于脚手架的词整个排除：父工单、子工单、试用工单、里程碑、阶段工单、桶、道、薄片、清理单、标签。name-map 表里「归哪道缝或哪条道」一栏的「道」是路线图的车道，也属于脚手架，编译时只取「缝」。

顺带看到的一处：`CONTEXT.md` 的「系统结构」一节把上面这些脚手架词和楼里的词放在一起。建议以后在 main 上分成两节，这次不动。

### 5.2 和产品的领域模型

产品的概念（笔记本应用的笔记、标签、同步）永远是 M1，在那个项目的图谱里作为「术语」类型的实体出现，不会变成 M2 的种类。M2 只随 Yudao 的版本增加种类、关系与字段（语义 5 节开头已经这样规定）。DDD 的聚合、限界上下文是 M1 的写法，Yudao 本体不规定产品必须用 DDD，只提供「实体」「术语」「模块」这些容器。

自举时同一个名字会出现在两层。规则是：M1 里叫「事项」的术语实体，用「对应」关系指向 M2 的种类「事项」，两者不合并。这样 Yudao 改自己的定义时，改的是 M1 的内容，M2 只有发版才变，生成者改不了评价自己的标准（基础规则 3）。
