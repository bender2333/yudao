### 2. 模块至分层的规范映射与比对结果

依据 `docs/design/architecture/overall-architecture.md` 第 1 节分层图、第 2 节职责边界表及第 6.1 节控制核心模块规范，与实际代码依赖逐条比对，结果分为**一致**、**多出**、**缺失**三类：

```
+----------------------------------------------------------------------------------------------------+
| 总体架构设计分层 (overall-architecture.md)             | 实际代码模块与依赖比对状态                       |
+----------------------------------------------------------------------------------------------------+
| 界面与命令行 (Client): client/, harness/__main__.py    | 一致: 仅通过 API 与应用层交互                   |
| 接口层 (Interface): harness/api/                       | 一致: 仅导入 harness.app.* (受到 importlinter 强约束) |
| 应用层 (Application): harness/app/                     | 一致: 处理命令并查询投影，不直接越权操作工作区 |
| 流程编排 (Core: Orchestrator): orchestrator.py         | 多出 (违规侵入): 直接管理环境与检查工作区生命周期 |
| 步骤驱动 (Core: StepDriver): engine.py, recording.py   | 一致: 步骤循环单向调用装配(P)与裁决(U)          |
| 上下文装配 (Core: Assembly P): assembly.py, context.py | 一致: 读取历史与材料生成请求提示词             |
| 裁决规则 (Core: Adjudication U): adjudication.py       | 一致: 提供纯函数式工具许可与提案校验           |
| 可信内核边界核对 (Core: Boundary Kernel): (独立模块)    | 缺失: 仍内嵌在 orchestrator.py 内部 (B2 未拆出) |
| 写入口与事件日志 (Core: Store): write_path.py, etc.   | 一致: 唯一点追加事实与投影更新                 |
| 定义与参数 (Definitions & Params): definitions/        | 一致: 静态 JSON 数据带版本驱动                  |
| 执行层 (Execution): environment.py, providers/         | 多出 (业务渗透): environment 硬编码质检测试特殊分支 |
| 知识层 (Knowledge - D25 语义系统): (未实施)             | 缺失: 轨迹图谱与状态推导完全未实现             |
| 观察层 (Observation - D28 元观察/JEV): (未实施)        | 缺失: 判定点准入与校准推导完全未实现           |
+----------------------------------------------------------------------------------------------------+
```

#### 逐条详细比对分析：
1. **一致条目**：
   - `Interface -> Application`：`harness/api/` 的 13 处导入全部指向 `harness.app`，无越层调用。
   - `StepDriver -> Assembly(P) & Adjudication(U)`：`harness/engine.py` 严格按照规范，通过 `ContextAssembly` 获得请求，通过 `tool_permission` / `proposal_decision` 获得裁决，未向上依赖流程编排。
   - `Core -> Store`：写入口（`WritePath`）与事件存储（`EventStore`）保持单一出口，事务内完成投影更新。
2. **多出条目（架构边界漂移与反向渗漏）**：
   - **编排器越权掌控执行环境**：`harness/orchestrator.py`（第 35-37 行、438-471 行）直接导入并调用了 `LocalEnvironment`、`inspection_root`、`cleanup_inspection_workspace`，直接创建并刷新 `inspections/<run_id>/<dept>` 工作区。规范要求编排器“只调用步骤驱动的开始、取消与取得结果，不接触环境与动作内部”，但编排器目前深度参与了文件物理生命周期管理。
   - **通用执行环境硬编码部门业务**：`harness/environment.py`（第 613、655 行）直接出现 `if action.department == "quality":`，在执行通用检查时硬编码触发 `capture_qa_tests()`。这破坏了执行层的通用性，将高层部门业务逻辑直接写死在底层执行服务中。
   - **根目录模块平铺蔓延**：`harness/` 根目录下平铺了 24 个混合职责模块（如 `bounds.py`, `collaboration.py`, `contracts.py`, `materials.py`, `projects.py`, `snapshot.py`, `tools.py`），导致各子模块之间产生网状交叉依赖。
3. **缺失条目**：
   - **独立内核边界核对模块缺失**：`overall-architecture.md` 第 6.1 节规定，时间、轮次、深度的核对以及停止原因的写入属于“从 orchestrator.py 分出的独立内核模块（B2）”，但当前代码中上述边界判定仍混杂在 `Orchestrator` 的实例方法中。
   - **语义知识层与观察层缺失**：D25 知识层与 D28 观察层仅停留在设计文档层面，代码中完全缺失。

## 五、方法 4：质量属性场景走查（Quality Attribute Scenarios）

将 CLAUDE.md 中规定的 5 条判据与 3 条核心目的，逐一形式化为质量属性场景（刺激、响应、度量），并在当前代码结构上进行穿透走查：

```
+----------------------------------------------------------------------------------------------------+
| 判据 / 目的      | 质量属性场景 (刺激 -> 响应 -> 度量)                        | 架构现状走查结论           |
+----------------------------------------------------------------------------------------------------+
| 判据 1: 持续负载 | 刺激: 评测提交复杂场景 (场景 3)                            | 失败: 3 次运行 100% 超时,  |
|                  | 响应: 系统无人工干预自主完成三部门交接与放行              | 质检无法闭环, 负载运行中断 |
|                  | 度量: 单任务时限 (90m) 内正常放行结束率 (当前: 0%)         |                            |
+----------------------------------------------------------------------------------------------------+
| 判据 2: 能够度量 | 刺激: 针对固定场景重复运行多次                            | 假性通过: 虽有指标文件,    |
|                  | 响应: 输出可对比的循环次数、完成度、正确性与 Token/时间成本 | 但循环未闭环 (cycles恒为1), |

|                  | 度量: 评测环境与运行态之间是否保持严格单向隔离             | 词并用 hack 注入文件       |
+----------------------------------------------------------------------------------------------------+
```

## 七、五大核心架构与需求发现

按对核心决定的影响严重程度，由重到轻排序：

### 发现 1（最关键阻碍）：质检部门开环死循环与验证脚手架缺失，导致三部门循环永远无法完成放行闭环

- **现象**：
  - 在场景 3 的 3 次计入运行中，Yudao 的运行放行率（Release Rate）为 **0%**（`ended_within_limit: passed=False`，`quality_release_bound_to_delivery: passed=False`）。
  - 证据：
    - `yudao-q38f-start-1/evidence/yudao/yudao-q38f-start-1/run-export.json`：Event 1550（`department_activated: quality`）到 Event 1894（`run_failed: cancelled`），质检执行了 27 次工具调用，但 `proposal_submitted` 为 **0**。
    - Event 1865、1878、1893：质检深陷在用 `python -c "replace bad lines"` 修复 `.yudao-qa-tests/qa6.py` 语法错误的死循环中。
- **原因链**：
  - **需求层 (D11/D38)**：要求“质检必须独立挑错，严禁在未经独立验证时宣布完成”，确立了独立挑错的目标，但未界定独立挑错的**形式边界与复杂度上限**。
  - **设计层 (`docs/design/department-loop.md`)**：只将质检视为一个普通角色的步骤循环，未提供结构化检验脚手架，直接暴露了图灵完备的自由 `bash` 工具。
  - **Prompt / 工单层 (`harness/definitions/roles.json`)**：质检 Prompt 强令“必须自行设计测试，不能信任研发的自测”，大模型受此刺激，倾向于在沙箱中从零徒手编写包含多文件、长断言的完整测试工程。
  - **执行环境层 (`harness/environment.py:529-532`)**：`_bash` 每次都是新进程，无状态特性迫使质检用 heredoc 大量写盘，而在 Windows 环境下跨行转义和编码极易出错，引发模型长链路试错。
- **对照案例**：
  - `oc-q38f-1`：OpenCode 单 agent 没有“自我证明独立性”的负担，仅用 3 次短小的 python assert 验证核心边界，快速完成自测退出（1947s 成功结束）。
- **可以被推翻的预测**：
  - **预测**：若不给质检提供结构化测试模板并设立测试编写步数硬上限，进入 M2 场景 2/3 回归时，Yudao 在 90 分钟内的放行完成率将持续为 **0%**，`ended_within_limit` 将 100% 判定为失败。
  - **检验数字**：场景 3 重测中 `quality_release_bound_to_delivery.passed == True` 的发生次数（预期仍为 0）。
- **最小处理办法与代价**：
  - **最小处理**：在质检 Prompt 与环境中引入“轻量化检验契约”——禁止质检编写多文件框架，强制使用单脚本断言；设置质检阶段的硬步数限额（如最多 8 步必须给出 `Release` 或 `Defects`）。
  - **不处理代价**：系统永远停在质检阶段，三部门协作架构沦为无限吞噬 Token 的黑洞，无法拿到任何交付质量读数。

### 发现 2：工程部门步骤严重膨胀与上下文线性累积，吞噬 80% 资源窗口

- **现象**：
  - 3 次运行中，工程部门消耗了总时间的 80%~90%（Run 1 耗时 4206s = 70.1 分钟；Run 3 耗时 4514s = 75.2 分钟）。
  - 单次运行消耗 Token 超过 1000 万至 1500 万（Run 1: 10,034,931；Run 3: 15,819,250）。
  - 证据：
    - `run-export.json`：Run 1 中工程单次激活包含 110 次模型请求；Run 3 包含 178 次模型请求。
    - Step 90 的 `context_assembled` 事件中，输入 Token 预估已达 **88,240**（单次调用延迟超过 35 秒）。
- **原因链**：
  - **需求层 (D08)**：规定“当前部门内不能遗忘过去的上下文”。
  - **设计层 (`docs/design/context-compaction.md`)**：自动压缩以 128k 窗口为基准，触发阈值过高，导致会话长期在 50k~90k 的高位运行，单步推理极慢。
  - **代码与工具层 (`harness/workspace.py`, `harness/engine.py:490`)**：研发频繁调用 `read_range`（行级哈希）与 `edit_range`，每次微小修改均伴随完整的树状态检查与事件序列追加；稍有行号偏移即需要重新读取，造成轮次剧烈膨胀。
- **对照案例**：
  - `oc-q38f-1`：OpenCode 采用整文件读写（`read`, `write`, `edit`），全流程仅用 31 次请求即完成所有功能实现（耗时 1947s，输入 Token 7.9M）。
- **可以被推翻的预测**：
  - **预测**：若不约束工程单激活步数上限并优化上下文截断，后续 M2 面对已有数千行代码的项目时，工程部门单次激活将 100% 触碰超时阈值，Token 开销将突破 3000 万/run。
  - **检验数字**：单次 run 的 `model_requests` 是否能降至 60 次以内。
- **最小处理办法与代价**：
  - **最小处理**：为工程部门激活设置更严格的步数上限（如 30-40 步）；将冗长的工具输出（如包含整段代码的输出）在后续步骤的上下文中仅保留引用哈希；迫使工程提早交付，把完善度交由质检挑错反向驱动。
  - **不处理代价**：留给质检的时间窗口几乎为零，且单次回归成本高达数十美元，彻底失去“改一处便宜且可反复运行”的可迭代性。

### 发现 3：流程编排核心单体化与高频共变死锁，阻碍规则与参数的轻量演化

- **现象**：
  - `harness/orchestrator.py` 单文件行数达 **1,990 行**，类方法 **85 个**，改动量（churn）高达 11,332，热点得分 **22,550,680**（远超全仓库所有其他模块）。
  - 共变分析显示：`models.py <---> projection.py` 共变 51 次，`models.py <---> orchestrator.py` 共变 45 次，`orchestrator.py <---> projection.py` 共变 43 次。
  - 证据：
    - `git log --numstat` 统计显示，编排器在近 1 个月内几乎每一个功能 PR 都会被改动。
    - Issue #467 评论中架构师明确记录：Orchestrator 1798 行（AST 类定义内部行数），维持过大状态。
- **原因链**：
  - **设计层 (`overall-architecture.md`)**：分层定义良好，但缺乏模块物理隔离守卫。编排器不仅承担事项状态迁移调度，还承揽了工作区清理重建、边界时限轮次判定、提案接纳副作用执行等诸多职责。
  - **代码层 (`harness/orchestrator.py:438-471`)**：未实现 B2 规划的“边界核对内核模块”，将时间、深度、检查工作区的操作全塞在 `Orchestrator` 内部；任何对事件模型（EventType）的扩充，都必须自顶向下贯穿编排器。
- **对照案例**：
  - `harness/api` 与 `harness/app`：通过 `pyproject.toml` 中的 `import-linter` 强力阻断，使得接口与应用层边界极其清晰，共变次数极低（仅 13 次）。
- **可以被推翻的预测**：
  - **预测**：若不在进入 M2 前完成 Orchestrator 职责剥离，M2 引入多项目并行或远程执行时，`orchestrator.py` 将突破 2,500 行，且针对循环规则或参数的任何修改均需动用核心代码提交，彻底违反判据 3（“换版本不用改代码”）。
  - **检验数字**：`orchestrator.py` 的代码行数与共变文件对数量。
- **最小处理办法与代价**：
  - **最小处理**：执行 B2 计划，将超时、轮次、深度检查抽离为独立内核判定函数；将检查工作区创建与销毁逻辑下沉至 `LocalEnvironment`。
  - **不处理代价**：代码复杂度失控，回归测试不断因编排器细微修改产生连带损坏（如 CI 中的 `test_time_limit_checked_between_activations` 频繁脆弱失效）。

### 发现 4：新建项目初始资产挂载机制断层，破坏评测真实性与“锚点受保护”判据

- **可以被推翻的预测**：

### 发现 5：三部门尚未展现超越单 agent 的质量机制，目前仅为高开销的单向流水线

- **现象**：
  - Yudao 的三部门循环在场景 3 实测中表现为**完全单向的流水线**：产品 -> 工程 -> 质检超时，`projection.cycles` 恒为 1，`projection.rework` 恒为 0，`projection.collaboration` 仅在 Run 2 发生 1 次。
  - 产出制品的 Correctness（0.958, 0.916, 0.916）与 OpenCode（0.916, 0.916, 0.941）在同一水平，但 Yudao 耗时是 OpenCode 的近 3 倍（5400s vs 1500~1900s），Token 消耗是其近 2 倍。
  - 证据：
    - Yudao 在 Run 1 中遗漏的 `unit_2_5`（换乘偏好模式下的线路规划错误），OpenCode 同样遗漏了。三部门本应依靠质检抓住此类复杂边界并迫使工程返工修复，但质检从未出具任何缺陷报告，自我纠错机制完全未生效。
- **原因链**：
  - **运行逻辑层**：由于工程耗时过长，质检没有足够的计算与时间预算来完成有效检验并开出返工单。
  - **架构目标层**：系统目前只打通了“能够调用模型生成数据”的粗糙骨架，尚未调谐到“多部门通过错误独立性带来质量增益”的临界点。
- **对照案例**：
  - 待定（Yudao 至今在外部复杂多文件评测场景中，尚未产生任何一次由质检挑出工程隐藏 Bug、工程返工后通过且最终质量超越单 agent 的完整记录）。
- **可以被推翻的预测**：
  - **预测**：如果只追求功能覆盖（直接做 M2 的远程执行或多项目并行），在场景 3 乃至场景 2 上，Yudao 的评测得分将持续无法战胜 OpenCode，无法在任何报告中出具“质量高于单个 agent”的第一份置信读数。
  - **检验数字**：场景 3 中 Yudao 正式放行产物的隐藏检查通过项数与 OpenCode 的净差值（当前为 0 或因超时判负）。
- **最小处理办法与代价**：
  - **最小处理**：以场景 3 为抓手，强制跑通一次“工程出现缺陷 -> 质检独立捕获并提 Defects -> 工程返工修复 -> 质检放行”的真实全闭环。
  - **不处理代价**：背离系统的首要根本目的（“同一个模型下，交付质量高于直接使用单个 agent”），沦为一个架构复杂但效能低下的玩具。

## 八、诊断结论：投入方向的唯一决策

依据上述 5 项事实发现及因果链条，严格回答本次诊断所服务的核心决定：

### 【结论】
**里程碑 M0 完成以后、M2 开始之前，投入必须唯一且坚决地放在【三部门循环的收敛与评测闭环】上。**  
具体而言，既不是提前抢跑 M2（接入已有项目/远程执行），也不是在 M1 的前端界面（像素画面、UI 动效）上继续细化，而是投入一个聚焦于**“收敛与度量底座”**的攻坚阶段，打通场景 3 的完整放行与纠错闭环。

### 【决策依据与因果推导】

1. **为什么绝不能提前进入 M2？**
   - M2 的核心内容是“接入已有项目”（3.8）与“远程执行环境”（3.2C）。
   - **事实证明**：在场景 3 这样一个从零开始、仅有数百行代码的全新项目上，Yudao 的工程部门就已经耗费了 75 分钟和 1500 万 Token，质检部门更是在 90 分钟内连一次测试都未能写完。
   - **后果推导**：如果此时强行进入 M2，面对拥有数千行既有外部代码、复杂构建环境的真实项目，上下文膨胀和步骤爆炸将立刻指数级恶化，Yudao 将百分之百陷入无休止的步骤超时和内存耗尽，系统将在未收敛的泥潭中彻底瘫痪。

2. **为什么不需要在 M1 界面上追加投入？**
   - Issue #183 的事实显示，M1 的核心子工单已全部关闭，并与 M0 合并交付走查。
   - 界面是“表演层与事实展现”，在核心循环无法收敛、每次运行结果都是 `FAILED / cancelled` 的情况下，界面再精美也只能展示超时报错，对系统进入“可迭代状态”贡献为零。

3. **为什么“三部门收敛与评测闭环”是唯一正确的投入点？**
   - **直接满足判据 1（真实负载）与判据 2（能够度量）**：只要将质检部门从徒手写测试的泥潭中解脱出来（引入轻量测试脚手架与限步裁决），并将工程步数收敛到 30-40 步，场景 3 就能在 45 分钟内顺利闭环。
   - **首次拿到目的 1 的可信读数**：今天的实测中，Yudao 工程交付的代码质量（0.958）本已略微超出 OpenCode（0.916），唯一阻碍取得胜利的是质检未能出具放行报告！只要循环跑通闭环，质检在最后一步完成核查放行，Yudao 就能立即在场景 3 上拿到**“三部门交付质量高于单 agent”的第一个具有统计显著性的可信读数**！
   - **保护评测锚点（判据 5）**：顺带落实 D37 的极简初始文件注入，彻底拔除运行器中的提示词与目录 hack，让评测回归真实客观。

### 【实施路径规划（最小必要动作）】
1. **质检轻量化与限步裁决**：优化质检 Prompt 与工具指导，限制质检编写测试的步数（$\le 8$ 步），强制在测试运行后调用 `submit_quality_report` 或 `submit_release`。
2. **工程上下文与步骤节流**：单次工程激活步数硬封顶（$\le 40$ 步），工具冗余输出次轮剥离，促使其提早交付。
3. **补齐 D37 初始数据文件支持**：让 `project.create` 原生支持挂载输入文件，移除 `evals/runner/yudao.py` 的特异性修补。
4. **验证验收**：在场景 3 上重新运行 3 次，以**“90 分钟内 100% 自主放行闭环、至少产生 1 次有效返工修复、得分全面超越 OpenCode”**作为唯一验收标准。
