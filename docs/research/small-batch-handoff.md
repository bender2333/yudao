# 小粒度交接的证据：切小了是不是更好

日期：2026-10-24。支持的文档：工单 [#834](https://github.com/bender2333/yudao/issues/834)（地图 [#836](https://github.com/bender2333/yudao/issues/836)，阻塞 [#835](https://github.com/bender2333/yudao/issues/835)）。用途：给「要不要做任务池」提供外部证据，只回答交接粒度这一问：把交接从整份 PRD、整份交付缩到小块，正反向都按小块流转，质量与成本会怎样。共享状态怎么组织见 [PR #751 的参照调研](https://github.com/bender2333/yudao/blob/claude/vigilant-allen-t3246c/docs/research/blackboard-orchestration-references.md)，这里不重复；引用其中已有的来源时只补它没写到的部分。

已经决定的前提（[#832](https://github.com/bender2333/yudao/issues/832)）：任务池保留正式成果与质检对整份交付的独立放行，只改工作的切法与下一步由谁做。

读取方式：第 12 节的每份材料读的是全文或全文的主要部分，除非另外注明；没能读到的列在第 11 节。数字都是作者自报，没有独立复现。每条结论后面的方括号是第 12 节的来源编号；没有量化对照的标「只有主张」。

## 1. 调研的问题

1. 小块交接相对整份交接，有没有量化对照（质量、返工、费用、token）。
2. 小块交接时独立验证怎么做：逐块验还是汇总以后整体验，各漏掉什么；下游把上游的错误当事实、验证与上游共享同一个错误假设，这两种情况有什么证据。
3. 谁来拆，拆错了怎么发现。
4. 收益在什么条件下成立。

## 2. 结论摘要

1. **单块越短，单次做对的概率越高，但切小本身不降低总的失败率。** 在 METR 的任务集上，人做 4 分钟以内的任务，模型几乎全部做对，4 小时以上的不到 10% [1]。按 Ord 的常数风险模型，同样总量的工作切成几块，成功概率不变 [2]；收益只能来自块与块之间的检验与重做。几项直接比较「拆」与「不拆」的实验里，拆分本身（不算块间检验）的贡献很小，或者是负的；有收益的拆分都带着逐块的测试或筛选（第 4.2、4.3 节）。
2. **需求按小块到达有明确的反面证据。** 同样的信息分几轮给出，15 个模型平均下降 39%，不稳定性增加 112%；把这些片段合成一次给出，恢复到整份给出的 95% [6]。原因是模型在早期就做假设、给出答案，之后依赖自己早先的答案。
3. **交付按小块、每块有可执行的检验，有正面证据**，例如按函数拆分并逐个测试 [19]、单独的测试设计者 [9]、每个冲刺之后由评估者在运行的应用上测试 [23]。人工代码审查的数据也指向同一方向：一次改动的文件越多，有用评论的比例越低 [27]。
4. **逐块验与整体验各自漏掉不同的东西。** 逐块验会高估整体：同一批交付按需求条目算达成 44.8%，考虑条目之间的依赖是 29%，整个任务达成只有 1.8% [14]。整体验在大块材料上效果下降 [4][27]。在 ChatDev 上加一个针对整体目标的验证步骤，任务成功率提高 15.6% [16]。
5. **验证的独立性来自三件事：验证者不看作者的推理，有外部的执行反馈，验证材料不来自作者。** 只换一个会话不够。验证问题在不看原回答的情况下回答，比看着原回答回答少重复原来的幻觉 [8]；测试由单独的 agent 写，测试准确率从 61.0% 提高到 87.8% [9]；没有外部反馈的自我纠正会让结果变差 [10]；两个模型都答错时，60% 的情况答的是同一个错误答案 [11]。
6. **按需拆分优于一次拆完；拆错了事后很难定位。** 只在执行失败时再拆，成功率比先计划后执行高 27% 至 33% [18]。事后找出是哪一步导致失败，最好的方法只有 14.2% 的准确率 [17]。能找到的做法都把对齐放在动手之前（每个冲刺开始前协商「完成」的定义 [23]），并保留整体检查。
7. **拆给多个 agent 有固定的开销。** 在相同表现下，多 agent 结构用的 token 是单 agent 的 1.6 至 6.2 倍 [13]；Anthropic 的一个单次案例里，三 agent 结构的费用是单 agent 的 20 多倍，换来的是核心功能能用 [23]。
8. **收益成立的条件**（第 9 节）：任务超出模型一次能可靠完成的范围；每块有可执行的检验；块之间耦合弱；接收一块的人看得到整份当前要求；保留整体检验。模型越强，拆小的收益越小 [5][13][23]。
9. **没有找到直接的对照**：多 agent 写代码时「小块正反向流转」对「整份 PRD、整份交付」的实验，也没有返工次数的数据。上面的结论是从相邻实验拼出来的。

## 4. 交接粒度与做对的概率

### 4.1 单块越短，单次越容易做对

- METR 把 170 个软件与研究工程任务按人完成所需的时间排列，成功率随任务长度下降，与对数时间拟合良好。博客的原话是当时的模型在人 4 分钟以内的任务上几乎全部成功，在 4 小时以上的任务上成功不到 10%；作者认为难点在于把较长的一串动作连起来，而不是缺少单步的技能 [1]。
- 同一份论文的失败分类里，o1 的 32 次失败中 16 次是过早放弃任务，GPT-4 的 31 次中 12 次是重复失败的动作 [1]。
- SWE-Bench Pro 的参考解平均改 4.1 个文件、107.4 行；在 SWE-bench Verified 上超过 70% 的模型，在这里的商业代码集上不到 18%。单文件问题的表现稳定，文件数增加时急剧下降 [3]。
- Chroma 在 18 个模型上的测试显示，即使任务很简单，输入越长结果越不可靠；LongMemEval 上，只给相关内容（约 300 token）的版本，所有模型都明显好于给全部历史（约 11.3 万 token）的版本 [4]。这支持「每次交接只装配与这一块相关的内容」。

### 4.2 切小本身不降低总的失败率

- Ord 用 METR 的数据提出常数风险模型：成功概率 P(t) = 2^(−t/T50)，T50 是 50% 成功的任务长度。按这个模型，一个 60 分钟的任务、6 个 10 分钟的任务、一个 20 分钟加 40 个 1 分钟的任务，成功机会相同，只由总的人工时长决定；任务长度翻倍，成功概率变成原来的平方。他据此认为当时的 agent「不太会从早先的错误中恢复」，人在长任务上衰减得慢，是因为人会回头改正失败的子任务 [2]。
  - 含义：切小以后，只有在每块之后能发现错误并重做，总成功率才会提高。没有块间检验的切分只是把同样的失败分摊到更多块上。
  - 限制：作者在 2026 年 2 月的补充里写明，另一项分析发现 agent 的风险率在任务过程中下降，所以 agent 大概并不遵循固定的半衰期 [2]。
- ClassEval 比较三种生成方式：整个类一次生成、逐方法生成并带上已生成的方法、逐方法独立生成。GPT-4 与 GPT-3.5 一次生成最好，类级 Pass@5 比另外两种高 6% 至 9% 与 4% 至 14%；较弱的模型逐方法更好，例如 CodeGeeX 与 SantaCoder 逐方法生成多做对 9% 与 7% 的类。作者的解释是强模型能利用整个类的上下文把握方法之间的约束，弱模型利用长上下文的能力有限 [5]。
- AgileCoder 把产品经理、开发、测试分给不同 agent，按冲刺增量开发。去掉冲刺，HumanEval 与 MBPP 只降 1.0 至 2.5 分；去掉它的代码依赖图（让 agent 知道已有代码的结构），ProjectDev 的可执行率从 57.5% 降到 23.4% [21]。在这份材料里，起作用的主要是「知道已经有什么」，而不是「分几次做」。
- Google、DeepMind 与 MIT 的 260 种配置里，可以并行分解的金融分析任务上，集中式多 agent 比单 agent 高 80.8%；顺序规划任务（PlanCraft）上各种多 agent 结构低 39.1% 至 70.0%；SWE-bench Verified 上低 2.1% 至 14.9% [13]。单 agent 基线超过约 45% 以后，再加 agent 的收益为负 [13]。
- Anthropic 的长时间应用开发实验：第一版让生成者按冲刺一次做一个功能；换到 Opus 4.6 以后，作者去掉了冲刺，生成者不拆分也能连续工作两个多小时，评估者改为在结束时检查一次 [23]。作者的判断是评估者的价值取决于任务是否超出模型单独能可靠完成的范围；在模型单独能做好的任务上，评估者是多余的开销 [23]。

### 4.3 拆分带来收益的地方：拆开以后逐块检验

- Parsel 把算法任务拆成分层的函数描述，每个函数生成多个候选，用测试筛选后组合。APPS 竞赛题的通过率比直接从 AlphaCode 与 Codex 采样高 75% 以上；HumanEval pass@1 从 67% 提高到 85% [19]。
- 先写计划再按步骤实现，Pass@1 比直接生成相对提高最多 25.4% [20]。
- Anthropic 的长时间 agent：初始化 agent 写出 200 多个功能的清单，全部标为未通过；之后的每个会话只做一个功能，做完提交、写进度记录、让代码处于可以合并的状态。原来的失败是 agent 想一次做完整个应用，做到一半上下文用完，留下没写说明的半成品，下一个会话只能猜（只有主张：文中没有前后对照的数字）[22]。

## 5. 正向：需求按小块到达

- Laban 等把 600 条指令各拆成若干片段，比较三种给法：一次给出整份；每轮给一个片段（分片）；把片段合成一份列表一次给出（合并）。15 个模型、六类任务（包括 HumanEval 与 LiveCodeBench 的代码任务）、20 万次以上模拟对话 [6]：
  - 分片相对整份平均下降 39%。能力只降约 16%，不稳定性（同一条指令多次模拟时高分位与低分位成绩之差）增加约 112%。
  - 合并的平均成绩是整份的 95.1%，所以下降不是因为拆分丢了信息，而是信息分几次到达。
  - 两个片段就会出现这种下降；粒度再细，影响不大。
  - 代码与数学任务上，第一次给出答案的时机在对话前 20% 的，平均得分 30.9；在最后 20% 的，平均 64.4。
  - 分片条件下最终答案比整份条件长 20% 至 300%；模型依赖自己早先错误的尝试。
  - 用户模拟与模型的温度都设为 0，分片条件的不稳定性仍在 30 分左右；整份与合并条件下降温能让不稳定性降 50% 至 80%。
  - 每轮都重复之前全部片段（作者称为 Snowball），只挽回 15% 至 20% 的下降；最后一轮把所有片段再说一遍，GPT-4o 从 59.1 回到 76.6，仍低于整份的 93.0。
- 「幻觉滚雪球」：模型先给出错误答案，再为它编造论据。单独问时，ChatGPT 与 GPT-4 能认出这些论据中 67% 与 87% 是错的，但在原对话里会继续沿着错误走下去 [7]。
- MAST 的标注里，「没有请求澄清、按错误假设继续」占 6.8%，「违反任务规格」占 11.8% [16]。
- Cognition 的例子：「做一个 Flappy Bird」拆成背景与小鸟两个子任务分给两个子 agent，一个做出了马里奥风格的背景，另一个做出了与游戏不符的小鸟，最后的 agent 要把两者拼起来。作者的结论是每个动作都带着隐含的决定，决定分散在几个 agent 里就会冲突，因此默认用单线程的 agent（只有主张）[26]。

这一节的材料说明：问题不在「一块小」，而在「接收方只看到一块，并且已经根据前面的块动了手」。把整份当前要求同时给出，表现接近一次给出整份 [6]。

## 6. 反向：交付按小块，与独立验证

### 6.1 逐块验的长处

- 人工审查：Microsoft 五个项目 150 万条审查评论，一次改动的文件越多，对作者有用的评论比例越低 [27]。
- DORA 2024：AI 使用上升，估计交付吞吐量下降 1.5%，交付稳定性下降 7.2%；报告认为过程改进不会自动带来交付改进，前提是遵守小批量与可靠测试这些基本做法 [28]。DORA 2025 把「小批量工作」列为放大 AI 正面作用的七项能力之一，并提醒 AI 工具倾向于一次生成完整的大功能，造成过大的 PR（相关性调查，帖子未给效应量）[28]。
- Anthropic 第一版三 agent 结构里，评估者在每个冲刺之后用 Playwright 操作运行中的应用，按带硬阈值的条目打分，一条低于阈值这个冲刺就不通过；第 3 个冲刺有 27 条。它查出的问题包括：矩形填充只在拖动起点与终点放了图块；删除处理的条件挡住了删除选中的出生点；`PUT /frames/reorder` 定义在 `/{frame_id}` 之后，请求返回 422 [23]。
- 逐条独立核对比整体判断准：CoVe 的 Wikidata 列表任务里，原回答列出的实体只有约 17% 正确，而对每个实体单独提一个验证问题，约 70% 能答对 [8]。

### 6.2 逐块验漏掉什么

- Agent-as-a-Judge 的 DevAI 基准由人工标注 55 个开发任务、365 条有依赖关系的需求。人工评判下，GPT-Pilot 按条目独立计算的需求达成率 44.80%，考虑依赖（前置需求没达成，后面的不算）是 28.96%，整个任务达成 1.81%；OpenHands 是 42.89%、28.68%、1.81% [14]。逐条通过的比例远高于整体完成的比例。
- Anthropic 长时间 agent：agent 用单元测试或 `curl` 检查以后就把功能标为完成，没有发现端到端走不通；改用浏览器自动化像用户一样测试以后，作者称表现大幅提高（只有主张：没有前后数字）[22]。
- MAST：很多验证器只检查代码能不能编译、有没有遗留的 TODO；作者认为只靠最后阶段的低层检查不够，需要同时检查低层正确性与高层目标。在 ChatDev 上加一个针对整体任务目标的验证步骤，ProgramDev 上任务成功率提高 15.6% [16]。
- 测试通过不等于正确：SWE-bench 上通过测试的补丁中 29.6% 的行为与参考补丁不同，其中人工确认 28.6% 肯定是错的，合起来使报告的解决率虚高 6.2 个百分点 [15]。逐块检验的质量取决于每块的测试。

### 6.3 整体验漏掉什么

- 改动越大，人工审查找到有用问题的比例越低 [27]；输入越长，模型越不可靠 [4]。验证者一次读入整份交付，也受这两点影响。
- Anthropic 第二版去掉冲刺、只在结束时检查一次，数字音频工作站这个应用做了 3 轮构建与 3 轮检查，共约 4 小时、124 美元；第 1 轮检查发现时间线上的片段不能拖动、没有乐器面板与效果编辑器，第 2 轮发现录音只是空壳、片段不能拖边缘调整长度或切分 [23]。从列出的问题看，结束时的一次检查查到的多是缺了整块的功能；作者没有比较逐冲刺检查与结束时检查各自漏掉了什么，这一点没有数据。

### 6.4 下游把上游的错误当事实，验证与上游共享错误

- 同一模型会沿着自己早先的错误走下去 [7]，多轮对话里依赖自己早先的答案 [6]。
- 验证者看到原回答时会重复它的错误。CoVe 的作者写明，看着原回答回答验证问题的模型倾向于重复其中的幻觉；验证问题不带原回答、逐条单独回答，长文传记的 FactScore 从联合验证的 60.8 提高到 63.7，再加一步逐条比对原回答与验证结果，到 71.4 [8]。
- 测试与代码出自同一个 agent 时，测试会偏向代码。AgentCoder 的消融：写代码的 agent 自己写测试，HumanEval 上测试准确率 61.0%、行覆盖 72.5%；由单独的测试设计者写，87.8% 与 87.5%；最终 pass@1 从 71.3% 提高到 79.9%，MBPP-ET 从 59.1% 提高到 89.1% [9]。
- 没有外部反馈的自我纠正会变差。GPT-3.5 在 CommonSenseQA 上原本 75.8%，让它检查并修改自己的答案一轮以后是 38.1%；GSM8K 从 75.9% 降到 74.7%。作者指出早先报告的改进依赖于用标准答案决定何时停止，没有标准答案时改进消失 [10]。
- 换一个模型也不一定独立。在一个排行榜数据上，两个模型都答错时，60% 的情况给的是同一个错误答案；同一厂商、同一架构的模型错误更相关，更大、更准确的模型即使架构与厂商不同，错误也高度相关 [11]。用模型做评判时，评判偏向与自己相似的模型；模型越强，错误越难发现、也越相似 [12]。
- 评估者自己也会被说服。Anthropic 调评估者时发现，它有时找到了真实的问题，又说服自己放行，并且倾向于浅层测试；生成者评价自己的作品时普遍自信地夸奖，主观的设计类任务上尤其明显 [23]。
- 多 agent 之间的错误传播：Google 等按执行轨迹估计，没有通信的独立结构把错误放大 17.2 倍，有协调者在汇总前校验子 agent 产出的集中式结构是 4.4 倍；但在他们自己的回归里，这一项在控制效率与开销以后不显著（p = 0.658）[13]。这组数字只能当作方向参考。

这一节的材料说明：验证的独立性来自三件事——验证者在提交判断之前看不到作者的推理 [8]；判断依据外部的执行结果（运行测试、操作应用）而不是阅读 [9][10][23]；测试材料不由作者写 [9]。只换一个会话、或者换一个同类模型，独立性有限 [11][12]。

## 7. 谁来拆，拆错了怎么发现

### 7.1 谁来拆

- 一次拆完再执行的方法，任何一个子任务失败都可能让整个任务失败。ADaPT 先让执行者直接做，失败了才把这一步拆开，拆分的深度随任务难度与执行者能力变化；成功率比基线高最多 28.3%（ALFWorld）、27%（WebShop）、33%（TextCraft）[18]。
- Anthropic 第二版去掉了规划者以后，生成者把范围定小了，做出的应用功能更少 [23]。规划者只写产品层面与高层技术设计，不写实现细节 [23]。
- Anthropic 研究系统早期，主 agent 给子 agent 的任务描述太含糊，子 agent 误解任务、重复别人的搜索；改进以后每个子任务写明目标、产出格式、可用的工具与来源、任务边界（只有主张：没有拆分质量的数字）[24]。同一篇文章认为大多数写代码的任务可以真正并行的部分比研究少，要求所有 agent 共享同一上下文、依赖多的领域不适合多 agent [24]。
- Anthropic 的工作流指南把「提示链」限定在任务可以干净地拆成固定子任务的情况，目的是用延迟换准确率，并在中间步骤加程序检查；子任务不能预先确定时用「协调者加工作者」，例子正是每次要改多个文件的编程产品（只有主张）[25]。

### 7.2 拆错了怎么发现

- 事后定位很难。Who&When 收集 127 个多 agent 系统的失败记录，标注出责任 agent 与决定性的出错步骤；最好的方法找对责任 agent 的准确率 53.5%，找对出错步骤只有 14.2%，o1 与 R1 这类推理模型也不实用 [17]。
- 能找到的做法都把对齐放在动手之前，或者把整体检查留着：
  - 冲刺合同：每个冲刺开始前，生成者提出要做什么、怎样验证完成，评估者审阅，双方迭代到一致；合同写在文件里 [23]。
  - 按依赖计分：前置需求没达成，后面的需求不算达成 [14]。拆错的块会让依赖它的块一起不通过，从而暴露出来。
  - 整体目标验证：MAST 在 ChatDev 上加的这一步提高任务成功率 15.6% [16]。
  - 拆分时带上「已经有什么」：AgileCoder 的代码依赖图去掉以后，可执行率降一半多 [21]。
- 拆错的一种常见形式是接收方在信息不全时做了假设（第 5 节）。Laban 等的数据显示，越早给出答案，结果越差 [6]。

## 8. 成本

- 多 agent 结构的固定开销：在每次试验约 4800 个推理 token 的匹配条件下，独立、去中心、集中、混合四种结构的额外开销分别是 58%、263%、285%、515%，每千 token 的成功数从单 agent 的 67.7 降到 42.4、23.9、21.5、13.6；在相同表现下 token 是单 agent 的 1.6 至 6.2 倍 [13]。
- Anthropic 研究系统的多 agent 用的 token 约为对话的 15 倍 [24]（已在参照调研中）。
- Anthropic 的应用开发案例：单 agent 20 分钟、9 美元，核心的游戏不能玩；三 agent 结构 10 个冲刺、6 小时、200 美元，能玩 [23]。第二版去掉冲刺以后，另一个应用约 4 小时、124 美元，其中三轮检查合计约 10 美元，构建约 114 美元 [23]。每种只跑了一次。
- AgileCoder 在 ProjectDev 上的 token 是 ChatDev 的约 5 倍（36818 对 7440），费用 0.44 对 0.12 美元，可执行率 57.79% 对 32.79% [21]。
- 拆分也可以降低费用：AgentCoder 在 HumanEval 上用约 5.7 万 token 达到 96.3%，作者对照的此前最好方法用 13.8 万 token 达到 90.2% [9]。
- 每块都附上整份当前要求会重复发送同样的内容。Claude 的提示缓存在前缀不变时，读缓存按基础输入价的 0.1 倍计费（Opus 5.5 与 Sonnet 5.5 是 0.05 倍），写缓存 1.25 倍，默认保存 5 分钟，每次命中重新计时 [29]。整份要求放在不变的前缀里，重复发送的费用主要是第一次的写入。
- 返工：没有找到多 agent 写代码中按交接粒度统计返工次数的数据。

## 9. 收益成立的条件

| 条件 | 证据 |
| --- | --- |
| 任务超出模型一次能可靠完成的范围 | 任务越长成功率越低 [1][3]；强模型上拆分的收益缩小或消失 [5][23]；单 agent 已超过约 45% 时再加 agent 收益为负 [13] |
| 每块有可执行的检验，失败可以重做 | 没有块间检验，切分不改变总成功率 [2]；有测试筛选的拆分收益大 [19][9]；在运行的应用上检验能查出阅读查不出的问题 [22][23] |
| 块之间耦合弱，可以并行 | 可分解任务 +80.8%，顺序任务 −39% 至 −70% [13]；编程任务可并行的部分较少（只有主张）[24][26] |
| 接收一块的一方看得到整份当前要求与已有的成果 | 分片 −39%，合并只差 5% [6]；知道已有代码的结构比分几次做重要 [21] |
| 保留整体检验 | 逐条通过远高于整体完成 [14]；整体目标验证 +15.6% [16] |
| 验证者独立于作者的推理与材料 | 第 6.4 节 [8][9][10][11] |
| 每块的交接开销可以接受 | 多 agent 1.6 至 6.2 倍 token [13]；缓存可以降低重复发送整份要求的费用 [29] |

## 10. 对任务池决定的含义

只列证据支持或反对什么，是否做任务池由用户决定。

**支持小块交接的证据**

1. 单块越短，单次做对的概率越高，每次要装配的上下文也越少 [1][3][4]。
2. 每块有可执行的检验时，错误能在扩散到后面的块之前被发现并重做 [2][9][19][23]。
3. 小块更容易审查：改动越小，审查找到有用问题的比例越高 [27]；DORA 的调查把小批量列为放大 AI 正面作用的能力 [28]（相关性）。
4. 按需拆分好于一次拆完 [18]，与任务池「下一步由谁做」按当时状态决定的思路一致。

**反对或限制小块交接的证据**

1. 切小本身不降低总失败率；收益只来自块间的检验与重做 [2]。拆分本身的贡献在几项对照里很小或为负 [5][13][21]。
2. 正向把需求按片段下发、接收方在只看到部分时就动手，是有量化证据的有害做法（平均 −39%）[6]。要按小块派任务，每块的接收方仍要看到整份当前要求。
3. 模型越强，拆小的收益越小：GPT-4 一次生成整个类好于逐方法 [5]；Anthropic 换到 Opus 4.6 后去掉了冲刺 [23]；单 agent 基线超过约 45% 后加 agent 为负 [13]。
4. 写代码这类顺序依赖强的任务，拆给多个 agent 的表现更差：SWE-bench Verified −2.1% 至 −14.9%，顺序规划 −39% 至 −70% [13]。
5. 每次交接与每块验证都有固定开销，token 1.6 至 6.2 倍 [13]，单次案例费用 20 多倍 [23]。
6. 逐块通过不等于整体通过（44.8% 对 1.8%）[14]。已经决定保留的质检对整份交付的独立放行，与这一点一致 [16]。
7. 拆错以后靠事后归因很难找出是哪一块（步骤级 14.2%）[17]，要在动手之前对齐「完成」的定义 [23]。

**与 Yudao 现有概念的对应**（只指出证据落在哪里，不提设计）

- 验证者先提交「独立判断」、之后才看到「作者的解释」，与 CoVe 的逐条独立验证、AgentCoder 的单独测试设计者是同一方向 [8][9]。小块交接下，每块都有作者的解释，这条规则要逐块成立，证据才适用。
- 「开环」与「检验覆盖比例」对应第 9 节第二条：没有可执行检验的块，切小不带来收益 [2]。
- 现状基准（2026-10-20 场景 3 两次都没走到放行，循环 3.5 次、返工 0 次）是在整份交接下得到的。第 4 节的材料无法判断这次失败是因为任务超出模型一次能完成的范围，还是别的原因；第 9 节第一条是否成立，要在任务池的对照里用同一场景测出来。

**没有证据的地方**

- 多 agent 写代码中「小块正反向流转」对「整份 PRD、整份交付」的直接对照实验。
- 质检「逐块验加整体放行」对「只做整体放行」的对照。
- 返工次数随交接粒度变化的数据。
- 中文材料与中文任务上的数据。
