## 1. 结论

不靠高频词，也不靠作者主动写的引用，先建一个**概念模型**，再把文档和代码的说法都变成事实，由规则判断有没有走样。

- **模型**：不从零建，把仓库里已经各自维护的三份半成品合成一份：`CONTEXT.md` 术语表、总图里的缝与方框、「总图的词与代码名对照」（`docs/design/architecture/name-map.md`）。模型放在 `CONTEXT.md`：一个词条就是一页，词条下加一小块固定格式的结构。
- **提取**：文档按模型里的名字和别名自动挂到概念上。脚本能认出的说法由脚本提取；脚本读不懂的文字由 LLM 翻译成「文档说法」。作者不用写标记，也不用写语义链接。
- **判断**：是否走样由规则得出，规则是 clingo 文本，结论带回来源。LLM 只翻译，不判断。
- **工具**：单独的工具，放在顶层 `tools/doc-consistency/`，不和仓库的代码区混合（第 12 节）。

用户已定：

1. 只提醒，不拦提交。
2. 判断走样靠规则，翻译文字可以用 LLM；LLM 由机器调用，不靠 agent 自己想起来。
3. 按名字自动挂。
4. 模型放在 `CONTEXT.md`。
5. 这是单独的工具，不和代码区混合。效果好的话，后续在图谱中支持，作为全局上下文装配的参考。

其余见第 11 节。

## 2. 为什么不跟引用走：一个现成的例子

总图第四节的标题写「九道在系统里，四道在系统外」，`CONTEXT.md`「总图」词条里还写着「十道在系统里、三道在系统外」。

- 两处之间没有任何引用，只看引用的做法看不见它。
- 总图是在提交 33b0254a（画面搬到系统外）改的，那个提交也改了 `CONTEXT.md`，只是没改到这一句。所以按文件看「一起改了没有」也抓不到。
- 只有按内容扫，把全仓所有「N 道…系统里／系统外」都找出来对一遍，才找得到。

引用是作者主动写的，无法保证都有，所以要全局扫描；扫描要有东西可对，这就是概念模型。这一处走样本方案只指出，不改。

## 3. 概念模型是什么

一个概念一条，字段固定，脚本读得懂：

| 字段 | 写什么 | 今天在哪 |
| --- | --- | --- |
| 名字、别名 | 正名，和指它时也算数的叫法 | `CONTEXT.md` 词条名 |
| 不用 | 指它时不该用的说法 | `CONTEXT.md` 的 `_Avoid_` |
| 定义 | 一段话，给人读 | `CONTEXT.md` 词条正文 |
| 定义在 | 正本里的哪一节、哪个方框 | 对照表的「总图位置」列 |
| 关系 | 属于、包含、依赖，指向别的概念 | 写在词条正文里的散文 |
| 取值 | 会被别处复述的数、清单 | 总图，各处各抄一份 |
| 代码 | 对应的类、函数、文件 | 对照表的「代码里现在的名字」列 |

链入页面不存，每次算。

推理用到两类事实，来源和可信程度都不同：

| 事实 | 内容 | 来源 |
| --- | --- | --- |
| 正本事实 | 模型里的名字、关系、取值、代码 | 总图、词条结构块、规则文件里的表格；LLM 提议的内容要架构师确认才进来 |
| 文档说法 | 「这段话这样写」，带原文与位置 | 脚本或 LLM 从文字提取；不代表内容正确，所以不用逐条确认，最多引发一条提醒 |

## 4. 文档和代码怎么变成事实

1. **自动挂**：脚本按模型里登记的名字和别名，在每一节里找到概念，记一条「提到」。没人写引用也连得上。「门」「环」这种单字和「事实」这种常用词在模型里标成不自动挂，只在改动的行里看。
2. **提取文档说法**：脚本按模型里的「写法」认出固定句式，比如「N 道在系统里」。句式认不出的文字由 LLM 翻译（第 7 节）。
3. **代码**：模型的「代码」字段和 Python ast 抽出来的定义两边对：模型写的名字代码里没了要报，内核里新加了公开定义、没有概念认领也要报。
4. **文件之间的引用**：链接、反引号路径、设计说明的总图位置行都作为事实，「从入口走不到的文档」靠它得出。

## 5. 用模型找走样

改动以后只看这次碰到的概念；里程碑结束和第一次上线时全量跑一遍。

| 走样 | 怎么发现 | 把握 |
| --- | --- | --- |
| 复述的取值和模型不一致 | 脚本或 LLM 提取说法，规则比较 | 高 |
| 模型里的名字改了 | 旧名自动留作别名一版，全仓剩下的旧名都提醒，给改法 | 高 |
| 模型写的代码不在了，或内核新定义没人认领 | ast 和「代码」字段对 | 高 |
| 正本里出现模型没有的名字 | 总图的标题、方框、表格和模型对 | 高 |
| 模型里一个概念的定义或关系改了 | 它的链入页面全部提醒 | 中 |
| 用了「不用」的说法 | 只在改动的行里报，整仓报噪音太大 | 中 |
| 两段文字对同一件事说法相反：谁负责、属于哪里、是否已实施 | LLM 提取说法，规则比较 | 待第 13 节的试验 |
| LLM 标了「说不清」的段落 | 脚本判断不了，把那段话和相关定义摆在一起 | 低，由正在干活的 agent 看 |

第 2 节的例子落在第一行：模型里「缝：系统里 = 9」，`CONTEXT.md` 那句写「十道在系统里」，不用任何引用就报出来。一份文档走不到任何概念、从入口也走不到，就是减法的候选。

## 6. 新概念怎么进模型

- **入口只有一个：改模型。** 和现在一样由架构师改；总图里的概念由总架构师在改总图的同一次改动里改。仓库规矩已经写着「总图的词与术语表不一致时以总图为准」，模型跟着总图走。
- **工具摆出「像是新概念」的地方，但不看词频**：总图里新出现、模型没有的方框、缝、表头；设计说明里新加的标题；内核里新加的公开定义；LLM 提取时遇到的、模型里没有的词。每条只有两种关法：进模型，或写明不是概念。
- **总图自己也挂在模型上**：总图是手写的 HTML，它的数字和名字也和模型对。改了总图没改模型，或反过来，都会报。
- 这样 `CLAUDE.md` 里手写的「一次改完」清单就不用人记了：谁复述了总图，由链入页面算出来。

## 7. LLM 放在哪里

有了模型，大部分「语义」变成了确定的步骤：名字和别名匹配、取值的写法匹配、沿关系传递、和代码对。这些脚本都能做。

10-29 报告的 46 条冲突里，36 条脚本能提取（阶段归属、实施状态、用词、数字）。另外 10 条要读懂文字才能变成事实，比如执行权属于 run 还是事项、谁负责全量集成，而且这 10 条最容易让执行者做错。归类是架构师的判断，没有复核。这一步交给 LLM，边界是：

1. **只产生文档说法**：不进正本，也不判断矛盾。猜错的后果是一条多余的提醒。
2. **词汇封闭**：只能用模型里已有的概念和关系。放不进去就标「说不清」，没见过的词列入「像是新概念」。
3. **必须带原文**：脚本核对原句确实在文件里，不在就丢弃。
4. **结果固定**：按段落内容、模型和提示词版本保存结果。段落没变就不重新调用，同样的输入得到同样的提醒。
5. **脚本优先**：脚本能提取的不调用模型。

活动文档有 134 份，约 9400 段、88 万字符，最近 7 天每天改动 100 到 5000 行（不含记录、归档、原型、评测与 ADR）。所以：

- **写文件时**不调用模型，只用脚本和已保存的结果，把提醒交给 agent、不撤回写入，做法照 `.claude/hooks/state-doc-dates.mjs`。
- **推送之后**由 LLM 在后台处理改过的段落。
- **调用失败时**明确提示「这次提取没有运行」，不用旧结果冒充。

提醒的时间点：会话开始、写文件以后、每轮结束、每次推送、里程碑结束。推送前的检查总是放行。

## 9. 实施顺序

五步，前一步做完才用得上后一步。每一步开工前另问用户。

1. **定写法**：字段、取值、文档说法的格式，写成一页规格。草稿见第 10 节。
2. **合并三份半成品**：架构师做。先做总图里的概念（缝、方框、状态、内环六步，对照表里就是这 118 行），它们被复述得最多；其余词条先只补「定义在」。
3. **建工具**：读模型与文档，脚本提取说法，规则比较取值和代码，出报告。先全量跑一次，存量记成基线。
4. **接提醒点**：写文件以后、会话开始、每轮结束、推送、里程碑结束。
5. **接 LLM 提取**：通过第 13 节的验收才进日常提醒；没通过，LLM 只留在建模时提议，经架构师确认进模型。

不做：调用关系、从模型生成总图。

## 10. 写法草稿

### `CONTEXT.md` 词条

每个词条三部分：标题、原有的定义与 `_Avoid_` 行（不变）、一块固定格式的结构。工具只读标题和结构块，定义照旧给人读。

```
#### 缝
（原有的定义段落与 _Avoid_ 行不变）
- 定义在：`docs/architecture.html`「要守的缝」
- 包含：写入口、路由、装配、执行、……
- 取值：系统里 = 9；系统外 = 4；合计 = 13
- 写法：系统里 →「N 道在系统里」；系统外 →「N 道在系统外」

#### 写入口
（原有的定义段落与 _Avoid_ 行不变）
- 属于：缝
- 定义在：`docs/architecture.html`「要守的缝」
- 代码：`harness/write_path.py` 的 `WritePath`、`Transaction`
- 代码状态：一致

#### 门
（原有的定义段落与 _Avoid_ 行不变）
- 不自动挂
```

| 字段 | 必填 | 值怎么写 | 工具拿它做什么 |
| --- | --- | --- | --- |
| 标题 `#### 名字` | 是 | 一个正名 | 概念的身份和锚点 |
| 别名 | 否 | 顿号分隔 | 指它时也算挂上 |
| 定义在 | 总图里的概念必填 | `路径`「小节」，沿用仓库已有的 574 处写法 | 核对小节存在；定义处改了就提醒链入页面 |
| 属于 / 包含 / 依赖 | 否 | 概念正名，顿号分隔 | 沿关系传递；目标必须是已有概念 |
| 取值 | 否 | `键 = 值`，分号分隔；清单写 `键 = [甲、乙]` | 和说法比对 |
| 写法 | 有取值时选填 | 键 →「带 N 的句式」 | 脚本认出复述 |
| 代码 | 否 | 反引号里的路径和名字 | 和 ast 两边对 |
| 代码状态 | 有代码时必填 | 一致 / 不一致：说明 / 代码里还没有 | 沿用对照表的三种状态 |
| 不自动挂 | 否 | 单独一行 | 单字、常用词不按名字挂 |

**模型自己要守的规矩**（工具核对模型本身）：

- 名字和别名全表唯一。
- 关系里写的概念都存在。
- 「定义在」指的小节存在。
- 一个概念里取值的键不重复。

**要跟着改的地方**：词条名现在是 `**名字**:`，改成四级标题才有锚点。仓库里只有 doc-scan 技能的 `term-audit.ps1` 按这个写法解析 `CONTEXT.md`，要一起改。

**第二步会碰到的量**：对照表 118 个总图的词里，只有 22 个已经是词条，47 个和某个词条名字相近，49 个术语表里没有（比如「期望版本」「事项的执行权编号」）。这 49 个里，总图的方框、缝、状态建成概念；缝「交换」里的字段（期望版本、执行权编号这类）写进所属缝的取值和代码，不进术语表。

### 文档说法

每条说法六项：主语、关系、对象、范围、原文、位置，再记提取方式（脚本，或模型加提示词版本）。主语和对象用模型里的概念；关系是封闭清单，清单在第 13 节的试验以后定。

### 规则

规则是 clingo 文本，放在工具目录的数据文件里，带版本。比如「同一个键有两个取值」：

```
conflict(K,V1,S1,V2,S2) :- claim(K,V1,S1), claim(K,V2,S2), V1 < V2.
```

## 12. 工具的形状

### 位置

顶层 `tools/doc-consistency/`：自己的 `pyproject.toml`、自己的测试。现有的打包只收 `harness*`，测试路径只有 `harness/tests`、`evals/tests`，都不会带上它。`harness/` 不引用它，它也不引用 `harness/`。

### 分层

| 层次 | 职责 | 边界 |
| --- | --- | --- |
| 事实来源 | 把材料变成事实，每条带来源：词条结构块、总图、文件引用、代码、脚本提取、LLM 提取 | LLM 只在这一层 |
| 规则 | clingo 文本，带版本 | 不写代码逻辑 |
| 推理 | 输入事实和规则，输出结论和来源 | 无状态，不读文件、不调模型、不写任何东西 |

Discussions #1426 第 2 条（规则表放哪）的答案就是这里：规则是工具目录里的数据文件。

### 为什么用规则语言

抽查的真实矛盾都用不到求解器：46 条冲突都是比较取值、同一属性只能有一个值、是否在清单内、谁有权做；随机抽的 30 条不一致是旧编号 17 条、禁用词 8 条、格式 4 条、数目前后不符 1 条。归类是架构师的判断，没有复核。

用仓库里的真实数据试了两个引擎（clingo 5.8.2、Z3 5.3.3），都在临时目录，用 uv 隔离：

| 问题 | clingo | Z3 |
| --- | --- | --- |
| 从入口走不到的文档（165 份，877 条引用） | 41 份，4.8 ms | 41 份，68 ms，要用内置的 Datalog 引擎 |
| 缝的数目：总图 9 与 4，`CONTEXT.md` 10 与 3 | 两处都报出，带来源 | 只报出一处，带来源 |
| 权责矛盾（报告里的标签规则，手写成事实） | 报出 | 没测 |
| 语义状态推导（示例数据） | 3 个随机种子结果相同，答案唯一 | 没测 |
| 真实界限内 keep ≥ work 的组合 | 要枚举 1929 亿种，没有运行 | 8 次共 34 ms，给出反例 |

选 clingo：没写就算没有，走不到、没人认领、缺核对都靠这一点；一次列出全部矛盾；只要规则不用选择和循环否定，相同输入只有一个结果。Z3 只在最后一行占优，那条关系设计说明没有规定，不算缺陷，简单比较也能回答，所以不引入；参数之间出现多变量公式时再接入。

只做文档核对的话，普通 Python 也够：走不到的文档那一题 0.3 ms，结果相同。用规则语言是因为规则能作为数据带版本，以后别的使用方也能共用一套写法。

### 以后

效果好的话，后续在图谱中支持，作为全局上下文装配的参考。可能的使用方还有语义系统知识层的状态推导与要求链核对、候选定义的结构校验。这些都要另写设计说明，到那时才有总图位置。

- 上下文装配的七条规则是用量和缓存的取舍，不直接调用推理，读图谱推出的结果。
- 内核不依赖它：写入口事务里的本体校验继续用普通代码。
- 产品里 LLM 提取放在总图的判定点：答案先写成事件，重放时读事件，不再问模型。推理结果是投影，不写回事实。

## 13. LLM 提取的验收与试验
