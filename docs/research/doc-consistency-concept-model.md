# 文档一致性核对：概念模型与符号推理方案

> 日期：2026-11-02。状态：方案，方向用户已确认。`tools/doc-consistency/` 与 `.doc-index/` 还没有建，`CONTEXT.md` 与钩子都没有改，不开工单；实现的每一步开工前另问用户。LLM 开放提取的试验没有通过，见第 13 节。
> 用途：回答文档一致性核对这一环怎么做：发现文档之间、文档与代码之间走样，由规则判断，只提醒、不拦提交。只服务 Yudao 的开发。支持 [决策记录](../decision.md) 里「文档一致性」四条。
> 依据：第 8 节的数字在 main 的 11ad31a5 上数；第 7、12、13 节的数字来自 2026-11-02 的试验，语料是提交 35cc686e；矛盾的类型取自 `docs/consistency-scan-2026-10-29.md`；上游讨论见 Discussions #1426。全部只读。

## 1. 结论

不靠高频词，也不靠作者主动写的引用，先建一份**文件图谱和概念模型**，把文档和代码的说法都变成事实，由规则判断有没有走样。

- **索引**：类似 Obsidian 的文件图谱、关系和 hash，放在文档之外，不往文档里写任何东西（第 12 节）。
- **模型**：不从零建，把 `CONTEXT.md` 术语表与总图里的缝和方框合成一份，词条下加一小块固定格式的结构；「总图的词与代码名对照」（`docs/design/architecture/name-map.md`）保留，作为代码到总图的对应表。
- **判断**：是否走样由规则得出，规则是 clingo 文本，结论带回来源。
- **LLM**：不进日常提醒。开放提取没有通过试验；定向提取要单独验证以后才接（第 7 节）。
- **工具**：单独的工具，放在顶层 `tools/doc-consistency/`，不和仓库的代码区混合。

### 两条线

| | 设计线 | 脚手架线 |
| --- | --- | --- |
| 范围 | 总图 → 子模块设计 → ADR、代码、测试 | 规则文件、工作流、技能 |
| 下面有没有代码 | 有 | 没有或很少 |
| 正本 | 总图 | `docs/agents/workflow.md` 与共同规则 |
| 核对什么 | 文档说法、正本、代码事实是否一致 | 同一角色在同一情形下，读到的指令是否唯一 |
| 词汇来源 | `CONTEXT.md` 与对照表 | 从工作流表格、技能目录、GitHub 标签直接读，不手写 |
| 不一致时 | 改下游：总图 > 设计 > 代码。ADR 是记录文档，不改，标记被取代或另写新的。代码落后设计要和走样分开报 | 改复述的那一份，流程只留在正本 |

脚手架的冲突直接拖慢 agent，所以脚手架线排在前面。它的矛盾只在同一角色的阅读范围内才影响效率，规则先算出每个角色读哪些文件，只报这个范围内的矛盾。

设计线能做符号推理，是因为 Yudao 从架构出发：词汇基本封闭（十三道缝、九个外环状态、内环六步），每份设计说明都写了总图位置，代码一侧已有导入规则与定义数据。需求记录写的是用户的话和意图，不算代码的抽象，不做形式化。

### 用户已定

1. 只提醒，不拦提交。
2. 判断走样靠规则，翻译文字可以用 LLM；LLM 由机器调用，不靠 agent 自己想起来。
3. 按名字自动挂。
4. 概念模型放在 `CONTEXT.md`。
5. 这是单独的工具，不和代码区混合。只做 Yudao 开发用的脚手架；图谱与全局上下文装配的复用只是愿景。
6. 分设计与脚手架两条线，脚手架线排在前面。
7. hash 不写进设计文档。索引、提取结果与确认记录都进仓库，单独放一个位置。

其余见第 11 节。

## 2. 为什么不跟引用走：一个现成的例子

总图第四节的标题写「九道在系统里，四道在系统外」，`CONTEXT.md`「总图」词条里还写着「十道在系统里、三道在系统外」。

- 两处之间没有任何引用，只看引用的做法看不见它。
- 总图是在提交 33b0254a（画面搬到系统外）改的，那个提交也改了 `CONTEXT.md`，只是没改到这一句。所以按文件看「一起改了没有」也抓不到。
- 只有按内容扫，把全仓所有「N 道…系统里／系统外」都找出来对一遍，才找得到。

引用是作者主动写的，无法保证都有，所以要全局扫描；扫描要有东西可对，这就是概念模型。这一处走样本方案只指出，不改。

## 3. 概念模型是什么

一个概念一条，字段固定，工具读得懂：

| 字段 | 写什么 | 今天在哪 |
| --- | --- | --- |
| 名字、别名 | 正名，和指它时也算数的叫法 | `CONTEXT.md` 词条名 |
| 不用 | 指它时不该用的说法 | `CONTEXT.md` 的 `_Avoid_` |
| 定义 | 一段话，给人读 | `CONTEXT.md` 词条正文 |
| 定义在 | 正本里的哪一节、哪个方框 | 对照表的「总图位置」列 |
| 关系 | 属于、包含、依赖，指向别的概念 | 写在词条正文里的散文 |
| 属性 | 这个概念有哪些属性、每个只能一个值还是可以多个 | 还没有 |

取值不手写：能从总图结构读出的直接读（第四节正好 13 个 `.seam`，每个带 `data-state`），写一份就多一份会走样的副本。代码名留在对照表，不进 `CONTEXT.md`：`CONTEXT.md` 现在没有一处代码路径，对照表有约 530 个代码名，归子架构师维护。

推理用到三类事实，来源和可信程度都不同：

| 事实 | 内容 | 来源 |
| --- | --- | --- |
| 正本事实 | 名字、关系、取值 | 总图结构、词条结构块、规则文件里的表格 |
| 代码事实 | 导入关系、定义数据、对照表、守卫清单 | Python ast、`harness/definitions/`、`name-map.md`，每次现算 |
| 文档说法 | 「这段话这样写」，带原文与位置 | 脚本提取；定向提取通过验证以后也来自 LLM。不代表内容正确，最多引发一条提醒 |

## 4. 文档和代码怎么变成事实

1. **文件之间的引用**：链接、反引号路径、设计说明的总图位置行，进索引。「从入口走不到的文档」「这段改了，哪些段落要看」靠它得出。
2. **自动挂**：工具按模型里登记的名字和别名，在每一节里找到概念，记一条「提到」。没人写引用也连得上。「门」「环」这种单字和「事实」这种常用词在模型里标成不自动挂，只在改动的行里看。
3. **提取文档说法**：脚本认「数字加量词」，比如模型里缝的量词是「道」，「十三道缝」「九道在系统里」都是候选，只在改动的行里报。同句共现太宽：同一句里有「缝」和数字的 246 句，抽 10 句只有 1 句在说缝的数目；固定句式又太窄，只有 2 句符合。
4. **代码**：模型与对照表写的名字代码里没了要报，内核里新加了公开定义、没有概念认领也要报；设计说明写的默认值和 `rules.json` 比较。和 `/seam-diff` 的分工：它在里程碑时按守卫核对代码与总图；这个工具核对文档之间，以及文档说法与代码事实。

## 5. 用模型找走样

改动以后只看这次碰到的概念；里程碑结束和第一次上线时全量跑一遍。

| 走样 | 怎么发现 | 把握 |
| --- | --- | --- |
| 复述的取值和正本不一致 | 数字加量词提取说法，规则比较 | 高 |
| 模型里的名字改了 | 旧名自动留作别名一版，全仓剩下的旧名都提醒，给改法 | 高 |
| 模型写的代码不在了，或内核新定义没人认领 | ast 和对照表对 | 高 |
| 正本里出现模型没有的名字 | 总图的标题、方框、表格和模型对 | 高 |
| 死引用：技能、标签、文件路径 | 索引和目录、GitHub 标签对 | 高 |
| 一个概念或一节改了 | 引用它、提到它的段落全部提醒，看过以后记确认 | 中 |
| 用了「不用」的说法 | 只在改动的行里报，整仓报噪音太大 | 中 |
| 两段文字对同一件事说法相反：谁负责、属于哪里、是否已实施 | 定向提取，规则比较 | 待验证 |

第 2 节的例子落在第一行：总图里缝是九与四，`CONTEXT.md` 那句写「十道在系统里」，不用任何引用就报出来。一份文档走不到任何概念、从入口也走不到，就是减法的候选。

第一次全量扫出的存量记成基线，之后只报新增。

脚手架刚清理过时，死引用不多：2026-11-02 核对 35 个文件约 73 条引用，真正失效的只有 1 条。脚手架线的矛盾主要在文字里，确定性规则只能给出「这段改了，这些段落要看」，判断仍靠读。

## 6. 新概念怎么进模型

- **入口只有一个：改模型。** 和现在一样由架构师改；总图里的概念由总架构师在改总图的同一次改动里改。模型跟着总图走。
- **工具摆出「像是新概念」的地方，但不看词频**：总图里新出现、模型没有的方框、缝、表头；设计说明里新加的标题；内核里新加的公开定义。每条只有两种关法：进模型，或写明不是概念。
- **总图自己也挂在模型上**：总图是手写的 HTML，它的数字和名字也和模型对。改了总图没改模型，或反过来，都会报。
- 这样 `CLAUDE.md` 里手写的「一次改完」清单就不用人记了：谁复述了总图，由索引算出来。

## 7. LLM 放在哪里

有了模型和索引，大部分「语义」变成了确定的步骤：名字和别名匹配、取值比较、沿关系传递、和代码对。这些工具都能做。

10-29 报告的 46 条冲突里，36 条脚本能提取（阶段归属、实施状态、用词、数字）。另外 10 条要读懂文字才能变成事实，比如执行权属于 run 还是事项、谁负责全量集成，这些最容易让执行者做错。归类是架构师的判断，没有复核。

**开放提取走不通**（第 13 节）：让模型自由提取主语和关系，再靠通用规则配对，主语对不上，规则把合法的多个值当矛盾。

**定向提取**：由模型先定好有哪些属性、每个只能一个值还是可以多个，LLM 只回答固定的问题，比如「这段说 `needs-triage` 由谁加」。主语来自模型，一定对得上；规则只比较单值属性。边界是：

1. **只产生文档说法**：不进正本，也不判断矛盾。猜错的后果是一条多余的提醒。
2. **词汇封闭**：对象只能来自模型与清单。放不进去就标「说不清」。
3. **必须带原文**：工具核对原句确实在文件里，不在就丢弃。
4. **结果固定**：按段落内容、所在小节、命中的词条、提取规则版本和模型保存结果，不带文件名和行号，也不带整张词表。这段没变就不重新调用。
5. **脚本优先**：脚本能提取的不调用模型。

这条路还没有验证，通过以后才接入日常提醒。验证要换一批答案：那 4 条脚手架矛盾已经看过，用人为植入的矛盾来测。

接入以后：写文件时不调用模型，只用脚本和已保存的结果，把提醒交给 agent、不撤回写入，做法照 `.claude/hooks/state-doc-dates.mjs`；推送之后由 LLM 在后台处理改过的段落；调用失败时明确提示「这次提取没有运行」，不用旧结果冒充。

提醒的时间点：会话开始、写文件以后、每轮结束、每次推送、里程碑结束。推送前的检查总是放行。

## 9. 实施顺序

每一步开工前另问用户。

1. **建索引**：文件与小节、hash、引用边，加生成图谱页面与查询命令。不依赖概念模型。
2. **脚手架线**：把工作流表格、技能目录、GitHub 标签读成事实；死引用、每个角色的阅读范围、「这段改了，这些段落要看」、确认记录。
3. **设计线，定写法**：词条结构块，草稿见第 10 节。
4. **设计线，合并模型**：架构师做。先做总图里的概念（缝、方框、状态、内环六步），它们被复述得最多。
5. **设计线，比较**：先做代码事实（确定性的，不依赖 LLM），再做取值比较。先全量跑一次，存量记成基线。
6. **接提醒点**：写文件以后、会话开始、每轮结束、推送、里程碑结束。
7. **定向提取**：单独验证，通过才接入。

不做：调用关系、从模型生成总图、代码注释反向提取、谓词预先对齐语义系统。

## 10. 写法草稿

### `CONTEXT.md` 词条

每个词条三部分：标题、原有的定义与 `_Avoid_` 行（不变）、一块固定格式的结构。工具只读标题和结构块，定义照旧给人读。

```
#### 缝
（原有的定义段落与 _Avoid_ 行不变）
- 定义在：`docs/architecture.html`「要守的缝」
- 包含：写入口、路由、装配、执行、……
- 量词：道

#### 写入口
（原有的定义段落与 _Avoid_ 行不变）
- 属于：缝
- 定义在：`docs/architecture.html`「要守的缝」

#### 门
（原有的定义段落与 _Avoid_ 行不变）
- 不自动挂
```

| 字段 | 必填 | 值怎么写 | 工具拿它做什么 |
| --- | --- | --- | --- |
| 标题 `#### 名字` | 是 | 一个正名 | 概念的身份和锚点 |
| 别名 | 否 | 顿号分隔 | 指它时也算挂上 |
| 定义在 | 总图里的概念必填 | `路径`「小节」，沿用仓库已有的 574 处写法 | 核对小节存在；定义处改了就提醒引用它的段落 |
| 属于 / 包含 / 依赖 | 否 | 概念正名，顿号分隔 | 沿关系传递；目标必须是已有概念 |
| 取值 | 总图读不出时才写 | `键 = 值`，分号分隔；清单写 `键 = [甲、乙]` | 和说法比对 |
| 量词 | 有数目时选填 | 一个字，比如「道」 | 认出数字加量词的复述 |
| 属性 | 否 | 属性名，后面写「单值」或「多值」 | 定向提取问什么；规则只比较单值属性 |
| 不自动挂 | 否 | 单独一行 | 单字、常用词不按名字挂 |

**模型自己要守的规矩**（工具核对模型本身）：

- 名字和别名全表唯一。
- 关系里写的概念都存在。
- 「定义在」指的小节存在。
- 一个概念里取值的键不重复。

**要跟着改的地方**：词条名现在是 `**名字**:`，改成四级标题才有锚点。仓库里只有 doc-scan 技能的 `term-audit.ps1` 按这个写法解析 `CONTEXT.md`，要一起改。

**第四步会碰到的量**：对照表 118 个总图的词里，只有 22 个已经是词条，47 个和某个词条名字相近，49 个术语表里没有（比如「期望版本」「事项的执行权编号」）。这 49 个里，总图的方框、缝、状态建成概念；缝「交换」里的字段（期望版本、执行权编号这类）留在总图与对照表，不进术语表。

### 文档说法

每条说法记主语、属性、极性（肯定或否定）、对象、范围、原文、位置，再记提取方式（脚本，或模型加提取规则版本）。不加时态与废弃标记：状态文档本来就不写历史。

### 规则

规则是 clingo 文本，放在工具目录的数据文件里，带版本。比如「同一个单值属性有两个取值」：

```
conflict(K,V1,S1,V2,S2) :- single(K), claim(K,V1,S1), claim(K,V2,S2), V1 < V2.
```

## 12. 工具的形状

### 位置

| 东西 | 位置 |
| --- | --- |
| 工具代码与测试 | 顶层 `tools/doc-consistency/`，自己的 `pyproject.toml` |
| 规则 | `tools/doc-consistency/` 里的 clingo 数据文件 |
| 索引、提取结果、确认记录 | 顶层 `.doc-index/`，进仓库，换机器也一致 |

现有的打包只收 `harness*`，测试路径只有 `harness/tests`、`evals/tests`，都不会带上它。`harness/` 不引用它，它也不引用 `harness/`。`.github/workflows/ci.yml` 的 `paths-ignore` 加上 `tools/**` 与 `.doc-index/**`，这两处的推送不运行产品的 CI。

### 索引

类似 Obsidian 的元数据缓存，文档一个字都不动：

| 内容 | 怎么记 |
| --- | --- |
| 节点 | 文件和小节。身份是「路径 + 小节标题」，hash 只代表内容版本。不记行号，行号每次现算，免得开头加一行就改动一大片 |
| 边 | 链接、反引号路径、总图位置行、段落提到的概念 |
| 提取结果 | 按第 7 节的键保存 |
| 确认记录 | 「下游看过上游这个版本，不用改」，记下两边的 hash，只追加 |

- **按来源文件分开存**，一份源文件一个文件，几个会话同时改时互不冲突；确认记录只追加，合并时保留两边。
- **索引落后不影响结果**：工具读取时重新计算 hash，和索引比出差异，所以不要求和文档改动同一次提交。
- **除了提取结果和确认记录，其余都能重建**。索引是缓存，不是事实来源，事实以文件为准。
- **待核对**：上游 hash 变了，下游就待核对；改过下游或记了确认就算处理完。取值类按内容比较，改对了提醒自然消失。
- **图谱页面**从这份索引生成：单个 HTML，能拖动、按目录上色、点一份文档高亮上下游。

增量的范围：

| 变化 | 处理 |
| --- | --- |
| 段落内容或所在小节变了 | 更新这一段；接入 LLM 以后只重提这一段 |
| 词条变了 | 接入 LLM 以后只重提命中这个词条的段落 |
| 提取规则或模型换了 | 全量重提，很少发生，也是有意为之 |
| 正本、代码、clingo 规则变了 | 不调用 LLM，clingo 全部重算，只要几毫秒 |

按内容算 hash，平常一天只有约 1% 的段落变化：2765 段里，和一天前比 20 段，和三天前比（中间有大批文档整理）1167 段。把文件名和行号算进去，同样的比较是 168 段和 1770 段。

段落没变只说明提取结果还能用，不代表内容仍然正确；总图改了，下游段落的 hash 不变，这正是规则比较要发现的走样。

### 分层

| 层次 | 职责 | 边界 |
| --- | --- | --- |
| 索引 | 文件、小节、hash、边 | 不判断 |
| 事实来源 | 把材料变成事实，每条带来源：总图结构、词条、工作流表格、代码、脚本提取；验证通过以后加定向提取 | LLM 只在这一层 |
| 规则 | clingo 文本，带版本 | 不写代码逻辑 |
| 推理 | 输入事实和规则，输出结论和来源 | 无状态，不读文件、不调模型、不写任何东西 |

### 为什么用规则语言

抽查的真实矛盾都用不到求解器：46 条冲突都是比较取值、同一属性只能有一个值、是否在清单内、谁有权做；随机抽的 30 条不一致是旧编号 17 条、禁用词 8 条、格式 4 条、数目前后不符 1 条。归类是架构师的判断，没有复核。

用仓库里的真实数据试了两个引擎（clingo 5.8.2、Z3 5.3.3），都在临时目录，用 uv 隔离：

| 问题 | clingo | Z3 |
| --- | --- | --- |
| 从入口走不到的文档（165 份，877 条引用） | 41 份，4.8 ms | 41 份，68 ms，要用内置的 Datalog 引擎 |
| 缝的数目：总图 9 与 4，`CONTEXT.md` 10 与 3 | 两处都报出，带来源 | 只报出一处，带来源 |
| 权责矛盾（报告里的标签规则，手写成事实） | 报出 | 没测 |
| 语义状态推导（示例数据） | 3 个随机种子结果相同，答案唯一 | 没测 |
| 真实界限内 keep ≥ work 的组合 | 要枚举 1929 亿种，没有运行 | 8 次共 34 ms，给出反例 |

选 clingo：没写就算没有，走不到、没人认领、缺核对都靠这一点；一次列出全部矛盾；相同输入得到相同的提醒。Z3 只在最后一行占优，那条关系设计说明没有规定，不算缺陷，简单比较也能回答，所以不引入。

单比文档，普通 Python 也够：走不到的文档那一题 0.3 ms，结果相同。用规则语言有两个理由：规则和代码分开，加一条规则不用动代码，架构师不写代码也能维护；文档事实和代码事实放进同一套规则比较，是这个工具比链接检查多出来的能力。

### 愿景

效果好的话，图谱可以作为全局上下文装配的参考，也可以拿提案声明的依赖和真实调用关系对账。现在都不设计。

## 13. LLM 提取的验收与试验

**验收**（架构师提议，用户确认）：在 10-29 的提交（35cc686e）上，脚手架文件范围内 4 条矛盾（T40、T42、T43、T44）至少找回 3 条，随机抽 100 条提醒误报不超过 20 条。没通过时，LLM 只留在建模时提议，不进日常提醒。全量 10 条的阈值是至少找回 8 条；全量预估约 1950 万 token，超过设定的 1500 万上限，只跑了脚手架范围。

**做法**：34 份文件、623 段，模型 `wb/cn:deepseek-v4.1-flash`（9router）；提示词里有 12 种关系与 `CONTEXT.md` 的 210 个词条，主语不在词表时写原样名字；clingo 比较「同一主语、对象不同」等四类。代码与判断由 Sonnet 5.5 子代理完成。

**结果：两条都没有通过。**

| 指标 | 结果 | 要求 |
| --- | --- | --- |
| 找回率 | 1/4 | 至少 3/4 |
| 误报 | 98/100 | 不超过 20 |

| 项 | 数 |
| --- | --- |
| 用量 | 474 万 token，其中输出 225 万（思考 201 万）；网关固定前缀约占总用量 37% |
| 耗时 | 约 66 分钟，失败 0 |
| 说法 | 3705 条，丢弃 15 条，「说不清」56 段 |
| 提醒 | 815 条：取值等单值类 486，唯一负责方对负责方 46，正反对立 2，归属不同 281 |
| 误报抽样 | 真矛盾 2，范围不同 29，提取错误 29，合法的多个值 40 |

逐条结果：

| 矛盾 | 结果 | 原因 |
| --- | --- | --- |
| T40 | 命中，但只是沾边 | 真正的矛盾是谁负责跑全量集成，命中的是运行范围和「全部」的比较 |
| T42 | 没命中 | 主语没对上：「给工单加 `needs-architect`」和「`needs-architect`」 |
| T43 | 没命中 | 一侧「设计说明有改动」是交回理由，没有提取到 |
| T44 | 没命中 | `executor` 技能的原文没写主体，没有提取到 |

两条「真矛盾」都是之前没人报过的轻微走样：`solo` 技能写集成层一趟 15 到 45 分钟，`issue-tracker.md` 写约 15 分钟；`architect-loop` 说范围写法和 `/solo` 相同，却多列了「标题前缀」。架构师抽查了 12 条判断，都站得住。

**结论**：3705 条里只丢弃 15 条，抽查到的都是原文，提取的可靠性还可以。失败的是开放提取：主语不封闭就配不上，通用规则把多值和不同范围都当矛盾。这次的词表是产品术语，没有脚手架的角色、标签和动作，所以「概念模型加 LLM」本身还没有被验证。

**局限**：关系清单是读过这 10 条矛盾之后写的，答案可能有泄漏；范围内只有 4 条答案；抽样由同一个子代理判断；设计说明与需求记录谁更准，这次没有测到。试验脚本与原始结果在本地 `.tmp/doc-consistency-trial/`，不进仓库。
