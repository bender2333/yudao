# 文档一致性核对：概念模型方案

> 日期：2026-11-02。状态：方案，还在和用户讨论。`CONTEXT.md`、脚本、钩子都没有改，不开工单；第一版的每一步开工前另问用户。
> 用途：回答文档一致性核对这一环怎么做：发现文档之间、文档与代码之间走样，不靠 LLM，只提醒、不拦提交。支持 [决策记录](../decision.md) 里「文档一致性：只提醒不拦，要一个不靠模型的环节」与「文档一致性：按概念模型核对」两条。
> 依据：数字在 main 的 11ad31a5 上数，只读。Discussions #1426 里的八个待定问题与子架构师查到的钩子能力这里没有读到，第 11 节的待定事是从决策记录与日记重新排的，可能与那八个有出入。

## 1. 结论

不靠高频词，也不靠作者主动写的引用，改成先建一个**概念模型**，文档和代码都挂到概念上，像 wiki：每个概念一页，写清它叫什么、定义在哪、和谁是什么关系、有哪些取值、对应哪些代码；每一页都能算出「链入页面」。

- 模型不从零建，把仓库里已经各自维护的三份半成品合成一份：`CONTEXT.md` 术语表、总图里的缝与方框、「总图的词与代码名对照」（`docs/design/architecture/name-map.md`）。
- 模型放在 `CONTEXT.md`：一个词条就是一页，词条下加一小块固定格式的结构。agent 本来就被要求按它用词，不再多一份文件。
- 文档不手写链接，脚本按模型里登记的名字和别名自动挂上去；只有复述模型里一个取值的地方，才写一个语义链接。
- 发现走样只用脚本，只提醒、不拦提交。LLM 最多在建模时提议，经架构师确认才进模型。

用户已定的四件：只提醒不拦提交；发现走样不靠 LLM；按名字自动挂、复述取值写语义链接；模型放在 `CONTEXT.md`。其余见第 11 节。

## 2. 为什么不跟引用走：一个现成的例子

总图第四节的标题写「九道在系统里，四道在系统外」，`CONTEXT.md`「总图」词条里还写着「十道在系统里、三道在系统外」。

- 两处之间没有任何引用，只看引用的做法看不见它。
- 总图是在提交 33b0254a（画面搬到系统外）改的，那个提交也改了 `CONTEXT.md`，只是没改到这一句。所以按文件看「一起改了没有」也抓不到。
- 只有按内容扫，把全仓所有「N 道…系统里／系统外」都找出来对一遍，才找得到。

引用是作者主动写的，无法保证都有，所以要全局扫描；扫描要有东西可对，这就是概念模型。这一处走样本方案只指出，不改。

## 3. 概念模型是什么

一个概念一条，字段固定，脚本读得懂：

| 字段 | 写什么 | 今天在哪 |
| --- | --- | --- |
| 名字、别名 | 正名，和指它时也算数的叫法 | `CONTEXT.md` 词条名 |
| 不用 | 指它时不该用的说法 | `CONTEXT.md` 的 `_Avoid_` |
| 定义 | 一段话，给人读 | `CONTEXT.md` 词条正文 |
| 定义在 | 正本里的哪一节、哪个方框 | 对照表的「总图位置」列 |
| 关系 | 属于、包含、依赖，指向别的概念 | 写在词条正文里的散文 |
| 取值 | 会被别处复述的数、清单 | 总图，各处各抄一份 |
| 代码 | 对应的类、函数、文件 | 对照表的「代码里现在的名字」列 |

链入页面不存，每次算。

## 4. 文档和代码怎么挂到概念上

三种挂法，只有第二种要作者动手：

1. **自动挂（主要的）**：脚本按模型里登记的名字和别名，在每一节里找到概念，记一条「提到」。没人写引用也连得上。「门」「环」这种单字和「事实」这种常用词在模型里标成不自动挂，只在改动的行里看。
2. **语义链接（少量，只在复述取值时）**：一句话要复述模型里的一个取值，就写成指向那个取值的链接，由脚本比对。取值只存一处，复述就不会走样。写法待定，见第 11 节第 4 条。
3. **代码**：模型的「代码」字段和 Python ast 抽出来的定义两边对：模型写的名字代码里没了要报，内核里新加了公开定义、没有概念认领也要报。

语义链接仍是作者主动写的，但漏写抓得到：脚本知道每个取值长什么样（「N 道…系统里」），一句话写了数却没链到取值，就提醒「这里复述了取值，改成链接，或者核一下」。

## 5. 用模型找走样

改动以后只看这次碰到的概念；里程碑结束和第一次上线时全量跑一遍。

| 走样 | 怎么发现 | 把握 |
| --- | --- | --- |
| 复述的取值和模型不一致 | 按取值的写法找到复述，比数 | 高 |
| 模型里的名字改了 | 旧名自动留作别名一版，全仓剩下的旧名都提醒，给改法 | 高 |
| 模型写的代码不在了，或内核新定义没人认领 | ast 和「代码」字段对 | 高 |
| 正本里出现模型没有的名字 | 总图的标题、方框、表格和模型对 | 高 |
| 模型里一个概念的定义或关系改了 | 它的链入页面全部提醒 | 中 |
| 用了「不用」的说法 | 只在改动的行里报，整仓报噪音太大 | 中 |
| 一句提到概念的话改了，意思还对不对得上定义 | 脚本判断不了，只把那句话和定义摆在一起 | 低，由正在干活的 agent 看 |

第 2 节的例子落在第一行：模型里「缝：系统里 = 9」，`CONTEXT.md` 那句写「十道在系统里」，不用任何引用就报出来。一份文档走不到任何概念、从入口也走不到，就是减法的候选。

## 6. 新概念怎么进模型

- **入口只有一个：改模型。** 和现在一样由架构师改；总图里的概念由总架构师在改总图的同一次改动里改。仓库规矩已经写着「总图的词与术语表不一致时以总图为准」，模型跟着总图走。
- **脚本摆出「像是新概念」的地方，但不看词频**：总图里新出现、模型没有的方框、缝、表头；设计说明里新加的标题；内核里新加的公开定义。每条只有两种关法：进模型，或写明不是概念。
- **总图自己也挂在模型上**：总图是手写的 HTML，它的数字和名字也和模型对。改了总图没改模型，或反过来，都会报。
- 这样 `CLAUDE.md` 里手写的「一次改完」清单就不用人记了：谁复述了总图，由链入页面算出来。

## 7. 哪一步要语义，和「不靠 LLM」怎么对上

有了模型，大部分「语义」变成了确定的步骤：名字和别名匹配、取值的写法匹配、沿关系传递（A 改了，包含 A 的 B 也要看）、和代码对。这些脚本都能做。

真要理解意思的只有两处：

- 一个词在这句里是不是指这个概念，比如「门」「事实」。
- 换了说法的复述，意思还对不对。

对上「不靠 LLM」的办法：LLM 只在建模时用，提议别名、提议「这句复述了哪个取值」，写进模型要经架构师确认。确认后就是模型里的事实，发现走样照样只用脚本；没确认的提议不触发任何提醒。不采纳「模型抽取的知识图谱」，理由是边是猜的；这里猜的边进不了图。第一版可以完全不用 LLM，那两处就摆给正在干活的 agent 自己看。

跑的时间点：会话开始、写文件以后、每轮结束、每次推送、里程碑结束。只提醒不拦提交：写文件以后的提醒照仓库已有的 `.claude/hooks/state-doc-dates.mjs` 那样，把提醒交给 agent、不撤回写入；推送前的检查总是放行。工具放 `scripts/`，用 Python（ast 自带），不进 `harness/`，也不进总图。

## 9. 第一版做什么、按什么顺序

六步，前一步做完才用得上后一步。每一步开工前另问用户。

1. **定写法**：字段、取值、语义链接的语法，写成一页规格。草稿见第 10 节，还等第 11 节第 4 条。
2. **合并三份半成品**：架构师做。先做总图里的概念（缝、方框、状态、内环六步，对照表里就是这 118 行），它们被复述得最多；其余词条先只补「定义在」。
3. **只读的脚本**：读模型，按名字挂文档，比取值和代码，出报告。先全量跑一次，存量记成基线。
4. **接两个提醒点**：写文件以后、会话开始。
5. **把复述改成语义链接**：从「一次改完」清单那几份起（`CLAUDE.md`「项目表述」、`AGENTS.md`「项目」、`CONTEXT.md`、路线图）。
6. **剩下三个提醒点**：每轮结束、推送、里程碑结束，看噪音再开。

第一版不做：LLM 提议、调用关系、从模型生成总图。

## 10. 第一步草稿：`CONTEXT.md` 词条的写法

每个词条三部分：标题、原有的定义与 `_Avoid_` 行（不变）、一块固定格式的结构。脚本只读标题和结构块，定义照旧给人读。

```
#### 缝
（原有的定义段落与 _Avoid_ 行不变）
- 定义在：`docs/architecture.html`「要守的缝」
- 包含：写入口、路由、装配、执行、……
- 取值：系统里 = 9；系统外 = 4；合计 = 13
- 写法：系统里 →「N 道在系统里」；系统外 →「N 道在系统外」

#### 写入口
（原有的定义段落与 _Avoid_ 行不变）
- 属于：缝
- 定义在：`docs/architecture.html`「要守的缝」
- 代码：`harness/write_path.py` 的 `WritePath`、`Transaction`
- 代码状态：一致

#### 门
（原有的定义段落与 _Avoid_ 行不变）
- 不自动挂
```

| 字段 | 必填 | 值怎么写 | 脚本拿它做什么 |
| --- | --- | --- | --- |
| 标题 `#### 名字` | 是 | 一个正名 | 概念的身份和锚点 |
| 别名 | 否 | 顿号分隔 | 指它时也算挂上 |
| 定义在 | 总图里的概念必填 | `路径`「小节」，沿用仓库已有的 574 处写法 | 核对小节存在；定义处改了就提醒链入页面 |
| 属于 / 包含 / 依赖 | 否 | 概念正名，顿号分隔 | 沿关系传递；目标必须是已有概念 |
| 取值 | 否 | `键 = 值`，分号分隔；清单写 `键 = [甲、乙]` | 和复述比对 |
| 写法 | 有取值时选填 | 键 →「带 N 的句式」 | 认出没写链接的复述 |
| 代码 | 否 | 反引号里的路径和名字 | 和 ast 两边对 |
| 代码状态 | 有代码时必填 | 一致 / 不一致：说明 / 代码里还没有 | 沿用对照表的三种状态 |
| 不自动挂 | 否 | 单独一行 | 单字、常用词不按名字挂 |

**模型自己要守的规矩**（脚本核对模型本身）：

- 名字和别名全表唯一。
- 关系里写的概念都存在。
- 「定义在」指的小节存在。
- 一个概念里取值的键不重复。
- 文档里的每个语义链接都指向存在的取值。

**要跟着改的地方**：词条名现在是 `**名字**:`，改成四级标题才有锚点。仓库里只有 doc-scan 技能的 `term-audit.ps1` 按这个写法解析 `CONTEXT.md`，要一起改。

**第二步会碰到的量**：对照表 118 个总图的词里，只有 22 个已经是词条，47 个和某个词条名字相近，49 个术语表里没有（比如「期望版本」「事项的执行权编号」）。哪些建成概念见第 11 节第 7 条。
