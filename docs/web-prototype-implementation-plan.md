## 1. 设计依据与范围

唯一界面基线是 [2026-09-06 原型快照](prototypes/2026-09-06/README.md)，可直接打开 [预览](prototypes/2026-09-06/department-workspace-preview.html)。用户先认可总览及独立部门工作区，再要求增加参照 OMP 的原始请求与用量观测，最后明确下一阶段 WebUI 和功能按原型设计开发。

最新补充为“provider配置等相关的原型还没有做，这部分预留”。因此 Provider 新增、编辑、删除、凭据输入、连接测试、部门模型选择及相关配置表单均不在已定 UI 范围。D18 的底层目录、绑定、路由和实际身份记录继续安排；配置页面等对应原型完成后再落定。

原型中的 Provider 和 Prompt 检查页只有静态查看，示例温度、窗口、模型及版本不是产品默认。原型发送只更新内存、初始打开观测页及调参控件也不构成运行规则。

需求分项：[D19 工作台](requirements/web-workspace-prototype.md)、[D20 部门指导](requirements/department-guidance.md)、[D21 请求观测](requirements/request-observability.md)。这些均不改变“大功能等待六项全部完成”的要求。

用户最新要求严格按原型样式实施、完成整个第二阶段。W0 的逐页视觉依据见 [视觉契约](prototype-visual-contract.md)，指导接收与生效约定见 [部门指导处理设计](department-guidance-design.md)。当前旧控制台及 D18 的少量只读字段不计为本计划的工作台实现。

## 2. 页面、行为与差距

| 原型区域 | 必须交付的使用过程 | 当前基础与新增工作 |
| --- | --- | --- |
| 共用工作台 | 总览、产品、工程、质检、观测切换；返回保持对象、草稿及查看位置；窄屏导航在顶部 | 现有 Web 重组为独立主视图，沿用服务与任务身份；完善刷新、历史导航和迟到请求隔离 |
| 总览 | 查看当前任务、活动/等待部门、真实交接和返工；点击流转查看材料；面向整体任务追加输入 | 复用任务投影、协作事件与持续输入；静态三节点图需覆盖真实六方向协作及多轮流转 |
| 部门工作区 | 主区工作消息和定向指导；区分用户、本部门、其他部门；检查区可收放 | 已有部门历史和协作记录，需面向工作整理；部门定向输入是新内核能力，不能复用总览输入后都交产品 |
| Context 检查 | 本次输入快照、来源、选中内容及相关模型请求；区分实际输入和工作记录 | 复用输入工件、来源审计及压缩记录；精准绑定当次尝试，不能跳到该部门任意“最新请求” |
| Provider / Prompt 检查 | 原型位置保留；可用时展示实际 Provider、模型、Prompt 原文与采用版本 | Provider 配置页面预留；Prompt 既有编辑能力保留，新的编辑/保存交互待补设计 |
| 请求列表 | 任务内按部门、状态、请求或模型筛选，显示每次尝试及用量/耗时 | 复用 H 的请求、失败、重试事件；补逐次耗时、一致查询、分页及模型请求索引；既有协作请求列表不能直接充当模型列表 |
| 请求详情 | 关联任务、部门、工作、调用和尝试；概览、Request、Response、事件原文；失败与重试互查 | 步骤输入、输出 item 和 usage 已有；完整发送内容及响应对象采集需补齐，来源范围明确 |
| 用量统计 | 同一筛选范围的小计、上报覆盖、按部门和模型分组；未知及进行中有独立状态 | 统一含缓存输入口径、部分字段覆盖及跨 Provider 模型身份；复用真实用量，不建设估价或预算控制系统 |

总览流动由实际事件决定，不能轮流点亮三个部门来模拟进展。材料入口需保留 PRD、PLAN、Git 差异、检查及封存下载，原型中尚未画出的展开方式先补充设计。

当前 `ModelRequest.request_id` 与 `timeline.requests` 属于部门协作。W1 必须分别建立协作请求、逻辑模型调用和物理尝试的确定关联：逻辑调用按任务、部门激活及根步骤定位，尝试按实际步骤和尝试次序定位。Context 跳转和重试汇总使用模型调用/尝试身份，不能套用原型的示例 ID 或协作请求 ID。内部 Web SSE 与 Provider 原始事件也分别标明来源。

## 3. 三层职责

| 层 | 责任 | 实施边界 |
| --- | --- | --- |
| 运行与采集 | 保存实际模型尝试、上下文、响应和用量；接收并处理部门指导 | 继续由原生内核决定处理顺序、交接和停止；适配器单次请求，不让页面自行推进部门 |
| 查询与命令接口 | 将事件和工件组织成总览、部门、请求详情及统计；接收带目标的用户命令 | 复用已有存储、审计及 Web API；查询不改状态，命令不由前端拼造有效材料 |
| 工作台界面 | 按原型呈现信息、输入、导航、等待和错误 | 同一任务身份贯通各页；Provider 配置区域预留；原始内容安全呈现，界面无模拟业务数据 |

以上是模块职责，不要求拆服务。先核对现有前端和 Python 依赖能否满足交互；原型中的单文件脚本仅为参考，不整体替换生产代码，也不为这次改版预先引入新的 Agent 或前端框架。

现有实现入口为 [Web/API](../harness/web/server.py)、[查询投影](../harness/views.py)、[交互持久化](../harness/interactions.py)、[部门循环](../harness/orchestrator.py)、[上下文装配](../harness/context.py) 和 [Responses 适配器](../harness/adapters/responses.py)。规划依据来自当前源码；开工时重新固定基线，衔接其他任务的修复。

## 5. 首个贯穿验收任务

沿用原型的 CSV 导出任务作为界面与交互样例，但功能验收以真实任务形成的要求为准：

1. 从总览创建或进入任务，查看产品、工程和质检的真实工作及交接。
2. 在总览追加一个影响导出规则的要求，原文、产品处理、PRD 与工程计划的变化可核对。
3. 进入工程部门追加一条职责内指导，看到真实接收、采用和处理记录；目标变更仍通过产品负责。
4. 从工程 Context 进入对应模型尝试，查看精确请求、响应、Prompt 版本和来源；切换尝试只读。
5. 在受控异常验证中触发一次可恢复失败或小窗压缩，核对重试/摘要来源及用量；真实服务的成功与本地故障模拟分别记录。
6. 由质检依据最终有效要求独立检查，完成交付；从历史重新打开消息、Git 差异和封存，结果与当时记录一致。

额外必验：任务未开始、等待部门、模型慢响应、部分返回后失败、连续重试耗尽、取消、新输入与结果交错、无 usage、采集不完整、查询失败、断线重连、终态输入与长文本。

## 6. 视觉与交互验收

桌面至少检查 1440 和原型 1024 宽度；窄屏至少检查 390/360，Raw JSON 检查 320。按原型核对中性背景、局部状态色、导航、主对话区与检查区比例、流转结构和响应式堆叠；浅色/深色均检查。保留当前可见任务和查看对象，页面不因长模型名、长错误或流式内容重排失控。

真实内容验证发送对象、草稿、重复提交、加载/空态/错误、焦点顺序、输入法、筛选后返回和浏览器历史。Raw 内容按文本呈现，超长内容可浏览；不增加原型没有确认的手动重试或自动重新执行行为。

视觉验证采用冻结预览重新生成同视口截图；原型作者已有截图只作历史参考。本轮已目检原型的总览、工程页、请求列表、窄屏 Raw 和统计页，未运行生产浏览器或业务测试。

## 8. 协作与状态记录

主代理负责需求、行为边界、接口约定及独立验收。运行子代理负责 W1/W6 的采集和指导生效，查询子代理负责一致的事实读取，界面子代理按 W2-W5 组织页面；共享控制模块保持单一负责人，避免与第一阶段在途修复并改。

正式开工先固定代码基线和文件责任，不把各页面分别实现成独立运行器。每包记录已实现、已验证、真实服务缺口及原型等待项，完成后及时独立提交与推送。六项完成之前，仍不启动长期记忆、跨任务项目演化或独立学习管线。
