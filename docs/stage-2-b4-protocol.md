# B4 三次变更真实验收协议

日期：2026-09-14。依赖：B3 外壳可用、A4 的 Prompt 版本机制可追溯、应用在 B3 提交后的冻结身份。本页不是验收结论。

人在项目工作台上走完，不是只调 API。仍用 `provider.md` 当前 back 服务与专用测试密钥。不换服务、不换默认 Prompt、不扩大重试。

## 1. 分层

| 层 | 本包 | 不做 |
| --- | --- | --- |
| 界面 | 从想法建项目、看板、部门、改工程 Prompt、从观测返回 | 不拖拽改状态；不做 B5 |
| 项目层 | 建事项、采纳、继承、Prompt 版本 | 不调用模型 |
| 内核 | 三部门一次事项 | 不改规则来制造放行 |

「仍有效要求」必须出现在第二、三事项的 `[project]` 钉住部件里，不能靠测试脚本把旧要求再贴进事项原文冒充继承。

## 2. 项目与三次事项

长期目标：逐行文本处理工具，可在同一项目里演进。

1. 从想法创建项目。首个事项：从标准输入逐行输出；空输入不崩溃、无输出。独立 QA 放行后自动采纳。
2. 在上一版本上增加文件输入（路径参数）；完整树继承；旧成果可取回；新成果采纳。
3. 把「保留重复行」改为「只保留首次出现」，保持空输入行为，更新必要检查。合法改方向。若有人仍按旧基线放行，应 `held` 而不是覆盖当前采纳。

过程中修改一次工程部门项目 Prompt（可写入一句与行为无关的标识句，便于核对应采用版本）。下一事项必须用新配置版本；历史请求仍显示原版本。

## 3. 必须能追溯

- 看板卡片与项目/run 事件一致。
- 部门 Context 能跳到对应模型尝试，返回后范围不变。
- 封存恢复后用外部 Python 跑公开检查。
- 观测可按项目 / 事项 / 部门筛选；两个项目互不可见。
