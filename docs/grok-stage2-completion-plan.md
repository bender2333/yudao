## 3. 不可违反的边界

1. 保持控制层、运行/采集层、查询层和界面层的职责边界。查询不能推进运行，页面不能自行执行部门循环。
2. 不引入第二套运行器，不把 OMP 作为运行依赖，不为 Provider 配置界面自行发明未确认的表单。
3. 不添加兼容层、迁移脚本、别名字段或隐式 fallback。过时接口直接删除并同步调用方和测试。
4. 不把本地 fake、mock、探针成功、历史提交或候选分支结果写成真实阶段验收成功。
5. 真实 Provider 使用 `provider.md` 指定的服务、模型和专用测试密钥；密钥不得写入代码、报告、截图或提交。
6. Provider 能力未公开时，使用显式登记的实验限制，不把限制写成服务商标称上限。
7. 所有真实失败必须保留原始错误、请求身份、输入来源和停止原因；不可通过关闭证书校验、修改全局网络或无限重试掩盖故障。
8. 每个工作包形成独立提交，提交前运行对应测试并记录报告；不要重写无关的 `jour.md` 或 `.serena/project.yml`。

## 4. 执行顺序

### P0：冻结基线和证据账

**任务**

- 固定 `239c3b1` 为本轮起点，记录候选分支和提交拓扑。
- 建立一份工作包证据表，区分：主线代码、候选代码、局部测试、真实运行、最终验收。
- 更新状态文档中明显过时的措辞：把 W1/W2/W3/W4/W6 改成“已有候选或局部实现，待修正、合入、联调和验收”；不要把它们改成完成。
- 修正文档中“没有应用代码变更”这类只适用于历史提交时点的表述。

**完成证据**

- 基线提交、工作树状态、候选提交列表和证据表。
- 文档状态与 `HEAD=239c3b1` 一致。

### P1：合并并审查 W1/W2/W3/W4/W6 候选

**任务**

- 审查 W1 请求采集查询、W2 工作台、W3 Context/请求详情、W4 请求列表/用量、W6 部门指导候选。
- 只合入与当前主线兼容且通过独立审查的提交；不直接合并整个隔离分支。
- 保持一次事实来源：事件、工件和已有投影继续是查询基础。

**完成证据**

- 每个工作包一个提交或清晰的合并提交。
- 合入前后的测试差异、已知风险和未关闭问题列表。

### P2：关闭 O1-O6、U1-U6、G1-G3

#### O 类：观测与查询

- O1：在途、已发送、收到部分输出、失败和完成必须可区分；部分输出不得进入有效部门历史或工具执行。
- O2：保存主机观察时间和本地顺序；Provider 原始时间缺失时不能拼造单一时序。
- O3：API、列表、详情和筛选保留 `cancelled`；UI 增加取消状态标签和筛选。
- O4：失败/取消尝试的消息只在观测详情出现，不混入普通部门历史。
- O5：`reported=False` 的 usage 不进入 Provider 上报小计和覆盖率；单条记录显示来源或未知状态。
- O6：统计总计补充有来源的费用和币种；不可合计时明确显示，不填零。

#### U 类：工作台行为

- U1：浏览器后退和前进必须重新按 URL 对象加载任务，不能复用另一个 run 的缓存、草稿或详情。
- U2：SSE 在总览、部门页、列表和详情中都能更新当前对象；详情不能因关闭 SSE 永久停止刷新。
- U3：长任务标题只在必要位置显示；关联区使用短目标，原始全文从输入详情查看。
- U4：Request/Response/Raw 使用视口内可滚动区域，至少用真实 64KB 请求在 320px 视口验证。
- U5：同时显示 requested provider/model 与 actual provider/model；没有响应模型时保持 unknown，不回填当前配置。
- U6：终态任务保留草稿并停止发送；只有显式“新建任务”入口能创建新 run。

#### G 类：部门指导

- G1：`completed` 必须绑定针对该 guidance 的真实回应、接纳事件或主机结果引用；只写自然语言“已处理”不能通过。
- G2：非活动部门需要被主动安排；保存被让出的工作依据，只恢复仍有效的工作。
- G3：指导、协作、取消、QA 和拒收的竞态必须有明确顺序；未得到真实处理结果时不能自动标记 processed 或放行 QA。

**完成证据**

- 每个缺口都有确定性测试。
- 至少一组真实长文本、失败响应、取消和 SSE 浏览器回归。
- 查询结果、导出结果和页面展示使用同一事实口径。

### P3：完成 W5/W7 工作台联调

**W5 范围**

- 总览真实流转、全局输入、交接详情、近期历史、材料入口、交付封存和历史回看。
- 全局追加只能由产品处理为有效要求；部门指导不能绕过部门职责边界。

**W7 范围**

- 按冻结原型检查 1440、1024、390、360 和 320px Raw 视口。
- 检查浅色/深色、导航、消息区、检查区比例、长模型名、长错误、流式内容和空态/错误态。
- 验证任务切换、浏览器历史、草稿、重复提交、取消、断线重连、筛选后返回和 Raw 复制/导出。

**完成证据**

- 冻结原型对照截图和视觉差异记录。
- Node UI 回归、Python Web 回归和真实浏览器记录。
- W5/W7 的完整流程报告，不以单个页面截图代替。

### P4：完成 Provider 与第一阶段真实验收

在 P2/P3 的跨层行为稳定后，使用冻结源码和 `provider.md` 指定配置执行：

1. 创建任务并完成基础三部门流程。
2. 在同一 run 追加真实新要求，验证输入版本、PRD、工程计划、Git 差异和交付变化。
3. 执行小窗压缩，核对摘要来源、原始输入、请求身份和继续执行。
4. 覆盖慢响应、TLS/连接中断、过载、429、重试耗尽、部分返回后失败、取消和迟到结果。
5. 由独立 QA 依据最终有效合同放行，验证交付封存、Git、事件、来源审计和 replay。

**停止条件**

- 真实服务失败时保存报告并标记 BLOCKED/PARTIAL，不能换服务、换 Prompt 或扩大重试次数来制造成功。
- 一次探针成功只能证明成功路径存在，不能关闭长流程连接风险。

### P5：完成 OMP 采用项的独立验证

- 固定所审查的 OMP 源码版本和具体路径。
- 对每个采用项记录：Yudao 已有等价能力、决定采用的最小机制、适配边界、不采用理由和测试。
- 至少验证请求/响应/工具/usage 稳定身份、失败可见、查询不推进、压缩不切断工具回合等原则。
- 将未采用的 OAuth、自动发现、远端压缩回退、复杂并行 Agent、独立 Stats 库明确归档。

### P6：完成 Prompt 固定任务比较

- 固定基线 Prompt、候选 Prompt、Provider、模型、工具集合、运行限制和任务材料。
- 任务族覆盖：带方向变更的文本任务、结构化数据任务、需要专家澄清的任务、带公开回归检查的修复。
- 基线组和候选组使用独立工作区和原始起点，交替执行，保留所有失败。
- 比较要求保持、计划合规、纠正与重复错误、协作正确性、交付/错误放行、实际请求成本。
- 结果只允许得出“采用、缩小范围或保留原版本”，不能从单次成功或模型自评推出质量改善。

### P7：启动 2.1 可信观察与固定基线

只有 P0-P6 的六项前置全部有完成证据后才能启动。

- 建立可搬移的观察证据包、显式交付复核、批次来源、问题轨迹和成本口径。
- 固定重复错误场景的基线任务和独立评价方法。
- 2.1 的基线报告必须能从结果回到原始输入、合同、计划、请求、尝试、工具和 QA 事实。

### P8：推进 2.2、2.3、2.E、2.4

- 2.2：在 2.1 基线上验证一个有界控制变化，使用未见任务和固定评价。
- 2.3：实现跨任务经验候选、独立验证、适用检索、采用、冲突和失效闭环；不得把同一 run 内的 LessonCandidate 当作长期记忆。
- 2.E：实现项目、变更和 run 的分离；验证连续三次真实变更、基线继承、合法改方向、项目采纳和新会话接续。六项前置完成后可与 2.2/2.3 并行。
- 2.4：最后比较基础、仅控制、仅经验和组合方案，并完成未见任务和反证失效验证。

## 5. 每个提交必须附带的回执

每个工作包完成时，向主任务回报以下内容：

1. 提交哈希和修改文件。
2. 当前行为变化及未改变的边界。
3. 运行的确切命令、通过/失败/跳过数量和报告路径。
4. 真实 Provider 是否调用；若调用，使用的模型身份、运行限制和脱敏结果。
5. 仍未解决的问题、阻塞原因和下一依赖。

不要把历史测试数字与当前 HEAD 的测试混加；不要删除失败报告；不要把候选分支状态写入主线完成状态。

## 6. Stage2 完成判定

只有同时满足以下条件，才可以把 Stage2 标记为完成：

- 六项前置工作均已在冻结主线完成并有独立验证。
- 第一阶段真实 Web 持续输入、小窗压缩、最终 QA、交付封存和来源审计全部通过。
- W1-W7 的工作台、观测、部门指导和真实浏览器行为已联调通过。
- Prompt 比较有固定任务、独立结果和成本证据。
- 2.1、2.2、2.3、2.E、2.4 的目标、依赖、结果和失败边界均已完成记录。
- 文档状态、提交拓扑、测试报告和真实运行报告相互一致。

在达到上述条件前，阶段状态只能写为 `PARTIAL` 或 `BLOCKED`，并说明具体缺口。
