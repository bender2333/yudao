# D40 骨架与应用：骨架向后兼容，应用一次完成

状态：有效。依据：[总图](../architecture.html)第二节三环与第四节「路由」「装配」「执行」三道缝、「投影」的缝里的最小投影；设计：[骨架与应用设计说明](../design/skeleton-and-application.md)、[可信内核设计说明](../design/trusted-kernel.md)；相关记录：[D35 自举](self-hosting.md)、[D38 系统意图与基础规则](system-intent.md)。路线位置：[总体路线图](../program-roadmap.md)阶段一「核心打通与换骨架」。编号 D39 留给暂缓的黑板编排。

## 已确认

1. 系统分两层。骨架要考虑向后兼容；应用一次完成，可以整体重写，内部没有兼容义务。
2. 分界不以现有 ADR 为限。分界用两条判据画出：下一个版本必须读得懂的事实（不能重算）进骨架；不会和 Yudao 同时换版本的对方所依赖的合同进骨架。再加一条：应用整体重写时没人保证它没有丢掉「一定会停」与「写入要经裁决」，所以这两件机制也在骨架，规则本身在定义里。与现有 ADR 冲突的地方以[骨架与应用设计说明](../design/skeleton-and-application.md)第 2 节为准。
3. 骨架分两部分：可信内核（谁能改：只由用户批准，范围按[可信内核设计说明](../design/trusted-kernel.md)）与契约（怎么改：只能向后兼容，可以按普通流程修改）。
4. 裁决只读骨架自己算的最小投影：每条流的当前版本、谁持有执行权、已用的时间与次数、每种正式成果的当前版本、当前定义与参数的版本。其余投影归应用，由应用从同一本事件日志自己算。
5. 路由、装配、执行是三道按定义选择实现的缝。任务池是路由的一个实现，进来时不碰骨架；黑板编排仍然暂缓。
6. MCP 与技能继续做。
7. 看门狗只写设计，建设在阶段三；成果由 Yudao 直接采纳之前，升级与回退都由用户手动进行。
8. 不建进程内的插件加载机制。版本切换靠槽位重启，定义已经是带版本、可撤回的数据，这个结构付不出租金（基础规则 5）。Cordis 留下的只有「契约先定、按键寻址」一条，缺的是三道缝的契约文字。
9. 部门留在定义里，不做成各自的代码包。「谁改谁」从「谁评价谁」反推：被谁评价，就不能改谁；工程被质检评价，工程不能改质检。
10. 真实用户场景验收放进测试分层的发布前一层，把试用技能的新手段自动化，说明书就是 README，不另写一份。
11. 骨架要能支持两种路由；任务池值不值得做，以后用评测回答。
12. 第二种路由不受之前 ADR 的限制，复用骨架，不改动成果驱动已有的成果与结构；约束它的只有骨架与基础规则。基础规则 3「生成者不裁决自己」由它用自己的方式满足。
13. 裁决规则「只能收紧」读作：已有的许可只能收紧，新的工具、提案与成果种类随定义的新版本加入、照常经过裁决。
14. 骨架要满足的七条写进设计说明第 5.4 节，验收用一个只在测试里用的第二种路由证明。
15. 裁决分开放：内核做通用检查与提案合同里的通用条件，成果驱动特有的检查由路由提供、只能收紧（设计说明第 5.5、12 节）。
