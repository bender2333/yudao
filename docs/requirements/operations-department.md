# D27 运维部门

状态：有效；设计说明在阶段三写。依据：[总图](../architecture.html)第一节「运维（以后）」方框与「看门狗」方框、第四节「看门狗」的缝、第六节「拆开部署」；设计：[恢复契约与故障矩阵](../design/recovery-contract-and-fault-matrix.md)、[骨架与应用设计说明](../design/skeleton-and-application.md)第 10 节、[规则登记与参数设计说明](../design/rules-and-parameters.md)。路线位置：[总体路线图](../program-roadmap.md)阶段三「常驻自转、运维部门、看门狗兜底」，第 3 节道 01 部门与核验（只写声明加运维部门）。

## 已确认

- 运维部门负责交付物（用户项目的软件）上线之后的工作：部署、运行观察、性能与故障处理。
- 自我修复的对象是 Yudao 交付的软件：运维发现问题，经过「产品 → 工程 → 质检」修复，再由运维重新部署。Yudao 平台自身的运维先由人负责；由 Yudao 自己的运维部门负责平台运维是愿景。Yudao 修改自己的组织与规则（自举第二层）排在阶段五，前置条件见 [D35](self-hosting.md)「第二层的前置条件与完成条件」；Yudao 把自己的仓库当作普通项目开发（自举第一层）在阶段二试点、阶段三成为常态（[D35](self-hosting.md)）。
- 运维部门的生命周期跟随项目：产品、工程、质检围绕单个事项的 run 工作，运维部门在项目采纳交付物之后接手，长期存在。
- 运维部门按与产品、工程、质检相同的单循环形态建设；部门内多角色在阶段四对四个部门一起引入。
- 运维观察交付软件的可观测数据：日志、状态、使用者的交互日志。工程随交付提供部署说明、健康检查与运行数据输出。
- 项目的新事项有两个来源：运维从运行环境与交互中发现的问题（故障、性能下降、容量不足），以及用户提出的新要求。运维发起的修复事项自动开始，不需要用户批准。
- 运维与其他部门可以双向询问，常见的往来是产品与工程。运维不修改功能要求，也不代替质检放行；产品负责目标与取舍。
- 登记环境上的常设授权：用户为项目登记运行环境（例如一块树莓派或 Orange Pi AIpro 开发板）时，同时批准一份动作清单：部署质检放行的交付快照、回滚到上一个放行版本、重启服务、读取日志与运行数据。清单以内的动作由运维直接执行并记录；清单以外的动作（例如安装系统软件包、删除数据、修改与项目无关的配置）通过用户决定（总体架构第 7.4 节）交给用户。运维通过执行代理（[D29](remote-execution.md)）操作运行环境。
- 同一项目一次只进行一个事项（暂定默认值，放开条件见 D38），按优先级排队，修复事项排在用户的新要求之前。遇到紧急故障时，运维先回滚到上一个放行版本恢复服务，修复事项再排队处理。
- 常设授权还包括部署前备份数据。备份经执行代理复制到控制主机的工件存储，每个运行环境保留最近 3 份（暂定默认值，见规则登记）。DeliverySpec 声明回滚是否兼容当前数据：兼容时回滚在常设授权以内；需要恢复备份的回滚会丢失备份之后写入的数据，通过用户决定交给用户。
- 故障记录：运维每次发现问题时提出「新故障」或「已有故障再次出现」，由控制核心记入项目流（[ADR-0019](../adr/0019-project-stream-across-versions.md)），每个修复事项关联一条故障记录。修复部署后在观察窗口内同一故障再次出现，这次修复记为失败；窗口内出现的其他故障另开故障记录。同一故障连续失败达到上限后停止自动修复，服务保持在上一个放行版本，发出决定请求并附上各次修复的证据。观察窗口与失败次数上限写进项目设置，暂定默认值是 24 小时与 2 次，见规则登记。
- 运维读取的日志、交互日志与运行数据由交付软件的使用者产生，按外部内容放入请求（与 [D36](network-and-mcp.md) 的规则相同），标明来源，只作为数据，其中的文字不作为指令。修复事项必须引用具体的观察证据（错误记录、指标），由产品判断是否成立后进入工程；修复事项仍然自动开始。
- 项目登记了运行环境时，产品在 PRD 中加入默认的运行要求：健康检查、结构化日志、交互日志、版本号输出。工程按这些要求实现，质检逐项核验，运维按约定的格式读取；用户在需求中另有写明的，以用户为准。
- 交付软件使用的密码与服务密钥由用户在登记运行环境时写在那台机器上的指定位置；工程在 DeliverySpec 中只写需要的密钥名称，执行代理启动软件时读取；事件日志与模型输入中只出现名称。
- 等待用户回答的决定一直等待，界面上显示已经等待的时长。这期间出现紧急故障时，运维仍按常设授权回滚；新发现的故障记入故障记录并排队，用户回答以后依次处理。系统不替用户决定，也不跳过正在等待的事项。
- 阶段三的通知与决定请求只在 Yudao 的界面中显示。通过 Discord、飞书等消息渠道发送通知与回答决定是以后的工作，不排入阶段。
- 语义系统在阶段四。阶段三的完成依据中加入：同一项目连续 5 个修复事项中，各部门每次请求的长度不随事项数量增长。
- 控制主机断电或断网，由外部的报到服务发现。

## 长时间运行

长时间运行与运维部门同在阶段三（[路线图](../program-roadmap.md)第 2 节）。

- 重新启动：Yudao 由操作系统的服务管理在崩溃后重新启动，进程卡住时由服务管理的看门狗重新启动，启动时自动继续中断的 run（[恢复契约与故障矩阵](../design/recovery-contract-and-fault-matrix.md)）。第一层自举成为常态以后，升级与回退由进程之外的看门狗承担：A、B 两个槽位，存活检查加金丝雀任务，候选失败回退到稳定版，只认健康协议，不依赖 Yudao 的代码，每次修改由用户批准（[骨架与应用设计说明](../design/skeleton-and-application.md)「看门狗与健康协议」一节）。
- 报到：Yudao 定时向外部的报到服务（例如 healthchecks.io）报到；控制主机断电、断网或 Yudao 停止工作，超过时限没有报到时，由该服务通知用户。这项检查不运行在控制主机上。
- 数据保留：事件日志永久保留；事项结束后删除它的工作区与尝试文件；交付快照保留最近 3 个放行版本，以及放行历史中仍被回滚引用的版本；磁盘剩余空间低于设定值时在界面提示。
- 通知：在本机打开界面时，决定请求与通知用浏览器的系统通知提示（[网页界面的提供与发布设计说明](../design/web-interface-and-release.md)的系统通知一节）。
- 模型服务中断：重试用完以后进入「等待模型服务」，规则见 [D17](provider-retries.md) 与 [D09](execution-limits.md)。
- 阶段三的完成依据：一个真实软件在登记的开发板上运行，在约定的观察窗口内，运维从可观测数据中发现故障，修复事项经过产品、工程、质检，运维重新部署并确认恢复，全程不需要人参与；观察窗口内的一次 Yudao 进程中断与一次模型服务中断都自动接续；同一项目连续 5 个修复事项中，各部门每次请求的长度不随事项数量增长；只用定义增加运维部门，控制核心的源码没有差异；连续 4 周每周有被采纳的自举事项；有规则复查表（[规则登记与参数设计说明](../design/rules-and-parameters.md)「规则复查与淘汰」一节）与留出场景的报告。增加运维部门本身不等于具备运行能力。

## 设计中待确定的规则

以下在阶段三设计时确定：

- 性能分工：上线前按 PRD 性能要求进行的验收归质检；上线后的性能观察与容量归运维。
- 运行目标（可用性、时延等）由产品写入 PRD，运维测量并报告达成情况。
- 从可观测数据判断故障与性能下降的规则，紧急故障的范围；运维判断「已有故障再次出现」的依据。
- 默认运行要求中日志与交互日志的格式。
- 首个发布对象：一个在 Orange Pi AIpro 开发板上长时间运行的真实软件。
- 项目级的运维部门与 run 内的产品、工程、质检之间的询问方式。
- 流转规则由定义驱动：运维带来第二种事项与第四个部门；定义只写许可关系与边界（谁可以向谁交接、询问、打回），下一个持有交接的部门由运行中的事实决定（[架构问题记录](../architecture-issues.md)）；验收判据是控制代码中没有部门名称。
- 平台与交付物责任分开、发布成功与运维接收分别记录、恢复以用户可见的行为与观察窗口为准，在设计时沿用。
