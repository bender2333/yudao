## 已确认

- 运维部门负责交付物（用户项目的软件）上线之后的工作：部署、运行观察、性能与故障处理。
- 自我修复的对象是 Yudao 交付的软件：运维发现问题，经过「产品 → 工程 → 质检」修复，再由运维重新部署。Yudao 平台自身的运维先由人负责；由 Yudao 自己的运维部门负责平台运维是愿景。Yudao 修改自己的代码与规则暂时不做。
- 运维部门的生命周期跟随项目：产品、工程、质检围绕单个事项的 run 工作，运维部门在项目采纳交付物之后接手，长期存在。
- 运维部门按与产品、工程、质检相同的单循环形态建设；部门内多角色在 Stage 5 对四个部门一起引入。
- 运维观察交付软件的可观测数据：日志、状态、使用者的交互日志。工程随交付提供部署说明、健康检查与运行数据输出。
- 项目的新事项有两个来源：运维从运行环境与交互中发现的问题（故障、性能下降、容量不足），以及用户提出的新要求。运维发起的修复事项自动开始，不需要用户批准。
- 运维与其他部门可以双向询问，常见的往来是产品与工程。运维不修改功能要求，也不代替质检放行；产品负责目标与取舍。
- 登记环境上的常设授权：用户为项目登记运行环境（例如一块树莓派）时，同时批准一份动作清单：部署质检放行的交付快照、回滚到上一个放行版本、重启服务、读取日志与运行数据。清单以内的动作由运维直接执行并记录；清单以外的动作（例如安装系统软件包、删除数据、修改与项目无关的配置）通过用户决定（总体架构第 7.4 节）交给用户。运维通过执行代理（[D29](remote-execution.md)）操作运行环境。
- 同一项目一次只进行一个事项，按优先级排队，修复事项排在用户的新要求之前。遇到紧急故障时，运维先回滚到上一个放行版本恢复服务，修复事项再排队处理。
- 路线位置：Stage 4：运维部门与长时间运行。原 Stage 3 的 3.8 运维工作包并入本项。

## 设计中待确定的规则

以下在 Stage 4 设计时确定：

- 性能分工：上线前按 PRD 性能要求进行的验收归质检；上线后的性能观察与容量归运维。
- 运行目标（可用性、时延等）由产品写入 PRD，运维测量并报告达成情况。
- 从可观测数据判断故障与性能下降的规则，紧急故障的范围。
- 首个发布对象：一个在树莓派上长时间运行的真实软件。
- 项目级的运维部门与 run 内的产品、工程、质检之间的询问方式。
- 流转规则改为由定义驱动：运维带来第二种事项与第四个部门，阶段按部门与事项种类定义，退回与询问动作对应阶段迁移与授权，状态机读取定义（[架构问题记录](../architecture-issues.md)）。
- 运行责任样例中的平台与交付物责任分开、发布成功与运维接收分别记录、恢复以用户可见的行为与观察窗口为准，在设计时沿用。
