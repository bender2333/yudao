# D16 使用 Git 管理任务内变化

状态：有效。依据：[总图](../architecture.html)第一节「一份事实」方框与第四节「写入口」的缝；设计：[ADR-0024](../adr/0024-git-in-process-with-pygit2.md)、[恢复契约与故障矩阵](../design/recovery-contract-and-fault-matrix.md)。路线位置：[总体路线图](../program-roadmap.md)阶段一「单机诚实闭环，三道槽位立缝」。

## 范围

任务内的原文、需求、计划和代码都用 Git 管理。范围是每个任务的本地 Git 历史，在正式接纳时提交。管理原文、ProductSpec/有效合同/PRD、工程计划/PLAN 和交付代码及公开验收记录。prompt 的修改及实际采用继续使用已有版本记录；作者的工作过程（模型对话与工具调用经过）不进入 Git。提供版本与差异查看，改变已生效要求仍通过产品提交新版本，不以 reset 历史绕过接纳或 QA。

跨任务分支合并、远程推送配置、已有仓库导入和项目采用不在本条范围。运行中任务的本地版本仓库与开发仓库本身分别管理。

## 有效设计

- 新输入保留精确原文，并产生对应 Git 提交。产品根据新输入修订 spec 和 PRD 时，产生正式材料提交，能查看前后真实差异及改变、保留、废止的业务说明。
- Git 管理原文、需求/spec、计划和交付代码的版本；事件记录部门职责、执行依据和正式接纳。提交对象已创建不表示需求已生效，只有正式接纳事件引用的提交进入任务有效历史。
- 每个任务使用主机私有的独立本地 Git 仓库。使用成熟 Git CLI，不自行实现 Git 协议，不依赖模型执行 Git 命令。仓库元数据及作者的工作过程不进入公开交付；跨部门上下文按可见范围确定。
- 同一提交中的 spec、有效合同和 PRD 来自同一次接纳。计划和 PLAN 同源；交付代码使用已验证的完整公开树字节。补充产品决定改变合同和 PRD 时同样形成提交。
- Git 父提交取自上次已接纳版本。原文或需求接纳只改变对应材料，保留上次正式交付代码；工具执行中的修改在交付接纳时提交，不随输入接收提前成为正式代码版本。
- Git 对象和内容验证成功后才接纳。一次需求与合同的多条事件在同一个数据库事务内提交，避免半批接纳。不可变提交引用用于查询，`refs/snapshots/` 仅保持对象可达，不表示接纳，不新增可变分支索引及同步流程。
- 用户停止具有立即控制效力，不依赖 Git 或材料保存成功。保存失败也须停止旧工作；明确展示已取消及版本保存失败，尽可能在失败事实中保留精确原文，不伪造已接收输入或新 Git 版本。一般补充输入保存失败仍不接纳。
- Git 变更管理不替代完整交付封存。Git 文件字节与封存来自同一公开树，完整目录清单另外保留，空目录和旧交付独立恢复继续由封存能力保证。
- Web 在现有原文、规格、计划和交付记录展示提交及父版本，事件详情显示真实 Git diff。仅能查询当前任务已接纳事件所引用的版本，不接受任意 Git 命令或修订表达式。缺失或篡改版本明确报错，不从当前工作目录补取。
- 查看版本与差异时，只能查看已接纳事件引用的提交（按事件记下的提交编号读取）；读不出或提交编号对不上时报错。查看时不按事件重新拼出材料去逐字节比对：内容在接纳时已经核对过，Git 按内容寻址，提交编号定了内容也就定了。
- 按事件重新拼出全部材料、与 Git 逐字节比对的完整核对只在专门的完整性检查（`replay.check`）里运行。

## 验收

- 同任务两版需求、计划和代码形成正式 Git 提交；新输入导致的 spec/PRD 真实 diff、原文字节、同源材料和完整封存逐字节一致，界面可以查看。
- 反例覆盖：Git 写入失败、接纳事务失败、未交付代码隔离、跨任务查询拒绝、当前与父材料篡改、停止与保存失败交错。
