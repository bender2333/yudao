# D16 使用 Git 管理任务内变化

## 用户原话与确认

> 添加细节实现，关于变化和变动，使用git进行管理

> 比如spec文档新需求，导致spec变更，那就通过git的方式进行变更管理

用户选择：任务内原文、需求、计划和代码都用 Git。确认范围为每个任务的本地 Git 历史，在正式接纳时提交；跨任务分支合并及远程仓库接入仍留在第二阶段。

## 有效设计

- 新输入保留精确原文，并产生对应 Git 提交。产品根据新输入修订 spec 和 PRD 时，产生正式材料提交，能查看前后真实差异及改变、保留、废止的业务说明。
- Git 管理原文、需求/spec、计划和交付代码的版本；事件记录部门职责、执行依据和正式接纳。提交对象已创建不表示需求已生效，只有正式接纳事件引用的提交进入任务有效历史。
- 每个任务使用主机私有的独立本地 Git 仓库。使用成熟 Git CLI，不自行实现 Git 协议，不依赖模型执行 Git 命令。仓库元数据及部门私有历史不进入公开交付和跨部门上下文。
- 同一提交中的 spec、有效合同和 PRD 来自同一次接纳。计划和 PLAN 同源；交付代码使用已验证的完整公开树字节。补充产品决定改变合同和 PRD 时同样形成提交。
- Git 父提交取自上次已接纳版本。原文或需求接纳只改变对应材料，保留上次正式交付代码；工具执行中的修改在交付接纳时提交，不随输入接收提前成为正式代码版本。
- Git 对象和内容验证成功后才接纳。一次需求与合同的多条事件在同一个数据库事务内提交，避免半批接纳。不可变提交引用用于查询，`refs/snapshots/` 仅保持对象可达，不表示接纳，不新增可变分支索引及同步流程。
- Git 变更管理不替代完整交付封存。Git 文件字节与封存来自同一公开树，完整目录清单另外保留，空目录和旧交付独立恢复继续由封存能力保证。
- Web 在现有原文、规格、计划和交付记录展示提交及父版本，事件详情显示真实 Git diff。仅能查询当前任务已接纳事件所引用的版本，不接受任意 Git 命令或修订表达式。缺失或篡改版本明确报错，不从当前工作目录补取。

## 当前范围

首批管理原文、ProductSpec/有效合同/PRD、工程计划/PLAN 和交付代码及公开验收记录。prompt 的修改及实际采用继续使用已有版本记录；部门私有对话不进入 Git。第一阶段提供版本与差异查看，改变已生效要求仍通过产品提交新版本，不以 reset 历史绕过接纳或 QA。

本轮不实现跨任务分支合并、远程推送配置、已有仓库导入或项目采用；不迁移旧运行数据。开发仓库本身仍按用户已有授权分批 commit、push，和运行中任务的本地版本仓库分别管理。

## 实施状态

已确认，实施中。新增 G 批次在已有原生骨架上接入，由 Codex 子 agent 实施 Git 存储、控制接纳及 Web；主 agent 负责架构、审查和验收。验收覆盖新输入导致真实 spec diff、原文字节、同源材料、Git 写入失败、接纳事务失败、未交付代码隔离、完整封存一致性、跨任务查询拒绝及桌面手机展示。
