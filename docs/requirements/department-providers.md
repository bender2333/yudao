OMP 的角色是模型选择关系，不等同 Yudao 的产品、工程、质检职责。借鉴的是统一 Provider、具体模型、角色绑定的关系；不照搬其多级选择优先链、OAuth、自动发现、扩展和认证回退。部门选定 Provider 下的具体模型，实际连接使用解析后模型的协议和地址。

## 当前状态与职责划分

状态：底层目录、三部门绑定和原生循环接入已实现，已通过本地 HTTP/SSE 多连接回归，真实跨 Provider 完整验收仍未完成。生产 `LoopSystem` 接收统一目录；现有实现在每次模型请求之前按部门默认解析调用目标与凭据（下文「配置与生效」），一次请求内的重试沿用该次解析的结果，进行中的请求不中断；创建事项不再解析调用目标（按项目部门设置的创建前检查由 #89 引入），解析失败时该部门的下一次请求进入待恢复；进程重启后按当前的设置与凭据来源继续解析。每次部门激活只建立与 Provider 模块的桥接，控制核心不持有凭据。旧的单一全局环境配置入口已移除；确定性测试使用明确的 `LoopSystem.for_testing` 入口。

宿主配置格式见 [目录示例](../examples/providers.json)，启动方式见 [README](../../README.md#模型配置)。`api` 与 `smoke` 默认读取 `.yudao/providers.json`，`--provider-config` 可以指定其他路径；目录文件缺失或内容损坏时服务以空态启动。凭据按引用解析，来源依次为进程内存、环境变量与 `.yudao/.env`。示例容量和模型名称是占位信息，不代表任何真实服务的已知能力。

配置由 Provider 模块（`harness/providers/facade.py` 的 `ProviderFacade`）重新读取：服务运行期间约每秒轮询目录文件与 `.yudao/.env`，按内容哈希识别变化；设置页保存、磁盘修改与手动重载都发布新的配置修订，内容无法解析时保留上一有效版本并报告错误（Stage 2.7，提交 `50fd2e1`）。新修订从相关部门的下一次模型请求起生效（#45）；已经发出的请求以及它一次请求内的重试继续使用解析当时的目标。

| 职责 | 管理的内容 | 边界 |
| --- | --- | --- |
| Provider 与模型目录 | Provider 的服务地址、接口协议和凭据引用；该 Provider 下可选模型的身份、上下文容量和输出能力 | 一份连接可供多个模型和部门复用；具体 SDK 与协议转换属于适配器 |
| 部门绑定 | 产品、工程、质检分别选用哪个 Provider 和模型 | 内核依据实际执行部门解析绑定；绑定不改变部门职责、工具权限或可见历史 |
| 执行与观察 | 对解析后的配置发出请求，记录实际尝试、结果、用量和失败 | 复用原生循环和 D17 重试；适配器完成一次请求，不管理任务、部门交接或历史 |

这三部分是现有系统内的职责划分，不要求新建三个服务。统一管理的是连接与模型目录；每个部门只保存绑定关系，无须复制一套 Provider 实现。

共享目录不等于共享可变的活动请求状态。每次部门激活与实际尝试有独立的执行归属，取消准确定位该次请求；不同任务复用配置时不能覆盖彼此的活动调用。现有 Web 单任务执行限制保持不变，本项不引入并行任务调度。

示例：产品绑定 Provider A 的模型 P，工程绑定 Provider B 的模型 E，质检绑定 Provider C 的模型 Q。A、B、C 可以相同或不同；具体品牌和模型尚未指定。

## 配置与生效

1. Provider 配置与部门默认绑定在系统层维护。用户最新明确 Provider 配置等相关原型尚未完成：Web 只预留位置，部门绑定选择、配置编辑、凭据及连接测试等交互待对应原型确定，取代此前“在新建任务入口增加选择”的界面设想。底层目录与绑定能力仍独立推进，当前已有原型内的 Provider 信息只读展示。
2. 每次模型请求由 Provider 模块按「项目部门设置，未写入的项使用部门默认」解析这一次请求的调用目标：连接、协议、地址、上游模型、容量、发送的推理档位与凭据引用；请求事件记录调用目标的公开部分、选择来源与部门 Prompt 版本（[ADR-0005](../adr/0005-resolve-call-target-per-request.md)）。
3. 项目部门设置、部门默认、目录与凭据的修改，从相关部门的下一次模型请求起生效，包括进行中的事项；正在进行的请求不中断，一次请求内的重试沿用该请求的调用目标。部门 Prompt 属于项目部门设置，按同一规则生效（D02、D24）。
4. 启动前验证所有已绑定配置的完整性及所需协议能力。指出哪个部门、哪份配置不可用；没有绑定、凭据缺失或能力不支持时明确拒绝启动，不临时借用其他部门的配置。这项检查按项目部门设置进行，由 #89 在新建事项前引入；在此之前，解析失败时该部门的下一次请求进入待恢复（模型管理设计说明第 5.5 节）。
5. 配置检查通过只表示具备请求条件，实际连接与模型能力仍以真实调用为准。未被本任务使用的 Provider 不阻止本任务启动。

凭据由宿主管理，配置保留引用。事件、Git、上下文工件、导出和浏览器不包含密钥、认证头或带凭据的 URL，也不保存密钥摘要作为模型身份。

凭据按引用在每次模型请求时从当前凭据来源解析，控制核心不持有明文凭据；Key 的更换从下一次请求起生效，包括进行中的事项。可保存宿主提供的非敏感凭据版本标识以区分实际使用版本，不能从密钥内容生成该标识；实际密钥仅用于请求认证。

进程重启后按引用从当前凭据来源继续解析。凭据缺失或被上游拒绝时，该部门的这次请求不发送或不再重试，事项进入待恢复，原因写明部门、模型与具体问题；用户修复配置后继续执行，系统不改用其他部门的配置或其他模型（[模型管理设计说明](../design/model-management.md)第 5.5 节）。停止原因只有一份封闭的清单，属于带版本的定义（[ADR-0014](../adr/0014-versioned-definitions.md)）。

## 与现有循环的关系

- 正常工作、返工和跨激活接续均使用实际执行部门的绑定。工程向产品咨询时，产品使用产品绑定；工程恢复工作后继续使用工程绑定。
- 历史仍属于同一任务的同一部门，跨激活完整保留；切换执行部门时只传递允许共享的工作材料，不转交完整私有历史。绑定不产生另一套会话或运行器。
- 压缩的整理请求使用该部门本次的调用目标，保留独立的调用用途（[模型管理设计说明](../design/model-management.md)第 8.4 节）。单独选择压缩模型属于新增选择，本项不默认开启。
- 上下文装配先取得本次请求调用目标的容量与输出约束。有效窗口等于调用目标的模型窗口，输出上限不超过模型能力；压缩阈值与输出预留都按本次请求计算（模型管理设计说明第 8 节）。模型容量未知时解析失败，事项进入待恢复，不套用其他模型或旧全局值。本地 token 估计的误差仍需明确记录。
- D17 的每次重试沿用该请求的调用目标及有效工作依据，不换 Provider 或模型。次数、取消、新输入处理和失败输出隔离继续由同一内核负责；取消送达正在执行请求的适配器。
- 不同模型可能返回不同工具与推理协议项。协议转换须保存输入、输出与工具关联的可追溯关系，不静默丢弃必需项或将失败的部分输出接入有效历史。

## 多 Provider 与多协议

Provider 身份、模型身份和接口协议分别记录。两个 Provider 可能都支持 Responses；同一品牌名称也不能决定实际使用哪种协议。修改展示名称或更换模型字符串不足以证明多 Provider 路由。

真实适配器支持 Responses、Chat Completions 与 Anthropic Messages（Stage 2.7）；真实 Go 服务覆盖前两种，Anthropic Messages 对当前两个模型受区域与端点限制（[2.7 执行报告](../archive/stage-2-7-provider-report.md)）。优先复用官方 SDK 和现有适配器，让支持该协议的多个独立连接走同一实现。对于选定服务需要的其他协议，先核对已有依赖及维护中的库，所需适配属于该服务的接入交付；在对应协议完成验收前明确标为不支持，不能将不同服务商自动视作 Responses 兼容。

首批服务商为 OpenCode Go（[D23](provider-layer.md)），真实验收使用用户提供的 Go 凭据。本设计不引入全协议平台、模型自动择优、备用服务切换或新的 Agent 框架；其他服务确定后，按其必要协议完成适配。

## Context/Trace 应保存的事实

每次实际尝试可追到该请求的调用目标、执行部门、Provider 配置身份、接口协议、请求模型、服务实际返回模型、调用用途及重试关系。请求开始前即保存选用配置；连接失败且没有响应时仍可解释发往何处，不能依赖最后一次成功响应补出本次身份。

实际采用的上下文与输出限制、SDK 最终发送的请求内容及其来源可核对。统一输入表示与协议编码后的实际请求有区别时分别记录关系，不能把前者冒充已发送的原文。配置显示和导出使用脱敏材料；实际返回模型未知时保持未知。

当前 Responses 请求通过 SDK 的 HTTP 请求钩子保存序列化后的 JSON 对象，独立记录为 `MODEL_REQUEST_SERIALIZED` 及 `sdk_request` 工件，并关联当次激活、步骤和配置快照。该工件保留实际 JSON 内容，不承诺原始字节排版或完整网络报文，不包含认证头。它与统一上下文工件分别保存；无法持久化该证据时不得继续发送请求。完整 Raw Response 和原型中的观测交互仍按 D21 推进。

用量和延迟按实际部门、Provider、模型与尝试归属，任务汇总来自这些事实。不同模型的用量仍是观察数据，不自动触发控制或改变部门模型。

## 验收条件

| 场景 | 应证明的行为 |
| --- | --- |
| 三部门不同绑定 | 捕获实际请求，核对各自目标连接、模型和凭据使用；也覆盖共享 Provider、不同模型以及完全共享配置 |
| 咨询、返工与返回 | 请求交给接收部门的模型，回到原工作后使用原部门模型；历史和工具权限保持隔离 |
| 慢响应、失败重试和取消 | 重试始终命中该请求的调用目标，取消命中活动调用，新输入可结束旧工作；失败不串入其他部门历史或模型记录 |
| 不同上下文容量 | 小窗口部门按自身限制压缩，大窗口部门不被错误套用同一个全局容量；压缩后继续完成工作 |
| 配置变更与缺失 | 部门默认、项目部门设置与凭据的修改从相关部门的下一次模型请求起生效，包括进行中的事项；正在进行的请求与请求内的重试沿用原调用目标；缺失配置、未知容量和不支持协议明确定位到部门，事项进入待恢复，不发生隐式替代 |
| 共享配置的请求隔离 | 不同任务复用 Provider 配置不会覆盖活动调用，取消不误伤其他任务，迟到结果仍属于原部门和原尝试 |
| Web 与历史观察 | 实时与历史显示实际使用配置，导出与请求证据一致且无凭据；配置及绑定选择页面等待原型，单独验收、不计为已完成 |
| 真实跨 Provider 流程 | 至少两个不同 Provider 配置在同一任务中由不同部门实际使用，完成协作和最终 QA；所宣称支持的每种协议均有真实请求与工具往返证据 |

本地请求捕获用于验证确定性路由和异常边界，不能代替真实服务验收。同协议的多连接验收不能证明其他协议已支持；当前单一 Provider 的连接成功也不能证明本项完成。

2026-09-06 本地实现验证：10 项 HTTP/SSE 集成场景通过，包括两连接与三个模型、咨询与返工、同目标重试、共享配置的并发取消隔离、凭据与绑定冻结、重启拒绝重绑定、缺失实际模型、缺失用量和小窗压缩。完整协作及小窗场景的输入来源、配置、输出限制与 replay 独立审计通过。全仓 35 个 Python 测试文件按四组覆盖，769 通过、7 项 Windows 平台能力跳过；前端 50 通过，桌面及手机只读字段复验通过。此次没有新增外部 Provider 调用，真实跨 Provider 最终 QA 和配置 UI 均未计为完成。

## 推进顺序
