# D17 模型等待与失败重试

## 用户原话

> 失败应该有重试机制，不能因为llm响应过久就失败，目前我看最长的响应应该是1分钟。

## 已确认

- 瞬时 provider 失败需要自动重试，不能一次波动就结束任务。
- 正常模型等待需要容纳约一分钟的响应；一分钟是用户观察值，不是要求在 60 秒中止。
- 新增细节单独保存，本项更新此前连接失败立即停止的设计。

## 本轮实施选择

原生内核负责决定重试与停止，Responses 适配器负责单次网络请求及错误分类，继续使用官方 SDK。默认单次请求等待 600 秒，`YUDAO_MODEL_TIMEOUT_SEC` 可调整。每个逻辑请求最多尝试 3 次，通常退避 1 秒、2 秒；限流或临时服务错误提供有效 Retry-After 时，最多等待 60 秒。

连接/TLS 中断、超时、HTTP 408/409/429/5xx 和没有终态的断流可重试。认证、参数、协议内容及上下文容量错误不盲重试。重试沿用当前 provider、模型和有效工作依据，不切换模型或服务。

每个实际尝试使用新的模型步骤编号，重新经过上下文装配和请求准入，计入每次部门激活最多 32 次调用。工作调用与压缩调用遵守相同规则。成功后下一次逻辑请求重新计算重试次数；重试耗尽才正式失败，步骤耗尽仍暂停。用量继续只读记录，不决定是否重试。

失败尝试的完整输入、已经收到的输出与用量仍保存供审计；失败步骤的输出不进入部门有效对话、摘要或工具执行。后续请求继续携带原文、当前工作和此前有效的本部门历史，不能把失败流里的残缺工具调用当作已完成回合。各部门历史边界不变。

退避不占状态锁，停止/取消立即打断等待。退避期间及下一次实际请求开始前检查新增输入，由产品处理已接收的新原文；旧工作不继续重试或接纳。Web 显示失败尝试、重试次序与等待，重试期间不提前把任务标为失败。

## 实现状态

H 已实现，收尾验收见 [验收记录](../mvp-acceptance.md)。默认等待仍为 600 秒；本地 SSE 延迟 65 秒后正常完成，仅调用一次。可恢复失败最多尝试 3 次，永久错误不重试，工作与压缩共用实际步骤计数。原始输出即时保存，失败尝试隔离、下一请求重新装配及取消/追加输入边界均有定向回归。

桌面与手机实际验证等待期间取消、追加输入后经产品继续到 QA，以及终态不残留等待文案；Node 前端 50 项通过。真实 `provider.md` 模型已出现通过重试恢复的连接中断，但 Web 与小窗两场最终仍因连续 3 次连接失败停止，未取得完整 QA 放行。真实运行源码与随后收尾修正分别记录，旧失败证据不改写，不以独立诊断替代任务完成。
