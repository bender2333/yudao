# D09 循环次数与超时限制

## 用户原话

> 细节，暂时不考虑provider 用量，先按照循环次数来进行限制，或者时间限制

> 不用限额。进行时间限制即可，尽可能放开限制，确定收敛即可

2026-09-30 架构师建议：因为模型不调用工具或工作区出现无法表示的条目而暂停的 run，发出决定请求，处理以后可以继续。用户回答：

> 暂停的 run 能不能继续采纳建议

## 已确认

- 当前不以 provider 用量作为任务是否继续的依据。
- 运行时间（`run_time_limit_sec`）作为主要收敛保证；循环次数和模型步数限制保留但默认值大幅放宽。
- 不围绕 provider 费用或 token 预算增加控制复杂度。
- 等待模型服务（2026-09-28，属于 Stage 4 长时间运行，见[总体路线图](../program-roadmap.md)第 5.1 节）：按 [D17](provider-retries.md) 重试用完以后仍然是连接失败、服务端错误、过载或限流，以及凭据失效、证书校验失败时，run 暂停并进入「等待模型服务」，按间隔重试，服务恢复后自动继续；进入等待时通知用户一次，用户可以取消。等待模型服务的时间不计入运行时间上限（`run_time_limit_sec`）。请求内容错误与上下文过长不进入等待，按原有规则处理。
- 暂停以后继续（2026-09-30）：因为模型连续不调用工具（`no_tool_call`）或者工作区出现无法表示的条目（`workspace_unrepresentable`）而暂停的 run，由用户决定处理以后继续执行或者停止事项；继续时从暂停的位置开始，已用的次数与时间不重新计算。因为次数耗尽而暂停的 run 不继续，需要新的额度时另开新事项。

## 当前实施选择

原生循环采用运行时间限制（`run_time_limit_sec`，默认 7200 秒）作为主要收敛保证。部门激活次数上限（`max_cycles`，默认 999999）和每次激活模型步数上限（部门循环的参数 `max_model_steps`，默认 999999）保留，但在实际运行中不再成为有效约束。调用方仍可显式配置较小值以恢复旧行为。单次模型请求保留超时处理。删除任务 token 预算配置及由此触发的暂停，不保留旧配置回退。

达到 `run_time_limit_sec` 上限进入 `FAILED`（停止原因为 `time_limit`）；达到 `max_cycles` 上限进入 `PAUSED`（停止原因为 `max_cycles`）；达到 `max_model_steps` 上限进入 `PAUSED`（停止原因为 `model_steps_exhausted`）。工作步骤连续第 4 次回复仍没有工具调用时进入 `PAUSED`（停止原因为 `no_tool_call`，见 [语义系统设计说明](../design/semantic-system.md)第 10.6 节的主机提示）。工作区出现公开树无法表示的条目（链接、特殊文件等，不含项目忽略规则排除的路径）时进入 `PAUSED`（停止原因为 `workspace_unrepresentable`），停止说明列出这些条目在工作区内的相对路径，人工处理说明是把这些路径加入项目的忽略规则或者删除它们。时间限制在每次激活准备和每步之间检查，使用单调时钟，不受系统时钟调整影响。停止原因只有一份封闭的清单，属于带版本的定义（[ADR-0014](../adr/0014-versioned-definitions.md)）。

`no_tool_call` 与 `workspace_unrepresentable` 暂停时，流程编排发出决定请求（[总体架构](../design/architecture/overall-architecture.md)第 7.4 节），阻塞范围为 run，选项为「处理以后继续执行」与「停止事项」，说明写明停止原因与人工处理说明。用户先处理：`workspace_unrepresentable` 把列出的条目加入项目的忽略规则或者删除；`no_tool_call` 可以先在部门设置中更换模型，从下一次请求起生效。回答继续以后，run 从暂停的位置继续：已确认的工具结果与提交不重新执行，已用的激活次数、模型步数与运行时间不重新计算，连续不调用工具的计数从零开始；同样的情况再次出现时再次暂停并发出新的决定请求。回答停止时事项停止，停止原因保持暂停时的原因。`max_cycles` 与 `model_steps_exhausted` 暂停的 run 不发出这个请求。

单次模型请求的时限只计算等待模型提供方的时间：从请求发出开始，到收到最后一段输出为止。主机自己的工作不计入，包括 SDK 的一次性初始化（在服务启动时完成）、请求发出前的落盘与输出片段的落盘。

SDK 返回的用量可作为只读事实保存，但不影响任务推进，也不猜算价格。上下文容量检查属于请求能否发送的约束，与 provider 用量预算分开；旧历史按 D10 自动压缩，固定原文和当前工作无法容纳时明确停止。

## 实现状态

已实现。采用运行时间限制（`run_time_limit_sec`）、部门激活次数（`max_cycles`）、每次激活模型步数（`max_model_steps`）和单次请求超时；摘要调用同样计入步数限制并可取消。达到时间限制后失败，达到次数限制后暂停，不接受后续提交。

用户新增 [D17](provider-retries.md) 后，有界重试同样按实际模型调用计入步数上限，不额外乘大调用上限。默认单次等待 600 秒；瞬时失败在次数许可内重试，等待期间继续处理取消与新输入。该扩展已在 H 批次实施。

等待模型服务及其不计入运行时间上限的规则未实施，在 Stage 4 实施。
