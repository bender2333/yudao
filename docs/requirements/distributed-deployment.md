# D29 分布式部署

确认时间：2026-09-24。状态：需求已记录；部署形态见 [ADR-0012](../adr/0012-single-control-core-scalable-execution.md)，服务之间的六条边界见 [ADR-0007](../adr/0007-boundaries-for-distributed-deployment.md)；拆分在 Stage 6 进行，未实施。路线位置：[总体路线图](../program-roadmap.md) Stage 6：分布式部署。

## 用户原话

2026-09-24 讨论路线图时的原话：

> 3. 另外我想要能支持微服务化，未来的可以拆分成微服务，部署在不同的服务器和平台上，类似分布式系统。 4. 以前的时候，做分布式系统的时候，任务分解是个很麻烦的问题，分布式无法解决依赖问题，也做不到任务分解，只能做编排和运行合并。现在有了AI，我们能做分解了，回到以前的系统，我们突破了核心的动心，能不能给我们的项目带来一些洞见呢？

架构师随后提问：「微服务化的对象是 Yudao 自身，拆分约束现在就记录为 ADR？」用户回答：

> 4. 可以，但是你需要跟我详细解释下。

## 已确认

- 拆分对象是 Yudao 自身：控制层、各部门、元观察与规则检查部门、Provider 与存储部署在不同的服务器和平台上。
- 路线位置：Stage 6：分布式部署。
- 为拆分部署保持的六条边界从现在起遵守，记录为 ADR-0007：消息往来、状态持久化、租约式执行所有权、封存快照传递、查询接口、Provider 统一入口。用户同意记录为 ADR，并要求架构师详细解释这六条边界。
- 2026-09-26 用户决定（[ADR-0012](../adr/0012-single-control-core-scalable-execution.md)）：控制核心（编排器、步骤驱动、上下文装配、裁决规则、写入口）在逻辑上只有一份，为可用性做主备，持有每个 run 的执行权；可以扩展、部署到不同服务器的是执行层（执行环境、Provider、外包 agent 的运行容器）与观察者（教训发现模块、元观察、演化模块等）。部门的身份（权威位置、装配规则、私有历史）保存在控制核心，部门不单独部署成服务；部门需要的执行环境与 Provider 可以部署到不同的服务器。元观察在组织上是一个部门，运行时是一个观察者加判定点。需要时按项目把 run 分给多个控制核心实例，每个实例持有自己那部分 run 的执行权。不引入外部工作流引擎。本条取代第 1 条中把各部门、元观察与规则检查部门作为部署单位的拆分方式；ADR-0007 的六条边界继续有效，作为服务之间的合同。
- 2026-09-26 用户决定（[ADR-0015](../adr/0015-desktop-client-and-http-contracts.md)）：服务之间（控制核心与 Provider、执行环境、外包 agent 的运行容器、观察者）使用 HTTP 加 JSON，流式结果使用 SSE 或分块传输，合同都是 pydantic 类型；接口层使用 FastAPI，从本机以外访问需要认证。

## 讨论中的分析

以下是架构师对用户第 4 项提问的回答，未经用户逐项确认，供 Stage 4 部门内多角色与 Stage 6 分布式部署的设计参考。Cognition、MAST 与 Anthropic 多代理研究系统的来源见[语义系统与部门内多角色：参照调研](../research/semantic-system-and-department-roles.md)。

1. 分解成为带有不确定性的提案。过去只有数据分片这类结构上独立的工作可以自动切分，一般任务是否相互独立取决于含义，框架只能运行人声明的任务图。AI 能理解含义，所以能提出分解；依赖关系仍然隐藏在含义里，分解错误要到合并时才暴露。分解计划写明依赖，由控制层检查依赖是否成环、每项是否有验收条件；依赖事实尽量由代码图谱、构建系统、测试影响分析等工具提供，AI 的判断作为补充。
2. 分解的好坏在合并时检验。合并冲突、接口不匹配、集成导致的缺陷，都说明分解遗漏了依赖。这些证据关联到当初的分解计划，据此重新规划，并交给持续改进工作线，逐步积累有效的分解方式。任务图随执行证据更新。
3. 沿契约拆分，共同决定在并行之前确定。Cognition 指出并行代理各自做出的隐含决定会互相冲突；MAST 统计的失败中，协作失误占 32.15%。能安全并行的单位之间要有事先确定的契约（接口、数据格式、文件归属）；命名、错误处理这类共同决定在分派之前写入设计。PRD 与 DeliverySpec 已经是部门之间的契约，同样的做法向下应用到工程内部的并行任务。
4. 瓶颈转移到验证与集成。分解和生成变得便宜之后，限制产出的是验证与合并的速度。验证比开发更容易并行：针对同一个封存快照、按 PRD 条目、在不同平台上的检查大多相互独立且只读，查证也是这样。Anthropic 的多代理研究系统也观察到依赖多的编程任务不适合多代理。拆分成服务之后，最先受益的是跨平台并行质检与并行查证；工程实现的并行需要契约先行。
5. 流程的每次转移多了第三种结果。带语义的判断便宜到可以设置在每一次交接上，同时带有置信度，所以每次转移都有通过、不通过、不确定三种结果；控制层为每个判定点预先规定三种结果的去向。
6. 确定性的边界。参照 Temporal 的工作流与活动的划分：模型调用、工具动作、决策模型判定都先记录，控制层的每个决定只依据已记录的事实，重放时不重新调用模型。
7. 同一个模式在每一层重复。部门之间、部门内部角色之间、工程内部并行任务之间、服务之间，都是「分解 → 隔离执行 → 集成 → 独立验证」。[组织与持续运行研究](../research/organization-runtime-evolution.md)第 2.2 节的最小工作契约可以作为各层共用的工作单位描述，层级增加时不增加新的机制。

## 设计中待用户确认的规则

以下在 Stage 6 设计时确定：

- 服务端数据库：按故障场景与总成本比较后选定；事件日志的写入口与订阅接口不变（[ADR-0012](../adr/0012-single-control-core-scalable-execution.md)、[ADR-0013](../adr/0013-event-log-and-single-write-path.md)）。
- 各部门需要的执行环境与 Provider 部署到哪些机器与平台（例如运维在生产网络内，质检在测试设备与不同操作系统上，工程在构建机器上），凭据保存在各自的环境里。
- 执行权期限与续期的具体规则（ADR-0012 规定在 Stage 6 加入）。
- Yudao 平台由自己的运维部门负责运维的愿景（D27）与分布式部署的关系，例如由一个部署运维另一个部署。
