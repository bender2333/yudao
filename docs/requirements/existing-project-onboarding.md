# D33 接入已有项目

状态：有效。依据：[总图](../architecture.html)第一节「你」与「一份事实」方框（接入已有项目是事项的一种起点）；设计：[接入已有项目设计说明](../design/existing-project-onboarding.md)、[ADR-0034](../adr/0034-adopted-change-writeback-three-tree-merge.md)。路线位置：[总体路线图](../program-roadmap.md)阶段二薄片 ①「真实项目接着做」。

## 已确认

- 用户可以把一个已有的代码项目交给 Yudao。只用从零开始的新项目测不出在已有代码上修改的能力，运维的修复事项也都是在已有代码上修改；[D32](comparison-experiment.md) 对照实验可以使用已有项目。
- 建档由部门完成：产品读取已有代码与文档，写出描述现有行为的初始 PRD；工程写出现有结构的说明。
- 初始 PRD 通过决定请求交给用户确认，确认后成为当前有效的要求。它决定以后什么行为算缺陷，所以需要用户确认。之后的事项在它的基础上修改。
- 已有的代码快照接入（来源、版本与摘要、文件清单、初始基线、隔离副本）是建档的前提。

## 设计中确定的内容

设计时确定的内容见[接入已有项目设计说明](../design/existing-project-onboarding.md)：

- 大型仓库的读取范围与顺序，初始 PRD 的粒度：第 4.2、4.3 节。
- 工程的结构说明放在哪里，由哪些部门看到：第 4.4 节。
- 已有测试与 git 历史怎样作为初始基线的证据：第 4.5、4.6 节。
- 用户不确认初始 PRD、提出修改时的往返方式：第 4.7 节。

## 设计决定

- 已有项目的代码经 `project.onboard` 接入并建档，`work_item.create` 没有代码快照来源（新建项目可以带起始文件夹，不建档，见 [D37](project-initial-files.md)）；评测场景 2 的 Yudao 一侧先建档，运行器回答确认，建档的用量与耗时在报告中单独列出。
- 建档以后源目录的修改不同步进项目；要在新代码上工作，接入为新项目。采纳写回按 [ADR-0034](../adr/0034-adopted-change-writeback-three-tree-merge.md) 合并事项起点、采纳成果与写回时目标分支三份代码树，保留期间的独立修改，冲突停止，核验最终树后生成分支与合并请求。
- 检查时限 `check_timeout_sec` 的暂定默认值是 600 秒，是项目级参数，按项目记录的检查用时设定，见规则登记。
- 验收用的真实项目：openai-agents-python 在 FeatBench openai-agents-python-842 基准提交时的代码，建档以后的事项实现 issue 842。
- 建档 run 的运行时间上限与普通事项相同，取运行时间上限的暂定默认值（7200 秒）。
