# D34 浏览器与 computer use

确认时间：2026-09-28。状态：需求已确认，设计未开始，未实施。路线位置：[总体路线图](../program-roadmap.md) Stage 3 的 3.2D，依赖 3.2B（MCP 接入）与 3.2C（执行环境服务），排在 3.9 之前。调研：[浏览器与 computer use 调研](../research/browser-and-computer-use.md)。

## 用户原话

2026-09-28 设计评测场景时，用户说明：

> 质检部门一定会安装 computer use 和浏览器使用，浏览器自动化相关的技能和工具，确保质检能够从 prd 生成对应的测试，去对应。

评测要在 Stage 3 结束之前完成，其中场景 1 需要质检操作网页。架构师问这项工具放在哪个阶段，用户回答：

> 这里应该是computer use和浏览器工具，这里可以参考codex

架构师调研 Codex、OMP 与 OpenCode 的做法后提出七个问题，用户回答：

> 评测规定两边都用 DeepSeek V4.1 Flash，这个不成立。可以用gemini 3.8 flash

> 我们会要求质检部门必须有vision能力

> Q4，安全的事情先放低优先级，跟着正常的浏览器mcp一致就行。 Q7，我会单独提供有视觉能力的模型，你无需再操心

> 其他采纳建议

文档写好以后，用户修改质检视觉能力的要求：

> 这样吧，质检部门设置的时候，只进行提醒就行，不必强行要求支持图像。

## 已确认

- 浏览器工具使用 Playwright MCP，经 3.2B 的 MCP 接入：每个动作一个工具；每一步把页面的可访问性结构文本交给模型，模型能看图时同时附上截图；截图另外保存为证据。
- computer use 用来操作桌面程序：被测的桌面程序在容器的虚拟屏幕中运行，部门通过截图、点击与输入操作它。网页应用使用浏览器工具，桌面程序使用 computer use。
- 两个工具在执行环境中运行，被测的交付软件在同一个执行环境中启动。安全暂放低优先级，按 Playwright MCP 等普通浏览器 MCP 的默认做法运行，不另加限制。
- 质检两个工具都可以使用；工程可以使用浏览器做研发自测，模型能看图时也可以使用 computer use；运维是否使用在 Stage 4 设计运维部门时决定。
- 质检部门的模型应当有视觉能力，设置时只提醒，不强制。部门定义写明建议能力，质检的建议能力是图像输入；保存项目部门设置或部门默认时，所选模型不支持图像，照常保存并提醒用户缺少的能力与影响；请求时按模型实际具备的能力提供工具，不支持图像时不提供 computer use，浏览器只给可访问性结构（[模型管理设计说明](../design/model-management.md)第 5.6 节）。质检没有核验的条目按已有规则如实报告，不能放行。
- 评测使用的模型由用户单独提供，有视觉能力，Yudao 与 OpenCode 两边相同（[D32](comparison-experiment.md)）。
- 3.2D 在 Stage 3 中，两个工具在这个工作包里一起验收；评测场景 1 的 Yudao 一侧依赖它。

## 设计中待确定的内容

以下在 3.2D 设计时确定：

- Playwright MCP 在执行环境中的运行方式（容器镜像、浏览器版本）与启用的能力（可访问性快照、截图、断言）。
- computer use 的虚拟屏幕、截图尺寸与动作集合，参照 Anthropic 的参考实现（Docker 容器加虚拟显示）。实现核对见 [computer use 实现调研](../research/computer-use-implementations.md)。
- 截图作为证据的保存位置与在界面上的显示。
- 质检从 PRD 生成测试的方式，以及测试记录怎样绑定交付快照。
