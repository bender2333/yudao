## 3. Stage 4：运维部门与长时间运行

### 3.1 运维部门（D27）

- **已确认**：负责交付物上线后的部署、运行观察、性能与故障处理；自我修复的对象是 Yudao 交付的软件；生命周期跟随项目，项目采纳交付物之后接手；按与产品、工程、质检相同的单循环形态建设；观察交付软件的日志、状态与使用者的交互日志；运维发现的问题作为修复事项自动进入产品、工程、质检流程，用户的新要求是另一个来源；登记运行环境时用户批准常设授权清单（部署质检放行的交付快照、回滚到上一个放行版本、重启服务、读取日志与运行数据），清单以外的动作通过用户决定交给用户；同一项目一次只进行一个事项，修复事项在前，紧急故障时先回滚再排队修复；运维通过执行代理（D29）操作运行环境；与其他部门双向询问；平台自身的运维先由人负责。2026-09-28 第二次讨论补充：故障记录与修复次数上限（观察窗口默认 24 小时，同一故障连续 2 次修复失败后交给用户）；常设授权包括部署前备份数据，需要恢复备份的回滚交给用户；交付软件的密钥只在运行环境机器上；运维读取的日志按外部内容处理；PRD 默认带上运行要求并由质检核验；未回答的决定一直等待，界面显示等待时长；通知与决定只在 Yudao 界面显示，消息渠道以后再做。
- **设计时确定**：需求记录中列出的规则（性能分工、运行目标写入 PRD、判断故障与性能下降的规则、首个发布对象、询问方式、由定义驱动的流转规则）；运行环境在画面上怎样表现。
- **原型依赖**：运维房间、发布与运行环境、故障链路、清单以外动作的用户决定。

### 3.2 长时间运行

- **已确认**：控制主机使用一台常开的机器。Yudao 由操作系统的服务管理在崩溃后重新启动，进程卡住时由看门狗重新启动，启动时按 3.1 自动继续中断的 run；Yudao 定时向外部报到服务（healthchecks.io）报到，超时没有报到时由该服务通知用户。数据保留：事件日志永久保留，事项结束后删除工作区，交付快照保留最近 3 个放行版本及回滚引用的版本，磁盘不足时界面提示。完成依据包括同一项目连续 5 个修复事项中各部门每次请求的长度不随事项数量增长。模型服务中断时，按 D17 重试用完以后仍然是连接失败、服务端错误、过载或限流，以及凭据失效、证书校验失败时，run 暂停并进入「等待模型服务」，按间隔重试，服务恢复后自动继续；进入等待时通知用户一次，用户可以取消；等待时间不计入 D09 的运行时间上限；请求内容错误与上下文过长不进入等待。
- **原型依赖**：run 的「等待模型服务」状态与通知。

## 4. Stage 5：部门内协作、上下文与界面

### 4.1 部门内部循环与角色（D26）

- **已确认**：部门内有固定的角色；产品为产品部门经理、产品架构师、产品探索者、产品审查者，工程为工程经理、工程架构师、主程、工程探索者、工程审查者，质检为质检经理、测试工程师、质检探索者、质检审查者；角色可以配置模型，设置分全局层与项目层；部门内的 SubAgent 就是这里的角色。
- **引入范围（2026-09-28）**：部门内多角色在本阶段对产品、工程、质检、运维四个部门一起引入，运维部门的角色在本阶段设计时确定。
- **内部规则（2026-09-25 讨论确定，详见 D26）**：
  1. 三个部门都采用中心型协作：中心角色分别是产品架构师、工程架构师、测试工程师，探索者、主程、审查者是它的工具；中心角色不做工具角色的写入工作；经理负责对外沟通、提交成果，并关注进度与数据流转、提醒中心角色，不分派部门内的工作。
  2. 三个部门都设审查者（产品审查者、工程审查者、质检审查者），审查每次从新的上下文开始。
  3. 部门向外层提交的每份成果都要通过主机按部门规定的检查，其中包括针对该版本的审查通过记录。
  4. 外层返工回到部门后，从账本接着做，只处理返工涉及的部分。
  5. 部门对外只有经理一个接口。
  6. 可以同时进行：探索者的多项查证、审查与作者的下一项工作、设计与实现分段进行、质检提前设计检查；PRD 被接纳后，各部门可以做预测性探索（只读查证并起草草案，有空闲槽位时进行，PRD 更新后全部作废）。
  7. 一次性角色不设同时任务数与请求数上限；连续 3 轮没有进展时重新规划；角色设置优先于部门设置；角色历史不跨事项延续。
- **原型依赖（已确定）**：部门内由小人走到工位递任务卡与结果卡，三个房间都围绕中心角色布置；白板显示计划条目与状态，点击弹出完整账本（审查次数与意见、进展判断、待决问题与对外询问）。
- **设计草案**：已按以上决定修改（2026-09-25）。草案第 17 节列出的受影响文档（D05、D07、D11、D20、3.4A、语义系统、恢复契约、v7 原型）与两条新 ADR，按用户决定在各阶段需求讨论完后一起修改；期间以 D26 与设计草案为准。

### 4.2 语义系统（D25）

- **已确认**：两项职责，一是整理事实与事件，随时进行语义压缩与分发；二是整理知识图谱与语义工程，供 Stage 6 使用。每个部门有各自的知识图谱；部门历史独立，部门之间只传递主机接纳的结构化结果。
- **2026-09-25 用户声明**：语义系统不是 RAG，也不是长期记忆；它参照 Semantica，是带有知识、事实、证据等内容的知识图谱，给 Agent 做上下文用。分两部分：一是整理（长任务的轨迹与结构化图谱）；二是上下文组装。
- **整理部分已确认（2026-09-25，详见 D25）**：
  1. 轨迹分事项、交接、计划条目、角色任务、尝试五层，带起止位置、结果与因果；部门账本是轨迹在部门这一层的视图。
  2. 轨迹的上面几层由主机从事件生成；尝试由角色在任务结束与压缩之前整理。
  3. 图谱内容分证据、事实、知识、决定、要求、实体、推测七类；事实必须附证据。
  4. 角色在工作中随时记录图谱内容，主机校验后写入；压缩之前补录。
  5. 轨迹与图谱只由事件生成，重放可以重建。
  6. 要求类条目带稳定编号并由主机校验引用；质检放行要求每条有效验收条件都有通过的检查结果与证据。
  7. 证据出现新版本、要求被修改或废止时，主机把受影响的内容标为待复核；矛盾的新事实必须写明取代哪一条或记录为冲突。
  8. 所有部门可见事项层与交接层的轨迹、要求类条目、主机接纳的材料内容与实体名称；计划条目以下的轨迹与部门记录的内容只有本部门可见。
  9. 知识只在本项目的本部门内使用，跨项目复用属于持续改进工作线。
  10. 用户可以查看轨迹与图谱，把部门记录的内容标为失效或写入更正；要求类条目通过追加需求修改；轨迹只能查看。
  11. 语义工程包括项目术语表，以及教训、洞见等语义。
  12. 抽象层包括教训、洞见、画像，必须关联依据；教训与洞见由教训发现模块找出（待设计，见下面的 TODO），洞见只能查询取得；复盘在成果被接纳后与事项结束时由中心角色进行，写出或更新画像；教训是参考内容，主机不强制执行；抽象层属于部门私有，画像按部门各自编写。
  13. Semantica 不作为依赖，借用 PROV-O 对应、四个时间字段、决定与因果、本体加约束形状、冲突类型；轨迹与图谱是存放在现有 SQLite 中的事件投影。
  14. 本体由系统定义，实体类型为固定清单，领域概念作为术语类实体；关系分八组；不记录模型给出的置信度。
  15. 压缩不再生成文字摘要，由角色整理的尝试与补录的图谱内容代替被移出的历史；整理失败按现行压缩失败的规则处理。
  16. 实体身份由「类型 + 名称」确定；实体在第一次被引用时建立；文件的移动与删除由主机按工作区变化记录；其他重复实体在复盘时合并。
  17. 语义系统保留由惊讶得出的知识、教训等内容，并标明来源于哪一次惊讶。
- **上下文组装已确认（2026-09-26，专题讨论，详见 D25）**：怎样获取知识、确认知识正确、把正确的上下文交给模型；用户要求参考 OMP 与 opencode 的实现。每次请求由固定的栏目组成，每个栏目写明来源、上限与重新计算的时机，放入的内容与原因由上下文清单记录；主机只主动放入有效与待复核的内容，事实与知识附证据种类，不计算综合可靠分数；记录事实时用 JEV 核对证据是否支持陈述，校准通过后显示，JEV 的协议接入在 Stage 5；常驻栏目、目录、按需取得、接触文件时附加四种方式配合使用；组装不调用模型；栏目按变化频率排列，历史只追加，当前状态栏目放在末尾且不写入历史，按协议使用缓存；工作上限 100000 token；达到压缩阈值时先把旧工具结果换成带取回地址的占位，不够再压缩；变更与新到达的输入作为通知在安全节点追加进历史；目录按与焦点一步相连的关系选出；各角色的上下文按 D25 专题第 11 条的表格分配，审查者看不到部门记录的事实、决定、推测与画像；压缩后历史开头放主机生成的轨迹节录；查询只用结构条件与全文检索，不用向量；画像、常驻教训、目录、接触时附加各有上限；项目上下文文本只保留名称、目标、当前采用成果与本事项，未采纳事项中只有知识与教训继续有效；JEV 校准样本由强 LLM 给出参照标注、分歧与抽样部分由用户裁定；常驻的当前有效要求只包括本事项 ProductSpec，项目中其他有效要求通过接触文件时附加、目录与查询取得；部门账本在当前状态栏目中显示，上限 4000 token。
- **总体架构中的位置（2026-09-26，详见 D25「已确认」第 26 条）**：语义系统分布在知识层、控制核心的 P 与 U、观察层四个位置，见[总体架构](../design/architecture/overall-architecture.md)第 3 节。
