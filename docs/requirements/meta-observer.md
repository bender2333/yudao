# D28 元观察与规则检查部门

确认时间：2026-09-24。状态：需求已记录，设计在 Stage 5 进行，未实施。路线位置：[总体路线图](../program-roadmap.md) Stage 5：运维部门与元观察。调研：[JEV 决策模型：能力边界与在 Yudao 中的用法](../research/jev-decision-model.md)。

## 用户原话

2026-09-24 讨论路线图时的原话：

> 2.在当前的部门之外，我希望添加一个元观察者和规则检查部门，这个部门会引进JEV，对部门之间的循环流转进行观察，JEV由于有置信度，可以进行一些流程判定和推进。

架构师随后提问：「元观察部门只在事先规定、并经过本地中文样本校准的判定点上自动推进；质检放行、产品取舍、规则修改都不交给它？」用户回答：

> 3.对，只做流程审查和观察，用于未来的自进化

## 已确认

- 元观察与规则检查部门（下文简称元观察部门）位于产品、工程、质检以及运维部门之外，不承担交付工作。
- 引入 JEV（TypeSafe 发布的决策模型 Jev）。
- 元观察部门只做流程审查和观察，结果用于未来的系统演化（Stage 7）。
- 判定点由控制层事先规定。判定点经过本地中文样本校准之后，控制层才按元观察部门的审查结果自动推进；每个判定点的结果分通过、不通过、不确定三种。
- 质检放行、产品取舍、规则修改都不交给元观察部门。
- 元观察部门不读取部门私有上下文，部门也不能向它分派工作。
- 路线位置：Stage 5：运维部门与元观察。

## 设计中待用户确认的规则

以下是架构师在讨论中提出、用户尚未逐项决定的规则，在 Stage 5 设计时确定：

- 判定点清单。讨论中提出的候选：询问应由哪个部门回答；回答是否回应了询问；新缺陷或新询问是否与之前的重复；缺陷是否引用了 PRD 条目；DeliverySpec 是否逐条覆盖 PRD；部门产出是否越权，例如替质检宣布放行。
- 不交给 JEV 的判断：循环整体是否有进展（跨步骤的因果判断，由轮次、重复询问、缺陷集合是否变化等确定的统计发现，再交给 LLM 分析）；代码是否正确；没有参照材料的质量判断。
- 校准样本的来源与标注方式。阈值在一批样本上选取，再用另一批样本复核；未通过校准的判定点只记录、不推进。
- 不确定结果的升级对象（LLM 判断或用户决定），以及循环停滞时事先规定的处理动作（例如请产品部门裁决、通知用户）。
- 每次判定的记录内容：状态、问题、选项顺序、模型版本、概率与置信度；重放使用记录的结果，不重新调用；定期抽样复核。
- 元观察部门的输入范围：事件与已提交的材料。部门产出由模型生成，写入判定状态之前按不可信内容处理，JEV 的判断与确定的检查一起使用。
- 观察范围是否在 Stage 4 之后扩展到部门内部角色之间。
- 审查与观察结果进入语义系统的知识图谱、供系统演化使用的方式。
