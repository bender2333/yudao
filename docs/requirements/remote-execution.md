# D29 远程执行环境

确认时间：2026-09-24，2026-09-28 按使用方式修改，设计 2026-09-29 确认，2026-09-30 按 [ADR-0022](../adr/0022-run-directly-without-containers.md) 修改。状态：设计已确认，未实施。设计：[执行环境服务设计说明](../design/execution-environment.md)。部署形态见 [ADR-0018](../adr/0018-single-control-host-remote-execution.md)，执行环境服务的合同沿用 [ADR-0007](../adr/0007-boundaries-for-distributed-deployment.md) 的边界。路线位置：[总体路线图](../program-roadmap.md) Stage 3 的 3.2C 执行环境服务。

## 用户原话

2026-09-24 讨论路线图时的原话：

> 3. 另外我想要能支持微服务化，未来的可以拆分成微服务，部署在不同的服务器和平台上，类似分布式系统。 4. 以前的时候，做分布式系统的时候，任务分解是个很麻烦的问题，分布式无法解决依赖问题，也做不到任务分解，只能做编排和运行合并。现在有了AI，我们能做分解了，回到以前的系统，我们突破了核心的动心，能不能给我们的项目带来一些洞见呢？

2026-09-28 架构师问 Yudao 在可以预见的时间内给谁用、运行在哪里，用户回答：

> 在可预测的时间内，都是我一个人用，但是会考虑多机部署，比如好几台电脑和嵌入式平台。

> 目前的嵌入式平台是指类似树莓派的板子

## 已确认

- 可以预见的时间内只有用户一个人使用。
- 多台机器的用途是执行：工程的构建、质检的检查、运维的部署与观察，在其他电脑或树莓派一类能运行 Linux 的板子上进行。
- 控制核心、事件日志、工件存储、Provider 模块与观察者在一台控制主机上运行，控制核心只有一个实例、不做主备，事件日志继续使用 SQLite（ADR-0018）。
- 执行环境是一个服务，有两种实现：本机进程与远程机器上的执行代理（ADR-0022）。本机进程在控制核心的进程内直接调用，执行代理经 HTTP 加 JSON 的合同调用（2026-09-29 用户决定）。用户在系统中登记机器，写明名称、地址与用途；每个项目授权使用其中的机器，写明登记的目录、可以执行的操作与是否作为本项目的运行环境，授权范围按项目分开（2026-09-29 用户决定）；只在局域网内使用期间，连接的认证与加密保留位置并标为 TODO，离开局域网之前加入访问令牌与 TLS，使执行代理只接受控制主机的请求。用户 2026-09-28 的原话：「TLS暂时TODO吧，由于现在只在局域网，安全都只占位和TODO即可」。
- 控制主机使用一台常开的机器（台式机、小主机或树莓派），长时间运行依赖它一直开机（2026-09-28 第二次讨论，用户采纳推荐）。
- 模型凭据只保存在控制主机。
- 远程动作的存活按动作判断：执行代理在动作进行期间发送心跳，超时没有心跳时动作结果记为未知，按 3.1 的动作核实处理。
- 代码在执行位置上直接运行，Yudao 不提供操作系统层面的沙箱；来源不明的仓库，把项目的执行位置设到另一台登记的机器（2026-09-30 用户决定，ADR-0022）。

2026-09-28 用户认同部门单独部署在原理上与单机没有区别，同时指出：

> 分布式部署和微服务化有助于资源调度和未来的并发能力，虽然当前不需要做，但是未来仍然是一个很好的架构

据此 ADR-0018 写明扩展途径：执行能力不够时增加执行环境，模型服务限流时增加连接，一台控制主机容纳不下时按项目分成多个控制核心实例；部门不作为拆分单位。

## 讨论中的分析

以下是架构师对用户 2026-09-24 第 4 项提问的回答，未经用户逐项确认，供部门内多角色与并行的设计参考。Cognition、MAST 与 Anthropic 多代理研究系统的来源见[语义系统与部门内多角色：参照调研](../research/semantic-system-and-department-roles.md)。

1. 分解成为带有不确定性的提案。过去只有数据分片这类结构上独立的工作可以自动切分，一般任务是否相互独立取决于含义，框架只能运行人声明的任务图。AI 能理解含义，所以能提出分解；依赖关系仍然隐藏在含义里，分解错误要到合并时才暴露。分解计划写明依赖，由控制层检查依赖是否成环、每项是否有验收条件；依赖事实尽量由代码图谱、构建系统、测试影响分析等工具提供，AI 的判断作为补充。
2. 分解的好坏在合并时检验。合并冲突、接口不匹配、集成导致的缺陷，都说明分解遗漏了依赖。这些证据关联到当初的分解计划，据此重新规划。任务图随执行证据更新。
3. 沿契约拆分，共同决定在并行之前确定。Cognition 指出并行代理各自做出的隐含决定会互相冲突；MAST 统计的失败中，协作失误占 32.15%。能安全并行的单位之间要有事先确定的契约（接口、数据格式、文件归属）；命名、错误处理这类共同决定在分派之前写入设计。PRD 与 DeliverySpec 已经是部门之间的契约，同样的做法向下应用到工程内部的并行任务。
4. 瓶颈转移到验证与集成。分解和生成变得便宜之后，限制产出的是验证与合并的速度。验证比开发更容易并行：针对同一个封存快照、按 PRD 条目、在不同平台上的检查大多相互独立且只读，查证也是这样。Anthropic 的多代理研究系统也观察到依赖多的编程任务不适合多代理。多台机器最先带来的收益是在不同平台上检查同一个交付快照。
5. 流程的每次转移多了第三种结果。带语义的判断便宜到可以设置在每一次交接上，同时带有置信度，所以每次转移都有通过、不通过、不确定三种结果；控制层为每个判定点预先规定三种结果的去向。
6. 确定性的边界。参照 Temporal 的工作流与活动的划分：模型调用、工具动作、决策模型判定都先记录，控制层的每个决定只依据已记录的事实，重放时不重新调用模型。
7. 同一个模式在每一层重复。部门之间、部门内部角色之间、工程内部并行任务之间，都是「分解 → 隔离执行 → 集成 → 独立验证」。[组织与持续运行研究](../research/organization-runtime-evolution.md)第 2.2 节的最小工作契约可以作为各层共用的工作单位描述，层级增加时不增加新的机制。

## 2026-09-29 用户确认的设计决定

用户对设计说明第 11 节的回答：

> 采纳推荐，目前先支持本机进行，容器就是走本机RPC?这样的话与远程机器通信一致了

- 每台机器一个机器流，与项目流一样跨版本保存（[ADR-0019](../adr/0019-project-stream-across-versions.md)）。
- 本机进程在进程内直接调用（[ADR-0018](../adr/0018-single-control-host-remote-execution.md)）。
- 核实可以引用迟到回执作为证据，只在还没有做出决定时。
- 升级要求执行代码摘要完全相同；用户在每台机器上运行升级命令，控制主机不远程安装。
- 机器离线、需要升级时进入待恢复，问题解决后自动继续，等待时间不计入运行时间。
- 执行位置上的代码可以访问外网。
- 项目没有设置执行位置时全部在本机进程运行。
- 树清单格式 `yudao-public-tree-v2` 增加可执行标记，旧清单继续可读（清单属于采纳成果，在项目流中）；单独一张工单。
- 远程 Windows 机器在真实测试之前不支持。
- 远程执行代理的真实验收与执行代理系统服务的验收在 Orange Pi AIpro 开发板上进行，开发板已经到位（2026-09-30 用户说明，开发板的情况见[执行环境服务设计说明](../design/execution-environment.md)第 1.1 节）；3.2C 的关闭条件：同一事项的工程构建在控制主机上完成，质检检查在这块开发板上完成。控制主机按用户当前的 Windows 11 电脑处理。
