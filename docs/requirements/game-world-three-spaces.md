# D41 三个空间：楼、机房、城

状态：需求已确认；依据：调研[游戏世界与代码世界的映射](../research/game-world-as-projection.md)，用户采纳它作为路线图「三个空间：楼、机房、城」的依据。总图位置：第一节「画面」方框与「画面 = P_view(事实)」；第四节「画面」的缝。路线位置：[路线图](../program-roadmap.md)「三个空间：楼、机房、城」，画面自己的阶段。设计：楼的部分见[画面与播放设计说明](../design/visualization.md)，机房与城未写。

## 确认的内容

1. **画面是投影，不是模拟。** 世界没有自己的状态，由一份事实（run 流、项目流、机器流、目录流）、语义图谱（项目流的投影）与行为记录（检查回执、试用记录、运维观察）用对照表加纯函数算出来；仓库只提供地址。三条性质：保持结构、可以回链、不说谎并且范围内不遗漏。三种检验：清单上每一项都有表行；重放事件得到同一个世界；每个物件能回到来源。装饰（待机活动、管道惯性）在自主行为的开关之下，不作断言。
2. **七种元件。** 世界里只有地点、物、连接、流、规则、操作、仪表七种东西；系统的每个概念归入一种，并写明来源、状态与变化、位置、操作、仪表与不画的部分（八列工作表）。归不进去的是别的概念的一部分，或者是装饰。
3. **三个空间。** 楼是组织（部门是房间、角色是小人、交接与询问是传送带上的包裹与信、大厅有决定板、动力是模型接线与上下文容器）；机房是机器（设备、执行代理、部署、故障；交付的软件是运行中的设备，带版本牌、健康灯、备份柜，故障冒烟）；城是产品（页面、接口、数据表是建筑，模块是街区，依赖是路，要求是蓝图，验收条件是检查站，证据让蓝图变成建筑，质检的试用会话与使用者是访客，故障是烟）。三个空间用一台摄像机切换。
4. **状态只来自记录。** 建筑的蓝图、在建、实体、冒烟、脚手架由要求、交付、证据、故障记录、待复核决定；访客只来自试用记录与交互日志；没有记录就没有访客。不给汇总的结论。
5. **规则是物件与物理。** 可改的规则（意图与 PRD、队列顺序、执行位置与机器授权、常设授权、工具登记、模型接线、决定的回答）是可操作的物件，每个物件对应一条现有命令；不可改的规则（只有写入口写事实、上下文隔离、三部门成环、工具许可、定义带版本、执行权只在控制核心、城只读）是推不动的物理。第二层自举以后，一部分刻在墙上的规则变成能推的方块。
6. **两种输入。** 文字照旧；指向是在城里点一栋建筑再说话，命令带着实体引用进入产品部门的焦点。这是唯一要改合同的地方：事项输入与指导的命令增加实体引用，随语义系统一起做。画出来的草图是材料，走附件。
7. **边界。** 城只读、只能指，没有低代码；改产品只能回到楼里提事项。代码留在工程房间的屏幕与资料页，门牌只写文件路径；函数内部不画。传送带画到部门之间与部门之内的流转为止，城里的路画实体之间的依赖。
8. **分层与渲染。** 来源层、查询层、投影层、世界层、交互层、渲染层六层（调研第 8.6 节）；换渲染不改世界与测试；三维的判据是映射里出现需要第三个轴的量，目前没有。
9. **几步与路线图的对应。** 画面是系统外面的一个使用方，按路线图第 4 节自己的阶段走，不跟系统的阶段绑在一起：搬出、楼跟着定义伸缩、机房、城、规则物件、子事项的小屋、铺传送带。每一步的前提是系统已经有了要画的记录（机房等运维记录，城等语义图谱与检查回执，指向式输入随语义系统改命令合同），画一个已经存在的来源，有自己的检验，单独有用。
