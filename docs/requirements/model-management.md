# D24 模型管理与部门模型选择

状态：有效。依据：[总图](../architecture.html)第四节「模型」的缝与第一节「模型与工具」方框；设计：[模型管理设计说明](../design/model-management.md)。路线位置：[总体路线图](../program-roadmap.md)第 3 节道 06 模型与判定点（能力表与按部门选模型）；阶段二结束时「模型与工具」的本机部分已建。

## 已确认

- 模型管理参照 OMP：统一管理全部模型与能力数据，再提供给上层调用；运行时按实际使用的模型计算。
- 模型管理为产品、工程、质检各给出一项部门默认。项目里的部门设置可以另选本项目该部门的模型，不修改部门默认。
- 运行中可以更换模型、推理档位与部门 Prompt。项目部门设置的修改从该部门的下一次模型请求开始生效；部门默认的修改对没有另选模型的项目同样生效，包括进行中的事项。
- 设置分全局与项目两层，每层再分部门与角色，每次模型请求按「项目角色设置、角色默认、项目部门设置、部门默认」的顺序取第一个写入的项（[设计说明](../design/model-management.md)第 5 节）；调用目标每次请求解析（设计说明第 5.3、6 节）；不保留事项级设置，删除事项内的 Prompt 编辑。
- 三部门的历史各自保存作者的工作过程；部门之间传递主机接纳的结构化结果，对话不跨部门；共享的内容按可见范围确定。
- 窗口未知的模型直接拒绝，由 Provider 模块负责。
- 目前只使用 1M 窗口的模型，暂不处理切换到小窗口模型。
- 压缩参照 OMP 与 opencode：阈值采用 OMP 公式，预留量取窗口的 15% 与 16384 中较大的一个（暂定默认值）；整理请求使用该模型声明的最低推理档位（暂定默认值）；数值与理由见规则登记。
- 推理档位参照 OMP：每个模型在目录中声明支持的档位，请求时限制在支持范围内，各协议映射到自己的参数。
- 准入作废后，部门默认与项目部门设置中的引用保留；该部门下一次模型请求不发送，事项进入待恢复，写明部门、角色、模型与原因，用户修复以后从这次请求继续；角色的模型失败时不自动改用其他模型，判定点的升级使用判定点声明的第二个判定者，角色的模型不变。
- 预置表是仓库内的数据文件，每个服务方案带来源与默认协议，整张表带版本号，随新版本发布生效；目前只有 OpenCode Go，另有自定义。
- 工具能力检查并入模型测试：最小问答之外再做一次工具往返（设计说明第 4.3 节）。三部门的每一步都靠工具调用，「是否接受要求调用工具」在主路径上没有手工声明的地方，只能由测试测出。
- 模型能力的基础清单参照 OpenCode，使用 models.dev 的快照作为模型能力表，随 Yudao 版本更新，运行时不从远端刷新；新建模型访问定义时据此预填窗口、输出上限与输入方式，能力表中没有的模型由用户自己声明，默认不支持图像。模型访问定义增加输入方式，调用目标带上输入方式，运行层据此提供工具；质检的建议能力按它提醒（设计说明第 4.1、4.3、5.6 节）。
- 连接地址保存请求基址，请求路径由协议的适配器拼接，与 OMP 相同；Web 新建事项只提交事项原文，上下文窗口取调用目标的模型窗口，运行边界使用系统默认值。
- 协议、模型列表地址与加入模型的规则（设计说明第 4.1 至 4.4、9.1 节）：
  1. 调用协议是模型访问定义的字段，取值为 Responses、Chat Completions、Anthropic Messages。连接是一个服务方案下的名称、地址、凭据引用、超时与模型列表地址，不声明协议。新建访问定义时预填协议：内置服务方案取模型能力表中这个模型的协议（来自 models.dev 每个模型的 `provider.npm`，没有单独声明时取服务方案的默认协议，OpenCode Go 为 Chat Completions）；自定义服务预填 Chat Completions；用户可以修改。修改一个访问定义的协议只使这个定义回到候选；修改连接的地址或凭据引用使该连接下全部定义回到候选。
  2. 自定义服务的模型列表地址默认是连接地址加 `/models`，显示在新建与编辑连接的表单上，可以修改；内置服务方案用方案的模型列表地址。获取失败时写明请求的地址与返回的状态码，没有收到响应时写明连接失败的原因；只接受 `x-api-key` 的自定义服务获取列表会失败，用户可以手动添加访问定义。
  3. 在模型列表中勾选要用的模型即选用它。窗口与输出上限先取上游模型列表返回的值，没有时取模型能力表，界面标明来源，以后可以修改；两处都没有时由用户填写，填好以后才能继续。选用以后自动对这个访问定义做模型测试：通过即写入准入，定义出现在部门默认与项目部门设置的选项中；未通过时显示原因，定义留在候选，用户修改以后可以再测试。准入只由真实的模型测试写入。
- 填写服务地址与 API Key，剩下是选择，选完直接能用（设计说明第 4.2、4.3、9.1 节）：
  1. 连接只要地址与 Key；ID、名称与凭据引用由系统生成，同一个地址只有一份连接。
  2. Key 的存法参照 OpenCode：随连接保存，始终保存在数据目录里，系统支持文件权限时只有所有者可读写，明文保存；没有「只在本进程有效」的选择；环境变量是另一种来源。
  3. 勾选即选用，系统依次补全参数、做模型测试，通过即启用；正常的路径上没有单独的「加入」与「模型测试」操作，测试失败时才需要点「重新验证」。
  4. 默认只列可自动配置的候选（窗口与输出上限已知），可以搜索与筛选；容量未知的模型由用户填写窗口与输出上限后继续。
  5. 第一个启用的模型自动成为还没有部门默认的部门的部门默认，已有的选择不被覆盖。
