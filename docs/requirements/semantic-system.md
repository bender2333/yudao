## 重点 TODO：上下文组装（专题讨论）

用户标记为核心问题，单独安排专题讨论：怎样获取知识、确认知识正确、把正确的上下文交给模型，使模型高效工作。讨论前不在设计中作出决定。已知属于这个专题的问题：

- 每次请求放入哪些内容、按什么顺序、放多少；
- 知识怎样取得（包括原设计草案第 7.4 节列为 TODO 的检索方式）；
- 怎样确认放入的内容正确、当前有效；
- 不同角色（中心角色、经理、工具角色、审查者）各自得到什么上下文。

## 已确认

- 语义系统是确定要做的模块。
- 语义系统参与上下文的管理与整理。
- 每个部门有各自的知识图谱、语义压缩与事实检索，替代长期记忆。
- 部门历史独立，用于上下文隔离；部门之间只传递主机接纳的结构化结果，对话不跨部门。
- 原始历史不遗忘、不删除；语义分解、洞见与数据流在完整历史保存（D08）与自动压缩（D10）的基础上优化部门上下文管理。
- 2026-09-24 用户决定：语义系统作为单独的项讨论，检索方式先列为 TODO。
- 2026-09-24 用户决定：语义系统放在 Stage 4：部门内协作、上下文与界面。
- 语义系统是关键环节，承担两项职责：一是整理事实与事件，随时进行语义压缩与分发；二是整理知识图谱与语义工程，供系统演化（Stage 7）使用。
- Stage 4 的记忆指语义系统承担的项目记忆；跨任务经验仍在持续改进工作线。
- 2026-09-25 用户声明：语义系统不是 RAG，也不是长期记忆；它参照 Semantica，是带有知识、事实、证据等内容的知识图谱，给 Agent 做上下文用。
- 2026-09-25 用户明确：Agent 最重要的是上下文管理。语义系统分两部分：一是整理，长任务运行很久以后，需要轨迹与结构化的图谱，只靠记忆会出现上下文不够、内容混乱的问题；二是上下文组装，列为重点 TODO，专题讨论。当前先讨论第一部分。
