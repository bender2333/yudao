# D20 部门定向追加指导

## 用户原话与来源

在原型任务 `01a075bd-73fc-7152-97a2-353292857d27` 中，用户要求进入部门查看 Context、Provider、Prompt，并手动输入对话调整部门消息；随后明确：

> 是给部门**追加对话和指导** 。部门内部部分，可以考虑全新的页面

本轮用户要求按原型规划 WebUI 和功能，纳入这项真实交互。

## 已确认

- 总览输入面向整体任务，部门输入有明确接收部门。
- 指导采用追加方式，保留原文，不编辑、删除或重写已有部门消息。
- 部门工作区区分用户、本部门、其他部门的工作消息，显示指导是否已被处理。

## 必须保持的边界

部门指导不是修改 Prompt，也不是模型返回的回复；“已接收”“已进入一次模型输入”“部门已回应或处理”必须有各自事实。发送成功不能由前端计时器模拟处理，切换部门不能改变接收对象。

复用原生三部门循环及正常权限检查。工程指导不能直接改产品合同，质检指导不能绕过独立 QA；涉及目标、验收或需求取舍时，仍需产品形成有效要求。部门之间通过已有协作传递必要材料，不共享完整私有历史。

原文、部门、任务、接收顺序和实际采用的请求需要可追溯。定向内容不能因为复用总览输入接口而直接广播给所有部门，也不能因本地刷新丢失已接收记录。

## W0 需要完成的处理约定

原型只模拟了追加与等待，没有确定内核处理时机。以下在实现前形成明确约定及反例，不能把建议冒称用户已确认：

| 问题 | 设计任务 |
| --- | --- |
| 活跃部门收到指导 | 明确当前工具、模型流和下一请求的处理边界；沿用安全接纳检查，防止旧结果覆盖新指导 |
| 非活跃部门收到指导 | 明确等待正常激活或回到该部门工作的条件；保持唯一执行循环，不开独立聊天运行器 |
| 接近最终 QA 或任务已结束 | 明确未处理指导如何影响放行，结束后拒收并保留草稿；不能悄悄丢弃待处理指导 |
| 原文保存范围 | 总览输入继续按 D03 保存 intend；部门指导采用带范围的原文记录，明确是否及怎样进入 intend，避免其自动扩散为全局要求 |
| 指导要求改变产品范围 | 明确交产品处理的回执和后续影响，维护原文与产品解释的区别 |
| 同时出现全局新输入、指导、取消 | 明确处理顺序及失效关系；取消仍立即生效，已完成的真实结果保留 |

## 验收与状态

状态：用户场景已确认，W0 的[处理设计](../design/department-guidance.md)已形成架构选择与反例，尚未实现。当前只有面向整体任务的持续输入；前端模拟追加不能计为完成。

验收至少覆盖三个部门的定向发送、活跃与非活跃接收、工具及模型在途、返工与咨询、终态边界、刷新重连、原文保真和处理来源审计。模型的实际输入必须含目标指导，其他部门不能收到未授权私有内容。
