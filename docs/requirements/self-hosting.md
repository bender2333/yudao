状态：有效。依据：[总图](../architecture.html)第五节自举与验收（两层自举）；设计：[可信内核设计说明](../design/trusted-kernel.md)、[网页界面的提供与发布设计说明](../design/web-interface-and-release.md)第 6.5 节、[规则登记与参数设计说明](../design/rules-and-parameters.md)、[循环与收敛设计说明](../design/loops-and-convergence.md)、[部门内多角色设计说明](../design/department-roles.md)、[验证的独立性设计说明](../design/independent-verification.md)；调研：[圈复杂度与变异测试调研](../research/complexity-and-mutation-testing.md)；相关记录：[D26](department-roles.md)、[D27](operations-department.md)、[D16](git-change-management.md)、[D31](outsourced-agent-roles.md)、[D33](existing-project-onboarding.md)、[ADR-0019](../adr/0019-project-stream-across-versions.md)。路线位置：[总体路线图](../program-roadmap.md)第 2 节。第一层的试点是阶段二薄片 ⑤「Yudao 做自己的工单」，在薄片 ①「真实项目接着做」与薄片 ④「改一处、看得见、能撤回」之后、五项前置条件完成以后开始；第一层成为常态在阶段三；第二层是阶段五；圈复杂度与变异测试的研发工具在阶段三。

## 已确认

1. 自举（用 Yudao 开发 Yudao）是核心目标。
2. 同一项目同一时刻只有一个角色编写代码，是暂定默认值，放开条件见 D38。将来支持多个写入者：同一执行主机上用 worktree 并发，不同执行主机之间通过分支进行。
3. 质量检查作为部门的工序：工程部门对单元测试、圈复杂度与变异测试作自我保证，质检部门做大的验证。测试、任务流转这类可以固定下来、自动化的事做成工序（节点），后续流程只看它的输出，不再看它的内部。
4. 圈复杂度与变异测试做成研发工具，在 Windows 与 Linux 上直接给出结果与诊断。目标形式是可执行工具与 skill 加 MCP；首要使用者是自主推进模式中的执行者 omp；以后由 Yudao 集成。
5. 当前阶段不建这个工具，也不改动开发流程的规则。阶段二结束之前，用户与 Claude 手动进行一次圈复杂度与变异测试，方法见[调研记录](../research/complexity-and-mutation-testing.md)第 2 节。
6. 边界：已发布的实例把 Yudao 仓库当作普通项目，开发下一个版本；运行中的实例不修改自己的内核（[可信内核设计说明](../design/trusted-kernel.md)）；需求来自用户；升级由用户决定；第二层（修改自己的组织与规则）建立在第一层之上，是阶段五。
7. 第一层的试点在薄片 ① 关闭并且五项前置条件完成以后开始（见「第一层试点的配对验收约定」）：已发布的实例使用单独的数据目录与端口；接入 Yudao 仓库；采纳写回；项目级的检查时限；外部执行者的基线数字。试点期间成果以合并请求交给现有的审查流程。
8. 质检依据回执的比例由验证密度参数决定，阶段一、二保持现值 1.0，调节规则在阶段四。
9. 跨平台：圈复杂度与变异测试做成稳定的跨平台工具库，现在与以后都要能在 Windows 上运行。阶段二结束之前的手动检查在控制主机的 Windows 上进行，工具与步骤见[调研记录](../research/complexity-and-mutation-testing.md)第 2 节；研发工具在阶段三建立，排在成果由 Yudao 直接采纳之前：那以后审查流程不再检查 Yudao 的成果，工程部门用它检查自己的交付。

## 第一层试点的配对验收约定

试点就是阶段二的薄片 ⑤「Yudao 做自己的工单」。

**前置条件**：薄片 ① 的用户试用通过，并且下面五项都有证据，试点才开始。

| 序号 | 条件 | 来自 |
| --- | --- | --- |
| 1 | 运行的实例是一次发布，从安装的发布包运行，使用单独的数据目录与端口，与被开发的代码分开 | 走查的做法（[网页界面的提供与发布设计说明](../design/web-interface-and-release.md)第 6.5 节） |
| 2 | Yudao 仓库按 `project.onboard` 接入，初始 PRD 经用户确认 | 接入已有项目 |
| 3 | 采纳写回保留目标分支的独立提交，冲突时停止，核验最终写回树以后生成分支与合并请求；建档材料按现有行为与要求分类 | 采纳写回（[ADR-0034](../adr/0034-adopted-change-writeback-three-tree-merge.md)） |
| 4 | 检查时限与建档的单轮上限按项目设置；检查使用项目自己的测试命令 | 项目级参数 |
| 5 | 外部执行者流程的基线数字已经导出 | 外部执行者的基线数字 |

**试点期间的做法**：Yudao 的成果以合并请求交给现有的审查流程与集成层，由仓库所有者合并。「被评价者改不了评价标准」由这个流程保证，保证外部执行者的方式相同，所以试点不按自我修改的级别限制工单。Yudao 一侧失败的工单，用对照一侧的实现补上，失败的原因记入事件与工单。外部执行者现在是 solo 执行者。

**试点工单**：六个，在薄片 ⑤ 开始时由总架构师从当时打开的工单里选定，写进准备工单。选定条件：界面 3 个、控制核心以外的后端 3 个；互相不依赖、改的文件不重叠；每张有可判定的验收标准；不改内核路径；已经写好「依据」「只改」与「环」。循环实例、收敛状态、事实来源与检验覆盖这几块画面由外部执行者在薄片 ④ 做完，不作为试点工单，因为薄片 ④ 的试用要看得见这些画面。Yudao 仓库是一个项目，同一项目的事项排队，一次进行一个。

**配对规则**：每张工单由外部执行者与已发布的 Yudao 实例各实现一次。每一对在开始前固定共同的源码起点、任务文本、模型组合、审查标准与评价材料版本；先后次序轮换；对照一侧的结果不合并；原始的失败与补跑全部保留，未知的用量和费用不填零。Yudao 的结果经合并请求进入现有的审查与集成流程。准备工单保存五项前置条件的证据、六张试点工单的清单与配对约定，关闭以后架构师核对证据，再开放配对工单；试点的父工单保持打开到六个配对结果都已核对。

**验收**：

- 任务：6 个真实工单，界面 3 个、控制核心以外的后端 3 个。
- 模型：两边的模型组合在开始前固定并记录，报告按组合分列请求数与用量。
- 评判：与两边执行者都不同的模型，在不知道来源的情况下审查两份结果；合并以后由集成层核对。
- 指标：到达审查通过所需的轮数；集成层的结果；架构师核对验收标准时发现的问题数；用户试用时提出的缺陷数；耗时、用量与费用；需要用户介入的次数。
- 通过条件：6 个工单中至少 5 个由 Yudao 独立到达「审查通过并通过集成层」；各项质量指标按配对比较不劣于外部执行者；外部评测场景同期没有退化。

**第一层成为常态**（阶段三与阶段四）：成果由 Yudao 直接采纳之前具备四项条件：路径守卫、接口的访问令牌、控制主机以外的执行机器、由已安装的实例提供的发布检查（[可信内核设计说明](../design/trusted-kernel.md)）。Yudao 自己的工单默认交给 Yudao 实例执行，外部执行者留作对照与后备；阶段三的完成依据要求连续 4 周每周有被采纳的自举事项（[D27](operations-department.md)「长时间运行」）。

## 第二层的前置条件与完成条件

第二层是阶段五：Yudao 根据运行证据修改自己的组织与规则。改的对象是定义与角色材料，内核、评价材料与基础规则不在其中。

**前置条件**：

1. 第一层作为常态运行满一个阶段（[D27](operations-department.md)「长时间运行」里阶段三的完成依据）。
2. 流转由定义驱动，控制代码中没有部门名称。
3. 由用户发起的参数对照完成 3 次以上，其中至少一次撤回；对照的记录与噪声范围可用（[规则登记与参数设计说明](../design/rules-and-parameters.md)）。
4. 内核守卫经过演练；留出场景可用。
5. 观察者的订阅与提案接口、判定点的合同已经运行（阶段四）。

**分步**：按提出者分两步。系统先提出界内参数的候选，由对照与用户决定采用；这一步稳定以后，系统提出结构性定义的候选，经结构校验、隔离对照与用户批准后限定采用，在界面上修改轮转方式的定义（`definition.propose`）也在这一步加入。运行提供事实；演化模块作为观察者提出组织、协议或日常规则的候选，独立评价决定是否在限定范围采用。候选不能自行批准，用户目标与授权边界不由被评系统修改。演化使用元观察的审查与观察记录，以及语义系统整理的图谱；用于最终判断的隐藏评价材料不进入被评系统可以读取的图谱。跨项目复用的教训与知识也走这条路：重复出现的作为候选，经过独立验证、限定采用，冲突或出现反例时停用。

**完成条件**：

1. 一类组织或协议的变化和一类日常规则的变化贯通证据、候选、隔离比较、独立评价、采用、观察与撤销。
2. 在未见任务上比较原组织、研发者的静态改进与系统的候选，收益算上额外的协调与维护成本。
3. 失败的候选不生效；采用以后出现反例时，能停止新增使用、处理在途工作并保留恢复依据。
4. 规则变化能追踪对知识、教训、技能与事项的影响，不默认旧的知识与教训继续适用。

学习要演示「重复问题 → 候选 → 独立验证 → 未见任务采用 → 反例 → 停用」，同时保留失败、无效与缺失的结果；训练与校准材料不混入未见的评价。开放性研究是独立的研究方向；模型权重的更新是可选项，不是阶段五的必做项。
