## 讨论中的分析

以下是架构师在讨论中的分析，未经用户逐项确认。

**只看节点输出的条件。** 下游只读取一个固定步骤的输出、不再看它的内部，需要三个条件同时成立：输入是声明的（代码树、检查定义的版本、运行环境中程序的版本，环境也是输入）；由不参与判断的一方执行并记录；输出格式固定。现在的开发流程三条都不满足：执行者的全局环境与锁文件不一致（#72 的登记）；测试计数由执行者自己写进交付评论，审查者只能再运行一遍；流程状态是由 agent 自己修改的 GitHub 标签，批次的起点写在评论的文字里。

**现在的开发流程就是用文字规则运行的三部门循环。** 执行者、审查者与架构师自主推进模式三份规则约有 34 个步骤，需要判断的只有 7 个：实现代码与测试、逐条编写验收核对、编写架构问题的内容、审查时核对验收标准与违规、决定审查是否通过并写明问题、核对 PR 是否符合工单、把审查意见改写成下一轮任务。其余是固定步骤，在 Yudao 中分别对应检查、提案校验（U）、项目设置与流转。

| 现在 | 在 Yudao 中 |
| --- | --- |
| 架构师与用户讨论，编写设计与工单 | 产品部门与用户：PRD、计划、决定请求 |
| 架构师在自主推进模式中的调度 | 控制核心 |
| 工作包父工单、子工单 | 事项、计划条目 |
| omp 执行者 | 工程部门的开发者（外包角色，经 ACP 接入） |
| OpenCode 审查者 | 质检部门，由 Yudao 自有的角色担任（放行不能外包，系统架构原理第 8 节） |
| 流程标签 | 阶段 |
| 架构问题登记 | 咨询请求 |
| 日记 | 事件日志与部门的私有历史 |

**自举的做法。** 参照编译器的做法：rustc 用按 SHA256 固定的上一个版本（stage0）编译当前源码。对应到 Yudao：一个固定版本的 Yudao 实例承载「Yudao」这个项目，部门修改的是项目仓库里下一个版本的代码，实例本身不变；把实例升级到新采纳的版本是一次部署，由用户决定，出现问题时回滚到上一个版本；ADR-0019 让项目流跨版本保存，升级实例不会丢掉这个项目。这与路线图第 5.4 节「一个 Yudao 部署中的运维部门负责另一个部署」是同一种结构，用在开发上。

**多个写入者以后的采纳。** 采纳一步改为合并队列的做法：对合并后的结果运行质检的大验证，通过才采纳；基线在这期间发生变化，就在新基线上重新合并、重新验证。GitHub 合并队列、bors、Zuul、GitLab merge train 都是先检查再合入。现在的 `adoption_held`（基线发生变化就不采纳）是只有一个写入者时的特例；先合并、再批量运行、失败后二分定位的做法不再需要。

**检查定义与交出检查。** 工序对应 CONTEXT.md 已有的「交出检查」（D26 设计说明第 12.6 节）。需要补充两点：必做的检查由项目的检查定义规定（命令、运行环境、运行时机、输出格式与发现项、对流转的作用、谁可以修改），工程可以另外增加；交出检查不依赖部门内多角色，在现在的单角色部门里就是提交交付与提交质检结论时的提案校验。检查的策略（阈值、排除规则）记录在定义中，不从被检查的代码中读取。质检以工程工序的主机回执为依据的比例由验证密度参数决定：阶段一、二保持现值 1.0（质检亲自运行检查），在同一树摘要上连续一致以后降低，出现不一致时回到全量，调节规则在阶段四；质检另按 PRD 做自己的验收检查；质检的独立性来自由谁决定核验什么。它与 3.8 设计中记入项目流的基线检查回执、Stage 6 需求中的「质检的检查定义」是同一个概念。

## 第一层试点的配对验收约定

2026-10-28 从 2026-10-25 的旧路线图搬入，词汇改到现在的路线：试点就是阶段二的薄片 ⑤「Yudao 做自己的工单」。

**前置条件**：薄片 ① 的用户试用通过，并且下面五项都有证据，试点才开始。

| 序号 | 条件 | 来自 |
| --- | --- | --- |
| 1 | 运行的实例是一次发布，从安装的发布包运行，使用单独的数据目录与端口，与被开发的代码分开 | 走查的做法（[网页界面的提供与发布设计说明](../design/web-interface-and-release.md)第 6.5 节） |
| 2 | Yudao 仓库按 `project.onboard` 接入，初始 PRD 经用户确认 | 接入已有项目 |
| 3 | 采纳写回保留目标分支的独立提交，冲突时停止，核验最终写回树以后生成分支与合并请求；建档材料按现有行为与要求分类 | 采纳写回（[ADR-0034](../adr/0034-adopted-change-writeback-three-tree-merge.md)，#346、#347） |
| 4 | 检查时限与建档的单轮上限按项目设置；检查使用项目自己的测试命令 | 项目级参数（#351） |
| 5 | 外部执行者流程的基线数字已经导出 | #345、#413 |

**试点期间的做法**：Yudao 的成果以合并请求交给现有的审查流程与集成层，由仓库所有者合并。「被评价者改不了评价标准」由这个流程保证，保证外部执行者的方式相同，所以试点不按自我修改的级别限制工单。Yudao 一侧失败的工单，用对照一侧的实现补上，失败的原因记入事件与工单。外部执行者现在是 solo 执行者。

**试点工单**：六个，在薄片 ⑤ 开始时由总架构师从当时打开的工单里选定，写进准备工单 #416。选定条件：界面 3 个、控制核心以外的后端 3 个；互相不依赖、改的文件不重叠；每张有可判定的验收标准；不改内核路径；已经写好「依据」「只改」与「环」。循环实例、收敛状态、事实来源与检验覆盖这几块画面（#395 下的六张）由外部执行者在薄片 ④ 做完，不作为试点工单，因为薄片 ④ 的试用要看得见这些画面（用户 2026-10-29 确认）。Yudao 仓库是一个项目，同一项目的事项排队，一次进行一个。

**配对规则**：每张工单由外部执行者与已发布的 Yudao 实例各实现一次。每一对在开始前固定共同的源码起点、任务文本、模型组合、审查标准与评价材料版本；先后次序轮换；对照一侧的结果不合并；原始的失败与补跑全部保留，未知的用量和费用不填零。Yudao 的结果经合并请求进入现有的审查与集成流程。准备工单 #416 保存五项前置条件的证据、六张试点工单的清单与配对约定，关闭以后架构师核对证据，再开放配对工单；#982 保持打开到六个配对结果都已核对。

**验收**：

- 任务：6 个真实工单，界面 3 个、控制核心以外的后端 3 个。
- 模型：两边的模型组合在开始前固定并记录，报告按组合分列请求数与用量。
- 评判：与两边执行者都不同的模型，在不知道来源的情况下审查两份结果；合并以后由集成层核对。
- 指标：到达审查通过所需的轮数；集成层的结果；架构师核对验收标准时发现的问题数；用户试用时提出的缺陷数；耗时、用量与费用；需要用户介入的次数。
- 通过条件：6 个工单中至少 5 个由 Yudao 独立到达「审查通过并通过集成层」；各项质量指标按配对比较不劣于外部执行者；外部评测场景同期没有退化。

**第一层成为常态**（阶段三与阶段四）：成果由 Yudao 直接采纳之前具备四项条件：路径守卫、接口的访问令牌、控制主机以外的执行机器、由已安装的实例提供的发布检查（[可信内核设计说明](../design/trusted-kernel.md)）。
