## 讨论中的分析

以下是架构师在讨论中的分析，未经用户逐项确认。

**只看节点输出的条件。** 下游只读取一个固定步骤的输出、不再看它的内部，需要三个条件同时成立：输入是声明的（代码树、检查定义的版本、运行环境中程序的版本，环境也是输入）；由不参与判断的一方执行并记录；输出格式固定。现在的开发流程三条都不满足：执行者的全局环境与锁文件不一致（#72 的登记）；测试计数由执行者自己写进交付评论，审查者只能再运行一遍；流程状态是由 agent 自己修改的 GitHub 标签，批次的起点写在评论的文字里。

**现在的开发流程就是用文字规则运行的三部门循环。** 执行者、审查者与架构师自主推进模式三份规则约有 34 个步骤，需要判断的只有 7 个：实现代码与测试、逐条编写验收核对、编写架构问题的内容、审查时核对验收标准与违规、决定审查是否通过并写明问题、核对 PR 是否符合工单、把审查意见改写成下一轮任务。其余是固定步骤，在 Yudao 中分别对应检查、提案校验（U）、项目设置与流转。

| 现在 | 在 Yudao 中 |
| --- | --- |
| 架构师与用户讨论，编写设计与工单 | 产品部门与用户：PRD、计划、决定请求 |
| 架构师在自主推进模式中的调度 | 控制核心 |
| 工作包父工单、子工单 | 事项、计划条目 |
| omp 执行者 | 工程部门的开发者（外包角色，经 ACP 接入） |
| OpenCode 审查者 | 质检部门，由 Yudao 自有的角色担任（放行不能外包，系统架构原理第 8 节） |
| 流程标签 | 阶段 |
| 架构问题登记 | 咨询请求 |
| 日记 | 事件日志与部门的私有历史 |

**自举的做法。** 参照编译器的做法：rustc 用按 SHA256 固定的上一个版本（stage0）编译当前源码。对应到 Yudao：一个固定版本的 Yudao 实例承载「Yudao」这个项目，部门修改的是项目仓库里下一个版本的代码，实例本身不变；把实例升级到新采纳的版本是一次部署，由用户决定，出现问题时回滚到上一个版本；ADR-0019 让项目流跨版本保存，升级实例不会丢掉这个项目。这与路线图第 5.4 节「一个 Yudao 部署中的运维部门负责另一个部署」是同一种结构，用在开发上。

**多个写入者以后的采纳。** 采纳一步改为合并队列的做法：对合并后的结果运行质检的大验证，通过才采纳；基线在这期间发生变化，就在新基线上重新合并、重新验证。GitHub 合并队列、bors、Zuul、GitLab merge train 都是先检查再合入。现在的 `adoption_held`（基线发生变化就不采纳）是只有一个写入者时的特例；先合并、再批量运行、失败后二分定位的做法不再需要。

**检查定义与交出检查。** 工序对应 CONTEXT.md 已有的「交出检查」（D26 设计说明第 12.6 节）。需要补充两点：必做的检查由项目的检查定义规定（命令、运行环境、运行时机、输出格式与发现项、对流转的作用、谁可以修改），工程可以另外增加；交出检查不依赖部门内多角色，在现在的单角色部门里就是提交交付与提交质检结论时的提案校验。检查的策略（阈值、排除规则）记录在定义中，不从被检查的代码中读取。质检以工程工序的主机回执为依据的比例由验证密度参数决定：Stage 3 保持现值 1.0（质检亲自运行检查），在同一树摘要上连续一致以后降低，出现不一致时回到全量，调节规则在 Stage 5；质检另按 PRD 做自己的验收检查；质检的独立性来自由谁决定核验什么。它与 3.8 设计中记入项目流的基线检查回执、Stage 6 需求中的「质检的检查定义」是同一个概念。
