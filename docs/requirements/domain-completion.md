# D12 职能的专业补全

状态：有效。依据：[总图](../architecture.html)第一节「产品」「工程」「质检」方框；设计：[产品 · 工程 · 质检的循环结构](../design/department-loop.md)。路线位置：[总体路线图](../program-roadmap.md)「职能之间：转实」，道 01 职能与核验。

## 有效规则

- 三个职能依据行业知识、项目约定和成熟组件补齐常规缺口，仅对影响目标、承诺或重要成本且无法推断的取舍提问。
- 产品负责需求与重要取舍，工程负责技术方案和自检，质检依据有效要求及适用共同约定独立检查。
- 默认依据与用户的原始输入分开；已有知识的采用不等待经验学习基线。QA 新提出的业务取舍先补定义，不追认为已约定缺陷。纯局部实现细节不强制跨职能询问。
- 共同的专业补全规则进入每次正常请求；产品的约束和工程的计划记录采用的专业默认与依据。
- 重要且不能推断的取舍保留咨询路径（[D07](expert-ask-react.md)），原文不被默认决定覆盖。
- 三个职能与直做角色都可向用户发起多题前沿决定请求（单批提出彼此独立的高影响取舍，附选项、唯一推荐与推荐理由，用户可选填补充说明）；角色指引优先让产品（直做形态中为接收入口输入的角色）在探索工作区后尽早提问，也允许根据首轮回答展开下一层依赖问题。
- 原始用户意图与起始材料对各职能与角色保持只读完整可见；已回答的用户决定汇入共享上下文供所有职能与角色参照，同时用户意图原文不被默认决定或用户追问回答覆盖。
- 不建设独立知识图谱，不新增职能。

## 验收

用实际模型跑完整任务，验证三个职能采用专业默认的效果、探索后向用户发起多题追问并依据回答展开下层依赖问题的效果，以及职能之间依据原始意图自由相互审查的效果。
