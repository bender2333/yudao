# D32 与单个 agent 的对照实验

确认时间：2026-09-28。状态：需求已确认，任务集未设计，未实施。路线位置：[总体路线图](../program-roadmap.md) Stage 3 的 3.9 组合验收第一次执行，之后每个阶段结束时重复。

## 用户原话

2026-09-28 架构师问用户判断 Yudao「做成了」的标准，用户回答：

> 标准就是你说的两个，一是能独立高质量交付，二是长时间自我运行并自我修复

第一条标准对应架构师举的例子：交给 Yudao 一个真实项目的需求，它能独立交付，质量高于直接使用单个 agent。架构师提出对照实验要控制模型这个变量，用户回答：

> 关于对比实验，需要用opencode来对比，暂时先用模型能力比较一般的model来测试，比如deepseek v4.1 flash这种

> opencode go， 任务由你来设计，我来review。 但是，这个对比实验，我希望能放到稍微靠后，等Yudao作为稍微完善的harness以后

## 已确认

- 对照对象是单独运行的 OpenCode。Yudao（产品、工程、质检三部门）与 OpenCode 都通过 OpenCode Go 调用同一个模型，模型选能力一般的，例如 DeepSeek V4.1 Flash。
- 任务集由架构师设计，用户审阅。每个任务有 Yudao 与 OpenCode 都看不到的验收检查，由独立检查判断交付质量。
- 每个任务在两边各运行 3 次。报告交付质量、模型请求数、用量与耗时，失败与缺失的结果如实列出。
- 实验在 Yudao 作为 harness 比较完善以后进行：3.9 组合验收时第一次执行，那时恢复、执行环境服务、网络与 MCP 都已完成。之后每个阶段结束时重复，新增的能力不能让结果变差。
- 实验结果决定 Stage 5 中语义系统、部门内多角色等工作的先后。部门内多角色的对照（[D26](department-roles.md)）使用同一个任务集。

## 设计中待确定的内容

- 任务集：任务的数量、种类与规模，是否包含在树莓派上运行的软件，每个任务的需求文本与隐藏的验收检查。
- 两边相同的条件：同一份需求文本、同样的运行时间上限、同一台机器与执行环境；OpenCode 的版本与使用的 agent 设置。
- 质量的判断方式与「高于」的含义：验收检查通过的比例，以及三次运行之间的差异怎样计算。
