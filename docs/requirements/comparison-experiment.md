# D32 与单个 agent 的对照实验

状态：有效。依据：[总图](../architecture.html)第四节系统之外「评价」的缝与第五节验收表的「真实场景」一层；设计：[评测场景：版本回归与 OpenCode 对照](../design/evaluation-scenarios.md)。路线位置：[总体路线图](../program-roadmap.md)阶段二薄片 ②「比单个 agent 好多少」。

## 已确认

- 对照对象是单独运行的 OpenCode。Yudao（产品、工程、质检三部门）与 OpenCode 使用同一个模型；模型由用户提供，具有视觉能力，暂时用能力比较一般的模型来测试。
- 版本回归与 OpenCode 对照使用同一组三个场景与同一个评分器：网页应用（WebGen-Bench 000080 待办清单）、在已有代码上加功能（FeatBench openai-agents-python-842）、从较长的 PRD 新建项目（PRDBench 44 北京地铁票价）。
- Yudao 按平时的入口运行，交付物交给评分器；不接入 Harbor 等外部评测框架。
- 每个场景有两边都看不到的隐藏检查。评分报告完成度（按需求条目统计）、正确性与失败分类（没有做、做了但结果不对）；场景 2 另报原有功能的失败条数；场景 1 另报丰富程度（10 项清单，多模态裁判打分）。
- 版本比较使用噪声范围，噪声范围来自同一版本的重复运行；每个指标报平均、最小与最大；结论是改进、无差别、退化三者之一，完成度的下降超出噪声范围才记为退化。
- Yudao 另报过程检查点（放行、质检检查绑定最后的交付、计划先于写入、重放一致、质检误放行）与循环、返工、询问次数。
- 每个场景两边各运行 3 次（暂定默认值，属于评价标准，只由用户修改，见规则登记），报告模型请求数、用量、费用与耗时，失败与缺失的结果如实列出；费用由用户填写的模型单价算出，没有填写时保持未知。
- OpenCode 的基础分在 Yudao 一侧之前运行；这三个场景作为回归场景，后续对 Yudao 的优化以它们的结果为依据；另设不参与调整的留出场景，从三个来源各取 2 个，第一次运行在阶段三结束时。
- 评测是最重要的工作内容，但不需要先做好。评测是阶段二的薄片 ②，与界面和后端工单并行进行，不要求排在其他工作之前；阶段二里评测只做一个场景：在已有代码上加功能（场景 2），Yudao 与 OpenCode 各运行 3 次，出一份对照报告，阶段二结束之前必须完成，没有完成时阶段二不能关闭。场景 1 与场景 3 的运行与对照、共享对隔离的对照不在阶段二里，待排期。
- 质检部门具备浏览器工具，从 PRD 生成测试并操作交付的界面；浏览器由 [D34](browser-and-computer-use.md) 提供，场景 1 的 Yudao 一侧依赖它；computer use 还没有排入阶段。评测使用的模型具有视觉能力，质检使用这个模型时浏览器的截图可以放入请求。
- 实验结果决定阶段四中语义系统、部门内多角色等工作的先后。部门内多角色的对照（[D26](department-roles.md)）使用同一组场景。新增一组对照使用被测模型，让部门共享可见范围并同时采用先判断后看解释，其余条件相同；隔离组复用本实验的运行；结论对可见范围与先判断后看解释两项一起适用。
- 评测使用的模型：被测模型为 `qhub/Qwen3.8-Flash`，与真实模型测试共用，模型名放在用户环境变量 `YUDAO_EVAL_MODEL` 中；界面智能体与裁判都用 `ag/gemini-3.8-flash-high`。模型经用户的模型服务调用（OpenAI 兼容接口，Chat Completions），地址与 Key 在用户环境变量 `YUDAO_EVAL_BASE_URL`、`YUDAO_EVAL_API_KEY` 中。
- 对照的条件与「高于」的判法：两边的起点相同，Yudao 新建项目时经起始文件夹带入题目给的文件；两边的上下文窗口与单次输出上限相同，取模型服务的模型列表为这个模型报告的值；每次运行的时间上限两边都是 120 分钟（暂定默认值，属于评价标准）；Yudao 的第一次交付与最终交付都评分。是否高于单个 agent 按 [D38](system-intent.md) 的 N-G1 判定，只看质检这一段带来的提高；两边的完成度逐次并排列出，不单独据此判定。
