# D11 三部门循环的整体定义

状态：有效。依据：[总图](../architecture.html)第一节「产品」「工程」「质检」方框与第三节外环；设计：[三部门的循环结构](../design/department-loop.md)第 2、3 节、[部门内多角色设计说明](../design/department-roles.md)。路线位置：[总体路线图](../program-roadmap.md)阶段一「单机诚实闭环，三道槽位立缝」，道 01 部门与核验。

## 已确认

- 大量参考 OMP 的成熟代码，把 Agent loop 改造成三部门循环。
- 产品、研发、质量各自限定角色与领域范围；单个部门具有 Agent 的历史维护和执行能力。
- 部门可以向其他部门提问，也可以提出动作要求；不局限于研发向产品发起单向澄清。
- 部门由围绕一个目标函数聚在一起的信息形成：作者的工作过程留在本部门内，意图、架构、已接纳的事实与接口约定属于全体；交接和回复主要使用明确消息与 spec。
- 任务只有在质量部门完成有效验收后才结束，部门模型自行结束一次响应没有整体完成权。
- OMP 是代码级参考，Yudao 掌握循环、上下文与协作规则，不依赖外部完整 Agent 运行时。

## 责任边界

请求其他部门采取动作不等于取得对方权限。动作由被请求部门在其职责内处理，结果以消息和 spec 回传。专家咨询、动作请求、需求变更、交付与验收结论分别保留来源与意义。

## 设计选择

当前动作采用现有职责内的补充说明、查看实现、公开检查、修订需求及按有效计划修正交付。部门按关注的成果开始工作，三个部门同时运行，质检在交付之前做预测性探索（[三部门的循环结构](../design/department-loop.md)第 2、3 节、[D26](department-roles.md)）；同一事项一次一个未结请求，不嵌套（暂定默认值，见规则登记）；接纳、工具回执与回复分别记录，回答或拒绝后回到适用原工作。
