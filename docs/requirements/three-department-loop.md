# D11 三部门循环的整体定义

## 用户原话

> 我们相当于在OMP的基础上，把agent loop改为三部门，并且限定角色和领域范畴，然后部门允许像其他部门提问或者作出动作要求，直到最后质量部门验收完毕才算任务结束，因为我们可以大量参考OMP。但是上下文需要严格控制在部门内，交接和回复以消息和spec为主。

2026-10-06 用户修正了上面「上下文需要严格控制在部门内」的因果：

> 上下文需要严格控制在部门内，这个我需要修正，因果反了，如我刚才讨论的，是信息的内聚形成部门，而不是理所当然的

## 已确认

- 大量参考 OMP 的成熟代码，把 Agent loop 改造成三部门循环。
- 产品、研发、质量各自限定角色与领域范围；单个部门具有 Agent 的历史维护和执行能力。
- 部门可以向其他部门提问，也可以提出动作要求；不局限于研发向产品发起单向澄清。
- 部门由围绕一个目标函数聚在一起的信息形成：作者的工作过程留在本部门内，意图、架构、已接纳的事实与接口约定属于全体；交接和回复主要使用明确消息与 spec。
- 任务只有在质量部门完成有效验收后才结束，部门模型自行结束一次响应没有整体完成权。
- OMP 是代码级参考，Yudao 掌握循环、上下文与协作规则，不依赖外部完整 Agent 运行时。

## 责任边界

请求其他部门采取动作不等于取得对方权限。动作由被请求部门在其职责内处理，结果以消息和 spec 回传。专家咨询、动作请求、需求变更、交付与验收结论分别保留来源与意义。

## 本轮设计选择

首批动作采用现有职责内的补充说明、查看实现、公开检查、修订需求及按有效计划修正交付。部门按关注的成果开始工作，三个部门同时运行，质检在交付之前做预测性探索（[三部门的循环结构](../design/department-loop.md)第 2、3 节、[D26](department-roles.md)）；同一事项一次一个未结请求，不嵌套（暂定默认值，见规则登记）；接纳、工具回执与回复分别记录，回答或拒绝后回到适用原工作。通用流程完成后删除旧单向专用路径。
