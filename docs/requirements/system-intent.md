## 用户原话

2026-10-06 用户以一份任务书校准了 Yudao 的意图。任务书写明：「本文的意图是用户刚刚校准过的，与仓库里的旧文档冲突时，以本文为准」；「本文凡是写『当前阶段』的地方，都是现状而不是系统的定义，不要把现状固化进架构。」下面是任务书第一、二、三、五节的原文；第四节是请架构师回答的工程问题，回答在上面四份设计说明里。

### 一、Yudao 是什么

> Yudao 是一个自动交付软件的系统。它由若干部门组成，每个部门由大语言模型驱动，围绕同一份有效要求协作。控制核心掌握状态迁移的主权，生成的模型只提交提案与证据，什么成为事实由控制核心裁决。事件日志是唯一的事实来源，可以完整重放。
>
> 系统固定不变的是结构：循环、边界、裁决、独立的证据。其余都是填进这个结构的内容，会随阶段演进：
>
> - 组成。当前阶段是产品、工程、质检三个部门，每个部门一个角色。之后有：运维部门；部门内的多角色（经理、中心角色、探索者、主程、审查者等）；外包角色（把 Claude Code、pi 这类完整的 agent 当作部门内的角色）；元观察与规则检查；教训发现、系统演化等观察者。增加一个部门或角色应当只写声明。
> - 使用者。当前阶段只有一个人。
> - 部署。当前阶段是一台控制主机加若干登记的执行机器。ADR-0018 写明了扩展途径，用户最初设想过把部门或角色做成独立服务、以集群方式部署。
> - 并发。当前阶段同一项目同一时刻只有一个角色写代码，将来要支持多个写入者。

### 二、用户的意图（按从目的到手段排列）

> 1. 目的有三条：
>    - 独立地高质量交付成果，质量高于直接使用单个 agent。
>    - 长时间自己运行并自己修复。用户不在场是常态。
>    - 自举：用 Yudao 开发 Yudao，并在此基础上自我迭代和演化。
>
>    更远的方向是受治理的系统演化：系统根据运行证据提出对自身组织与规则的修改，经独立评价、限定采用、可以撤销。
>
> 2. 近期的阶段目标是尽快进入可迭代状态：改一处，跑真实任务，看到结果，决定保留还是撤回，这个圈能便宜地反复转。判据有五条：
>    - 有持续的真实负载在跑。
>    - 能度量：有固定的回归用例，记录循环次数、完成度、正确性与成本，改动前后可以比较。
>    - 改动便宜且可撤回：规则与参数是带版本的数据，换版本不用改代码。
>    - 看得见：循环是否收敛、卡在哪一层，能直接看出来。
>    - 锚点受保护：被迭代的系统改不了评价它的标准。
>
>    自举是进入这个状态的一种方式，作为路线图的一部分来安排。它分两层：第一层是 Yudao 把自己的仓库当作普通项目来开发；第二层是 Yudao 修改自己的组织与规则，建立在第一层之上。
>
> 3. 方法是把 agent 系统当作控制论工程来做。系统的本体是循环，循环是嵌套的。现在能识别出四层：角色的步骤循环、部门激活、部门之间的循环、项目循环。层数不是固定的，新的层只在有运行证据表明需要时才加，嵌套深度有硬上限。每一层都有边界，每一轮都有记录、有裁决、有上限。
>
> 4. 约束是不能为了可控而失去 agent 的能力。用户明确不要 LangGraph 那样预先写好流转路径的静态编排。具体含义：
>    - 部门之间谁问谁、返工回到哪，由运行中的事实决定。
>    - 边界以内的路径由 agent 自主决定，也允许它自己拆任务、起子循环；子循环同样有边界。
>    - 控制只放在边界和接纳上：生成保持开放，接纳严格。
>    - 边界要宽。用户的原话是「尽可能放开限制，确定收敛即可」。
>    - 用户的判据：为了某个场景提升 1% 而选一条规则，却丧失了大部分场景的能力，这不是好方案。
>
> 5. 规则是演化来的，不是预先定死的。先反复观察到某种失败，再抽象成规则；先定规则再找理由是过早抽象。除了第三节的基础规则，其余规则都是带理由的暂定默认值，由运行证据放松或收紧。
>
> 6. 独立与上下文。分成多个部门是为了错误独立：目标函数不同（挑错与完成），证据来源不同（跑测试与写代码）。需要独立的是判断，不是上下文。
>    - 意图、架构、已有的事实、接口约定应当共享。用户观察到的好团队是一专多精的，上下文有交叉，彼此熟悉、信任交付，进而把对方的工作当作抽象来用。
>    - 需要隔开的只有作者的工作过程与自我辩护。验证者先独立形成判断，再看对方的解释。
>    - 上下文边界放多宽是可调的参数，不是不变量。
>    - 验证密度随记录自适应：一个角色连续多轮结果可靠就少查，结果让人意外的地方多查。
>    - 今后任何新增的部门、角色、观察者或嵌套层，都要说得出它新增的独立性是什么。
>    - 部门在循环之内，持有交接并产出成果；观察者在循环之外，只按读取范围订阅事件，结果只能以提案形式提交。
>
> 7. 裁决的方式。主权始终在控制核心，手段有三种，按下面的顺序优先：
>    - 代码能精确判定的，由确定的规则判定：测试、构建、类型检查、改动范围、轮次与时间、本体校验。
>    - 需要判断但有参照材料的局部问题，在事先规定的判定点上，交给带校准置信度的决策模型（JEV）。结果分通过、不通过、不确定三种，去向事先规定。判定点用本地中文样本校准通过之后才自动推进，没通过的只记录。每次判定记录输入、问题、选项顺序、模型版本与概率，重放时使用记录的结果。
>    - 以上都判定不了的，升级给更强的模型或者用户。
>
>    JEV 不负责质检放行、产品取舍、规则修改，也不做跨步骤的因果判断和代码是否正确的判断。
>
> 8. 「可控」有主次：
>    - 第一，循环一定会停，而且每次停下都有明确的原因。这由代码保证，不靠人盯。
>    - 第二，不越界。
>    - 第三，是否收敛能被检测出来。收敛无法事先保证，只能事后检测。
>    - 第四，用户能看到里面实际发生了什么。
>    - 第五，用户能中途介入，只在安全节点生效。
>
> 9. 能固定下来的事就封装起来。测试、流转、检查这类可以自动化的东西做成系统内置的工序，之后只看它的输出，不再看它的内部。
>
> 10. 可视化是服务于以上各条的工具，有两个用途：
>     - 看懂。用户已经不逐行读代码，需要靠视觉对循环和它造出来的东西形成框架性的认识。在线时能实时检查状态，隔几小时回来时能看到哪些事等他决定、发生了什么、循环是否在收敛。
>     - 调整。这是可视化编程落地的地方：让循环能被看懂，并能方便地调整循环的方式和参数。

### 三、基础规则

> 这六条是整个系统最底层的规则，高于任何具体设计。它们不随演化改变。
>
> 1. 现实的证据高于模型的意见。真正独立的证据只有三种来源：把东西实际跑一遍，换一个不同的模型，或者人。系统能力的上限，是意图里有多大比例能变成可以执行的检验。
> 2. 没有传感器的地方明说是开环。无法检验的东西（设计品味、架构好坏）要标出来，不用更多的模型审查假装闭环。
> 3. 生成者不裁决自己，被评价者改不了评价标准。它包含原有的四条不变量：目标层只由用户修改；权威关系只经带版本的定义与用户批准改变；生成的模型只能提议，不能宣布状态已改变；撞到上限记为失败，不得悄悄放宽。
> 4. 可信内核在自我修改之外，并且小到用户本人能看懂。内核至少包括：裁决的核心代码、评价用的任务集、发布的闸门。
> 5. 每条规则和结构都要付租金：说明它拦什么、花多少，付不起就删。效果相同时简单的赢。成本是目标的一部分。
> 6. 一定会停；改进只有超过噪声才算数。

### 五、已经定下的决定（可视化部分）

> A. 可视化编程的对象是循环的规则，不是产品代码，也不是某次运行的路径。在图上能改的：
>    - 参数：时间上限、轮次上限、验证密度、上下文边界、判定点的阈值等。在界内直接生效。
>    - 循环方式：增减角色、部门与观察者，谁能打回谁，判定点放在哪，是否允许起子循环。生成候选版本，通过结构校验，用户批准后采用。
>    - 目标：要求与验收标准。由用户直接改。
>
>    在图上不能改的：某一次运行里具体走哪条路；第三节的基础规则。
>
> B. 图上固定画出的只有三样：边界、裁决点（包括判定点）、权威关系。边界以内画实际发生的轨迹，不画预设的路径。
>
> C. 画面分两层。事实层是事件日志的函数，进入自动化测试；表演层可以有自己的状态，但不占用承载事实的视觉通道，不回写。角色当前的任务与流式输出属于事实。
>
> D. 画面要让循环的动态可见：收敛、震荡、停滞、漂移、撞到边界，并能指出是哪一层。先让循环可观测，再让它可编辑。
>
> E. 画面要区分一条事实是怎么来的：确定规则判定的、决策模型判定的（附概率）、角色陈述的、主机测量的。开环的地方也要画出来。
>
> F. 被造出来的产品也要画出来，底图由主机从代码机械导出，不能只来自 agent 的陈述。
>
> G. 不做的事：产品代码的可视化编程；3D；把设置和表单搬进游戏世界；没有真实指称的游戏机制。
>
> H. 可视化的大部分工作适合作为第一层自举的首批真实工单，因为界面改坏了不影响裁决。

### 可迭代状态的五条判据

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-T1 | 有持续的真实负载在运行 | 每周由 Yudao 实例完成并被采纳的真实事项数大于 0，连续 4 周 |
| N-T2 | 能度量：固定的回归场景，记录循环次数、完成度、正确性与成本，改动前后可以比较 | 每个版本有一份评测结果，含循环次数、返工次数、询问次数、完成度、正确性、请求数、用量、费用与耗时；两份结果的比较给出改进、无差别、退化之一 |
| N-T3 | 改动便宜且可撤回：规则与参数是带版本的数据，修改它们不需要修改代码 | 修改一个限额或一个角色的可见范围不需要发布新版本；每次修改有事件记录；撤回是一条命令 |
| N-T4 | 看得见：循环是否收敛、停在哪一层 | 每个进行中与已结束的循环实例，在界面上有层、已用的边界、收敛状态与停止原因 |
| N-T5 | 锚点受保护：被迭代的系统修改不了评价它的标准 | 修改内核清单中任一路径的交付不会被自动采纳；评测使用的评分器与隐藏检查取自当前运行的已发布版本；演练一次并留下记录 |

### 循环

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-L1 | 每一层循环有声明的边界，每一轮有记录、有裁决、有上限 | 对事件日志检查：每个循环实例有开始事件、每轮的记录、结束事件与停止原因；已用量不超过上限加一次调用的最长时限 |
| N-L2 | 层数不固定：新增一层要有运行证据，嵌套深度有硬上限 | 定义中声明各层；深度上限是内核常量，现值为 2；新增层的声明引用运行证据 |
| N-L3 | 子循环同样有边界，上限从上一层的剩余量继承 | 子循环的时间上限不大于上一层的剩余时间；上一层只收到子循环的一条结果 |
| N-L4 | 已用量跨进程重启保持 | 终止进程再启动，已用时间、激活次数、模型步数与重启之前连续 |

### 保留 agent 的能力

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-A1 | 部门之间谁问谁、返工回到哪，由运行中的事实决定；定义只写许可关系与边界，不写顺序 | [循环与收敛](../design/loops-and-convergence.md)中防止滑向静态编排的五条判据全部通过 |
| N-A2 | 边界以内的路径由 agent 自己决定，可以自己拆任务、起子循环 | 一个角色在自己的边界内发起子循环并取回结果，控制核心只核对边界与接纳结果 |
| N-A3 | 控制只放在边界与接纳上 | 规则登记中每条规则的形式是许可、边界、接纳条件三者之一 |
| N-A4 | 边界默认放宽，收紧需要运行证据 | 每条收紧的记录引用至少两次独立运行中的同一类失败 |
| N-A5 | 一条规则的取舍看它在全部回归场景上的影响 | 新增或收紧规则的对照结果覆盖全部回归场景，任一场景退化即不采用 |

### 规则的演化

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-P1 | 基础规则以外的每条规则是带理由的暂定默认值 | 定义中每条限额与规则有四项记录（拦截什么、花费多少、放松的证据、收紧的证据）与取值界限 |
| N-P2 | 先反复观察到失败，再抽象成规则 | 规则的来源字段引用事件或教训候选的编号 |
| N-P3 | 规则能淘汰 | 每个阶段结束时有一份规则复查记录：触发次数、花费、保留或删除的结论 |

### 独立与上下文

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-I1 | 共享与隔开按信息的内聚划分：一个部门是围绕一个目标函数聚在一起的信息，它的工作过程留在部门内；意图、架构、已有的事实、接口约定属于全体 | 部门的定义写明它内聚的目标函数、证据来源与工作过程；共享的取值下，质检与产品的上下文清单里有架构说明、被接纳的事实与接口约定 |
| N-I2 | 隔开的只有作者的工作过程与自我辩护 | 验证者在提交独立判断之前的任何请求里，没有作者的历史与解释性陈述 |
| N-I3 | 验证者先独立形成判断，再看对方的解释 | 事件顺序：独立判断事件早于任何含作者解释的验证者请求；有测试覆盖 |
| N-I4 | 上下文边界的宽度是可以调整的参数 | 两套可见范围的取值可以各自运行同一个评测场景，不修改代码 |
| N-I5 | 验证密度随记录调整：连续可靠时减少核验，出现意外时增加核验 | 同一快照上重复运行的检查比例随一致记录下降，出现不一致以后恢复全量；调整写成事件 |
| N-I6 | 新增的部门、角色、观察者或嵌套层写明它内聚的是什么：目标函数、证据来源、工作过程，由此说明它新增的独立性 | 定义校验拒绝没有填写目标函数与证据来源的新增项；三项都与已有成员相同的新增项由用户决定是否保留 |
| N-I7 | 部门在循环之内持有交接并产出成果；观察者在循环之外，只按读取范围订阅事件，结果只以提案形式提交 | 去掉观察者以后，同一份记录的模型输出产生相同的事实事件 |

### 裁决

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-J1 | 三种手段按顺序使用：确定的规则，判定点上的决策模型，升级给更强的模型或用户 | 每条裁决记录写明使用的手段；规则能判定的地方没有判定点 |
| N-J2 | 判定点有合同：问题、参照材料、选项、三种结果各自的去向 | 定义中的判定点通过结构校验；缺少参照材料或去向的声明被拒绝 |
| N-J3 | 判定点用本地中文样本校准通过以后才自动推进，没有通过的只记录 | 未校准的判定点开启与关闭时，同一份记录的模型输出产生相同的事实事件 |
| N-J4 | 每次判定记录输入、问题、选项顺序、模型版本与概率，重放使用记录的结果 | 重放不发出判定请求，结果与记录一致 |
| N-J5 | 决策模型不负责质检放行、产品取舍、规则修改、跨步骤的因果判断与代码是否正确 | 判定点的结果可以触发的迁移不包含放行、产品合同的接纳与定义的采用；由结构校验覆盖 |
| N-J6 | 不确定的结果升级，去向事先规定 | 每个判定点的「不确定」有一个去向：更强的、与生成者不同的模型，或决定请求 |

### 可控的五个层次

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-C1 | 循环一定会停，每次停下有明确的原因，由代码保证 | 对全部事件序列基准与评测运行：每个 run 以封闭清单里的原因结束或进入等待；N-L4 通过；每种等待有时长上限 |
| N-C2 | 不越界 | 越界的工具调用在执行之前被拒绝并写成事件 |
| N-C3 | 是否收敛能事后检测出来 | 每个循环实例有收敛状态：收敛中、震荡、停滞、漂移、达到边界，由代码从事件计算，进展只按主机记录的事实判定 |
| N-C4 | 用户能看到里面实际发生了什么 | N-T4 与可视化各条 |
| N-C5 | 用户能中途介入，只在安全节点生效 | 取消、指导、新输入、参数修改都在安全节点处理并写成事件 |

### 工序

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-S1 | 测试、流转、检查这类可以固定下来的事做成内置工序，下游只读取它的输出 | 项目的检查定义写明命令、运行环境、输出格式与对流转的作用；回执由主机产生；下游按回执判断 |

### 可视化

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-V1 | 用户隔几小时回来时能看到：哪些事等他决定、发生了什么、循环是否在收敛 | 首页三项都来自事件；第三项给出每个进行中事项的收敛状态 |
| N-V2 | 在线时能实时检查状态；角色当前的任务与流式输出属于事实 | 画面上每个角色的任务与输出对应一条事件 |
| N-V3 | 可视化编程的对象是循环的规则：参数在界内直接生效，只作用于之后创建的 run；循环方式生成候选，通过结构校验并经用户批准后采用；目标由用户直接修改。某一次运行的路径与基础规则不能在图上修改 | 三类修改各有一条命令与一条事件；界面没有修改某次运行路径的入口 |
| N-V4 | 图上固定画出的只有边界、裁决点与权威关系；边界以内画实际发生的轨迹 | 事件为空时画面没有轨迹；固定画出的连线由组织定义的许可关系导出 |
| N-V5 | 事实层是事件日志的函数并进入自动化测试；表演层不占用承载事实的视觉通道，不回写 | [应用层与接口层](../design/app-and-interface.md)中画面诚实性的七条不变式有对应的测试 |
| N-V6 | 循环的动态可见：收敛、震荡、停滞、漂移、达到边界，并指出是哪一层 | 见 N-C3、N-T4 |
| N-V7 | 区分一条事实的来源：确定规则判定的、决策模型判定的（附概率）、角色陈述的、主机测量的；开环的地方也画出来 | 画面上每条事实带来源；没有可执行检验的验收条件有开环标记 |
| N-V8 | 被造出来的产品也画出来，底图由主机从代码导出 | 底图的每个元素对应公开树清单或主机运行的工具输出 |
| N-V9 | 不做：产品代码的可视化编程、3D、把设置和表单搬进游戏世界、没有真实指称的游戏机制 | 界面评审清单 |

### 基础规则

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-K1 | 现实的证据高于模型的意见；度量意图里有多大比例变成了可执行的检验 | 每次放行附检验覆盖比例；放行引用的证据来自实际运行、另一个模型或人 |
| N-K2 | 没有传感器的地方明说是开环 | 验收条件的检验方式有「开环」一项，放行记录与画面都列出 |
| N-K3 | 生成者不裁决自己，被评价者修改不了评价标准，包括四条不变量 | 目标只由用户的命令修改；权威关系只随定义的版本改变；模型输出只作为提案；达到上限的 run 不继续 |
| N-K4 | 可信内核在自我修改之外，小到用户本人能看懂：有行数上限，只依赖内核自身与少数几个库，每条内核规则对应一个测试名称；至少包括裁决的核心代码、评价用的任务集与发布检查 | 内核清单存在；内核差异、行数、导入方向与探针在发布前运行；内核行数不超过清单写明的上限 |
| N-K5 | 每条规则和结构说明拦截什么、花费多少，付不起就删除；成本是目标的一部分 | N-P1、N-P3；每份对照报告有费用一列 |
| N-K6 | 一定会停；改进超过噪声才算数 | N-C1；版本比较使用噪声范围 |

## 当前阶段的取舍与放开条件

| 当前的取舍 | 放开时需要的条件 |
| --- | --- |
| 三个部门，每个部门一个角色 | 控制代码中没有部门名称；新增项写明独立性；多角色在评测场景上不劣于单角色 |
| 一个使用者，局域网内使用 | 每条命令带操作者身份；目标的所有者按项目写明；访问令牌与 TLS |
| 一台控制主机，控制核心一个实例 | ADR-0018 的三个触发条件；项目流可以单独导出并在另一个实例上重放一致 |
| 同一项目同一时刻一个角色写代码，一次一个事项 | 采纳的成果写回代码仓库；采纳之前对合并后的结果运行检查定义规定的检查；工作区按事项分开 |
| 自有角色，没有外包角色 | ACP 接入；外包角色的输出有独立的下游核验；外包与自有在配对工单上对照 |
| 没有观察者，没有启用的判定点 | 观察者的订阅与提案接口；每个判定点各自校准通过 |
| Yudao 的开发由 omp 执行 | 自举第一层的前置条件与验收（路线图的自举工作线） |
| Yudao 平台的运维由人负责 | 一个部署中的运维部门负责另一个部署，健康检查保留外部途径 |
| 代码在执行位置上直接运行，没有操作系统层面的隔离 | 自举项目的执行位置放在控制主机以外的登记机器上，在现有机制内完成 |
| 评测只有三个回归场景，被测模型是能力一般的模型 | 留出场景建立；评分材料的校验方式不变 |
| 通知与决定请求只在客户端显示 | 消息渠道接入 |
| run 流不跨版本保存，升级前排空 | 保持；它让控制核心的修改不背旧格式 |
| 角色清单随系统版本发布，深度 1 | 组织与角色的候选、结构校验与用户批准的流程；子循环的合同 |
| 只使用 1M 窗口的模型 | 压缩阈值与工作上限成为参数以后，小窗口模型按参数运行 |
| 不签名；computer use 只考虑 Windows；只在局域网内使用 | 各自的 ADR 写明的放开条件（ADR-0023、ADR-0026、ADR-0015） |
