# D38 系统意图与基础规则

状态：有效。依据：[总图](../architecture.html)第一、二、五节。路线位置：三条目的与五条判据按[总体路线图](../program-roadmap.md)第 5 节逐阶段核对。设计：[可信内核](../design/trusted-kernel.md)、[规则登记与参数](../design/rules-and-parameters.md)、[循环与收敛](../design/loops-and-convergence.md)、[验证的独立性](../design/independent-verification.md)、[形态与核验角色](../design/forms-and-verifier-role.md)。

本记录写系统的目的、达到目的的判据、六条基础规则，以及从意图拆出的需求与验收标准，供工单与设计说明按编号引用。系统是什么见总图，术语见 `CONTEXT.md`，基础规则在系统里对应的具体规则与出处见 [基础规则](../foundation-rules.md)。其他需求记录与本记录冲突时，以本记录为准。

## 目的

1. 独立地高质量交付成果。有核验角色的形态（默认三部门）下，同一个模型，交付质量高于直接使用单个 agent。没有核验角色的形态不承诺更高质量，承诺的是快照进出、上限、写入口与「开环完成」的标记，让看记录的人分得清哪些交付经过了独立核验。
2. 长时间自己运行并自己修复。用户不在场是常态。
3. 自举。第一层是 Yudao 把自己的仓库当作普通项目来开发；第二层建立在第一层之上，系统根据运行证据提出对自身组织与规则的修改，经独立评价、限定采用、可以撤销。

近期的阶段目标是进入可迭代状态：改一处，跑真实任务，看到结果，决定保留还是撤回，这个圈能便宜地反复转。判据五条，见下表 N-T1 至 N-T5。

## 基础规则

六条基础规则是整个系统最底层的规则，高于任何具体设计，不随演化改变。

1. 现实的证据高于模型的意见。真正独立的证据只有三种来源：把东西实际跑一遍，换一个不同的模型，或者人。系统能力的上限，是意图里有多大比例能变成可以执行的检验。
2. 没有传感器的地方明说是开环。无法检验的东西（设计品味、架构好坏）要标出来，不用更多的模型审查假装闭环。
3. 生成者不裁决自己，被评价者改不了评价标准。它包含四条不变量：目标层只由用户修改；权威关系只经带版本的定义与用户批准改变；生成的模型只能提议，不能宣布状态已改变；撞到上限记为失败，不得悄悄放宽。
4. 可信内核在自我修改之外，并且小到用户本人能看懂。内核至少包括：裁决的核心代码、评价用的任务集、发布的闸门。
5. 每条规则和结构都要付租金：说明它拦什么、花多少，付不起就删。效果相同时简单的赢。成本是目标的一部分。
6. 一定会停；改进只有超过噪声才算数。

## 需求与验收标准

下列需求按意图与基础规则逐条拆分，验收标准是完成的依据。编号在工单与设计说明中引用。

### 目的

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-G1 | 独立地高质量交付：有核验角色的形态下，同一个模型，交付质量高于单独运行的 agent | 回归场景两边各运行 3 次（条件具备的场景先做，场景 3 最先），按[评测场景设计](../design/evaluation-scenarios.md)第 6.3 节判定：3 次中至少 2 次，核验角色在时间上限以内给出结论，并且最终交付比本次第一次交付多通过至少 1 条隐藏检查（第一次交付已经全部通过的那次不计入）；3 次都没有误放行。两边每次的完成度、正确性、用时与用量逐次并排列出，不单独据此判定「高于」。对照的单个 agent 是 OpenCode（[D32](comparison-experiment.md)）；以开环完成结束的交付不计入对照，报告上写开环完成，不写成放行 |
| N-G2 | 长时间自己运行并自己修复：用户不在场时，进程中断与模型服务中断以后自动继续，交付软件的故障经修复事项修复，每次停止都有原因 | 阶段三的交付验证（[路线图](../program-roadmap.md)第 2 节、[D27](operations-department.md)「长时间运行」）：你不在的一周里，一次进程中断与一次模型服务中断都自动接续，一次故障由运维发现、经三部门修复、运维重新部署；进程重启前后已用的运行时间连续累计 |
| N-G3 | 自举第一层：一个已发布版本的 Yudao 实例把 Yudao 仓库当作普通项目，独立完成真实工单 | [D35](self-hosting.md)「第一层试点的配对验收约定」：6 个配对工单上，质量按配对比较不劣于外部执行者；两边从同一组模型取得 |
| N-G4 | 自举第二层：系统根据运行证据提出对自身组织与规则的修改，经独立评价、限定采用、可以撤销 | [D35](self-hosting.md)「第二层的前置条件与完成条件」的四条完成条件；阶段五的交付验证（[路线图](../program-roadmap.md)第 2 节）：系统提出组织定义、流转规则与工作单元降解的候选，经独立评价限定采用，劣化时撤回 |

### 可迭代状态的五条判据

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-T1 | 有持续的真实负载在运行 | 每周由 Yudao 实例完成并被采纳的真实事项数大于 0，连续 4 周 |
| N-T2 | 能度量：固定的回归场景，记录循环次数、完成度、正确性与成本，改动前后可以比较 | 每个版本有一份评测结果，含循环次数、返工次数、询问次数、完成度、正确性、请求数、用量、费用与耗时；两份结果的比较给出改进、无差别、退化之一 |
| N-T3 | 改动便宜且可撤回：规则与参数是带版本的数据，修改它们不需要修改代码 | 修改一个限额或一个角色的可见范围不需要发布新版本；每次修改有事件记录；撤回是一条命令 |
| N-T4 | 看得见：循环是否收敛、停在哪一层 | 每个进行中与已结束的循环实例，在界面上有层、已用的边界、收敛状态与停止原因 |
| N-T5 | 锚点受保护：被迭代的系统修改不了评价它的标准 | 修改内核清单中任一路径的交付不会被自动采纳；评测使用的评分器与隐藏检查取自当前运行的已发布版本；演练一次并留下记录 |

### 循环

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-L1 | 每一层循环有声明的边界，每一轮有记录、有裁决、有上限 | 对事件日志检查：每个循环实例有开始事件、每轮的记录、结束事件与停止原因；已用量不超过上限加一次调用的最长时限 |
| N-L2 | 层数不固定：新增一层要有运行证据，嵌套深度有硬上限 | 定义中声明各层；深度上限是内核常量，现值为 2；新增层的声明引用运行证据 |
| N-L3 | 子循环同样有边界，上限从上一层的剩余量继承 | 子循环的时间上限不大于上一层的剩余时间；上一层只收到子循环的一条结果 |
| N-L4 | 已用量跨进程重启保持 | 终止进程再启动，已用时间、激活次数、模型步数与重启之前连续 |

### 保留 agent 的能力

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-A1 | 部门之间谁问谁、返工回到哪，由运行中的事实决定；定义只写许可关系与边界，不写顺序 | [循环与收敛](../design/loops-and-convergence.md)中防止滑向静态编排的五条判据全部通过 |
| N-A2 | 边界以内的路径由 agent 自己决定，可以自己拆任务、起子循环 | 一个角色在自己的边界内发起子循环并取回结果，控制核心只核对边界与接纳结果 |
| N-A3 | 控制只放在边界与接纳上 | 规则登记中每条规则的形式是许可、边界、接纳条件三者之一 |
| N-A4 | 边界默认放宽，收紧需要运行证据 | 每条收紧的记录引用至少两次独立运行中的同一类失败 |
| N-A5 | 一条规则的取舍看它在全部回归场景上的影响 | 新增或收紧规则的对照结果覆盖全部回归场景，任一场景退化即不采用 |

### 规则的演化

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-P1 | 基础规则以外的每条规则是带理由的暂定默认值 | 定义中每条限额与规则有四项记录（拦截什么、花费多少、放松的证据、收紧的证据）与取值界限 |
| N-P2 | 先反复观察到失败，再抽象成规则 | 规则的来源字段引用事件或教训候选的编号 |
| N-P3 | 规则能淘汰 | 每个阶段结束时有一份规则复查记录：触发次数、花费、保留或删除的结论 |

### 独立与上下文

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-I1 | 共享与隔开按信息的内聚划分：一个部门是围绕一个目标函数聚在一起的信息，它的工作过程留在部门内；意图、架构、已有的事实、接口约定属于全体 | 部门的定义写明它内聚的目标函数、证据来源与工作过程；共享的取值下，质检与产品的上下文清单里有架构说明、被接纳的事实与接口约定 |
| N-I2 | 隔开的只有作者的工作过程与自我辩护 | 验证者在提交独立判断之前的任何请求里，没有作者的历史与解释性陈述 |
| N-I3 | 验证者先独立形成判断，再看对方的解释 | 事件顺序：独立判断事件早于任何含作者解释的验证者请求；有测试覆盖 |
| N-I4 | 上下文边界的宽度是可以调整的参数 | 两套可见范围的取值可以各自运行同一个评测场景，不修改代码 |
| N-I5 | 验证密度随记录调整：连续可靠时减少核验，出现意外时增加核验 | 同一快照上重复运行的检查比例随一致记录下降，出现不一致以后恢复全量；调整写成事件 |
| N-I6 | 新增的部门、角色、观察者或嵌套层写明它内聚的是什么：目标函数、证据来源、工作过程，由此说明它新增的独立性 | 定义校验拒绝没有填写目标函数与证据来源的新增项；三项都与已有成员相同的新增项由用户决定是否保留 |
| N-I7 | 部门在循环之内，按关注的成果工作并产出成果（[三部门的循环结构](../design/department-loop.md)第 2 节）；观察者在循环之外，只按读取范围订阅事件，结果只以提案形式提交 | 去掉观察者以后，同一份记录的模型输出产生相同的事实事件 |

### 裁决

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-J1 | 三种手段按顺序使用：确定的规则，判定点上的决策模型，升级给更强的模型或用户 | 每条裁决记录写明使用的手段；规则能判定的地方没有判定点 |
| N-J2 | 判定点有合同：问题、参照材料、选项、三种结果各自的去向 | 定义中的判定点通过结构校验；缺少参照材料或去向的声明被拒绝 |
| N-J3 | 判定点用本地中文样本校准通过以后才自动推进，没有通过的只记录 | 未校准的判定点开启与关闭时，同一份记录的模型输出产生相同的事实事件 |
| N-J4 | 每次判定记录输入、问题、选项顺序、模型版本与概率，重放使用记录的结果 | 重放不发出判定请求，结果与记录一致 |
| N-J5 | 决策模型不负责放行、要求里的取舍、规则修改、跨步骤的因果判断与代码是否正确 | 判定点的结果可以触发的迁移不包含放行、要求合同的接纳与定义的采用；由结构校验覆盖 |
| N-J6 | 不确定的结果升级，去向事先规定 | 每个判定点的「不确定」有一个去向：更强的、与生成者不同的模型，或决定请求 |

### 可控的五个层次

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-C1 | 循环一定会停，每次停下有明确的原因，由代码保证 | 对全部事件序列基准与评测运行：每个 run 以封闭清单里的原因结束或进入等待；N-L4 通过；每种等待有时长上限 |
| N-C2 | 不越界 | 越界的工具调用在执行之前被拒绝并写成事件 |
| N-C3 | 是否收敛能事后检测出来 | 每个循环实例有收敛状态：收敛中、震荡、停滞、漂移、达到边界，由代码从事件计算，进展只按主机记录的事实判定 |
| N-C4 | 用户能看到里面实际发生了什么 | N-T4 与可视化各条 |
| N-C5 | 用户能中途介入，只在安全节点生效 | 取消、指导、新输入、参数修改都在安全节点处理并写成事件 |

### 基础规则

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| N-K1 | 现实的证据高于模型的意见；度量意图里有多大比例变成了可执行的检验 | 每次放行附检验覆盖比例；放行引用的证据来自实际运行、另一个模型或人 |
| N-K2 | 没有传感器的地方明说是开环 | 验收条件的检验方式有「开环」一项，放行记录与画面都列出；没有核验角色的事项以开环完成结束，记录、页面与报告上不写成放行 |
| N-K3 | 生成者不裁决自己，被评价者修改不了评价标准，包括四条不变量 | 目标只由用户的命令修改；权威关系只随定义的版本改变；模型输出只作为提案；达到上限的 run 不继续 |
| N-K4 | 可信内核在自我修改之外，小到用户本人能看懂：有行数上限，只依赖内核自身与少数几个库，每条内核规则对应一个测试名称；至少包括裁决的核心代码、评价用的任务集与发布检查 | 内核清单存在；内核差异、行数、导入方向与探针在发布前运行；内核行数不超过清单写明的上限 |
| N-K5 | 每条规则和结构说明拦截什么、花费多少，付不起就删除；成本是目标的一部分 | N-P1、N-P3；每份对照报告有费用一列 |
| N-K6 | 一定会停；改进超过噪声才算数 | N-C1；版本比较使用噪声范围 |
