> 2026-09-19：本文是已关闭的 2.1–2.6 历史合同。用户新增的 2.7 统一 Provider 层与 Go 接入见 [独立计划](stage-2-provider-plan.md)，不改写本文历史验收结果。

日期：2026-09-15  
版本：v1.0  
依据：`docs/stage-2-harness-baseline.md`（Stage 2 重新收敛定义）

## 概述

Stage 2 目标：做出可日常使用的三部门 Harness 基线，质量对标 OMP，进化等高级能力推迟到后续。

**完成标准**：
- ✅ 真实任务连续 10 次至少 8 次到 DONE
- ✅ 失败可通过 Context/Trace View 追溯
- ✅ Provider 配置可通过界面完成
- ✅ 桌面/手机体验流畅
- ✅ 核心功能不弱于 OMP

**实施顺序**：2.1 → 2.2 → 2.4 → (2.3 + 2.5 并行) → 2.6

## 2.5 Prompt 优化

**目标**：三部门指令调优，减少无效往返

### 任务清单

#### 2.5.1 数据收集
- [ ] 收集 10+ 真实任务的完整 transcript
- [ ] 标注无效往返：
  - 产品过度澄清（应直接形成 PRD）
  - 工程不必要的专家请求（应自主完成）
  - 质检模糊返工（应明确验收标准）
- [ ] 统计往返次数分布

**产出**：`docs/stage-2-prompt-analysis.md`

#### 2.5.2 产品 Prompt 优化
当前问题示例：
- 过度询问细节而不是形成有效 PRD
- 等待用户补充而不是使用专业补全

优化方向：
- [ ] 强化"优先形成有效 PRD，细节由工程推断"
- [ ] 补充专业补全依据（常见约定、默认行为）
- [ ] 明确何时需要澄清（影响目标、成本）

**产出**：更新产品 prompt（`harness/prompts/product.md` 或代码中）

#### 2.5.3 工程 Prompt 优化
当前问题示例：
- 遇到小问题就请求专家协助
- 计划过于保守，不敢自主决定

优化方向：
- [ ] 强化"职责内问题自主解决"
- [ ] 明确专家请求边界（跨职责、重大变更）
- [ ] 补充工程默认依据（成熟组件、项目约定）

**产出**：更新工程 prompt

#### 2.5.4 质检 Prompt 优化
当前问题示例：
- 返工理由模糊（"不够好"而非具体缺陷）
- 过度严格或过度宽松

优化方向：
- [ ] 明确验收标准（功能、质量、安全）
- [ ] 返工必须指出具体问题和验证方法
- [ ] 平衡质量与效率（避免完美主义）

**产出**：更新质检 prompt

#### 2.5.5 回归验证
- [ ] 用相同任务测试新旧 prompt
- [ ] 对比往返次数、成功率、用量
- [ ] 收集反面案例（优化过度导致失败）

**产出**：Prompt 优化效果报告

**验收标准**：
- ✅ 10+ 真实任务分析完成
- ✅ 三部门 prompt 更新并验证
- ✅ 平均往返次数减少 20%+（或其他可测量指标）
- ✅ 成功率不降低

**责任人**：主 agent + 分析子 agent

**时间估算**：5-7 天

**依赖**：2.1 完成（需真实数据），可与 2.3 并行

## 风险与缓解

### 风险 1：2.1 网络问题无法根治
**影响**：真实验收无法通过，阻塞后续

**缓解**：
- 准备 Plan B Provider（OpenAI/Anthropic）
- 优化重试策略（更长等待、更多重试）
- 降低验收标准（5 次 3 成功 → 临时可接受）

### 风险 2：2.2 Provider 配置原型延迟
**影响**：界面无法实施，2.2 阻塞

**缓解**：
- 先实施 2.4 OMP 对标（识别缺失）
- 并行推进 2.3 Web 原型（不依赖配置界面）
- 最小化原型（仅列表 + 表单，不做复杂交互）

### 风险 3：2.3/2.5 并行资源冲突
**影响**：进度延迟

**缓解**：
- 明确子任务边界（前端 vs 分析）
- 文件责任分离（避免同时修改）
- 主 agent 协调冲突

### 风险 4：2.6 成功率不达标
**影响**：Stage 2 无法完成

**缓解**：
- 2.1-2.5 各阶段持续测试（早发现问题）
- 降级方案（80% → 70%，但需明确原因）
- 延长 2.6 时间（深度优化）
