# 为 Stage 6 分布式部署，从现在起遵守六条边界

Stage 6 把控制层、各部门、元观察与规则检查部门、Provider 与存储部署到不同的服务器和平台上（[D29](../requirements/distributed-deployment.md)）。决定：从现在起，所有设计与实现遵守以下六条边界，拆分本身在 Stage 6 进行。

1. 部门执行与控制层之间只通过明确的消息往来。控制层下发激活，部门交回提案、证据、工具回执与模型调用记录。每条消息有身份，可以记录、去重和重发。部门一侧不持有控制层的对象，取消通过消息和执行所有权传达。
2. 部门继续工作所需的全部信息都持久化到事件与工件：阶段、已用的次数与时间、在途动作、调用尝试、部门历史。凭据只保存引用，由执行所在的机器从本机的凭据来源解析。
3. 同一 run 同一时间只有一个有权推进的执行者。执行所有权记录在事件库，每次取得都产生新的身份；推进状态的写入在同一事务中核对这个身份，失去所有权的执行者提交的结果一律拒收。执行者分布在不同机器上时，所有权带有期限，由执行者按时续期。
4. 部门之间只通过按内容摘要标识的封存快照传递成果，不共享工作目录。
5. Web、CLI、API 通过命令入口提交操作，通过查询接口读取状态，不直接引用投影、事件库、工件等内部模块。
6. 生成模型与决策模型的调用只通过 Provider 模块。

理由：进程重启后接续与换一台机器接续是同一个问题：接手的执行者与原执行者没有共享的内存。3.1 可靠恢复已经要求第 2、3 条的单机部分（[恢复契约](../design/recovery-contract-and-fault-matrix.md)第 2、3 节）；D13 的完整交付快照与质检的检查副本符合第 4 条；2.7 之后第 6 条已经成立。现有实现中依赖同一进程的做法包括：激活时向部门循环传入十一个回调函数、进程内的锁与取消标志、只在内存中的运行开始时间与凭据快照、Web 直接引用内部模块读取数据。这些做法继续扩大，Stage 6 就需要重写核心。成熟做法：Temporal 的工作流与活动之间只交换可以序列化的输入与结果，活动通过心跳与超时判断存活；分布式锁需要一个随每次写入核对的递增编号（fencing token），才能拒绝失去锁的执行者迟到的写入；事件库在追加时核对期望版本；持续交付在各环境之间传递同一份不可变制品；命令与查询分开（CQRS）。

后果：

- Stage 6 之前不引入消息队列、网络服务、新的数据库或容器编排，各模块仍在同一进程中运行；消息以函数调用传递，内容是带有身份、可以序列化的数据。
- 3.1 设计执行所有权与激活接口时遵守第 1、3 条；期限与续期在 Stage 6 加入。
- Web 的直接读取在 Stage 4 的前端优化与可观测性工作中改为查询接口，Stage 6 开始之前全部完成。
- 现有的产品、工程、质检共用一个 run 工作目录，质检的检查已经使用按摘要取出的快照副本。新的设计不增加部门之间对共享目录的依赖，其余部分在 Stage 6 拆分时改为快照传递。
- 运维部门、元观察与规则检查部门、语义系统从设计开始遵守六条边界。
- 设计文档与工单按六条边界审查。
- Stage 6 的运行方式（是否采用 Temporal 等成熟引擎、事件库使用哪种数据库）在该阶段按故障场景与总成本比较后决定。
