# 桌面程序在控制主机的交互桌面上用真实输入试用

3.2D 的 computer use 让部门通过截图、点击与输入操作交付的桌面程序（[D34](../requirements/browser-and-computer-use.md)）。原设计在容器的虚拟屏幕中运行被测程序；2026-09-30 用户决定不使用容器与 WSL（[ADR-0022](0022-run-directly-without-containers.md)），屏幕从哪里来留给专题 2。控制主机是 Windows 11 家庭中文版，用户同时在使用它的桌面；家庭版不能安装 Hyper-V，没有 Windows 沙盒，也不能作为远程桌面的被连接端。2026-10-02 用户决定 computer use 现阶段只考虑 Windows，参照 Codex、OMP 等第三方 agent 的做法，并逐项采纳建议（[设计说明](../design/browser-and-computer-use.md)第 5 节、第 16 节第 7 至 12 项）。决定：

- 桌面种类的试用会话只在控制主机上、在用户已经登录的交互桌面上进行。控制主机以外的执行位置不提供桌面种类。
- 输入只用真实输入（`SendInput`），移动真实光标，被测程序切换到前台；不使用后台投递（`PostMessage`）与 UI Automation 的控件操作。
- 每个桌面会话开始前经用户同意（决定请求「使用本机桌面」）；整台控制主机同一时刻只有一个桌面会话，其余排队。
- 桌面锁定或处在安全桌面时等待解锁；用户正在操作时等用户停下；会话期间显示不出现在截图中的提示框，托盘菜单可以停止。
- 会话期间最小化其他程序的窗口，结束时恢复；截取主显示器并等比缩小到 1280×800 以内，坐标按比例换算。

考虑过的做法：

- 后台投递消息，不占用用户的鼠标与前台（OMP 的默认方式，Cua Driver）。Tk 忽略投递的按键与文字，Chromium 忽略全部投递事件，WPF 忽略大部分（OMP `fdfeef1f78` 的 `crates/pi-natives/src/desktop/win32/delivery.rs` 第 63–88 行）；两者在这些情况下都要求改用前台方式。投递成功也不能说明用户用鼠标与键盘能完成这项操作。
- UI Automation 的控件操作（Invoke、SetValue）。不需要前台，但 Tk 8.6 没有 UIA 支持，Python 自带的是 Tk 8.6；按控件操作同样绕过了用户实际使用的输入路径。
- 另建一个 Windows 会话或虚拟机（UFO² 的画中画桌面、Windows 沙盒、Hyper-V、Windows Agent Arena）。家庭版都不能使用；UFO² 的画中画桌面没有发布代码；微软的 agent workspace 与 MXC 是预览功能，MXC 的会话不支持界面程序。
- Linux 执行位置上的 Xvfb 虚拟屏幕。不打扰用户，但用户决定现阶段只考虑 Windows。
- 在登记的 Windows 机器上试用。执行代理以 WinSW 服务运行，处在 Session 0，服务不能与用户桌面交互。

理由：

- 在本机 Windows 上做 computer use 的产品（Codex、Claude 桌面应用、UI-TARS-desktop、Windows-MCP、UFO²）都直接操作用户正在使用的桌面；Codex 写明在 Windows 上不能在后台工作，会移动鼠标并占用前台，要求桌面保持解锁。
- 真实输入对所有界面库有效，试用记录反映用户能完成的操作，这与 3.2D 不提供浏览器脚本工具的理由相同。
- 用户的同意、独占、锁屏等待与让出，把「Yudao 与用户共用一套鼠标和键盘」限制在用户同意的会话以内。

后果：

- 桌面会话期间用户不能正常使用控制主机；长时间无人值守时，桌面锁定会使桌面会话等待。
- 只在 Linux 上运行的桌面程序，以及在登记的机器上运行的桌面程序，不能用 computer use 核验；质检把这些条目记为无法核验。
- 操作真实桌面的自动测试带 `desktop` 标记，默认的全部运行排除它们，在用户同意的时间运行（[测试分层设计说明](../design/test-pyramid.md)）。
- 截图尺寸随主显示器变化，屏幕工具的坐标是最近一次截图的像素，界面按回执中的截图尺寸显示。
