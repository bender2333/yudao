# 部门由信息的内聚形成，需要独立的是判断

此前的需求记录与设计把部门的上下文严格隔开写成固定规则：现有结构说明只给工程，部门记录的事实与决定只本部门可见，审查者看不到本部门记录的任何内容。用户 2026-10-06 校准了这一点：分成多个部门是为了错误独立，目标函数不同（完成与挑错），证据来源不同（写代码与运行测试），「需要独立的是判断，不是上下文」；并修正了因果：「是信息的内聚形成部门，而不是理所当然的」（[D38](../requirements/system-intent.md)）。决定：

- 部门是围绕一个目标函数聚在一起的信息：证据来源、工作过程与判断。部门的定义写明这三项。新增的部门、角色、观察者或循环层同样写明，它新增的独立性就是这三项与已有成员的差别；三项都与已有成员相同的新增项，由用户决定是否保留。
- 内容按四类决定默认谁可见：
  - 共享：意图原文、当前有效的产品合同、架构与现有结构说明、工程计划、被接纳的事实与决定、接口约定与启动方式、封存的代码快照、主机回执、质检的缺陷记录，所有部门与角色可见；
  - 作者的过程：角色的推理、工具调用的经过、失败的尝试与草稿，只有作者自己可见；
  - 作者的解释：交付说明与答复中的实现理由、已知不足与自我评价，验证者提交独立判断以后可见；
  - 评价材料：评测的隐藏检查与参考解法、校准样本的标注，任何部门、角色与观察者都不可见。
- 先判断后看解释：提案合同为交付说明的每个字段标明属于事实还是解释；验证者的请求里放入解释字段的条件，是事件日志中已经有这次交接的独立判断；质检结论必须引用一条独立判断，与它不同的条目写明改变的理由。部门内的审查者使用同一个步骤。
- 共享一类放多宽，是角色定义中的可见范围参数。现值保持不变，由 [D32](../requirements/comparison-experiment.md) 新增的一组对照决定是否改为共享；这组对照同时开启先判断后看解释，结论适用于两项一起采用。
- 验证密度是界内的参数，由确定的规则按记录调节：工程与质检的主机回执在同一树摘要上连续一致时降低，出现主机测量与陈述不一致等意外时回到全量。质检从验收条件导出的检查与试用用例不在这个比例之内。

理由：

- 把上下文整体隔开，同时隔开了验证者需要的事实与架构，带来重复探索与部门之间的询问；会带偏验证者的是作者的过程与自我辩护。
- 先规定部门、再规定上下文不能越过部门，因果是倒过来的。按内聚划分，边界由定义得出，新增结构时也用同一个判据。
- 可见范围已经是角色定义里的数据，扩充词表就能成为参数，不需要新的机制。

后果：

- 语义系统中部门记录的事实、决定与知识改为所有部门只读可见；推测、教训、洞见与画像默认本部门可见，取值是参数。
- 审查者看不到作者的历史；能否看到本部门记录的事实，作为另一组对照。
- 试用会话的浏览器与网络取回使用同一条规则，拒绝 Yudao 服务自己的地址。
- 设计见[验证的独立性设计说明](../design/independent-verification.md)。
