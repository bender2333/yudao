# 骨架与应用分两层：骨架向后兼容，应用一次完成，裁决只读骨架自己算的最小投影

用户 2026-10-23 与 Sonnet 讨论自举与组件化以后提出（[D40](../requirements/skeleton-and-application.md)）：系统分两层，骨架要考虑向后兼容，应用一次完成；分界不受现有 ADR 的限制；任务池可能只是一个模式，以后加也要能支持。此前的设计把可信内核定为「决定什么成为事实、评价版本好坏」的部分（[ADR-0027](0027-trusted-kernel-outside-self-modification.md)），但裁决读的是整份运行状态投影，投影与事件定义都在内核清单里，应用每加一种事件就改一次内核；流程编排把路由、驱动、调度写在一个 2437 行的模块里，第二种路由没有位置；哪些东西升级时必须兼容，没有一张表。决定：

- 系统分两层。骨架是下一个版本必须读得懂的事实、不会和 Yudao 同时换版本的对方所依赖的合同，以及应用整体重写时必须仍然成立的保证（一定会停、写入经裁决、生成者不裁决自己）。其余是应用：能从事实重算、只在一个进程里和自己说话、重写以后外面看不出区别。
- 骨架分两部分。可信内核按 ADR-0027，谁能改由内核清单与用户批准决定。契约部分（薄驱动、路由契约、装配契约、执行契约、骨架事件的种类、对外的合同）按普通流程修改，但只能向后兼容：字段只增、事件种类只增、接口只加可选参数、契约带版本。
- 裁决只读骨架自己算的最小投影：每条流的当前版本、谁持有执行权、已用的时间与次数、每种正式成果的当前版本、运行状态与待回答的决定请求、当前定义与参数的版本。最小投影只由骨架事件折叠，纯函数，可以重算。其余投影（部门历史、模型请求、上下文清单、询问栈、循环实例、收敛状态、资料）归应用，由应用从同一本事件日志自己算。成果之间的关系（交付引用 PRD、放行绑定交付）写在定义的提案合同里，裁决按合同核对版本。
- 事件分骨架事件与应用事件。骨架事件是内核写入或读取的那几种：事项的创建与结束、执行权、一轮工作的开始与结束及其用量、工具许可、正式成果的接纳与拒绝、决定请求与回答、项目流的全部事件；它们的种类与字段只增。其余 run 流事件是应用事件，按 [ADR-0019](0019-project-stream-across-versions.md) 跟随应用版本，升级前排空。
- 流程编排分成薄驱动与路由实现。薄驱动在骨架：读事实，问路由该让哪个部门开始一轮工作、一轮以什么结束、事项以什么结束；问装配要请求；交给执行；结果经写入口写回；每个安全节点问边界的核对。薄驱动不含部门、成果与阶段的名称。路由、装配、执行是三道带版本的契约，实现在应用里，由定义选择：组织定义写明路由实现的名称，默认是成果驱动（[ADR-0039](0039-departments-work-from-watched-outputs.md)，[三部门的循环结构](../design/department-loop.md)）；任务池以后是另一个实现，不碰骨架。
- 不建进程内的插件加载机制。版本切换靠槽位重启，定义已经是带版本、可撤回的数据。部门留在定义里，不做成各自的代码包。
- 看门狗在两层之外，是最老的进程，只认健康协议：A、B 两个槽位，存活检查加金丝雀答题，候选失败回退到稳定版；不依赖 Yudao 的代码，Yudao 的 agent 对它没有写权限，每次修改由用户批准。现在只写设计，建设在 Stage 4。
- 「谁改谁」从「谁评价谁」反推：被谁评价，就不能改谁。工程被质检评价，工程不能提出对质检的修改；质检的修改由不受它评价的一方提出；评测的隐藏检查与误放行探针在两者之外。
- MCP 与技能照做，路线图的 M5 与 3.2D 不动。

理由：

- 向后兼容只对两种东西有意义：不能重算的事实，以及不会同时换版本的对方。用这两条画线，骨架有确定的清单，应用可以整体重写。
- 门卫判断只需要几样通用的事实，与部门叫什么、成果有几种、画面显示什么无关。把这几样从大投影里分出来，内核不再随应用一起长，并且能读完；应用的投影算错只影响路由或画面，不会放进一条不该放的写入。
- 「会不会被自己改」作为分界的判据是循环的：什么都能被自己改，只要允许。按功能（决定事实、评价版本）加上兼容判据画线，才有确定的答案。
- 进程内插件加载买的是不重启替换，而槽位切换本来就以重启换版本；这个结构付不出租金（基础规则 5）。
- 任务池与成果驱动的差别只在「什么时候让哪个部门开始一轮工作、一轮怎么结束、事项怎么结束」，这正是路由契约的三个问题。把它做成契约的一个实现，以后加不碰骨架。

考虑过的做法：

- 骨架只留纪要里的四样（事件日志的单一写入口、插件加载机制、看门狗、极薄驱动循环）。按两条兼容判据与第三条保证判据，裁决入口、边界的核对、最小投影、定义的格式、对外的合同都必须在骨架里，否则应用重写时没人保证写入经裁决、一定会停。
- 整份运行状态投影留在内核（现状，ADR-0027 的「裁决读取的运行状态投影」）。内核随应用一起长，10 月以来 22% 的改代码提交碰内核文件。
- 部门做成各自的代码包，由别的部门演进（纪要）。部门是定义里的数据（[ADR-0014](0014-versioned-definitions.md)），增加部门只写声明；代码包会让「增加一个部门只写声明」不再成立。
- 进程内的插件加载与可逆副作用（Cordis、DeepSeek Harness 的做法）。留下的只有「契约先定、按键寻址」，我们缺的是三道缝的契约文字；内核框架在有第二个实现之前没有试验的对象。架构师没有核实 Cordis 与 DeepSeek Harness 的实现。
- 两种编排模式各自是流程编排的一种实现、其余控制核心共用（[ADR-0041](0041-two-orchestration-modes-share-control-core.md)，暂缓）。本 ADR 把它改成：路由是骨架的契约，两种模式都是应用里的路由实现；ADR-0041 恢复讨论时按此修改。

后果：

- 取代 ADR-0027 的两处：可信内核里的「裁决读取的运行状态投影」改为「骨架自己算的最小投影」；内核清单里 `harness/projection.py` 与 `harness/models.py` 的条目改为最小投影模块与事件信封、骨架事件的数据结构，应用的投影与应用事件的数据结构移出内核文件。清单的修改由用户在合并对应工单时批准。
- [总体架构](../design/architecture/overall-architecture.md)第 1.1、2、6.1 节、[可信内核设计说明](../design/trusted-kernel.md)第 2、3 节、[三部门的循环结构](../design/department-loop.md)（成果驱动路由的设计说明）、[测试分层设计说明](../design/test-pyramid.md)第 4 节按本 ADR 修改；设计见[骨架与应用设计说明](../design/skeleton-and-application.md)。
- 术语表增加骨架、应用、最小投影、薄驱动、路由契约、装配契约、执行契约、骨架事件、看门狗、金丝雀任务、健康协议。
- Stage 3 新增工作包「骨架与应用」与里程碑 M0.5，排在 M0 之后、M2 之前；M2 的核心工单在新结构上做。迭代底座的 B2 已随 #350 完成（`harness/bounds.py`），B1、B7 继续。
- 看门狗的健康协议是骨架的对外合同之一，设计在 Stage 4 补全；真实用户场景验收进入测试分层的发布前一层，运行器的工单在评测工作线。
