# 每次模型请求在控制核心装配，自有角色的步骤由控制核心驱动

语义系统规定每次模型请求由固定的栏目组成，其中当前状态栏目、通知、接触时附加与查询都依赖随时变化的共享状态（[语义系统设计说明](../design/semantic-system.md)第 10 节）。总体架构需要确定会话进行中的上下文在哪里装配，以及自有角色的循环放在哪一层（[总体架构：职责分层](../design/architecture/overall-architecture.md)）。决定：每次模型请求由控制核心装配；自有角色不设单独的会话执行者，控制核心驱动每个角色任务的步骤：装配请求（P）→ 经 Provider 调用模型（f）→ 每个工具调用先经过工具许可（U）→ 主机工具由控制核心执行，环境工具在执行环境中执行 → 记录结果并附加内容 → 下一步。执行层只有 Provider、执行环境与工具、外包 agent。控制核心的边界是裁决不使用模型。

理由：

- 当前状态栏目每次请求重新计算（部门账本、待复核与冲突提示、目录），并行的一次性角色随时在记录新内容；通知、接触时附加与按可见范围的查询都读取当时的知识层。执行者按一份固定的资料清单计算不出这些内容；让执行者直接读取知识层，装配器就在两处运行，版本可能不一致，上下文清单也只能依赖执行者自己的报告。
- 现有实现中，`harness/engine.py` 的 `run_department` 接收 11 个回调（`prepare_step`、`begin_tool`、`record_tool`、`finish_compaction` 等），每一个都属于装配、裁决或记录。[ADR-0007](0007-boundaries-for-distributed-deployment.md) 理由中列出的「十一个回调」，来自把循环外壳放在核心之外、再把核心的职责以回调传入；除去这些职责，循环外壳没有别的工作。
- 一次模型调用需要几秒到几分钟，每一步在核心装配一次需要毫秒，控制核心保持一份的判断（[系统架构原理](../design/architecture/core-and-materials.md)第 7.2 节）不受影响。
- 会话可以丢弃：一个角色任务的状态全部在事件与投影中，任何一步都能从已提交的状态重新装配后继续，不需要恢复任何会话的内存。

考虑过的做法：激活时由控制核心装配初始输入并给出资料清单，会话内的上下文变化由执行者使用同一份带版本的装配器代码完成，每次调用前把装配摘要记录为事件。这个做法要求执行者读取知识层与事件流，才能算出当前状态栏目、通知与接触时附加，形成两份装配器。

后果：

- 控制核心与材料之间的往来只有三种：模型调用、环境工具调用、外包 agent 的派发与交回。每条往来带身份，可以记录、去重与重发，对应 ADR-0007 第 1 条。
- 控制核心内部分为流程编排、步骤驱动、上下文装配（P）、裁决规则（U）、事件库与运行状态投影。流程编排只调用步骤驱动的开始、取消与取得结果；步骤驱动只通过 P 与 U 的接口取得请求与裁决结果。`engine.py` 的回调随之取消。
- 控制核心同时驱动多个角色任务，等待模型与工具时不占用其他任务的执行。
- 每一步都要装配、都要读取知识层，投影随事件写入逐步更新并保存；从头重放只用于重建与核对重放一致。
- 外包 agent（[D31](../requirements/outsourced-agent-roles.md)）自己管理会话内的上下文：控制核心只装配它的初始输入；它的工具调用经过 Yudao 的工具，工具许可、接触时附加与查询范围照样有效；每次请求重新计算的当前状态栏目对它无效。
- 分布式部署时，做成服务池的是 Provider、执行环境与外包 agent 的运行容器，控制核心保持一份。
