# 可信内核在自我修改之外，下一个版本由当前运行的已发布版本检查

Yudao 的第三条目的是自举：已发布的版本把 Yudao 仓库当作普通项目开发下一个版本，在此基础上根据运行证据修改自己的组织与规则（[D38](../requirements/system-intent.md)）。基础规则要求被评价者改不了评价标准，可信内核在自我修改之外，并且小到用户本人能看懂。自举以后，发布脚本、评测的评分器与裁决代码都会成为被开发的对象；本机进程能读写实例的事件日志与工件，接口没有访问令牌。决定：

- 可信内核是决定什么成为事实、评价一个版本好坏所用到的全部代码与材料：写入口与事件日志的追加规则、裁决读取的运行状态投影、裁决规则及其调用的合同与协作规则、边界的核对（时间、轮次、深度的计数与停止原因的写入）、定义的加载与结构校验、判定点的准入与记录、内核的不变式测试、评测场景的隐藏检查、参考解法与评分器、发布检查、内核清单与基础规则的文本。流程编排的调度、步骤驱动、上下文装配、知识层、读取模型、应用层、接口层与执行层不属于内核。
- 内核清单列出内核的路径、Python 行数上限、允许的导入（内核文件只导入内核文件、标准库与 pydantic）、每条基础规则对应的测试名称与发布检查的探针。清单由用户所有；行数上限的初值取建立清单时的实际行数，以后只允许下降。内核修改每次由用户经决定请求批准。
- 检查下一个版本所用的裁决代码、评测材料与发布检查，全部取自当前运行的已发布版本。运行的实例从安装的发布包运行，被开发的代码只在项目的运行工作区里；升级实例是一次用户决定。
- 采纳之前，控制核心把交付相对基线的改动路径与运行实例的内核清单比较（路径守卫），有交集时不自动采纳，发出决定请求「内核修改」并附差异。发布检查对上一个发布标签与待发布提交再比较一次，并运行内核差异、行数、导入方向、探针与回归场景，结果写进决定请求「实例升级」。
- 自举项目的执行位置放在控制主机以外的登记机器上；接口加入访问令牌，执行位置上的代码取不到令牌。

理由：

- 用被开发的版本检查它自己，等于让被评价者修改评价标准。编译器用上一个版本编译下一个版本是同一个做法（[D35](../requirements/self-hosting.md) 的分析）。
- 内核只包括决定事实与评价版本的部分。调度与上下文装配出错影响效率与路径，事实仍然经过裁决规则，它们的错误由内核的不变式测试发现；把它们放进内核，内核会大到用户读不懂。
- 行数上限只降不升，迫使与裁决无关的内容移出内核文件。

后果：

- 边界的核对从流程编排中分出来，已用的运行时间写入事件（[ADR-0031](0031-declared-loop-layers-and-sub-loops.md)）。
- 仓库里的发布脚本只负责构建与上传；发布检查由已安装的实例提供。
- 自举第一层的试点期间，Yudao 的成果以合并请求交给现有的审查流程。路径守卫、访问令牌、另一台执行机器与实例提供的发布检查，是成果不经这个流程、由 Yudao 直接采纳之前的条件（[路线图](../program-roadmap.md)）。
- 设计见[可信内核设计说明](../design/trusted-kernel.md)。
