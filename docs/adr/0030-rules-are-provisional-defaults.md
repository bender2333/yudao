# 规则是带理由的暂定默认值，参数在界限以内直接修改

定义是带版本的数据，但只随发布改变（[ADR-0014](0014-versioned-definitions.md)）；应用层没有读取或修改定义的命令；需求记录里的数值大多没有写明理由与可调性，同一个数值常常同时写在需求记录、设计说明与定义里。用户校准的意图是：规则先反复观察到失败再抽象出来，除基础规则以外都是带理由的暂定默认值，由运行证据放松或收紧；每条规则和结构都要付租金，付不起就删除（[D38](../requirements/system-intent.md)）。决定：

- 基础规则写在内核清单里，不进入登记。其余每条规则与数值是暂定默认值，在定义原有的条目上增加四项记录与取值界限：拦截什么、花费多少、放松的证据、收紧的证据，并写明来源。全部暂定默认值合起来就是规则登记，不另建系统。设计说明里的常量（工作上限、栏目上限、校准的样本数、停滞的轮数、执行槽位、各种时限）同样进入登记，数值与理由只写在登记里，文档引用条目名称。
- 每条登记有种类：参数在界限以内由用户直接修改；结构（组织、许可关系、角色、判定点、循环层）走候选、结构校验与用户批准。规则的形式只能是许可、边界、接纳条件三者之一，没有表达顺序的形式。
- 参数的当前值写成事件，带修改者、原值、新值与理由；创建 run 时冻结进这个 run，正在运行与已经停止的 run 不受影响，达到上限的 run 不因为参数修改而继续。每次请求与每次裁决记录定义版本与参数版本。收紧可以由确定的调节规则在界内自动生效；放宽只经对照与用户。
- 对照在采样之前写好约定，在同一组任务上配对运行两个版本；噪声范围来自同一版本的重复运行；结论是改进、无差别、退化三者之一。只影响裁决、阈值、检测与画面的改动，用已有的事件日志离线重新裁决。无差别的改动只在降低成本或删除结构时采用，增加结构的改动必须达到改进。成本（用量与费用、经过的时间、占用用户的次数、检查的执行时间）进入度量与采用规则，不进入运行中的控制。
- 每个阶段结束时做一次规则复查：按事件统计每条规则的触发次数与花费，给出保留、放宽或删除的结论。拦截严重后果的规则（越界写入、未授权的外部动作、内核守卫）不按触发次数淘汰，它们的租金是一条故障注入测试。

理由：

- 规则先于证据写定只会累积；带上拦截什么与花费多少，才能在证据面前放松或删除。
- 修改一个数值需要发布新版本时，改动无法便宜地撤回；参数事件沿用 `run_created` 冻结长期目标与执行位置的做法，重放可以核对。
- 定义里不出现顺序，是防止系统滑向预先写好流转路径的静态编排的判据之一。

后果：

- 应用层增加 `parameter.set`、`definition.propose`、`definition.adopt`、`definition.withdraw` 与 `experiment.start`。
- 由用户发起的参数对照从 Stage 3 结束时开始；由系统提出的候选在 Stage 6。
- 角色清单的增删走结构修改的候选流程。
- 设计见[规则登记与参数设计说明](../design/rules-and-parameters.md)。
