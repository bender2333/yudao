# Yudao 自己的 Git 操作在进程内用 pygit2 完成

Yudao 的版本存储（`harness/git_versions.py`）、公开树的忽略规则判断（`harness/public_tree.py`）与快照的来源核对（`harness/snapshot.py`）都通过启动 `git` 命令完成。一次激活收尾要启动 10 个 git 子进程。在 Windows 上，启动一个进程就要数百毫秒（本机一次 `git rev-parse` 约 490 毫秒），一次收尾空闲时 1 至 3 秒、负载下 5 至 6 秒；一次完整的三部门循环负载下超过 100 秒，其中大部分是进程启动。测试因此变慢，多个测试同时运行时超过等待界限（#107、#214、#219）。#219 实测 pygit2（libgit2 的 Python 绑定）在进程内完成同一次收尾（写对象、提交、更新引用与逐项读回核对）用时 34.7 毫秒。2026-10-02 用户决定：

- Yudao 自己的 Git 操作全部在进程内用 pygit2 完成：版本存储的读写、忽略规则的判断、快照来源的核对。删除这三处的 git 子进程调用。
- 版本库的格式不变，仍是标准 Git 版本库，已有的数据目录不需要转换；用户与外部工具仍可以用 git 命令查看。
- 部门在工作区中运行的 `git` 命令（交付的项目自己的版本控制）不在此列，仍由执行环境按动作运行。

考虑过的做法：

- 继续调用 git 命令，只减少次数：#219 已从 16 次减到 10 次，剩下的成本是进程启动本身，无法再减。
- dulwich（纯 Python 的 Git 实现）：不需要编译，但大版本库上的对象读写比 libgit2 慢，忽略规则的判断与 git 的细节差异更多。pygit2 在 Windows、Linux x86_64 与 aarch64（开发板）上都有预编译的 wheel。

后果：

- 新增依赖 pygit2，写入 `pyproject.toml` 与锁文件。
- 测试里等待一次激活收尾或完整循环的时间降到原来的几十分之一，按 #107 放宽的墙钟界限仍保留，只用来防止一直等待。
- 忽略规则以 libgit2 的判断为准（2026-10-02 用户确认）。外层 `.gitignore` 点名一个具体路径、内层 `.gitignore` 再用 `!` 取回它的写法（例如外层 `sub/keep.txt`、内层 `sub/.gitignore` 写 `!keep.txt`），git 命令行判为不忽略，libgit2 判为忽略，这个文件不进入快照与公开树。这种写法少见，结果只会少收文件。
- 执行代理（[ADR-0018](0018-single-control-host-remote-execution.md)）在远程机器上不使用版本存储，不受影响。
