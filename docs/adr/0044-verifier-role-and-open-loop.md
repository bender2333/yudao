# 核验是角色的性质，固定结构只剩循环、边界、裁决

状态：有效；依据：用户在 `/grill-with-docs` 里的决定（方案出处：分支 `plan/verification-as-node` 的 `docs/plan-verification-as-node.md`）。

用户的目的是让同一套底下的层能退化成单 agent、普通多 agent，往上是三部门，再往上是部门内的子组织与观察者，而且各种形态复用同一套抽象。此前「独立的证据」是第四样固定结构，质检的规矩按部门名写在装配、执行、记录与内核的一行里，任务池又自己写了一份判定部门；换一种形态就要改这些共用的地方。

决定：

- 固定不变的结构只剩循环、边界、裁决。独立的证据是可以填进去的内容，由**核验角色**取得。
- 分四层：事实与裁决只认通用的说法（事项、事件、某种成果的某一版及其依据、提案、回执、角色的写入范围、上限、决定请求），不认部门种类、PRD、放行；循环只认一轮工作，谁开工、怎么结束都问路由；路由各写轮转的规矩；组织（定义）填部门与角色。任何形态都只换下面两层。
- 核验是角色身上可以声明的性质，只有一套：只写检查材料、在独立副本上由主机跑检查、先看事实再看解释、结论绑定当前版本。任何路由放进一个核验角色就有核验。
- 定义里没有核验角色的事项交了完成就按流程采纳，不因为缺少核验发决定请求，记为**开环完成**，记录、页面与报告上不写放行。
- 外包不要求下游有核验角色。最差的配置是一个外包角色直做，等于跑一次外面的 agent（例如 OpenCode），Yudao 仍守快照进出、上限、写入口与开环完成的标记。
- 部门内的多角色与分形只用子事项这一种机制；观察者不做部门。

考虑过的另一种做法：核验写成成果驱动这一条路由自己的规矩，通用的角色定义里不出现核验。没有采用：每一条要核验的路由都得再写一份，任务池已经是第二份；用户要的是复用。

代价：角色定义多了两项，多数角色用不到；成果驱动继续写它原来的那几种接纳事件以保住已有的事件序列，内核要同时认通用接纳与这几种老事件，直到它们只剩读取；开环完成的交付会进项目代码，靠标记而不是门挡住「看起来像核验过」的误读，自举不用开环的配置。
