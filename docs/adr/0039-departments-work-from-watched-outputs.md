# 部门按关注的成果开始工作，询问链允许回问

[ADR-0036](0036-concurrent-departments-and-nested-asks.md) 让三个部门同时运行、询问成为嵌套的调用，但保留了外层的交接：同一事项同一时刻只有一个部门持有交接，控制核心按阶段状态机决定下一个持有交接的部门；询问链上一个部门只出现一次。2026-10-14 用户与架构师讨论 #488、#489：交接的每一步都能从成果的依据推出——交付必须写明依据的 PRD 版本，结论必须写明核验的交付，每块内容只有一个写入者，只有质检的放行结束事项；阶段状态机却把部门写死在代码里（`harness/models.py` 要求定义中的部门与阶段相同），与「部门是填进结构的内容」相反。询问链「只出现一次」的规则挡住了正常的回问，而回问另开分支不会互相等待，用量逐层递减已经保证链会结束。决定：

- 每个部门关注一组成果，写在组织定义的数据里：产品关注用户的输入与发给它的指导；工程关注 PRD 的新版本、针对它最新交付的缺陷记录与发给它的指导；质检关注 PRD 被接纳、新的交付与发给它的指导。关注的成果有了新版本、部门在等待工作时，控制核心让它开始一轮工作；一轮工作以提交正式成果或回答用户结束，然后部门等待工作。
- 控制核心记录事件、提交时核对依据的版本、送达通知、让部门开始一轮工作、处理取消、暂停与上限，不决定下一个轮到哪个部门。阶段状态机与交接删除，事项进行到哪一步从成果推算。
- 质检的结论只有缺陷记录与放行；要求有问题时质检询问产品，产品在回答里修订 PRD。
- 用户的指导是接收部门关注的成果：部门正在一轮工作中时作为通知送达，在等待工作时以这段指导开始一轮工作；以用户为提问方的询问分支删除。
- 询问链允许回问：回问在被问部门那里另开一个询问分支，不送进它正在等待的会话。链的层数上限是规则参数 `organization.ask_chain_max_depth`，默认 3；用量逐层递减并计入最初的提问方。不另设拒绝或转交的返回格式。
- 不变：只有质检对当前 PRD 与当前交付的放行结束事项；每块内容只有一个写入者；提交时核对依据的版本；放行等发给产品的输入处理完；一个事项一条事件流。

理由：

- 成果之间的依赖本身就决定了谁能开始工作，单独的状态机是重复的事实来源；去掉它以后，循环来自部门之间的成果，部门成为数据中的内容，增加或调整部门只改组织定义。
- PRD 改了以后工程立即开始返工，不用等质检核验完旧交付再交回；用户对正在等待的部门的指导可以立即动手，询问分支里的工程不能改运行工作区。
- 一个部门提交以后等到关注的成果变化才开始下一轮，不会接连提交新版本让别人的结论过期。
- 写入口在另一方先写入时按最新状态重新判断再提交，多个会话写同一条事件流不需要拆分。
- 回问另开分支，分支与正在等待的会话互不等待，不会死锁；层数上限把最坏情况的花费限制在几层以内，作为规则参数可以按记录调整。

考虑过的做法：

- 保留交接，由控制核心按状态机决定下一个部门。正确，但部门写死在代码里，PRD 变化与用户指导都要等持有交接的部门让出。
- 三个部门一直运行，不等待。模型没有新信息时空转花钱，部门可能接连提交新版本，让别人的结论总是过期。
- 询问链只靠用量递减结束，不设层数上限。会结束，但两个部门来回追问几十层、每层装配整个部门历史的花费太高。
- 询问链加「无进展检测」。要再做一次判断，复杂且容易误判。

后果：

- [三部门的循环结构](../design/department-loop.md)第 2、3、4.4、5、6、9、10、11 节，[部门指导的处理设计](../design/department-guidance.md)，术语表的「交接」「持有交接」改为「关注的成果」「一轮工作」，轨迹的「交接」一层改称「一轮工作」。
- 取代 ADR-0036 中「交接与完成只由控制核心决定」「一个部门在同一条询问链上只出现一次，三个部门时链最长两层」「询问链规则由结构限定深度，不需要另设数字」三处；ADR-0036 的其余决定不变。
- 工单 #473、#474 与从 #474 拆出的工单、#475、#476、#477 按本决定修改。
