# 控制核心逻辑上只有一份并持有执行权，执行层与观察者可以扩展

Status: 「为可用性做主备」「Stage 6 为执行权加入期限与续期」「需要时按项目把 run 分给多个控制核心实例」「服务端数据库的选择在 Stage 6 按故障场景与总成本比较」由 [ADR-0018](0018-single-control-host-remote-execution.md) 取代：控制核心、事件日志、工件存储、Provider 模块与观察者在一台控制主机上运行，事件日志使用 SQLite，执行权没有期限与续期；「后果」中路线图 Stage 6 与 D29 的理解改为 3.2C 执行环境服务把执行环境分布到登记的机器上。其余决定继续有效。

路线图与 [D29](../requirements/remote-execution.md) 设想把部门或角色做成独立服务、以集群方式部署；[ADR-0010](0010-control-core-drives-role-steps.md) 规定每次模型请求在控制核心装配、自有角色的步骤由控制核心驱动。两者需要统一部署单位，并定义 [ADR-0007](0007-boundaries-for-distributed-deployment.md) 第 3 条中持有执行权的「执行者」。决定：

- 控制核心（编排器、步骤驱动、上下文装配、裁决规则、写入口）在逻辑上只有一份，为可用性做主备。它持有每个 run 的执行权，执行权编号在写入口与领域写入一起核对；Stage 6 为执行权加入期限与续期。
- 可以扩展的是执行层（执行环境、Provider、外包 agent 的运行容器）与观察者（教训发现模块、元观察、演化模块等）。部门的身份（权威位置、装配规则、私有历史）保存在控制核心，部门不单独部署成服务。元观察在组织上是一个部门，运行时是一个观察者加判定点。
- 需要时按项目把 run 分给多个控制核心实例，每个实例持有自己那部分 run 的执行权；结构不变。
- 不引入外部工作流引擎。控制核心本身就是按事件重放的状态机，会话可以丢弃，恢复时从已提交的状态重新装配。
- 从现在起可以引入接口服务（[ADR-0015](0015-desktop-client-and-http-contracts.md)）与执行环境的容器实现。服务端数据库的选择在 Stage 6 按故障场景与总成本比较，事件日志的接口不变（[ADR-0013](0013-event-log-and-single-write-path.md)）。

本决定取代 ADR-0007「后果」中的两条：「Stage 6 之前不引入消息队列、网络服务、新的数据库或容器编排」与「Stage 6 的运行方式在该阶段决定」。ADR-0007 的六条边界继续有效，作为服务之间的合同。

理由：

- 控制核心的裁决不使用模型，每一步的工作量很小，负载在等待模型与工具；拆成多个服务会把 U 与权威关系分散到多处。
- 按部门拆分部署得不到新的独立性：部门之间的隔离来自装配规则与可见范围，这些都由控制核心执行。部门需要靠近的环境与权限，由执行环境的服务池提供。
- 外部工作流引擎的核心能力是让执行到一半的代码接着运行，Yudao 用不上；引擎的执行历史会成为事件库之外的第二份事实。
- [系统架构原理](../design/architecture/core-and-materials.md)第 7 节的分析。

后果：

- 跨网络的往来只有：模型调用、环境工具调用、外包 agent 的派发与交回、判定点、观察者的订阅与提案、客户端的命令、查询与事件流。每条往来带身份，可以记录、去重与重发。
- 路线图 Stage 6 与 D29 中「部门部署到不同的服务器」按本决定理解：部门需要的执行环境与 Provider 部署到不同的服务器，部门的控制留在控制核心。
