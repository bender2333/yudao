# 网络取回与登记的 MCP 服务器固定在控制主机上运行

代码在 run 的执行位置上直接运行，执行环境服务有本机进程与远程执行代理两种实现（[ADR-0018](0018-single-control-host-remote-execution.md)、[ADR-0022](0022-run-directly-without-containers.md)）。3.2B 新增两类动作：网络取回与项目登记的 MCP 服务器的工具调用。原计划把它们和读写文件、登记的命令一样放在 run 的执行位置上。2026-10-01 用户逐轮采纳推荐，决定（[设计说明](../design/network-and-mcp.md)）：

- 网络取回与登记的 MCP 服务器在控制主机上执行，与 run 的执行位置无关：执行位置是一台登记的机器时，这两类动作仍然在控制主机上进行，执行代理不实现它们。
- 它们仍然是动作类别：经过同一份动作合同（动作身份、尝试、回执、结果未知的核实），由执行环境服务的本机进程实现提供。动作类别按放置分两种：随 run 的执行位置（读写文件、登记的命令、检查、试用会话、浏览器与屏幕动作），固定在控制主机（网络取回、登记的 MCP 服务器）。
- 3.2D 的 Playwright MCP 是试用工具，随试用会话在 run 的执行位置上运行，使用 3.2B 的 MCP 客户端模块，不经项目登记。
- MCP 服务器的凭据只在控制主机：登记里只写凭据名称，不发给执行代理。
- 需要读写工作区的能力由内置的文件工具与登记的命令提供。必须运行在登记的机器上的 MCP 服务器（例如操作板上硬件的服务）不支持，这类能力由登记的命令或 Stage 4 的外部动作提供。

考虑过的做法：

- 随 run 的执行位置运行（原计划）。执行位置是开发板时，开发板要能联网、安装 Node 与 uv，执行代理里要带取回与 MCP 客户端，登记的凭据还要发到开发板，与「模型凭据只在控制主机」的规则冲突；远程的调用还要加心跳与迟到回执的处理。
- 每个 MCP 服务器登记一个运行位置。登记多一个字段，执行代理要实现 MCP 客户端与凭据的传送，而现在没有需要在登记的机器上运行的 MCP 服务器。

理由：

- 取回与外部服务不读写项目的工作区，运行位置对结果没有影响。
- 凭据留在控制主机，与模型凭据遵守同一条规则。
- 执行代理保持小，开发板不需要联网，也不需要安装 Node 与 uv。
- 动作结果未知只出现在控制主机的进程中断时，没有心跳与迟到回执。

后果：

- 总体架构第 7.3 节表中「网络取回、MCP 工具」的执行环境由「本机或执行代理」改为「控制主机」；#68、#69 中「在执行环境中启动」改为「在控制主机上启动」。
- 3.2B 的动作不进入执行代理；执行代理需要 MCP 客户端模块只为 3.2D 的 Playwright MCP。
- 登记的 MCP 服务器是第三方程序，以运行 Yudao 的账户的权限运行，与登记的命令相同，Yudao 不提供操作系统层面的沙箱（ADR-0022）；子进程的环境变量只有登记里写明的变量与操作系统运行所需的基础变量。
