# 组织、角色、动作、本体与规则作为带版本的定义

角色清单、本体、判定点、预置表都写明「随系统版本发布，变化属于 Stage 6」；Stage 6 要求候选在限定范围内采用、可以撤销，并追踪规则变化对经验与事项的影响；现在部门 Prompt、协作规则、提案合同与工具定义写在代码里，停止原因有两套。决定：

- 以下内容作为带版本的定义，用 pydantic 校验，随系统发布：
  - 组织：部门、角色、谁能拒绝谁、交接与询问规则、事项种类（交付事项、运维事项等）；
  - 角色定义：Prompt、工具、可见范围、栏目、执行者种类（自有或外包）；
  - 动作与工具定义：类别、契约、许可规则；
  - 提案合同、本体、判定点、技能；
  - 限额与参数、停止原因（一份封闭的清单）；
  - 服务方案预置表（[ADR-0003](0003-versioned-preset-table-no-remote-refresh.md)）。
- 每个事项记录它使用的定义版本；每次模型请求与每次裁决记录所用定义的版本。
- 运行中任何 agent 与观察者都不能修改定义。定义只在发布新版本时改变，或在 Stage 6 经用户批准、在限定范围内采用新版本。

理由：

- 权威拓扑是设计时的常量（[Loop System 原理](../archive/native-harness/loop-system-principles.md)第 9 节），带版本的定义让它在运行中不可协商，同时让 Stage 6 的演化有明确的对象：候选就是定义的新版本，隔离比较就是按指定版本运行事项，撤销就是换回旧版本。
- 预置表已经证明这种做法可行：数据加版本，界面显示版本与来源。
- 每次裁决记录定义版本，重放与审计才能说明当时按哪一套规则判断。

后果：

- 部门 Prompt、协作规则、提案合同、工具定义与限额从代码移到定义中；新增部门、角色、动作类别、判定点与技能，等于增加定义。
- 用户在项目部门设置中修改的 Prompt 与模型属于设置，不属于定义。
- 停止原因只有定义中的一份清单。
