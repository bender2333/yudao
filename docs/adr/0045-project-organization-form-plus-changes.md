# 项目的组织是一份形态加本项目的改动

状态：有效；依据：用户在 `/discuss` 里的决定（[决策记录](../decision.md)「2026-11-02 - 项目上的组织：形态加本项目的改动」）。

总图把三部门写成填进结构的一种内容：最少一个部门一个外包角色，最多 N 个部门、观察者与部门内角色分形。用户要能在自己的项目上看清并改动这些安排，模型管理这类系统配置保持通用。

决定：

- 一个项目的组织由发布带的一份形态加本项目的改动合成。改动按部门、角色、成果种类与观察者的身份只写不同的项，其余跟随发布。合成结果过同一套结构校验，新建事项时整份冻结进事实。
- 部门的身份与显示名分开，改名只改显示名。
- 用户在自己的项目上采用一份组织，经结构校验与用户确认就生效，范围只有这个项目，不经对照。对照与限定采用管发布的默认形态和系统提出的候选。
- 组织决定事项怎么走，按事项冻结；模型、推理档位与 Prompt 只影响下一次模型请求，留在项目部门设置与项目角色设置。
- 新建事项时可以临时选发布带的一份形态，项目的组织不变。
- 自己加的部门不进全局的部门默认，模型写在本项目。

考虑过的另一种做法：项目整份复制一份定义再改。没有采用：发布会一直改工具、提案合同与内置材料，复制出来的定义会悄悄变旧，还要另做一套升级对比。OpenCode 与 OMP 也是内置 agent 加项目按名字覆盖（OpenCode `fe8cd6596f` `packages/core/src/config/plugin/agent.ts`，OMP `338d2ce665` `packages/coding-agent/src/task/discovery.ts`）。

代价：发布改了形态，跟随发布的项目下一个事项就用上新内容，事先不问用户；发布的改动与本项目的改动合不到一起时，新建事项被拒绝，要用户处理。合成规则、身份与显示名的分开要进定义的格式，这是只增的合同。
