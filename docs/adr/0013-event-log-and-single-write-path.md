# 一份事件日志：全局位置、流版本与唯一写入口

现在事件按 run 编号存放，项目事件另有一张表，投影在每次调用时从头重放，写入分散在编排器、提交与交互三处。[D25](../requirements/semantic-system.md) 的内容有效期要在事项之间比较，界面需要跨项目的事件流与缺口检测，[恢复契约](../design/recovery-contract-and-fault-matrix.md)第 3 节要求执行权与领域写入在同一个事务中核对，D25 要求同名实体只能新建一个。决定：

- 只有一份事件日志。每条事件有全局位置（跨项目单调递增）、所属的流（项目、事项、run 等）与流内版本。
- 所有写入只经过一个写入口。写入口在同一个事务中完成：核对执行权编号，核对流版本，接收 U 的裁决结果，追加事件，更新投影。
- 投影保存下来，随写入逐步更新；从头重放只用于重建与核对重放一致。
- 读取方按全局位置订阅，写入以后在进程内通知订阅方。
- D25 的有效开始、有效结束与按事件位置回答「当时哪些内容有效」，使用全局位置。

理由：

- 一个写入口可以在一处实施执行权、流版本、本体校验与唯一性约束，恢复、并行采纳与语义系统共用同一个保证。
- 全局位置同时满足跨项目的事件流、缺口检测、快照与事件的对应，以及跨事项的有效期比较。
- 投影保存以后，每一步装配与查询不再随事件数量变慢。
- 事件存储采用追加时核对期望版本的做法（EventStoreDB、Marten 等），分布式锁需要随写入核对的递增编号（fencing token），见 [ADR-0007](0007-boundaries-for-distributed-deployment.md) 的理由。

后果：

- `events` 与 `project_events` 合成一份日志；按 run 的序号由全局位置与流版本代替。现有数据不迁移。
- 编排器、提交与交互中的写入都改为经过写入口。
- 事件流按全局位置推送，断线后按位置补齐；界面的快照查询返回它对应的全局位置。
- 事件日志使用 SQLite（WAL），保存在控制主机上（[ADR-0018](0018-single-control-host-remote-execution.md)）。
