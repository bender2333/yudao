# 项目流跨 Yudao 版本保存，run 流跟随应用版本

状态：有效；依据：[D27](../requirements/operations-department.md)；路线位置：各阶段通用。

长时间运行要求一个项目跨越 Yudao 的多次升级持续存在：运维部门要知道登记的运行环境、常设授权、上一个放行版本与故障的历史，才能部署、回滚并判断同一个故障（[D27](../requirements/operations-department.md)）。一次升级如果改变了事件格式、让旧版本的事件不能再读取，项目的长期事实就丢失了。2026-09-28 用户采纳本决定。决定：

- 事件日志中的流分两类。项目流记录项目的长期事实：登记的运行环境与常设授权、放行版本历史与当前部署的版本、故障记录、事项队列、当前 PRD 与采纳成果，以及语义系统写入的跨事项内容：项目的要求集合（要求类条目与要求编号）、各部门的画像、知识、实体、已采纳事项的图谱、后续事项读取的已采纳与未采纳事项的内容，以及改变这些内容状态的记录（[语义系统设计说明](../design/semantic-system.md)第 4 节）。事项的进行过程在项目流中只记录它的存在、在队列中的位置、关联的故障记录与最终结果（采纳成果或放弃原因）。事项内部每次 run 的询问、尝试与动作属于 run 流；语义系统中只在一次 run 中使用的内容（事项层以下的轨迹、尝试整理、接触时附加、压缩检查点）也属于 run 流。
- 机器流：用户在系统中登记的每台机器一个流，记录机器的登记与修改（名称、地址、用途）。机器由多个项目共用，不属于任何一个项目，与项目流一样是长期事实，按下一条的规则跨版本保存（2026-09-29 用户决定，[执行环境服务设计说明](../design/execution-environment.md)）。项目对机器的授权属于项目流。
- 项目流与机器流跨 Yudao 版本保存。新版本只能增加字段、事件种类，或者给已有字段增加取值（原有取值的含义不变），已有字段的含义不变；新增字段在事件种类的定义中写明旧事件的缺省含义。需要改变含义时定义新的事件种类，旧种类继续可以读取。项目流与机器流事件种类的字段与取值登记在一份清单中，删除字段、删除取值或改变字段类型时测试失败。
- run 流跟随应用版本。每个 Yudao 版本声明自己的 run 事件版本。
- 升级时 run 事件版本相同：直接重新启动，按[恢复契约](../design/recovery-contract-and-fault-matrix.md)自动继续。run 事件版本不同：先排空，Yudao 停止开始新事项，等正在进行的 run 结束（最长受运行时间上限约束），再升级。用户可以强制升级：正在进行的 run 记为因升级停止，对应的事项用已采纳成果重新开始，排在队列最前面。旧版本的 run 事件保留供查阅，不参与继续执行。

事件日志只有一份（总图第四节「写入口」缝），两类流按流的种类区分，写入口与全局位置不变。

理由：

- 项目的长期事实数量少、变化慢，只增加字段就能满足演化；这是事件溯源系统常用的弱模式做法（Greg Young，《Versioning in an Event Sourced System》），不需要转换代码。
- 升级前导出、升级后导入一份项目档案，每次格式变化都要写导出与导入，实际上是迁移；放弃项目历史则要求用户在每次升级后重新登记环境，运维也失去放行历史与故障记录。
- run 内部的过程数量大、变化快，结果已经进入项目流，随版本停止读取对长期运行没有影响。

后果：

- [恢复契约](../design/recovery-contract-and-fault-matrix.md)的版本规则按本决定：不兼容只针对 run 流。
- 项目流事件的新增字段需要写明缺省含义，事件种类的设计要比 run 流更谨慎。
- 语义系统的项目流事件种类同样登记在字段清单中；本体对这些内容只增加种类、关系与字段（[语义系统设计说明](../design/semantic-system.md)第 4、5 节）。
