# 画面只认画面合同，播放节奏归画面：事实来自查询，状态等它之前的动作演完再上画面

用户 2026-10-24 给出与 Sonnet 讨论的可视化方案（事件时间与叙事时间解耦、缓冲队列加最小播放时长、堆积时的取舍、播放节奏属于可视化自己），要求结合视图同步把这部分重构，并说明：「事实只来自数据库，画面的独立是指，怎么画出来，表现形式需要与数据库解耦合的，比如之前的缓冲层就是可视化部分自己的内容」。

此前的结构（[ADR-0021](0021-client-pixel-view-follows-v9-structure.md)）：React 把查询结果交给画面（`setModel`），把事件交给画面（`playEvent`）。核对 main 时看到：排队与取舍在楼、楼层、房间各写一份；画面驱动按 Yudao 的事件种类分支，画面数据与查询字段一一对应；事件立刻演，重新查询的结果约 0.3 秒后整体替换状态，状态跑在动作前面，房间的状态变化还会打断正在演的动作；楼层把服务端的 `in_progress` 当成不认识的状态，进行中的事项不进房间；画面诚实性的不变式在客户端没有测试。详见[画面与播放设计说明](../design/visualization.md)第 1 节。

决定：

- 客户端在同步层（视图同步，不变）与画面之间加翻译层。画面层只认画面合同：状态（此刻画面上该有什么）与动作（发生了什么，用来演），都用画面自己的说法，都带位置；另有决定卡片与流式文字两样实时内容，以及交出用户操作的回调。画面层不导入 Yudao 的任何代码，不发命令。
- 事实只来自数据库：翻译层把查询结果翻成状态，把事件翻成动作，不累加事件得出事实。服务端状态值到画面状态的对应只写在翻译层。每种事件在每个场景要么翻成动作，要么写明不画，由测试核对。
- 播放节奏属于画面：动作分关键、普通、进度三级，级别与时长写在每个场景的声明表；状态等位置不大于它的动作演完再上画面；画面最多落后 5 秒（暂定），超过时普通动作丢掉、关键动作缩短、同类合并；打开、重新同步与从后台切回时直接跳到最新；决定卡片与流式文字不等。
- 画面是同一个客户端里的独立模块，不拆成单独的包或应用；服务端的接口合同不变，不为画面新增查询或事件流。
- 原型先行：原型 v13 实现翻译层与播放时间线，定稿以后客户端照做。客户端工单进里程碑 M0.5。

理由：

- 画面只吃事件、自己累加状态，要在客户端再写一份 Yudao 的业务规则，Yudao 每改一次画面就跟着改，反而不独立；打开与重新同步时仍然需要快照。事实只在服务端算一次。
- 状态等动作演完：画面讲的故事顺序正确；每个上画面的状态都是数据库在某个位置真实有过的状态，落后有上限，画面不失真，回放一致（H7）照样成立。
- 翻译只写一处：Yudao 新增事件种类或改字段只改翻译层；楼层的缺陷说明同一个对应写在几处就会漏。
- 节奏要看到效果才能判断，原型里调；客户端跟原型走，录制的核对链条保持完整。
- 单独的包或应用现在只有一个使用方，换不来它的成本；画面合同是唯一边界，以后拆只是搬代码。

后果：

- 新的[画面与播放设计说明](../design/visualization.md)；应用层与接口层设计说明第 5.8 节的不变式移到它的第 8 节，第 5.7 节写明像素画面经翻译层取得状态与动作。
- ADR-0021 继续有效，状态一栏补一行：从原型 v13 起，传给画面的是画面合同。
- 画面最多落后 5 秒；客户端多一层翻译。
- #477 中像素画面同时显示几个部门工作与询问的一条移出 M0，与「客户端跟上 v12」一起进 M0.5 的画面工单；在那之前 M0 的试用只能从页面文字看出几个部门同时工作。
- 撤回这个决定要改原型、客户端与测试。
