# 用独立下游核验的有无，判断意图与权威变更要不要阻塞等待用户

目标、约束、验收标准来自用户的意图；组织的权威关系（谁能拒绝谁）属于 [ADR-0014](0014-versioned-definitions.md) 的组织定义。两者都只能经用户批准改变，不能由部门或者模型的输出自行宣布，这一点不在讨论范围内。没有说清楚的是：意图或者权威关系里出现含糊、出现矛盾的地方，要不要在往下做之前停下来等用户回答。一律不停，含糊之处可能被系统自己的判断悄悄定型；一律先停下来问清楚，Yudao 达不到长时间运行的能力，并且把决定的重量转嫁给用户，跟无条件采纳用户的第一句话是同一类问题换了个方向——一个用批准做掩护，一个用追问做掩护。

决定：

- 遇到含糊、又存在独立的下游核验能够挡住错误判断的地方（例如需求的某种读法是否选错，质检的测试能够验出来），不阻塞：产品部门按合理判断选一种读法，立即驱动工作，选择本身记入事件，事后可以修正。
- 遇到没有独立下游核验能够挡住错误判断的地方——读法之间互相矛盾，没有测试能说明该信哪一条；或者变更会影响权威关系里谁在信任链末端（[核心与材料](../archive/design/architecture/core-and-materials.md) 第 8 节「可以外包的判据」用的是同一条标准）——经[总体架构](../design/architecture/overall-architecture.md)第 7.4 节的用户决定这条合同向用户提出请求，并按合同的阻塞范围尽量不阻塞，只阻塞受影响的那个动作、角色任务或者 run，不整份意图或者整个组织定义一起等。
- 组织的新版本在采纳前，裁决规则 U 额外校验权威关系的结构：信任链不能出现循环；至少留一个角色的放行依据来自独立产生的证据，不是另一个模型的意见；目标、约束、验收标准无论经过多少层部门，最终都能追溯到用户。三条有一条不满足，这份提案被拒绝。

理由：

- 「有没有独立的下游核验」是原理里已经用过的标准——第 8 节判断一个角色能不能外包，用的正是这一条。用同一把尺子判断要不要停下来等用户，不需要另外发明一条规则。
- 一律先问清楚才生效，等于把决定的重量转嫁给用户，并且让循环没办法在没有操作者的时候运行，这跟「循环可以在没有操作者的情况下长时间运行，每一次停止都有明确的原因」（[核心与材料](../archive/design/architecture/core-and-materials.md) 第 4.2 节）相违背；停止要有原因，含糊本身不构成这个原因。
- 一律不问、无条件采纳系统自己的判断，会让「U ≠ f」在意图与组织这两层失守：系统的产出反过来定义它要满足的目标，或者反过来定义它该向谁负责。

后果：

- [核心与材料](../archive/design/architecture/core-and-materials.md) 第 2 节「四条不变量」与第 3 节「人留在意图这一层」按本决定改写，权威拓扑不再作为独立于组织定义之外的常量出现。
- [总体架构](../design/architecture/overall-architecture.md)第 7.4 节的用户决定合同不需要新增字段，「阻塞范围」这一项在意图含糊与权威变更这两种场景下同样适用。
