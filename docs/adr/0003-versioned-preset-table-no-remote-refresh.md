# 预置表数据驱动且版本可见，不做远端自动更新

服务方案预置（按协议的请求基址、认证方式、模型列表地址、文档链接、必需请求头）会随上游服务的变化而过时，需要一种增长方式。决定：预置是 Provider 模块内的一份数据文件，每个服务方案一行并带来源链接，整张表带 `revision`，界面显示 revision 与来源；新增服务方案等于在文件中新增一行，随新版本发布生效。模型能力表是同一模块内的另一份数据文件：发布前由提取脚本从 models.dev 取出预置服务方案下各模型需要的字段生成，带 revision、快照日期与来源，同样随新版本发布。两份表都**不做**运行时的远端自动更新，也不设兼容性基准版本。

理由：cc-switch 把 50 多个预设写在 60–106KB 的 TS 文件里，模型改名与能力更新靠人工跟进，更新滞后是它公开承认的问题；LiteLLM 采用相反的做法，每个进程启动时从 GitHub main 下载能力表，并通过接口公开 `source_revision`。Yudao 目前只接入 OpenCode Go，不需要远端下载流程，但「我现在用的是哪一版表」必须能回答。

后果：预置表过时需要发布新版本来更新；界面必须显示 revision 与来源，让用户能判断手上的表是否已经过时。预置表只含接入规则，不带模型、容量、推理档位或准入；这些由模型访问定义与模型测试负责。模型能力表只用于预填模型访问定义的窗口、输出上限与输入方式；Yudao 信任它的记录，记录有误时替换来源，不在准入中核实（[模型管理设计说明](../design/model-management.md)第 4.1、4.3 节）。
