# 采纳写回以三份代码树合并变更

状态：已确认（2026-10-08）。适用范围：3.8 接入已有项目的采纳写回（#347、B8）。

## 背景

Yudao 的项目从接入快照独立演进。采纳写回发生在事项运行期间，源仓库的目标分支可能已经被其他提交推进。若直接把采纳时的完整代码树写到目标分支，可能删除目标分支在运行期间新增的内容；若直接把目标分支复制到结果，也可能丢失本事项产生的删除与修改。

## 决定

采纳写回只写回本事项相对其起点的变更。写回使用三份代码树：

1. **起点树**：本事项创建时绑定的 `code_tree_digest` 与 `tree_ref`。
2. **采纳树**：质检放行并被采纳的交付快照，绑定 `code_tree_digest`、`tree_ref`、`run_id`、定义版本和参数版本。
3. **目标树**：写回动作开始时从目标分支读取的提交与公开树摘要。

建档确认的第一次采纳只建立起点，不产生写回。普通事项的变更已经全部出现在目标树时，记录「无需写回」与依据；不建立空的分支或合并请求。

主机使用 pygit2 的三方合并，显式以起点树为基准，把采纳树的变更与目标树合并，生成写回树；合并请求的差异基于目标提交。一次写回准备冻结一份目标提交。最终树核验完成后、推送前重新读取目标分支，提交改变时记录 `target_changed` 并停止本次准备；重新发起时按新目标合并核验。写回检查采用项目冻结的检查时限，超时记录失败。合并请求创建以后目标分支再推进时，由独立审查与集成核验确认实际合并结果。

应用变更集出现内容冲突、删除与修改冲突、路径类型冲突或目标树无法表示时，写回停止，记录冲突工件与三份摘要，不推送分支，不创建合并请求。解决冲突以后由用户或后续事项重新发起写回，重新读取当前目标树；系统不自动选择一侧内容。

同一项目的写回按采纳顺序进行。当前事项的起点依赖上一项采纳时，上一项写回必须已经合入目标分支；核实依据是实际合并提交与请求身份，允许目标仓库的 squash 合并方式。否则记录等待前项写回，保留此次采纳，不创建依赖缺失的分支。用户在原项目继续提出事项时，工作区仍按项目自己的采纳链演进，源仓库的独立变更只在写回合并中读取。

写回树生成以后，主机在可以丢弃的检查副本中运行项目登记的写回检查，覆盖本次变更与原有行为；原交付与项目基线中已登记的检查都包含在这份命令清单中。每项命令回执绑定最终写回树摘要、实际 argv、退出状态和输出工件。清单为空、检查未运行、超时或失败时停止写回，不推送、不创建合并请求。原放行仍绑定采纳树，最终写回树的核验回执单独保存；合并请求仍经过独立审查与集成验证。

起点树、采纳树、目标提交及其树、最终写回树、核验回执、写回分支和合并请求身份全部写入事件和工件。目标提交里不属于事项公开树的文件保持原样，不进入本事项的变更集。公开树中的文件删除与可执行标记按树清单处理。

外部动作按已有动作契约处理：写回身份由采纳身份与命令身份确定，分支名和合并请求中保存这条身份。推送或创建合并请求的结果未知时先核实远端分支、提交与请求身份，核实以前保持待核实；远端已有对应结果时记录核实事实，同一身份只产生一个分支与一个合并请求。源目录中的未提交修改保持原状，写回在独立目录中进行。

## 后果

- 写回保留目标分支在事项运行期间的独立提交，并保留本事项的新增、修改与删除。
- 采纳快照、写回目标提交与最终写回树各自有摘要，重放和审查可以区分三者。
- 冲突成为可观察的失败结果，不能被“选择当前分支”或覆盖文件的方式隐藏。
- #347 的本地裸仓库验收需要增加目标分支推进、删除与冲突场景；真实 GitHub 合并请求只在自举试点中验收。
