# 设计与实施分离：设计说明不记状态，易变的一方反向引用设计

状态：有效；依据：用户在 `/grill-with-docs` 里的决定。

此前的设计说明夹着实施状态（未实施、已实施）、工单号、代码名和行号，代码一动就过期；2026-10-29 全量扫描的问题大半来自这里。用户决定把设计和实施分开：

- 设计说明回答一个功能「怎么做」：方案、边界与范围、接口、流转与失败处理、公式与常量及理由、验收，配简单模块图和包图。详细到可以直接当父工单用；不写状态、工单号和详细的实现（代码名、字段名与类型、路径、行号）。写法见[设计说明规范](../agents/design-spec.md)。
- 依赖方向反过来：设计说明稳定，工单、代码注释、规则登记的 `origin` 经常变，所以由后者引用前者，设计说明不引用它们。引用写「文档路径 + 小节标题」，不写节号和行号。设计说明可以指向需求记录、ADR、总图、其他设计说明、对照表与调研数据。
- 进度只在 GitHub 的里程碑、工单和 git 里。每份设计说明的改动记在自己文末的变更记录里，不再写 `docs/CHANGELOG.md`。
- 常量由设计说明写默认值、范围和理由，规则登记照着实现，运行中的现值是参数事件，与文档无关。

考虑过另一种做法：设计说明只留意图和两张图，流转、失败处理和公式移到测试与规则登记里。没有采用：测试最后才有，实现之前这些规矩无处放；测试读不出为什么；需求方也没法 review 测试代码。

代价：行为规矩只在设计说明里写一遍，没有第二份；设计说明比「只留意图」长；工单正文变薄，验收标准取自设计说明的「验收」一节；现有的设计说明要逐份补到模板（边界与范围、接口、验收三节），补完之前新旧写法并存。
