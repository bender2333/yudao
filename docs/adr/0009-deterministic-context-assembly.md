# 上下文组装按结构关系与固定规则进行；需要判断的选择在声明的判定点做、先写成事件；不使用向量检索

每次模型请求时，主机要从轨迹、图谱与材料中选出内容交给角色（[语义系统设计说明](../design/semantic-system.md)第 10 节）。决定：选择按结构关系与固定规则进行；需要判断的选择（挑哪些上下文、含糊的读法）只在定义里声明的判定点做，可以问一个小模型，判断的依据与结果先写成事件，装配再读这条事件；重放时读事件，不再问模型。不使用向量模型做选择；角色按需查询时只用结构条件与 SQLite FTS5 trigram 全文检索。需要判断的工作放在写入一侧：复盘时写画像，教训发现模块找出教训与洞见，记录事实时用 JEV 核对证据；组装只读取这些已经记录的结果。

理由：

- 同样的事件得到同样的请求内容，每次请求可以重放，上下文清单能为每条内容写明放入原因。
- 每次请求不增加时延与失败点。
- 用户明确语义系统不是 RAG。图谱中的内容通过焦点、实体与关系相连，结构关系已经能选出与当前工作相关的内容；Claude Code 用 glob 与 grep 即时查找代码，避开了索引过期的问题（[上下文组装：参照调研](../archive/research/context-assembly-reference.md)第 4.1 节）。
- 使用向量检索需要新增向量协议、向量模型的测试与准入，以及本地向量存储。

考虑过的做法：Zep 与 Graphiti 用语义、全文与图关系混合召回，再用 cross-encoder 或节点距离重新排序；ExpeL 按向量相似度选取示例；JEV 在重新排序上的效果也好（MRR 从 0.622 提高到 0.843）。这些做法会使同一请求的内容依赖模型版本与索引状态，难以重放与解释。

后果：

- 换一种说法的同一内容，靠实体身份与关系找到；重复的实体由中心角色在复盘时合并，重复的教训与洞见由教训发现模块合并。
- 选择的质量取决于记录时关联的实体与关系是否齐全，本体的校验与接触时附加承担这部分工作。

修订（总架构师，2026-10-25）：确定性的定义从「不调用模型」改为「同样的事件重放出同样的请求」。装配里可以有判定点，条件是选择先写成事件再被消费、重放只读事件；判定点校准通过之前只记录，不改变装配结果（术语表「判定点」）。不用向量检索的理由不再是重放，是复杂度：现阶段结构关系够用。总图第三、四节按此写。
