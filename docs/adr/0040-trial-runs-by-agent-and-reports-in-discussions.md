# 试用由 agent 执行，结果公开发帖

2026-10-21 用户提出要有一个 Yudao 的试用 skill：让经验丰富的 agent 使用者实际把 Yudao 用起来，从产品流、性能、使用方便、功能与其他方面去找问题，并把问题放到 GitHub Discussions 的 general 分类。此前仓库里关于试用的路径有两条：架构师用发布版按试用指南走一遍（[网页界面与发布设计说明](../design/web-interface-and-release.md)第 6.5 节），以及用户用 `/qa` 反馈、架构师建工单（同第 6.6 节）。两条都要求人在场；仓库没有面向外部使用者的公开反馈通道，Discussions 的 General 分类一直空着。决定：

- 试用由 agent 全程执行。agent 按「经验丰富的 agent 使用者」的标准评判：上下文有没有带够事实、工具调用有没有真的推进、契约与放行有没有绑在真实证据上、失败以后能不能恢复与重放、一次尝试花了多少、交付能不能被第三方核验；不评论代码风格与命名。人的角色是提供环境与凭据。
- 试用对象是试用者自己从 main 打包并安装的实例。默认隔离安装：仓库外的独立虚拟环境、独立数据目录、独立端口，不覆盖试用者已有的安装；试用前记下旧安装以便回退。构建失败时降级为源码实例，界面维度记「降级：没有页面文件」，帖子与环境与前提里都写明。
- 走查八个维度：产品流、性能与成本、上手与使用方便、功能够不够用、稳定性与恢复、可观测与可诊断、文档与实际一致、数据与安全。每个维度给固定检查动作与一个结论。
- 固定五个轻量任务：最小编码交付、追加需求与定向指导、故意出错看报错、重放一致性、导出与数据。任务集是带版本的数据文件（`docs/trial/tasks.md`），方法在 skill 里；任务集变了版本号加一，新旧结果不直接比较。
- 读数口径沿用 `docs/evaluation/` 的同名项（循环次数、返工次数、部门之间询问次数、模型请求数、输入与输出与缓存与总用量、费用、模型延迟、耗时），全部从 `run.export` 导出算，与 `evals/runner/yudao_metrics.py` 同源。模型服务没有上报的项写「未知」，不算 0，也不进平均值。
- 问题分四档：阻断、绕行、烦人、建议。每条带复现步骤、期望、实际与证据（run id、事件 id、截图、日志片段、命令与输出）。偏好、猜测与 main 上尚未承诺的能力进帖子末尾的「观察」，后者标明对应的工单或阶段；只有当前文档已承诺而实际做不到或做错的才算问题。
- 结果合成一篇帖子发到 Discussions 的 General 分类（仓库 id `R_kgDOSpFnRw`，分类 id `DIC_kwDOSpFnR84DIxLV`），不占 Announcements。标题是「试用：<一句话结论> — <main 提交短号> <版本>」。发帖前按机械清单脱敏：本机绝对路径、用户名与机器名、凭据与 Key、试用者代码全文一律不进帖；提交号、run id 与事件 id 保留，它们是核对用的锚点。帖子发完自动发布，不等人工确认。
- 帖子只做公开记录，不自动建工单。维护者读帖子以后把确认的问题转成工单，排在队列最前，与现有 `/qa` → 工单的路径一致；分诊的判断权仍在维护者手里。
- 试用只读被测对象：不改 Yudao 源码、不改仓库工作树、不提交、不当场修缺陷。允许改试用者自己环境的配置（Provider、凭据、部门 Prompt），那是试用者的环境，不是被测对象。
- 试用不改规则文件（`CLAUDE.md`、`AGENTS.md`、`docs/agents/`）、CI 工作流与设计说明，不建工单。
- 试用产生的原始材料留在 `.yudao/trial/<提交短号>-<时间>/`，已被忽略，不进版本控制。

理由：

- 用户不在场是常态，试用必须能由 agent 独立完成才可能持续跑。人执行、agent 记录的分工最贴近体感，但记录容易漏、跨次不可比，人不在场时这条路走不通。
- 试用要能比较才有意义。固定任务与同名指标让两次读数可以对照，这是「改一处、看到结果、决定保留还是撤回」的前提；任务与判据都带版本，改了就标版本、不与旧读数混算。
- 外部试用者通常没有仓库写权限，开不了 issue。General 是他们唯一能发的地方，帖子公开，结论对所有读者成立，不用先经过维护者。
- 脱敏做成机械清单而不是人工过目：人眼会漏，规则不会。规则本身也会漏，所以原始材料留在本地不入库，帖子发出去以后仍可核对。
- 不自动建工单：分诊是判断。自动建单会把未经确认的条目堆进队列，稀释真正阻断的问题。
- 试 main 而不是发布版：发布版与 main 的能力差着一段，用户报的缺口经常是还没发布的。试 main 能把「还没做」与「做坏了」分开——前者进「观察」，后者才算问题。

考虑过的做法：

- 由人执行、agent 只做记录归档。最贴近真实体感，但记录容易漏、跨次不可比，人不在场时这条路走不通。
- 直接复用仓库已有的固定评测场景 3（`evals/runner/run_yudao_eval.py`）。口径最严谨，还带五项过程检查点，但一次要跑三次、每次最长 90 分钟，还要真实模型的钱，社区用户跑不动，固定场景留给里程碑与评测。试用改用自己的一批轻量任务，指标口径仍然对齐。
- 试已安装的发布版。更贴近普通用户拿到的东西，但如上所述，缺口与缺陷分不开。
- 装成试用者平常那个 Yudao。最贴近真实使用，但会覆盖他的安装与数据。隔离是默认，skill 里另写按真实用户方式装的做法与回退步骤，由试用者自己选。
- 每个问题发一篇帖子。便于单独讨论，但一次试用的读数散了。
- 帖子发完自动开工单。省掉维护者手工转，但把分诊判断从维护者手里拿走。
- 发布前人工确认再发。少一道自动闸门；用户明确选了自动发布，改用机械脱敏补位。

后果：

- 新增 `.claude/skills/trial/SKILL.md`（方法）与 `docs/trial/tasks.md`（任务集，带版本）。
- Discussions 的 General 分类开始有试用帖子。只采信作者是试用者本人的帖子与评论；仓库是公开的，别的来源不采信。
- 试用发现的问题进入维护者的分诊视野，但不自动进队列；工单归属仍按 [工单标签规则](../agents/triage-labels.md) 定。
- 试用读数与 `docs/evaluation/` 的读数不是同一套：任务集不同、模型可能不同，只能在试用之间比，不能与评测场景的读数直接比。
- [CLAUDE.md](../../CLAUDE.md) 工作流程第 7 步不变：架构师用发布版走查、用户用 `/qa` 反馈走工单，仍是里程碑交给用户之前的必经步骤。新 skill 是并行的另一条路，不取代它。
- 试用器的能力边界（能不能开浏览器、能不能操作命令行）决定哪几个维度能测；缺的部分记「降级」并写明，不用猜补。
