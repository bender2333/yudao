# 三个部门同时运行，询问是嵌套的调用

此前每个 run 同时只允许一个部门调用模型；询问是一份提案，提交以后提问方的激活结束，回答在新的激活中作为材料出现，再由控制核心决定工作回到哪里；全系统同时只有一条请求，被询问的部门不能再询问；合同或输入一变化，正在工作的激活就结束。用户 2026-10-12 校准的意图是：三个部门的循环同时运行，循环之间可以互相发消息，用法与工具调用相同，事项是否完成由质检认定（[D38](../requirements/system-intent.md)）。决定：

- 一个事项内三个部门同时运行：持有交接的部门做本部门的正式成果；质检在 PRD 被接纳以后、交付到达之前做预测性探索，按 PRD 起草测试用例；部门在被询问或收到指导时工作。交接与完成只由控制核心决定，只有质检的放行结束事项。
- 询问是一次工具调用。提问方的步骤循环停在这次调用上；被询问的部门在自己的历史上开一个询问分支，分支看到这个部门到此刻为止的历史、当前状态与问题；分支提交回答以后，回答作为工具结果回到提问方，被询问部门的历史只增加一条问题与回答的记录，分支的工作过程留在事件里。
- 产品在回答里可以修订 PRD；工程与质检回答时只读取文件与运行检查，不修改运行工作区、交付说明、缺陷记录与放行结论。
- 一个部门在同一条询问链上只出现一次，三个部门时链最长两层。
- 询问分支的上限取被询问部门的声明值与提问方剩余量中较小的一个，用量计入提问方；没能回答时，原因作为工具结果交回提问方。
- 指导发给指定的部门，发给产品的就是新输入；接收部门在工作或在链上等待时作为通知加入它的历史，不在工作时按询问的规则在分支里处理，回答交给用户。部门指导的正式回应、放行前所有指导都要有处理结果的规则删除。
- PRD 有了新版本时，正在工作与等待的部门在下一步收到通知后接着工作；部门的工作只因取消、暂停与上限停止。每份正式成果写明依据的版本，依据的已经不是当前版本时提交被拒绝。

理由：

- 询问做成工具调用，提问方的思路连续，回答回到提问方，不需要控制核心另外决定工作回到哪里。
- 询问分支保留了被询问部门自己的上下文，回答的质量取决于这个部门已经知道的内容；分支与部门正在进行的工作互不等待，两个部门互相询问时不会出现谁都在等对方的情况。只把问题与回答接回历史，部门当前任务的上下文不被分支的读取过程挤占。做法参照 OMP 的检查点与回退（oh-my-pi@e3106be，`packages/coding-agent/src/session/session-manager.ts:2700-2716`）。
- 同时运行让质检在看到交付之前按要求写出测试用例，判断不受实现的影响，这是分成几个部门的依据。
- 回答期间不改动交付快照，质检的证据保持独立；PRD 由产品裁决，澄清的结果写进 PRD。
- 询问链规则由结构限定深度，不需要另设数字。
- 版本在提交时核对，部门可以在 PRD 变化后接着工作，由它自己判断已有工作的价值，正确性由提交时的核对保证。

考虑过的做法：

- 三个部门串行，询问同样做成嵌套的调用。循环结构相同，但质检不能在交付之前独立准备，用户的新输入也要等正在工作的部门让出。
- 每次询问开一个新会话，只带当前的正式成果与问题。被询问的部门没有自己的上下文，回答的质量低。
- 把询问送进对方正在运行的循环。两个部门互相询问时会互相等待。

后果：

- 流程编排在一个事项内安排多个会话；部门历史的装配排除询问分支的过程；协作请求、`resume_phase`、工作依据变化时结束激活的规则删除；指导改为通知或分支处理。
- 设计见[三部门的循环结构](../design/department-loop.md)。
