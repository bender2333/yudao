# 可信内核靠检查可信，不靠大小可信

状态：有效；依据：用户在 `/grill-with-docs` 里的决定（[决策记录](../decision.md)「2026-11-03 - 内核的更高要求靠机器检查，取消行数上限」）。

基础规则四原来的理由是内核小到用户本人能看懂，手段是内核清单的行数上限。用户不读内核代码；上限用完以后，总图放在「只由你批准」一环的薄驱动与插件加载进不了清单，执行者为了不超上限删过有用的注释。总量上限拦不住的是另一类错：测试名义上存在却没有真正检查，函数复杂到说不清。

决定：

- 基础规则四与 D38 的 N-K4 改成「对内核代码的要求高于其他地方」，取消行数上限。
- 要求落成两条机器检查，只对改到的内核代码：故意改坏一处时内核自己的测试必须报错、没有未覆盖的位点；改到的函数圈复杂度不超过 10。变异只用 `harness/tests/kernel/` 里的测试，所以内核目录的测试要自己立住：只用录好的事件序列和对模块的直接调用，存储用真实的 SQLite。
- 用户读的是内核清单里的规则表与测试名称，不读内核代码。
- 检查按模块接入：它所在的缝已定并立住，且最近两周改动的行数少于这个模块行数的一成。

考虑过的另一种做法：保留上限，薄驱动列入时上调；或改成按语句数计、只降不升、按模块分别设。没有采用：都是总量限制，大小与内核该管的事无关，也拦不住上面两类错，还会逼着删注释、挤行。

代价：两条检查证明不了规则本身是对的。规则错了或漏了、并发与重启造成的错，仍靠内核目录里用真实事件序列写的不变式测试和独立审查。变异测试在 Windows 上要选能跑的工具，耗时未知，路线图 #173 的试跑做完才接进合并检查；接入之前内核没有总量上限，只有原有的守卫。
