# 功能与质量优先：命令不经登记，结果未知交还模型

此前的工具设计为可审计与安全加了几层限制：本地命令只能是项目登记的命令及参数，检查的程序只能是 Yudao 自己的 Python 或工作区里的文件，命令进程按名字去掉看起来像密钥的环境变量；结果未知的动作只有声明「可以重新执行」的才自动重新执行，其余等用户回答；网络取回只能取登记或一次性批准的来源，MCP 工具分不提供、使用前询问、直接使用三种处理方式；项目对机器的授权逐项列出可以执行的操作。结果是质检运行不了 `uv run pytest`、`npm test` 这类命令，有依赖的项目无法独立验证；模型遇到未登记的命令只能停下；用户不在场时，一个等待回答的决定请求让整个事项停住。2026-10-13 用户明确：功能和质量最重要，安全和可审计优先级最低。决定：

- 判断标准：一个机制只为安全或审计存在，又让功能变差（多一次等用户、多一种拒绝、少一种能力），就删除，以后也不再为安全或审计增加这类机制。只负责记录、不挡功能的部分保留：事件日志记下每条命令与输出，保存的内容里凭据只写名称，命令输出中已知密钥的值替换成名字。隔离方式不变：Yudao 不做沙箱，来源不明的仓库放到另一台登记的机器上运行（[ADR-0022](0022-run-directly-without-containers.md)）。
- 删除 `run_command` 与项目的命令登记（登记表、参数白名单、命令版本冻结、「可以重新执行」声明），新增 `bash` 工具，接受任意命令字符串，三个部门都能用。持有交接的工程在运行工作区运行；其他会话（质检、产品、在询问分支里回答的工程）在自己的检查工作区运行，检查工作区每个会话一个，从当前快照建立，质检的从封存的交付建立，会话的文件工具与 `bash` 都用它，会话结束时删除。所有执行位置都用 bash，Windows 上用 Git for Windows 的 bash；每次调用启动一个新进程，不保留 shell 状态；保留时限、输出上限与结束整个进程树；可以后台运行，会话结束、事项暂停或取消时后台进程全部结束；没有许可规则。
- `run_check` 保留为交付与放行唯一认可的证据，接受任意命令字符串，删除程序的限制；每次在快照的全新副本中运行，质检的副本另外放入质检的测试材料，回执绑定快照与测试材料的版本。`bash` 的结果是动作回执，不能作为检查。
- `bash` 与 `run_check` 的进程得到 Yudao 进程（远程是执行代理进程）的全部环境变量。
- 结果未知的动作全部作为工具结果交还发出它的会话，写明执行被中断、结果未知，附上已经收到的输出，由模型检查以后决定是否重新执行；文件工具按动作前的快照自动核实，核实出确定结果时交回这个结果。删除「核实结果未知的动作」决定请求与自动重新执行。
- 网络取回三个部门始终都有，任何 http 与 https 地址都可以取回；删除来源登记、一次性批准、对回环与内网地址的拒绝。保留只发 GET、不带凭据与 Cookie、大小与时限与重定向次数的上限、完整内容存为外部来源工件并分页读取、拒绝 Yudao 服务自己的地址、评测期间不联网。
- MCP 服务器写在项目设置中（怎样启动或连接、哪些部门可以使用），服务器提供的工具全部直接提供；删除三种处理方式与一次性批准。服务器仍在控制主机上运行（[ADR-0025](0025-network-and-mcp-run-on-control-host.md)）。
- 项目对机器的授权只保留登记的目录与 Stage 4 的「是否作为运行环境」，删除「可以执行的操作」及保存执行位置、修改授权、工具许可三处对操作的核对。
- `bash` 能读写这个账户能访问的全部文件，包括别的部门的材料与评测的隐藏材料，Yudao 不另加拦截。部门的可见范围对 Yudao 提供的工具有效；模型看到的内容里不出现主机的绝对路径。评分之前核对评测隐藏材料的摘要，与材料版本记录的摘要不同时这次运行无效。
- 删除 Stage 6 的准入钩子（只能收紧的许可规则）。

理由：

- Yudao 的目的是交付质量高于直接使用单个 agent，并且在用户不在场时长时间自己运行。质检能运行项目真实的构建与测试，独立验证才成立；没有等用户的批准，事项才不会停在半路。
- 登记命令保证不了安全：项目的构建脚本与测试本来就能执行任意代码，现在的 `run_check` 也能执行模型自己写的 Python。可审计只需要事后的记录，事件日志已经记下每条命令、输出与主机看到的退出状态，事前登记没有增加证据。
- 证据的可信来自主机实际执行并绑定快照，与命令是否登记无关。检查在快照的全新副本中运行，工作区里积累的依赖、构建产物与缓存影响不了结论。
- 检查工作区每个会话一个，满足「每块内容只有一个写入者」（[三部门的循环结构](../design/department-loop.md)第 3.2 节），不需要命令规则。
- 任意命令无法事先声明能否重新执行，模型能检查工作区的实际状态，由它决定比由用户决定更快，也不让事项停住。
- 做法与 OMP、OpenCode 一致：两者都提供任意 shell；OMP 在 Windows 上优先使用 Git for Windows 的 bash，bash 工具可以后台运行，默认时限 300 秒、最长 3600 秒（oh-my-pi@e3106be，`packages/utils/src/procmgr.ts:135-180`、`packages/coding-agent/src/tools/bash.ts:335`、`packages/coding-agent/src/tools/tool-timeouts.ts:11`）。

考虑过的做法：

- 只留一个 `bash`，证据按命令运行时公开树的摘要判断。工具更少，但证据会受工作区里残留文件的影响。
- 保留登记命令，增加 OpenCode 式的 allow、ask、deny 规则。「ask」在用户不在场时让事项停住，规则又拦不住构建脚本中的任意代码。

后果：

- 本决定取代 [ADR-0022](0022-run-directly-without-containers.md) 中「命令只能是登记的命令」「进程的环境变量中没有凭据」两项，取代 [ADR-0025](0025-network-and-mcp-run-on-control-host.md) 中「需要读写工作区的能力由内置的文件工具与登记的命令提供」与「子进程的环境变量只有登记里写明的变量与操作系统运行所需的基础变量」，以及 3.1 已确认的「对结果未知的外部动作由用户作出决定」、[D36](../requirements/network-and-mcp.md) 的登记与一次性批准、[D29](../requirements/remote-execution.md) 中项目授权的「可以执行的操作」。
- 工具边界见[本地通用工具设计说明](../design/local-tools.md)；网络取回与 MCP 见[网络取回与 MCP 工具设计说明](../design/network-and-mcp.md)；结果未知的处理见[恢复契约与故障矩阵](../design/recovery-contract-and-fault-matrix.md)第 4 节。
- 当前定稿原型 v10 中的一次性批准卡片、登记命令的列表与表单、MCP 工具的处理方式、动作核实的决定不再实现，下一版原型删除（[原型变更记录](../prototypes/CHANGELOG.md)开头的待办）。
