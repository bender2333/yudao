# 循环层写在定义里，角色可以发起子循环，每一层都有边界

Status: 「嵌套深度的上限是内核常量，现值为 2」按总图第三节改为（2026-10-25 记）：上限必须存在、由内核的边界核对，数值是定义里的上限（现值 2），和时间、次数、重试一样来自定义，修改经用户批准。见[循环与收敛设计说明](../design/loops-and-convergence.md)第 2、3 节。其余决定继续有效。

此前的文档把循环写成固定的四层，部门内多角色的设计规定嵌套深度 1、工具角色不能再分派；原理文档要求触发递归的信号由代码判定，不能由模型自己判断。用户校准的意图是：层数不固定，新的层只在有运行证据时才加，嵌套深度有硬上限；允许 agent 自己拆任务、起子循环，子循环同样有边界；循环一定会停，每次停下都有明确的原因，由代码保证（[D38](../requirements/system-intent.md)）。现在运行时间的起点只保存在进程内存里，几种等待没有自己的上限，部门内循环只受事项运行时间上限约束。决定：

- 循环层写在定义里：一轮是什么、边界、进展的度量、交给上一层的记录。新增一层的声明引用运行证据，即上一层在某类任务上反复停滞或达到边界的记录。嵌套深度的上限是内核常量，现值为 2。
- 角色通过一个主机工具发起子循环，写明目标、预期结果、可用内容的引用与边界。是否发起由角色决定，控制核心只核对深度与剩余量。子循环的上限取声明值与上一层剩余量中较小的一个；结束时上一层的历史只收到一条角色结果；子循环里的修改与提案同样经过工具许可与提案校验。
- 停止由代码保证：已用的时间与次数在每个安全节点写入事件，进程重启以后连续累计；任意两次模型请求或动作之间至少有一个安全节点，单次请求与单个动作各有时限；不计入运行时间的等待只有封闭清单里的几种（等待模型服务、等待用户决定、等待机器、等待桌面），每种等待有一个时长上限参数，超过时发出决定请求并通知用户一次，等待用户决定由用户结束；结束状态的停止原因必须属于封闭清单。
- 收敛无法事先保证，事后检测：收敛状态（收敛中、停滞、震荡、漂移、达到边界）是知识层的一个投影，只由事件计算，进展只按主机记录的事实判定，不调用模型。

理由：

- 不允许角色自己拆任务，就要在定义里预先写好拆分的位置，这是用户明确不要的静态编排；子循环的风险在于没有边界，所以控制放在深度与从上一层继承的剩余量上。
- 每一层自带记录的折叠，上一层只收到一条结果，上下文不随嵌套增长。
- 已用量只在内存里时，进程重启会让运行时间上限失效；等待没有上限时，「一定会停」只对运行中的部分成立。
- 进展交给模型判断时，模型的自述可以抵消主机的事实，违反「现实的证据高于模型的意见」。

后果：

- 部门内循环作为一层登记边界：角色任务数与审查次数的上限进入规则登记；停滞只按主机记录的进展事实判定，中心角色的进展判断照常记录，作为参考；停滞不结束事项。
- 工具角色可以发起子循环。
- 设计见[循环与收敛设计说明](../design/loops-and-convergence.md)。
