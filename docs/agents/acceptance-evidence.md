# 交付、审查与阶段验收的证据

适用：执行者写 `DELIVERY:`、审查者在 PR 上提交审查、架构师核对父工单、更新验收基线、交给用户试用、关闭里程碑或进入一个阶段时读取（第 5、6 节只有架构师读）。架构师维护设计、规则与工单；执行者实现代码；审查者独立核对代码与证据；派发者按工单原生依赖与流程标签调度（[派发者规则](dispatcher.md)）。

## 1. 记录身份与结论

| 结论 | 必须给出的身份与证据 | 负责角色 |
| --- | --- | --- |
| 实现完成 | 实现提交、修改文件、逐条验收核对、检查命令和结尾计数 | 执行者 |
| 审查通过 | PR 上对当前提交的批准、运行的相关检查与反向验证、结尾计数、失败项 | 审查者 |
| CI 通过 | PR 当前提交或 main 提交上 `check` 的运行 | CI |
| 集成通过 | 实际检出的提交（PR 的合并提交或 main 的提交）、运行范围、结尾计数、结果工件、未解决项 | 派发者（合并之前）、架构师（试用之前） |
| 真实验收通过 | 安装或运行的版本与提交、场景与材料版本、模型配置摘要、完整操作、事件与工件、每次尝试的结论 | 该验收工单的执行者与独立审查者；架构师核对父工单 |
| 可以交给用户试用 | 同一发布包的集成结果、架构师按用户路径的真实走查、试用指南、未完成条件均已处理 | 架构师 |
| 里程碑关闭 | 用户的试用结论、版本回归、复盘、判据读数都已写在试用工单的关闭评论里（第 5 节） | 架构师在用户确认以后写；总架构师在阶段结束时汇总（第 6 节） |

每份结果只证明它记录的版本与场景。提交代码、审查通过、集成通过和真实验收分别记录；“最近一次通过”始终带提交号。父工单关闭与里程碑关闭时，架构师同步 `docs/current-baseline.md`、路线图、需求与设计索引；里程碑关闭时另在试用工单写关闭评论（第 5 节）。

## 2. 未解决问题

- 与当前验收条件有关的设计差异、缺少证据、失败或未知结果，审查必须要求修改，并给文件位置、原因与阻塞的验收条件。需要架构决定的注明「架构问题」，由架构师更新设计与任务评论。
- 与本工单无关的既有失败，必须给出在未含本工单改动的基线提交上复现的证据，并关联处理工单，写明影响的能力与里程碑。审查者报告问题，架构师建立或核对处理工单；关联尚未建立时审查者不批准。
- 既有失败影响本次交付或本里程碑的能力时，先处理失败再给对应验收通过结论。测试基准与原型只有在已确认的行为发生变化时才按新行为更新。
- 审查指出了验收范围内的未决差异时，结论是要求修改；不在批准的审查里留下待架构师决定的验收问题。
- 期望结果来自要求、设计或原型。新增测试应当能区分符合与违反要求的结果；把实现公式复制到测试中不能单独证明符合要求。

## 3. 测试分层的生效条件

单元层与模块层全部由 CI 在每次推送时运行；执行者与审查者运行与改动相关的测试文件，包括本次改动涉及的集成文件；集成层全部由 CI 在每次合并以后运行（[测试分层设计说明](../design/test-pyramid.md)第 4 节）。新增文件必须登记，测试命令以 `AGENTS.md`「常用命令」为准。

前端改动运行相关单元与端到端文件。像素画面、驱动、录制材料或回放行为的改动，同时运行其对应的逐场景回放文件，并列出每个失败场景；端到端用当前源码构建的页面。

## 4. 后台推进期间维护规格

架构师修改工单前重新读取标签、领取、最新任务评论、PR 与原生依赖。未领取的工单在修改正文期间标为 `needs-triage`，设计文档进入主分支、正文与原生依赖一致、「依据」一行更新以后恢复 `ready-for-agent`。执行或审查中的工单，修改内容写到任务评论，执行者在下一轮读取；保留执行者的已有改动。

新子工单先带 `needs-triage`，建立父子关系、里程碑与原生阻塞项，核对规格以后再改为 `ready-for-agent`。核对规格包括：在当前 main 上核对「只改」清单与正文列出的函数、字段和文件，写上「依据」一行，按 `CLAUDE.md`「工单规范」检查大小上限、合同改动的范围与 `touches-core`。父工单只由架构师核对后关闭。执行者推送分支并开 PR，审查者只在 PR 上提交审查；合并由 GitHub 在 main 的规则满足时完成，子工单随 PR 合并关闭。自主推进模式下，任何机器上的工作都经过同样的 CI、审查与合并条件，没有一人既执行又审查的例外。用户指定的 solo 模式范围除外：范围内没有审查，结论「审查通过」不存在，工单关闭的证据是 PR 上的 `DELIVERY:` 评论与合并时 `check` 通过的运行，规则见 `AGENTS.md`「Solo 模式」。

## 5. 发布里程碑的关闭

适用于路线图第 1.4 节的发布里程碑（标题「阶段几 · 序号 名字」，带一张试用工单）。里程碑回答的问题有了证据、用户试用过，才关闭。关闭证据只写在一处：试用工单的关闭评论，下面五项各占一行，每行写结论和链接，证据留在原处，不复制；一行不能空，没有的写「无对照（首个发布）」或「暂无，<哪个里程碑起有>」，不写估计的数。这条规则对此后关闭的里程碑生效，已关闭的 Stage 3 · M1 至 M5 不补。

顺序：复盘（`CLAUDE.md` 工作流程第 7 步）、发布前检查与发布（[测试分层设计说明](../design/test-pyramid.md)第 4 节）、版本回归、架构师按试用指南走查并交给用户、用户试用、写关闭评论、关闭。

- **发布**：版本号、main 提交、`scripts/release.py` 输出的 wheel SHA-256。该提交已通过发布前检查并走查过（第 1 节「可以交给用户试用」）。
- **试用结论**：
  - 试用的是用户本人，用发布出来的版本，按试用指南（[网页界面的提供与发布设计说明](../design/web-interface-and-release.md)第 6.6 节）操作。架构师的走查和 `/trial` 的帖子是附加证据，不替代用户的试用。
  - 由用户在场的架构师按用户在会话里说的话写，附原话：试用结论（通过或不通过）、版本与 main 提交、指南各条的结果（通过、不通过、没试）、发现的问题工单号与是否都已关闭、用户原话。
  - 通过要同时满足：用户对里程碑的问题（路线图第 1.4 节的表）答「是」；发现的问题工单都已关闭，用户同意延后的挪到后面的里程碑并在评论里列出。
  - 不通过：里程碑和试用工单保持打开，试用工单改回 `waiting`；问题建成工单排在队列最前，修好以后发修订版本（同文第 6.2 节），架构师对改动处重新走查，改动影响模型输入或行为的重跑一次版本回归；再交给用户，新结论追加成新评论，旧的保留。里程碑的问题本身答案是「否」时，继续在本里程碑修，还是以「未达到」关闭、把后续转入后面的里程碑，由用户决定，评论照实写。
- **版本回归**：
  - 对照上一个发布：同一个固定场景（评测工具里已有 Yudao 一侧运行器和评分器的场景，目前是场景 3）、同一模型，材料版本与评分器版本相同。对照对象是上一个发布的读数，取自它的关闭评论里的链接，不重跑。首个发布写「无对照（首个发布）」，并链接自己的读数留作下一个发布的基准。
  - 在要发布的 main 提交上按 `evals/README.md`「运行一次评测」跑 Yudao 一侧，结果与报告提交到 `docs/evaluation/`，文件名带里程碑短名，写明两侧的 main 提交；次数以里程碑工单为准，至少一次。记完成度、正确性、质检误放行次数、过程检查点失败项、循环次数、返工次数、模型请求数、用量、费用、耗时（`evals/runner/yudao_metrics.py` 的 `collect` 与评分器给出）；模型服务没上报的写「未知」，不写 0。
  - 「没有变差」指 `evals/runner/yudao_compare.py` 的 `compare` 结论不是「退化」也不是「受阻」（目前没有命令行入口，手动调用）。材料或评分器版本不同时结论是「受阻」，写原因，对照一侧按新版本重跑以后才能比较。噪声范围来自同一版本的重复运行，每侧 3 次（[规则登记与参数设计说明](../design/rules-and-parameters.md)第 4 节）；次数不够时写「<结论>（噪声范围未知，每侧 n 次）」并列出逐项差值，这只说明没有明显退化，不说明完成度没有变差。评测工具还没有的部分（对单个 agent 的对照、操作代理照说明书判分）不作要求，写「暂无，阶段二 · 2 起有」。
- **复盘**：用 `/retro <里程碑标题>`（[复盘 skill](../../.claude/skills/retro/SKILL.md)），发在 Announcements，内容和顺序以该 skill 第 10 步为准。这一行写帖子链接，以及「改动与预期」表里提议、用户确认、否决、已生效各几行。规则句子与参数的修改要用户确认才生效，没有确认的不阻塞里程碑关闭，架构师交给用户试用时把仍是「提议」的行一并列出。关闭时架构师读回帖子，确认它存在、范围含这个里程碑；查不到就先复盘再关闭。
- **判据读数**：写这个里程碑运行中得到的、属于路线图第 5 节该阶段一列的读数和来源链接，例如场景 3 的读数、CI `check` 的运行。每格的验收标准以[系统意图](../requirements/system-intent.md)N-T1 至 N-T5 为准，这里不重写；暂时不能度量的写「暂无，<哪个里程碑起有>」。

关闭的权限与步骤：

- 用户确认之前，试用工单保持 `ready-for-human`，里程碑保持打开。用户不在场（包括自主推进）时不关，下一个里程碑照常推进。被唤醒的架构师、派发者和 solo 执行者不关闭它们：「试用通过」只有用户能给。用户本人直接关闭了的，关闭评论由架构师下次会话开始时补写。
- 用户确认以后，用户在场的架构师依次：在试用工单写关闭评论；同步 `docs/current-baseline.md` 的发布行、路线图与索引；关闭试用工单与 GitHub 里程碑；记入 `docs/CHANGELOG.md` 与 `claude_jour.md`；把变化告诉总架构师。总图的建设状态与缝的已定、未定仍只由总架构师改。

## 6. 阶段的结束与进入

**阶段结束。** 一个阶段的里程碑全部关闭时，总架构师按路线图第 2 节该阶段的「结束时总图」与第 5 节那一列逐格核对 main，每格写「预期 / main 上的实际 / 证据链接」，实际读数取自该阶段各里程碑关闭评论的「判据读数」一行，写成该阶段的阶段工单的一条评论。不过的格补成缺口工单，不改总图的状态。全部过了，总图的建设状态、缝的已定未定与 `docs/current-baseline.md` 随之更新；部门的种类变了时，`CLAUDE.md`、`AGENTS.md` 开头与 `CONTEXT.md` 的部门表述一起改；阶段工单按路线图第 1.4 节的条件关闭。可迭代状态的五条判据在阶段二结束时按这些读数核对。

**阶段进入。** 阶段按顺序进入。下面四项都成立，才能建这个阶段的里程碑、把它的工单从 `waiting` 放行。检查者是总架构师，在用户在场的会话里逐项核对，勾在这个阶段的阶段工单正文的「进入包」一节并附证据链接；被唤醒的架构师与子架构师不勾。这是总架构师自查，机械的检查只有两个：派发者只取 `ready-for-agent` 的工单；`/to-parents` 找不到阶段工单或里程碑时停下来。某一项不成立时，这个阶段的工单留在 `waiting`，缺的东西补成工单，归在阶段工单下。

| 项 | 内容 | 什么时候确认 |
| --- | --- | --- |
| 1 进入条件 | 下面表里这个阶段的一行，每条有证据 | 上一阶段的结束核对之后 |
| 2 阶段工单 | 一个阶段一张，不放进里程碑，开始标 `waiting`。正文有：问题陈述、阶段结束时用户能做什么、结束时总图、交付验证（取自路线图第 2 节）、进入包（本表四项各自的证据）、里程碑、父工单、归并的旧工单；#976、#977 的结构加上「交付验证」「进入包」两节就是模板 | 进入条件的证据写在它上面，所以最晚在上一阶段的结束核对时建好 |
| 3 里程碑表 | 这个阶段的每个里程碑：名字、回答的问题、内容（总图位置）和先后，格式同路线图第 1.4 节的表，接在该表后面；GitHub 里程碑的说明写同一行 | 第 1、4 项成立之后，建 GitHub 里程碑之前 |
| 4 设计说明搬迁 | 旧路线图（`docs/archive/program-roadmap-2026-10-25.md`）里属于这个阶段的条目（运维部门规则、长时间运行、两层自举的前置条件与试点约定等，路线图第 6 节）逐条列在阶段工单的「进入包」，每条写目标文件。全部搬完才成立：目标文件存在，开头状态行有总图位置，设计索引或需求索引有条目，`grep -rn "program-roadmap-2026-10-25" docs --include=*.md`（排除 `docs/archive`）的命中里没有指向这个阶段旧章节的 | 第 1 项成立之后，建里程碑之前 |
