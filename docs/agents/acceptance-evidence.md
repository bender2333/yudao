# 交付、审查与阶段验收的证据

适用：执行者写 `DELIVERY:`、审查者写 `REVIEW:`、架构师核对工作包、更新验收基线或交给用户试用时读取。架构师维护设计、规则与工单；执行者实现代码；审查者独立核对代码与证据。后台流程按工单原生依赖与流程标签继续领取任务。

## 1. 记录身份与结论

| 结论 | 必须给出的身份与证据 | 负责角色 |
| --- | --- | --- |
| 实现完成 | 实现提交、修改文件、逐条验收核对、检查命令和结尾计数 | 执行者 |
| 审查通过 | 实际审查的提交、独立运行的检查、结尾计数、失败项、PR | 审查者 |
| 集成通过 | 实际检出的主分支提交、运行范围、结尾计数、结果工件、未解决项 | 架构师的集成流程 |
| 真实验收通过 | 安装或运行的版本与提交、场景与材料版本、模型配置摘要、完整操作、事件与工件、每次尝试的结论 | 该验收工单的执行者与独立审查者；架构师核对工作包 |
| 可以交给用户试用 | 同一发布包的集成结果、架构师按用户路径的真实走查、试用指南、未完成条件均已处理 | 架构师 |

每份结果只证明它记录的版本与场景。提交代码、审查通过、集成通过和真实验收分别记录；“最近一次通过”始终带提交号。工作包关闭与发布时，架构师同步 `docs/current-baseline.md`、路线图、需求与设计索引。

## 2. 未解决问题

- 与当前验收条件有关的设计差异、缺少证据、失败或未知结果，必须写 `REVIEW: FAIL` 并给文件位置、原因与阻塞的验收条件。需要架构决定的注明「架构问题」，由架构师更新设计与任务评论。
- 与本工单无关的既有失败，必须给出在未含本工单改动的基线提交上复现的证据，并关联处理工单，写明影响的能力与里程碑。审查者报告问题，架构师建立或核对处理工单；关联尚未建立时保留 `needs-review`。
- 既有失败影响本次交付或本里程碑的能力时，先处理失败再给对应验收通过结论。测试基准与原型只有在已确认的行为发生变化时才按新行为更新。
- 审查指出了验收范围内的未决差异时，结论保持失败；不在 `REVIEW: PASS` 下留下待架构师决定的验收问题。
- 期望结果来自要求、设计或原型。新增测试应当能区分符合与违反要求的结果；把实现公式复制到测试中不能单独证明符合要求。

## 3. 测试分层的生效条件

执行者与审查者交付前运行 `uv run python -m pytest -m "unit or module"`，再运行本次改动涉及的集成文件；集成层批量运行由架构师负责。新增文件必须登记，测试命令以 `AGENTS.md`「常用命令」为准。

前端改动运行相关单元与端到端文件。像素画面、驱动、录制材料或回放行为的改动，同时运行其对应的逐场景回放文件，并列出每个失败场景；端到端用当前源码构建的页面。

## 4. 后台推进期间维护规格

架构师修改工单前重新读取标签、领取、最新任务评论、PR 与原生依赖。未领取的工单在修改正文期间标为 `needs-triage`，设计文档进入主分支、正文与原生依赖一致以后恢复 `ready-for-agent`。执行或审查中的工单，修改内容写到任务评论，由后台协调流程在下一轮采用；保留执行者与审查者的已有改动。

新子工单先带 `needs-triage`，建立父子关系、里程碑与原生阻塞项，核对规格以后再改为 `ready-for-agent`。父工单只由架构师核对后关闭。Windows 独立执行与审查流程中，审查者的交付动作止于推送分支、创建 PR、发表评论与切换标签；主分支合并和工单关闭由后台架构协调流程处理。aipro 单人流程的适用条件与操作按[运行配置](autopilot-runtime.md)第 4 节执行。
