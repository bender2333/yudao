# 交付、审查与阶段验收的证据

适用：执行者写 `DELIVERY:`、审查者在 PR 上提交审查、架构师核对工作包、更新验收基线或交给用户试用时读取。架构师维护设计、规则与工单；执行者实现代码；审查者独立核对代码与证据；派发者按工单原生依赖与流程标签调度（[派发者规则](dispatcher.md)）。

## 1. 记录身份与结论

| 结论 | 必须给出的身份与证据 | 负责角色 |
| --- | --- | --- |
| 实现完成 | 实现提交、修改文件、逐条验收核对、检查命令和结尾计数 | 执行者 |
| 审查通过 | PR 上对当前提交的批准、运行的相关检查与反向验证、结尾计数、失败项 | 审查者 |
| CI 通过 | PR 当前提交或 main 提交上 `check` 的运行 | CI |
| 集成通过 | 实际检出的提交（PR 的合并提交或 main 的提交）、运行范围、结尾计数、结果工件、未解决项 | 派发者（合并之前）、架构师（试用之前） |
| 真实验收通过 | 安装或运行的版本与提交、场景与材料版本、模型配置摘要、完整操作、事件与工件、每次尝试的结论 | 该验收工单的执行者与独立审查者；架构师核对工作包 |
| 可以交给用户试用 | 同一发布包的集成结果、架构师按用户路径的真实走查、试用指南、未完成条件均已处理 | 架构师 |

每份结果只证明它记录的版本与场景。提交代码、审查通过、集成通过和真实验收分别记录；“最近一次通过”始终带提交号。工作包关闭与发布时，架构师同步 `docs/current-baseline.md`、路线图、需求与设计索引。

## 2. 未解决问题

- 与当前验收条件有关的设计差异、缺少证据、失败或未知结果，审查必须要求修改，并给文件位置、原因与阻塞的验收条件。需要架构决定的注明「架构问题」，由架构师更新设计与任务评论。
- 与本工单无关的既有失败，必须给出在未含本工单改动的基线提交上复现的证据，并关联处理工单，写明影响的能力与里程碑。审查者报告问题，架构师建立或核对处理工单；关联尚未建立时审查者不批准。
- 既有失败影响本次交付或本里程碑的能力时，先处理失败再给对应验收通过结论。测试基准与原型只有在已确认的行为发生变化时才按新行为更新。
- 审查指出了验收范围内的未决差异时，结论是要求修改；不在批准的审查里留下待架构师决定的验收问题。
- 期望结果来自要求、设计或原型。新增测试应当能区分符合与违反要求的结果；把实现公式复制到测试中不能单独证明符合要求。

## 3. 测试分层的生效条件

单元层与模块层全部由 CI 在每次推送时运行；执行者与审查者运行与改动相关的测试文件，包括本次改动涉及的集成文件；集成层全部在合并之前运行（[测试分层设计说明](../design/test-pyramid.md)第 4 节）。新增文件必须登记，测试命令以 `AGENTS.md`「常用命令」为准。

前端改动运行相关单元与端到端文件。像素画面、驱动、录制材料或回放行为的改动，同时运行其对应的逐场景回放文件，并列出每个失败场景；端到端用当前源码构建的页面。

## 4. 后台推进期间维护规格

架构师修改工单前重新读取标签、领取、最新任务评论、PR 与原生依赖。未领取的工单在修改正文期间标为 `needs-triage`，设计文档进入主分支、正文与原生依赖一致、「依据」一行更新以后恢复 `ready-for-agent`。执行或审查中的工单，修改内容写到任务评论，执行者在下一轮读取；保留执行者的已有改动。

新子工单先带 `needs-triage`，建立父子关系、里程碑与原生阻塞项，核对规格以后再改为 `ready-for-agent`。核对规格包括：在当前 main 上核对「只改」清单与正文列出的函数、字段和文件，写上「依据」一行，按 `CLAUDE.md`「工单规范」检查大小上限、合同改动的范围与 `touches-core`。父工单只由架构师核对后关闭。执行者推送分支并开 PR，审查者只在 PR 上提交审查；合并由 GitHub 在 main 的规则满足时完成，子工单随 PR 合并关闭。任何机器上的工作都经过同样的 CI、审查与合并条件，没有一人既执行又审查的例外。
