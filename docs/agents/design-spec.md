# 设计说明规范

适用于 `docs/design/` 下的设计说明（含 `architecture/` 里的总体架构）。需求记录与 ADR 不在此列。设计与实施分开：设计说明写设计，进度在 GitHub，实施在代码。

## 设计说明是什么

回答一个功能「怎么做」，细化总图的一个方框或一道缝：怎么实现、边界和范围在哪里、接口在哪里。详细到可以直接当父工单用：子架构师从它拆子工单，父工单只是一个壳，「依据」指向它，进度记在 GitHub。不写详细的实现，不指向容易变动的东西。

功能、设计、实现各归各处：

- 功能（做什么）：用户的话与确认的规则，在需求记录里。例：整理失败不能悄悄把事项结束。
- 设计（怎么做）：设计说明。例：整理连续失败到上限，事项进入待恢复，向用户发出决定请求；用户可以换模型后继续，次数清零，已收下的交付保留。
- 实现（用什么写）：代码、规则登记、测试。例：参数键、枚举名、函数、字段、路径、行号。

## 结构

文件第 3 行只放一行：`总图位置：……。依据：……。`。总图位置写哪一节、哪个方框或哪道缝；依据写需求记录、ADR、相关的设计说明与调研（路径加小节标题）。再往下按需要的深度写下面这些节，没有内容的节不写：

1. 功能与依据：这份说明让系统做到什么，一两段。
2. 边界与范围：做什么、不做什么，和相邻模块的分界；本说明里的常量，每个写默认值、范围和理由（见「常量」）。
3. 接口：在哪道缝上，谁调用谁，交换什么（写意思，不写类型和签名）。配一张简单的模块图；涉及新增或调整代码的包时，再配一张包图（UML 包图，用 mermaid 画包和包之间允许的依赖方向）。整个系统的包图在总体架构里。
4. 方案：怎么做，含流转、失败处理、公式与取舍理由。
5. 验收：怎样算做到了，功能层面，用方案里的词写。父工单的验收标准取自这一节；子工单自己写实现层面的验收。
6. 未决问题：设计上还没定的事；定了就改写进正文。

## 不写什么

- 状态：已实施、未实施、实施中、当前代码是什么样。进度看 GitHub 的里程碑与工单，变更看 git。
- 历史：日期、谁在哪天定的、原来怎样改成怎样。改动的经过记在 `docs/CHANGELOG.md`（[共同规则](shared-rules.md)「文档与记录」）。
- 工单号、里程碑与阶段编号。
- 详细的实现：代码名（类、函数、文件、参数键、枚举值）、字段名与类型、路径、行号。总图的词与代码名不一致的，记在对照表（`docs/design/architecture/name-map.md`）里。参照外部实现时写它的提交号，那是出处。包图画的就是包和目录，用它们的真实名字，这是例外。
- 现状与差距：「现有做法 → 改为」这类表。
- 指向容易变动的事物的链接：工单、代码、规则登记。可以指向需求记录、ADR、总图、其他设计说明、对照表与调研数据。

判断一句话是设计还是实现：把句子里的代码名、字段名、路径、行号、工单号拿掉。还成立、读得懂，是设计，留下；拿掉就没意思了，是实现，出去。

## 反向引用

设计说明稳定，工单、代码注释、规则登记的 `origin` 经常变，所以由后者引用前者，设计说明不引用它们。引用写「文档路径 + 小节标题」，不写节号和行号。改小节标题时，在 `docs/CHANGELOG.md` 那一行写「旧标题 → 新标题」。设计说明互相引用也用小节标题。

## 常量

设计说明里出现的常量（默认值、上限、比例、次数、时长）按下面几条处理：

1. 每个常量在「边界与范围」里写默认值、范围和理由；范围型的，写范围就够。
2. 规则登记（`harness/definitions/rules.json`）照着实现：界限同设计说明的范围，`origin` 写回那份说明的小节标题。
3. 一个常量只在一份设计说明里写数，别的文档引用那份的小节标题。
4. 改常量：先改设计说明，再由工单改登记。实施者认为范围不合适，交回架构师，不自己改。
5. 运行中的现值是参数事件，与文档无关。设计说明不写「见规则登记」。
