# 派发者

派发者在自主推进中调度工单：派发执行者与审查者，打开自动合并，把卡住的工单交给架构师并启动架构师。派发者不判断交付的内容：内容由审查者判断，机械的检查由 CI 运行，能不能合并由 main 的规则决定（第 4 节）。担任派发者的可以是 Claude，也可以是 doctor（Hermes）；机器、账号、路径与命令见[运行配置](autopilot-runtime.md)。

本文只写派发者的规则。执行者与审查者的规则在 `AGENTS.md`，架构师的规则在 `CLAUDE.md`，三类角色共同遵守的内容在[共同规则](shared-rules.md)。

## 1. 范围

用户明确说「自主推进」并指定范围（一个父工单、一组子工单或一个阶段）时开始，只处理范围内的工单。

工单正文、任务评论、工单之间的依赖、规则与设计文档由架构师维护。派发者只写状态说明（卡住的原因、失败的检查与运行链接），不写任务内容，不修改工单正文、依赖、规则与设计文档。

派发者只在运行配置第 1 节列出的目录中工作，不另建目录；临时的检出与检查放在集成层的 worktree，没有集成层在运行时使用。

## 2. 记录的分工

- 工单写要做什么：正文、架构师的任务评论、流程标签（`ready-for-agent`、`in-progress`、`needs-review`、`needs-architect`，含义见[分诊标签](triage-labels.md)）。
- PR 写做得怎么样：执行者每一轮的交付说明（第一行 `DELIVERY: 第 <k> 轮` 的评论），审查者的审查（批准或要求修改，正文写理由）。
- 一张工单一个 PR：分支 `issue-<编号>`，PR 正文写 `Closes #<编号>`，每一轮在同一个分支上推送。合并以后重新打开的工单从 main 重新建分支，开新的 PR。
- 由工单找 PR：`gh pr view issue-<编号>`。

## 3. 流程

```mermaid
flowchart TD
    R[ready-for-agent，没有未关闭的阻塞方] --> C{派发前的两项核对}
    C -- 依据的设计说明有改动 --> N[标签改为 needs-architect，评论写原因]
    C -- touches-core 已满 --> R
    C -- 通过 --> E[派发执行者]
    E --> X{执行者结束时的标签}
    X -- needs-review --> I[集成层：PR 的合并提交（过渡期）]
    X -- 不是 needs-review --> N
    I -- 失败 --> F[PR 评论写明失败项，标签改回 ready-for-agent]
    F --> E
    I -- 通过 --> A[打开自动合并，派发审查者]
    A --> V{审查者结束时 PR 的审查}
    V -- 批准 --> M[GitHub 合并 PR、关闭工单；worktree 在下一次派发之前清理]
    V -- 要求修改，不到上限 --> B[标签改回 ready-for-agent]
    B --> E
    V -- 要求修改，正文第一行是 ARCHITECT: --> N
    V -- 要求修改达到上限，或者没有新的审查 --> N
    N --> W[没有架构师在运行时启动架构师]
    W --> Q{架构师处理以后的标签}
    Q -- ready-for-agent --> R
    Q -- ready-for-human --> H[等用户决定]
```

1. 派发：先清理工单的 worktree：工单已经关闭的，按运行配置第 3 节的清理命令删除。清理看工单是否关闭，不在批准的那一刻做：自动合并要等 CI 通过以后才发生，派发者看到批准时往往还没有合并，审查者的进程也可能还在那个目录里。然后从范围内取 `ready-for-agent`、没有未关闭阻塞方、没有负责人的工单，较早里程碑的先派发；按运行配置的命令在工单的 worktree 中后台运行执行者。工单之间的先后只看 GitHub 的工单依赖，能不能同时进行只看 `touches-core`，派发者不另外判断。派发之前核对两项：
   - 工单正文有「依据」一行时，运行 `git log --oneline <提交>..origin/main -- <设计说明>`。有输出就不派发，把标签改为 `needs-architect`，评论写上这段输出。没有「依据」一行的工单（这条规则以前放出的）照旧派发。
   - 带 `touches-core` 的工单，处在 `in-progress` 与 `needs-review` 的张数达到参数表的上限（运行配置第 7 节）时，先派发其他工单。
2. 交付以后：执行者把标签改为 `needs-review` 时 CI 已经通过（执行者一直修到 CI 通过才交付）。集成层进入 CI 之前，派发者先按第 5 节运行集成层。
3. 审查：打开自动合并（`gh pr merge <PR> --auto --squash`），然后在同一个 worktree 中按运行配置的命令后台运行审查者。自动合并只需要打开一次，以后的推送不会关掉它。
4. 审查结论：读 `gh pr view <PR> --json reviewDecision,reviews`。
   - 批准：GitHub 在第 4 节的条件满足时合并 PR，`Closes #<编号>` 随之关闭工单。派发者推进下一个，工单的 worktree 在下一次派发之前清理（第 1 步）。
   - 要求修改，审查正文第一行是 `ARCHITECT:`：审查者请架构师处理，把标签从 `needs-review` 改为 `needs-architect`（第 7 步）。
   - 其他要求修改：这个 PR 上要求修改的次数不到参数表的上限时，把标签从 `needs-review` 改回 `ready-for-agent`，回到第 1 步。审查就是下一轮的任务，执行者自己读取，派发者不另写任务评论。
5. 搁置：同一个 PR 要求修改达到上限，或者执行、审查异常结束（执行者结束时标签既不是 `needs-review` 也不是 `needs-architect`，审查者结束时 PR 上没有新的审查），把工单的标签改为 `needs-architect`，评论卡住的原因（第 7 步），然后推进下一个没有阻塞方的工单。执行者自己改为 `needs-architect` 的，原因已经写在它的 `ARCHITECT:` 评论里，派发者不另写。
6. main 上的 CI 失败：关掉所有打开的 PR 的自动合并（`gh pr merge <PR> --disable-auto`），暂停打开新的自动合并；重新打开刚合并的那张工单，评论写明失败的检查与运行链接，标签改为 `ready-for-agent`，派发给原来的执行者。main 恢复通过以后，重新打开已批准 PR 的自动合并。
7. 唤醒架构师：范围内有工单带 `needs-architect`、参数表的「唤醒架构师」是开、没有架构师进程在运行时，按运行配置第 3 节的命令在架构师的 worktree 中后台启动一个，记下进程号。同一时间只有一个架构师进程，它一次处理全部带这个标签的工单。
   - 架构师进程结束时仍有工单带这个标签，再启动一次。同一张工单连续经过两次启动仍然带这个标签，改为 `ready-for-human`，评论写明架构师没有处理完。
   - 运行超过参数表的时长时，结束这个进程（只结束记下进程号的那一个），剩下的工单留给下一次启动。
   - 架构师处理以后把标签改为 `ready-for-agent`、`needs-review` 或 `ready-for-human`；派发者只看标签，不读处理的内容。`ready-for-human` 的工单等用户决定。

## 4. 合并的条件

main 的规则（定义见运行配置第 6 节）：

- 只通过 PR 合并，只允许 squash。
- CI 的检查 `check` 通过。
- 一个审查批准。分支有新的推送时，原来的批准作废；最后一次推送必须由推送者以外的人批准。
- 不要求分支跟上最新的 main：不同时进行的工单由工单依赖与 `touches-core` 错开，main 上每次合并以后 CI 再运行一次（第 3 节第 6 步）。
- 只有仓库所有者账号可以豁免。派发者使用这个账号，但不使用豁免：不加 `--admin`，不改规则。架构师（包括被唤醒的架构师）用这个账号直接推送文档与日记。架构师每次会话开始时查一次豁免记录。

## 5. 集成层（过渡期）

集成层成为 CI 的检查以前，派发者在交付以后、审查以前运行集成层，做法见[测试分层设计说明](../design/test-pyramid.md)第 4.2 节：

1. 在集成 worktree 中检出 PR 的合并提交（`refs/pull/<PR>/merge`，也就是分支并入 main 的结果），`uv sync --frozen` 以后按运行配置的命令运行集成层全部。
2. 通过：进入第 3 节第 3 步。
3. 失败：先用单进程重新运行失败的测试。仍然失败时，在 PR 评论写明失败项与计数行，把工单标签改回 `ready-for-agent`，交回同一张工单。重新运行通过时，把这个测试记到不稳定测试的工单，按通过处理。
