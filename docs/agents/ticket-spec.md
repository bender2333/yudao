# 工单规范

建立或改写工单时读这份文件，入口是 `/ticket` 技能。GitHub Issues 与 `docs/` 的分工见 [issue-tracker.md](issue-tracker.md)，命令写法也在那里；状态与种类标签见[工作方式](workflow.md)第 4 节。工单正文只写摘要并链接 `docs/` 里的设计、计划与证据。

每张工单带一个分诊标签，`bug`、`enhancement` 等类型标签可以同时使用。阻塞关系用 GitHub 原生的工单依赖，只在一张用到另一张的结果时设。

## 层级与归属

三级工单：

- 阶段工单：一个阶段一张，置顶。写阶段结束时用户能做什么、结束时的总图、进入包、薄片清单（每个薄片的父工单、子工单、试用工单）。
- 父工单：一个桶一张。桶是总图第四节的一道缝或路线图第 3 节的一条道。`/to-parents` 从阶段拆出。父工单正文是设计说明的壳：依据指向设计说明，验收标准取自设计说明的「验收」一节，进度记在 GitHub。
- 子工单：执行者领取的立缝或切片。`/to-children` 从父工单拆出。

里程碑与阶段一一对应：

- 标题用路线图第 2 节的阶段名，五个阶段都建。里面放这个阶段的父工单、子工单、试用工单和试用中发现的缺陷；还没进入的阶段里的工单标 `waiting`，进入时放行。
- 「待排期与阶段总览」放阶段工单与还没有定阶段的工单。定了阶段就移进那个阶段的里程碑。这里不建试用工单。
- 阶段工单与里程碑由总架构师建，子架构师与架构师循环不建。进入一个阶段要三项都成立（[验收证据规则](acceptance-evidence.md)第 6 节），才放行它的工单。

画面的里程碑：

- 画面走路线图第 4 节自己的步，一步一个里程碑，标题 `画面 N：<那一步的名字>`，由总架构师建；第 4 节写明放进某个阶段做的步（步 0「搬出」）不另建。
- 依赖只有一个方向：画面的工单可以以系统的工单为前置，系统的工单不以画面的工单为前置。阶段与薄片的试用只看系统与页面，不等画面。

薄片与试用：

- 一个薄片回答阶段的一个问题（路线图第 2 节的表）。薄片的先后用父工单之间的依赖表示。
- 每个薄片一张试用工单，标题 `[阶段二 试用 ①] <薄片回答的问题>`，薄片达到之前标 `waiting`，不阻塞下一个薄片的工单。最后一个薄片的试用就是阶段的试用。
- 阶段工单在三件事都完成后关闭：里程碑已关闭；阶段结束核对已完成（验收证据规则第 6 节）；它名下没有里程碑的子工单都已关闭、迁入下一个阶段或标 `wontfix`。

清理单：

- 不回答阶段问题、要改代码或测试的维护工作，例如删重复与过期的测试、清理脚本。判断办法：不做它，这个阶段的问题还答得了，就是清理单；答不了就是这个阶段的工单。
- 归在所属的父工单下（测试清理在测试清理父工单下，其余在阶段工单下），不放进里程碑，不阻塞试用；依赖某个阶段里的工单时设工单依赖。
- solo 把它们列进范围时一起做。跟踪类的清理单在阶段结束核对时关闭，剩余项另开工单。
- 文档、归档与规则文件的清理不开工单（`CLAUDE.md`「文档维护与归档」）。

## 一张子工单怎么写

工单写结束条件（验收标准、覆盖要求、要改的清单条目），执行者能不能做哪件事不写在工单里。

- 标题：`[桶或道] 动作与交付目标`，例如 `[路由的缝] 第二种路由接上契约测试`。正文用中文，结构、「依据」「环」「只改」「验收」的格式以 `/to-parents` 与 `/to-children` 的模板为准，设计文档链接写在「What to build」。
- 依据：写设计说明的路径加小节标题（不写节号和行号）、放出工单时核对过的 main 提交、总图位置。执行者用提交判断设计说明在放出以后有没有改动，用总图位置知道改的是哪道缝、守哪些规矩。
- 大小：「只改」列出要改的文件，手写文件个数不超过运行配置第 7 节的上限，超过时拆单。一张工单是一次执行者会话做得完、CI 全部通过的纵向切片。上限由架构师拆单时守，执行者发现超过，记日记继续做，一轮做不完分多轮。
- 同时可做的工单不改同一处代码：两张没有依赖的工单「只改」落在同一份文件的同一块，拆单时调整切片或合成一张，不靠排队错开。执行中遇到的冲突执行者自己解；两边改了同一段逻辑、取哪一边都丢行为的才交回，由架构师重新拆。没有依赖的工单可以同时进行，不限张数。
- `touches-core`：「只改」包含核心文件（运行配置第 7 节）的工单加这个标记，合并前在分支上跑一次集成层。
- 环：写改的是总图第二节哪一环与要守的规矩。只增环要带版本、字段只增；需你批准环指改内核路径。环告诉执行者守什么，放出工单不以它为条件。
- 内核路径：改内核路径的工单不事前批准、不加标签，执行者像普通工单一样领取、合并。内核由机器守：`harness/tests/kernel/test_manifest.py` 查内核只导入内核、标准库与 pydantic，查总行数不超过上限且上限只降不升；改动前后覆盖读数不降，改动的行有测试执行到（`AGENTS.md` 共同要求「内核路径的测试覆盖」）。覆盖要求默认是共同要求的三条，工单可以写更高的数。总图第二节「只由你批准」指运行中的系统改自己的内核，这道环在第二层自举时再立。
- 接口合同：改接口合同的工单包含重新生成的接口快照与客户端类型，以及让客户端类型检查与单元测试通过的最小改动；新画面、样式与文字另成工单。
- 两端共用的枚举或清单（事件种类、停止原因、查询能力）：工单带一份两端共读的夹具与两端各一条一致性测试。服务端核对枚举与夹具一致，客户端核对声明表覆盖夹具，缺行即报错。
- 删减功能：工单在「只改」与验收中写明删除的行为（[测试分层设计说明](../design/test-pyramid.md)「用例的变化」）。守着这些行为的用例由执行者随工单删，交付说明逐条列出，架构师事后用 CI「用例变化」对照。重构单与清理单按测试分层设计说明「一个测试凭什么留」的删除口径删重复、下移与过时的用例，写明接替的用例。两种都要删了以后覆盖率不降，内核测试也一样。
