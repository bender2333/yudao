# 工作方式

开发 Yudao 的流程按 Yudao 自己的结构做：一份事实（GitHub 与 `docs/`），四个循环，边界（角色的权限与工单的「只改」），裁决（CI、内核改动的独立审查、用户试用）。每个角色进来先读状态，做一件事，做完留下证据：改代码的工作在工单上留评论，其余的工作以提交与变更记录为证据。这份是流程的正本；技能写怎么做一段流转，引用这里，不复述。

## 1. 事实放在哪

每种事实只在一处。

| 事实 | 位置 | 谁定 | 谁改 |
| --- | --- | --- | --- |
| 意图：目的、判据、基础规则的意思；评价标准 | [D38](../requirements/system-intent.md)、[基础规则](../foundation-rules.md)、评测的隐藏检查、参考解法、评分器与发布检查 | 用户 | 总架构师 |
| 系统的形状、三环、缝，缝的已定未定 | 总图 `docs/architecture.html`、画面总图 | 用户 | 总架构师 |
| 阶段、薄片、十条道 | 路线图 `docs/program-roadmap.md` | 用户 | 总架构师 |
| 模块怎么分、每道缝细化在哪 | 总体架构 `docs/design/architecture/`、对照表 | 用户与子架构师 | 子架构师 |
| 一个方框或一道缝怎么做 | 设计说明 `docs/design/`（[设计说明规范](design-spec.md)） | | 子架构师 |
| 为什么这样定 | 需求记录、ADR、调研、原型 | | 架构师 |
| 术语 | 术语表 `CONTEXT.md` | | 架构师 |
| 工单正文、依赖、子工单 | GitHub Issues：标签是状态，原生子工单与依赖是结构，里程碑是阶段 | | 架构师（状态标签按第 4 节） |
| 阶段工单与里程碑：建、关、改名 | GitHub | | 总架构师 |
| 试用结论与试用工单、里程碑的关闭 | 试用工单的关闭评论（[验收证据规则](acceptance-evidence.md)第 5 节） | 用户 | 架构师 |
| 每次状态变化的证据 | 那张工单上一条带前缀的评论 | | 按第 5 节 |
| 代码达到合同的证据 | PR 与 CI | | solo 执行者、审查者、CI |
| 代码与测试 | `harness/`、`client/`、`evals/` | | solo 执行者 |
| 合并 PR 与推送 main | GitHub | | solo 执行者；架构师（只推文档） |
| 观察、报告、想法 | GitHub Discussions | | 任何角色 |
| 规则 | `CLAUDE.md`、`AGENTS.md`、`docs/agents/`、技能 `.claude/skills/`、CI 工作流 | 用户 | 总架构师；用户不在场时架构师循环 |
| 过程与理由 | `claude_jour.md`、`agents_jour/`、`docs/decision.md`、`docs/CHANGELOG.md` | | 任何角色 |

Discussions 不表示工单的状态。帖子里要改代码的事转成工单，在帖子里回一句「已转 #编号」；要改设计、原型或文档的事直接改，回一句改了哪份文档；总图与规则的事开 `architecture` 工单（第 7 节）。分类：Announcements 放复盘，General 放试用报告，Ideas 放等分诊的想法，Show and tell 放只读的扫描与差异报告。

引用只往上指：工单、代码注释与规则登记引用设计说明，设计说明引用总图，反过来不引用。

## 2. 角色

| 角色 | 做什么 | 不做什么 |
| --- | --- | --- |
| 用户 | 定走向、规则、试用结论；看总图、对照表与工单点到的契约文件 | 不写代码与测试，不定工单正文，不审也不合并 PR |
| 总架构师 | 总图、路线图、规则与理念；建阶段工单与里程碑；阶段的结束核对；处理 `architecture` 工单 | 不管其余工单层面的事 |
| 子架构师 | 一条工作线或一个模块：讨论、设计说明、拆单、分诊、验收、试用准备 | 不改总图；不改代码与测试 |
| 架构师循环 | 用户不在时的子架构师，做同样的事 | 不改意图；不关试用工单与里程碑 |
| solo 执行者 | 领子工单，实现、自测、开 PR、写交付说明、合并前核对、合并 PR 与推送 main | 不改总图与规则 |
| 审查者 | 只审改到内核代码的 PR（第 8 节），在全新的上下文里 | 不推送，不改标签 |
| agent 试用者 | 用从 main 打包的实例走真实用户的路子，写试用报告 | 不建工单 |

## 3. 工作的层级

工单只管改代码与测试的工作。其余的工作都不走工单：架构设计（总图、路线图、总体架构、ADR）、模块设计（设计说明、需求记录、术语表）、原型设计（原型页面也算在内）、规则修改（规则文件、技能、CI 工作流）、调研、文档的整理与归档。这些由第 1 节「谁改」一列的角色直接改，推送 main，记入 `docs/CHANGELOG.md` 与日记，不起草工单，也不建工单占位。设计或原型定了、要改真实代码时才建工单，工单的「依据」指向设计说明。

`architecture` 工单不做这些工作，只把要总架构师定的问题交上去：它有标签、看得见、关闭时留下结论，被挡住的代码工单靠它接着流转（第 7 节）。总图与规则本身仍由总架构师直接改。

代码工作的层级：

```
阶段      里程碑 + 置顶的阶段工单；终点是路线图里这个阶段的「结束时总图」
└ 薄片    试用工单；用户能试用的一段
  └ 父工单  一个桶：总图的一道缝或路线图的一条道；正文是设计说明的壳
    └ 子工单  一个 PR 做完的立缝或切片：依据、环、只改、验收
另有：缺陷单、清理单、交总架构师的问题（`architecture` 工单）
```

工单怎么写见[工单规范](ticket-spec.md)。

## 4. 状态与标签

每张打开的工单只带一个状态标签：

| 状态 | 意思 | 谁改成它 |
| --- | --- | --- |
| `waiting` | 在等一个前提条件，条件写在最后一条评论里；父工单等子工单不另写 | 架构师 |
| `ready-for-agent` | 规格齐全，可以领 | 架构师 |
| `in-progress` | 有人在做 | 执行者领取时 |
| `needs-review` | PR 与交付说明都在，合并前核对中 | 执行者 |
| `needs-triage` | 交回架构师：设计问题、规则矛盾、验收做不到、冲突两边都丢行为、连续三轮没过。新报告的问题也标它 | 任何角色 |
| `ready-for-human` | 要用户做或定：执行环境、要用户提供的条件、试用 | 任何角色 |

种类标签，有就带一个：`stage`（阶段工单）、`trial`（试用工单）、`parent`（父工单）、`cleanup`（清理单）、`bug`（缺陷）、`architecture`（交总架构师的问题）。子工单不另带种类。另一个标记 `touches-core`：「只改」含核心文件，合并前在分支上跑一次集成层（核心文件的清单在[运行配置](autopilot-runtime.md)「参数」）。

标题：`[缝或道] 动作与交付目标`；试用工单 `[阶段二 试用 ①] 薄片回答的问题`。

## 5. 证据评论

每次状态变化在工单或 PR 上留一条评论，第一行以前缀开头。下一个人读这些评论就能接上，不用回翻会话，所以每一段流转都可以从干净的上下文开始。

| 前缀 | 谁写 | 写什么 |
| --- | --- | --- |
| `DELIVERY:` | 执行者 | 改了哪些文件、测试命令与计数、逐条验收与证据、删掉的用例与理由、覆盖读数 |
| `REVIEW:` | 审查者 | 批准或要求修改，逐条理由 |
| `ARCHITECT:` | 执行者 | 卡在哪里、事实（文件与行号、命令与结果）、建议、需要谁决定 |
| `TRIAGE:` | 架构师 | 交回的结论：拆小、改正文、补设计、交上一级 |
| `VERDICT:` | 架构师 | 验收标准逐条：过了、没过、说不清；说不清不算过 |
| `TRIAL:` | 架构师 | 试用工单上薄片走到哪一步：`TRIAL: <达到 \| 复盘 \| 试用 \| 缺陷 \| 发布 \| 走查 \| 导游卡> @ <main 短提交>`；导游卡那一条写启动命令、这次看得见的变化与去哪里看、立住了哪几道缝 |
| `HANDOFF:` | 任何角色 | 停下时：做到哪里、还剩什么、下一步 |

## 6. 四个循环

```
内循环    子工单 → PR → CI → 合并前核对（内核改动加独立审查）→ 合并          solo 执行者
中循环    父工单的子工单全部关闭 → VERDICT → 没过的补成缺口子工单           子架构师或架构师循环
外循环    薄片达到 → 复盘 → agent 试用 → 明确缺陷修完 → 发布走查 → 导游卡
          → 用户试用 → 反馈分流：缺陷成子工单；模块走向交子架构师；总图边界成 architecture 工单
自我改进  复盘的教训：能写成 CI 检查的写成检查，否则改到某个技能的某一段；
          每条改动写预期与撤回条件，下一次复盘对账
```

外循环的顺序与证据见[验收证据规则](acceptance-evidence.md)「试用工单与里程碑的关闭」；阶段的结束与进入见同一份「阶段的结束与进入」。试用期间继续推进下一个薄片。

## 7. 出问题往哪交

一条路往上交，每一级先在当时的 main 上核对前提，只处理自己这一层：

| 卡在 | 交给 | 怎么交 |
| --- | --- | --- |
| 执行环境、要用户提供的条件 | 用户 | `ready-for-human`，评论写要用户做什么 |
| `needs-triage` 的理由（第 4 节） | 子架构师或架构师循环 | `ARCHITECT:` 评论，`needs-triage` |
| 与总图冲突、总图缺了什么 | 总架构师 | 一张 `architecture` 工单，写现象、总图哪一节、要定什么；相关工单 `ready-for-human`，`TRIAGE:` 评论写明它的编号 |
| 规则本身要改 | 总架构师；用户不在场时架构师循环 | 直接改，记入 `docs/CHANGELOG.md` 与 `claude_jour.md` |
| 意图要改：目的、判据、基础规则的意思 | 用户 | 一张 `architecture` 工单，写现象与要定什么，等用户；相关工单 `ready-for-human` |

总架构师定了以后直接改总图或规则，在 `architecture` 工单上评论结论并关闭。被它挡住的工单由子架构师或架构师循环按 `/triage` 核对后放回。

执行者不交回的情况（文件超上限、要改「只改」以外的文件、依据改过、点名的东西搬了家、设计没写到的边界）见 `AGENTS.md`「请架构师处理」。

## 8. 独立审查

改到可信内核代码的 PR（内核清单 `harness/definitions/kernel-manifest.json` 里 `kind` 为 `module` 的路径，或清单本身），solo 执行者在合并前派一个全新上下文的审查子代理，按 `reviewer` 技能审，结论写成 `REVIEW:`。批准了才合并；要求修改算这一轮没过，改完再审。其余 PR 由 solo 执行者按 `solo-worker` 技能的合并前核对自己合并。

## 9. 技能

**入口 `/next`**：读 GitHub 的状态，按下面的顺序取第一件能做的事，把对应技能的步骤原样抄进待办，不做的步骤留着写「skip：原因」。

1. 等用户的事（只在用户在场时，先出一张不超过 10 行的卡）
2. `needs-triage` 的工单；挡住它的 `architecture` 工单已关闭的 `ready-for-human` 工单
3. 子工单全部关闭的父工单（验收）
4. 达到的薄片（试用）
5. 设计未写的桶（阶段工单的薄片清单里记着）
6. 还没拆的父工单
7. Discussions 的 Ideas

用户在场与不在场是同一个入口，权限只差意图这一处，其余不等用户：

| | 用户在场 | 用户不在场（架构师循环） |
| --- | --- | --- |
| 改意图：目的、判据、基础规则的意思（[D38](../requirements/system-intent.md)、[基础规则](../foundation-rules.md)） | 可以，用户定了以后总架构师改 | 不可以，开一张 `architecture` 工单等用户 |
| 改其余规则、CI 工作流 | 可以，改完告诉用户，记入 `docs/CHANGELOG.md` 与 `claude_jour.md` | 可以，同样记入，日记里写明用户不在场 |
| 改设计说明、拆单、分诊、验收、试用准备 | 可以 | 可以 |
| 关闭试用工单与里程碑 | 可以，用户确认以后 | 不可以 |

**技能**（每个管一段流转；用法与例子见[技能使用说明](../../.claude/skills/README.md)）：

| 技能 | 管什么 | 调用的积木 |
| --- | --- | --- |
| `discuss` | 想法 → 结论，同时更新术语表与 ADR | grilling、domain-modeling、research、prototype |
| `module-sync` | 一个模块的体检卡与走向选择 | codebase-design |
| `to-design` | 结论 → 设计说明，开头写总图位置，更新索引 | codebase-design |
| `to-parents` | 阶段或模块 → 父工单，旧工单定去向 | ticket |
| `to-children` | 父工单 → 子工单 | ticket |
| `solo-worker` | 子工单 → PR → `DELIVERY:` → 合并 | tdd、diagnosing-bugs |
| `reviewer` | 内核 PR → `REVIEW:` | code-review |
| `verify` | 父工单与阶段 → `VERDICT:` | seam-diff |
| `trial-intake` | 薄片：agent 试用、缺陷、发布走查、`TOUR:`、反馈分流 | trial、discussion-note |
| `triage` | `needs-triage`、Ideas、外部报告 → `TRIAGE:`；代替 Matt 的 `/triage` | grilling |
| `milestone-retro` | 证据 → 教训 → 检查或技能改动 | — |

`solo` 是执行者的循环，按范围一轮一轮跑 `solo-worker`；架构师循环是 `/next` 在用户不在场时一件一件做下去。积木直接调用，不复制进来：grilling、domain-modeling、research、prototype、tdd、diagnosing-bugs、code-review、codebase-design、ticket、trial、seam-diff、doc-scan、discussion-note。

**每个技能用同一副骨架**：

```
何时用 / 何时不用
先读什么（只列这一段要的）
步骤（每步带「完成：」）
常见借口（这一段真实发生过的跳步说法，和为什么不行）
危险信号
交付：改成哪个状态、留哪个前缀的评论；回复交代哪几项
```

各个技能都会碰到的借口：工单关了就当建好了；CI 绿了就当验收过了；子代理说过了就当核对过了；用户不在，这一步先跳过；设计还没写，先拆了再说。

## 10. CI

合并前的 `check` 与合并后的集成层见[测试分层设计说明](../design/test-pyramid.md)「CI 中的分层」。另有几项只显示、不挡合并的检查：

| 检查 | 什么时候 | 防住什么 |
| --- | --- | --- |
| 用例变化 | 每个 PR | 删除与交付说明对不上 |
| 状态自洽：每张打开的工单只有一个状态标签；父工单关了子工单还开着；`ready-for-agent` 缺验收；`in-progress` 太久没动静；试用工单关了没有用户确认 | 每天一次 | 状态与事实对不上 |
| 工单正文：子工单有依据、环、只改、验收；父工单有总图位置 | 工单新建或编辑 | 含糊的工单流到执行者 |
| PR 改动的文件对照「只改」 | 每个 PR | 越界的修改 |
| 设计说明第 3 行是总图位置，正文不出现工单号，链接都在 | 改到 `docs/design/` | 设计说明变成进度表 |
| 技能有骨架的段落，引用的文件与技能都在 | 改到 `.claude/skills/` | 技能变粗、变重复 |

复盘时从 GitHub 算读数：首轮通过率、交回率、试用发现的缺陷数、从放出到合并的时长。

## 11. 规则事实怎么写

规则事实指谁做、只由谁、谁不、是不是清单一员、以谁为准、在场可否、交给、穷尽清单这几类话。它们的正本是第 1、2、4、5、7 节与第 9 节权限表里的表格，以及[验收证据规则](acceptance-evidence.md)第 1 节的结论表，每条事实只在一张表的一列里写一次。正本以外只许两种写法：引用，或下面的句式。

| 写法 | 例子 |
| --- | --- |
| 引用 | `needs-triage` 的理由见第 4 节 |
| 由谁 | `DELIVERY:` 由执行者写 |
| 只由谁 | 总图只由总架构师改 |
| 谁不 | 审查者不推送 |
| 是不是清单一员 | 文件超上限不是 `needs-triage` 的理由 |
| 以谁为准 | 设计说明与 ADR 冲突时以设计说明为准 |
| 在场可否 | 用户不在场时架构师循环不可以改意图 |
| 交给 | 执行环境的问题交给用户 |
| 穷尽清单 | 只有设计问题、规则矛盾、验收做不到、冲突两边都丢行为、连续三轮没过是 `needs-triage` 的理由 |

主语写出来，不写「你」或祈使句；角色用第 2 节的名字、合称（架构师、任何角色）或机器（CI、脚本、钩子）；键用正本的首列或第 1 节「位置」里的载体名；清单条目用正本的条目名；「在场」「之前」这类限定另写一句或放括号；「以谁为准」只对规则的载体，数据与运行状态的优先级是流程，不算规则事实；用户只有定与确认两个动词。表格里只写「按第 N 节」的格子是引用。改规则文件后运行 `tools/doc-consistency` 的 `rules check`。
