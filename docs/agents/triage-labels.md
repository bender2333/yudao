# 分诊标签

技能用五个分诊角色说话，这份文件把角色对应到本仓库实际使用的标签字符串。

| 技能中的角色 | 本仓库的标签 | 含义 |
| --- | --- | --- |
| `needs-triage` | `needs-triage` | 维护者需要评估这张工单 |
| `needs-info` | `needs-info` | 等报告人补充信息 |
| `ready-for-agent` | `ready-for-agent` | 规格完整，可以交给无人值守的 agent |
| `ready-for-human` | `ready-for-human` | 需要人来处理 |
| `wontfix` | `wontfix` | 不处理 |

技能提到某个角色时（例如「加上 AFK-ready 的分诊标签」），用表中对应的标签字符串。

五个标签在 `bender2333/yudao` 中都存在。`wontfix` 是 GitHub 的默认标签，其余四个随这套配置创建。GitHub 默认的 `bug`、`enhancement`、`question` 与这五个正交：它们说明工单**是什么**，这五个说明工单**在分诊中的位置**。

## 等前提条件的工单：`waiting`

`waiting` 是本仓库另加的标签，不属于技能的五个角色：工单在等一个前提条件，条件写在工单最后一条架构师评论里；父工单等的是子工单，看子工单的进度，不另写评论。前提条件满足时，架构师在当时的 main 上核对正文，改为 `ready-for-agent` 或 `ready-for-human`。标 `waiting` 的有：

- 试用工单（每个薄片一张，见 `CLAUDE.md`「工作流程」第 7 步）：薄片的工单全部关闭、集成层通过、架构师按试用指南走查以后，改为 `ready-for-human` 交给用户。
- 子工单还没有全部关闭的父工单，以及下面的父工单与里程碑还没有全部关闭的阶段工单。
- 排在正在派发的里程碑之后、到那时按当时的代码重写正文的工单。
- 等用户提供条件的工单，例如模型、机器或真实项目。
- 阶段收尾的手动检查（全部父工单关闭以后进行）、以后专题的占位工单、试点开始之前的自举试点工单。
- 还没有进入的阶段里的工单：这个阶段的四项进入条件（[验收证据规则](acceptance-evidence.md)第 6 节）成立之前一直标 `waiting`；成立以后由总架构师去掉，按本节开头的办法逐张在当时的 main 上核对正文。

## 不再使用的标签：`kernel-approved`

`kernel-approved` 是 2026-10-26 加的事前批准标签，2026-10-27 起不再使用（用户决定）：改内核路径的工单不事前批准，与其他工单一样标 `ready-for-agent`，守内核的是 CI 里的内核测试、内核清单的检查与测试覆盖（`CLAUDE.md`「工单规范」「环」一条）。旧工单上的标签与批准行只是历史，不表示任何许可。

`needs-triage` 只用于四种情况：新报告的工单等架构师评估；新子工单核对规格期间（[验收证据规则](acceptance-evidence.md)第 4 节）；架构师退回工单、改写正文期间；Ralph 循环（solo 模式）里同一张工单连续三次没有通过，循环停止重试、交回架构师评估。

## 自主推进模式的流程标签

自主推进模式（见[派发者规则](dispatcher.md)与 `AGENTS.md`）另用三个标签表示工单在执行、审查与架构师之间的位置。同一时间一个工单只带其中一个，切换时去掉原标签。

| 标签 | 含义 | 由谁加上 |
| --- | --- | --- |
| `in-progress` | 执行者正在处理 | 执行者，领到 `ready-for-agent` 工单时 |
| `needs-review` | CI 已通过，交付说明已写在 PR 上，等待审查 | 执行者，在 PR 上发出 `DELIVERY:` 评论后 |
| `needs-architect` | 等架构师处理：执行者交回、审查者请架构师处理、要求修改达到上限、执行或审查异常结束、依据的设计说明在放出以后有改动 | 执行者，在工单上发出 `ARCHITECT:` 评论后；其余由派发者 |

solo 模式（`AGENTS.md`「Solo 模式」）使用同一套流程标签，由 solo 执行者自己切换：领取时 `ready-for-agent` 改为 `in-progress`，交付评论发出以后改为 `needs-review`（此时是合并前的自我核对，没有别的审查者），核对不通过改回 `in-progress`，合并后工单关闭并去掉标签；设计问题、工单太大与连续三次没过的交回架构师用 `needs-triage`（下面三条通道），执行环境挡住的改为 `ready-for-human`。不使用 `needs-architect`。

Ralph 循环把「连续三次没有通过」当作停止信号：同一张工单连着三次失败以后，循环不再重试它，把标签从 `in-progress` 改成 `needs-triage`，并在工单上留一条评论写清三次分别卡在哪、已经试过什么、需要什么。架构师重新评估这张工单；`needs-triage` 不会启动被唤醒的架构师，架构师在场的会话与用户一起处理它。

循环在每一批派活以前按外部状态刷新一次台账：已经关闭的工单标成完成，带 `in-progress` 或 `needs-review` 的（别人正在做）这一轮不派，带 `waiting` 或 `ready-for-human` 的标成等前提条件，带 `needs-triage` 的不再进候选。台账与外部状态对得上才派活。

循环交回外部有三条通道：同一张工单连着三次没有通过，用 `needs-triage` 升级；任务里遇到架构、需求、设计上的问题，用 `needs-triage` 提问题（结构化评论：发现了什么、建议怎么做、需要谁决定）；**执行环境挡住了任务**（缺凭据、权限不够、CI 平台挂了、依赖装不上），用 `ready-for-human` 转给用户，工单上写清哪一步被挡住、已经试过什么、需要什么。外部处理完标签改回 `ready-for-agent`，循环刷新时重新排上。

审查的结论是 PR 审查的状态（批准或要求修改），不用标签表示。要求修改后，派发者把标签改回 `ready-for-agent`；卡住的工单改为 `needs-architect`，派发者启动架构师。架构师处理以后改为 `ready-for-agent`、`needs-review` 或 `ready-for-human`，`ready-for-human` 表示架构师已经看过、要用户决定。`needs-architect` 与 `needs-triage`、`waiting` 是两回事：架构师自己退回工单、改写正文期间用 `needs-triage`，等前提条件用 `waiting`，都不会启动被唤醒的架构师。

另有一个标记 `touches-core`：工单的「只改」包含核心文件（范围见[运行配置](autopilot-runtime.md)第 7 节），由架构师放出工单时加上。带它的工单合并前在分支上跑一次集成层，「只改」以外的文件不改、要改就交回。它与上面的标签同时存在，不限制同时进行的张数，也不表示先后；先后用工单依赖表示。

2026-10-14 以前用过的 `review-passed`、`review-failed` 不再使用。仓库里保留这两个标签，已有工单上的记录供评测统计使用。
