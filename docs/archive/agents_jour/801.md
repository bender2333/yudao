2. **根因与出处**：
   - `client/src/renderer/src/views/project/department.tsx` 第 183 行：链接自己拼了 `?dept=`，页面上的文案承诺了部门筛选。
   - `client/src/renderer/src/shell/routing.ts`：`parseRoute` 只读 `?w=`、`?at=`、`?round=` 三个参数，`?dept=` 没有任何地方读它。
   - `client/src/renderer/src/views/project/observe.tsx`：筛选条件是页面内的局部状态（draft / applied），初始为空，要在「部门」下拉里选部门、再点「按条件筛选」才生效；地址带来的部门筛选条件进不来。
   - 服务端不是问题：`project.attempts` 与 `project.usage` 都接受 `department` 参数（`harness/app/project_queries.py` 的 `ProjectAttempts`、`ProjectUsage`），过滤条件齐备，不用改服务端。
3. 语义定下来（写在这里，事后好核对）：**范围与筛选条件分开，不造第三种含义**。
   - `?w=` = 事项范围（作用域）：看的是哪些事项的请求；项目级的一份（#746 已定）。
   - `?dept=` = 观测页的部门筛选条件（筛选条件，不是范围）：看的是哪个部门的请求。
   - 据此定下的取舍：部门工作间的「本部门的模型请求」把本部门带进观测页，落到页面时这一格筛选立刻生效（请求记录与用量统计用同一组筛选）；观测页自己换这一格筛选时地址跟着改，清掉时地址里去掉这个参数——地址里写的与页面上生效的始终是同一件事，刷新、后退与分享链接都对得上；换事项范围时这一格筛选不丢（`?w=` 与 `?dept=` 各自保留）；请求详情页与「返回请求记录」的链接带着它；只有已知的部门取值才认，未知取值按没有筛选处理，不把无效的部门发给服务端；页面上用部门的中文名说明当前筛选的是哪个部门。
4. 实现（纯客户端）：
   - `client/src/renderer/src/shell/routing.ts`：`Route` 增加 `departmentFilter`；`parseRoute` 读 `?dept=`（只认已知的部门）；`paths.observe` 与 `paths.observeDetail` 接受部门；`withScope` 换范围时保留这一格筛选。
   - `client/src/renderer/src/views/project/observe-filter.ts`（新增）：筛选条件的类型、空条件、进入页面时的初值（`seedFilters`）、页面上说明当前筛选的部门（`departmentFilterNote`，中文名）。
   - `client/src/renderer/src/views/project/observe.tsx`：进入页面时以地址里的部门为初值；地址里的部门变了（后退、前进、别的页面带进来）时，下拉里的初值与已生效的筛选都跟着变；「按条件筛选」与「清除筛选」把这一格写回地址；页面上的说明写明当前只看哪个部门的请求；进请求详情与返回请求记录都带着这一格筛选。
   - `client/src/renderer/src/views/project/department.tsx`：链接改用 `paths.observe`（不再自己拼地址）。
   - `client/src/renderer/src/app.tsx`：页签的观测页地址带着这一格筛选（点当前的观测页签不会把筛选丢掉）。这一处不在分诊评论的只改清单里，实现时补记在工单评论上。
5. 测试：
