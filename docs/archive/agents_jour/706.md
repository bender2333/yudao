1. 起因：#669 合并以后 main 的集成层一直红着一条用例（`harness/tests/test_project_queries.py::test_the_action_receipt_shows_the_command_text`），#658 与 #697 两次 main 推送都有这一条失败。合并前的检查看不到它（集成层按规则在合并以后运行）。
2. 定位（两步）：
   - 先在运行机上拿到现场：发一个调试分支，把运行的阶段与停止原因、动作视图、事件序列写进断言信息，用 `gh workflow run CI --ref <分支>` 手动跑一次集成层，从运行日志里读到运行以 `TreeError: Git ignore rules cannot be decided: ... path too long: '.../product.yudao-ignore-probe.git/'` 结束，动作停在「结果未知」。
   - 再在本地复现：用同样深的临时目录（`--basetemp` 指向 `...\pytest-of-runneradmin\pytest-0\popen-gw3\test_the_action_receipt_shows_0`）跑同一条用例，同样的报错。根因落在 `harness/public_tree.py` 的 `ignore_probe_directory`：忽略规则的判断要在工作区旁边建一个 Git 探测库，而 libgit2 拒绝长度超过约 190 个字符的仓库路径（实测：探测库路径 189 个字符正常，193 个字符失败）。
3. 实现（`harness/public_tree.py`）：
   - 探测库不再放在工作区旁边，改放在系统临时目录下一个进程专属的目录里（`yudao-ignore-<进程号>`），名字取工作区绝对路径的摘要（前 12 位 sha256）加原来的后缀，两个工作区不会共用一个探测库；进程退出时整个目录删掉（atexit）。
   - 判断结果不变：探测库仍然是空的裸库（空模板、`core.excludesFile` 指向空设备），工作树仍然显式指向被判断的工作区。探测库的位置本来就不参与规则判断——规则来自工作区的 `.gitignore` 与探测库自己的 info/exclude（后者始终为空），工作树是显式挂上的；改动只是把「空探测库」放到一个短路径上。
   - 路径长度与工作区深度无关，深的数据目录不再让每一次运行都失败。
4. 测试：`harness/tests/test_public_tree.py` 新增一条用例——工作区路径深到旧做法会超限时，忽略规则的判断仍然成功，结果与 Git 命令行一致。反向验证：把 `ignore_probe_directory` 改回旧做法，这条用例以同样的 `path too long` 失败。
5. 顺带核对了受影响的人：探测库只在工作区里有忽略文件（`.gitignore` 或 `.git`）时才会被打开，所以没有忽略文件的工作区不受影响；真实项目通常有 `.gitignore`，因此深路径的数据目录对用户是真实的影响，不是只在 CI 里出现。
