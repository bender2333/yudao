1. 分诊（工单评论）：先查恢复页的状态是从哪里推出来的——服务端算出来的。`harness/recovery.py` 的 `observation_state` 只看 run 是否处在终态（`terminal`），不区分结束的方式；`harness/app/project_queries.py` 的 `RunRecoveryResult.state` 同样只有四个取值（运行中、中断、待恢复、已终止）。中文的「已终止」与像素标记「已取消」都在客户端（`labels.ts` 的 `RECOVERY_STATE`、`recovery.tsx` 的 `STATE_KIND`），但根因在模型：正常完成没有自己的状态。`harness/tests/test_issue_18_recovery_observation.py` 第 135 至 148 行断言「完成的 run 观察状态为已终止」，是工单 #18 定的口径，所以这是口径问题，模型、测试与设计说明要一起改。
2. 口径的来由（读了几处已有的词表再定）：「已终止」「已取消」这两个说法在项目里各有意思——#735 的架构师结论是「运行已被取消」说的是运行、「已取消」说的是事项，两句都对，本工单按这个口径把「已取消」留给被取消的事项；楼层的状态词表里 `done` 是「已完成」、`cancelled` 是「已取消」、`paused` 是「已暂停」，事项状态表里 `stopped` 是「已停止」。恢复页是运行层的页面，跟着这些词表走。
3. 定下来的七种状态与页面说法：运行中、中断、待恢复（三种未结束），已完成（阶段 DONE）、已暂停（阶段 PAUSED）、已取消（停止原因是 cancelled）、已停止（其余结束方式：执行失败、因 Yudao 升级停止等）。标记一一对应：运行中、暂停、成功、已取消、失败。
   - 「已完成」与「已停止」分开是本工单的要害：中文的「已终止」是被中止的意思，用在成功交付上读起来是错的。
   - 「已取消」单独一个状态：被取消的事项要一眼看得出是取消，不能被含糊的词盖住。
   - 「已暂停」也单独一个状态：只把「已完成」拆出来的话，暂停等待用户处理的事项会落进「已停止」，页面上给它一个失败的标记（✗），那是新造出来的错。暂停是真实存在的情形（模型连续不调用工具时运行暂停等回答），所以给它自己的说法与标记。
   - 「已停止」而不是「失败」或「执行失败」：阶段 FAILED 同时覆盖真正失败与因升级停止，后者不是失败；「已停止」也是概览页上同一个事项的写法，两个页面不打架。
4. 概览页与恢复页的说法怎么对齐：概览页的事项卡片对这件事写的是「已采纳 · 已完成」（事项状态 + 阶段名，`labels.ts` 的 `phaseLabel` 对阶段 DONE 给「已完成」），恢复页现在的说法是「已完成」——**同一个词说同一件事**，不再出现「已终止」与「已采纳」互相打架的情况。所以没有动恢复页的页头，也没有另加一行事项状态。
5. 页面上不再出现机器标识：`运行以 baseline_verified 结束` 改成用停止原因的中文名（`harness/models.py` 的 `STOP_REASON_LABELS` 是这份中文名的单一来源），`进程在 ENGINEERING 阶段停止` 改成阶段的中文名（`harness/app/labels.py` 的 `phase_name`）。客户端的 `STOP_REASON` 与服务端的这份中文名一一对应，两边不各写一套。
