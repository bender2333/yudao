2. 核对的事实（服务端 `harness/app/read_models.py` 的流转推导，事件种类表 `FLOW_TYPES`）：阶段状态机删掉以后（工单 #556）流转记录只有三种——
   - 交付到达（`delivery_accepted`）给出「版本交付」，工程→质检，状态「已完成」；
   - 询问的开始与结束（`ask_started` / `ask_answered`）各给出一条「询问」，方向是提问方→被询问方；
   - 质检提交缺陷记录（`qa_submitted`，结论为 `rework_engineering`）给出「问题反馈」，质检→工程，状态「已退回」。
   事件种类里已经没有「返工」，也没有「需求交接」。
3. 缺陷的根因在客户端，三个地方：
   - `client/src/renderer/src/views/project/flow-segments.ts:20` 的分组条件写 `record.kind === "返工"`，永远不成立；分组键因此少了返工这一维，同一对部门的全部行并成一段。
   - 后果之一在 `client/src/renderer/src/pixel/floor/render.ts:634`：牌子的颜色按段的 `kind === "rework"` 取红色，段的 kind 永远取不到 "rework"，返工那块红牌子不再出现。
   - `client/src/renderer/src/views/project/overview.tsx:439` 的流转记录表里 `record.kind === "返工"` 同样不成立（后半句 `record.status === "已退回"` 有效，删掉前半句即可，行为不变）。
4. 端到端用例证实了这条缺陷：改之前 `client/tests/e2e/floor.spec.ts` 的「流转覆盖层」一条跑不过——预置的「交付历史」项目在 quality→engineering 上真实发生的两条行是「询问」与「问题反馈」，用旧写法数「返工」的行得到 0（用例期望 1），「问题反馈」被并进非返工段，quality→engineering 只有一段而不是两段，全画面也不是四段。
5. 实现：
   - `flow-segments.ts`：返工判定改成一个具名的常量 `REWORK_KIND = "问题反馈"`，段的 kind 照旧写 "rework"（画面按它取红色，是画面内部的标记，不出现在页面上）。
   - `overview.tsx`：只改那一处判断，删掉不会命中的前半句，按「已退回」判断醒目的颜色。
   - 单元测试 `client/tests/unit/flow-segments.test.ts`：数据换成现在的流转种类。工程→质检的「版本交付」与「询问」合成一段（次数 2）；质检→工程的「询问」与「问题反馈」各成一段（问题反馈是返工段，kind 写 rework）。期望值写成字面值，不复用实现的分组公式。
   - 端到端 `client/tests/e2e/floor.spec.ts`：「流转覆盖层」一条的预期按真实事件改写——预置项目在 quality→engineering 上有「询问」与「问题反馈」各一条，全画面四段（engineering→product、engineering→quality、quality→engineering 的非返工段与返工段），engineering→quality 的两条版本交付合成一段次数 2。另加一个读牌子的取色探针（`readSignColors`）：返工那块牌子的底色是红的，同一条路径上的另一块是白底，两者的差别用「红减蓝」分开（实测 111 与 10）。文件里 `HISTORY` 常量的注释也改了（原来写的是「两种非返工流转与一条返工」）。
   - `docs/design/app-and-interface.md` 第 4.3 节 `project.flow` 一行的类型改成现在的三种，并写明质检提交缺陷记录让工程返工、这一类流转的种类是问题反馈。这一处不在工单的「只改」清单里（清单是分诊时写的，那时还没发现设计说明本身也写着已删掉的种类），按 solo 的做法在工单评论里补记了。
