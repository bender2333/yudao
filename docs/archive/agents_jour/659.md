# 工单 #659：[M0] 新开的标签页打开 Yudao 后一直停在「正在读取数据」，看不到项目

## 记录

执行者 minimax-M3.1-Flash / 2026-10-22 05:40 /
1. 动手前核对：
   - 符号检查：`client/src/renderer/src/contract/view-sync.ts` 的 `refreshAll` 取所有视图位置的最小值作为重新订阅的起点，位置 0 表示「这个视图还没有快照」；`client/src/renderer/src/contract/client-app.ts` 的 `resync` 用它重订阅；`client/src/renderer/src/contract/event-stream.ts` 第 109 至 114 行在 `previous` 与已读到的位置对不上时判为缺口，交给重新同步。与工单正文一致；
   - 「只改」清单：本工单原来没有清单，按实施范围补上（见工单评论），手写 2 个。
2. 实现：
   - `view-sync.ts`：`refreshAll` 取最小值时跳过 0（一个刚打开或查询失败的视图不该把重新订阅拖回 0）；新增纯函数 `resubscribePosition`，给出重新订阅的起点：视图位置与事件流已读到的位置里更晚的那个。
   - `client-app.ts`：`resync` 用 `resubscribePosition` 取起点，不往回退。
   - 这一改动的机制：服务重放整段历史以后，客户端的 `previous` 核对与已读到的位置对不上，判为缺口，再次重新同步——每十秒一轮的循环就是这么来的。重新订阅不再退回 0，循环就断了。
3. 测试：`client/tests/unit/resubscribe-position.test.ts` 四项——视图位置为 0 时不会把重新订阅拖回 0、不会比事件流已读到的位置更早、视图需要更早的事件时按视图的位置来、两边都没有位置时从 0 开始。
   - 反向验证：把 `resubscribePosition` 改回只取视图位置后重跑，两项失败（视图位置为 0 时被拖回 0、比事件流已读到的位置更早）；改回后四项通过。
4. 本地自测：
   - `cd client && npm run typecheck`：通过；
   - `node --test --test-force-exit --test-timeout=120000 --test-reporter=spec tests/unit/resubscribe-position.test.ts`：`tests 4 / pass 4 / fail 0`。
5. 有一处没有验证：工单的第一条验收标准（新开标签页几秒内显示真实的项目列表）没有在本地复现与验证——它要一个已经有长历史的数据目录与一次真实的浏览器会话，本机这两个条件都不具备。改动的机制与工单正文给出的证据对得上（重新订阅的位置是 0，服务重放整段历史，`previous` 对不上再次重新同步），单元测试覆盖了位置的选取；页面上的实际表现留给走查的人在新标签页里确认。
6. 工单「要查的」里第 3 条（后台标签页停止重绘）没有证据，留在 #659 继续查；第 1 条（`Last-Event-ID`）已核对：`eventsource` 包只在收到过带 `id` 的事件以后才在重连时发这个头，值是事件位置，服务端那条「非整数按位置未知处理」的路径与工单正文用 curl 复现的症状一致，客户端这条路径上发的是合法值。
