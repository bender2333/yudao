3. 机制（先在本机验过再写代码）：Windows 上「按直接子进程的进程号终止」打不到两种情形——直接子进程已经退出、它起的子进程被重新挂到别处；子进程自己又派生了下一层。作业对象（`CreateJobObject` + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）一次收住整棵树，关键是**先挂上再放行**：子进程以 `CREATE_SUSPENDED` 创建，`AssignProcessToJobObject` 之后用 `NtResumeProcess` 放行，命令自己起的子进程因此从一开始就在容器里，没有「先跑起来再挂上」的空档。POSIX 用 `start_new_session` 的进程组整组 `SIGKILL`（原有做法保留）。本机探针（`.tmp/probe3.py`、`.tmp/probe6.py`）确认：挂上以后孙进程 `IsProcessInJob` 为真；直接子进程退出后`QueryInformationJobObject` 的 `ActiveProcesses` 立刻反映剩下几个（`echo hello` 为 0、留下子进程时为 1，判「有没有留下子进程」因此准确）；`TerminateJobObject` 之后那些孙进程消失、管道立即读到 EOF。
4. 回执的返回不再依赖管道关闭：`_run_process` 不再 `await process.communicate()`（走 `wait()` 也不行——`base_subprocess._wait` 的等待者在管道全部断开时才被唤醒，同一根永远开着的写端照样等不到），改为自己读两个管道 + 轮询 `process.returncode` 判直接子进程退出（`_wait_for_end`）；命令结束后先结束整棵树，再最多等 `_OUTPUT_DRAIN_SEC`（3 秒）收输出，到点关掉自己这一端的读管道、带已有输出返回（`_finish_readers`、`_close_read_side`）。「确实杀不掉」时回执写「some processes from the command could not be stopped」，不把「已停止」当结论写出去（`_tree_stopped_note`）。
