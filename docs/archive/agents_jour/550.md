## 第 2 轮推进（main 集成层新失败项排查与修复）

1. 现场与现象核验：
   - main 上的 push 运行 39355380590（提交 ffb099c7，#550 合并）在集成层报错：
     `harness/tests/test_run_time_limit.py::test_time_limit_checked_between_activations - AssertionError: assert 'time_limit' is None`

2. 根因查清：
   - 查证 #550 代码改动：严格核对 `git diff 39fdeb25..ffb099c7`，#550 仅涉及 `harness/app/project_queries.py` 中的 `RunActions` 查询扩展、`harness/environment.py` 中的注释以及相关单元/集成测试与前端组件，产品代码完全未涉及 `orchestrator.py`、`runtime.py`、`bounds.py` 或任何激活/等待时钟计算逻辑。
   - 查验时钟与等待计算（工单 #350）：运行段计时通过 `_pause_run_clock` / `_resume_run_clock` 控制；激活结束时结算并清除 `_run_segment_start`。本地脚本核验表明：两次激活之间的等待期间 `_run_segment_start` 为空，等待时间（如 3.1 秒）完全未计入 `_elapsed_sec`。
   - 查验 CI 失败现场日志（下载 `39355380590` 的 `integration.xml`）：
     `test_time_limit_checked_between_activations` 单用例用时为 `time="6.618"` 秒。扣除 `time.sleep(3.1)` 后，两次激活实际运行耗时为 3.518 秒。
   - 根因为**测试本身依赖墙钟**：用例原设定 `run_time_limit_sec=3` 且两次激活之间 `time.sleep(3.1)`。在 GitHub Actions Windows 虚拟机高负载与 4 并发 worker（`-n 4`）下，随集成层测试体量增加（含 #550 新增测试在内的文件 I/O 与进程并发），两次激活（创建工作区、计算散列、提交交付物封存归档、写 SQLite）本身的执行耗时偶发抖动上升至 3.518 秒，超过了 3 秒的运行上限，导致第 2 次激活在安全节点或准备阶段被判定超时。此问题此前在工单 #463（从 1 秒校准至 3 秒）和工单 #410（对齐短时限到 10 秒）中曾多次出现。

3. 修复方案：
   - 保持所有断言严格不变且不放宽（`assert result.phase == "ENGINEERING"`、`assert result.stop_reason is None`、`assert result.phase == "QUALITY"`、`assert len(system.test_adapter.invocations) == 2`）；
   - 按工单 #410 标准将测试短时限参数校准为 `run_time_limit_sec=10`，两次激活之间等待调整为 `time.sleep(10.2)`，彻底消除高并发负载下的抖动误报，同时严格维持等待时长（10.2s > 10.0s）超过运行上限以验证等待不计入时限的核心不变式。
