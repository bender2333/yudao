# 演化式开发与上下文管理

> 日期：2026-09-06。依据：用户要求设计、架构与方向支持持续修改，及时重构与解耦，同时记住历史原因，减少历史细节对当前工作的干扰。
> 状态：设计资料。本轮未实现项目状态管理、上下文失效或重构自动化，不改变第一阶段另一会话的验收范围。
> 配套：总体架构、[领域补全](domain-completion-design.md)、[记忆与控制](../archive/research/memory-and-control.md)。
> 原生能力接入与 2.E 工作包详见[项目演化设计](native-project-evolution-design.md)；[AI 原生 SDLC 研究](ai-native-sdlc-insights.md)记录最新外部参考与项目取舍。
> 最新范围校正见第一阶段设计复核：同任务部门历史按 D08/D10 保留并自动压缩；本文跨项目、跨任务选择性上下文设计不替代该用户要求。当前请求容量与次数控制不等于任务 token 预算。

## 1. 持续变化是正常工作方式

Yudao 自身及其承接的项目都需要支持演化式开发：需求逐步清楚，设计按反馈修正，架构随真实复杂度调整。一次交付完成后，后续任务继续基于有效成果推进，不能每次从完整历史重新猜项目方向，也不能把最初方案当成永远不能变的合同。

这同时包含两项责任：代码结构使合理变化容易发生，上下文结构使执行者知道当前应当依据什么。只重构代码会留下过时认知；只压缩上下文会保留难以修改的实现。一次重要变更需要同时检查两者。

普通项目演化贯穿所有大阶段。第四阶段的额外能力是系统根据证据提出自身组织和规则候选并独立比较；日常需求迭代、设计修订和模块重构不等待该阶段，也不逐项套用自主规则采用流程。

## 2. 当前事实、目标与历史分别表达

| 内容 | 回答的问题 | 必须保持的区别 |
| --- | --- | --- |
| 当前有效方向与决定 | 现在要做什么，哪些要求和约定仍生效 | 用户新决定可以取代旧方向，旧输入保留为历史，不继续强制执行 |
| 当前实现与验证状态 | 代码实际支持什么，在哪个工作树/提交，哪些检查真实完成 | 设计已确定不等于代码已实现，代码已提交不等于验收通过 |
| 当前任务与目标差异 | 本次要从现状改变什么、影响哪里、怎样检查 | 局部任务不自动重启整个项目，也不私自修改未涉及方向 |
| 历史决定及理由 | 当时为什么这样做，依据什么条件，后来为什么改变 | 原因仍可参考，旧决定的执行作用可能已经结束 |
| 历史过程与原始证据 | 当时具体发生了什么，怎样重新核对 | 保存完整，不默认进入每次任务上下文 |

“当前”总是相对于项目、分支或工作树、任务范围和版本。并行分支可能各有有效实验决定，不能把最后写入的一条全局记录当成所有工作树的新事实。

当前工作摘要指向上述来源，是便于工作的一种表示，不能成为覆盖代码、原始要求或真实回执的第二套权威。发生不一致时指出具体差异，再处理受影响工作，不能让摘要自行猜测已经完成。

## 3. 模块化围绕变化和责任展开

模块应聚合共同履责、通常一起变化的内容，对外暴露少量有清楚含义的输入、输出及约束。隐藏容易变化的实现细节，使一次局部调整尽量停留在相应模块内。

需求改变时先沿已有责任边界分析影响。若当前边界仍然合适，在其中完成增量；若变化反复穿透同一边界，就把必要重构纳入当前工作，避免不断复制逻辑或让上层依赖下层私有细节。

| 可观察迹象 | 应考虑的调整 | 应保留的检查 |
| --- | --- | --- |
| 一个模块同时承担多个独立变化的职责 | 拆开责任，将关联行为留在对应模块 | 各职责原有行为、交接与异常仍可核验 |
| 相同业务规则散落多处，修改常有遗漏 | 将该规则集中为有明确责任的实现 | 同一有效规则在所有消费方一致 |
| 调用方反复读取另一模块内部结构 | 改成围绕真实需求的公开接口 | 合同和失败行为清楚，内部修改不再传播 |
| 两类实现存在稳定共性及真实差异 | 抽象已存在的共性，让差异保持局部 | 抽象减少复杂度，不能只为统一名称增加层次 |
| 现有抽象只有转发，或充满特殊分支 | 缩小、合并或删除不再有用的抽象 | 功能及依赖关系更容易理解 |
| 成熟依赖已满足所需通用行为 | 使用已有能力，删除重复自研部分 | 实际版本、行为和必要适配经过验证 |

重构时机由真实复杂度和修改阻力决定，不预设文件长度、固定复用次数或每轮必须重构的仪式。需要的抽象及时建立，不再有价值的抽象也及时撤除。

纯重构以保持已约定可观察行为为目标；功能、接口或方向改变明确记录为变化。二者可以属于同一工作包，但验证要能分辨结构调整与行为变化各自发生了什么。[EC02](#ec02-重构定义)

每个提交尽量形成可理解、可验证的完整增量。新路径尚未可用时不拆除能够工作的必要能力；替代就绪后直接更新受影响调用方并删除过时实现，不保留旧接口兼容层、迁移脚本或回退分支。历史 Git 版本与已发布工件供追溯或运行处置使用，不等于新代码同时维护两套接口。

## 4. 历史原因怎样保留

对影响方向、模块责任、重要依赖、接口或质量约束的决定，保留简短记录：当时的问题与条件、选择、主要原因、相关代价、成立范围、重新考虑它的条件，以及原始依据。

决定改变时记录新依据及其取代关系。旧记录仍解释过去，当前入口明确指向现在有效的选择。不必为每个局部变量或通用组件行为创建决策档案；领域默认可以沿用一组已经明确的项目约定。

有必要长期保留的“为什么”往往是条件。例如选择本地存储是因为单机运行和低写并发；将来引入团队协作时，应重新评估这些条件，而不是继续服从“曾经选过本地存储”。也不能反过来断言新需求出现就必须更换数据库，需要核对实际并发与责任。

决策理由是当时的取舍说明，不自动证明运行故障的根因。历史缺少理由时标明缺失；后来形成的解释单列为推断，不能补写成当时已经知道的事实。不需要保存或传递模型私有推理过程来完成此项职责。

已有 `jour.md` 保持按时间记录重要信息；当前有效入口与专题设计负责指向生效决定。后续若独立决策文件有实际价值再按重要决定拆分，不预先建立决策管理平台。[EC01](#ec01-架构决策记录)

## 5. 三层上下文

三层按读取用途划分，可以共用已有文件和持久化设施，不要求三套存储。

这三层主要规定项目资料和历史材料的用途。当前运行内部另有已确认的部门历史视图：同部门完整历史跨激活保留，临近窗口上限可摘要压缩，原始经历不删除。默认少量项目资料不表示默认删除同任务部门历史；历史被提供也不使旧要求重新生效。先进语义选择的实现需在这一约定上进一步验证。

| 层次 | 默认携带的内容 | 不默认携带的内容 |
| --- | --- | --- |
| 当前工作层 | 当前目标、实际实现状态、本次改动、适用约束、相关模块合同、未解决事项 | 被取代目标、其他工作树成果、无关计划全文 |
| 决策依据层 | 与本次选择相关的简短原因、适用条件、关键例外及来源引用 | 所有备选方案争论、每次尝试的完整过程 |
| 历史证据层 | 按明确问题取回的原始决定、代码版本、检查与运行记录 | 每次激活自动回灌全部历史对话和工具输出 |

当前任务应既知道“现在用哪种方案”，也在需要时知道“为什么，以及什么条件下要重新考虑”。与当前任务无关的旧讨论不占用默认上下文。

历史详细内容只有在解释当前约束、诊断问题、审查拟改决定或核对旧行为时展开。查回后同时显示当时范围、是否已被取代及当前替代项；被检索到不等于重新生效。

## 6. 一次上下文装配怎样进行

1. 确认项目、工作树/分支、本次任务及当前采用的要求、方案和执行版本。代码存在未提交变化时，记录实际工作副本状态，不能只用 HEAD 代表全部实现。
2. 从可信当前来源取得目标、已确认决定、实际实现和验证状态，明确本次要改变的差异。保留必需权限和约束，不把未知状态填成已完成。
3. 按部门、当前步骤和相关模块选择所需合同、适用知识、默认依据与有效经验。产品不默认读取全部工程私有过程，工程也不默认获得隐藏评价材料。
4. 对本次涉及的重要决定加入简短原因和重新考虑条件；准备可按需查回的历史引用。相关性选择先受权限、范围及读取用途约束：作为当前执行依据的知识必须有效，历史查询可以取回已替代或失效材料，同时明确其历史状态与替代关系。
5. 在请求容量内装配，并记录实际来源、版本、选择原因和未纳入范围。跨 run 的可选项目历史按需取回；当前部门历史遵循 D08/D10 进行有来源的压缩，仍有效的关键限制不能为了压短而静默删除。
6. 发送前核对所依据的任务与知识仍适用；变更接纳与分派采用共同控制顺序。失效在先则重新装配，已开始发送的请求按在途处理。

必须信息本身超过容量时报告上下文不足，不能截断目标后继续假装完成原任务。当前 D10 明确固定原文与当前工作无法容纳时停止，后续更小的工作单元必须明确新范围；按需查阅也占用容量，应保留与任务规模相称的查阅空间。

`ContextManifest` 一类记录的作用是核对实际装配，不是只记录理想输入。模型适配器、文件自动发现、工具返回和会话历史带来的额外内容也需要受同一范围约束；单独核验提示文本不能证明模型实际只看到了这些内容。

## 7. 摘要与索引随变化更新

摘要必须保留来源与适用范围，可以从原始材料重新生成。连续对上一份摘要再压缩容易丢失否定条件和例外；重要决定的现行摘要应回到源记录校验。

| 变化 | 需要重新判断的内容 | 仍保留的内容 |
| --- | --- | --- |
| 用户调整目标或重要约束 | 受影响的要求、默认、设计、待办、验收及任务上下文 | 原任务表达、旧决定及当时成果 |
| 模块拆分、改名或接口变化 | 模块说明、代码定位、调用关系、使用旧接口的任务材料 | 旧版本源码及原有设计原因 |
| 某项经验或规范不再适用 | 相关检索结果、装配候选、有效性摘要 | 历史采用和失效依据 |
| 分支切换、合并或工作副本修改 | 当前实现索引、未完成事项、与当前代码绑定的验证说明 | 各分支自己的历史与作用范围 |
| 已运行检查得到新结果 | 当前实现的证据覆盖及相关待办 | 旧回执及其受测快照，不覆盖成新结果 |

索引和缓存按实际引用的内容与范围判断是否过期，不能仅靠时间较新或文字相似推断仍有效。相关引用失效后先标明受影响部分，再更新；无法建立完整依赖关系时扩大必要复核范围并说明不确定性。

变更不要求全量删除历史、重建整个图谱或让全部任务重新开始。没有影响依据的内容不随意失效，已被确认受影响的内容也不能因为摘要仍在缓存里就继续进入请求。

## 8. 一次变化的完整闭环

```mermaid
flowchart LR
    C[用户调整或发现实际问题] --> I[确认当前范围与影响]
    I --> D[更新有效决定和工作目标]
    D --> M[必要的模块重构与功能修改]
    M --> V[针对当前合同验证]
    V --> S[更新实现状态与受影响上下文]
    S --> N[下一项任务按新上下文继续]
    D --> H[保留历史决定、原因与取代关系]
    V --> H
    H -->|按需查询| N
```

用户明确提出方向变化时，把它作为有效的变更输入处理，不重复索要已经给出的许可。范围内可合理决定的局部设计由专家完成；存在重要且不能推断的取舍才提问，同时推进无依赖的工作。

变更先更新目标及影响说明，已实现状态在代码和验证真正完成后更新。两者之间明确显示待实现差异，不能提前把未来架构写成当前运行事实。

结构调整后的验证要覆盖相关合同、集成关系与已知反例。行为已经合法改变的旧检查保留其历史，不继续强制旧要求；新检查应依据当前定义，不能为了通过而悄悄弱化本次目标。

提交记录、当前说明、重要原因和证据在一个可审查的工作包中一致。后续上下文按新状态生成，记录接续点和未完成事项，不需要把整段开发聊天重新交给下一位执行者。

## 9. 并行任务与在途上下文

工作树隔离文件修改，不自动解决共享接口和语义冲突。并行任务需要明确基线、修改范围、依赖合同及谁负责整合。另一分支已完成某功能，不等于当前分支已具备；读取资料时保留这一差异。

同一任务收到新方向时，先判断是否影响正在做的部分。无关工作可继续；受影响且尚未分派的步骤重新装配；已经发出的请求无法撤回其上下文，结果回来后根据新范围决定复用、重验或弃用，实际消耗保留。

若变化已经使在途动作失去必要性或授权，接纳变更时就停止相关新增动作，并在能力范围内取消已有动作，核实可能发生的外部影响。不能只等待旧动作全部结束后再弃用结果，也不能把取消请求已发出写成副作用已经消失。

检查当前版本和开始分派应与变更接纳处于同一有效控制顺序。旧执行者不能凭旧上下文推进新目标，也不能在失去当前权利后继续分派外部动作；可能已经发出的副作用仍需核实。具体边界沿用[记忆失效](../archive/research/memory-and-control.md#93-失效和实际分派之间的边界)和[恢复设计](organization-runtime-evolution.md)。

用户需求的版本化修改与运行组织/规则的版本更换分别处理。已有 Ask/React 可以承载职责内的要求更新；冻结在途组织版本不表示冻结用户需求。组织规则确需替换时依照相应停止、核实与接续流程，不把任意旧执行状态直接套进新协议。

## 10. 会话结束与重新进入项目

一次工作结束或换会话前，留下紧凑接续材料：实际工作树与代码状态、本次结果、仍有效的目标、重要决定及简短原因、真实验证及限制、未完成事项和下一步所需来源。未完成就是未完成，不为形成漂亮摘要宣称阶段通过。

新会话先核对这些材料与当前代码、任务状态是否一致，再取本次所需内容。日记是历史入口，不能逐条当作当前指令执行；尤其被后续决定替代的分工、目标和接口要求，只具有历史解释作用。

恢复上下文只使执行者理解现状，不等于已经取得继续运行旧任务、重放工具或重复外部动作的许可。任务责任与副作用判断由运行控制处理。

## 11. 当前基础与开发边界

本工作树核对基于 `50af8d2`，第一阶段另一会话的后续代码未纳入本结论。

以下是旧基线说明。最新主树改造已拥有原生逐次请求、首次 intend 原文和有效合同优先表达，并在加入部门历史压缩；具体新状态见第一阶段复核，不能用本节旧快照判定新实现缺失或验收结果。

`harness/context.py` 已按投影、部门及激活组装当前要求、交付、Ask/React、QA 返工与预算，并记录装配清单及排除项。旧规格全文、其他部门对话与完整历史不默认注入，提供了选择性上下文的基础。

其中最近若干规格、工单和转换的标识能够帮助定位，但不等于完整的决策原因，也不保证“最近”材料就是本次最相关材料。当前实现尚不足以证明具备跨任务项目现状管理、按决定查原因、分支作用域、依赖变更后的摘要失效及新会话接续能力。

还需在集成时核对旧交付、旧 QA 与 Reaction 对新要求的适用性，不能仅因它们仍在投影中就称为当前有效材料。现有 QA 校验另有要求与快照绑定，不能从装配存在旧材料直接推断能够错误放行。当前清单总摘要及适配器追加输入也不足以直接充当完整上下文缓存身份或实际输入证明；这些属于后续衔接核验，本轮未修改相关运行代码。

演化式开发的方法立即适用于我们的工作；新增自动管理能力按独立包推进：

| 独立准备或交付 | 当前可做什么 | 真实接入前需要什么 |
| --- | --- | --- |
| 当前状态与决定材料 | 用固定项目演化故事区分目标、实现、验证和历史 | 对应项目/任务事实的稳定来源 |
| 原因查询与上下文校准 | 验证保留关键理由、排除过时命令、按问题查历史 | 清楚的可读范围和实际装配记录 |
| 变化影响与材料更新 | 构造改需求、换接口、分支合并、知识失效的前后材料 | 稳定版本引用、当前任务控制顺序和索引失效能力 |
| 真实部门接入 | 确定三部门所需输入、输出和接续合同 | 第一阶段相关上下文、事件与模型边界验收版本 |

用户进一步明确这些必须是 Yudao 产品原生能力。第二阶段 2.E 将持续项目、变更与单次 run 分开管理，交付完整基线接续、有效状态和原因查询、上下文失效与项目结果采纳。普通多次任务和新会话接续在第二阶段完成；第三阶段扩展持续并行与持久恢复，第四阶段让系统研究自身策略改进。没有另加一个大阶段，也不把日常重构推迟到后续阶段。

## 12. 验收场景

| 编号 | 场景 | 应有的证据 |
| --- | --- | --- |
| EC-01 | 同项目先后改变两次产品方向 | 当前任务只执行最新有效方向，仍能解释两次变化及原条件 |
| EC-02 | 新架构已设计，代码仍是旧结构 | 上下文明确目标与实际差异，不引用不存在的模块作为已实现能力 |
| EC-03 | 历史含大量已放弃方案，新任务只改一个模块 | 默认上下文聚焦当前模块及相关理由；历史全文按需查阅 |
| EC-04 | 曾放弃的方案再次被提出 | 能找回旧原因并核对条件是否改变；不会盲目重复，也不永久排斥重审 |
| EC-05 | 一项仍有效约束很早决定，之后有很多新记录 | 约束仍进入相关任务，不被“只取最近几条”挤掉 |
| EC-06 | 模块重构替换接口 | 当前代码与说明更新，旧接口调用删除；相关行为与集成检查通过，历史仍可定位 |
| EC-07 | 工件/接口变化而摘要或缓存尚未更新 | 受影响摘要被识别，不能用旧位置或旧通过证据支撑新任务 |
| EC-08 | 两个 worktree 使用不同实验方案 | 各自上下文与实际代码一致，未合入成果不被当作当前实现 |
| EC-09 | 分派前接纳新方向，旧结果随后到达 | 旧结果不推进新目标；可复用成果重新判断，消耗与原上下文保留 |
| EC-10 | 新会话接续未完成工作 | 能核对现状、理由、未完成项及下一步，不重读全部历史才能开始 |
| EC-11 | 历史记录含旧命令，或理由已丢失 | 旧文本作为历史资料；理由缺失明确呈现，不补造当时动机 |
| EC-12 | 缩短上下文后关键例外被遗漏 | 校准发现错误遗漏，不以 token 更少判为通过；源记录可核对 |
| EC-13 | 正式比较期间用户合法调整需求 | 已采结果、变更原因与偏离记录保留，新比较重新确定口径，不合并成同一改善证据 |

评价同时看修改影响范围、合同是否维持、当前信息是否正确、关键原因能否找回、历史是否干扰行动，以及实际上下文与查阅成本。不会因为文件更多、抽象层更多或摘要更短就判定改善。

## 13. 成熟模式依据

### EC01 架构决策记录

- 来源：Michael Nygard，[Documenting Architecture Decisions](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)。
- 访问：2026-09-06；实际阅读相关正文中的重要决定范围、Context、Status、Consequences 与 superseded 处理。
- 可采用：重要决定保留当时情境、决定、代价和被替代关系；过去为何成立仍可查，当前选择单独明确。
- 限制：ADR 是工程记录方法，不自动解决模型上下文选择、权限、并发或代码状态一致性。本设计借鉴其职责，不要求机械套用每项审批或每个细节建档。

### EC02 重构定义

- 来源：Martin Fowler，[Definition Of Refactoring](https://martinfowler.com/bliki/DefinitionOfRefactoring.html)。

- 可采用：重构改善内部结构和修改成本，同时保持可观察行为；需求变化与结构调整应分别说明并验证。
- 限制：定义不提供本项目模块边界或自动判断算法。最初尝试的 `/bliki/Refactoring.html` 返回 404，以上是实际读取成功的页面。
