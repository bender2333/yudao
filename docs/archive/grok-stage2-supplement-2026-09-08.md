### S1：关闭 G1 的两个结果缺口

目标是让用户能区分“已得到解释”“还需动作”“动作已有证据”，并使最终 QA 所等待的指导状态有事实依据。

1. 在现有指导合同中明确解释与动作完成的处理含义；不能只根据任意 `completed` 文本决定动作已完成。纯解释、无需改动、有理由无法执行仍可产生明确回应。
2. 动作结果由宿主绑定到实际采用该指导的工作和有效依据。模型给出的引用不能扩大宿主允许的结果集合；不让模型机械抄写内部标识，也不保留一条更宽松的手工引用通路。
3. 不把同 run、同部门、同合同的任意旧动作归因到新指导。当前批次、作用对象、实际回执和有效版本须相符；已有结果可作为“无需新动作”的解释依据，但不得冒充指导之后完成了新动作。
4. 空结果、无关旧结果、拒收、失败、已失效结果均不能形成“动作已核实完成”。多个指导同批处理时，也不能用一次无关写入证明所有指导都已完成。
5. 保留 G2/G3 已有调度、只读权限、协作先后与取消优先规则；输入、查询、导出和 UI 对处理状态使用同一含义。不要用自然语言关键词/正则分类替代明确的处理合同，不通过禁止合理解释来消除反例。

完成依据：F1/F2 在旧实现上呈现不符合合同的结果，修正后不再标动作完成；纯解释无需工具、真正执行后宿主绑定、跨激活继续处理仍通过。正式回归还覆盖：不同指导/批次的结果、同合同旧写入、跨 run、拒收和失败结果、失效合同/计划/交付、QA 前后到达、工具在途、取消及已让出工作变化。最后检查模型实际看到的工具说明与宿主接纳合同一致。

范围入口：`harness/collaboration.py`、`validation.py`、`context.py`、`tools.py`、`orchestrator.py` 及指导测试。继续使用现有模块；本计划不要求新增通用工作流、语义分类器或兼容层。

### S2：把 HTTP 400 从未知失败变成可解释结果

1. 读取当前指定 Provider 配置，固定地址、协议、模型、运行限制和实际依赖版本。只用宿主凭据引用，不将凭据写到脚本、终端输出、报告或 Git。
2. 优先检查已保存的 SDK 请求和错误材料；没有足够诊断时，补有界、脱敏的错误采集，保存允许的错误 code/type/param、请求关联和必要说明。错误正文可能回显输入或密钥，不能直接全量公开；同时不要只留状态码使故障不可解释。
3. 对同一配置做最小 Responses 调用，随后逐步恢复实际工具、输入及输出参数，按证据找出哪个差异触发错误。只做必要的受控对照；诊断调用不执行生产工具，也不改写原失败 run。
4. 若为应用构造错误，修复并以本地协议反例验证；若确认提供方能力或配置不支持，记录来源和最小失败样例，提出具体配置/适配选择。保持原计划不临时换服务、模型或 Prompt，不新增隐式协议 fallback。
5. 修正后用新 run 重跑基础 happy smoke。400 不在原地靠增加重试恢复；旧失败照常保留。

交付：一份可读的诊断结论、所需最小修正及回归证据。结论可以是“仍无法确认”或“需补某项配置”，但必须指出已验证/排除的条件和下一项需要的信息。探针成功之后仍要进入 S3 的完整流程。
