## 3. 第一阶段还需要完成什么

### 3.1 先完成正在进行的真实性与控制边界返修

以下问题已在 `grok-runtime-review-task.md` 中分配给构建任务；本次快照仍看到对应原实现，应作为第一阶段收尾处理：

| 问题 | 对用户的实际影响 | 通过条件 |
| --- | --- | --- |
| 取消与迟到提案之间存在提交竞态 | 取消后，旧模型结果可能继续推动流程 | 取消与提交的交错可确定性复现，终态及 replay 一致 |
| 预算只计上下文估算，未完整纳入实际 usage | 实际调用已超预算，运行仍继续 | 真实 usage 正确累计，无漏计或重复计费，耗尽后不激活下一部门 |
| 检查在原工作树运行，随后还原并记录回执 | 检查可能测试修改后的代码，却把通过证据绑定到原代码 | 检查证据确实绑定受测快照；可丢弃副本和链接行为经过验证 |
| OMP 可能自动读取仓库上下文 | manifest 声称隔离，实际模型请求仍混入其他指令 | 直接捕获实际模型请求，证明无关 canary 指令没有进入请求 |
| abort 未核对目标 session | 取消遗留任务可能影响当前任务 | 错误 session 的取消不影响活动调用 |

代码入口分别为 `harness/orchestrator.py`、`projection.py`、`tools.py`、`adapters/omp.py`。这些是可信执行和可观测性的组成部分。

Web 返修已出现对应实现，但不能标为全部验收通过。静态检查仍需关注旧 health 响应覆盖当前状态，以及后台异常发生在最后一条 SSE 事件之后时，页面能否自动看到错误。相关入口为 `harness/web/static/app.js` 的 `loadHealth` 和事件回调，以及 `harness/web/server.py` 的 `_run_worker`。本轮未做浏览器截图或交互验收。

### 3.2 再完成真实验收与计划中的 Phase 5

第一阶段的交付应能展示：

1. 真实 provider 上的完整产品、工程、质检、完成流程，以及一次真实 Ask/React 往返；工程与质检各自执行检查，回执关联当前 spec 和代码快照。
2. 上述运行及失败运行均有可复核的事件、上下文来源、成本、停止原因和 replay 结果；保留失败记录。
3. 浏览器能发起、观察、取消任务，切换任务、断线重连、后台异常和长文本布局均有行为验证。
4. 按现有实施计划补齐轻量 Phase 5：返工时的会话更替语义、受限经验候选、失效说明、检查点与停止复盘、只读评价入口。候选产生不意味着自动用于后续任务。

初始 `grok-build-task.md` 主要分配了 Phase 1、2、4 和 Phase 3 接口，后续任务才补真实 provider。该批构建任务完成与完整 Phase 1-5 计划完成应分别报告，不能默认删去未做的 Phase 5。

后续范围校正：最新 `grok-implementation-plan.md` 已明确 Phase 5 只记录来源与证据完整的经验候选，并支持停止后的查询、导出和重放；不增加独立 LLM 蒸馏、自动注入、候选评价或可继续执行的检查点。因此，本节上方对旧版 Phase 5 的核对属于历史快照，不再将额外蒸馏、Scorer 和恢复执行作为第一阶段欠项。第二阶段按 [返工观察设计](stage-2-evidence-and-evaluation-design.md)独立设计评价能力。

### 3.3 明确恢复能力的边界

当前 `replay` 只重建投影；`PAUSED/FAILED/DONE` 都被当作终态处理，没有暂停后继续执行的入口。SSE 续传也仅恢复事件订阅。

按目前操作约定，暂停后由人介入并新建任务。若要支持长任务中断后继续，需要另行定义：恢复到哪个已确认检查点、外部副作用是否已发生、旧调用结果如何失效、预算如何经明确决策调整。不能仅凭事件库存在就称为已经实现。建议把这项能力纳入第二阶段的真实长任务验证，不要求第一阶段先建设分布式调度。

## 4. 后续阶段建议

依赖主线是：**可信运行证据 -> 独立评价 -> 有界局部控制 -> 跨任务经验 -> 可复用技能 -> 执行结构演化**。每一步回答一种新的问题，原有运行内核持续可用。

### 第二阶段：可信经历与独立评价

回答：我们能否准确还原一次运行、发现可验证的结果差异，并为后续变化建立独立评价基线？对应 D1。失败原因属于待验证解释，不因记录完整就已经得到因果证明。

- 将运行事实整理为可追溯的 Episode，关联 spec、行动、产物、真实回执、停止原因和上下文来源；解释与事实分别保存。
- 先固定评价任务、指标和失败定义，再采集结果；开发校准任务与未见评价任务分开，保留失败样本。
- 独立复核与 QA 职责分离：QA 负责当前任务是否放行，外部评价负责判断整个系统是否在改善；初版只读，不新增可随意推翻流程的角色。
- 如需测量“惊讶”，先记录事前预测，再记录观察与差异；不能事后补写预测，也不能只信模型自报置信度。
- 用真实长任务明确验证状态重建与恢复执行的区别；先完成本地明确检查点的恢复语义。

通过条件：独立评价能发现错误放行，并把结果追溯到当时有效的目标、代码和证据；同一固定版本可获得可比较的质量、返工、无进展往返、上下文量和成本基线。尚未完成的 MVP Phase 5 保留为显式欠项，不因进入新阶段自动消失。

2026-09-06 设计讨论补充：用户已选定“多轮返工仍重复同类错误”为第二阶段首个观察场景。具体设计见 [第二阶段草案](stage-2-evidence-and-evaluation-design.md)。最小版本聚焦各轮交付、问题轨迹与独立复核；长任务恢复保留为单独设计议题，不作为该场景前置。只有同一有效要求下的可复核反例才能支持“错误放行”，单纯评价意见不一致保留为分歧。

### 第三阶段：有界局部控制

回答：依据上述信号调整当前任务的执行方式，是否优于固定策略？对应 D2。

从一种范围小、可单独比较的控制变化开始，例如取证深度、重试选择或既定总预算内的分配。选择一个已有运行数据支持的问题，不一次实现完整 Meta-Controller。

通过条件：在相同模型、任务和总预算约束下，与固定策略比较，减少无效往返或失速，质量不下降；每次调整有原因和记录，越界动作被拒绝。此阶段不自动修改用户目标、验收标准、部门权威或拓扑。

### 第四阶段：受治理的经验复用

回答：过去的经历，能否减少未来未见任务中的同类错误？对应 D3。

先选择一类重复问题作为学习对象。Episode 保存事实，Lesson 是可以被推翻的解释，Schema 是经多情境验证的规律。负责提炼的模块只产生候选，独立评价之后才决定是否在指定范围内使用。

通过条件：候选在未直接重放的任务上减少同类错误；每条可用经验都有适用范围、来源、反例和失效办法；经验被推翻后停止注入，原始证据仍可追溯。不以经验条数、蒸馏次数或相同任务再次成功代替学习证据。

沿用现有事件与工件存储，等实际检索需求证明必要后再选其他存储。知识图谱、向量库和 Council 不作为这一阶段的先决条件。

### 第五阶段：技能与执行结构演化

先回答稳定流程能否封装成可展开的 Skill，再回答是否值得改变局部执行结构。对应 D4，然后单独验收 D5。

第一步保留稳定流程的输入、输出、适用范围、独立检查和内部步骤，将其作为可复用执行单元。通过条件是在未见任务中降低上下文或执行复杂度，交付质量不退化，异常时能够展开步骤重新处理。

第二步才允许比较新的路由或部门内部有界子循环。候选先隔离比较，再经独立评价决定在什么范围采用；递归、并发和成本始终有代码限定。三部门可以成为一种执行单元，而不是要求每个层级复制三个部门。

候选版本的留存、撤销和恢复属于可审计的演化生命周期，不要求为过时接口添加兼容层。

### 隔离发展环：与运行适应路线分别验收

开放性研究不必等待所有执行结构演化完成，但也不能跳过证据基础：

- 第二阶段有可信 Episode 后，可并行 O0/O1：定义产物身份与谱系，固定观察者、评价方法和训练前缀/评价后缀，只读测量新颖性与可学习性。
- 观察协议可靠后，可以开始 O2 的隔离实验，尝试生成新任务、环境或产物；不直接改动实际执行策略。
- 有经过验证的 Skill 后，再做 O3/O4：使用新原语打开新的产物空间，研究生成者与观察者是否共同进步。

通过条件是后续产物既仍有非平凡新颖性，观察者又能通过过去产物学到规律并改善对未见产物的理解。随机噪声、单一排行榜上涨或一张新颖输出都不能单独满足这个条件。发展产物要进入日常执行，仍须经过相应阶段的独立评价。

模型权重更新是可选的最慢变更层，不列为主线必做阶段。运维部门在交付物确实需要持续运行和运行反馈时引入，不以凑齐部门数量作为下一阶段目标。

## 5. 下一份交给 Grok 的任务应写清什么

当前 Grok 继续完成已有运行时、真实 provider 和 Web 验收任务。后续任务按独立结果拆分，不把整个长期架构一次性交付。

下一份设计建议围绕“可信经历与独立评价”形成可审阅约定：

1. 首先研究哪类问题。建议从多轮返工中重复同类错误切入，便于连接当前三部门证据与后续经验效果。
2. 谁决定成功，什么事实支持结论。明确 QA 当前放行与循环外评价的边界，以及产品在用户目标内细化需求的权限。
3. 哪些信息是事实，哪些仅为经验假设。明确候选不会因被保存就自动进入下一次上下文。
4. 用哪些独立任务证明改善，如何排除只记住原题。证据量、阈值和观察窗口在采集评价结果前确定，不照抄研究笔记的示例数值。
5. 中断后希望保留和继续什么。把恢复语义写成真实场景后，再交给 Grok选择已有库与具体实现。
