## 3. 不可违反的边界

1. 按三个职责层组织：运行内核及采集拥有调度和接纳权，查询/命令接口组织事实与转交命令，工作台呈现信息和用户输入。复用当前模块，不拆服务，不让查询推进运行或页面自行执行部门循环。
2. 不引入第二套运行器，不把 OMP 作为运行依赖，不为 Provider 配置界面自行发明未确认的表单。
3. 不添加兼容层、迁移脚本、别名字段或隐式 fallback。过时接口直接删除并同步调用方和测试。
4. 不把本地 fake、mock、探针成功、历史提交或候选分支结果写成真实阶段验收成功。
5. 真实 Provider 使用 `provider.md` 指定的服务、模型和专用测试密钥；密钥不得写入代码、报告、截图或提交。
6. Provider 能力未公开时，使用显式登记的实验限制，不把限制写成服务商标称上限。
7. 所有真实失败必须保留原始错误、请求身份、输入来源和停止原因；不可通过关闭证书校验、修改全局网络或无限重试掩盖故障。
8. 每个工作包形成可审查的小提交并推送；只暂存本包改动。日记只追加本包事实，不提交他人已有的未提交内容。
9. 沿用 D09 的循环、模型步骤、容量和请求等待规则，不从研究材料恢复任务 token 预算或新增任务总时限配置。失败分类、三次内核尝试及 SDK 零重试按现有 D17 核对，不为取得成功临时放宽。
10. `jour.md` 的 A-D 设计建议没有自动成为本计划的新增前置。重复提案控制可在 2.2 据新基线评估；事件哈希链和旧数据处置另行定范围，不能据本计划删除历史记录。第三阶段的持续并行、持久恢复和运维不纳入本批。

### P4：完成 Provider 与第一阶段真实验收

立即核对当前配置和场景可执行性；在 P2/P3 必要修复后完成最终版本的下列场景。应用通过宿主目录/凭据引用使用配置，不在生产运行时新增 `provider.md` 解析逻辑。三部门先显式绑定用户指定服务，不因缺少第二套服务阻止此次验收；真实跨 Provider 仍单独待验，本地多连接或单服务成功不替代它。

1. 创建任务并完成基础三部门流程。
2. 在同一 run 追加真实新要求，验证输入版本、PRD、工程计划、Git 差异和交付变化。
3. 执行小窗压缩，核对摘要来源、原始输入、请求身份和继续执行。
4. 在新工作台执行部门指导、Context 到实际尝试的跳转、请求/响应查看、导出和历史回看；记录实际浏览器操作。API 编排或脚本协调等待单独说明，不能称为无干预自然运行。
5. 由独立 QA 依据最终有效合同放行，验证交付封存、Git、事件、来源审计和 replay。

慢响应、TLS/连接中断、过载、429、重试耗尽、部分返回后失败、取消和迟到结果用本地确定性故障覆盖。真实服务自然发生的失败保存原文，不要求为了覆盖表而反复等待远端偶发故障。小窗场景须确实压缩成功并继续到最终交付，压缩次数本身不算通过。

贯穿样例沿 W7 的 CSV 导出任务：全局追加导出规则、工程定向指导、追踪实际输入与尝试、独立 QA、封存恢复；另用可在小窗口完成的任务核对压缩。执行前固定公开验收要求和输入材料字节，最后从封存恢复完整交付并运行外部检查，不能用旧版本交付替代新合同。

**失败处理**

- 可恢复错误先由既有内核处理；耗尽后本次 run 如实失败并保留，不恢复旧终态。应用缺陷修复后可在新 run 重新验收，前后版本和首次失败均保留。
- 外部依赖持续不可用时标明受影响场景及恢复条件，继续独立本地工作；不因一次失败停止整个计划，也不无限新建 run。不能换服务、换 Prompt 或扩大重试次数来制造成功。
- 一次探针成功只能证明成功路径存在，不能关闭长流程连接风险。

只有六项前置完成后才能启动，按 [2.1 设计](stage-2-evidence-and-evaluation-design.md) 和 [离线复核设计](research/offline-review-design.md) 分批交付。研究中的 `harness.analysis` 与 demo 来自另一工作树，当前主线没有该入口，不把研究示例当现成命令或整体导入旧运行代码。

- 建立可搬移的观察证据包、显式交付复核、批次来源、问题轨迹和成本口径。
- 固定重复错误场景的基线任务和独立评价方法。
- 2.1 的基线报告必须能从结果回到原始输入、合同、计划、请求、尝试、工具和 QA 事实。

| 增量 | 可独立交付的结果 | 验收证据 |
| --- | --- | --- |
| L1 | 复核证据能保存、搬移、只读加载并重算轨迹 | 三轮失败/修复/复发可追溯；只在隔离测试副本删除来源或改字节，搬移仍可核验，篡改明确失败；加载不执行交付 |
| L2 | 显式本地材料清单驱动多轮独立复核 | 启动检查前发现静态错误；缺失、超时和 QA 依据不足保留原位；交付、要求、检查和环境对应 |
| L3 | 多份已核验证据的批次统计与来源查询 | 同包重复不增加任务分母；重评保留成本；损坏、缺失、人工校准和真实材料分别展示 |
| 2.1 基线 | 真实多轮轨迹、独立评价、问题身份和成本贯通 | 同名但要求改变时划分比较区段；按预登记任务和评价口径形成基线报告 |

证据目录内容哈希只能证明其自洽性，不能凭此声称历史来源未被整体重写。独立复核不改写内部 QA 结论；疑似错误放行须有绑定同一交付与公开要求的反例。先跑通一份证据的完整过程，再扩展批次和 UI；沿用 SQLite、现有工件和检查能力。

### P8：推进 2.2、2.3、2.E、2.4

**P8-A / 2.2：一项局部控制。** 依据 [控制与记忆设计](research/memory-and-control.md) 和 2.1 基线选一种实际重复错误，先形成触发依据、允许动作和停止条件，再接入唯一内核。交付固定事实序列校准、正常返工不误触发的反例、独立任务前后比较和全部新增成本。该控制不修改需求、绕过 QA 或重置原有限制。

**P8-B / 2.3：跨任务经验。** 先贯通一条“候选来源 → 独立验证 → 适用检索 → 实际输入采用 → 冲突/反证失效”流程，再扩大数量。复用现有 LessonCandidate 作为来源，不把同一 run 候选直接视为有效经验。验证相反建议、要求改名/改义、重复来源、过期索引、装配后失效与发送前后两种顺序。验收查询能从建议追到支持/反证和实际受影响请求；没有适用经验时正常按基础流程继续。真实迁移收益使用未见任务证明。

**P8-C / 2.E：原生项目演化。** 六项前置完成后可与 P7、P8-A/B 分别推进，不依赖先证明学习收益。按 [项目演化设计](research/native-project-evolution-design.md) 实施：

1. E0 固定连续变更故事和来源约定；E1 完成项目登记、完整基线、一次变更执行、核验后采纳以及下一次继承。
2. E2 接入原因查询、合法改方向、必要重构、上下文失效、旧基线结果拒收及新会话接续。QA 通过与项目采纳是独立事实，新会话不恢复旧终态 run。
3. E3 接入项目视图，真实执行三次变更：逐行文本处理、增加文件输入、将“保留重复行”改为“只保留首次出现”。保持仍有效的空输入行为并更新变化的检查，完整树包含必要删除和移动。

验收覆盖人工未提交修改、旧交付迟到、方向已变但代码未完成、过期摘要和缺失原因。原型未覆盖的项目页面先形成与现有设计一致的可审查方案；Provider 配置页仍按 W-P 处理。

**P8-D / 2.4：综合比较。** 按 [实验规约](research/experiment-protocol.md) 固定基础、仅控制、仅经验、组合四组，冻结策略与经验集，在未见任务比较交付质量、错误放行、重复错误和完整成本，并验证反证停用。共享评价只读，检查材料不注入被测模型。正式试验中的再修改属于新版本，不能继续混算原组。单次任务内多轮不增加独立样本数，结果可以是无改善或退化，不能通过删失败样本达成阶段指标。

所有 P8 子包在开工时先补一页当前合同、入口、最小端到端范围与验收材料，复用上述设计。常规实现选择据现有要求推进；只有涉及新的产品取舍、外部配置或数据删除等未决定边界时，向用户提出具体问题并继续其他独立工作。

## 5. 协作与验证安排

Grok 统筹范围、集成与独立验收；有子代理能力时按责任并行，工具不可用则顺序执行同样的工作包。

| 责任 | 文件与工作范围 | 并行约束 |
| --- | --- | --- |
| 运行与指导 | `orchestrator.py`、`validation.py`、`context.py`、`interactions.py`、工具与相关测试 | 共享状态和协议只由一位负责人整合 |
| 观测查询 | `observability.py`、导出、API 只读查询及测试 | 先与运行负责人确定事实含义，再与界面联调 |
| 工作台 | `harness/web/static/`、UI 测试、原型对照 | 复用接口，不生成运行事实 |
| 独立验证 | 故障场景、浏览器、封存复核、实验报告 | 被测源码冻结；真实验收串行使用明确配置，避免代理同时占用同一 run |

进入模块前先检查 `.codegraph/`；存在时优先 `codegraph explore` 定位当前实现。共享文件避免并改；需要隔离时创建工作树，但不硬编码旧分支或不存在的工作目录。

局部行为变更先跑相关测试，内核、指导及跨层整合完成后在冻结版本做完整 Python 回归和 Node UI 回归。使用项目已有环境；没有可用环境时可用当前依赖约束创建独立验证环境，并记录实际版本。基础命令：

```powershell
python -m pytest -q harness/tests/test_observability.py harness/tests/test_department_guidance.py harness/tests/test_web.py
node --test harness/tests/test_web_ui.js
python -m pytest -q harness/tests
```

这些是本地回归，不会替代浏览器和真实模型验收。缺少运行时、跳过的平台检查、历史报告缺失均单独记录。新报告使用含批次/提交的独立路径；已通过且代码没有再变的范围无需无理由重复执行。

## 6. 每个提交必须附带的回执

每个工作包完成时，向主任务回报以下内容：

1. 提交哈希和修改文件。
2. 当前行为变化、所关闭的问题编号和验证范围。
3. 运行的确切命令、通过/失败/跳过数量和报告路径。
4. 真实 Provider 是否调用；若调用，使用的模型身份、运行限制和脱敏结果。
5. 仍未解决的问题、阻塞原因和下一依赖。

不要把历史测试数字与当前 HEAD 的测试混加；不要删除失败报告；不要把候选分支状态写入主线完成状态。

## 7. Stage2 完成判定

只有同时满足以下条件，才可以把 Stage2 标记为完成：

- 六项前置工作均已在冻结主线完成并有独立验证。
- 第一阶段真实 Web 持续输入、小窗压缩、最终 QA、交付封存和来源审计全部通过。
- W1-W7 的工作台、观测、部门指导和真实浏览器行为已联调通过。
- Prompt 比较有固定任务、独立结果和成本证据。
- 2.1、2.2、2.3、2.E、2.4 的目标、依赖、结果和失败边界均已完成记录。
- 文档状态、提交拓扑、测试报告和真实运行报告相互一致。

W-P 配置 UI 尚待原型、真实第二套 Provider 尚待配置时，在总账保留等待状态并说明影响。它们不阻止已确认页面和指定服务的验收，但不得声称完整配置体验或跨服务验收已完成；若上位阶段完成要求仍包含这些项，总体保持 PARTIAL，直至补齐或用户明确调整范围。

实验完成与改善目标达成分别报告。2.4 如未证明预先约定的改善目标，应提交完整负面结果和未达项，不能把“比较做完”写成“系统已经学会改善”。

在达到上述条件前，阶段状态只能写为 `PARTIAL` 或 `BLOCKED`，并说明具体缺口。
