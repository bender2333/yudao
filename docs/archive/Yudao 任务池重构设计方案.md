# Yudao 任务池重构设计方案

Oct 22, 2026 · @bender

## 背景与问题诊断

当前 Yudao 实际是三个部门一次性串行走完、没有形成循环，与最初“每一轮循环都可控”的设计目标不符。

- 部门按产品 → 工程 → 验证的固定顺序交接，上一个部门完整做完才传给下一个，没有小粒度的正向传递。
- 回传通道存在，但同样是整体打包回传，没有小粒度回传。
- 结果更像静态编排（固定工序的流水线），而不是能自己转起来的循环系统。
- 根因：三个部门等于固定了三段“公式”，每段内部虽然靠 agent 在转，宏观结构却是死的；任务分解被绑死在部门顺序上。

人类团队协作并不要求所有东西做完才交给下一个团队，可以增量交接，这是引入小粒度双向流动的依据。

## 设计目标与原则

新设计的目标是让循环真正转起来，并且让循环的形状由任务本身决定，而不是由预先写死的部门顺序决定。

- **循环优先于流程**：先有循环，才谈得上“每轮可控”。循环次数和路径不固定：简单任务转一圈收敛，复杂任务可以来回多圈。
- **每轮可控的含义**（讨论中拆出的三层）：每轮输入输出可观测；每轮可中断、可调整；每轮行为可预期、可调参。
- **有界循环，内部可控**：把智能体工程当作控制论工程来做，同时保留 agent 的能力，不退化成固定工序的静态编排。
- **规则不预先固定**：规则希望从任务与角色的交互中涌现或被抽象出来，并能演化；稳定下来的规则再固化。
- **部门是当前阶段**：产品、工程、验证三部门只是现阶段形态，后续会加入运营部门、观察者等角色，新增角色不应要求改动核心机制。
- **尽快到达自举阶段**：改进 Yudao 自身也应是普通任务，走同一套机制，不开特殊通道。

## 核心机制：任务池

任务池是一块共享的任务看板加状态机，各部门通过发布、认领、拆分、回传任务来驱动循环，而不是按固定顺序排队。

&#91;embedded content: 任务池架构 · 上排发布认领，下排消费事件\]

用户和三个部门都通过任务池发布、认领、回传任务；观察者读取状态做兜底治理，可视化只经 Redis 订阅事件。

- **任务节点**至少包含：任务 ID、状态、能力标签、依赖的任务 ID、内容载荷、置信度、验证结果。
- **状态机（示例）**：待认领、已认领、处理中、完成、需返工、阻塞。
- **两种分发方式可混用**：定向发布（产品拆完后明确指派给工程），或自行匹配（任务带能力标签，各部门监听并认领匹配的）。
- **任何一方处理完都可以继续发新任务**：拆出子任务、打回发起方、转给第三方，不存在必须的终点。例如产品拆出两个子任务发给工程，工程再拆后发给验证，验证发现问题可直接打回产品或工程。
- **认领必须是原子操作**，避免两个部门同时认领同一块任务；可用数据库行级锁、分布式锁或投票机制。
- **任务池不关心处理者是谁**：只认标签、状态、依赖，所以新增能力等于新增一个订阅者（与微服务的发布订阅同一思路），不需要改核心机制。

## 部门边界与上下文工程

部门保留下来，但角色变了：它是上下文容器和职责边界，不再是执行顺序的边界。

**为什么保留部门**

- 独立上下文，可以做独立验证和独立实施，防止上下文污染。
- 三部门等于把上下文分成三份，每份更干净、更高效，部门内部还能做内聚的上下文组装。

**任务池与上下文是两层**

- 任务池只暴露元信息：任务是什么、状态、依赖、验证结果摘要。
- 部门处理任务时用的完整上下文（详细历史、内部推理、细节资料）保持私有，不进任务池，避免任务池变成大家都往里塞东西的大杂烩。
- 部门内可以有多个 agent 和多种角色（如产品经理、架构师、测试经理）；对外统一为一个黑箱接口：收到任务、给出结果和验证状态，内部怎么分工是部门自己的事。

**为什么是 agent loop，而不是普通多 agent**

- 普通多 agent 往往各自背着不断膨胀的记忆，时间越长无关信息越多，造成记忆污染。
- loop 的每一轮都可以重新组装上下文，只注入这一轮需要的部分；上一轮产出是输入之一，但不是整段历史照单全收。
- 组装应当主动、精确：任务节点标注依赖哪些历史产出，组装时按依赖拉取，而不是把任务池历史整体扔给 agent。

**后置事项**：知识图谱或语义系统可作为组装时的检索层，把每轮产出沉淀为可复用的经验资产。当前优先把循环跑通，图谱留到后面。

## 用户需求接入与收敛

用户被当作任务池的一个特殊参与方，需求模糊或变化时走正常的任务流转，而不是另设变更机制；为避免所有事情都推给用户，澄清只作为低置信度时的兜底路径。

- **接入方式**：用户发起的初始任务带“待澄清”状态；产品拆解时若某个子任务依赖用户，就生成“待用户确认”的任务节点放回池子，等用户响应后继续。
- **需求变化**：就是用户发起新任务，或对已有节点提出修改，照常流转。
- **要避免的风险**：什么都要用户澄清，会退化成早期 vibe coding 那样“先想清楚再给”；人参与循环还可能成为瓶颈。
- **默认推进**：遇到模糊点，产品部门先做合理假设、标注置信度并继续往下推进；只有置信度低于阈值，或假设一旦错误代价很大时，才打回去问用户。
- **大部分模糊靠后续验证环节收敛**，而不是层层上报。
- **置信度来源**：计划考虑用带置信度打分的 JEV 决策模型，既用于规则裁决，也用于决定是否升级给用户（JEV 目前尚未启用）。

## 存储与事件

第一版用 PostgreSQL 存任务、任务关系和事件历史，用 Redis 发布订阅做实时事件广播，两者各司其职。

| 组件 | 负责 | 不负责 |
| --- | --- | --- |
| PostgreSQL | 任务当前状态、任务关系（有环图的边）、不可变事件日志、原子认领（行级锁） | 实时推送 |
| Redis 发布订阅 | 状态变更时的实时事件广播，订阅方如可视化 | 存储任务全貌与历史 |

- **任务与事件共用一个库**：一张任务状态表保存当前快照，一张不可变事件表记录状态如何变化，两者关联；回溯时靠事件日志重建任意时刻的状态。
- **任务关系是有环图**，不是树，也不是无环图：验证打回产品、产品打回工程这类反向边和汇合点都要能表达。用邻接表存边，在关系库里用一张单独的任务关系表即可。
- **查询要做环检测**：遍历“某任务的完整历史链路”时记录已访问节点，避免程序自己绕圈。
- **环的代价由监控治理**：允许环就有无限打转的风险，靠预算上限和观察者兜底，而不是靠结构防止。
- **状态变更时的动作**：任务池写库的同时向 Redis 推一条事件；数据库是真相来源，事件总线只负责实时通知。

## 可视化（游戏化）解耦

可视化是任务池事件流的纯消费者：只订阅事件总线，不碰数据库，也不认领任务。

- **动机**：agent 内部状态的可观测性，要么靠 graph 式报告，要么靠看代码；把 agent 具象成人物、把交互组件具象成场景，状态一目了然。
- **接口解耦**：可视化通过接口接收事件，与任务池核心互不牵制，各自独立演进。
- **不直接读数据库**：直读会把可视化绑死在表结构上，换库或改表都要跟着改；数据库也只能给某一时刻的快照，拿不到“状态刚刚变化”这一瞬间。复用任务池已有的 Redis 事件发布订阅即可。
- **映射思路（示例）**：agent 认领任务，人物走向任务点；任务完成，场景发生变化；任务被打回，人物往回走或出现警示。
- **事件时间与叙事时间分离**：事件可能在零点一秒内就被接走，画面必须放缓才看得清。可视化内部加一层缓冲队列，每个动作有最小播放时长；事件堆积时可以合并、只播关键事件或快进次要事件。
- **这些播放节奏策略完全属于可视化组件自己**，不反向影响事件产生的一侧。

## 降解路径：从 agent 到确定性代码

某类任务一旦稳定，就把它的处理者从 agent 换成确定性代码，任务池接口不变，从而避开 agent 概率性出错。

- **动机**：人会把熟悉的事习惯化成 SOP，不再动用脑力；循环里发现固定下来的东西，就变成确定的流程和代码。
- **为什么任务池支持**：任务池按能力标签匹配处理者，不关心对方是 agent 还是脚本；替换只是换一个订阅者的实现，其他部分不用动。
- **结果**：部门内部会逐渐演化成 agent 与确定性代码混合的结构，部门依然存在，只是内部构成在变。
- **降解信号**：某类任务连续成功次数、置信度是否持续偏高、是否从未被打回，这些都能从任务的执行历史里量化。
- **谁来发起**：观察者角色监控这些信号，达到阈值时提示或触发“该把这类任务换成确定性代码了”。
- **终态**：规则本身也能固化，且规则是从数据里长出来的，而不是预先拍脑袋定的。

## 风险与未知的未知

五个风险点里，并发认领和循环终止已有明确的工程解法，幻觉级联和审计轨迹还没有具体方案。后三项来自对常见多 agent 编排失败模式的对照检索，未逐篇核对原文。

| 风险 | 说明 | 对策 | 现状 |
| --- | --- | --- | --- |
| 认领并发冲突 | 多个 agent 同时认领同一任务，重复处理或互相覆盖结果 | 原子认领，分布式锁或投票机制 | 思路已定 |
| 循环振荡与终止 | 验证与产品来回打回，收敛不了 | 预算上限，加观察者判断 | “原地打转”的判据待细化 |
| 幻觉级联 | 上游 agent 的错误产出被下游当作事实放大；验证若基于同一错误假设，会一起出错 | 暂无 | 待讨论 |
| 审计轨迹 | 任务被谁改过、为什么改、依据是什么 | 不可变事件表可承载 | 需定义记录哪些字段 |
| 自我诊断不可信 | 不能让 agent 自己判断是否陷入循环，判断机制本身可能已失效 | 用外部机制检测：重试上限、预算、观察者 | 部分覆盖 |

## 技术选型、实施顺序与待决问题

第一版用 Python + PostgreSQL + Redis 把循环跑通，架构稳定后再用 Rust 重构；知识图谱留到循环跑通之后。

**选型**

- 语言：Yudao 的 agent 层现在是 Python，任务池沿用 Python；后续出于性能考虑计划用 Rust 重构。
- 存储与事件：PostgreSQL + Redis 发布订阅（见“存储与事件”）。

**建议的实施顺序**

1. 任务池：任务节点、状态机、原子认领、事件表。
2. 让三个部门改为发布与认领任务，交接粒度缩到小块，正反向都按小块走。
3. 上下文按依赖精确组装。
4. 观察者：预算上限、振荡检测。
5. 可视化订阅事件总线。
6. 稳定任务类型的降解。
7. 知识图谱与经验沉淀。

**待决问题**

- [ ] 最小闭环先拿哪个场景试（例如产品到工程这一段）。
- [ ] 部门间统一交接单元的格式：文档、代码、任务描述都有，是否统一包一层带状态、依赖、验证结果的结构。
- [ ] “原地打转”的判据：用什么指标识别振荡。
- [ ] 幻觉级联的对策，以及验证如何避免和上游共享同一错误假设。
- [ ] 审计轨迹要记录哪些字段。
- [ ] 演化式软件开发（用户需求持续变化）如何对应到这套机制，讨论中暂缓。
- [ ] JEV 决策模型何时引入，目前尚未使用。
