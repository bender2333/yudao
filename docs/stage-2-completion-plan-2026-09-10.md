## 0. 本阶段结束时，系统是什么

系统应先成为一个类似 OMP 的可运行 Harness：用户从 Web 或 API 发起一个事项，三部门各自维护上下文并完成交接、工具执行、QA、交付、停止、重试、压缩、审计和 replay。项目层负责事项归属、成果采纳和继承，但不另起一套运行器。

证据驱动的局部控制、跨任务经验和四组比较属于后续阶段，不是 Stage 2 的完成条件。

## 2. 概念层级

```
项目（长期目标、资料、当前采用成果、部门 Prompt 配置）
 ├─ 部门 × 3（属于项目，不是事项的下级）
 ├─ 事项（一次有边界的变更）
 │    └─ 主 run（一次执行；Stage 2 一事一 run）
 │         └─ 模型尝试 / 工具 / 事件 / 用量
 ├─ 采纳记录（QA 放行之后的项目事实，可与 QA 不一致地被 hold）
 └─ 项目材料（无活跃事项时只记录原文）
```

因果：项目提供长期身份和继承；事项提供本次要改变什么；run 仍是三部门循环的执行单位；尝试是观测的最小范围。看板卡片指事项，不指 run。观测可以按项目 / 事项 / 部门筛选，但事实仍来自所属 run。

用语：

- **项目**：显式登记的长期对象。目录名、最新 DONE 的 run、聊天会话都不是项目。
- **事项**：一次变更。协作总览的流程和看板都指它。
- **采纳**：项目接受一份已放行交付为当前成果。不是 QA release，也不是部署。
- **有效产品合同**：该 run 内当前 ProductSpec，加上绑在该 spec 上、未改写 spec 的已回答协作。由投影决定，模型不能改写。
- **仍有效的决定摘要**：跨事项继承时注入的、上一份被采纳工作所依据的有效产品合同摘要。不是历史对话。

避免把「任务」「工作项」「run」混用。第三版原型里的「工作项」即事项。

## 3. 三层职责

沿用既有分层，本阶段只在中间加一层，不拆内核。

| 层 | 责任 | 本阶段变化 | 不做 |
| --- | --- | --- | --- |
| 界面 | 呈现项目导航、概览、看板、部门页、观测；把用户动作变成命令 | 按第三版原型重组外壳；部门页内部与观测详情沿用第一版 | 不生成运行事实，不拖拽改状态，不做 Provider 配置表单 |
| 业务引擎 · 运行内核 | 一次 run 的交接、合同、QA、封存、run 内 Git、重试、压缩、指导 | 只携带项目/事项归属、初始树、项目钉住材料和初始 Prompt | 不知道「项目当前成果」，不做采纳 |
| 业务引擎 · 项目层 | 登记、建事项（唯一产品入口）、采纳结算、继承恢复、部门 Prompt 项目配置、项目材料、项目读模型 | 新增；只在创建事项时调用 `create_run` | 不调用模型，不改 run 事件 |
| 基础设施 | 事件库、工件、封存、Provider 目录 | 同库新增 `project_events` 表 | 项目事件不进入 run 流 |

学习轨道在汇合点之后，同样三层，不另起服务：

| 层 | 谁用 | 产出 |
| --- | --- | --- |
| 证据 | 已结束的项目内 run | 可搬移、可核验的经历包；加载不执行交付 |
| 评价 | 研发者事先固定的检查 | 独立副本上的复核结论；不改写原 QA 或终态 |
| 分析 / 控制 / 经验 | 研发者 | 问题轨迹、一项有界控制、一条可停用的经验；进入执行必须经唯一内核入口 |

查询只生成投影。结算是项目层的幂等记账：它记录已经发生的 run 终态，不是新工作。读取项目时可以转交一次补跑，事件本身可审计。查询层仍不发起事项、不改 Prompt、不调模型。

## 4. 因果链与顺序

```text
H0 冻结合同、源码、Provider、任务材料和证据口径
  └─ H1 核对三部门运行内核与状态主权
       ├─ H2 项目 / 事项 / run 唯一入口与采纳接线
       └─ H3 Context、Provider、Raw、usage、审计和 replay 收口
            └─ H4 同一冻结版本上的真实 Web/API 端到端联调
                 └─ H5 文档、回归、证据账和 Stage 2 冻结
```

H2 与 H3 可以在 H1 后并行，但 H4 必须同时依赖二者。A1–A3、B3、A4、B4 和 2.1 L1–L3 的现有证据作为输入复用，不重新扩大 Stage 2 范围。2.2 局部控制、2.3 跨任务经验、2.4 四组比较移到后续证据改进阶段。

## 5. 已确认边界

- 三部门是同一个 Harness 的执行引擎组织；Product、Engineering、Quality 各自维护部门历史，不能把一次部门激活当成全新 Agent。
- 运行内核拥有一次 run 的状态主权：上下文装配、模型单次调用、工具准入与执行、交接、停止/取消、重试、压缩、QA、交付、封存和终态判断。
- 项目层只负责项目、事项、初始材料、Prompt 配置、Provider/Prompt 快照、成果采纳和继承，不调用模型、不另起 runner、不直接改 run 事件。
- Provider adapter 只负责模型服务调用；OMP 作为机制参考，不成为运行时状态主权方。
- Web、API、CLI 和 replay 只通过同一事件库和投影读取事实。Fake、探针和局部测试只用于局部回归。
- 8000 窗口只保留为压力验收附录。有效窗口由任务限制与 Provider/模型能力共同决定，接近容量阈值时才触发压缩；不把 8000 写成生产默认。
- 旧运行数据直接弃用，不迁移、不留兼容入口；真实失败、取消、暂停和重试耗尽记录原样保留。

## 6. 工作包与交付物

### H0：冻结验收基线

固定源码 SHA、`provider.md` 指定 Provider、三部门 Prompt、任务原文、工具权限、预算、重试上限、上下文窗口和公开验收表。建立不含凭据的运行登记模板，明确 32000 主验收、容量对照和 8000 压力附录的关系。

**产出与验收：** 可复核的冻结清单、脱敏 Provider 快照、任务材料哈希和证据目录；未跟踪文件不进入冻结。

### H1：运行内核收口

核对三部门历史隔离、交接合同、工具准入、proposal 与采纳配对、停止/取消优先级、重试耗尽、上下文超限、预算/步数耗尽和压缩边界。压缩请求不得执行工具，终态不能由模型自然语言单独宣布。

**产出与验收：** 同一 run 的事件序列能证明 Product → Engineering → Quality 的因果关系；失败路径保持真实状态；已有本地回归和必要的边界测试通过。

### H2：项目、事项与 run 接线

验证“项目 → 事项 → run”唯一入口。创建 run 时绑定 `project_id`、`work_item_id`、初始树、材料、Prompt 版本和 Provider 快照；只有 QA release 后才允许项目采纳，失败、取消、暂停和未接纳候选不能进入项目成果。

**产出与验收：** 项目事件与 run 事件可分开重建；跨项目不可见；采纳与 QA release 可分别核对；项目层不产生第二运行器。

### H3：观测、审计与 replay

确保一条 run 能回查原始意图、有效合同、部门历史、Context parts、实际模型输入、Prompt/Provider 快照、Raw 请求/响应、usage、工具事件、压缩摘要及其来源。`model_input_audit` 必须可核验为 `verified`，查询只读，replay 不依赖进程内缓存。

**产出与验收：** 事件投影、详情页和 replay 对同一终态给出一致事实；原始历史可回查，压缩发生与未发生都能解释。

### H4：真实端到端联调

在同一冻结版本使用真实 Provider 完成至少一条主场景：

`Web 或 API → Product → Engineering → Quality → 实际工具 → 独立 QA → 交付/封存 → release → replay`

同时保留至少一条真实失败、取消、超时、Provider error 或重试耗尽记录。核对部门隔离、交接、工具权限、Context/Provider 展示、停止/重试规则、输入审计，并证明 Web 与 API 指向同一运行内核。

**产出与验收：** 一份含运行 ID、事件序列、Raw/usage、审计和 replay 结果的真实证据包；成功与失败都不被脚本改写。

### H5：Stage 2 收尾

更新 `stage-2-progress.md`、`stage-2-evidence-ledger.md`、验收报告和 `jour.md`；执行受影响模块定向回归及完整回归；确认冻结提交、未跟踪文件和远端发布状态；由主代理独立复核完成判定。

## 7. Stage 3 与后续证据改进阶段

Stage 3 从一个已经可运行的三部门 Harness 出发，扩展 OMP 类通用能力：更广泛的 shell/搜索/技能、恢复、并行、第二协议 Provider、CLI/嵌入和运维。Stage 3 不是本计划的阻塞项。

随后另立“证据改进阶段”，再处理 2.2 局部控制、2.3 跨任务经验和 2.4 四组比较。2.1 L1–L3 仅作为观测基础设施复用；没有真实重复错误时，不编造控制、经验或比较样本。

## 8. 工作包回执规则

每个工作包完成后在证据账和 `jour.md` 记录：提交哈希、源码冻结身份、修改文件、关闭项与开放项、测试命令及通过/失败/跳过数量、报告路径、真实 Provider/模型/窗口/重试限制/运行 ID，以及失败的原始错误、影响范围和恢复条件。凭据不得进入文件或报告。
