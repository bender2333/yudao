## 2. 概念层级

```
项目（长期目标、资料、当前采用成果、部门 Prompt 配置）
 ├─ 部门 × 3（属于项目，不是事项的下级）
 ├─ 事项（一次有边界的变更）
 │    └─ 主 run（一次执行；Stage 2 一事一 run）
 │         └─ 模型尝试 / 工具 / 事件 / 用量
 ├─ 采纳记录（QA 放行之后的项目事实，可与 QA 不一致地被 hold）
 └─ 项目材料（无活跃事项时只记录原文）
```

因果：项目提供长期身份和继承；事项提供本次要改变什么；run 仍是三部门循环的执行单位；尝试是观测的最小范围。看板卡片指事项，不指 run。观测可以按项目 / 事项 / 部门筛选，但事实仍来自所属 run。

用语：

- **项目**：显式登记的长期对象。目录名、最新 DONE 的 run、聊天会话都不是项目。
- **事项**：一次变更。协作总览的流程和看板都指它。
- **采纳**：项目接受一份已放行交付为当前成果。不是 QA release，也不是部署。
- **有效产品合同**：该 run 内当前 ProductSpec，加上绑在该 spec 上、未改写 spec 的已回答协作。由投影决定，模型不能改写。
- **仍有效的决定摘要**：跨事项继承时注入的、上一份被采纳工作所依据的有效产品合同摘要。不是历史对话。

避免把「任务」「工作项」「run」混用。第三版原型里的「工作项」即事项。

## 3. 三层职责

沿用既有分层，本阶段只在中间加一层，不拆内核。

| 层 | 责任 | 本阶段变化 | 不做 |
| --- | --- | --- | --- |
| 界面 | 呈现项目导航、概览、看板、部门页、观测；把用户动作变成命令 | 按第三版原型重组外壳；部门页内部与观测详情沿用第一版 | 不生成运行事实，不拖拽改状态，不做 Provider 配置表单 |
| 业务引擎 · 运行内核 | 一次 run 的交接、合同、QA、封存、run 内 Git、重试、压缩、指导 | 只携带项目/事项归属、初始树、项目钉住材料和初始 Prompt | 不知道「项目当前成果」，不做采纳 |
| 业务引擎 · 项目层 | 登记、建事项（唯一产品入口）、采纳结算、继承恢复、部门 Prompt 项目配置、项目材料、项目读模型 | 新增；只在创建事项时调用 `create_run` | 不调用模型，不改 run 事件 |
| 基础设施 | 事件库、工件、封存、Provider 目录 | 同库新增 `project_events` 表 | 项目事件不进入 run 流 |

学习轨道在汇合点之后，同样三层，不另起服务：

| 层 | 谁用 | 产出 |
| --- | --- | --- |
| 证据 | 已结束的项目内 run | 可搬移、可核验的经历包；加载不执行交付 |
| 评价 | 研发者事先固定的检查 | 独立副本上的复核结论；不改写原 QA 或终态 |
| 分析 / 控制 / 经验 | 研发者 | 问题轨迹、一项有界控制、一条可停用的经验；进入执行必须经唯一内核入口 |

查询只生成投影。结算是项目层的幂等记账：它记录已经发生的 run 终态，不是新工作。读取项目时可以转交一次补跑，事件本身可审计。查询层仍不发起事项、不改 Prompt、不调模型。

## 4. 因果链与顺序

```text
S2-0  收口 B1 并提交（含第 7 节对 B0 的修正）
  └─ S2-1  同一冻结上关闭 A1–A3（A1 = 已确认 Provider 配置的 32000 到 QA + 容量对照；压缩只记录）
        ├─ S2-2  B3 第三版外壳
        └─ S2-3  A4 Prompt 固定任务比较
              └─ S2-4  B4 三次变更真实验收
                    └─ S2-5  2.1 可信观察与固定基线
                          ├─ S2-6  2.2 一项局部控制
                          ├─ S2-7  2.3 一条跨任务经验
                          └─ S2-8  2.4 四组综合比较
```


为什么是这个顺序，而不是别的：

1. **先提交项目层，再冻结内核。** 脏工作树不能当被测版本。B4 和 A4 都要在带项目归属的内核上跑；A1 在该冻结上重做 32000 到 QA，不再要求窄窗压缩后到 QA。
2. **外壳和 Prompt 比较可以并行。** A4 需要的是项目级 Prompt 版本机制和冻结内核，不需要第三版页面。B3 等 S2-1 的 32000 到 QA，不等待压缩发生。

3. **B4 必须在 B3 之后。** 三次变更是人在项目工作台上的真实路径：创建项目、看看板、改 Prompt、从观测跳回。没有外壳就只是 API 编排，不能称为项目级验收。
4. **B4 必须能追溯 Prompt 版本。** 不要求 A4 已经得出「采用」结论，只要求版本机制可核对「改配置后的下一事项用新版本、历史请求不变」。
5. **学习轨道必须在产品结构稳定之后。** 2.1 的经历挂在项目内的 run 上。没有项目层，基线和经验会重新长在裸 run 上，后面还要搬一次。
6. **先观察，再动手，再比较。** 没有固定基线的控制或经验只是故事。2.2 与 2.3 可在 2.1 之后并行，因为一个走内核入口、一个走检索与注入，但 2.4 必须等两组都冻结。

B5 接入已有项目建档不在本阶段完成条件里，保持后置。

3. **A4 的「采用」只改被测项目的部门 Prompt 配置。** `department_prompts.py` 的系统默认只有在比较支持且用户确认后，另一次提交再提升。没有改善则项目配置和系统默认都不动。
4. **Stage 2 维持一事一主 run。** A4 基线组与候选组是两个事项（或两个项目），不是同一事项的第二次 run。2.1 复核是离线评价，不创建新 run。2.4 四组是四次独立事项。同一任务材料的多轮不增加样本数。
5. **有进行中事项的项目不能归档。** 归档后仍可补跑结算（记账已发生的放行）。创建事项、改 Prompt、记材料、重命名等写命令对归档项目返回冲突。`start_work_item` 先检查可写，再创建。

## 7. 对 B0 的收口修正

S2-0 对照合同时，下列缺口先写进 [项目工作台合同](project-workbench-contract.md)，再改工作树。不把它们当成实现细节悄悄修。

1. **钉住部件补回「仍有效的决定摘要」。** 排布 D-C 要求跨 run 注入：当前采用成果 + 仍有效的决定摘要 + 本事项差异。B0 §5 目前只有成果摘要、已采纳标题和本事项名。没有决定摘要，B4 第三次变更无法稳定保持「空输入不崩溃」这类仍有效要求——产品部门只能靠事项原文记住旧合同。修正：从源 run 投影取出当前有效产品合同，写成确定性摘要，放进 `project` 钉住部件；不带历史对话、失败尝试或过时计划。
2. **继承只允许同一项目的源 run。** 装树前核对源 run 的 `project_id` 与当前项目相同；投影派生事项时，所属 run 的 `work_item_id` / `project_id` 必须匹配。
3. **结算与归档的关系按第 6 节假设 5。** 读取路径转交幂等结算，不算查询层「写新工作」；合同 §1「查询不写事件」改为「查询不发起新工作，可转交幂等记账」。
4. **归档进行中项目。** 有 `in_progress` 事项时归档失败。避免归档后活动 run 再写入采纳，造成「只读项目仍在前进」。
5. **「记录原文」是服务器不变量，不只是界面开关。** 有 `in_progress` 事项时拒绝 `record_material`；活跃事项的输入走 run 级 inputs/guidance。项目材料本阶段只出现在项目投影里，不自动注入后续 run 的模型输入。

工作树里已发现「先 `settle_pending` 再检查归档」的顺序，与上列第 3、4 条冲突，收口时改掉。

- 基线组与候选组 = 两个事项或两个项目，独立工作区、相同原始起点，交替执行，保留失败。

- 结论只允许：采用（只写被测项目配置）、缩小范围、保留原版。没有改善也出正式报告。系统默认 Prompt 不在本包改。

### S2-4：B4 联调与三次变更真实验收

在 B3 完成、A4 版本机制可追溯、S2-1 冻结可指认之后，同一源码执行三次事项：

1. 从想法创建逐行文本处理项目，首个交付经独立 QA 放行后自动采纳。
2. 在上一版本上增加文件输入；完整树继承、旧成果可取回、新成果采纳。
3. 把「保留重复行」改为「只保留首次出现」，保持空输入行为，更新必要检查；合法改方向，旧基线结果拒收。

过程中修改一次工程部门项目 Prompt，下一事项必须用新版本，历史请求仍显示原版本。还要覆盖：看板与事件一致、Context 到模型尝试的跳转、封存恢复后的外部检查、项目/事项/部门筛选和跨项目隔离。

三次事项的「仍有效要求」必须能从项目钉住部件回到上一份有效产品合同，不能只靠测试脚本把旧要求再贴进事项原文冒充继承。

### S2-5：2.1 可信观察与固定基线

2.1 是学习轨道入口。研究工作树的 `harness.analysis` 不是现成实现。归属：证据包、问题轨迹和基线都挂在项目内的 run 上。

开工前先补一页当前合同，最少写清：首个任务族与公开检查、评价由哪些主机检查承担、采样与成本口径、证据包字段、来源缺失/篡改如何失败。未写完不开工。

- L1：证据包可保存、搬移、只读加载、重算轨迹；来源缺失或篡改明确失败；加载不执行交付。
- L2：本地材料清单驱动多轮独立复核；缺失、超时、QA 依据不足保持原状态。
- L3：多份已核验证据批次统计；重复包不重复计分；重评成本和来源分开显示。
- 固定真实重复错误场景、独立评价方法、成本口径和问题身份，形成第一份可追溯基线报告。

首个端到端结果：固定的三轮「失败 → 通过 → 失败」样例能追到字节，搬移后只读可重算，原运行不被改写。然后再采真实任务（含失败和暂停）。真实运行没有自然回归也如实报告。

### S2-6：2.2 一项局部控制

从 2.1 基线选一个真实重复错误。登记触发条件、允许动作、停止条件、不适用条件；只通过唯一内核入口接入。控制不能修改需求、绕过 QA 或重置既有限制。

验收必须包含：正常返工不误触发、未见任务前后对照、全部新增请求/人工/存储成本、失效时的停止和回退。收益只能用未见任务证明。

### S2-7：2.3 跨任务经验

先贯通一条链路：候选来源 → 独立验证 → 适用检索 → 实际输入采用 → 冲突/反证失效。现有 `LessonCandidate` 只是 run 内待验证记录，不能直接当成有效经验。同一 run 的候选不能直接成为有效经验。

必须验证：相反建议、重复来源、过期索引、装配后失效、发送前后失效；没有适用经验时走基础流程。经验挂在项目内；收益用未见事项证明。

### S2-8：2.4 综合比较与阶段验收

冻结四组：基础、仅控制、仅经验、组合。四组共享评价、任务材料和停止规则，顺序执行。单次任务多轮不增加样本数，失败不能删除或改写。

交付综合报告：质量、错误放行、重复错误、请求/人工/存储/时间成本、未见任务结果、反证停用。结果可以是无改善或退化。只有证据支持才改变默认控制或经验集。
