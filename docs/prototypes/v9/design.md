# 原型 v9：像素引擎改为实体—组件—系统结构

更新：2026-09-29。状态：已实现，待用户审阅。

## 1. 范围

v9 换掉 v8 像素引擎的内部结构，分三步做完：

- **第一步：三个部门加共用机房，按实体—组件—系统重新搭建。** 项目楼层（大厅、三个部门、成果库、通往机房的门）、楼里的小人、通往机房的管线、地下室的机房都由实体组成：角色、包裹、房间、管道、设备。房间与管道按图结构声明，域事件生成任务或者信号，角色在自己的队列里做任务，空闲的角色自己挑事情做，管道持续运转。像素画风与页面导航保持 v8 的样子。
- **第二步：运维部门只用声明加进来。** 运维房间的排布、陈设、持续状态、任务种类全部写在声明里（第 3、8 节），引擎与画面代码里没有运维的字样。
- **第三步：决定请求在世界里完成回答。** 决定单贴在大厅的板上，点开在画面里回答，回答的整个过程不离开世界（第 9 节）。

保持 v8 原样的部分：

- 屏幕清单、页面导航、系统页、资料页、观测页、页面上的决定卡片——[v8 design.md](../v8/design.md) 第 6、7、9、10 节。
- 像素画风：配色、字体、贴图，第 8.2 节的小人外形与配件。
- 部门房间画面：`js/pixel/room.js`、`engine.js`、`sprites.js` 不改。
- 事实到画面的对照表——第 5.4、8.3 节两张表——作为任务与信号的目录使用（第 4 节）。
- `Y8.api` 的查询、命令、事件形状；界面层与示例后端的边界。界面层的面板（`ui/scenes.js`）多读两份已有的查询：部门工作间的角色列表、等待回答的决定请求。

创战纪式的画法、摄像机代替页面导航、外包角色的呈现、预测与说服，属于这一版验证过以后的下一步。

## 2. v8 的做法

- `layoutFor(hasOps)` 按写死的部门数组与 `x += 116` 这样的算式算房间位置，`pipesFor(lay)` 用字符串键一条条手写管道折线。
- `primaryItem(d)` 给每个部门挑一件事项，`syncWorkers()` 给每个部门建一个角色对象；`restFor(a)` 按事项状态返回姿势；细一点的事实靠 `tempWorker` 在原地叠 2.4 秒的临时姿势，小人不走动。
- `playEvent(ev)` 对事件类型做一次大的分支判断，每种事件对应一次编排好的动画，播完以后画面状态由 `restFor` 重新接管。
- 运维房间的陈设、持续状态、事件处理分散在 `drawOpsProps`、`restFor`、`playEvent` 里。
- 管道的光点由时间的算式决定，有事项活动就画，没有就不画。机房的设备位置、管线与事件动画写在画面代码里，部署的包裹从天花板垂直落到设备上。

## 3. 房间与管道：图结构声明

项目楼层的声明全部在 `js/pixel/floor-decl.js`：

```js
rooms = [
  { id: 'hall', label: '大厅', roomKind: 'hall', w: 100, pipeOutX: 22 },
  { id: 'product', label: '产品', roomKind: 'dept', w: 110, agentKind: 'agent', ports: [...], spots: {...}, props(c, r) {...} },
  { id: 'engineering', … }, { id: 'quality', … },
  { id: 'library', label: '成果库', roomKind: 'shelf', w: (flags) => (flags.ops ? 82 : 136), ports: ['in'] },
  { id: 'operations', label: '运维', roomKind: 'dept', w: 88, when: 'ops', agentKind: 'ops', ports: ['in', 'out'],
    spots: {...}, lit(ctx) {...}, tint(c, r, t, ctx) {...}, rest(ctx) {...}, props(c, r, t, ctx) {...} }
]
links = [
  { from: 'hall', to: 'product', kind: 'handoff' },
  { from: 'product', to: 'engineering', kind: 'handoff', valve: true },
  { from: 'engineering', to: 'quality', kind: 'handoff', valve: true },
  { from: 'quality', to: 'library', kind: 'handoff', valve: true },
  { from: 'quality', to: 'product', kind: 'return' },
  { from: 'product', to: 'engineering', kind: 'tube' }, { from: 'engineering', to: 'quality', kind: 'tube' }, { from: 'product', to: 'quality', kind: 'tube' },
  { from: 'library', to: 'operations', kind: 'handoff', optional: true },
  { from: 'operations', to: 'machine_room', kind: 'handoff', optional: true },
  { from: 'operations', to: 'hall', kind: 'return', via: 'under', optional: true }
]
```

房间声明的字段：

| 字段 | 含义 |
| --- | --- |
| `roomKind` | `hall`、`shelf`、`dept` 三种画法；部门房间的墙、屏幕、灯、门、工位由 `floor.js` 通用地画 |
| `w` | 宽度，数字，或者以 `flags` 为参数的函数 |
| `when` | 出现的条件名：`floorModel` 里同名字段为真才生成这个房间（`flags: ['ops']`，快照带着运维数据时运维房间出现） |
| `agentKind` | 没有角色设置时，这个房间里那一个角色的种类 |
| `ports` | 墙上画哪几个管道口：`in`、`out` 是交接管道，`tubeIn`、`tubeOut` 是传信管 |
| `spots` | 把任务的位置（文件柜、终端）对到房间里已有的陈设上 |
| `rest(ctx)` | 这个房间的持续状态，省略时用通用的事项状态表 |
| `lit(ctx)`、`tint(…)` | 什么时候亮灯；房间的着色（运维故障时泛红光） |
| `props(c, r, t, ctx)` | 房间的陈设怎样画，用 `engine.js` 已有的画法 |

`ECS.declareRooms(world, defs, flags)` 按声明顺序从左到右排布（起点 x 为 4，房间之间 6 个像素），算出每个房间的门、管道口、工位、文件柜、终端、监控屏的位置；`when` 不满足的房间不生成。宽度、位置沿用 v8 的常量，大厅的交接管道从信箱一侧出发，其余房间的交接管道从右墙的管道口出发。

`ECS.declareLinks(world, defs)` 按 `kind` 对应的路由规则算折线：`handoff` 与相邻房间之间的 `tube` 走水平线，跨过一个房间的 `tube` 走天花板下的长传信管，`return` 默认走天花板，声明 `via: 'under'` 时走地板下；`machine_room` 指走廊尽头通往机房的门；`optional` 的管道在端点不存在时跳过。声明可以自带折线 `pts`（机房与楼里的管线用它）。重新声明时同一根管道保留原来的流动状态。

`ECS.declareNodes(world, defs)` 声明不属于房间排布的节点，例如机房里的设备，几何由声明明确给出。`ECS.route(world, from, to)` 在声明的交接管道里找一条最短的路：两个房间之间有直接的管道就是它，没有就一段一段接起来（质检放行交给运维，包裹经过成果库）。

## 4. 角色、任务与信号

### 4.1 角色与工位

一个部门里有几个角色，取决于快照。Stage 5 的 `floorModel.roles` 是每个部门一份 `{ id, name, kind, status, task }` 的列表（界面层用 `department.workspace` 组装）；没有这个字段的档位，一个部门一个角色，种类是房间声明的 `agentKind`。回放到过去的时间点时也没有这个字段（部门工作间的查询不能回放），画面按一个部门一个角色画。快照里运维数据出现或消失时房间与管道按新的条件重新声明，角色、包裹、信号与管道的流动状态原样带过去。角色实体 `{ id, department, roleKind, name, seatIndex, queue, current, rest, bubble }` 对应 `engine.js` 场景里 `id` 为 `'ch-' + 角色 id` 的 actor，精灵是「部门.种类」。

房间里的工位随角色数排开：一个角色时是 v8 的单个工位；n 个角色时桌宽取 34 与「(房间宽 − 10) ÷ n − 2」中较小的，间隔 2，从左到右依次是探索者、审查者、主程、中心角色、经理（经理靠近右墙的管道口，跟部门房间画面的排布规则一致）。桌宽不到 30 时不画显示器。中心角色是架构师、测试工程师或者唯一的那个角色，没有中心角色时是经理；事项的小旗与桌上显示器的状态画在中心角色的桌上，其他角色的显示器看自己有没有在工作。

### 4.2 事件变成任务或者信号

一个域事件落到两类里的一类，判断依据是「这件事要不要有人去做」：

- **任务**：需要某个角色走到某个位置、做一个动作。任务定义 `{ label, spot, pose, ms, bubble, icon, facing, … }` 写在任务目录里，目录来自 [v8 design.md 第 8.3 节](../v8/design.md)那张「事实、来源、小人动作、房间变化」的表，加上部门内角色之间的动作、运维的动作、决定请求的送单与收单、待机活动。`spot` 是房间里的位置：`desk`、`stand`、`cabinet`、`terminal`、`monitor`、`inspect`、`port_in`、`port_out`、`door`、`peer`（另一个角色的工位旁）、`at`（任务自带的坐标）。
- **信号**：不需要角色去做什么，只是画面上的一个指示变化——管道通不通、时钟走不走、门缝亮不亮灯、信箱闪一下、监控屏告警。[v8 design.md 第 5.4 节](../v8/design.md)里整层或者整个物件的变化属于这一类。信号是带过期时间的命名值（`ECS.signal`），画面按名字读取。

事件落在哪个任务上由目录的 `keyOf` 决定（大多数事件类型本身就是任务键，少数按 payload 再分支：质检的放行与打回、工具的种类、审查的结论）。事件落在哪个角色上：

1. 事件带 `role`（角色 id 或者种类）就是那个角色。
2. 任务声明了 `actor`，就由这种角色做，不管事件指定了谁：分派任务由经理做，`role` 指的是接任务的人。
3. 任务声明了 `by`，事件没有指定角色时由这种角色做：对外的交接、传信、提交提案、装箱封存、门缝里的指导、决定单的送出与收下由经理做。
4. 任务声明了 `dept`，就由那个部门做：事件本身没有部门字段时用，例如运维的部署、回滚、故障记录、停止自动修复。
5. 都没有时是部门的中心角色。

任务队列的规则：每个角色一个队列。角色空着的时候取队首，走到 `spot`，从到达的时刻起做 `ms` 毫秒的 `pose`，做完取下一个。队列里最多留 3 个可以被挤掉的任务，超出时挤掉最早的；交接与传信的任务放在队首，不会被挤掉。整层静止（中断）时小人不出发，队列等着。任务可以声明 `then`（做完以后放进走向对象队列的任务）与 `fx`（开始与做完时的效果：信号、房间闪光、包裹沿管道走），效果由画面按声明执行。

### 4.3 持续状态

角色「现在该干什么」的持续状态取自快照，写在角色的 `rest` 上，形状与任务相同（`spot`、`pose`、`icon`、`iconText`、`facing`、`hold`、`away`）；没有任务在做时角色照 `rest` 摆放。静止的画面因此只由快照决定，事件只决定动作的起点。

一个房间里有几个角色时（跟部门房间画面的规则一致）：

- 部门整体的特殊状态（等待模型服务、待核实、询问中、待恢复、等待你的决定）落在中心角色身上；暂停、失败、完成、取消对每个人都一样。
- 其余按角色自己的状态：空闲喝茶，被分派拿着任务卡坐着，交回以后高兴，失败趴下，工作打字，外出的角色从画面上消失、回来时从门口走进来。
- 房间可以声明自己的持续状态（运维：有故障时站在监控屏前，有运行环境时工作，否则待机）。

### 4.4 交接

交接由三部分组成：交出方的经理走到管道口把包裹放进去（一个任务），包裹沿管道移动，接收方的经理走到管道口取出（一个任务）；返工与回流走另一侧的管道口。两个房间之间没有直接的管道时（质检放行交运维），包裹沿 `ECS.route` 找到的几段管道一段一段走。包裹（PRD 卷轴、交付箱、放行单、信件）是世界里的实体：放进管道时生成，沿折线移动，到达终点后销毁并触发接收方的任务。

### 4.5 部门内的角色之间（Stage 5）

- `x_role_task_assigned`：经理走到接任务的角色的工位旁，递出任务卡（头顶「分派任务」）。事件的 `role` 是接任务的角色。
- `x_role_result_returned`：交回结果的角色走到经理的工位旁，经理收下。事件的 `role` 是交回的角色。
- `x_review_recorded`：审查者在自己的桌上盖章，通过时对勾，退回时感叹号。
- `x_explorer_fetch`：探索者走到文件柜查资料。

同一时刻几个角色各自做着不同的任务，互相走动，画面上看到的就是这些队列在同时运转。

### 4.6 待机活动

空闲的角色（持续状态是喝茶，队列空）每隔一段时间自己挑一件事：从目录的待机活动里按权重抽一项，间隔取 5 至 12 秒，房间里的角色越多每个人挑得越稀（乘以 1 + 0.15 × (角色数 − 1)）。

| 活动 | 权重 | 内容 |
| --- | --- | --- |
| 坐着伸懒腰 | 3 | 在工位上伸腰 |
| 起身走动 | 4 | 走到房间里的一个位置伸懒腰 |
| 翻文件柜 | 3 | 走到文件柜翻找 |
| 门口抬头看 | 2 | 走到门口，抬头看 |
| 说话 | 4 | 房间里另一个空闲的角色也在，两人在房间中间碰头相对说话 |

待机活动不产生事实，头顶没有对话框；真正的任务一到，正在做的与排着的待机活动立刻放弃，走到一半的路也停下。整层静止或者系统设置为减少动画时不进行。`ECS.config.autonomy` 是自主行为的开关（待机活动、管道的惯性），验收脚本关掉它以后静止画面只由快照决定。

## 5. 管道的流动

管道是持续运转的实体，由 `ECS.stepPipes` 每帧推进，状态 `{ state, speed, load, phase }`：

- `flowing`（快照里两端有活跃事项，或者管道上有包裹在移动）：流速加速到满速，光点逐渐布满管道。
- `idle`：减速，光点淡出。
- `stopped`（等待模型服务、整层中断）：迅速停下，光点留在管道里，恢复以后接着流动。

光点的位置由累计的相位决定，停下时相位不再前进。因此管道的流动是一个有惯性、有内容的过程：事项一个接一个进来时管道里始终有光点在走，事项全部完成以后光点走完淡出，等待模型服务时光点停在原地。

## 6. 角色头顶的对话框

沿用 [v8 design.md 第 8.3 节](../v8/design.md)「模型请求中：打字，头顶思考气泡」与「流式输出：气泡中逐字出现文字」，推广到所有任务：

- **正在做**：角色做队列里的当前任务时，头顶出现说话气泡（实心尾巴），内容是任务的标签；模型请求在流式输出到达时，第一段文字取代默认的标签，后面的文字接在后面，气泡里显示最新的十几个字。
- **打算做**：队列里已经有下一个任务、而且这个任务带有标签时，头顶出现思考气泡（圆点尾巴）；队列里没有下一个任务，或者下一个任务没有标签，不显示这种气泡。
- 头顶已经有状态图标时，气泡画在图标上方；系统设置为减少动画时不画气泡；待机活动没有气泡。
- 气泡的内容只来自任务自己的字段，跟画面其余部分同一条规则：只显示已经查到的事实。房间里有几个角色就有几个各自的气泡。

## 7. 机房与楼

首页的楼与地下室的机房是两块画面，各有一个世界：

- **机房**：每台机器是一个设备节点（`ECS.declareNodes`，位置按机器数量均分），每个项目通往它正在使用的设备的管线是一根管道实体（折线：从右侧竖井顶端下来，沿天花板下的通道向左，再垂直下到设备），管线里有光点在流动，流速与光点数量由 `ECS.stepPipes` 推进（用着设备的项目是 `flowing`，只是运行环境的是 `idle`）。设备上的动作牌子、迟到回执、运行环境牌子、在线灯、故障信标由设备的当前数据画出，设备的闪光是带颜色的信号。
- **机房的事件**：远程动作开始，文件夹包裹沿这个项目通往设备的管线走下去；远程动作结束，回执沿管线走回去；部署，封存的箱子沿管线走下去；回滚，箱子从设备沿管线走上来。管线还没有画出来时包裹从天花板直接落到设备上。机房里没有角色。
- **楼**：每个用着机器的项目一根通往机房的管线（管道实体，沿右侧竖井下到地下室），光点由管道的流速推进；远程动作、部署、回滚的包裹沿它走。楼里每层一个小人（角色实体，没有房间，走位、待机由 `ECS.stepCharacters` 推进）。楼是缩小的示意画面，每层为四个部门房间留了固定的位置。

## 8. 运维部门：只写声明

运维部门（Stage 4）用第 3 节的声明加进来，涉及的全部内容在 `floor-decl.js` 里：

- 房间节点：宽度 88，快照带 `ops` 字段时出现，成果库变窄为 82，小人是运维部门 Agent。
- 陈设与状态：监控屏（故障时红色，屏下写运行的版本）、备份柜、小推车、门口的「停止自动修复」牌；有故障时房间泛红光；持续状态是有故障盯着监控屏、有运行环境时工作、否则待机。
- 管道：成果库到运维房间的交接管道、运维房间到通往机房的门的交接管道、运维房间回大厅的回流管道（走地板下）。
- 任务种类：部署（走到管道口把箱子放进通往机房的门，箱子到达以后门缝亮灯）、回滚（旧版本的箱子从门里取回，到达以后房间闪橙光）、发现故障（走到监控屏，监控屏闪红，故障信件沿回流管道送回大厅，大厅信箱亮一下）、停止自动修复。

快照的 `ops` 字段目前只有运行的版本、有没有故障、有没有停止自动修复三项；v8 design.md 第 8.3 节写的备份柜随备份亮起、监控屏显示两次修复的编号需要接口层补上备份与修复编号的字段，补上以后只在运维房间的声明里增加陈设与状态。

`ecs.js`、`floor.js`、`decision-card.js` 里没有任何具体的部门名。验收脚本 `checks/behaviors.js` 检查这一点，并且用内存里的声明做两次实验：去掉运维的房间声明，画面照常运转，运维的事件没有反应也不出错；再只写声明加一个新的房间与一种任务，新房间按顺序排进去、有自己的小人、新任务落在它的小人身上，引擎与画面代码一个字符不改。

## 9. 决定请求：在世界里回答

决定请求是「用户回来时哪些事需要我决定」，卡片的内容与选项来自 `decisions.list`（种类、材料、选项、挡住的对象），回答走命令 `decision.answer`。v9 在项目楼层里把这个场景做成完整的世界内交互：

- **决定单的来历**：提出决定的部门的经理走到门口送出决定单，决定单沿弧线飞到大厅的板上；没有部门的决定请求（初始 PRD）从大厅上方飞进来。飞行期间板上还看不到这张单子，落下来时板子闪一下。
- **大厅的板**：告示板立在大厅的地面上（不与墙上的钟、槽位灯、管道重叠），上方一块「待你决定」的牌子，每个等待回答的决定请求是板上一张便条，便条上沿的颜色是它所属事项的颜色（最多画 6 张，多的写「+N」）。没有等待回答的决定请求时，板子不出现。
- **卡片**：点板子，一张纸在画面里摊开：左边的色条按种类区分，抬头是决定的种类，下面是项目与事项、已经等待的时间、挡住的对象，再往下是材料（标题在左，内容在右，按宽度折行；放不下时截断并提示其余内容在文字列表里），材料里指向别的页面的内容是可以点的链接（固定在说明栏上方的一行）。多张决定请求时抬头左侧翻页（也可以用左右方向键，在别处的文本框里打字时方向键不翻页），右上角关闭（Esc 也可以）。
- **回答**：纸的下方是说明栏（画面里的横线纸，上面叠一个透明的输入框，中文输入法需要它），最下面每个选项是一枚章（选项太多时按比例收窄）。点章调用 `decision.answer`（带着决定的版本，说明附在里面）；需要说明的选项没写说明时纸上提示，不提交；命令被拒绝时纸上显示原因。接受以后纸上盖「已回答：选项名」的章，选项变灰，说明栏的文字留着，1.2 秒后纸自动收起；事件流带来的新列表里这个决定已经不在时，纸也留到盖章结束。
- **回答以后**：事件流送来回答事件，回答过的决定单从板上飞回提出决定的部门的门口，经理在门口收下（头顶「收到回答」）。板子上的便条随快照减少。
- **文字版本**：画面下方的「文字列表」里同样列出这些决定请求（页面卡片，材料与选项相同），这是画面之外读取与操作的方式。回放到过去的时间点时不显示决定请求。

项目概览页页面上方的「待你决定」区块，内容放在大厅的板与文字列表里。首页的决定卡片、标签栏的「待你决定」弹窗、恢复页与运维工作间的卡片沿用 v8 的页面卡片，它们与卡片里指向别的页面的链接（模型管理、部门设置……）一起，属于之后把整个系统搬进世界的步骤。

## 10. 系统清单

- **任务派发**（`ECS.dispatch`）：事件按第 4 节的规则转成任务或者信号。
- **移动与执行**（`ECS.stepCharacters`）：角色从当前位置走到任务的 `spot`，到达后播放 `pose` 并开始计时；没有任务时照 `rest` 摆放，空闲时自己挑待机活动。
- **包裹**（`ECS.stepPackages`）：沿管道的折线移动，到达终点后销毁并执行回调。
- **管道**（`ECS.stepPipes`）：第 5 节。
- **信号**（`ECS.signal`）：第 4.2 节。
- **气泡**（`ECS.bubbleFor`）：第 6 节。
- **渲染**：把房间、管道、角色、包裹这些实体的当前状态画到画布上，复用 `engine.js` 已有的画布原语，不新增画法。

## 11. 分工

核心的实体、组件与系统（第 3 至 6 节）、任务目录与声明、项目楼层画面（`floor.js`）、机房与楼的改写（`building.js`）、世界里的决定卡片（`decision-card.js`）、验收脚本由架构师完成；楼里的小人（`building.js` 里的走位与待机）由 omp 完成（任务 B），细则见 [BUILD.md](BUILD.md)。

## 12. 验收

九档 × 现有页面 × 两种宽度与主题跑一遍，控制台错误为零，十九个场景全部能走完。v9 的画面与 v8 有两类差别：

- **事件进行中的画面与新增的画面**：角色走到具体位置、包裹沿管道与管线移动、头顶对话框、待机活动、管道的惯性、多角色、大厅的决定板与决定卡片、运维小人对事件的动作。
- **静止以后的画面**：关闭自主行为、快照不带角色与决定请求时，项目楼层、楼与机房在静止时跟 v8 逐像素相同（房间位置、管道走向、小人外形与姿势都不变），由 [BUILD.md](BUILD.md) 第 4 节的回放比较与楼与机房的比较验证。多角色、决定板出现在快照带着这些数据的时候，这些画面由 `behaviors.js` 的行为检查与 `life.js` 的过程截图查看。
