# 原型 v9：像素引擎改为实体—组件—系统结构

更新：2026-09-29。状态：已实现，待用户审阅。

## 1. 范围

v9 只换掉 v8 的像素引擎内部结构（`js/pixel/floor.js`、`building.js` 里跟房间、管道、角色有关的部分，新增 `js/pixel/ecs.js`），不改其余东西：

- 屏幕清单、页面导航、系统页、决定卡片、资料页、观测页——[v8 design.md](../v8/design.md) 第 6、7、9、10 节原样保留，本说明不重复。
- 像素画风——配色、字体、贴图，[v8 design.md](../v8/design.md) 第 8.2 节的小人外形与配件原样保留。
- 部门房间画面——`js/pixel/room.js` 原样保留，`engine.js`、`sprites.js` 同样不改。
- 房间与管道的拓扑——大厅、产品、工程、质检、成果库、运维（Stage 4）、通往机房的门，跟 v8 design.md 第 5.2、5.3 节一样，一个部门一个角色，不新增部门。
- 事实到画面的对照表——第 5.4、8.3 节两张表——原样保留，v9 把它们当作任务与信号的目录来用，见第 4 节，不重新定义一遍事实与动作的对应关系。
- `Y8.api` 的查询、命令、事件形状不变；界面层与示例后端的边界不变。

会变的只是：房间与管道从写死坐标改成图结构声明（第 3 节）；域事件从直接触发一次动画改成生成任务或者信号，由角色自己的队列消化（第 4 节）；新增角色头顶的对话框（第 5 节）。

新增部门、创战纪式的画法、摄像机代替页面导航、外包角色的呈现、预测与说服，都不在这一版里，属于验证过这一步之后的下一步。

## 2. 现状与要换掉的地方

`floor.js` 现在的结构：

- `layoutFor(hasOps)`：按 `DEPTS = ['product', 'engineering', 'quality']` 这个写死的数组和 `x += 116` 这样的坐标算式，算出每个房间的位置；`pipesFor(lay)` 同样用字符串键（`'hall>product'`）一条条手写管道的折线。新增一个房间要改这两个函数的函数体。
- `primaryItem(d)`：一个部门只挑一件"当前最要紧"的事项，`syncWorkers()` 给每个部门建一个角色对象，角色的 `data.item` 就是这一件。一个部门同时只能有一个可见的角色状态。
- `restFor(a)`：对 `primaryItem` 返回的这一件事项的 `status` 字段做一次大的分支判断，直接返回一个姿势。状态没变时姿势也不会变；细一点的事实（`model_requested`、`tool_started` 这些）经 `playEvent` 的 `tempWorker` 在原地叠一个 2.4 秒的临时姿势和图标，时间到了退回 `restFor` 的姿势，角色不会真的走到文件柜或者终端那个位置。
- `playEvent(ev)`：对事件类型做一次大的分支判断，每种事件对应一次编排好的动画调用（`send`、`portTrip`、`flash`）。事件播完，画面状态由 `restFor` 重新接管，动画本身不留下任何状态。

这样做的结果：房间里的东西是"当前状态的一次性图解"，不是一个在跑的模拟；一个部门永远只有一个可见的角色，即使这件事项经过的步骤很多，也只在原地叠一层临时姿势，不会走动。

## 3. 房间与管道：图结构声明

每一层楼（v9 阶段还是固定的产品、工程、质检加大厅、成果库、运维、机房门）用一份声明描述，不再写坐标算式：

```
rooms = [
  { id: 'hall', label: '大厅', roomKind: 'hall' },
  { id: 'product', label: '产品', roomKind: 'dept' },
  { id: 'engineering', label: '工程', roomKind: 'dept' },
  { id: 'quality', label: '质检', roomKind: 'dept' },
  { id: 'library', label: '成果库', roomKind: 'shelf' },
  { id: 'operations', label: '运维', roomKind: 'dept', optional: true }
]
links = [
  { from: 'hall', to: 'product', kind: 'handoff' },
  { from: 'product', to: 'engineering', kind: 'handoff' },
  { from: 'engineering', to: 'quality', kind: 'handoff' },
  { from: 'quality', to: 'library', kind: 'handoff' },
  { from: 'quality', to: 'product', kind: 'return' },
  { from: 'product', to: 'engineering', kind: 'tube' },
  { from: 'engineering', to: 'quality', kind: 'tube' },
  { from: 'product', to: 'quality', kind: 'tube' },
  { from: 'library', to: 'operations', kind: 'handoff', optional: true },
  { from: 'operations', to: 'machine_room', kind: 'handoff', optional: true },
  { from: 'operations', to: 'hall', kind: 'return', via: 'under', optional: true }
]
```

一个通用的排布函数把这份声明变成位置：房间按声明顺序从左到右排开，宽度由房间种类决定（大厅 100、部门房间 110、运维房间 88、成果库在有运维房间时 82、否则 136，跟 v8 的宽度一样，画面看起来不变）；每条 `link` 的折线由起点房间的出口、终点房间的入口和 `kind` 对应的路由规则（`handoff`/`tube` 走 `PIPE_Y`/`TUBE_Y` 那条水平线，`return` 默认走天花板的回流线，声明 `via: 'under'` 的走地板下）算出，不再要求每条管道单独手写坐标。`optional: true` 的房间与管道在 `hasOps` 为假时整体跳过。

这份声明现在描述的房间和管道，跟 v8 现在画出来的完全一样，这一步要验证的是"排布能不能从声明生成"；加一个部门、看排布是否还成立，是第二步的事。

## 4. 事件变成任务或者信号

一个域事件落到两类里的一类，判断依据是"这件事要不要有人去做"：

- **任务**：需要某个角色走到某个位置、做一个动作。[v8 design.md 第 8.3 节](../v8/design.md)那张"事实、来源、小人动作、房间变化"的表作为任务目录：表里的每一行是一种任务定义（标签、位置 `spot`、姿势 `pose`、时长、头顶图标、气泡），`spot` 是这个任务要在房间里的哪个位置完成（工位、文件柜、终端、检验台、管道口……），值从表里"小人动作"那一列的描述对应（"翻文件柜"→文件柜位置，"走到终端拉下拉杆"→终端位置）。项目楼层里的房间没有画文件柜与终端，这两个位置取房间里对应的站位。
- **信号**：不需要角色去做什么，只是画面上的一个指示变化——管道通不通、时钟走不走、门缝亮不亮灯、看板上的一个数字。[v8 design.md 第 5.4 节](../v8/design.md)那张表里"循环次数与时间""待恢复""等待执行槽位"这类整层或者整个物件的变化属于这一类，直接改画面的状态，不进任务队列。

一个部门角色有一个任务队列。事件到达时，能归到任务目录某一行的，在该角色的队列尾部加入一个任务；角色空着的时候取队首的任务，走到 `spot`，从到达的时刻起做 `ms` 毫秒的 `pose`，做完取下一个。队列里最多留 3 个可以被挤掉的任务，超出时挤掉最早的；交接与传信的任务放在队首，不会被挤掉。整层静止（中断）时小人不出发，队列等着。

角色"现在该干什么"的持续状态（打字、等待模型服务的沙漏、待恢复的牌子、坐着喝茶……）取自快照，写在角色的 `rest` 上，形状与任务相同；没有任务在做时角色照 `rest` 摆放。因此静止的画面只由快照决定，事件只决定动作的起点。角色的自主性只体现在队列空的时候：快照是喝茶时，每隔 5 至 12 秒起身走到房间里的一个位置伸个懒腰再回工位；"这一步该做什么"永远来自队列里已经存在的任务，角色不会自己凭空生成一个任务。

v9 每个部门依然只有一个角色（跟 v8 一样，部门内多角色是 Stage 5 的数据，这一步不提前用）。一件事项经过的多个步骤（装配上下文、模型请求、工具调用、提交提案……）会让这一个角色依次走到文件柜、工位、终端、管道口。

交接由三部分组成：交出方的角色走到管道口把包裹放进去（一个任务），包裹沿管道移动，接收方的角色走到管道口取出（一个任务）；返工与回流走另一侧的管道口。包裹（PRD 卷轴、交付箱、放行单、信件）是世界里的实体：放进管道时生成，沿折线移动，到达终点后销毁并触发接收方的任务；同一时刻多个包裹各自的位置随时可以查，为将来同时存在多个在途包裹做好准备。大厅里排队的包裹仍由快照里的排队事项画出；v9 阶段一个项目仍然一次只处理一个事项，所以画面上看到的在途包裹数量跟 v8 一样。

## 5. 角色头顶的对话框

v8 design.md 第 8.3 节写了"模型请求中：打字，头顶思考气泡"与"流式输出：气泡中逐字出现文字"，v8 的项目楼层里，小人头顶只有一个 `think` 小图标，没有文字气泡。v9 把这一条补完并且推广到所有任务：

- **正在做**：角色做队列里的当前任务时，头顶出现说话气泡（实心尾巴），内容是这个任务的标签——普通任务用第 8.3 节"事实"这一列的简短说法（"翻找资料""执行登记命令"）；模型请求在流式输出到达时，第一段文字取代默认的标签，后面的文字接在后面，气泡里显示最新的十几个字，任务从最后一段文字起多留一会儿。气泡内容只来自这个任务本身的字段，任务是什么，气泡就说什么，没有第二个信息来源。
- **打算做**：队列里已经有下一个任务、而且这个任务带有可以说清楚的标签时，头顶出现思考气泡（圆点尾巴）；队列里没有下一个任务，或者下一个任务没有标签，不显示这种气泡，不能猜。
- 头顶已经有状态图标（沙漏、问号……）时，气泡画在图标上方；系统设置为减少动画时不画气泡。
- 两种气泡都不是新的事实来源：说话气泡的内容是"正在执行的任务"这个已经存在的状态的直接显示，思考气泡的内容是"队列里下一项"这个已经存在的数据的直接显示，跟画面其余部分同一条规则——只显示已经查到的事实。

## 6. 系统清单

- **任务派发**：事件到达时按第 4 节的规则转成任务或者信号；任务加入对应部门角色的队列。
- **移动与执行**：角色从当前位置走到任务的 `spot`，到达后播放 `pose` 并开始计时（v8 已有的走动补间逻辑复用，不重写）。
- **持续状态**：没有任务在做时，角色照快照写下的 `rest` 摆放；快照是喝茶时偶尔起身走动。
- **包裹**：沿管道的折线移动，到达终点后销毁并执行回调。
- **气泡**：第 5 节。
- **渲染**：把房间、管道、角色、包裹这些实体的当前组件状态画到画布上，复用 `engine.js` 已有的画布原语（`paint.*`、`P.drawBitmap`、`P.text` 等一律不改）；管道流动的亮点（`drawPipe` 里沿路径按时间间隔画点）在"快照里两端有活跃事项"或者"管道上有包裹在移动"时出现。

## 7. 分工

核心的实体、组件与系统骨架（第 3 至 6 节）、任务目录与派发规则、项目楼层画面（`floor.js`）、验收脚本由架构师完成；楼里的小人（`building.js`）交给 omp 完成（任务 B），细则见 [BUILD.md](BUILD.md)。

## 8. 验收

九档 × 现有页面 × 两种宽度与主题跑一遍，控制台错误为零，十九个场景全部能走完；项目楼层画面、楼与机房在静止时跟 v8 逐像素相同（房间位置、管道走向、小人外形与姿势都不变），由 [BUILD.md](BUILD.md) 第 4 节的脚本验证。差别只在事件进行中（角色走到具体位置、包裹沿管道移动、头顶出现对话框）和待机时偶尔起身走动。这一步要求的是"静止的画面跟 v8 相同，背后是一个在跑的队列"。
