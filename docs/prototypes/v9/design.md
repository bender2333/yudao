# 原型 v9：像素引擎改为实体—组件—系统结构

更新：2026-09-29。状态：设计，待用户审阅。

## 1. 范围

v9 只换掉 v8 的像素引擎内部结构（`js/pixel/floor.js`、`building.js` 里跟房间、管道、角色有关的部分，新增 `js/pixel/ecs.js`），不改其余东西：

- 屏幕清单、页面导航、系统页、决定卡片、资料页、观测页——[v8 design.md](../v8/design.md) 第 6、7、9、10 节原样保留，本说明不重复。
- 像素画风——配色、字体、贴图，[v8 design.md](../v8/design.md) 第 8.2 节的小人外形与配件原样保留。
- 部门房间画面——`js/pixel/room.js` 原样保留，`engine.js`、`sprites.js` 同样不改。
- 房间与管道的拓扑——大厅、产品、工程、质检、成果库、运维（Stage 4）、通往机房的门，跟 v8 design.md 第 5.2、5.3 节一样，一个部门一个角色，不新增部门。
- 事实到画面的对照表——第 5.4、8.3 节两张表——原样保留，v9 把它们当作任务与信号的目录来用，见第 4 节，不重新定义一遍事实与动作的对应关系。
- `Y8.api` 的查询、命令、事件形状不变；界面层与示例后端的边界不变。

会变的只是：房间与管道从写死坐标改成图结构声明（第 3 节）；域事件从直接触发一次动画改成生成任务或者信号，由角色自己的队列消化（第 4 节）；新增角色头顶的对话框（第 5 节）。

新增部门、创战纪式的画法、摄像机代替页面导航、外包角色的呈现、预测与说服，都不在这一版里，属于验证过这一步之后的下一步。

## 2. 现状与要换掉的地方

`floor.js` 现在的结构：

- `layoutFor(hasOps)`：按 `DEPTS = ['product', 'engineering', 'quality']` 这个写死的数组和 `x += 116` 这样的坐标算式，算出每个房间的位置；`pipesFor(lay)` 同样用字符串键（`'hall>product'`）一条条手写管道的折线。新增一个房间要改这两个函数的函数体。
- `primaryItem(d)`：一个部门只挑一件"当前最要紧"的事项，`syncWorkers()` 给每个部门建一个角色对象，角色的 `data.item` 就是这一件。一个部门同时只能有一个可见的角色状态。
- `restFor(a)`：对 `primaryItem` 返回的这一件事项的 `status` 字段做一次大的分支判断，直接返回一个姿势。状态没变时姿势也不会变；细一点的事实（`model_requested`、`tool_started` 这些）经 `playEvent` 的 `tempWorker` 在原地叠一个 2.4 秒的临时姿势和图标，时间到了退回 `restFor` 的姿势，角色不会真的走到文件柜或者终端那个位置。
- `playEvent(ev)`：对事件类型做一次大的分支判断，每种事件对应一次编排好的动画调用（`send`、`portTrip`、`flash`）。事件播完，画面状态由 `restFor` 重新接管，动画本身不留下任何状态。

这样做的结果：房间里的东西是"当前状态的一次性图解"，不是一个在跑的模拟；一个部门永远只有一个可见的角色，即使这件事项经过的步骤很多，也只在原地叠一层临时姿势，不会走动。

## 3. 房间与管道：图结构声明

每一层楼（v9 阶段还是固定的产品、工程、质检加大厅、成果库、运维、机房门）用一份声明描述，不再写坐标算式：

```
rooms = [
  { id: 'hall', label: '大厅', kind: 'hall' },
  { id: 'product', label: '产品', kind: 'dept', desks: 1 },
  { id: 'engineering', label: '工程', kind: 'dept', desks: 1 },
  { id: 'quality', label: '质检', kind: 'dept', desks: 1 },
  { id: 'library', label: '成果库', kind: 'shelf' },
  { id: 'operations', label: '运维', kind: 'dept', desks: 1, optional: true }
]
links = [
  { from: 'hall', to: 'product', kind: 'handoff' },
  { from: 'product', to: 'engineering', kind: 'handoff' },
  { from: 'engineering', to: 'quality', kind: 'handoff' },
  { from: 'quality', to: 'library', kind: 'handoff' },
  { from: 'quality', to: 'product', kind: 'return' },
  { from: 'product', to: 'engineering', kind: 'tube' },
  { from: 'engineering', to: 'quality', kind: 'tube' },
  { from: 'product', to: 'quality', kind: 'tube' },
  { from: 'library', to: 'operations', kind: 'handoff', optional: true },
  { from: 'operations', to: 'machine_room', kind: 'handoff', optional: true },
  { from: 'operations', to: 'hall', kind: 'return', optional: true }
]
```

一个通用的排布函数把这份声明变成位置：房间按声明顺序从左到右排开，宽度按 `desks` 数量与固定的每工位宽度算出（v9 每个房间只有一个工位，跟 v8 的宽度一样，画面看起来不变）；每条 `link` 的折线由起点房间的出口、终点房间的入口和 `kind` 对应的路由规则（`handoff`/`tube` 走 `PIPE_Y`/`TUBE_Y` 那条水平线，`return` 走天花板的回流线）算出，不再要求每条管道单独手写坐标。`optional: true` 的房间与管道在 `hasOps` 为假时整体跳过。

这份声明现在描述的房间和管道，跟 v8 现在画出来的完全一样，这一步要验证的是"排布是不是能从声明生成"，不是"能不能加新东西看起来不一样"——加一个部门、看排布是否还成立，是第二步的事。

## 4. 事件变成任务或者信号

一个域事件落到两类里的一类，判断依据是"这件事要不要有人去做"：

- **任务**：需要某个角色走到某个位置、做一个动作。[v8 design.md 第 8.3 节](../v8/design.md)那张"事实、来源、小人动作、房间变化"的表，原样作为任务目录：表里的每一行是一种任务定义（`{fact, sourceEvent, pose, spot, roomEffect}`），`spot` 是这个任务要在房间里的哪个位置完成（工位、文件柜、终端、管道口、试用台……），跟现在 `restFor` 只给姿势不给位置比，这是新增的一个字段，值从表里"小人动作"那一列的描述直接对应（"翻文件柜"→文件柜位置，"走到终端拉下拉杆"→终端位置）。
- **信号**：不需要角色去做什么，只是画面上的一个指示变化——管道通不通、时钟走不走、门缝亮不亮灯、看板上的一个数字。[v8 design.md 第 5.4 节](../v8/design.md)那张表里"循环次数与时间""待恢复""等待执行槽位"这类整层或者整个物件的变化属于这一类，直接改组件的值，不进任务队列。

一个部门有一个任务队列。事件到达时，能归到第 8.3 节某一行的，在该部门队列尾部加入一个任务；角色空着的时候从队尾取下一个任务，走到 `spot`，播 `pose`，应用 `roomEffect`，做完取下一个。角色的自主性只体现在"队列空的时候做什么"（第 5.4 节第一行已经写明：坐在工位喝茶，偶尔起身在房间里走动、伸懒腰）和"两个任务之间怎么走过去"，不体现在"这一步该做什么"——那永远来自队列里已经存在的任务，不会自己凭空生成一个任务。

v9 每个部门依然只有一个角色（跟 v8 一样，部门内多角色是 Stage 5 的数据，这一步不提前用）。真正会变的是：一件事项经过的多个步骤（装配上下文、模型请求、工具调用、提交提案……）现在会让这一个角色依次走到文件柜、工位、终端、提案托盘，不再是原地叠一层 2.4 秒的图标后弹回一个粗粒度的姿势；队列空的时候是真的在房间里走动，不是固定摆一个喝茶的姿势。

包裹（PRD 卷轴、交付箱、放行单、信件）改成持久的实体：创建时生成，携带 `department`（当前所在，随交接移动更新）、`atRest`（是否正停在某个工位/管道口，还是正沿某条管道移动）、`pathProgress`，被采纳或者归档时销毁。现在的 `st.movers` 是一次性补间数组，画完丢弃，改成持久实体后同一时刻多个包裹各自的位置随时可以查，为将来同时存在多个在途包裹做好准备，v9 阶段一个项目仍然一次只处理一个事项，所以画面上看到的在途包裹数量跟现在一样。

## 5. 角色头顶的对话框

v8 design.md 第 8.3 节已经写了"模型请求中：打字，头顶思考气泡"与"流式输出：气泡中逐字出现文字"，但没有真正实现——现在 `model_requested`/`model_stream_progress` 只落到 `playEvent` 里 `tempWorker` 的一个 `think` 小图标，没有文字气泡。v9 把这一条补完并且推广到所有任务：

- **正在做**：角色执行队列里当前这个任务时，头顶出现说话气泡（实心尾巴），内容是这个任务的标签——普通任务用第 8.3 节"事实"这一列的简短说法（"翻找资料""执行登记命令"），模型请求类任务在流式输出到达时逐字追加，这正是 8.3 节原本要的效果。气泡内容只来自这个任务本身的字段，任务是什么，气泡就说什么，没有第二个信息来源。
- **打算做**：角色头顶出现思考气泡（圆点尾巴），只在队列里已经有下一个任务、而且这个任务已经带有可以说清楚的内容时出现（比如已经排好的重试时间、已经分派下来的下一步）；队列里没有下一个任务，或者下一个任务的内容还没确定，不显示这种气泡，不能猜。
- 两种气泡都不是新的事实来源：说话气泡的内容是"正在执行的任务"这个已经存在的状态的直接显示，思考气泡的内容是"队列里下一项"这个已经存在的数据的直接显示，跟画面其余部分同一条规则——只显示已经查到的事实。

## 6. 系统清单

- **任务派发**：把到达的事件按第 4 节的规则转成任务或者信号，任务加入对应部门的队列。
- **移动与执行**：角色从当前位置走到任务的 `spot`，到达后播放 `pose`（v8 已有的走动补间逻辑复用，不重写）。
- **待机**：队列空时的行为，来自第 5.4 节第一行的既有定义。
- **气泡**：第 5 节。
- **渲染**：把房间、管道、角色、包裹这些实体的当前组件状态画到画布上，复用 `engine.js` 已有的画布原语（`paint.*`、`P.drawBitmap`、`P.text` 等一律不改）；管道流动的画法（`drawPipe` 里沿路径按时间间隔画亮点）不变，只是数据来源从"这条管道的两端有没有活跃事项"这一个布尔值，改成"这条管道上有没有正在移动的包裹实体"。

## 7. 分工

核心的实体、组件与系统骨架（第 3 至 6 节）、房间与管道的排布函数、任务派发规则由架构师写；把 v8 现有的第 8.3、5.4 节两张表逐行转成 v9 的任务/信号定义（`spot` 字段需要为每一行补齐，其余字段从原表照抄），以及用新结构让 v8 现有的十九个场景在项目楼层与楼里的画面上照常播完，交给 omp 按 [BUILD.md](BUILD.md) 完成：任务 F 项目楼层，任务 B 楼与机房。

## 8. 验收

九档 × 现有页面 × 三种宽度与主题跑一遍，控制台错误为零，十九个场景全部能走完，画面看起来跟 v8 现在的截图基本一致（房间位置、管道走向、小人外形都不变）；差别只在角色现在会走到具体工位而不是原地切换姿势、队列空时真的在走动、头顶出现对话框。这一步不要求"看起来比 v8 惊艳"，要求的是"同样的截图，背后是一个在跑的队列，不是一次性动画"。
