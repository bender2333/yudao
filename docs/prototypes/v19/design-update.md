# V19 页面结构设计提案

总图位置：第一节「轮转方式」「下一个部门」「运维」「独立的证据」，第二节「定义」与四层，第三节「子组织」「增量与整份」。依据：[项目的组织设计说明](../../design/project-organization.md)、[形态与核验角色设计说明](../../design/forms-and-verifier-role.md)、[部门内多角色设计说明](../../design/department-roles.md)、[术语表](../../../CONTEXT.md)。

## 设计目标

单个角色的用户进入项目就能交代事情、回答问题和查看结果。多个角色的用户能理解当前采用的协作方式、各方的职责、核验关系，以及下一步需要自己处理什么。部门数量可以变化，包含运维与用户增加的部门。

本文记录供页面原型采用的结构提案。现有 V19 的可用范围、发布目录与正式设计说明按各自的当前内容执行；本文的任务池与运维场景用于说明完整的页面安排，其发布可用性需要在原型中标明。

## 组织中的几个维度

| 维度 | 内容 | 页面位置 |
| --- | --- | --- |
| 协作方式 | 直做、按成果、任务池；决定谁开工、怎样交接与结束 | 组织摘要中用一句话说明，修改时随组织模板或组织草稿采用 |
| 部门与角色 | 当前有哪些部门、角色，各自负责什么 | 组织成员列表，按职责分组；部门数量从定义读取 |
| 由谁执行 | 自有角色、外包角色、内部子组织 | 对应角色的详情 |
| 核验安排 | 谁核验谁的哪份成果，事项最后采纳什么成果 | 组织摘要中的完成条件，以及相关角色之间的核验关系 |
| 观察者 | 在事项外读取事实并提出证据、提案或振荡信号 | 设置中的开关，读取范围在高级配置 |

模板把这些维度组合成可直接使用的一份组织。新建项目仍然只要求项目名字与一张模板卡，起始文件夹可选。用户需要改动模板时，再进入对应配置。

「一个角色」「几个角色」描述参与者规模；「三部门」是产品、工程、质检的一份预设组织；「中心型小组」描述一个角色内部的子组织。页面分别表达这些信息。

## 工作页面

### 单个角色

项目打开就是对话。头部保留项目名字、设置入口与查看交付的入口；运行状态、已用时间与上限合在一行，运行期间提供停止按钮。

对话按事项分组。当前事项展开，已结束事项默认显示要求摘要、结果与「看这一版」，可以展开完整对话。进行中的细节与工具记录折叠，等待用户回答的问题直接显示。

输入框紧邻一行紧凑的发送用途选择：「指导工程」「开始新事项」。选中的用途及发送后果始终可见；存在进行中的事项时，新事项明确写出排队关系。用户明确选中的指导对象在连续发送时保持不变；发送新事项或追加输入后，回到当前状态决定的默认用途。

设置默认显示名字、文件夹、实际生效模型与当前组织；长期目标按需展开。模型一行同时写明跟随来源。增加核验角色与调整组织从当前组织一行进入。

### 几个角色直做

沿用对话与输入区，在宽屏对话旁常驻协作状态，窄屏放在对话上方。部门列表直接显示名字、当前状态、正在处理的工作与协作关系。直做模式说明谁主执行、其他角色怎样按需协助，不把询问关系排成串行阶段。

点选部门留在工作页，查看当前工作、等待原因、需要回答的问题及内部小组状态，同时将输入框切换为指导该部门。「查看往来」展开同一线程内最近的相关记录；「配置」作为次级入口。运行进度更新时保留输入草稿、用户选中的部门和面板滚动位置。

输入区只显示一个指导对象、开始新事项，以及适用时的追加输入。提示写明指导属于当前事项还是部门，并显示下轮读取的后果。指导记录关联目标部门及适用事项；示例工作进入相应部门时显示读取状态。

组织摘要说明谁接输入、谁主要执行、其他角色怎样协助、谁交完成，以及是否需要核验。需要独立核验时，写明核验者和被核验的成果。

### 按成果协作

常驻协作状态显示输入接收方、完成条件、每个部门的实际状态及成果去向。每个部门的成果关系写在对应行，例如「交付 → 质检、运维」「缺陷记录 → 工程」，并说明核验对象与打回后的返工去向。关系由产出、关注、核验与事项来源生成，支持循环和并行部门。

状态明确区分当前事项、其他事项与运行环境；同一时间有多方工作时分别列出。结束一个事项时保留其他事项仍在进行的部门状态。进行中的事项展示开始时冻结的组织，组织已更新时显示说明。

组织页以成果关系说明协作：谁产出什么、哪些部门关注它、谁核验、事项如何结束。产品、工程、质检可以作为预设示例；增加运维或其他部门后，列表和关系随定义变化。

### 任务池

主页面保留对话与常驻部门状态，协作区内显示工作单元摘要：待认领、依赖阻塞、进行中、等待核验与已完成各有多少。点开摘要查看工作单元列表、依赖关系、认领者与打回原因。角色认领、交回或单元通过时，部门状态同步更新，并分别标明待单元核验与待整份核验。

组织配置展示工作单元的大小、认领资格与核验安排。有核验角色时，页面同时区分单元核验与整份交付的核验；若事项以放行结束，单元全部通过后仍需整份交付的核验结论。

任务池在发布目录尚未可用时，入口注明「设计预览」，配置操作属于原型演示。

## 配置入口与层级

多个角色的项目统一使用「对话」「成果库」「组织」三个主要入口，项目设置从项目名字旁进入。角色与部门详情由组织列表打开，页面保留项目与所在组织的路径。

组织页先显示当前安排的一段说明及成员列表。说明覆盖输入交给谁、怎样协作、怎样核验与结束；列表默认只显示名字、职责、当前状态和执行方式。

用户选择「调整组织」后，按当前协作方式显示相关字段：

| 协作方式 | 需要调整的关系 |
| --- | --- |
| 直做 | 各种来源由谁接、谁主要执行、谁交完成、谁核验完成成果 |
| 按成果 | 成果种类、谁产出、谁关注、谁核验、事项最后采纳什么 |
| 任务池 | 工作单元、依赖、认领资格、单元核验与事项结束条件 |

角色详情分为职责、执行方式、模型与 Prompt、工具与写入范围。每组只在进入详情后展开；默认值注明跟随来源，项目覆盖值提供恢复入口。

组织修改保留草稿、校验、差异、采用与历史。草稿状态及拒绝原因只在调整组织期间出现。确认采用前展示完整差异与结束条件的变化，说明只影响之后新建的事项。

进入高级配置时保持项目导航与所在位置，关闭后回到原来的页面和滚动位置。当前配置各自标明生效时间：组织影响新建事项；模型与 Prompt 影响下一次模型请求；授权、位置和工具遵循对应合同。

## 中心型小组

在具体角色的「由谁执行」中选择内部子组织，再选择发布提供的内部组织。中心角色、探索者、主程、审查者的分工和协作规则由所选定义给出。

外层显示这个角色正在处理的工作、内部小组标记与需要上交的结果。点选部门即可查看内部角色的当前状态；「查看内部工作」原地打开当前工作记录。内部组织和示例线程仍从角色配置进入，路径例如「组织 › 工程 › 内部」。上层与内部各自显示核验安排，内部完成后将结果作为外层角色的提案返回。

时间和用量显示从上一层剩余范围中分配的关系。达到嵌套深度上限时，执行方式选择写明原因。核验角色的执行方式保留现有外包限制。

## 运维与更多部门

「添加部门」位于组织成员列表末尾。选发布提供的部门声明或填写自定义部门；按既有定义合同填写目标、判断依据、工作方法、成果关系与权限，再过同一套组织校验。

运维场景同时呈现运行软件的状态与故障产生的修复事项。常驻运维行显示环境健康与部署版本，其成果去向说明故障交给哪个部门；开发部门继续各自显示当前工作。点选运维即可指导；运行环境与部署从协作区的次级入口打开。

运维发现故障后，通过定义中的事项来源及接收方创建修复事项，页面说明故障来源与优先顺序。修复的部门协作按项目定义进行；需要质检放行的交付由质检核验，后续部署状态单独记录。

组织摘要分别说明开发事项怎样完成、交付是否独立核验、运行环境是否部署及当前部署版本。运维角色的出现不自动增加串行阶段，也不自动建立核验关系。

运维详情集中展示登记的运行环境、常设授权范围、部署版本、健康情况与故障记录。清单以外的动作通过决定请求交给用户。运行环境授权与部门定义修改各走自己的操作，新增部门不会自动扩大机器授权。

发布目录没有提供运维形态或故障来源时，原型以「设计预览」注明完整场景；正式项目仍以当前发布提供的能力为准。

## 原型走查场景

| 场景 | 需要验证的结果 |
| --- | --- |
| 单个角色修改个人博客 | 打开后能直接输入；当前事项、等待回答的问题和交付容易找到；能够区分指导与新事项 |
| 几个角色制作报名表单 | 工程与产品的职责清楚；角色往来折叠；可以找到各角色实际生效的模型 |
| 直做增加核验角色 | 明确改变了完成条件；新事项等待核验，在跑的事项保留原组织 |
| 按成果协作 | 能看懂当前工作、等待的成果与返工去向，部门数量变化后仍能阅读 |
| 任务池 | 能找到待认领与阻塞的工作单元，区分单元完成与整份交付放行 |
| 工程内部使用中心型小组 | 能进入内部线程、定位内部角色并返回外层，分别理解内外核验结论 |
| 增加运维 | 能区分故障、修复事项、已放行交付和部署状态，找到运行环境与授权范围 |
| 增加自定义部门 | 完成职责与协作关系配置，能看到校验结果和采用后变化；导航随成员增加保持清楚 |
| 进入与关闭高级配置 | 项目导航保持一致，能够回到原页面与位置 |
