本文件只写跟 [v11 design.md](../v11/design.md) 不一样的地方，其余照旧：v12 沿用 v11，v11 沿用 [v10](../v10/design.md)，v10 沿用 [v9](../v9/design.md)，v9 沿用 [v8](../v8/design.md)。构建约定见 [BUILD.md](BUILD.md)。用词以 [CONTEXT.md](../../../CONTEXT.md) 为准。

## 1. 本版处理的范围

v12 做两件事：补上之前整理出来的遗漏点（表中 A 开头的行），体现 2026-10-12 以来的设计变化里用户看得到的部分（B 开头的行）。

遗漏点的来源有四处：[原型变更记录](../CHANGELOG.md)开头「下一版原型的待办」四条；v9 至 v11 的设计说明里写明不实现或留给下一版的地方；[架构问题记录](../../architecture-issues.md)与开放工单里涉及原型的条目；`docs/design/`、`docs/requirements/` 写了用户看到的内容而 v11 没有对应画面的地方。设计变化的来源是 [决策记录](../../decision.md) 2026-10-21 以后的条目、ADR-0036 至 ADR-0042（ADR-0041 暂缓，仓库里没有这份文件）、[骨架与应用](../../design/skeleton-and-application.md)、[三部门的循环结构](../../design/department-loop.md)、[循环与收敛](../../design/loops-and-convergence.md)、[恢复契约与故障矩阵](../../design/recovery-contract-and-fault-matrix.md)。

做与不做按下面四条判断：

1. 待办四条照做；其中说法已经过时的部分按 [ADR-0038](../../adr/0038-function-first-commands-without-registration.md) 与现在的设计说明改写（见 A7）。
2. 最新设计里用户看得到的变化照做；骨架内部（内核、契约、测试）没有界面表现的不画。
3. 已经放出或排在 M0 至 M2 的工单要用到、原型又缺的画面照做，设计说明写明了内容的才做。
4. 其余的遗漏点不在这一版：属于 Stage 4 以后或者与本版两类来源都不相干的页面，或者设计说明自己写明不需要原型；设计说明不清楚、要靠编造才能画的，记在第 5 节「未做与未决」。

任务池的规格还没有定（地图 #836 已关闭，规格留到评测时），本版不为它设计画面。

## 2. 遗漏点的画法

### 2.1 命令与取回不经登记（A1、A2、B13）

- 动作与回执：命令的动作写命令原文，工具是 `bash`；回执写「命令」一项，去掉「登记名」与参数列表。文件工具、网络取回与 MCP 调用的回执写「目标」；取回与 MCP 调用另写「外部来源工件」（工件标识），不写快照。示例数据的待办清单里加了一条 MCP 调用（工程用 GitHub 官方 MCP 服务的 `search_code`），与 MDN 的取回一起放在「动作与回执」里。
- 网络取回可以取回任何 http 与 https 地址：示例数据里等待批准的 MDN 取回改为已取回，决定卡片「授权网络取回与 MCP 工具」删除。
- 结果未知的调用交还给模型的内容写在恢复页（第 2.3 节），动作行只写「结果未知」的状态。
- 房间与楼层里小人说的话写命令原文，例如「现在执行 python -m pyt…」；终端的动作照旧是走到终端拉下拉杆。

### 2.2 设置页与工具页（A3、A5、A6、A10）

- 设置页删除「登记命令」「工具授权」两节；机器授权只写登记的目录（Stage 4 起另有运行环境与常设授权）；执行位置只有本机进程与授权的机器，删除「本机容器」与「容器基础镜像」。
- 工具与扩展页是只读汇总：网络取回只列最近的取回记录；MCP 按项目列服务器、连接方式、可以使用的部门、最近一次状态与工具，每台服务器带「在项目设置中修改」的链接；删除各项目的授权表、「恢复约定」「重试」两列、准入钩子与「设计待定」提示。浏览器、computer use 与只读观察者照旧，工具表改为「工具、说明」两列。

### 2.3 恢复页（A7、A8、A9、B9、B10、B12）

- 恢复观察状态七种：运行中、中断、待恢复、已完成、已暂停、已取消、已停止。删除「待核实」与「已终止」；示例数据里的 `terminated` 按真实情形改为已完成或已停止。结束的四种在「原因」一节写结束方式、停止原因、最后已确认的位置与所在部门。
- 「动作核实」改为只读的「结果未知的动作」：每条写处理方式（核实确认、交还会话、等待机器恢复以后核实）、发出它的会话、执行的机器、输入依据、执行前后、依据与核实的结果；交还会话的一条另写交还的工具结果原文（「执行被中断，结果未知。已经收到的输出……」）。没有用户的决定，「决定请求」一节写明结果未知的动作不在这里。首页状态项「结果未知的动作」删除。
- 等待机器：机器离线时事项待恢复，恢复页的原因一节写「等待机器」、机器名、问题、开始等待的时间与已经等待的时长，说明恢复在线以后按尝试身份核实、等待时长上限 24 小时；概览、看板卡片、楼层门口的牌子与左侧栏的项目标记都写「等待机器」（楼层门口写「等待机器：笔记本」）。
- 限额按会话写：事项合计（已用时间、工作轮数、模型步数、重试）之外，列出每个会话（部门主线、询问分支）的已用时间、工作轮数与模型步数。「激活」一词按 CONTEXT 改为「一轮工作」：恢复页、观测页与首页的循环层写「一轮工作」，循环实例写「工程 · 第 2 轮工作」。
- 因升级停止写「重新开始的起点」：采纳成果；没有时是起始文件夹快照，都没有时是空树。运行页排空一节写明排空在服务下一次启动时结束，强制升级同样写起点。

## 3. 设计变化的画法

### 3.1 三个部门同时工作（B1）

- 状态四种：工作中、等待工作、回答询问、等待用户。概览「当前事项」写三个部门各自的状态与原因（例如「质检 工作中（预测性探索：按 PRD r1 起草测试用例）」）；部门工作间标题区在状态旁写原因，另起一行列出三个部门，本部门加粗；看板卡片写正在工作的部门（「工程、质检在工作」）。
- 楼层：事项停在某个房间，别的部门同时在工作中或回答询问时，那个房间同样亮灯、屏幕滚动、小人坐在桌前工作；包裹与门口的小旗只在事项所在的房间。首页楼里的灯同理。
- 示例：场景 1 中 PRD 被接纳以后，工程开始实现，质检同时开始预测性探索；场景 3 中质检的预测性探索与工程同时进行。

### 3.2 进度按成果写（B2）

概览「当前事项」写「PRD r2 · 交付 r1（依据 PRD r2）· 结论：放行」；还没有交付时写「还没有交付」。不写阶段名称；观测页「运行限制」里事项名下的小字改为事项状态。资料页旧 run 写结束方式，不写阶段。场景 1 补上 PRD r1、PRD r2、交付 r1 与质检结论 r1 四份资料。

### 3.3 询问（B3）

- 示例数据把协作请求改为询问：`asks` 记提问方、被询问的部门、上一层询问（回问时有）、问题、状态、回答、附带的 PRD 版本；事件是 `ask_started` 与 `ask_answered`；查询 `run.asks` 给出询问链与层数。
- 概览「当前事项」列出这个事项的询问：状态、询问链（例如「工程 → 产品 → 工程」）、回问标记、问题与回答，产品的回答附带 PRD 新版本时写「附带 PRD r2」。部门工作间在「询问、部门消息与指导」一节列出本部门发出与收到的询问，房间信息写「传信管：N 封询问等待本部门回答」。
- 等待原因：提问方仍是工作中，原因写「在等待产品的回答」；被询问的部门写「回答询问」，原因写「回答工程的询问」。
- 流转记录的种类改为用户输入、PRD、交付、缺陷记录、询问、回答、放行、采纳（3.8 另有结构说明与基线核验）；没有「需求交接」「咨询」「返工」。
- 场景 3 改写：工程询问产品，产品回问工程，工程在询问分支里回答，产品的回答附带 PRD r2；质检开始预测性探索，询问工程两次，最后一封停在工程的传信管出口。

### 3.4 指导（B4）

指导只有三种状态：已接收、已进入模型输入、已回答。部门工作间的说明改为「部门正在工作时，指导在它的下一步作为通知加入；部门在等待工作时，以这段指导开始一轮工作」。场景 4 最后一步改为工程回答指导，没有更新计划这一步。

### 3.5 计划、结论与交付（B5、B6、B14）

- 资料页删除 PLAN 一节与索引里的 PLAN 计数；示例数据删除计划资料、计划接纳的事件与部门 Prompt 里的计划；动作图鉴删除「计划贴上白板」。Stage 5 部门内的「计划条目」（部门账本）保留，见第 5 节。
- 质检的结论写「放行」与「缺陷记录」；流转记录、时间轴的关键事实与资料页里「返工」「退回工程」改为「缺陷记录」。像素画面里检验台上的红色单子仍写「返工」，见第 6 节。
- 资料页交付一项写明「文件清单由主机从交付快照得出，不取自交付说明」。

### 3.6 画面由成果事件驱动（B7）

示例数据里没有 `transition` 与协作请求的事件。界面层（`js/ui/scenes.js` 的 `pixelEvents`）按一张对照表把事件交给像素画面，像素代码继续读 v11 的词汇：

| 事件 | 交给画面 |
| --- | --- |
| `spec_accepted`、`contract_accepted` | 原事件，另加一次包裹从产品送往工程（PRD 卷轴） |
| `delivery_accepted`、`structure_accepted` | 原事件，另加一次包裹从工程送往质检（交付箱） |
| `qa_submitted`（缺陷记录） | 原事件，另加一次包裹从质检经回流管道送回工程 |
| `qa_submitted`（放行） | 原事件，另加一次包裹送往成果库；载荷写明 `release_to` 时送往那个部门（运维接手放行的修复） |
| `ask_started` | 传信：提问方塞信，信沿传信管到被询问的部门 |
| `ask_answered` | 回信，并关闭这次询问（提问方不再在管口等待） |
| 其余 | 原样 |

PRD 被接纳时质检也收到通知，画面只画送往工程的一次，质检房间按第 3.1 节亮灯。

## 6. 有意的静止画面差异

楼层回放（`checks/replay.js`）与楼、机房的逐像素比较（`checks/identity-building.js`）喂给两版相同的调用或数据，只比较画法。v12 改了画法的地方只在下面几处，都只在 v9 录制里不会出现的数据或事件上起作用：

1. 项目楼层与首页的楼：快照里事项带 `departments`、另一个部门在工作中或回答询问时，那个房间亮灯、屏幕滚动、小人坐在桌前打字（第 3.1 节）。v9 的快照没有这个字段，画面不变。
2. 小人说的话：工具是 `bash` 时按命令原文说；命令没有名字时说「现在执行命令」（v11 说「现在执行登记命令」）；楼层任务的标签「执行登记命令」改为「执行命令」，只在没有说话内容时显示。
3. 楼层大厅板上的决定单：新的三种决定按第 2.4 节着色。

示例数据变了，所以按数据画出的静止画面（例如待办清单的质检房间不再停在等待批准，换乘站在 3.2C 起门口写「等待机器：笔记本」）与 v11 不同，这些属于数据的变化，不是画法的变化。

## 7. 与客户端的关系

客户端（`client/`）已经按设计说明做了其中一部分：成果写回一节（`WritebackSection`）、恢复页、源目录的写回设置等。v12 的画面以设计说明为准，与客户端现状不同的地方由界面工单按设计说明处理，原型不追客户端。
