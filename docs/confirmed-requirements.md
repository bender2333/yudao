## 产品目标

三部门共同构成 Yudao 的 Agent loop。核心目的是掌握上下文的选择粒度、组装时机和内容，使后续任务、部门 prompt、产品要求和经验可以在明确边界内演化。

OMP 仅作代码级参考，例如 provider 层封装、流式响应和工具协议处理；Yudao 不依赖 OMP 的进程、会话或完整 Agent loop。

## 材料与职责关系

| 材料 | 谁提供或维护 | 用途 |
| --- | --- | --- |
| `intend.md` | 用户输入，由系统忠实保存 | 保留原始命令、目标和资料，供回查用户实际表达 |
| `PRD.md` | 产品部门 | 保存转换和维护后的有效需求，解释目标、范围与验收 |
| 研发任务分解与计划 | 研发部门 | 把产品要求转成实施步骤，在实施之前形成 |
| 交付与检查证据 | 研发、质检及宿主检查工具 | 证明实际产出及其是否符合要求 |
| 三部门 prompt | 用户可查看和修改，由系统保存使用记录 | 规定各部门处理信息和开展工作的方式 |

`intend.md` 和 `PRD.md` 承担不同职责。需求更新时不反向改写原始输入；研发的计划也不能自行改变产品要求。prompt 修改通过运行时生效，不绕过代码中规定的工具权限、合同校验或最终放行条件。

## 三部门专家协作

Ask/React 是三部门之间的专家问答能力。部门之间可以根据问题所需的专业判断互相提问，不把请求方向固定为研发到产品。

- 研发可以向产品澄清目标、范围和取舍。
- 质检/验收可以随时要求产品重新解释要求或验收含义，不必先判定交付有缺陷才能澄清。
- 产品可以向研发了解实现难度、技术约束与成本，也可以向验收了解可验证性、验收成本与风险，取得依据后维护需求。
- 同一部门既可以是提问者，也可以是回答者。跨部门传递有来源的问题、必要背景和回答，不共享完整私有对话。

专家回答与责任决定分别记录。研发提供成本判断不等于批准产品范围变更；验收提供解释或建议不等于放行交付；产品取得咨询意见后仍负责需求取舍。一次咨询回答不必产生新 PRD，实际改变要求时才更新有效需求及其影响。

请求需能追踪由谁提出、向谁提出、依据什么材料、等待什么回答，以及回答后由谁继续工作。本轮采用单一未结请求、有界接续，支持回答、拒绝、取消、超时与版本失效，不嵌套咨询或共享私有聊天。

## 已确认的运行中输入规则

用户已选择：当前工具完成后，在下一次模型调用前由产品部门处理新输入。停止/取消命令仍立即处理。

新输入需要先保存和确认接收。已开始的工具允许完成；随后产品依据新增原文维护需求，再决定后续工作。不能继续使用已经失效的要求驱动研发。若当前模型响应包含多个工具请求，输入到达后的边界以已启动工具完成为准，不能把整个工具队列当成必须执行完的一个工具。

## 本轮明确的交互细节

- prompt 默认修改当前任务，在目标部门下一次激活生效；已发请求不追溯变更，首批不建设全局默认编辑。
- intend 原文依顺序直接拼接，各次字节范围、时间与状态单独记录，原文工件逐条可复原；首批仅支持文本，未支持附件明确报错。
- PRD 与结构化合同同一次接纳生成，包含有效补充决定；草稿不推进执行。变更核对计划、请求、交付、检查和摘要适用性。
- 研发事前计划保存为受控工件及 PLAN.md，普通计划自动接续，调整说明原因；重要需求取舍回产品。
- Web 文本新建或补充任务，`/stop`、`/cancel` 立即取消；终态后明确新建任务。
- 专家请求一次一个，不嵌套，回答或拒绝后回到适用原工作；取消、超时与版本变化保留明确结果。

以上为本轮依据已有授权确定的设计选择，不冒称用户此前逐项明确过。
