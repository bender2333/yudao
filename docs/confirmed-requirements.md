# 已确认需求与实施清单

本文记录用户已经确定的产品目标、需要实现的能力及其状态。设计建议和待决细节单列，不作为已经确认的需求。更新日期：2026-09-06。

## 产品目标

三部门共同构成 Yudao 的 Agent loop。核心目的是掌握上下文的选择粒度、组装时机和内容，使后续任务、部门 prompt、产品要求和经验可以在明确边界内演化。

OMP 仅作代码级参考，例如 provider 层封装、流式响应和工具协议处理；Yudao 不依赖 OMP 的进程、会话或完整 Agent loop。

## 本次新增需求的用户原话

> 现在添加一些细节，请把确定好的需要实现的都记下来。
> 现在先使用web启动，web输入任务和命令，像TUI一样，随时都能再次输入。 三部门的prompt可以隐藏或者展示，也能修改。用户原始的命令和资料作为intend.md，不用任何修改，原文存储。产品部门负责进行转换和需求维护，最终版本记录到PRD.md中。研发部门需要先进行任务分解和计划，再去实现。

## 材料与职责关系

| 材料 | 谁提供或维护 | 用途 |
| --- | --- | --- |
| `intend.md` | 用户输入，由系统忠实保存 | 保留原始命令、目标和资料，供回查用户实际表达 |
| `PRD.md` | 产品部门 | 保存转换和维护后的有效需求，解释目标、范围与验收 |
| 研发任务分解与计划 | 研发部门 | 把产品要求转成实施步骤，在实施之前形成 |
| 交付与检查证据 | 研发、质检及宿主检查工具 | 证明实际产出及其是否符合要求 |
| 三部门 prompt | 用户可查看和修改，由系统保存使用记录 | 规定各部门处理信息和开展工作的方式 |

`intend.md` 和 `PRD.md` 承担不同职责。需求更新时不反向改写原始输入；研发的计划也不能自行改变产品要求。prompt 修改通过运行时生效，不绕过代码中规定的工具权限、合同校验或最终放行条件。

## 已确认的运行中输入规则

用户已选择：当前工具完成后，在下一次模型调用前由产品部门处理新输入。停止/取消命令仍立即处理。

新输入需要先保存和确认接收。已开始的工具允许完成；随后产品依据新增原文维护需求，再决定后续工作。不能继续使用已经失效的要求驱动研发。若当前模型响应包含多个工具请求，输入到达后的边界以已启动工具完成为准，不能把整个工具队列当成必须执行完的一个工具。

## 待确定的交互细节

- 修改 prompt 对当前激活和后续激活的生效时机，以及修改作用于当前任务还是默认部门设置。
- 连续输入在 `intend.md` 中的分隔方式；命令状态、时间等系统记录独立于用户原文。非文字资料的引用和原文件保存方式尚待明确。
- `PRD.md` 草稿、有效版本与运行时结构化合同怎样对应，修改要求时如何处理在途计划和旧交付。
- 研发计划的保存位置、更新方式及是否需要用户确认；用户尚未要求每份计划都等待人工批准。
- “命令”的首批集合及与普通任务文本的区分方式；不预设完整终端或任意 shell 执行。

## 当前实施安排

当前进行 [原生循环重构](native-loop-design.md)，先验证每次模型调用的上下文所有权，并保持现有交接、证据、停止和 Web 能力。上述新增需求形成后续明确工作包，不能因底层重构通过便标记为已经实现。

新增工作围绕一条完整流程展开：Web 原文输入 -> 原文保存 -> 产品维护 PRD -> 研发形成计划 -> 实施与质检 -> 用户再次输入 -> 产品调整需求与后续工作。运行中输入边界已经确定；prompt 修改的生效边界等剩余细节仍需明确。

后续阶段的长期记忆、知识图谱、暂停恢复、运维与新部门不因本次输入自动进入当前实施范围。每个可验证的小功能完成后提交和推送，并更新本清单的状态及对应验收证据。
