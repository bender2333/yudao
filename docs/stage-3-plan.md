## 1. 最近一次完整交付是什么

用户能把一个可信的小型代码项目接入 Yudao，让工程用搜索、阅读、编辑和本地命令完成变更，质检对确定的交付快照独立核验。运行进程意外退出后，用户能看到中断位置和待核实动作，继续同一任务而不重复已确认的交付与采纳。

这一能力通过后，才增加多个隔离工作区的并行执行。网络/MCP、其他订阅与扩展接口是本阶段的后续包；语义系统、部门内多角色与技能属于 Stage 4，运维属于 Stage 5 的运维部门。Go 所需三协议已前移到 2.7，调用与未来恢复必须复用 [统一 Provider 模块](design/provider-layer.md)。

## 2. 三层责任

| 层 | 新增责任 | 保持的边界 |
| --- | --- | --- |
| 用户与观察 | 展示命令执行、待恢复、动作核实、继续失败的原因；后续显示排队和执行槽位 | Web / CLI / HTTP 共用一个业务入口；replay 和 SSE 不恢复执行 |
| 业务引擎 | 工具准入、恢复协调、执行所有权、项目调度 | run 决定合同与 QA，项目决定采纳；恢复不替模型判断任务已完成 |
| 基础能力 | 搜索/编辑/进程工具、动作回执、持久化、工作区隔离 | 工具回报真实结果；宿主决定准入、重试和结果是否有效 |

恢复协调只处理“谁可以继续、从哪里继续、哪些动作须核实”。原有编排器继续决定部门流程；项目调度器只分配执行机会。沿用现有 EventStore、工件、项目采纳与工具准入，不建立新的事实库。

## 4. 3.2A：先交付一条本地编码链路

### 4.1 产品过程

1. 选择可信项目的一份确定代码快照，只读采集源目录；在 Yudao 管理的独立工作区开始事项。
2. 产品确认本次变更，工程制定计划，然后搜索、阅读、编辑、执行项目授权的本地构建/测试命令。
3. 模型可以看到命令退出状态和输出；成功退出只证明该命令成功，不自动等于任务完成。
4. 工程提交确定的完整代码树；QA 在独立副本上运行公开检查并给出结论；项目按现有规则采纳。

首批只交付代码快照接入所必需的能力：来源、版本/摘要、文件清单、初始基线和隔离副本。B5 的三部门自动建档、复杂远程仓库管理、远程 push 和自由项目对话仍后置。源项目不被直接改写；变化由可核验交付提供。

### 4.2 工具边界

| 能力 | 设计要求 | 验收反例 |
| --- | --- | --- |
| 搜索/目录/区间阅读 | 限在公开项目材料范围；返回来源和位置；大结果明确截断，并能继续取回 | 私有部门目录、Git 元数据、路径逃逸和链接绕行不能变成跨部门材料 |
| 区间编辑 | 针对已读取版本或可唯一核对的原文；不匹配时拒绝覆盖，让模型重新读取 | 文件已变、重复匹配、不存在目标、编码差异不能静默改错 |
| 本地命令 | 项目明确授权的命令及参数范围，固定工作目录、最小环境、时限、输出限制和进程树管理 | 未授权命令、超时、取消、子进程遗留、输出过量及退出失败均有真实状态 |
| 动作回执 | 执行前记录动作身份与输入依据；结果绑定命令、快照、退出状态、输出及尝试 | 执行完成但确认未落盘时不能伪装成未执行 |
| 独立 QA | 检查绑定最后提交的完整树，检查中的修改不得偷偷成为已测试交付 | 修改检查副本、复用旧回执、改树后沿用通过结论均被拒绝 |

首批“受控 shell”收敛为项目登记的本地命令执行，不提供默认任意 shell 字符串、安装软件或发布权限。专用文件工具继续负责可审计编辑，工程命令结果不能替代质检回执。

工作目录和环境白名单不是操作系统沙箱；项目脚本本身也能执行任意代码。首批限定可信本地项目与经审阅的构建/测试入口，不宣称能隔离恶意代码。若要求对任意代码强制限制文件与网络访问，必须先选用成熟 OS/容器隔离并验证，再开放该执行范围。不能靠命令名匹配或 Prompt 声称实现硬隔离。

### 4.3 现有依赖与成熟实现

- 文件、进程、SQLite、临时目录和归档先检查 Python 标准库与项目已有实现；不另造文件工具体系。
- 搜索优先使用维护中的 ripgrep。若采用，将它声明为运行前置并验证平台可用性，不静默退回另一套语义。
- 网络取回留给 3.2B，复用已有 HTTPX；模型继续使用官方 OpenAI SDK。MCP 到 3.2B 再选择官方 Python SDK，不自写协议客户端。
- 进程超时不等于整棵进程树已停止。Windows 和 POSIX 分别验证宿主支持，优先成熟进程管理能力；尚未验证的平台不得标为支持。
- 已有 OMP 工具与会话审查用于接口和证据模式；不引入 OMP 运行时接管 Yudao 的部门循环。

## 5. 3.1：恢复能力的交付合同

详细故障矩阵见 [恢复契约](design/recovery-contract-and-fault-matrix.md)。以下是不可省略的产品边界。

### 5.1 能恢复什么

首批恢复同一受支持应用版本中、因进程中断或模型引用无法使用而未结束的 run，保持项目、事项、有效合同和已用限额；模型与部门 Prompt 在每次请求时按当时的项目部门设置与部门默认解析（[ADR-0005](adr/0005-resolve-call-target-per-request.md)）。已完成、已取消及因次数耗尽停止的任务不通过恢复按钮重新开始；需要新目标或新额度时另开明确的新事项。

显式“继续执行”经 Web/CLI/API 共用一个命令入口。服务启动先重建状态并呈现待恢复原因，不在历史查询或 SSE 重连时隐式调用模型。首次提供一个简单 CLI 恢复命令不等于提前建设完整 3.7 接口平台。

### 5.2 恢复必须按这个因果顺序

1. 读取持久事实，核对应用版本、工件完整性和冻结配置。
2. 原子取得本 run 的执行权；既有有效执行者仍存在时拒绝重复恢复。
3. 区分未发送、已完成、结果未知的动作；核实遗留子进程和工作区，未知副作用未解决前不继续依赖它的步骤。
4. 从最后一个一致边界恢复部门工作，已确认工具结果与提交不重新执行；新输入、指导及取消仍按有效版本处理。
5. 保持部门隔离、压缩来源、步骤/循环计数；新请求有新尝试身份，重试仍受原有次数限制。
6. 重新经过独立 QA、完整封存和项目采纳；已完成但尚未结算的 run 只补幂等结算。

SQLite 内同事务维护执行权判定和有权推进的领域提交；进程内锁不能代替跨进程所有权。获得新执行权不意味着旧进程或旧工具已停止：对共享同一 run 工作区的写动作，必须先证明旧进程树结束或完成隔离与状态核实，才能发出新的冲突动作。

已确认模型响应但工具只执行了一部分时，恢复剩余合法动作，不重新调用模型生成一整批动作。只有不完整响应时才按现有错误分类与剩余尝试额度处理，不能把所有解析错误都改成可重试。

### 5.3 凭据、计数和版本

凭据只保存引用；重启后按引用从宿主重新解析密钥，不把密钥写入事件或工件。模型引用无法使用（定义被移除、准入已作废、窗口未知、凭据缺失或被上游拒绝）时，事项进入待恢复，说明部门、模型与具体问题；用户修复配置后继续执行，系统不自行改用其他模型（[模型管理设计说明](design/model-management.md)第 5.5 节）。凭据有版本时核对版本；来源不提供版本时明确记录无法证明同一密钥，不伪造身份，凭据变更单独明确处理。

恢复不能新增一次免费的部门激活、把 32 步重新计满或把三次重试重新开始。发送状态未知的尝试仍占用已准入的尝试与步骤；用量未知不填零，也不因为恢复而猜算费用。

首批不支持跨不兼容应用版本恢复。不维护旧事件兼容层，不做运行数据 migration；明确拒绝后，可使用已采纳成果开始新事项。事件语义变更前必须记录版本边界，不能等恢复时临时猜测。

### 5.4 为什么先保留现有持久化

首批是单机、同版本、单 run 的恢复，SQLite 与已有事件/工件最贴近当前领域事实。先用文件写完成但确认未保存、旧执行者未退出、交付完成未采纳三个窄场景检验，不因为“已有 SQLite”就宣布恢复已解决。

现有研究已经比较 Temporal 的工作流/活动恢复、LangGraph 的检查点与重执行。二者仍要求应用处理外部副作用、业务版本及授权，而且会增加持久状态映射。若窄场景迫使项目自行建设通用工作流、分布式租约或复杂调度服务，则停止扩大自研范围，用同一场景评估成熟引擎后再决定。现运行内核在实验期间保持可用。

## 6. 3.4：恢复通过后增加并行

3.4A 只让不同项目的独立事项并行，每个事项仍一个主 run、每个 run 仍串行三部门循环。每个 run 独立工作区、Provider 请求状态、历史和事件；项目调度只管理队列、执行槽位、排队取消及运行取消。

验收用两个事项形成真实时间重叠，其中一个在工具执行时被中断，另一个继续完成。恢复前者后，两份交付各自可核验；已完成者不重跑，取消一个不会取消另一个。两个是最低验收样例数，不是永久写死的并发上限。

容量由一个明确的宿主执行槽位设置控制，遵守现有每 run 限额。记录调用、实际用量、等待和耗时，但不在本轮引入 token/资金硬预算或父子额度分配平台。排队顺序、取消生效和重启后的队列状态必须可解释。

3.4B 才开放同项目多事项的隔离工作区，并用项目当前采纳版本做原子比较。两项都通过 QA，也只有仍基于有效项目版本的结果可以自动采纳；另一项保留为候选，后续集成有自己的合同和 QA，不自动合并冲突，不让“最后写入者覆盖”决定项目成果。

同事项多 run 与共享目录并发修改不在 Stage 3 开放；父子任务属于 Stage 4 部门内多角色，自动组织选择属于 Stage 7 受治理的系统演化。

## 7. 验收与停止推进条件

| 交付 | 必须看到的完整证据 |
| --- | --- |
| 本地工具 | 真实模型在可信代码项目上完成搜索→阅读→编辑→命令→独立 QA→封存→采纳；公开树外访问和陈旧编辑被拒绝 |
| 恢复 | 交接、文件/命令、QA/采纳三类边界各做真实进程终止与重启；同 run 完成或对未知效果明确停止核实；不能以 mock 抛异常代替进程中断 |
| 恢复反例 | 双进程争抢、旧执行者发工具、取消竞争、数据库/工件失败、凭据缺失、版本不匹配、步骤耗尽均有明确结果 |
| 并行 | 两个隔离事项重叠执行，其中一个中断/取消；另一个结果不受影响；恢复、限额及观测各自准确 |
| 同项目采纳 | 两个相同基线的候选竞争时，持久层只接受一个有效采纳；另一份可取回且未覆盖成果 |

每包都要检查历史查询、导出、replay 的只读性。恢复可靠的标准是：每个适用故障点都落在“有证据地继续”或“明确等待核实/停止”，且可继续的正常场景确实到最终 QA；不能把所有动作都停给人处理来宣称恢复通过。

发现重复领域推进、未知副作用被重放、旧执行者仍可写入同一工作区、计数被重置、错误采纳时，3.1 不关闭，3.4 不开始。环境失败和缺失记录单列，不改验收分母或用历史通过结果替代。

## 8. 实施方式与本轮状态

每包按契约/样例、最小端到端实现、独立反例审查、真实验收四步推进。实现可由子代理按工具、控制、观察分工；恢复引擎与项目采纳的共享修改不得无边界并发。每次小交付提交、推送，再开始下一个依赖包。

本轮交付设计文档，不运行真实验收、不改业务代码。3.0A 文档与合同已完成，当前设计的本地链接、表格、代码块和差异格式检查通过；3.0B、3.2A、3.1、3.4 均保持待执行。真实 Provider/任务材料/宿主环境在 3.0B 冻结，不在设计阶段填写尚未获得的运行结果。
