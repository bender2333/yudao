# 第三阶段计划：完整 Harness 与可持续运行的组织

日期：2026-09-09。性质：计划与目标，不表示任何能力已实现。上位依据：[总体路线图](program-roadmap.md) 第 4 节、[组织与持续运行研究](research/organization-runtime-evolution.md)、[OMP 系统审查](research/omp-stage2-system-review.md)（审查底本 OMP `e3106be`）、[S4-A 采用映射](s4a-omp-adoption-evidence-2026-09-08.md)、[可观测性研究](research/observability-design.md)。起点以 [第二阶段重新排布](stage-2-replan-2026-09-09.md) 与 [项目工作台合同](project-workbench-contract.md) 描述的 Stage 2 末状态为准。

## 0. 用户对本阶段的补充要求

路线图原定第三阶段是"可持续运行的组织"：技能、部门内部循环与分型、部门协议、异步与恢复、运维。用户在 2026-09-09 补充：基础做出来以后，skill、tool use、恢复这些 harness 的常见能力都要补齐，**第三阶段结束时 Yudao 应当是一个类似 OMP 的完整 harness**。

两者并不冲突：OMP 一类 harness 的通用能力（工具、技能、会话恢复、扩展点、多 Provider、命令行与嵌入接口）正是"组织能力"要站在上面的地基。本阶段因此分两层推进：先补 harness 通用能力，再在其上做组织能力，最后用一次对照验收同时证明两者。

一条贯穿的架构原则：**OMP 级能力，Yudao 式控制。** 能力全部加在宿主侧，模型的权限边界不变——工具准入、合同、质检放行、采纳、预算仍由宿主决定；Prompt 不作为安全控制；一个能力加进来，对应的证据、审计和停止原因同时加进来。

## 1. 阶段目标

阶段结束时的系统：一个能承担复杂、长时间、并行工作的多部门 harness，具备通用工具、技能、持久恢复、多 Provider、扩展点和命令行/嵌入接口；能对一个实际交付物完成需求、开发、发布、观察、修复、恢复验证的闭环。

整体验收要证明四件事：

1. **可恢复执行**：进程在任何交接、工具、外部动作边界被杀死后，能从持久事实恢复控制并继续，旧执行者没有推进权，外部动作的真实状态被核实而不是假定。
2. **可组合交付**：一个复杂事项由多个内部单元（有界子循环、并行只读工作、技能）协作完成，外层仍能独立核验；与三部门单循环相比质量不降、协作或上下文成本下降。
3. **持续运行闭环**：一个真实交付物在约定观察窗口内完成发布、观察、故障发现、修复与恢复验证，用户可见状态与事实一致。
4. **Harness 对照完整**：第 3 节每个能力域达到目标状态，或有明确写下的"不采用"决定与理由；一个真实外部项目从建档到多次事项的全过程只用 Yudao 完成。

## 4. 分层与责任

| 层 | 本阶段新增 | 不变 |
| --- | --- | --- |
| 界面 | CLI / NDJSON / 无界面模式；观测新增等待、恢复、并行、技能、动作核实视图；Provider 配置页 | Web 项目级工作台是主界面；查询不推进 |
| 业务引擎——运行内核 | 执行所有权与代次、从一致边界续行、四种有限组织的有界子循环、交接接收语义、技能调用与展开 | 交接、合同、QA、封存、run 内 Git、D17 重试规则 |
| 业务引擎——项目层 | 调度器与执行槽位、预算账、外部动作契约登记、技能注册、项目设置（授权、MCP、扩展）、运维职责 | 登记、事项、采纳、继承、Prompt 配置 |
| 基础设施 | 工具运行时扩展（受控 shell、搜索、编辑、取回、MCP 客户端）、第二协议适配器与推理设置、事件库新增责任 / 等待 / 预留事实、扩展点宿主 | 事件与工件是唯一事实；SQLite、文件工件、原生界面 |

三层是职责边界，不要求三个服务。新增能力全部按"能力 + 证据 + 停止原因"三件一起交付。

依赖与并行：

```
3.0 ─┬─ 3.1 恢复 ──── 3.4 并行 ──── 3.6 内部循环与协议 ─┐
     ├─ 3.2 工具 ──┬─ 3.5 技能 ───────────────────────┼─ 3.8 运维 ── 3.9 对照验收
```

## 6. 完成判定

同时满足：

- 第 1 节四件事各有一份在冻结提交上的真实验收记录。
- 研究 §10.1 故障矩阵十二项全部有测试；涉及外部动作的项至少做过一次真实故障注入。
- 第 3 节每个能力域达到目标，或写明"不采用"及理由；没有"待定"。
- 与 Stage 2 基线相比，质量、协作成本、上下文成本、墙钟和资金成本有完整报告；改善与未改善分别写。
- 文档状态、提交拓扑、测试报告与真实运行报告相互一致。

阶段结束不能只展示"多个 Agent 同时跑"或"队列接通了"；必须看到真实责任、交付、运行反馈和恢复一起工作。

## 7. 边界

- 不做第四阶段：系统自己提出组织与规则候选、候选实验、版本采用与撤销。研发者设计并比较有限版本，系统执行。
- 不预先引入消息队列、工作流服务、向量库、Kubernetes、常驻运维 Agent；选型必须过 §10.2 的故障场景与总成本比较。
- 沿用 S4-A 不采用项：OAuth 运行时、自动发现、适配器内重试、key 轮换、`previous_response_id`、远端压缩回退、Snapcompact、OTEL 作为领域事实。
- 不做嵌套分形、共享工作区并发修改、固定并发数、computer-use。
- Prompt 不是安全控制；扩展不能写事件、不能授予权限。

## 8. 与 Stage 2 现状的接口

Stage 2 必须先完成：轨道 A（A1–A4）、轨道 B（B1–B4，B5 建档可放到 3.9 前）、2.1–2.4。这些是本阶段的地基，不能并行开工。

Stage 2 已为本阶段留好的接口，实施时不要重造：
