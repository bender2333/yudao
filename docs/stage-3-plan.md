## 1. 阶段结束时用户能做什么

- 把一个已有的代码项目接入 Yudao，确认产品写出的初始 PRD，之后提出的变更由工程用搜索、阅读、编辑和命令完成，质检对确定的交付快照独立核验；质检能在浏览器中实际操作交付的网页。
- 代码在控制主机上直接运行；在登记的其他电脑与开发板上，执行代理在登记的目录中运行代码（见[执行环境服务设计说明](design/execution-environment.md)第 5.3 节）；来源不明的仓库放到另一台登记的机器上运行（[ADR-0022](adr/0022-run-directly-without-containers.md)）；网络取回与 MCP 工具在授权范围内使用。
- 进程意外退出后，Yudao 启动时自动继续中断的任务，只有结果未知的外部动作交给用户决定；Yudao 升级时按 run 事件版本直接继续或先排空。
- 不同项目的事项同时进行，同一项目的事项排队，用户可以调整顺序。
- 在模型管理页维护模型目录与准入，每个项目单独选择各部门的模型与推理档位；质检的模型不能看图时得到提醒。
- 在浏览器中打开 Yudao 服务提供的界面，在系统首页看到需要自己决定的事、离开期间发生了什么，在本机打开页面时收到浏览器的系统通知；每项能力都有对应的界面。
- 用评测工具在三个评测场景上与 OpenCode 对照，得到可以重复的报告；版本比较带噪声范围，结论是改进、无差别、退化之一，报告带费用与检验覆盖比例。
- 用一条命令在界限以内修改限额、检查时限与可见范围等参数，修改写成事件，撤回也是一条命令，不需要发布新版本。
- 在画面上看到每个循环实例的层、已用的边界、收敛状态与停止原因，以及每条事实的来源与开环的验收条件。
- 内核有清单，修改内核路径的交付不自动采纳；发布检查由已安装的实例提供。
- 已发布的 Yudao 实例在 Yudao 自己的仓库上完成真实工单，成果以合并请求写回，经现有的审查流程合并（自举试点）。

## 5. 3.1：恢复能力的交付合同

详细故障矩阵见[恢复契约](design/recovery-contract-and-fault-matrix.md)。以下是不可省略的产品边界。

### 5.1 能恢复什么

恢复 run 事件版本相同的应用版本中、因进程中断或模型引用无法使用而未结束的 run，保持项目、事项、有效合同和已用限额；模型与部门 Prompt 在每次请求时按当时的项目部门设置与部门默认解析（[ADR-0005](adr/0005-resolve-call-target-per-request.md)）。已完成、已取消及因次数耗尽停止的任务不通过恢复重新开始；需要新目标或新额度时另开明确的新事项。

Yudao 启动时先重建状态，再按 5.2 节的顺序自动继续所有因进程中断而未结束的 run；只有结果未知的外部动作通过用户决定交给用户（[总体架构](design/architecture/overall-architecture.md)第 7.4 节）。Yudao 进程由操作系统的服务管理在崩溃后重新启动，属于 Stage 4 长时间运行。模型引用无法使用时事项进入待恢复，用户修复配置后经桌面客户端、命令行与接口共用的一个命令入口继续执行。历史查询与事件流重连不调用模型。

### 5.2 恢复必须按这个因果顺序

1. 读取持久事实，核对 run 事件版本、工件完整性和事项使用的定义版本（[ADR-0014](adr/0014-versioned-definitions.md)）。
2. 原子取得本 run 的执行权；既有有效执行者仍存在时拒绝重复恢复。
3. 区分未发送、已完成、结果未知的动作；核实遗留子进程和工作区，未知副作用未解决前不继续依赖它的步骤。
4. 从最后一个一致边界恢复部门工作，已确认工具结果与提交不重新执行；新输入、指导及取消仍按有效版本处理。
5. 保持部门隔离、压缩来源、步骤与循环计数；新请求有新尝试身份，重试仍受原有次数限制。
6. 重新经过独立质检、完整封存和项目采纳；已完成但尚未结算的 run 只补幂等结算。

SQLite 内同事务维护执行权判定和有权推进的领域提交；进程内锁不能代替跨进程所有权。获得新执行权不意味着旧进程或旧工具已停止：对共享同一 run 工作区的写动作，必须先证明旧进程树结束或完成隔离与状态核实，才能发出新的冲突动作。

已确认模型响应但工具只执行了一部分时，恢复剩余合法动作，不重新调用模型生成一整批动作。只有不完整响应时才按现有错误分类与剩余尝试额度处理，不能把所有解析错误都改成可重试。

### 5.3 凭据、计数和版本

凭据只保存引用，控制核心不持有明文凭据；每次模型请求由 Provider 模块按引用从当前凭据来源解析，重启以后同样如此，凭据的更换从下一次请求起生效，不把密钥写入事件或工件（[ADR-0005](adr/0005-resolve-call-target-per-request.md)）。模型引用无法使用（定义被移除、准入已作废、窗口未知、凭据缺失或被上游拒绝）时，事项进入待恢复，说明部门、模型与具体问题；用户修复配置后继续执行，系统不自行改用其他模型（[模型管理设计说明](design/model-management.md)第 5.5 节）。凭据被上游拒绝在 Stage 3 进入待恢复；Stage 4 起改为进入等待模型服务，按间隔重试，恢复后自动继续（[总体路线图](program-roadmap.md)第 5.1 节）。请求事件记录调用目标的公开部分与凭据引用；来源提供非敏感版本标识时一并记录，不从密钥内容生成标识。

恢复不能新增一次免费的部门激活，也不能把已用的模型步数（上限见 [D09](requirements/execution-limits.md)）、已用的运行时间或三次重试重新计数。发送状态未知的尝试仍占用已准入的尝试与步骤；用量未知不填零，也不因为恢复而猜算费用。

版本规则按 [ADR-0019](adr/0019-project-stream-across-versions.md)：项目流跨 Yudao 版本保存，升级时只增加字段、事件种类或已有字段的取值，已有字段的含义不变；run 流跟随应用版本，不维护旧事件兼容层，不做运行数据 migration。每个版本声明自己的 run 事件版本：升级前后相同时直接重启，按本节自动继续；不同时先排空（停止开始新事项，等正在进行的 run 结束）再升级。用户可以强制升级：正在进行的 run 记为因升级停止，对应的事项用项目的起点重新开始，并记下「因升级重新开始」的优先级；3.1 中同一项目一次只有一个事项，重启后它第一个开始，排在队列最前面由 3.4A（#19）验收。run 事件的语义变更前必须改变 run 事件版本，不能等恢复时临时猜测。

### 5.4 为什么沿用现有持久化

恢复是单机、同版本、单 run 的恢复，SQLite 与已有事件、工件最贴近当前领域事实。先用文件写完成但确认未保存、旧执行者未退出、交付完成未采纳三个窄场景检验，不因为「已有 SQLite」就宣布恢复已解决。

不引入外部工作流引擎（[ADR-0012](adr/0012-single-control-core-scalable-execution.md)）。Temporal 的工作流与活动恢复、LangGraph 的检查点与重执行都要求应用自己处理外部副作用、业务版本及授权，引擎的执行历史还会成为事件日志之外的第二份事实。控制核心本身是按事件重放的状态机，会话可以丢弃，恢复时从已提交的状态重新装配；两者的成熟模式用于划分执行历史、动作与检查点的边界。

## 6. 3.4A：恢复通过后增加并行

3.4A 只让不同项目的独立事项并行，每个事项仍一个主 run；同一事项同一时刻只有一个部门持有交接，其他部门可以做预测性探索（[D26](requirements/department-roles.md)，Stage 5 实施）。每个 run 独立工作区、Provider 请求状态、历史和事件；项目调度只管理队列、执行槽位、排队取消及运行取消。

验收用两个事项形成真实时间重叠，其中一个在工具执行时被中断，另一个继续完成。恢复前者后，两份交付各自可核验；已完成者不重跑，取消一个不会取消另一个。两个是最低验收样例数，不是永久写死的并发上限。

执行槽位数是规则登记中的参数，修改写成事件，遵守现有每 run 限额；Stage 5 起执行槽位按角色任务占用，预测性任务优先级低于正式任务，正式任务需要槽位时预测性任务在安全节点让出（D26）。记录调用、实际用量、等待和耗时，本阶段不引入 token 或资金硬预算、父子额度分配平台。排队顺序、取消生效和重启后的队列状态必须可解释。

同一项目一次只进行一个事项。同一项目的其他事项排队，前一个事项结束后再开始，从当时项目采纳的版本出发。排队顺序：因升级重新开始的事项最前；Stage 4 起运维发起的修复事项排在用户新要求之前（[D27](requirements/operations-department.md)）；用户新要求之间的顺序用户可以调整（`work_item.reorder`）。

同事项多 run 与共享目录并发修改不在 Stage 3 开放；父子任务属于 Stage 5 部门内多角色，自动组织选择属于 Stage 6 受治理的系统演化。

## 7. 验收与停止推进条件

| 交付 | 必须看到的完整证据 |
| --- | --- |
| 恢复 | 交接、文件与命令、质检与采纳三类边界各做真实进程终止与重启；重启后自动继续，同 run 完成或对未知效果明确停止核实；不能以模拟抛出异常代替进程中断 |

| 并行 | 两个不同项目的隔离事项重叠执行，其中一个中断或取消；另一个结果不受影响；恢复、限额及观测各自准确；同一项目的第二个事项排队 |
| 模型管理 | 三种协议的连接测试、模型测试与带工具往返的真实请求有证据；运行中更换模型与档位从下一次请求起生效 |
| 界面 | 每个工作包的界面在真实运行的系统上通过 Playwright 端到端测试，页面上的数据都来自查询与事件流 |
| 对照实验 | 三个评测场景上 Yudao 与 OpenCode 各运行 3 次的结果，失败与缺失如实列出；共享上下文一组的结果与解释翻转率 |
| 迭代底座 | 内核演练的记录；终止进程再启动，已用的运行时间连续；一个参数的修改与撤回各是一条命令与一条事件；一份带噪声范围、费用与检验覆盖比例的评测报告 |
| 自举试点 | 6 个配对工单的审查轮数、集成层结果、架构师发现的问题数、用户试用的缺陷数、耗时、用量与费用、用户介入次数 |

每包都要检查历史查询、导出、replay 的只读性。恢复可靠的标准是：每个适用故障点都落在「有证据地继续」或「明确等待核实或停止」，且可继续的正常场景确实到最终质检；不能把所有动作都停给人处理来宣称恢复通过。
