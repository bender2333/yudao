## 2. 原型带来的结构变化

### 2.1 概念层级

```
项目（长期）
 ├─ 部门 × 3（项目级、持久；产品 / 工程 / 质检）
 ├─ 事项（一次有边界的变更；= 2.E 的"变更"）
 │    └─ run（一次执行）
 │         └─ 模型尝试 / 工具 / 事件 / 用量
 ├─ 当前采用成果、有效决定、资料
 └─ 部门 Prompt 项目配置
```

- 项目：长期目标、资料、有效决定、当前采用成果、事项历史、三部门的项目级工作区与 Prompt 配置。
- 部门：属于整个项目，不是某一次事项的下级。部门页默认展示本部门在整个项目上的工作，可聚焦一个事项。
- 事项：一次目标与交付边界。协作总览的流程图和看板卡片都指事项；一个事项可对应一到多个 run。
- run / 尝试：执行事实，观测的最小范围。

前两版原型里"项目 → 任务 → 工作台"的层级已被 2026-09-08 的确认替代：三部门属于整个项目。

### 2.2 与当前代码的差距

| 原型要求 | 当前实现 | 差距 |
| --- | --- | --- |
| 项目对象、项目列表、置顶/归档 | 没有；一切以 `run_id` 为作用域，`LoopSystem.create_run(task)` 直接开跑 | 需要项目作用域的事件、投影与登记 |
| 事项与跨部门看板 | 没有；run 的阶段就是流转 | 需要事项读模型：承接部门、状态、最近交接、回退来源、关联 run |
| 部门项目级工作区 | 部门历史按 run 保存与装配（D08） | 需要跨 run 的部门聚合读模型；模型输入仍以 run 为单位 |
| "继续开发"继承成果 | 每个 run 新建空工作区、独立 materials 与 Git | 需要从项目当前采用成果的完整封存恢复到新 run 工作区（复用 D13） |
| 采纳 | QA release 即终态 | QA 通过与项目采纳分开记录（2.E §5） |
| 部门 Prompt 项目配置 | `update_prompt(run_id, department, text)`，run 作用域 | 项目作用域配置、有版本；run 创建时固化 |
| 接入已有项目并建档 | 没有 | 后置 |
| 观测按项目/事项/部门筛选并返回来源 | 按 run 筛选 | run 增加归属字段，观测增加筛选维度 |
| 资料与设置只在项目概览、左栏折叠 | 单任务控制台 | 属于外壳重组 |
| Provider 配置 UI | 预留 | 继续预留 |

## 3. 架构：在运行内核之上加一层，不拆内核

三层责任沿 2.E：

| 层 | 责任 | 本轮变化 |
| --- | --- | --- |
| 界面 | 项目导航、概览、看板、部门页、观测；呈现信息与发出命令 | 外壳按第三版重组；部门页内部沿用现有实现 |
| 业务引擎 | 运行内核（现有，run 作用域，交接与停止规则不变）+ 项目与事项管理（新增） | 新增一项内聚责任：登记、run 归属、采纳、继承、部门项目配置；不新增部门、不新增第二运行器 |
| 基础设施 | 事件库、工件、封存、run 内 Git、Provider 目录 | 事件库增加项目作用域；其余复用 |

### 3.1 关键决定

- **D-A 项目是显式登记的对象。** 事件库增加项目作用域的事件流，项目读模型从事件重建；不用目录名、聊天会话或"最新一次 DONE 的 run"冒充项目身份。
- **D-B run 必须归属项目与事项。** 创建 run 时绑定 `project_id` 与 `work_item_id` 并写入 `RUN_CREATED`，不保留"无项目 run"的路径。现有 `.yudao/*` 数据目录是各轮验收数据，不迁移；需要回看时用当时的代码版本读取（待用户确认，见第 8 节）。
- **D-C 部门项目级工作区是读模型。** 聚合项目内各 run 中该部门的公开工作（消息、交接、交付、指导回应）与项目级材料。每次模型请求仍按 D08/D10 装配本 run 的部门历史；跨 run 只注入"项目当前采用成果 + 仍有效的决定摘要 + 本事项差异"，不带全部历史（2.E §6）。
- **D-D 事项等于一次变更。** 首批：创建事项即创建其主 run；事项状态由 run 阶段和采纳事实派生，不另存一份可拖动的状态；"继续开发"在同一项目创建新事项，其 run 工作区从项目当前采用成果的完整封存恢复。项目级 Git 历史不在首批，D16 仍是 run 内 Git。
- **D-E QA release 不等于采纳。** 首批在 release 且基线仍是项目当前成果时自动采纳并记录来源；基线已变则保留为未采纳候选，不覆盖后来版本（2.E §5）。
- **D-F 部门 Prompt 项目配置。** 项目作用域、有版本；空白拒绝，同文本不加版本；新 run 创建时把当时版本固化为该部门在此 run 的初始 Prompt 版本，run 内 `update_prompt` 机制不变；检查区分开显示"项目当前配置"与"某次请求实际采用"。与 [配置约定](prototypes/2026-09-09/department-prompt-configuration.md) 一致。
- **D-G 看板是读模型。** 卡片上的操作只能触发既有命令（创建事项、追加输入、部门指导、取消）；不做拖拽改状态。
- **D-H 无活跃事项时的部门讨论首批不对话。** 无活跃事项时，部门输入框提供"作为新事项开始"，其余讨论只按原文记录为项目材料。原因：当前内核只在 run 激活内调用模型；没有 run 的部门对话需要新的执行模式，属于 2026-09-08 已留待后续的部门内部循环设计。待用户确认。
- **D-I 接入已有项目建档后置到 B5。** 先跑通"从想法新建 → 首个事项 → 采纳 → 继续开发"。
- **D-J Provider 配置继续预留；观测继续只读。**

## 5. 各包验收要点

### 5.1 B1 项目与事项内核

- 同一项目连续两个事项：第二个事项的 run 工作区与第一个事项采纳成果的完整封存逐字节一致；第二个事项交付后项目当前成果指向新版本，旧版本仍可取回。
- QA release 但项目基线在其开始后已变：该交付保留为未采纳候选，项目当前成果不变，事件记录原因。
- 从事件重放能重建项目投影（事项列表、当前成果、有效决定、部门 Prompt 配置版本）；删除派生表不影响重建。
- 两个项目各有事项，任何查询不串数据；run 的 `RUN_CREATED` 含项目与事项归属。
- 取消、失败、暂停的 run 在事项与看板上保留原停止原因，不被采纳。

### 5.2 B2 部门 Prompt 项目配置

- 保存新文本版本加一；同文本重复保存不加版本；空白拒绝；所编辑版本已过期时返回冲突并保留草稿。
- 新 run 创建时该部门初始 Prompt 版本等于当时项目配置；run 内 `update_prompt` 只改本 run，不改项目配置。
- 历史请求的 Prompt 原文与版本不因项目配置修改而变化；检查区能同时看到项目当前配置与所选请求实际采用内容。
- 三个部门、多个项目之间互不影响。

### 5.3 B3 Web 外壳

- 结构与第三版原型一致：左栏项目列表可折叠，项目概览独占资料与设置入口，部门页默认全项目、可聚焦事项且两个范围草稿独立，协作总览流程/看板同一数据，观测筛选同时作用于请求列表与用量，返回时恢复来源页面与范围。
- 项目切换、浏览器后退不串数据；SSE 更新当前项目内可见对象。
- 没有 mock 业务数据；空项目、无活跃事项、终态事项各有对应空态。
- 视觉：1440/1024/390/360/320，浅/深色，长任务名、长模型名、长错误、64KB Raw。
- 现有部门工作区行为（对话、指导、Context 精确跳转、Prompt 查看/编辑）在新外壳内回归通过。

### 5.4 B4 联调与真实验收

- 使用 `provider.md` 指定服务与专用测试密钥，三部门显式绑定；限制按试验登记，不写成标称能力。
- 一个从想法新建的项目，三次事项：逐行文本处理工具 → 在已有代码上增加文件输入 → 用户明确把"保留重复行"改为"只保留首次出现"。每次事项由独立 QA 放行并自动采纳；第二、三次从上一次采纳成果开始；空输入行为保持，去重相关检查更新。
- 期间修改一次工程部门项目 Prompt，下一次事项的工程 run 实际采用新版本，历史请求不变。
- 看板卡片流转与事件一致；观测能从部门 Context 进入具体尝试并返回；封存恢复后外部检查通过。
- 真实失败保留原文，不换服务、不换 Prompt、不扩大重试；任何场景缺失按场景标 PARTIAL。
