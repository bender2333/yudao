## 1. 研究 7.1：两类运行责任分开

正式接收前应具备：发布对象与环境、已验证版本、运行窗口、用户目标、监测方式、响应者、可执行缓解、升级对象、恢复标准、结束责任方法。发布成功与运维接收分别记录。

下列指标的分母、阈值、窗口均为**待 Stage 5 确定**。这里只规定指标必须有分母，以及告警从哪里来、谁有权做什么、责任何时结束。

### 1.1 平台运行责任（Yudao 自身）

对象：事件库、工作进程、Provider 连接，以及界面订阅能否看到真实状态。不包括「被交付服务对终端用户是否可用」。

| 项 | 内容 |
| --- | --- |
| 责任人角色 | **平台运营者**（研发者或指定值班），由人担任。愿景是由 Yudao 自己的运维部门承担平台运维，见[总体路线图](../program-roadmap.md)。模型不能自行结束平台责任。 |
| 指标（须有分母） | **调度可用性**：分母 = 约定窗口内「应被调度的有效任务次数」（创建后未取消且预算未在创建时即非法）；分子 = 其中进入激活或写出明确停止原因的次数。**事件持久化**：分母 = 控制层尝试 `store.append` 的次数；分子 = 成功持久且事后可读的次数。**Provider 到达**：分母 = 已发出的模型尝试（`sent` 尝试，见 `list_model_attempts.total_attempts`）；分子 = 有终态（完成/失败/取消）的尝试。**未知用量持续时间**：分母 = 窗口内未结算尝试数；分子 = 其中超过「待 Stage 5 确定」时限仍 `missing`/`unknown` 的数量。 |
| 告警来源 | 事件库写入失败、工作进程消失而 run 非终态、Provider `provider_error` 且影响「应被调度任务」、观察订阅断开（研究 10.1：失联 ≠ 执行失败）。来源应能在平台外做一次探活（研究 7.2：不能只靠已故障平台自报）。 |
| 响应授权 | 待 Stage 5 确定。样例范围：**允许**重启工作进程、只读查询事件库、断开并重连 Provider（不改用户目标）。**不允许**改事项合同、代签 QA、把失败 run 改写成成功、对交付物环境做发布。 |
| 结束责任 | 平台对象停止服务或移交给下一平台运营者，且交接记录写明未结算用量与未终态 run。结束不等于历史上的 append 消失。 |

平台恢复而交付物仍返回错误内容时，平台指标可以「好」，交付物指标继续失败（OR-12）。

### 1.2 交付物运行责任（被交付的服务）

对象：已发布、面向用户的运行约定。模型供应商超时导致**任务未做完**，不自动算交付物功能缺陷。

| 项 | 内容 |
| --- | --- |
| 责任人角色 | **运维部门**（Stage 5）。与平台运营者的指标分开记录。产品仍负责取舍，工程负责修复，质检负责验证。运维部门提供事实与运行约束，不修改功能要求。 |
| 指标（须有分母） | **用户目标成功率**：分母 = 约定窗口内从用户入口发起的、符合「用户目标」定义的尝试次数；分子 = 按事先定义判定成功的次数。**失败分类占比**：每类失败次数 / 同一分母。**成功时延**：成功样本的时延分布；分母 = 成功次数。**失败时延**：失败样本；分母 = 失败次数。空分母不得记为 100% 成功（研究 10.1）。 |
| 告警来源 | 用户入口探针、错误日志、人工报告。探针定义待 Stage 5 确定。告警进入**既有变更流程**（项目事项），不另开模型私聊当工单。 |
| 响应授权 | 待 Stage 5 确定。样例：**允许**在已登记的缓解清单里执行（见 2.2 / 3.2 假设项）。**不允许**超出清单的数据删除、扩大授权范围、跳过质检验证宣布恢复。 |
| 结束责任 | 交付物停止服务或移交，且观察窗口内最后一次用户入口检查已记录。没有接收者则发布该版本的工程/事项仍承担跟进。 |

SRE 四信号（时延、流量、错误、饱和度）用来从用户症状对照内部原因；不把每条模型错误升级为人工告警（研究 7.1）。饱和度可对照平台「活跃执行数 / 队列」，分母待 Stage 5 确定。

## 2. 故障链路（共同骨架）

研究 7.2：症状 → 确认影响 → 建立响应责任 → 授权缓解 → 生成修复 → 独立检查 → 确认恢复 → 复盘。紧急缓解可以先于完整根因，但必须留下理由、外部变更和待验证假设。

恢复完成看**用户可见行为**和约定观察窗口，不看「重启命令成功」或「日志变安静」。

复盘区分：已确认原因、促成条件、尚待验证解释、修复动作、需实验的规则建议。临时处置不自动变成长期规则。

修复任务由运维部门提出，作为项目层**事项**进入同一条变更流程：产品要求 → 工程交付 → 质检。

用户可见状态通过明确命令进入控制层后由投影显示；点击不能直接写成功终态（研究 7.3）。

## 3. 候选甲：Yudao 自己的 Web 控制台

假设：控制台已作为「交付物」发布到某环境（环境本身待 Stage 5 确定）。用户目标样例：打开项目工作台，能看到与事件库一致的事项/run 状态，并能提交一条合法命令（创建事项或取消）。

### 3.1 一次假设故障链路

症状：研发者打开控制台，事项列表空白或与 `EventStore.list_events` 不一致。

| 步 | 谁 | 看到什么事实 | 写什么记录 | 用户可见状态 |
| --- | --- | --- | --- | --- |
| 症状出现 | 运维部门或用户 | 浏览器里列表空；平台侧事件库仍能列出同一 `project_id` 的事项（若 B1 已落地） | 告警或手工记录：时间、URL、截图/响应码、探针 id。正式告警通道**待 Stage 5 确定** | 「症状已报告，影响未确认」；不得显示「已修复」 |
| 确认影响 | 运维部门 | 用户入口探针失败次数 / 窗口内入口尝试（分母待 Stage 5 确定）；是否仅某一项目 | 影响范围：哪些项目、是否写路径受影响 | 「已知 N 次入口失败 / 分母 M」；分母未知则显示「证据不足」 |
| 建立响应 | 运维部门接收运行责任（若尚未接收则先记接收） | 责任方、版本哈希、环境名 | `ops_responsibility_accepted`（新增）；未接收则事项仍挂原发布者 | 「交付物运维：运维部门；平台运营者：乙」 |
| 缓解 | 运维部门，仅授权清单内 | 例如：切到只读静态页、关闭创建按钮、重启**控制台进程**（不是改事件历史） | 缓解命令、实际外部变更、假设（「前端查询参数错」） | 「缓解已执行：只读；写命令已停」；分别显示已停分派 / 仍计费的平台 run（若有） |
| 修复进入事项 | 运维部门提出，产品取舍后开事项 | 有效要求：例如「列表必须来自项目事件查询，空表示真的零事项」 | 既有 `work_item_created` + run；不是新事件类型代替事项 | 工作台：该事项状态由 run 投影派生（Stage 2 合同） |
| 工程修复 | 工程 | 代码与主机检查；无发布工具则发布仍是人工/待 3.2 契约 | 现有计划/交付/检查；发布另记 `release_recorded`（新增） | 事项「工程交付已接纳，未发布」或「已发布版本 X，运维未接收」 |
| 质检验证 | 质检 | 独立按合同检查；含用户入口，不采信工程自报 | 现有 `QA_SUBMITTED`；入口检查回执 | 「质检未放行」或「放行，观察窗未结束」 |
| 确认恢复 | 运维部门 | 观察窗（待 Stage 5 确定）内用户入口成功率分母非 0，且与事件库抽样一致 | 恢复记录：窗口起止、分母、分子、仍失败的样本原文 | 「观察中」直到窗口结束；结束才「运行约定恢复」 |
| 复盘 | 运维部门起草，产品/工程/质检补事实 | 已确认原因 vs 假设 | 复盘文档；规则候选另走 Stage 7，不在复盘里生效 | 界面只链到复盘工件，不改历史投影 |

平台对照：若根因是 `events.sqlite` 锁死，平台运营者按 1.1 处理；控制台进程恢复后若列表仍错，继续走交付物链路（OR-12）。

### 3.2 假设的缓解清单（未授权实施）

待 Stage 5 确定哪些自动、哪些人工。样例条目：重启控制台进程；禁用创建/取消按钮；展示「查询失败」而不是空列表冒充零事项。不包含：删除事件库、改 `RUN_DONE`、对用户目标做产品放行。

## 4. 候选乙：贯穿验收的文本 CLI 工具

假设：`src/echo.py`（或其后继去重版）作为命令行工具发布到约定环境（例如某台机器上的固定路径）。用户目标样例：对给定文件执行「按行处理」（第二次或第三次变更后的合同行为）。

### 4.1 一次假设故障链路

症状：用户运行 `python src/echo.py samples/input.txt` 得到非合同输出（例如重复行未按第三次合同去掉，或文件输入不可用）。

| 步 | 谁 | 看到什么事实 | 写什么记录 | 用户可见状态 |
| --- | --- | --- | --- | --- |
| 症状出现 | 用户或探针脚本 | 退出码、stdout/stderr、argv、工具版本/文件 digest | 告警附件=探针日志；禁止只贴模型自然语言 | 「CLI 探针失败」；Yudao 工作台若未接该交付物，则状态在事项评论/附件里 |
| 确认影响 | 运维部门 | 同一 argv 在发布环境复现；对比封存 `code_tree_digest` | 是否仅缺文件路径、是否版本与事项采纳不一致 | 「发布 digest D1，事项采纳 D2」或「同 digest 仍失败」 |
| 建立响应 | 运维部门 | 运行责任清单 | 与甲相同的接收记录，对象改为 CLI 环境 | 责任方与版本可见 |
| 缓解 | 运维部门 | 授权项例如：从 PATH 摘掉损坏版本、指回上一已验证 digest（若有查询与授权） | 实际路径变更；未验证的「回滚成功」不得写 | 「当前环境指向版本 V；待核实」 |
| 修复进入事项 | 运维部门提出，产品取舍后开事项 | 新事项：修复合同行为或声明环境装错 | 贯穿任务同族的第三次或热修事项 | 项目内事项列表出现该修复 |
| 工程修复 | 工程 | 继承已有 CLI 代码，走主机检查 | 现有交付链；[技能档案样例](skill-dossier-sample.md) 可在 Stage 4 技能完成后用于检查步骤 | 事项内可见检查回执 |
| 质检验证 | 质检 | 独立 `run_check` / `collect_evidence`；并在**发布环境**再跑同一用户入口（不只是 CI 工作区） | QA + 环境探针回执（新增环境字段） | 「工作区通过，发布环境未测」必须能区分 |
| 确认恢复 | 运维部门 | 观察窗内探针分母非 0 | 与甲相同结构，入口改为 CLI argv 集合 | 窗口结束前保持「观察中」 |
| 复盘 | 同上 | 例如「采纳了旧基线交付」或「环境未装新 digest」 | 复盘；过期基线已在 2.E 场景中 | 不把环境装错写成模型能力问题 |

### 4.2 与平台故障的区分

Provider 超时导致**没有做出新版本**，记平台/任务失败。用户环境里旧 CLI 仍按旧合同工作，则交付物可用性按旧约定单独算，不把任务失败并进 CLI 错误率。

## 5. 两个候选对照：谁更适合做首个持续运行对象

| 维 | Web 控制台 | 文本 CLI |
| --- | --- | --- |
| 用户入口是否独立于平台 | 弱。控制台读同一事件库、同一工作进程。平台故障与交付物故障难分（OR-12 仍成立，但样本会混） | 强。入口是命令行与文件，不依赖工作台存活 |
| 发布与查询 | 现无发布；Web 已在跑，容易把「开发机上的 serve」误当成已接收的运行责任 | 发布物是单一可执行文件/脚本，digest 可对封存树 |
| 观察分母 | 浏览器会话、鉴权、多页面，分母难事先钉死 | argv 集合可写成固定探针（与 1.2 检查同源） |
| 缓解 | 重启进程可能同时影响平台与「交付物」 | 换 PATH 或文件不碰事件库 |
| 与贯穿验收的关系 | 控制台是 Yudao 产品本身，事项会改观察者 | CLI 正是 2.E / 3.9 任务族，修复事项不改变评价工具 |
| 现有检查 | 浏览器验收存在，但是对开发中的 UI，不是运维 SLO | `run_check` 已能跑 CLI 行为 |

**更适合作为运维部门首个持续运行对象的是贯穿验收的文本 CLI 工具。** 理由：用户入口与平台可分开测量；探针分母可先钉在固定 argv；缓解不改 Yudao 事实库；与研究 7.1「模型超时 ≠ 交付物缺陷」、OR-12「平台恢复但业务仍错」更容易做一次真实验证。Web 控制台更适合作为**第二**个对象，或作为平台可用性的用户面，而不是第一条交付物 SLO 的分母来源。

最终选定权在用户（见第 8 节第 1 条）。本文不代替该决定。

## 6. 「待 Stage 5 确定」的占位与依赖

| 占位 | 依赖什么信息 |
| --- | --- |
| 观察窗口长度 | 真实发布环境、故障注入是否可约、用户是否接受「窗口内必须出现一次真实故障」（Stage 5 运维部门的完成依据） |
| SLO 数字与错误预算 | 选定交付物的历史失败率或可接受失败份额；服务事件分母定义；与 token/资金预算分列（O09 示例阈值不套用） |
| 用户目标与探针脚本 | 合同原文（CLI 用 1.1/1.2 或第三次去重句；Web 用哪条工作台操作） |
| 告警通道 | 邮件/即时消息/仅工作台通知；谁值守 |
| 响应授权清单 | 环境登录方式、能否自动重启、回滚是否有查询接口（3.2 外部动作契约） |
| 升级对象 | 平台运营者 ↔ 运维部门 ↔ 用户（研发者）的升级线 |
| 结束责任手续 | 停服标准、移交文档字段 |
| 指标存储 | 探针结果是否写入项目事件表（非 run `events` 表），避免污染 `project_run` |

进入 Stage 5 之前，这些空缺**不影响**写清责任分离与链路步骤（研究第 11 节）。

## 7. 比较与验收时看什么

实验协议第 8 节「持续运维」：

- 最小通过：发现、分派（事项）、修复、发布、外部恢复检查闭环；用户可见状态与事实一致。
- 不足以通过：模型说已修好，或只重启了进程。

OR-12：平台恢复后仍须对用户入口失败。

图形化（研究 7.3）：在部门节点上展开等待、责任、未知副作用；首屏突出谁负责、在等什么、交付是什么。本样例不设计新 UI。

## 8. 待决点

1. 用户选定运维部门的首个运行对象：Web 控制台、贯穿 CLI、还是外部服务。
2. 发布记录与运维接收的事件落在项目事件表还是别处；不得写入模型可伪造的「已批准」。
3. CLI 若只在开发工作区运行、从未发布，则本样例的「交付物」不成立，运维部门不能以它开始承担运行责任。
4. 缓解是否包含自动回滚：取决于 3.2 对发布动作的查询/取消能力；本技能档案明确不覆盖发布。
5. 观察窗内「必须有一次真实故障」如何注入：人工、还是约定缺陷版本；注入本身要进审计。
