## 0. 现状（2026-09-09 核对）

现有唯一组织是三部门单循环 + 专家协作 + 部门指导。没有技能、没有子循环、没有运维职责、没有发布动作。

| 事实 | 位置 | 含义 |
| --- | --- | --- |
| 部门工具集按部门过滤 | `harness/tools.py::tools_for`、`TOOL_DEFS` | 工程可写文件、`run_check`、`submit_plan` / `submit_delivery`；`collect_evidence` 仅质检 |
| 工具准入 | `harness/orchestrator.py::Orchestrator._begin_tool` | 部门无权、指导专用激活、协作写权限、计划范围均可拒收 |
| 主机检查与回执 | `harness/tools.py::ToolRuntime._run_check` / `_collect_evidence` / `_execute_check`；`harness/workspace.py::Workspace.bind_check` / `record_check` | 检查在工作区副本上跑；回执写入 `receipts.jsonl`，绑定 activation 与合同/计划哈希 |
| 提案合同 | `harness/validation.py::evaluate_proposal`、`_accept_delivery`、`_accept_review` | 自然语言不改状态；交付必须有绑定当前快照的工程回执 |
| 协作一次一个未结请求、不嵌套 | `harness/collaboration.py::request_errors` | 已有 `pending_request` 时拒绝新请求；接收方必须是**另一部门** |
| 部门指导 | `EventType.DEPARTMENT_GUIDANCE_*`；`harness/collaboration.py::guidance_response_errors` | 研发者对当前部门的有限 steering，不是子循环 |
| 循环上限 | `harness/orchestrator.py::Orchestrator.create_run`（默认 `max_cycles=8`）；`_prepare_activation` 在 `cycle_count >= max_cycles` 时暂停 | 停止原因 `max_cycles` |
| 步骤上限 | `harness/orchestrator.py` 捕获 `ProviderError.reason == "model_steps_exhausted"`；`harness/models.py::PAUSED_REASONS` | 暂停，不是失败 |
| 用量派生 | `harness/observability.py::USAGE_SOURCES`、`_usage_source`、`ObservabilityQuery.model_usage` | 来源集合：`reported` / `missing` / `unknown`；合计只加 `reported` |
| 用量记账事件 | `harness/orchestrator.py::Orchestrator._record_usage` | 复用 `EventType.TOOL_CALLED`，`payload.name == "provider_usage"` |
| 默认 Prompt | `harness/department_prompts.py::DEFAULT_PROMPTS` | 工程：先计划、写文件、`run_check`、提交 DeliverySpec；不能自报完成 |

协作不能在工程内部开同级子单元（接收方必须是另一部门）。下文四种组织所需的内部单元、预留账、并行槽位都是**待新增**记录，不是现有事件。

## 1. 共同场景与选择理由

选用贯穿验收的**第二次变更**：「在已有 echo 工具上增加文件输入」（[原生项目演化设计](../research/native-project-evolution-design.md) 第 9 节）。

理由：

1. 子成果边界比第三次「去重只保留首次出现」清楚：参数分类、文件读取、与既有 echo 行为的接线可以分开验收，适合比较「独立分工后集成」。
2. 已知遗漏类型具体（缺文件、空文件、路径与字面量歧义、编码），适合观察「执行加内部复核」是否只复述同源意见。
3. 可比方案数量少且可事先钉死（位置参数路径 vs `--file`），适合「有界探索再收敛」，不打开开放设计。
4. 第三次变更是单一语义翻转，硬拆并行子任务会把任务本身变容易或变歪，干扰组织比较（研究 9.1：不能把任务变容易算成组织收益）。

本样例假定第一次变更已采纳：`src/echo.py` 对 `python src/echo.py hello` 打印 `hello` 并退出 0。第二次变更在同一项目事项上继承该代码与有效合同。

### 1.1 固定公开要求（四种组织共用）

纳入：

1. 保留：`python src/echo.py hello` 打印 `hello`，退出 0。
2. 新增：当唯一参数是工作区内现存普通文件的相对路径时，按行打印文件原文（不改行尾语义以外的内容），退出 0。
3. 空文件：打印空输出，退出 0。
4. 路径不存在：退出非 0，不写网络、不新建配置文件。
5. 不新增网络访问。

未纳入（须由产品合同写明，执行者不得自行发明）：

- 标准输入回退、递归目录、通配符、多文件拼接。
- 「参数既像路径又像字面量」的默认：本样例规定**现存文件优先于字面量**；该句必须出现在公开验收条件里。

### 1.2 可检查成果

| 检查名（样例） | 命令或条件 | 期望 |
| --- | --- | --- |
| `echo_literal` | `python src/echo.py hello` | stdout=`hello\n` 或与第一次变更一致的既有行尾；exit 0 |
| `echo_file` | 工作区放入 `samples/input.txt`（两行 `a`/`b`），`python src/echo.py samples/input.txt` | 打印文件两行；exit 0 |
| `echo_empty_file` | 空文件路径 | 空 stdout；exit 0 |
| `echo_missing` | 不存在的路径 | exit ≠ 0 |
| 工作区约束 | `Workspace.snapshot()` 的公开树 | 无网络配置、无计划范围外写入 |

主机执行：`ToolRuntime._execute_check`（时限 `CHECK_TIMEOUT_SEC=30`，输出封顶 `CHECK_OUTPUT_LIMIT=4000`）。回执字段：`exit_code`、`snapshot_hash`、`activation_id`、`effective_contract_hash`、`engineering_plan_hash`、`tree_changed`。

### 1.3 预期失败（比较时必须保留，不得从分母剔除）

1. 只改了文件读取、破坏了字面量 echo。
2. 内部复核写「没问题」，独立 QA 用空文件或缺文件打出反例（对应研究 OR-02）。
3. 两个子任务局部通过，接线后路径与字面量冲突（对应研究 OR-01）。
4. 探索阶段中途改验收口径（例如临时加入 stdin），把未事先固定的方案算成收益。

### 1.4 现有事件 vs 比较所需新事件

现有、四种组织都会用到：

| 事件 / 工件 | 类型或位置 | 本场景用途 |
| --- | --- | --- |
| 事项与 run 创建 | 项目层事项 + `EventType.RUN_CREATED`（含 `max_cycles`） | 根任务身份、循环上限 |
| 有效合同 / 计划 / 交付 | `CONTRACT_ACCEPTED`、`PLAN_ACCEPTED`、`DELIVERY_ACCEPTED` | 外层要求与整体成果 |
| 工具起止 | `TOOL_STARTED`、`TOOL_CALLED` | 写文件与 `run_check`；`name=="provider_usage"` 的同类型事件是用量记账，不是工具 |
| 提案拒收 | `PROPOSAL_REJECTED` | 合同或回执不绑定 |
| 用量尝试 | `MODEL_REQUESTED` / `MODEL_ATTEMPT_FINISHED` / `MODEL_ATTEMPT_FAILED` | 模型用量原始事实 |
| 检查回执 | `Workspace.record_check` → `receipts.jsonl` | 主机证据 |
| 暂停 | `RUN_PAUSED`（`max_cycles` / `model_steps_exhausted`） | 现有停止原因 |
| 质检 | `QA_SUBMITTED` | 外层独立验收 |

比较四种组织还需新增（名称只作文档标识，不规定实现）：

| 建议记录 | 回答什么 |
| --- | --- |
| `organization_selected` | 研发者预选的组织版本与依据 |
| `work_contract` | 2.2 六问的当时文本与要求版本 |
| `progress_target` / `progress_result` | 3.2 本次要消除的缺口，以及是否出现对应事实 |
| `budget_reserve` / `budget_settle` / `budget_unknown` | 3.3 预留、回执结算、未知用量单列 |
| `slot_held` / `slot_released` | 并发槽位占用与释放 |
| `internal_unit_started` / `internal_unit_finished` | 内部执行单元身份（非跨部门协作） |
| `integration_check` | 集成核验与冲突（OR-01） |
| `review_opinion` | 内部复核意见类型：主机反例 / 来源冲突 / 未验证怀疑 |

禁止用现有 `COLLABORATION_REQUESTED` 冒充工程内部子任务：`request_errors` 要求接收方是另一部门。

## 2. 组织一：单执行循环

适合：目标集中、成果难拆分、往返少（研究 3.1）。本场景里，文件输入与既有 echo 改同一文件、同一公开接口，可以一个人顺序做完。

### 2.1 执行故事（步骤表）

| 步骤 | 执行单元 | 输入 | 产出 | 检查 | 事件（现有 / 新增） |
| --- | --- | --- | --- | --- | --- |
| 1 | 工程负责人（外层） | 第二次变更事项、第一次采纳的 `src/echo.py`、有效合同 | 接收工作；预选「单执行循环」 | 合同哈希与工作区 digest 与基线一致 | 现有事项/run；新增 `organization_selected`、`work_contract` |
| 2 | 同一工程执行单元 | 合同、当前树 | `engineering_plan`：范围 `src/`，任务为改 `src/echo.py` 并跑四项检查 | `validation.py` 接纳计划 | 现有 `PLAN_ACCEPTED` |
| 3 | 同上 | 计划、`read_file` | 修改后的 `src/echo.py` | 路径在计划范围（`_begin_tool`） | 现有 `TOOL_CALLED`（`write_file`） |
| 4 | 同上 | 工作区快照 | 四项 `run_check` 回执 | 回执绑定当前 activation / 合同 / 计划 / `snapshot_hash` | 现有 `TOOL_CALLED`（`run_check`）+ `record_check` |
| 5 | 同上 | 回执与文件 | `delivery_spec` | `_accept_delivery` 拒绝无回执或文件缺失 | 现有 `DELIVERY_ACCEPTED` |
| 6 | 外层质检（不属于本组织内部） | 封存树 | 独立 `run_check` / `collect_evidence` + `qa_review` | 工程回执不得当作质检回执 | 现有 `QA_SUBMITTED` |

修正：某项 `run_check` 非 0 时，仍由同一单元改文件再检查。无进展规则见 2.3。

### 2.2 最小工作契约（研究 2.2）

1. **为什么做**：根目标是贯穿任务第二次变更；要求版本 = 本事项有效合同（含 1.1）。未纳入 stdin/多文件。
2. **由谁负责**：工程部门对外交付；内部只有一个执行单元。未接收前由提出该事项的产品/研发者跟进。异常升级：工程负责人 → 根任务控制（研发者取消或改合同）。
3. **交付什么**：`src/echo.py`；`delivery_spec.files` 含该路径；`check_names` 含 1.2 四项；证据为绑定当前快照的工程回执。
4. **可以做什么**：`tools_for("engineering")`：读写删移、`run_check`、提交计划/交付/协作。不可：`collect_evidence`、改产品合同、自报 exit_code。
5. **如何结束**：成功 = 计划接纳 + 交付接纳 + 外层 QA 放行。失败 = 合同不满足或主机反例未消。等待 = 本场景默认无外部等待。取消 = 用户取消，迟到工具无推进权。预算耗尽 = `max_cycles` 或 `model_steps_exhausted` 进入 `PAUSED`，或未来预算账耗尽。
6. **如何继续**：依赖第一次变更的采纳树；恢复位置 = 最后一致的计划/工作区/回执；动作核实 = 重读 `receipts.jsonl` 与 `TOOL_CALLED`，不假定超时等于未执行。版本 = 本 run 冻结的合同与计划哈希。

### 2.3 进展判断（研究 3.2）

本次要消除的缺口（写入新增 `progress_target`）：

1. 字面量行为是否仍在主机上成立。
2. 现存文件路径是否按行输出。
3. 空文件与缺文件是否符合合同。

无进展上限（样例，实施前可改）：同一 `progress_target` 连续 2 次结束看不到新回执、新反例或被接收的澄清，则停止局部循环，留下失败诊断与已知成果。不可满足的权限（例如要写计划外路径）立即报告，不等循环耗尽。

| | 例子 |
| --- | --- |
| 算进展 | `echo_file` 从无回执变为 exit 0，且 `snapshot_hash` 绑定当次写入 |
| 不算进展 | 只改写计划措辞；或对同一失败的 `echo_missing` 再调用一次相同 argv 的 `run_check` |

### 2.4 必须观察的额外成本与失败（研究 3.1）

| 3.1 项 | 如何在事件里看到 |
| --- | --- |
| 无进展重复 | 连续 `progress_result` 为无新事实；或相同 `run_check` argv + 相同 `exit_code` + 相同 `snapshot_hash` 重复出现 |
| 检查缺失 | `submit_delivery` 被 `_accept_delivery` 拒绝（`PROPOSAL_REJECTED`，字段 `check_names`）；或交付未列 1.2 某项 |
| 上下文增长 | `CONTEXT_ASSEMBLED` / 模型尝试的 `input_tokens`（`reported` 才计入合计）；压缩事件 `COMPACTION_RECORDED` 次数上升 |

研发者预选依据：单文件、单接口、子任务拆开后仍要改同一路径，分工的集成风险可能高于顺序执行。

## 3. 组织二：执行加内部复核

适合：已知遗漏多，复核可定位具体错误（研究 3.1）。本场景的空文件、缺文件、路径/字面量歧义属于这类遗漏。

### 3.1 执行故事（步骤表）

| 步骤 | 执行单元 | 输入 | 产出 | 检查 | 事件（现有 / 新增） |
| --- | --- | --- | --- | --- | --- |
| 1 | 工程负责人 | 同 1.1 合同 | 预选本组织；指定执行者与复核者（同一部门、隔离上下文） | 二者不能改对方工作区 | 新增 `organization_selected`、`internal_unit_started` ×2 |
| 2 | 执行单元 | 合同、基线代码 | 初稿 `src/echo.py` + 自测四项检查 | 同单循环的主机检查 | 现有写文件 / `run_check`；新增单元身份字段 |
| 3 | 复核单元 | 只读：合同、初稿树、执行者回执 | `review_opinion` 列表，每条标注类型 | 复核者可 `read_file` / `list_files` / `run_check`，不可 `write_file`（样例权限） | 新增 `review_opinion`；现有只读工具 |
| 4 | 执行单元 | 被采纳的意见（须引用意见 id） | 有限修正 + 新回执 | 修改必须关联意见 id 与新 `snapshot_hash` | 新增意见采纳记录；现有 `write_file` / `run_check` |
| 5 | 工程负责人 | 修正后树与回执 | 整体 `delivery_spec` | `_accept_delivery` | 现有 `DELIVERY_ACCEPTED` |
| 6 | 外层质检 | 封存交付 | 独立反例或放行 | 内部「通过」只是意见 | 现有 QA；对应 OR-02 |

复核轮次上限（样例）：1 轮有限修正。第二轮仍无新主机事实则按 3.3 无进展结束。

### 3.2 最小工作契约

1. **为什么做**：同一第二次变更合同；内部增加「对照 1.2 找具体遗漏」，不扩大功能范围。
2. **由谁负责**：工程负责人对整体交付负责；执行单元对初稿与修正负责；复核单元对意见类型与引用负责。未接收前责任不转移。升级：复核与执行争执 → 工程负责人，不得让复核代签 QA。
3. **交付什么**：与组织一相同的对外交付；另交付意见清单（类型、引用的检查名或合同句）。
4. **可以做什么**：执行单元同组织一。复核单元：只读 + `run_check`。二者均不可改合同、不可 `collect_evidence`（质检工具）。
5. **如何结束**：成功 = 有限修正后交付被外层 QA 放行。失败 = 意见为空泛且无主机反例却耗尽轮次，或执行拒绝定位意见又无反证。等待/取消/预算同组织一，复核耗时计入完整成本。
6. **如何继续**：依赖初稿树身份；恢复时先核验初稿 `code_tree_digest` 与意见 id；复核意见不是完成判定。

### 3.3 进展判断

本次缺口：

1. 执行者自测是否覆盖 1.2 四项。
2. 复核是否给出可定位项（主机反例或合同原文冲突），而不是「看起来可以」。
3. 被采纳意见是否对应新回执。

无进展上限（样例）：复核 1 轮 + 执行修正 1 轮；若复核只产出「未验证怀疑」且执行未补检查，计一次无进展。连续 2 次则停止。

| | 例子 |
| --- | --- |
| 算进展 | 复核用 `echo_empty_file` 打出 exit ≠ 0；执行修正后同名检查 exit 0，回执 `snapshot_hash` 变化 |
| 不算进展 | 复核只写「代码清晰、可以提交」；或执行按意见改注释、检查集合不变 |

### 3.4 必须观察的额外成本与失败

| 3.1 项 | 如何在事件里看到 |
| --- | --- |
| 同源错误 | 执行与复核的 `run_check` argv 集合相同，且都未包含事后 QA 打出的那一项；两条意见都未引用该检查名 |
| 空泛意见 | `review_opinion` 类型为「未验证怀疑」且无 `check_name` / 合同句引用 |
| 复核代替真实检查 | 出现「复核通过」记录，但没有新的主机回执，却直接 `DELIVERY_ACCEPTED` |

研发者预选依据：合同已点名空文件与缺文件，历史单循环容易漏；复核成本可接受，因为检查集合事先固定。

## 4. 组织三：独立分工后集成

适合：子成果边界明确、依赖少（研究 3.1）。本场景拆成两个隔离目录内的写入，再由集成责任写入共享的 `src/echo.py`。首批并发只覆盖独立只读与隔离目录写入（研究 3.3 末段）。

### 4.1 子任务划分（事先固定，运行中不得再拆无限层）

| 子任务 | 隔离产出 | 局部验收 | 不得做 |
| --- | --- | --- | --- |
| A 参数分类 | `work/a/classify.py`（或等价模块） | 给定「hello」→ 字面量；给定现存 `samples/input.txt` → 路径；给定不存在路径 → 路径且调用方应走缺文件 | 不实现整段 CLI 打印 |
| B 文件读取 | `work/b/readfile.py` | 读现存文件按行返回；空文件返回空序列；缺文件返回可区分错误，不抛未声明异常 | 不解析 CLI |
| I 集成 | `src/echo.py` | 1.2 全部检查；冲突时整体未完成，局部成功仍保留（OR-01） | 不在 A/B 目录并发改 `src/echo.py` |

### 4.2 执行故事（步骤表）

| 步骤 | 执行单元 | 输入 | 产出 | 检查 | 事件（现有 / 新增） |
| --- | --- | --- | --- | --- | --- |
| 1 | 工程负责人 | 合同、根预算剩余 | 原子预留 A、B 额度与各 1 个写入槽；启动 A、B | 两项预留之和 ≤ 剩余 − 收尾预留 | 新增 `budget_reserve`、`slot_held`、`internal_unit_started` |
| 2a | 单元 A | 合同中的参数规则、只读基线 | `work/a/*` | A 局部检查（隔离树） | 现有文件工具（未来在子工作区）；新增单元 id |
| 2b | 单元 B | 合同中的文件规则、只读基线 | `work/b/*` | B 局部检查 | 同上，并行 |
| 3 | 先完成者 | 自身局部交付 | 结束本单元；**剩余额度回到父可用池** | 不得私自开新工作花掉余额 | 新增 `budget_settle`、`slot_released`、`internal_unit_finished` |
| 4 | 超时或用量未知者 | 已发出的模型/检查动作 | 保留 `budget_unknown`，不按零记账 | 核实前不把预留分给别人 | 新增 `budget_unknown`；现有尝试状态 `failed` / 无 usage |
| 5 | 集成单元 I | A、B 封存树 + 合同 | 写入 `src/echo.py`（仅 I 可写该路径） | 1.2 四项；冲突则 `integration_check` 失败，整体不报完成 | 新增 `integration_check`；现有 `run_check` / `DELIVERY_ACCEPTED` |
| 6 | 外层质检 | 整体封存 | 独立验收 | 局部成功 ≠ 整体完成 | 现有 QA |

父取消：停发新分派；A/B/I 各自状态可见；迟到结果无推进权（研究 3.3「请求取消后结果迟到」）。现有 `cancel` 只作用于一个 run，传播到内部单元是待实施行为。

### 4.3 最小工作契约

1. **为什么做**：同一第二次变更；纳入 A/B/I 的边界如上。未纳入第三次去重。
2. **由谁负责**：工程负责人接收整体工作并选择本组织。A/B/I 各有责任人。A 未完成不把「分类已过」写进整体完成。升级：集成冲突 → 负责人，不自动生成第三层组织。
3. **交付什么**：对外仍是 `src/echo.py` + 1.2。对内：A、B 各有可取回树身份与局部回执。
4. **可以做什么**：A 只写 `work/a/`；B 只写 `work/b/`；I 写 `src/`。只读基线可并发读。权限仍受 `_begin_tool` 与计划 `scope` 约束；实施时计划范围必须事先包含这些目录。
5. **如何结束**：成功 = 集成检查全过且 QA 放行。失败 = 集成冲突或局部不可用且无替代。等待 = 子单元用量未知时的核实。取消 = 父取消后子状态分别记录。预算耗尽 = 任一量纲耗尽即停止新增分派。
6. **如何继续**：依赖 A/B 内容身份；恢复时分别核验局部树，不重做已证明有效的局部检查（研究 10.1「并行节点之一失败」）。未知外部动作先核实。

### 4.4 进展判断

负责人层缺口：A 局部验收、B 局部验收、集成四项检查是否出现**新的**主机事实。

A 的缺口：字面量 vs 路径分类是否有回执。B 的缺口：读文件三类结果是否有回执。I 的缺口：1.2 是否在**集成树**上成立。

无进展上限（样例）：每个子单元自身 2 次；负责人层在「两局部已完成但集成无新回执」上 2 次。局部已完成的单元不再计数消耗无进展额度。

| | 例子 |
| --- | --- |
| 算进展 | B 首次对空文件给出可区分错误回执；或 I 的 `echo_literal` 从失败变为 exit 0 |
| 不算进展 | A、B 互相改计划依赖而不改隔离树；或 I 重复跑与上次相同失败的同一组检查 |

### 4.5 必须观察的额外成本与失败

| 3.1 项 | 如何在事件里看到 |
| --- | --- |
| 集成失败 | `integration_check` 失败；A/B 的 `internal_unit_finished` 仍为成功；整体无 `DELIVERY_ACCEPTED` 或交付被拒 |
| 重复劳动 | A 与 I 都实现了读文件；两边 `write_file` 路径语义重叠可审计 |
| 并行写冲突 | 两个单元的 `TOOL_CALLED` 写同一相对路径（本样例禁止写 `src/echo.py` 的除 I 以外单元；若发生即失败样本） |
| 协调时延 | 墙钟：从 A、B 均 `slot_held` 到 I 首次检查的间隔；对比单循环步骤 3–4 的墙钟 |

研发者预选依据：分类与读取可以隔离验收；集成责任单独指定，用来对照单循环是否更便宜。

1. **为什么做**：同一第二次变更；纳入两个已命名接口；未纳入 stdin、第三候选。

## 6. 比较口径（研究 9 + 实验协议第 8 节）

### 6.1 实验单位

- 基本样本：本事项（第二次变更）的一次完整三部门 run（或 Stage 2 项目事项下的一次 run）。多轮返工、重评、随机重复**不**算新的独立任务；随机重复只描述波动（研究 9.1）。
- 比较组：当前有效方案（三部门单循环，工程内部无子组织）、本文件四种研发者预选组织、必要时再加一个「人工静态清单」（2.2 的研发者手写步骤，不跑内部 Agent）。
- 固定：1.1 要求、1.2 检查、工具授权（`tools_for` 现状 + 若 3.2 已加工具则四种组织同一工具集）、环境、根预算数字。模型升级或多给预算则**分层报告**，不并入组织收益。
- 对照任务（实验协议第 8 节「无法分解的对照」）：建议另备第三次变更或「只修一处打印错误」；本文件不展开，避免和主样本绑死。

### 6.2 先质量、后成本

质量先决：外层 QA 按 1.1/1.2 放行或明确失败。错误放行不得用平均时延下降抵消。失败任务的耗时与费用仍计入。

成本计入：候选生成（探索）、无效实验、失败重试、协调、内部复核、集成冲突处理、评价、观察。技能展开成本记在技能样例，不记入本比较，除非某组织实际调用了技能。

实验协议第 8 节「部门子循环」：

| | 本样例对应 |
| --- | --- |
| 最小通过证据 | 责任人可指到事件；聚合检查 = 1.2 在集成或单树上执行；根预算表可核对；取消后子状态可见 |
| 不足以通过 | 只展示多个模型同时输出，而无接收、无聚合检查、无预算账 |

相关 OR：OR-01（集成冲突）、OR-02（内部过、QA 反例）、OR-03（最后一份额度）。

### 6.4 Stage 2 的 2.1 基线形成后如何执行本组比较

研究第 11 节：组织比较样例的接入时机是「第二阶段正式基线形成后执行比较」。路线图第 4 节：先由研发者设计并比较有限组织；本阶段交付执行能力，第四阶段才让系统自提组织。第三阶段计划：比较实验的**执行能力**在 3.6，依赖 3.4 并行与预算账。
