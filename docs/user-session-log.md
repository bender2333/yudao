# 用户使用记录

本文件记录以用户身份实际使用 Yudao 时遇到的问题。记录先于修复：问题先登记，再由架构师分诊、拆工单。

记录格式：`编号 / 日期 / 场景 / 现象 / 复现步骤 / 初判 / 状态`。

## 这一轮走查的概览（2026-10-21 至 2026-10-22）

范围：主实例上 7 个项目（含 2 个归档试验项目）、19 个事项（17 个走到放行采纳、2 个被停止），另有一个**干净数据目录的实例**（新装的 Yudao）上 9 个项目、10 个事项；13 个页面与几十条可点路径；真实模型 9router 的 `ds`（deepseek-v4.1-flash，Chat Completions），三部门绑定同一模型。**这一天的走查已整理成工单 #629 的验收记录**（环境、各段用时、质检结论、指导与重启各一次、25 张工单，以及还差的两处：没有走 wheel 的发布验收、没用评测场景 3 的输入因而没有评分器可对照）。

发现的问题 31 张，其中 **14 张已合入并由走查的人在页面上复验过**：#652（两个输入框共用一份状态）、#653（初次连接误报「连接中断」）、#654（PRD 各版状态）、#655（动作列表的「登记名」）、#656（用量只显示总数）、#659（新开标签页卡在「正在读取数据」）、#664（事件种类漏登记中文说明，事件流断掉）、#669（事件载荷里带不再生效的窗口）、#670（部门消息没有正文）、#672（归档以后取不回来）、#697（旧事件读不懂，事件流在第 5 条上断）、#701（顶栏的「待你决定」计数，涨与落都跟着走了）、#674（改了部门设置／置顶／归档以后，项目设置页自己更新）、#702（三个系统页的顶栏路径改成中文页名）。

剩下这几张看着各说各的，落到同一个形状上：**数据在某处已经变了，界面或读模型没跟着变**。区别只在修法：#684 要的是「重建读模型或者按需重算」，#677、#683 要的是核对口径，#679 要的是退避策略。

**#704 是另一个形状**：它不是「该更新的没更新」，而是「整个界面停住了，而且提示指向一条无效的操作」。这一条是 2026-10-22 下午**自己撞上**的——main 上有人把服务端接口版本从 6 提到 7，本地 `harness/release_assets/` 里的页面文件还是上一次构建的产物，页面立刻变成完全不可用。查工单时发现 #374（发布版本不同时页面重载）已关闭且只覆盖「发布版本不同」，而设计说明第 5.1 节那句「页面与服务的版本总是相同」在从源码运行时不成立。**「版本」在这套设计里有两个含义，代码只拿其中一个做判断。**

**#707 又是另一个形状**：不是数据没更新，是**页面上两句话互相打架**——状态写「已停止」，原因写「已完成基线核验」。用户放弃的操作没有被记住。

**#721 又是另一个形状**：**「放行」是一个没有范围的说法**——质检说它验过了，评分器说 4 项不对。差别不在质检不认真，而在**它自己写的检查覆盖不到 PRD 的每一条需求**。**第三次运行（U65）把这一条的结论换了一个形状**：三次并排后可以确定，**线路偏好（R3）是质检从来没覆盖过的那一项**（第 1、3 次都做错、都放行、都没抓到），而**第 2 次 R3 之所以对，不是因为那次质检更严**——那次退回的是 `max_transfers`，**返工那一轮顺带把 R3 也改对了**。所以 **R3 的检出完全靠评分器、不靠质检**。修法因此不能停在「让质检更认真」，要指向**按需求条目建立覆盖对照**。

**#716 又是另一个形状**：**同一条拒绝路径的不同分支，给用户的说法语言不一致**。源目录里含宿主私有目录时是全中文的，含链接时却是「中文 + 英文 + 英文」，**而且用户唯一需要的那句「该怎么做」是英文的**。

**#715 又是另一个形状**：**信息在，人看不到；而且归因说错了**。服务端把 Provider 的状态（`available` 与中文说明）都放进 `system.status` 了，**客户端却只有模型管理页在用**，首页与顶栏一个字都不说；而服务端那条说明说的是「尚未配置 Provider」——**实际是绑定的那个模型解析不到了**，用户照这句话去模型管理页「完成服务接入」，那里早就配好了。

**#714 又是另一个形状**：**错误被说成了事实**。服务端读某份交付的原文时抛了业务异常（git 记录与事件材料对不上）并返回 500，页面上却显示「这一版没有留下原文」——**原文是在的**，用户被告知了一件与事实相反的事，而且界面上没有任何失败提示，从页面上完全看不出出事了。

**这一条的根因比工单记的更靠里，而且范围比工单记的更大**（U64）：把请求拦成 500 逐个入口量过以后，**资料页有两处不同的情况**——PRD 的「查看原文」失败时写「这一版没有留下原文」，**交付的「查看内容」失败时那个展开框完全空白**（只有标题与「收起」按钮，**连「没有内容」都没有**）；**首页的项目列表失败时说「没有符合的项目」「还没有项目」**。三处的根因是同一处：`useSnapshot` 在查询失败时把状态设成 `{data: null, loading: false}`，**与「本来就没有」在返回类型上完全一样**，而错误在更上游的 `view-sync.ts` 第 59 行被 `catch { }` 整个吞掉了。资料页那两处由 #714 做，其余由 #728 做。

**#713 又是另一个形状**：**页面上写着内部机器词**。模型服务不可用时冒出来的那张决定卡片，标题、说明、选项、跳转链接都做得很完整，偏偏「原因」一栏写着 `provider_unavailable`（2026-10-22 用户决定可以直接显示原始标识，**这一条已按 wontfix 关闭，不再算缺陷**）。

**#709 又是另一个形状**：不是数据没更新，是**后端有、界面没有**。写回命令在后端已经做完并合入（#347、#542、#661），可是页面上一个入口都没有——用户走完「接入已有项目 → 确认初始 PRD → 采纳」，**成果回不到自己的代码目录**，而且**页面上没有一句提示说「还有一步没做」**。这一类是用户永远不会主动报的：他不知道后端有什么，只有把两边的清单摆在一起比才看得见。

**这一轮走查的最大一个归纳（U58）**：今天新找到的缺陷里，**多数的根因不是「算错了」或「没做」，而是「记录得细、解释得少」**：

- **#704**：页面与服务对不上时，提示只给了一个无效的「重新加载」，没说该重启服务还是重建页面（两种情形修法相反）；
- **#713**（2026-10-22 起按用户决定不再算缺陷）：决定卡片把 `provider_unavailable` 摆出来，其实是**多给了信息**，不是缺陷；
- **#715**：Provider 的状态与中文说明**服务端给了、客户端一个字都没显示**，用户点了才知道；
- **#721**：「质检放行」没有范围，质检复算了路径、没复算票价边界，用户无从知道放行覆盖了哪些。

**但要说准（U60）**：2026-10-22 用户决定「页面直接显示原始标识与原文，不再要求翻译」，**所以缺的不是翻译**。缺的是**该说的结论没说**：**① 有些状态字段界面上一个都没用**（`system.status` 的 `provider.available`——服务端给了状态与中文说明，界面一个字都没有）；**② 读取失败被说成「没有内容」**（#714 资料页两处、#728 其余页面；**根因在共用读取层**，不是某一处文案写错）；**③ 原因说错了**（#715 把「绑定的模型解析不到」说成「尚未配置 Provider」）；**④ 提示没给下一步**（#704 只给了一个无效的「重新加载」）；**⑤ 结论没有范围**（#721 的「质检放行」没说覆盖了哪些要求）。**⑥ 读不出来的时候说的是「没有」**（#714／#728：失败与「本来就没有」在读取层的返回类型上就没有区分，用户被说服了而不是被提醒了——**这是前五件里唯一一件「说了一句假话」的**，前五件都是「该说的没说」）。

**系统把「发生了什么」记得很细**（事件日志、字段、哈希、原因标识都在），**但常常没把它翻译成人看得懂的一句话**——要么那句话没写，要么写了一半（#716 的中英混排），要么没有范围（#721）。**这一类问题的共同修法是同一件事：把「事实」翻译成「人该知道的结论，包括它的边界」。**

**下午又找到一层更具体的形状（U64–U68，六处）**：**根因不是「没有」，是「已经有了（或只差一步），但没有接到使用它的地方」。**

- **#721**：**基线核验**（`baseline_review`）要求「PRD 的每条要求一条结论，不许多也不许少」，**普通质检**（`qa_review`）没有这个要求——**同一份合同文件里两处严格程度不同**；
- **#729**：**产品与工程**的上下文里有 `qa_defects`（上一轮的质检缺陷），**质检自己看不到**——**同一个机制在三个角色手上不一样**；
- **#730**：**排空、强制升级、磁盘空间都已经在那一页上了**，`system.status` 里也有排空状态，**但侧栏入口的条件用了 `runtime.slots` 这个还不存在的查询**——**做出来了，用户进不去**；
- **#731**：**排空有开始、没有结束**（目录流里没有「排空已结束」这种事件），**升级只恢复一次，第二个事项又要再重启一次**；
- **#728**：**失败信息其实产生过**（`view-sync` 把它整个吞掉、`useSnapshot` 把它变成「没有内容」）——**读不出来的时候说的是「没有」**；
- **#723**：`execution.slots` **登记了、能改、有变更记录、页面上还显示着**，**但代码里一次都没被读过**。

**这六处的修法是同一件事：把「已经有的那一份」接到「该用它的地方」，而不是新造一套。****上午那五件是「缺」，下午这六件是「没接上」——后者更好修，因为料已经在手上了。**

**还有三件是「说了一句假话」**：#728（读不出来说成「没有内容」，用户被说服而不是被提醒）、#732（质检的结论用越南语写，用户在自己的项目页上读不懂为什么不能放行）、#733（**「排队中」这个词在应用里指两个状态**——楼层写「排队中」、看板卡片写「未开始」，而服务端的 `held` 是「采纳成果被挂起」，与排队无关）。**这三件比前面那些更重**：前面是「该说的没说」，这三件是「**说了一句错的话**」；**而 #733 更基础——不是某一处写错了，是同一个词在应用里指了两件事**，五处代码都通顺，只是不在任何一处写着「这个词指什么」。

**走查手法这一轮又添了三条**：① **在浏览器里把请求拦成 500**，比造真的服务端故障更快也更可控，而且走的正是失败路径——**但拦完要读那一处的 DOM 全文与 HTML**，空白框是「什么都没有」，截图上看不出来（U64）；② **把三个角色的「同一类能力」摆在一起比**——同一个机制在三个角色手上往往不一样，**这种不对称在代码里不报错、不报警、只在结果里显形**（U66）；③ **逐个读同一类文字的多个样本**，比读一个样本有用——只看一个会以为「都是中文」（U68）。

一条重要的更正（U26）：这一轮中间有一段时间，页面在新开的标签页里一直加载不出来（侧栏「项目 0」、主区「正在读取数据」、顶栏「连接中」），当时记成了产品缺陷。**那是我用的那个嵌入式浏览器会话被后台冻结造成的**（请求发出去了、响应到了却不被处理，界面停在最后一次绘制）。换一枚全新的浏览器打开，一切正常。#659、#664、#697 在那之后都陆续合入，也都是用新的浏览器复验的。教训记在 U26：**同一件事要用另一条路再量一遍，换一枚浏览器、换一份数据、换一个维度。**

**#697 也已于 2026-10-22 合入（c6837c29）**：事件流不再断（各个起点都能连上，第 5 条也照送）。但**页面仍然用不了**：刷新首页以后侧栏「项目 0」、主区「还没有项目」、两节「正在读取数据」、顶栏「连接中 · 正在建立事件流」；服务端日志里页面发的查询都答 200（接口里 5 个项目都在），事件流订阅也**只有一条**、连上以后没有断开没有重连。与 #697 修好前不一样的是：**重同步的循环没有了**（以前每秒一轮，现在是一条连接挂着），但界面仍然不更新——查询的响应到了没有落进界面，事件流连上了也没有变成「已连接」。复测见 U25，已经补到 #659 的评论里。

**结论：现在剩下的只有浏览器这一侧。** 服务端（事件流、查询、读模型）已经全部核对过是对的；客户端的应用层用客户端自己的模块在 Node 里连真实服务也是对的（三个视图 0.2 秒落地、25 秒零重同步）。差别只出现在浏览器里。

**更正（见 U26）：上面这段判断是错的。** 换一枚全新的浏览器打开，页面完全正常（顶栏「已连接」、5 个项目、楼层与报告都渲染、0 错误 0 失败请求）；那些症状是我这边那个浏览器会话被后台冻结的样子，不是产品的缺陷。#659 关掉是对的，已经给它补了更正评论。**被 #664 挡过的那几条路径，随后都用新浏览器在页面上重走了一遍**（见下面「走查中确认正常」里的四条）。

**#659 也已于 2026-10-22 合入（c9cf1662）**，客户端不再退回位置 0（实测重订阅位置停在 4）。但页面**仍然**加载不出来，原因是另一条新问题 **#697**：#636 至 #638 删掉旧协作请求机制以后，事件日志里 7039 条有 6561 条（93%）读不懂（载荷模型删掉了 `request_id`、`collaboration_request_id` 等字段，而载荷基类不允许多余字段），事件流在第 5 条上就断，客户端每秒重订阅一次。实测与证据见 U23。**这一条修好以前，页面上的路径全部走不了**；#664 与 #697 是同一类要求的两面——事件流对读不懂的事件必须容错，不能因为一条事件把整条历史作废。

另一条是 **#672**：勾上「显示归档的项目」以后已归档的项目仍然不出现，「恢复项目」永远点不到——归档这个可逆操作在界面上变成了单向。

## 过渡期的现象（不另开工单）

产品当时无法当场修订合同。工程部门发现合同自相矛盾后用旧协作请求通道（`request_type: consultation`）问产品，产品两次提交 `product_spec` 与 `product_decision` 都被拒（`product cannot issue product_spec / product_decision in the current work`）。原因：

- `harness/collaboration.py` 第 47 至 48 行：产品能提交 `product_spec`，只在协作请求是 `request_type == "action"` 且 `action == "revise_requirements"` 时；咨询类请求不授予修订合同的权限。
- `harness/validation.py` 第 118 至 124 行：阶段闸门先于上面这条判断。
- 新询问机制没有这个限制：`harness/validation.py` 第 119 至 122 行，`active_ask` 的收件方是 product 时允许提交 `product_spec`；`harness/tests/test_ask_branch.py` 的 `test_ask_answer_with_spec_revision_continuous_work` 覆盖了它。
- 本次运行 `run.asks` 返回 0 条询问：模型在 `ask`（新）与 `submit_request`/`submit_response`（旧）两套通道之间选了旧的那套。

这是 #636（删除协作请求的工具、提案、规则与提交校验）合上以后的过渡状态，模型只剩一条通道时不会选错。新机制本身可用且有测试覆盖。等 #636 至 #639 合并后再走一次，确认产品能在询问回答里当场修订合同。
