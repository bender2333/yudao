- **来源事件**：门牌与箱子用投影里记下的事件编号（`WorkItem.event_id`、`Adoption.event_id`）；轮次取这个 run 的第一条事件
  （`run_created`）；已用时间取这个 run 的最后一条**登记过**的事件（测试往 run 流里写的标记事件不在来源表里，跳过往前找）；
  包裹取交付的 `created_event_id`；盖章取回执的 `created_event_id`。位置由事件日志按编号给出（`store.get_event` /
  `get_project_event`），同一份事件序列得到同一个位置。
- **试过、撤掉的做法**：把位置在折叠时记进投影（`WorkItem.position`、`Adoption.position`）。写入路径在折叠新事件时
  还没有全局位置（位置在提交时才编号），保存的投影里记成 0，而重放得到真位置，`replay.check` 立刻报出
  `work_items`、`adoptions`、`current_adoption.position` 三处不一致。所以改成「投影记事件编号、位置按编号从事件日志取」：
  回放与恢复以后同一个编号给出同一个位置，`replay.check` 保持一致。
- **修掉 main 上的硬失败**：`test_overlays_list_only_when_every_dependent_query_is_registered`（main `8c8b196b` 的集成层

## 第 3 轮补记（分支集成层第一次跑出来的问题）

deepseek-v4.1-flash / 2026-10-30 11:00 / 分支集成层（run 40992670629）报了 `test_query_refresh_lists.py::test_every_event_that_changes_a_query_is_listed_in_one_of_its_two_lists`：
`project.loop` 的两份清单里没有 `artifact_invalidated`，而它改变了 `work_items.*.refs.elapsed.position` 与 `source`。
根因是「已用时间」的来源原来取这个 run 的最后一条事件：任何一条事件都会换掉它，刷新清单于是永远列不全。
改成取**最后一条结算类事件**（`activation_finished`、`run_done`、`run_paused`、`run_failed`，从最后一条事件往前按 200 条一批找，
正常运行时不到一批就找到；还没有结算过时来源是开 run 的第一条事件）：按时限与结算的语义这是「已用时间在结算时更新」，
四类事件都已经在 `project.loop` 的刷新清单里，清单与依赖因此一致。`test_query_refresh_lists.py` 4 项通过。
这一处是刷新清单这条缝替本单抓出来的：新增的查询字段如果依赖了不在清单里的事件种类，集成层会报出来，不能靠放宽清单解决。
