# 工单 #553 执行日记

角色：执行者（9router/ag/gemini-3.8-flash-high）
工单：#553 [循环结构] 询问分支的用量上限、没能回答与重新启动
分支：`issue-553`

## 1. 规格与范围

依据：`docs/design/department-loop.md` 第 4.5、4.7、9 节，`docs/adr/0031-declared-loop-layers-and-sub-loops.md`（main 97488db4）。

要做的：
1. 分支的上限取被询问部门的声明值与提问方剩余量中较小的一个（模型步骤数与时间，按 ADR-0031 子循环的规则），用量计入提问方。
2. 达到上限或模型反复不提交回答（连续只回复文字的次数用现有的规则参数）时，分支以没能回答结束：写 `ask_answered`（结果为没能回答，写明原因），原因作为提问方那次 `ask` 调用的工具结果，提问方接着工作。
3. 分支进行中重新启动 Yudao（在同一个数据目录上新建 `LoopSystem`）：分支从事件重新装配后继续，回答交回提问方。提问方在重新启动以后仍然停在 `ask` 调用上，收到回答后接着工作。
4. `ask_answered` 的载荷增加提问方 `requester`、被询问的部门 `recipient`（取自对应的 `ask_started`，与它相同）、结果 `status`（`answered`、`unable`）与没能回答的原因 `reason`（已回答时为空）。`harness/app/payloads.py` 的 `AskAnsweredPayload`、`harness/tests/event_sequence.py` 中 `ask_answered` 的 `KEY_FIELDS` 同步；接口合同、openapi 快照与客户端生成的类型随之更新。

## 2. 执行过程与关键决断

1. **载荷合同与事件字段同步**：
   - `harness/app/payloads.py`：`AskAnsweredPayload` 补充 `requester: Department`、`recipient: Department`、`status: Literal["answered", "unable"]`、`answer: str = ""`、`reason: str = ""`。
   - `harness/tests/event_sequence.py`：`KEY_FIELDS["ask_answered"]` 更新为 `("answer", "reason", "recipient", "requester", "revision", "status", "with_spec_revision")`。
2. **限额计算与用量折叠（ADR-0031）**：
   - `harness/engine.py`：`StepLimits` 扩展 `department_max_model_steps: Mapping[str, int]` 支持部门级声明步数上限。
   - `StepDriver` 在 `_steps` 循环内记录已用步数 `_consumed_steps`，在发起 `ask` 时将提问方剩余可用步数传给控制核心；询问分支返回后，将分支消耗的步数累加至提问方的已用步数中，确保子循环步数完整计入提问方额度。
   - `harness/orchestrator.py`：`_execute_ask` 计算 `branch_max_steps = min(declared_steps, remaining_steps)`。若上限 `<= 0`，分支立即以 `unable` 结束并写明原因。分支运行结束或遇到 `Stopped`（如 `model_steps_exhausted`、`no_tool_call` 等）时，写入 `ask_answered`（`status="unable"`, `reason=...`），原因作为 `ask` 工具的失败结果交回提问方。
   - `_run_ask_branch` 记录分支结束事件 `ACTIVATION_FINISHED` 时的 `elapsed_ms` 继承当前 run 累计耗时，并在 `_recover_run_usage` 时取各激活结束事件 `elapsed_ms` 的最大值，防止分支子会话重置全局累计时钟。
3. **跨进程中断与重新启动恢复**：
   - `harness/orchestrator.py`：在 `_await_unknown_actions` 中排除 `ask` 工具，避免进行中的询问分支被误当做 unknown 动作写入 `handed_back`。
   - `harness/engine.py`：在 `_unexecuted_calls` 中放行仅有 `TOOL_STARTED` 的 `ask` 工具调用；并在 `_begin_tool` 中做幂等保护，如果事件流中已有相同调用 ID 的 `TOOL_STARTED` 则不重复写入。
   - `_execute_call` 补充 `name == "ask"` 分支，使提问方恢复时能重新进入 `_nodes.ask`；`_execute_ask` 发现当前有进行中的 `active_ask` 时直接重用原 `branch_session_id` 继续驱动分支会话。
   - 修复 `_is_handoff_session`：仅当工程部门是被询问方（`recipient`）时才剥夺其持有交接的运行工作区身份；提问方工程部门在恢复后保持使用运行工作区，避免文件写入落入临时检查目录。
4. **测试与基准更新**：
   - `harness/tests/test_ask_branch.py` 扩充用例：测试双方与状态字段、分支步数耗尽以 unable 结束且用量计入提问方、分支无工具回复以 unable 结束、跨进程终止后重启自动恢复并放行完成。
   - `harness/tests/event_scenarios.py` 新增 `ask_branch_exhausted` 场景并注册到 `SCENARIOS`。
   - 运行 `--write-event-baselines` 重新生成 `ask_answer_with_spec_revision.json` 与新增的 `ask_branch_exhausted.json` 基准。
   - 运行 `--write-openapi-snapshot` 重写 OpenAPI 快照并在 client 中执行 `npm run generate:api`。
