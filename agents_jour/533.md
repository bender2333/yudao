# 工单 #533：依赖说明总长度的测试改为按实测 token 数推出窗口

## 背景与目标

按 `docs/design/test-pyramid.md` 第 10 节第 3 条与第 11.1 节最后一段：
依赖固定材料（部门提示、规则、提案合同、工具清单）总长度的测试，其上下文窗口与阈值
改为由实测 token 数推出，不再随工具说明与部门提示的长短变化；token 估算的计算补直接单元测试。

只改 `harness/tests/helpers.py`（只追加）、`harness/tests/test_context.py`、
`harness/tests/test_compaction_engine.py`、`harness/tests/test_compaction.py`（只加 token 估算单元测试）。
不动 `harness/definitions/tools.json`、`harness/context.py`、`harness/compaction.py`、
`harness/models.py`、事件序列基准与场景。

## 基线失败证据（改动前）

把 `harness/definitions/tools.json` 的 bash 说明加长一倍后运行旧测试：

```
assert 3698 <= 3600
harness/tests/test_context.py:476
```

即 `test_narrow_window_work_request_spends_the_window_left_after_its_input`
把输入估算写死上限 3600，说明一变就超。同批 `test_compaction_engine.py`、
`test_compaction.py`、`test_assembly.py`、`test_smoke.py` 通过。

## 实现

### 步骤 1：`harness/tests/helpers.py` 追加 `pinned_input_tokens`

```python
def pinned_input_tokens(system, run_id, department="product") -> int
```

- 用 `system.project(run_id)` 取投影，`ContextAssembler(system.artifacts).assemble(...)` 装配
  版本 0 的 `DepartmentPrompt`（提示词取 `DEFINITIONS.role(department).prompt`，
  先经 `save_department_prompt` 落成工件拿 `prompt_ref`）。
- 窗口传 `1_000_000`，避免装配本身因窗口失败；历史为空，只测不带历史时一次工作请求的输入。
- 返回 `assembled.manifest.input_token_estimate`。
- 只追加，不改任何已有函数。

### 步骤 2：`test_context.py::test_narrow_window_work_request_spends_the_window_left_after_its_input`

- 先在 `tmp_path / "pinned"` 子目录用宽窗口（`context_window=1_000_000`）的 `_bound_system`
  建一个 run，测出产品部门的 `n`；`window = n + 4096 + 512`。
  - 子目录的原因：`_bound_system` 里第二个 `LoopSystem` 默认 `resume_on_startup=True`，
    同一数据目录会在启动时自动激活第一个未结束 run，耗尽只有三段的回放脚本，
    报 `IndexError: list index out of range`。
- 再用该窗口建 run 跑 `activate_once`。
- 断言：`n <= input_token_estimate <= n + 1024`；
  `max_output_tokens == min(4096, window - input) == 4096`；
  `max_output_tokens > response_reserve(window, 4096)`（不在测试里复制预留公式，直接调实现）；
  `output_reserve_tokens == max_output_tokens`；`admitted is True`；
  `capture.requests[0]["max_output_tokens"]` 与载荷一致；`model_input_audit` 为 `verified`。
- 去掉 `2000 <= ... <= 3600` 与「旧的固定 15% 预留只给 1200」的注释。

关键数值（bash 说明加长一倍状态）：`n = 3314`，实际 `input_token_estimate = 3698`，
`window = 7922`，`response_reserve(7922, 4096) = 3961 < 4096`，admitted `7794 <= 7922`。

### 步骤 3：`test_compaction_engine.py` 两项

`test_empty_summary_does_not_fail_the_run_and_department_continues` 与
`test_empty_compaction_summary_allows_retry_on_next_activation`：

- 先建一个临时 run（`context_window=1_000_000`）测 `n`，再建真正的 run：
  `window = n + SUMMARY_OUTPUT_TOKENS * 2`。
  - 余量依据 `harness/compaction.py::plan_compaction` 的约束：
    `summary_limit = min(4096, max(1, window//10), max(1, (threshold - pinned)//2), output_reserve)`
    至少 32，以及 `context_window >= 2 * SUMMARY_OUTPUT_TOKENS`（8192）时的摘要提示词预检。
- 大文件字符数改为窗口的 8 倍：`"TOOL_OUTPUT " * (window * 8 // 11)`，
  读取后一定超过窗口，保证触发压缩。
- 删掉「合并 #471 拉长 submit_* schema……4000 窗口的固定区超过压缩预算」这段注释，
  改为说明窗口如何由固定材料推出。
- 断言不变（phase != "FAILED"、无压缩事件、至少一次工作请求与一次压缩请求）。

### 步骤 4：`test_compaction.py` 加 token 估算单元测试

两项：`test_estimate_tokens_counts_characters_not_bytes` 与
`test_estimate_tokens_rounds_up_in_groups_of_four_characters`。

- 期望值全部写成具体数字（空串 0；1–4 字符 1；5 字符 2；8 个中文字符 2；
  100 字符 25；4001 字符 1001），不在测试里复制实现公式。
- 反向验证：把 `harness/models.py::estimate_tokens` 临时改为 `max(1, len(text) // 4)`
  后两项都失败，还原后通过。用文件编辑改回，未用 git 回滚。

## 结论

窗口与阈值现在由 `pinned_input_tokens` 实测推出，与工具说明、部门提示的长度解耦；
`estimate_tokens` 有直接单元测试。工具说明加长一倍时，`test_narrow_window...`
从失败（`assert 3698 <= 3600`）变为通过。
