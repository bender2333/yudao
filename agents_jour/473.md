# 工单 #473：嵌套询问与询问链

依据：[三部门的循环结构](../../docs/design/department-loop.md)第 4.4、4.5 节与 [ADR-0039](../../docs/adr/0039-departments-work-from-watched-outputs.md)。分支：`issue-473`，worktree 在 `D:/codes/yudao-worktrees/issue-473`，起点是 main 的 `d2213a99`。

## 记录

执行者 minimax-M3.1-Flash / 2026-10-24 /

1. 核对现象（第一轮做了一半，推上去的提交 `6d8b42e8` 集成用例不绿）：
   - 投影里只有一个 `active_ask`，装不下嵌套：外层的产品分支回问工程时，内层的询问没有地方放；工单要求的链上层数（默认 3）没有地方读。
   - 工单正文要求「回问在被问部门那里另开一个询问分支，不送进它正在等待的会话」，而当时的代码按**部门**判断是不是在分支里：同一部门的主线会话与分支会话分不开。
   - `harness/engine.py` 的 `_unexecuted_calls` 按部门找「上次没有处置完的工具调用」。嵌套分支一激活，就把外层主线那次还没结果的 `ask` 调用当成自己的补执行，于是系统自己多开了一层（工程 → 产品），现场是 `ask_started` 出现三层，链路外的脚本用尽后事项失败。
   - 检查工作区按**部门**建目录（`inspections/<run_id>/<部门>`）。同一部门的主线会话与分支会话同时在场时，分支的建立与清理会删掉主线的检查工作区；嵌套一轮以后质检分支结束时主线的工作区已经不在，事项以 `FileNotFoundError` 结束。
2. 口径（三条）：
   - **询问归属于发起它的会话**。投影里的询问是一个栈（`ask_stack`），每层记着发起它的会话（`origin_session_id`）与分支会话（`branch_session_id`）；回答按分支会话弹出对应那一层，外层继续等。
   - **层号按会话在链上的位置算**：主线是 0，分支是它回答的那次询问的层号，发出询问的会话是它发出的那次询问的层号减一。上限从规则登记 `organization.ask_chain_max_depth` 读（默认 3，bounds 1 至 6，kind structure，form boundary），不写死在代码里。
   - **检查工作区按会话一个**（[本地通用工具设计说明](../../docs/design/local-tools.md)第 2 节本来就写的是「每个会话一个」）。路径的最后一段从部门改成会话标识：主线会话与它在询问分支里的会话各用各的，互不删除对方的目录。
3. 实现：
   - `harness/models.py`：`RunProjection` 的 `active_ask` 换成 `ask_stack`（每个字段一个 dict），加 `branch_sessions`；新增三个只读方法：`ask_by_origin`（这个会话发出的、还没回答的询问）、`ask_by_branch`（这个会话是哪一个询问的分支）、`ask_position`（这个会话在链上的层号）。
   - `harness/projection.py`：`ask_started` 记下发起它的会话；`ask_answered` 按分支会话弹出那一层；**分支会话的激活不改部门主线的会话记录与最近激活**（主线的检查回执按主线的激活编号核对，分支的激活编号原来会把主线的覆盖掉，主线随后的交付被判「没有这一次的检查回执」）。
   - `harness/adjudication.py`：`ask_chain_decision(position, limit)` 是纯函数，超过上限时给出「链已有几层、上限是多少、把要问的内容写进回答」；`_ask_branch_permission` 与 `offered_tools` 按**会话**判定是不是在分支里，分支里的 `ask` 在层数允许时提供；`tool_permission` 增一个 `session_id` 参数。
   - `harness/engine.py`：`_begin_tool` 传会话；`_unexecuted_calls` 的补执行范围收窄到**这次激活自己的会话**（原来是整个部门），分支不再接手主线没处置完的调用。
   - `harness/orchestrator.py`：`_execute_ask` 的恢复路径按会话找自己那次没结束的询问（原来按部门找，内层回答后外层会另开一层）；分支的步数按分支会话与它开出的下一层一起算（`_branch_steps`），用量逐层计入最初的提问方。
   - `harness/assembly.py`：分支的历史里去掉外层会话还没结果的询问调用那一段（同一个部门的嵌套分支才会遇到：外层主线的询问调用在分支开出来时还没有结果，历史以没有结果的工具调用结尾，装配直接失败）。
   - `harness/environment.py`：`inspection_root` 与 `cleanup_inspection_workspace` 按会话标识建目录；新增 `cleanup_run_inspections`（启动扫描按 run 整体删除）。
   - `harness/sessions.py`、`harness/runtime.py`、`harness/context.py`、`harness/smoke.py`：跟着上面的会话口径改。
   - `harness/definitions/rules.json`：新增 `organization.ask_chain_max_depth`（value 3，bounds [1,6]，kind structure，form boundary，四项记录与来源按工单正文）。
   - `harness/definitions/organization.json`：协作规则里的「分支里不能再询问」改成「分支里可以再问别的部门，包括回问链上已有的部门……询问链的层数有上限，超过时这次提问被拒绝，这时把要问的内容写进回答」——模型看不到这条就不知道分支能回问。
   - `harness/streams.py`：run 事件版本 7 → 8（询问按会话归属的栈，语义变了，进行中的旧 run 走强制升级）。
