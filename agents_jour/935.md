1. 核对工单写的现象：本地复现得到同样的 `provider_error`。工单正文记的是运行机上的一次偶发失败（运行 40131922030，③ 集成层，`1 failed, 1282 passed in 833.04s`），失败信息 `the run ended before the interrupt point: {"run_id": "run_...", "status": "failed", "stop_reason": "provider_error"}`；同一提交重跑通过，同一份代码的另一次集成层运行（40130332234）1283 条全过。本地连续运行也过——说明它依赖运行机负载，不是断言写错了。
2. 查清「模型提供方为什么报错」：这一条里的模型不是真的模型服务，是测试用的假模型（`FakeAdapter`）。工单说的 `provider_error` 来自假模型的脚本用尽：`harness/adapters/fake.py` 第 109 行，某个会话的脚本取空了就抛 `ProviderError("fake adapter script exhausted")`，引擎把它记成 `provider_error`（`harness/engine.py` 第 266 至 268 行、第 368 至 399 行；不重试，`retryable=False`）。子进程日志里只有 `stop_reason`，看不出是哪个会话出的问题——这正是工单里「提供方先报错的话运行就提前结束了」那句话的由来。
3. 定位到具体是哪一步：`harness/tests/test_unknown_action_handed_back.py` 的 (c)（第 194 行）、(d1)（第 213 行）、(d2)（第 256 行）按部门给出的脚本里只有 `product` 与 `engineering`，没有 `quality`。PRD 被接纳以后工程与质检同时工作（工单 #878），质检会话也会发起模型请求；没有它的脚本时，假模型报「脚本用尽」，整个 run 以 `provider_error` 结束。读子进程的事件库证实：事件 23 是工程的 `tool_started`（`call-append`），事件 26 是质检的 `model_requested`，事件 27 `model_attempt_failed`（`err=fake adapter script exhausted`，`session=ses_qua_…`，`department=quality`），事件 28 `run_failed`（`stop_reason=provider_error`）。同文件里的 (a)、(b) 给了质检脚本（`{"proposal": {"kind": "quality_auto"}}`），它们的日志是空的，没有这个错误。
4. 为什么它会偶发：质检会话的失败与「被挡住的那一步」（工程的 bash 子进程写下 `started` 标记）是两件并行的事。标记先到，父进程就杀掉子进程，用例通过；提供方的错误先到，run 先结束，父进程看见进程已经退出，就报「运行提前结束」。本地 6 次并发跑（造负载）每一次都是标记先到，所以本机复现不出失败；但每一次的日志都能看到 run 确实以 `provider_error` 结束了（`"status": "failed", "stop_reason": "provider_error"`）——运行机负载重时先到的是错误那一侧，这就是 CI 上偶发失败的原因。
5. 顺带查清的一件事（比偶发本身更要紧）：改动之前这条用例是**空过**的。run 以 `provider_error` 结束以后没有重启、没有交还，`action_verified` 事件根本没有；「文件只有一行」不是因为「命令没有被再运行」，而是因为运行压根没走到重启那一步。修好以后事件序列是：事件 39 `action_verified`（`resolution=handed_back`，`error=执行被中断，结果未知…`）、事件 40 `run_resumed`，工程会话带着交还的结果继续（`write_file` 与 `run_check`），`call-append` 没有第二次 `tool_started`——命令确实没有被再运行。
6. 改动一（根因，`harness/tests/test_unknown_action_handed_back.py`）：(c)、(d1)、(d2) 的脚本按部门补上质检会话（`{"proposal": {"kind": "quality_auto"}}`，与同文件的 (a)、(b) 一致；`tail` 里质检的脚本也从空列表换成同一项（重启以后质检会话同样会发起模型请求）。三处都写了注释说明为什么质检也要给脚本。
7. 改动二（断言没有放宽，反而收紧了，`harness/tests/test_unknown_action_handed_back.py`）：(c) 补三条断言——这次调用的结果确实交还了模型（`action_verified` 恰好一条，`resolution == "handed_back"`）、整个 run 里 `call-append` 只有最初那一次 `tool_started`（命令没有被再运行）。原来的「文件只有一行」保留。这样「运行没有重启」这种情况会在用例上直接失败，不会再空过。
8. 改动三（工单要的「能读懂的信息」，`harness/tests/process_kill.py`）：子进程打印的运行结果里加上 `error` 与失败的那一次请求（`failed_session` 写明会话与部门、`failed_error`），父进程「运行提前结束」的断言信息里点明「上面的 JSON 写着停止原因与出错的会话」。现在这条失败长这样：`the run ended before the interrupt point: {"run_id": "run_…", "status": "failed", "stop_reason": "provider_error", "error": "fake adapter script exhausted", "failed_session": "ses_qua_…（quality）", "failed_error": "fake adapter script exhausted"}（运行在到达中断点以前就结束了；上面的 JSON 写着停止原因与出错的会话）`。辅助函数 `_failed_attempt` 放在 `main()` 之前：这个模块的 `if __name__ == "__main__": main()` 在文件中间（父进程一侧的辅助在它后面），放在后面的话子进程跑到那行时函数还没有定义（NameError）。
