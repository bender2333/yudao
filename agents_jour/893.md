1. 核对前提：工单正文记的失败是 `harness/tests/test_call_target_per_request.py::test_revoked_admission_blocks_the_next_request_until_retested` 报 `assert [] == ['model_unavailable', 'model_unavailable']`（两个部门各有一条待恢复的决定请求，实际一条也没有）。工单里引用的两次运行（40101782147 与 40107171826）的 CI 日志里都不是这一项失败：40101782147 失败的是 `test_smoke_guidance_audit.py` 的两项 `StopIteration`（工单 #870），40107171826 失败的是同一文件的两项。真正失败过的是另一次运行 40048915796（提交 cbe68f1a）：junit 制品（`integration-results`）里这一项的失败信息就是 `assert [] == ['model_unava..._unavailable']`，位置 `test_call_target_per_request.py:384`。工单评论把两次运行的失败项记混了，失败本身是真的。
2. 找到根因（第一层）：那一轮运行的 main 上还没有 #856。#856 之前的实现里，停下其余会话用的是整个事项共用的取消开关（`harness/orchestrator.py` 的 `_Activation.abort_flag` 指向 run 的 `_abort`，`harness/engine.py` 的 `StepDriver.cancel()` 把这个开关打开）：`run_until_stop` 看见 run 被未回答的决定请求挡住以后停其余会话，顺手把事项记成已取消（run_failed，停止原因 cancelled），`_withdraw_decisions` 随之撤销待恢复的决定请求。旧代码在 `blocks_run` 分支交回的是这一轮开头读到的投影（状态仍是 running），于是用例看到的是「状态 running、一条待恢复的决定请求也没有」。#856 的提交说明里写的正是这件事：「待恢复的决定请求也写不出来」。#856（提交 04a1151a，2026-10-25 合入 main）改成每个会话有自己的停止开关，停下其余会话不再改变事项的状态，这一类失败在现在的 main 上不再出现。
3. 找到根因（第二层）：用例本身还假定「两个会话都会走到被挡住的那一步」。一条未回答的决定请求就挡住整个 run（`harness/decisions.py` 的 `blocks_run`，`harness/orchestrator.py` 的 `_stop_requested` 在安全节点上判断）：先到的会话写下请求以后，后到的会话在自己的安全节点上看见它，就停在那里、没有停止原因、不发自己的请求。被挡住的那一步（解析调用目标失败）紧跟在会话的第一个安全节点以后，两个会话的驱动器任务在事件循环里前后相邻，这个余量只有一轮事件循环。实测：在第二个会话（质检）的驱动器上让它在第一个安全节点以前让出一次，待恢复的决定请求就从两条变成一条（`['engineering']`），这正是这一项偶发失败的形态。
4. 改动（`harness/tests/test_call_target_per_request.py`）：夹具换成 `_RecordingFacade`（ProviderFacade 的子类），记录每个部门解析调用目标失败（= 被挡住的那一步）；用例在断言两条待恢复的决定请求之前先核对两个部门都走到了这一步（`set(facade.blocked_departments) == {"engineering", "quality"}`）。这样「两个会话都走到被挡住的那一步」从假定变成核对：真出了这一类失败，用例直接说哪个部门没有走到（夹具记录），而不是给出「实际是空的」这种看不出原因的断言。用例的断言没有放宽：两个部门各有一条待恢复的决定请求，各写明自己的部门（`assert {decision.request["department"] for decision in decisions} == {"engineering", "quality"}`），另外三条断言原样保留。
5. 登记架构问题（`docs/architecture-issues.md`）：模型管理设计说明第 5.5 节写的是同时被挡住的会话各发一条，实现里只有先到的会话发。两个可选做法留给架构师定：(1) 进行中的会话不因为别的会话的请求而停在安全节点（与设计说明第 5.5 节一致）；(2) 承认实现里的这条规则，改写设计说明第 5.5 节并按它断言用例。这张工单的「只改」清单里没有这个文件，按 solo 约定在工单上补记了要改的文件与原因。
