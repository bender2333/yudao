上一轮刚起步就被中断，worktree 里留下 3 处未提交改动（roles.json、tools.json、work_items.json）。本轮接着做完。

## 本轮经过

### 起点

- `git status`：3 处定义改动（`run_baseline_check` 的定义与说明）。
- 发现一处上轮的错误：`run_baseline_check` 被加进了 **engineering** 的工具清单（roles.json），而工单正文写明质检负责触发。本轮改成加进 **quality** 的清单；work_items.json 的普通事项质检清单本来就是对的，没有动。
- 直接构造内核测试时全量收集失败：environment.py 的 `_UNIMPLEMENTED` 检查按「出现在某个工具清单里的环境工具必须有执行方法」拒绝启动。注册执行方法以后恢复。

### 实现

- `harness/environment.py`
  - `run_baseline_check` 注册到 `_PROCESSES` 与 `_KIND_TOOLS["check"]`（动作类别 check，核实方法 query，可取消——与 run_check 同一既定合同）。
  - 新增 `_run_baseline_check`：基线副本 = 事项起点树 + 这个部门的检查材料 + 声明涉及的交付文件；命令取交付检查已经记录的那一条（`_delivery_check_command`），模型给的 `command` 参数不参与；声明的文件逐项核对属于起点到交付的改动清单；时限、输出截断、进程树清理与树变化核对（基线副本与源工作区两处动作前后读取）与 run_check 相同；退出码非零且不是 124/130 时基线失败。
  - `Workspaces._attach_trial_source` 同时绑定基线来源：起点树（run_created 记下的采纳成果或起始文件夹快照，返工后不变）、改动清单（封存树相对起点多出或改了内容的文件，一次算好）、交付说明里的检查记录与封存交付树（声明文件的内容从这里取）。
- `harness/actions.py`、`harness/workspace.py`：`CheckReceipt` 只增两个字段——`command`（主机执行的命令，交付回执照抄，基线按名字取它）、`baseline`（基线回执标记）。回执文件与读回照旧写出。
- `harness/validation.py` `_receipt_evidence`：随成果内容写出的回执证据带 `command` 与 `baseline`（交付说明里的 checks 因此带命令）。
- `harness/coverage.py`：纯函数 `baseline_outcome`（退出码 → failed/passed/unable_to_run）、`baseline_records`（本次激活的基线回执按检查名归并，tree_changed 的回执不参与）、`criterion_baseline_covered`（命令检查的覆盖 = 交付通过且同名基线失败）、`baseline_open_records`（放行记录的基线明细：failed/passed/missing/unable_to_run）。`coverage_report` 增加 `baseline_valid`；不给基线归并时保持旧读法（命令检查按交付通过计入，`baseline_valid` 记 False——放行记录写明缺少基线回执）。
- `harness/tightening.py` `_review`：放行记录一次算好 `coverage.baseline_valid` 与 `baseline_checks`；只读工作区事实里的基线回执，不补运行。放行准入与结果词不变（`_release_criteria_errors` 没有动），QA_SUBMITTED 门不变。
- `harness/app/payloads.py`：`QaCoveragePayload.baseline_valid`、`QaSubmittedPayload.baseline_checks`（新 `BaselineCheckRecord`）、`CheckReceipt.command/baseline`。
- `harness/models.py`、`harness/projection.py`：`QAReview.baseline_checks`，投影从载荷读回（旧事件缺省空）。
- 定义（roles/tools/work_items）：质检的普通事项清单加 `run_baseline_check`；tools.json 的定义与参数（name 必填、files 可选、additionalProperties false——command 参数进不来）；两个部门 prompt 写明基线检查的做法与口径。

### 差异与自定的边界

- 设计说明写「基线副本由事项起点树的引用、质检测试材料、质检声明需要叠加的交付文件组成」。实现里质检的检查材料从检查工作区复制进基线副本（与 run_check 的做法一致）；声明文件的内容从封存交付树取（检查工作区里改过交付文件也不影响基线副本的内容）。
- 设计说明没有写命令记录在哪里。实现把主机执行的命令记进检查回执（`command` 字段），交付说明里的 checks 随回执带它；基线按名字取记录，取不到时拒绝执行并写明要先跑交付检查。
- 基线回执不是交付检查的证据：`latest_check` 的既有过滤条件（tree_changed 等）之外，基线回执由 `baseline` 位区分，交付证据路径不读它。
- 「基线与交付用相同的时限」实现为同一个 run 冻结的 `check_timeout_sec`（不给 timeout_sec 参数；工具定义也没有这个参数）。
- 放行记录的基线明细（`baseline_checks`）取「最不利」的结果词：任一检查名 missing 优先，其次 unable_to_run，再次 passed，全失败才是 failed。
