# 工单 #562：从候选建立访问定义时直接采用预填容量（应用层）

## 背景与目标

从 #385 拆出（2026-10-16 架构师）：应用层从候选建立模型访问定义时直接采用预填容量。#385 正文验收第 3 条由本工单完成；界面（勾选加入、自动模型测试、删除「接受容量」）由下一张子工单完成。设计依据：[模型管理设计说明](docs/design/model-management.md) 第 4.3、4.4 节与 [ADR-0002](docs/adr/0002-candidates-need-test-to-admit.md)。

要解决的问题：
1. 从候选建立访问定义时，窗口、输出上限与协议取候选的预填值，来源随定义保存（以后可以修改）；两处都没有窗口或输出上限的候选，必须在请求里给出才能保存，否则拒绝并写明缺少哪一项。
2. 删除「接受容量」限制（去除后端 `_require_capacity` 中的 `capacity_confirmed` 检查；无单独的接受容量命令，本工单做让接口合同、OpenAPI 快照与客户端生成类型同步更新并保证 `npm run typecheck` 通过的最小改动）。
3. 修改窗口、输出上限等字段保持准入（设计说明第 4.4 节）。

## 事实来源与核对位置

- 候选解析与预填来源：`harness/providers/discovery.py`（114-162 行 `_parse_candidates`）。
- 候选事件载荷：`harness/app/payloads.py`（`CatalogCandidatesCollectedPayload.candidates`）。
- 应用层命令与合同：`harness/app/catalog_commands.py`（`ModelInput` 与 `CatalogConnectionSave`）。
- 校验与容量要求：`harness/providers/facade.py`（`save_provider_entry` 与 `_require_capacity`）。
- 准入有效性判断：`harness/providers/store.py`（`admission_is_current`）。

## 决策

1. **预填来源标注**：在 `harness/providers/discovery.py` 中增加 `PREFILL_SOURCE_LABELS` 与 `format_capability_source(candidate)`，并在 `_parse_candidates` 中生成 `candidate["capability_source"]`，格式与前端 `prefillSourceText` 一致（如 `协议：能力表 · 窗口：上游模型列表 · 输出上限：上游模型列表 · 输入方式：能力表`）。
2. **去除容量确认硬性限制**：在 `harness/providers/facade.py` 的 `_require_capacity` 中删除 `row.get("capacity_confirmed") is not True` 报错分支；当 `context_window` 或 `max_output_tokens` 为 `None` 时，分别产出对应字段的 `ValidationIssue`（写明 `缺少 context_window` 或 `缺少 max_output_tokens`）。
3. **校验顺序前置**：在 `facade.save_provider_entry` 中，先执行 `_require_capacity(models_raw, provider_id, ...)` 再执行 `_parse_document`，确保缺失容量字段时以明确的 `缺少 context_window`/`缺少 max_output_tokens` 报错返回，而不是因底层解析提前抛出泛化异常。
4. **ModelInput 合同与助手构造**：在 `harness/app/catalog_commands.py` 中，将 `ModelInput.max_output_tokens` 允许为 `PositiveInt | None = None`，并实现 `@classmethod from_candidate(...)` 与 `model_input_from_candidate`，支持直接从候选字典提取预填容量与来源，或在调用时覆盖容量和来源。
5. **修改窗口保持准入**：`admission_is_current` 比较范围仅包含 `base_url`、`credential_ref`、`protocol`、`model` 与 `reasoning_mode`，不比较容量字段；修改窗口后定义准入依然有效。
6. **快照重写与客户端生成物**：使用 `--write-openapi-snapshot` 重写 `harness/tests/openapi/openapi.json`，在 `client` 执行 `npm run generate:api` 重新生成客户端 TypeScript 类型，验证 `npm run typecheck` 通过。

## 第 2 轮（审查要求修改与架构师决定）

### 1. 任务背景与决策

第 1 轮审查指出三项阻塞：
1. 范围外改动：`harness/providers/discovery.py` 新增 `PREFILL_SOURCE_LABELS` / `format_capability_source` 并在 `_parse_candidates` 预填 `capability_source`。
2. 清理残留：`ModelInput.capacity_confirmed` 字段、`from_candidate` 设置与两处 `pop("capacity_confirmed")` 仍在合同内。
3. 测试缺口：缺少提交不带确认标记、容量齐全的裸行保存成功的用例，无法区分「预填直接采用」与「行内确认」。

架构师决定（选 C）：
- 本工单彻底删除 `capacity_confirmed` 接口字段，所有发送方在同一个 PR 内停止发送；界面内按钮与 `FormRow` 留给 #563。
- `discovery.py`、`__init__.py` 与 `payloads.py` 恢复到 main 状态，来源随定义保存改为在 `ModelInput.from_candidate` 内拼装。
- 补齐裸行保存成功的测试，反向验证加回门槛时变红。
