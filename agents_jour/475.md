1. 开工前的核对：工单 #475 的标签是 `ready-for-agent`，没有开着的 PR；依赖的 #474（部门按关注的成果开始工作，三个部门同时运行）与 #520（PRD 新版本的通知、同时互相询问与检查工作区按会话保留）都还开着，`#474` 的两个前提 #473 与 #485 已关闭。工单正文没有「只改」清单，按设计说明与控制核心的实际位置定下本轮要改的文件（见下面第 6 条）。
2. 读代码得到的结论：当前结构里一个 run 同时只有一次激活（`harness/orchestrator.py` 的 `_running` 与 `_active` 按 run 编号占位），部门由阶段状态机决定（`department_for_phase`）；询问分支在提问方的激活里同步跑（`_execute_ask` 等待 `_run_ask_branch`），分支有自己的会话编号（`ses_ask_…`）与自己的历史。已有的 `test_ask_branch_resumes_across_system_restart` 只覆盖「分支刚开始就中断」这一种。
3. 找到的三个缺口（都能在当前结构里复现）：
   - 会话一级没有累计用量：只有事项（run）记累计已用时间与次数（`elapsed_ms`、`activations`、`model_steps`），会话（部门的一轮工作、每个询问分支）没有自己的累计值。
   - 中断以后继续的会话拿到一份新的上限：分支的步数上限按 `min(部门声明, 提问方剩余)` 算，没有扣掉这个分支会话已经用掉的步数；部门会话重新开始一次激活时也一样，步骤计数从零开始。
   - 结果未知的动作没有交还给发出它的会话：`harness/orchestrator.py` 的 `_handed_back_action` 与 `_auto_verified` 写的核实记录没有会话编号。结果进了部门主线的历史，分支会话读不到；分支的历史因此以「没有结果的工具调用」结尾，下一次请求被拒（`History ends with tool calls that have no recorded result`），分支以「没能回答」结束——这正是工单验收第 4 条说的情形。
4. 实现：
   - `harness/orchestrator.py`：每个会话累计的已用时间、激活次数与模型步数记在激活结束事件里（`session_elapsed_ms`、`session_activations`、`session_model_steps`）；启动与每次激活前从事件恢复（`_recover_session_usage`）；会话这一段用掉的时间按 run 的累计已用时间之差算（`_start_session_segment` 与 `_settle_session_segment`），分支会话的时间因此计入提问方所在的会话（用量计入提问方）。
   - 步骤上限：分支会话的步数上限扣掉这个会话已经用掉的步数（`_session_model_steps`）；部门会话这一次激活的步数上限扣掉「上一次没有结束的激活」用掉的步数（`_session_unfinished_model_steps`，只算最后一条激活结束事件之后的步数，正常流程里是零）。分支的时间上限同样扣掉这个会话已用的时间。
   - 结果未知的动作：核实记录带上发出它的 `tool_started` 的会话编号（`_handed_back_action` 与 `_auto_verified`），因此这次工具结果进入那个会话的历史。
   - `harness/app/payloads.py`：`ActivationFinishedPayload` 增加三个会话级字段（默认值 0，旧事件按 0 处理）。
   - `harness/streams.py`：run 事件版本 8 → 9（激活结束事件增加字段、核实记录增加会话编号，语义有变；按 ADR-0019 与恢复契约第 2 节提高版本）。
   - `harness/tests/event_sequence.py`：保留的字段表里加上三个会话级字段；`session_elapsed_ms` 与其它时间字段一样写成占位（随机器变化的值不进基准）。
   - `harness/tests/process_kill.py`：中断点可以按会话过滤（`--hold-session`），用来在某个会话进行中结束进程。
5. 测试（新增 `harness/tests/test_issue_475.py`，四条用例，真实子进程运行系统并终止）：
   - 询问分支会话进行中结束进程，重新启动以后分支会话继续、回答交回提问方、事项运行到放行；同时核对结果未知的动作交还的是这个分支会话（核实记录的会话编号等于分支会话的编号 ✓）。
   - 工程提交交付以后、质检开始核验以前结束进程，重新启动以后质检开始核验这份交付（放行依据的交付内容摘要等于中断前接纳的那一份 ✓）。
   - 重新启动前后各会话与事项的已用时间与次数连续累计（事项的累计已用时间不倒退 ✓；分支会话的模型步数是累计值，中断前用掉的那一步仍然算在里面 ✓；会话的累计步数与事件里数出来的步数一致 ✓）。
