# 工单 #634 执行日记

角色：执行者（9router/ag/gemini-3.8-flash-high）

分支：`issue-634`

## 1. 规格与范围

依据：`docs/design/department-loop.md` 第 4.1 至 4.3、4.7 节，`docs/adr/0036-concurrent-departments-and-nested-asks.md`（main 97488db4）。

要做的：
1. 冒烟的 `collaboration` 场景换成 `ask` 场景。任务：产品在第一份 PRD 之前用询问问工程可行性，工程在分支里回答；之后工程用询问问产品那个未定的取舍，产品在回答里修订 PRD。运行摘要用 `ask_audit` 取代三项协作字段，审计内容：每次询问的开始与结束事件成对（同一事项，结束在开始之后，结束事件的双方与开始一致），记录方向；第一份 PRD 之前有一次产品问工程，结果为已回答；有一次工程问产品，回答附带 PRD 修订，新版本在开始与结束之间被接纳；还有进行中的询问时写入说明。退出码对 `ask` 场景要求审计通过、这两项都成立。命令行取值改为 `("happy", "ask", "all")`，README 的命令同步。
2. 冒烟里读取协作请求的其他地方：`_expected_guidance_only` 删除 `pending_request` 的条件；模型输入审计的工作依据只核对 `effective_contract_hash`，不再核对 `request_id`。
3. `compacted_runner` 的工程一步不再用协作请求（例如询问产品并由分支回答，或者其他让产品此后再次工作的步骤），保留它原来的用途：产品在大文件上反复压缩、各次激活之间合同会变化。`test_assembly.py` 与 `test_project_queries.py` 中用到它的用例不修改也要通过。
4. `test_collaboration_engine.py::test_new_spec_explicitly_disposes_each_effective_decision_and_preserves_its_source`（三种 `disposition`）检查的是 PRD 修订逐条处理已有补充决定，改写后移到 `test_contracts_plans_module.py`（同为模块层），用例名不变。PRD 修订改由产品在回答询问时提交，补充决定在产品自己的一轮工作中提交。
5. 删除与改写工单清单中列出的用例，删除 `test_collaboration_engine.py`、`test_collaboration_responded_parties.py`，同步 `layers.toml`。

## 2. 执行过程与关键决断

1. **失败证据获取**：
   - 运行 `uv run python -c "from harness.smoke import run_smoke; run_smoke(scenarios=['ask'])"`，触发 `ValueError: unknown smoke scenario`，确认改动前不支持 `ask` 冒烟场景。
2. **冒烟入口与审计实现**：
   - `harness/smoke.py`：定义 `ASK_TASK` 任务描述，包含产品初版规格前询问工程可行性并在分支回答、工程询问产品未定取舍并在回答附带修订 PRD。
   - 冒烟可选场景从 `["happy", "collaboration"]` 调整为 `["happy", "ask"]`，命令行参数选项改为 `choices=("happy", "ask", "all")`，README 命令同步为 `--scenario ask`。
   - 运行摘要移除 `collaboration_requests`、`collaboration_responses`、`collaboration_audit`，替换为 `ask_audit`（调用 `_ask_evidence`）。
   - `_ask_evidence` 严格校验成对 `ask_started` / `ask_answered`（双方一致、结束在开始后、同一事项唯一），记录方向；校验首版 PRD 前有产品问工程已回答（`pre_spec_ask`）；校验有工程问产品附带 PRD 修订并在起止事件间被接纳（`requirements_revision`）；校验未结束的进行中询问；未通过时记入 notes 并设 `status="unverified"`。
   - `_expected_guidance_only` 移除 `pending_request` 判定，仅保留产品部门豁免与待处理指导检查。
   - 模型输入审计中 `work_basis` 移除 `request_id`，仅保留 `effective_contract_hash`；当发生 `CONTRACT_ACCEPTED` 时同步更新当前所有激活的基准哈希，匹配跨询问分支的持续工作。
   - `smoke_exit_code` 增加对 `ask` 场景的核验（要求 `ask_audit` 状态为 verified 且两项关键询问条件成立）。
3. **测试夹具与测试用例适配**：
   - `harness/tests/helpers.py`：`compacted_runner` 移除 `collaboration_request`、`pending_request_id`、`response_turn` 调用，改为工程向产品发起 `ask` 并由产品分支 `answer`，工程收到回答后继续交付。`test_assembly.py` 与 `test_project_queries.py` 均无需修改通过。
   - `harness/tests/test_smoke.py`：夹具改名 `saved_ask`、`ask_run`、`ask_invocations`，更新 `_PRODUCT_RETURN_SCRIPT` 为询问场景，摘要断言调整为 `ask_audit`；删除原协作审计用例，新增 `ask_audit` 审计通过、缺首版前发问、缺附带修订回答、双方或事件不匹配时的断言用例；工作依据修改用例仅保留 `effective_contract_hash`。
   - `harness/tests/test_tool_contracts.py`：`test_smoke_exit_code_does_not_accept_fake_or_missing_evidence` 适配 `ask` 场景与 `ask_audit` 字段。
   - `harness/tests/test_compaction_engine.py`：`test_empty_summary_does_not_fail_the_run_and_department_continues` 与 `test_empty_compaction_summary_allows_retry_on_next_activation` 中的协作请求替换为 `delivery_turn`，适配 `test_changed_contract_rebuilds_compaction_from_preserved_original_sources`。
   - `harness/tests/test_orchestrator.py`：删除 4 个协作请求用例，`test_max_cycles_pauses_with_human_action` 改写为工程交付后质检退回达到循环上限。
   - `harness/tests/test_interaction_engine.py`：删除 2 个 pre-prd 咨询用例，`test_project_department_prompt_changes_apply_from_the_next_model_request` 改写为同激活内连续工作请求。
   - `harness/tests/test_contracts_plans_module.py`：`test_supplementary_decision_changes_contract_without_new_spec` 改为产品在质检退回后的独立工作轮次中提交补充决定；移入 `test_new_spec_explicitly_disposes_each_effective_decision_and_preserves_its_source`，三种 disposition（retain、integrate、retire）均通过。
   - `harness/tests/test_collaboration_rules.py`：仅保留 `test_normal_proposals_remain_available`，删除其余 20 个协作规则用例及未使用的辅助函数。
   - 删除 `test_collaboration_engine.py` 与 `test_collaboration_responded_parties.py`，并从 `harness/tests/layers.toml` 移除登记。
