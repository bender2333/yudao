执行者 solo-deepseek-v4.1-flash / 2026-11-03 23:15 / 做法（按三处验收切）：

1. **生命周期事件（验收一）**：`McpSessions` 多一个写入方（`events`），会话建立成功写 `mcp_server_started`（服务器名称、传输、进程标识、进程创建时间），`close()` 逐台关闭以后各写一条 `mcp_server_closed`（原因 `closed`），启动或连接失败写 `mcp_server_failed`（原因已脱敏）。会话表由 `Orchestrator.mcp_sessions` 建立时接上写入方：`_mcp_server_event` 用写入口在 run 流里追加一条应用事件，状态前后都是当时的状态，提出者是系统；写不进去不打断会话的建立与关闭，原因记入 `_close_errors`（与检查工作区的清理错误同一做法）。
2. **遗留进程（验收二的后半）**：`mcp_session.leftover_servers(store)` 按（run、服务器名称）把 `mcp_server_started` 与 `mcp_server_closed` 一一配对，剩下的就是没有关闭记录的服务器；`end_leftover_server` 用 `mcp_client.terminate_legacy_process`（进程标识与创建时间两项都对得上才结束，整棵进程树一起）结束仍然存活的进程。`LoopSystem` 启动序列里（清理孤立检查工作区之后、继续未结束的 run 之前）`_end_leftover_mcp_servers_on_startup` 结束这些进程并补写 `mcp_server_closed`（原因 `leftover`，`ended` 说明这一次有没有真的结束进程）。进程已经不在（Windows 上 SDK 的作业对象会随 Yudao 进程一起结束它）时照样补写关闭事件：事件里的启动与关闭要配得上，恢复时「有启动没有关闭」就等于还有遗留进程。
3. **超时与取消（验收三）**：客户端的 `ToolCallResult.cancelled` 到了 `_call_once` 以后，会话已经先发取消通知、等应答最多 10 秒、stdio 结束整个进程树、HTTP 关闭会话（`#69` 的 `_cancelled_result` 做这几步）。这一侧把会话从表里去掉（下一次调用按同一台服务器重新建立）、补写 `mcp_server_closed`（原因 `cancelled`），交回 `is_error=True`、`error_code="cancelled"` 的结果，正文写明「能/不能确认服务器已停止」「执行被中断，结果未知」「由发出这次调用的会话决定是否重新调用」。没有自动重试。
4. **中断以后交还（验收二的前半）**：`recovery.py` 的 `await_unknown_actions` 已经是「有 `tool_started` 没有结果就交还发出它的会话」的机制，MCP 调用与取回、命令走同一条路（`tool` 不是文件动作），本单**没有另造一套**，只补真实进程终止的验收（`harness/tests/test_mcp_lifecycle.py`）。

另记一条实现上的事实：Windows 的 venv 里 `Scripts\python.exe` 是转交给基础解释器的启动器，客户端 `_remember_process` 记下的是这个启动器（Yudao 的直接子进程），真正的服务器是它的子进程；所以事件里的进程标识是启动器，结束进程时靠 `children(recursive=True)` 把服务器与它自己起的子进程一起收掉。用例的断言据此写：记录下来的进程不在、服务器自己的进程标识与它起的子进程也不在。
