### 第一轮：一个事项里多个会话同时运行

**做了什么**

1. **控制核心不再限制一个 run 只允许一个部门调用模型**（`harness/orchestrator.py`）：
   - `_running` 从「run → 一个占用」改成「(run, 部门) → 占用」，同一部门同时只有一轮，不同部门同时各一轮。
   - `_active` 从「run → 一个激活」改成「run → 部门 → 激活」，取消与唤醒都按全部会话做。
   - `run_until_stop` 改成并行的驱动循环：按 `ready_departments` 给每个等待工作的部门开一个任务，`asyncio.wait` 等到有一个会话结束就重新看一遍投影；事项到终态或被未回答的决定请求阻塞时，其余会话停止并收尾。
   - `_prepare_activation` 接收要激活的部门，在事务里重新核对「这个部门现在仍然有新的工作」（状态在别的会话工作期间变过时不再开始一轮）。
   - 运行的计时按会话改：`_pause_run_clock`/`_settle_run_segment` 在还有别的会话工作时继续计时。
2. **关注的成果有了新版本的每个等待中的部门都开始一轮工作**（`harness/collaboration.py`）：新增 `ready_departments`，与 `next_department` 同一套规则（还没回答的询问、被指导提前安排的部门、按定义顺序的部门），但一次给出一组而不是一个。被指导提前安排的部门同一轮里只安排一个（让出的工作由各部门自己记着，投影里新增 `department_yielded_work`）。
3. **质检关注「PRD 被接纳」**（`harness/definitions/organization.json`）：质检的 `watched` 多一项 `product_spec`。判断按部门分开：工程看「当前 PRD 与它最近一次成果依据的版本是否不同」，质检看「当前有效合同与质检上一次工作的依据是否不同，并且还没有交付要核验」——预测性探索发生在交付到达以前。质检上一次工作的依据记在投影的 `department_bases` 里。
4. **预测性探索这一轮不提交结论**（`harness/validation.py`）：质检的结论是对当前交付的核验，这一轮开始时没有交付就没有可以核验的对象，提交被拒绝（`this work has no delivery to review`）。这条规则同时给了事件序列基准一个确定的结束点：这一轮以被拒绝的提交结束，交付到达以后质检开始新一轮工作，检查工作区从这份交付建立。
5. **产品可以同时是多个询问的被问方**（`harness/validation.py`）：原来「产品可以在回答里修订 PRD」看的是最后发起的那一次询问；同时运行的会话让待回答的询问不止一条，改成看还有哪些询问等着产品回答。
