# 工单 #564：决定的查询包含实例升级请求

## 背景与目标

处理 `docs/architecture-issues.md` 中 #462 执行者登记的问题（2026-10-16 11:00）。
目录流三个实例升级事件（`instance_upgrade_requested`、`instance_upgrade_answered`、
`instance_upgrade_withdrawn`，`32865edb` 即 #355 引入）没有进入决定的查询合同：

- `harness/app/decision_queries.py:60` `DecisionView.request` 的联合只有
  `DecisionRequestedPayload | ProjectDecisionRequestedPayload`，`decisions.list` 列出实例升级请求时
  pydantic 构造 `DecisionView` 失败（42 项校验错误），整个查询不可用。
- `harness/app/decision_queries.py:127-131` `DECISIONS_LIST.changed_by` 不含这三个事件，
  客户端订阅 `decisions.list` 的视图（`client/src/renderer/src/contract/view-sync.ts` 按
  `changed_by` 重查）在回答与撤回后不重查。
- `DecisionsList.kind`（同文件 22-29 行）本来是不限制取值的字符串，`_decisions_list` 把它作为
  `saved_decisions(..., kinds=(request.kind,))` 的一个元素传入，`kind=instance_upgrade` 筛选已经生效，
  不需要改代码。

目标：联合加入 `InstanceUpgradeRequested`，`changed_by` 加入三个事件，用应用层测试固定两条结论。

## 事实来源

- 请求载荷 `harness/app/payloads.py` 的 `InstanceUpgradeRequested`（约 1498 行）：
  `kind: Literal["instance_upgrade"]`、`blocks: Literal["instance"]`、
  `options: list[DecisionOption]`、`description`、`facts: list[str]`、`report: InstanceUpgradeReport`。
  已在 `PAYLOADS`（1619-1622 行）按 `CatalogEventType.INSTANCE_UPGRADE_*` 登记，#462 的成果。
- 写出方 `harness/release_check.py`：`check_repository(path)`（约 320 行）返回
  `ReleaseCheckReport`（53-66 行，`repository/pending_commit/base_tag/kernel_changes/
  kernel_python_lines/python_lines_max/findings/text` + `passed` 属性）；
  `request_instance_upgrade(system, report)`（约 403 行）经
  `system.writes.transact(catalog_stream(), decide)` 写入目录流，返回 `decision_id`，`actor="system"`。
- 回答方 `harness/orchestrator.py:1677-1682`：`answer_decision` 的目录流分支返回 `run_id=None`。
- 查询方 `harness/app/decision_queries.py`：`_decisions_list`（74-113 行）读
  `saved_decisions`，`_view`（62-72 行）用 `request=decision.request` 构造 `DecisionView`，
  合同是 `extra="forbid"` 的 `Contract`（`harness/app/contracts.py:12-14`）。
- 事件流范围 `harness/app/event_stream.py:123-133` 的 `matches`：目录事件按 `type` 判定范围，
  `EventScope(types=(...))` 能订阅三个目录事件。

## 决定

- 联合在末尾追加 `InstanceUpgradeRequested`：pydantic 联合按顺序校验，前面的成员
  `kind` 都是字面量且不含 `instance_upgrade`，追加不会改变已有请求的判定结果；
  OpenAPI 的 anyOf 因此在 `KernelModificationRequested` 之后多一个 `$ref`。
- `changed_by` 在同一元组末尾追加三个 `CatalogEventType.INSTANCE_UPGRADE_*`，顺序与
  `PAYLOADS`（1619-1622 行）一致。
- 不动 `DecisionsList`：第 3 项「kind 筛选」由现有字符串参数完成，测试直接固定行为。
- 不动 `harness/app/payloads.py`（#543 在改），只从它 import `InstanceUpgradeRequested`。
- 测试落在 `harness/tests/test_release_check.py`（登记表第 131 行，module 层）：该文件已有
  `repository` 夹具（66-86 行，临时 git 仓库）与两个实例升级用例，`Application(system).query`
  无网络、无完整循环，module 层允许。新增四项：
  `test_the_query_lists_the_instance_upgrade_request_with_its_report`、
  `test_the_kind_filter_returns_only_instance_upgrade_requests`、
  `test_answering_an_instance_upgrade_request_shows_in_the_query`、
  `test_the_catalog_stream_decisions_mark_the_list_for_resubscription`。
- 订阅事件流的实际收包不加：验收第 2 条的判据写在括号里（`changed_by` 生效），
  `decisions.list` 的 `changed_by` 由 `test_the_catalog_stream_decisions_mark_the_list_for_resubscription`
  固定；事件流本身的范围判定在 `test_event_stream.py` 已覆盖。界面实例升级卡片不做（工单明示）。
