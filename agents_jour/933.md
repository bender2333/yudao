1. 核对工单的前提（main 上核对，设计说明第 5.5 节自 6b8bc9d4 起没有改动）：
   - `harness/decisions.py` 的 `blocks_run`：只要有一条未回答、阻塞整个 run 的决定请求就为真。
   - `harness/orchestrator.py` 的 `_at_safe_node`（会话在安全节点上的停止判断）：`_stop_requested` 把 `blocks_run(decisions)` 当成停止条件，会话在自己的安全节点上看见别的会话已经写下请求，就停在那里，不写自己的请求，也没有停止原因。
   - 同文件的 `run_until_stop`：看到 `blocks_run` 就停下其余会话、结束这一轮。
   - 结论与工单写的一致：后一个会话在自己的安全节点上停下以后，永远走不到「自己也被挡住」那一步（解析调用目标），因此没有自己的那条请求。
2. 实现：
   - `harness/engine.py`：安全节点的回答（`Judgment`）多带一个事实「别的会话已经写下待恢复的决定请求」（`blocked_by_other_session`）；步骤驱动在因为这个事实停下之前，先走自己那一步（`_begin_call`：解析调用目标）。解析不出来就是它自己也被挡住，这一步的停止结果与它自己走到那一步时完全一样（`Stopped` 带 `provider_unavailable` 与调用目标的公开部分），由流程编排走同一条路写决定请求（`_end_run` → `_await_model`）；解析得出来就照常停下，不发请求。没有 Provider 门面时（假适配器的用例）不探这一步，行为与从前一样。
   - `harness/orchestrator.py`：安全节点按 `harness/decisions.py` 的新判断给出这个事实；停止判断本身没有改（别的会话写下请求以后，仍然进行中的会话照常停下，事项的状态不变，工单 #856 的口径）。
   - `harness/decisions.py`：新增 `blocked_by_other_session(decisions, department)`——有未回答、阻塞整个 run 的决定请求，且这个部门自己没有一条时为真（这个部门自己已经有一条时不重复：它写下以后就停在那里）。
   - 决定请求由每个会话各写一条、事项等这几条都回答以后再继续，这一半本来就是这样：`_answer_run_decision` 在还有未回答的阻塞请求时不交回要继续执行的 run。
3. 用例（`harness/tests/test_call_target_per_request.py`，改的是既有那条 `test_revoked_admission_blocks_the_next_request_until_retested`）：
   - 场景确定化：质检的驱动器在安全节点以前让出一次（恢复上一次激活没有处置完的工具调用那一步），先一个会话（工程）的请求就已经写下，后一个会话（质检）在自己的安全节点上看见它。没有这个让出，两个会话的驱动器在事件循环里前后相邻，余量只有一轮，第二个会话常常先走到被挡住那一步，用例就成了靠时序碰运气。夹具（`_RecordingFacade`）记录两个会话各自走到被挡住的那一步。
   - 断言：两个会话各有一条待恢复的决定请求，各写明自己的部门、模型与问题；回答其中一条以后另一条仍然待回答、事项没有继续（没有新的模型请求发出去）；两条都回答以后事项按第 5.5 节继续，被挡住的部门重新开始一轮（交付重新发出并被接受）。
   - 反向核对：把 `harness/engine.py` 里那一步暂时去掉（`if False and ...`），同一条用例失败在 `assert {'engineering'} == {'engineering', 'quality'}`——只有工程走到了被挡住那一步，正是工单写的现象。
