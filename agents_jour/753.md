# 工单 #753：集成层里发布构建那条用例偶发 worker 崩溃

## 记录

执行者 solo-minimax-M3.1-Flash / 2026-10-23 00:20 /
1. 领取与准备：标签 `ready-for-agent` 改为 `in-progress` 并认领；worktree 从 origin/main 建出，`uv sync --frozen` 装好项目环境。
2. 查崩溃的原因（工单正文列的三种可能逐一排除）：
   - 不是内存不足：崩溃前没有任何内存相关的输出，两次崩溃的进程都是在**同一个时间点**被杀掉的（见下面第 3 条）。
   - 不是构建超时：构建本身没有超时机制，超时的是测试的时间上限（见下面第 4 条）。
   - 是**测试的时间上限到了，pytest-timeout 结束了整个进程**。
3. 证据（CI 运行 39801173109 与 39808383343，集成层作业）：
   - 39801173109：worker 起来的时刻 15:03:56，崩溃时刻 15:08:53，差 297 秒；输出 `1 failed, 1220 passed`，没有一条断言失败。
   - 39808383343：worker 起来的时刻 15:50:15，崩溃时刻 15:55:11，差 296 秒；输出 `1 failed, 1224 passed, 7 errors`。
   - 两次都是「差 297 秒上下」，与集成层的时间上限 300 秒一致（少的两三秒是 worker 起来到接下这一项之间的差）。
   - xdist 的原话是 `[gw0] node down: Not properly terminated`：worker 进程直接没了，不是测试失败。
4. 机制（读 `pytest_timeout.py` 的源码确认）：
   - 根 `conftest.py` 第 16 行按层定时限，`TIMEOUTS = {UNIT: 5, MODULE: 60, INTEGRATION: 300}`，第 145 行给每一项加上 `pytest.mark.timeout(...)`；`harness/tests/layers.toml` 里 `test_release_script.py` 是集成层，因此这一项的上限是 300 秒。
   - pytest-timeout 在 Windows 上没有 `SIGALRM`，默认用线程方式；线程到点以后调用 `os._exit(1)`，**结束的是整个进程**。集成层用 `-n 4` 运行，结束的进程就是一个 worker，worker 消失以后 xdist 报「worker crashed」。
   - 这一项的上限覆盖夹具的准备阶段（`pytest_runtest_protocol` 在准备之前就装上了计时器），而发布构建（`npm ci` + Vite + `uv build --wheel`）正是在夹具里跑的，CI 上要三百多秒，正好在 300 秒上下。
5. 复现（本地，确定性）：
   - 把这一项的时间上限压到 30 秒（`.tmp/crash_repro.py` 换掉标记），运行 `PYTHONPATH=.tmp uv run python -m pytest harness/tests/test_release_script.py -n 2 --dist loadgroup -p crash_repro`；
   - 输出与 CI 一样：`[gw0] node down: Not properly terminated`，接着 xdist 换 worker 重来（gw2、gw3……每一个都在同一处被杀）。
6. 顺带查到的第二个缺陷（同一个文件、同一条发布构建路径，不修就看不到绿灯）：工单 #704（合并为 #760）给发布脚本加了一步「把这一份页面文件对应的接口版本写进 `harness/release_assets/api-version.json`」，但同一张工单里发布脚本的核对仍然要求 wheel 内的 `harness/release_assets/` 与页面构建输出**逐个相同**，接口版本记录因此被当成「页面构建输出以外的文件」，**发布脚本每一次都失败**。自 7473c01e 起 main 的集成层每次推送都红，7 个 ERROR 就是这个（`ERROR at setup of ...`，断言信息是 `wheel ... 的 harness/release_assets/ 中有页面构建输出以外的文件：api-version.json`）。本地复现：修脚本之前同一文件是 `8 passed, 7 errors`。
7. 实现：
   - `scripts/release.py`：`verify_wheel_contents` 把 `api-version.json` 当作发布资源目录里页面文件以外的**元数据**，不参与与页面构建输出的比对；另外单独核对它读不读得出它记的版本，读不出就拒绝。别的一律照旧拒绝。文件的步骤说明同步写上这一份文件。
   - `harness/tests/test_release_script.py`：
     - 发布构建的时限写在自己身上（`RELEASE_BUILD_TIMEOUT_SEC = 900`）：构建超时的时候结束那一棵进程，以一条说清原因的失败结束，worker 不消失。`_run_release` 改成自己开进程（`Popen`），超时时用文件里已有的 `_stop` 把 npm 与 vite 一起结束掉。
     - 页面文件与页面构建输出的比对不再把 `api-version.json` 算成页面构建输出以外的文件（它不是页面文件）。
     - 新增一条用例：wheel 里带着发布脚本写下的那一份接口版本记录，内容逐字相同。
   - 根 `conftest.py`：新增 `FILE_TIMEOUTS`，工作量超过本层上限的文件单独定时限（`test_release_script.py` 1200 秒，比子进程的 900 秒大，超时先由测试自己接手）。
   - `harness/tests/test_release_wheel_contents.py`（新增，模块层）与 `harness/tests/layers.toml`：模块层跑得快的用例把发布脚本的核对规则钉住——接口版本记录不算页面构建输出以外的文件、别的文件仍然拒绝、接口版本记录读不出版本也拒绝。它在 PR 的 `check` 作业里就能发现发布脚本的回归，不必等合并以后的集成层。
   - `docs/design/test-pyramid.md` 第 2.2 节与 `docs/design/web-interface-and-release.md` 第 5.1、6.1、6.3 节写明这两件事；`docs/CHANGELOG.md` 与 `docs/architecture-issues.md` 登记。
8. 关于工单正文里问的「对 CI 友好的做法（分批、限制并发、挪到专门的作业）」：查下来不是容量问题，因此没有采用那三种做法。发布构建是一条顺序的链（装依赖、构建页面、构建 wheel），限制并发不会让它变短，挪到专门的作业也不会改变「时间上限到了就结束进程」这件事；改的是**这一项的时间上限与它自己的时限**，效果落在 CI 上：集成层作业用的就是仓库里的 `conftest.py`，改动直接生效。
9. 本地自测（命令与计数行见 PR 的交付说明）：`harness/tests/test_release_wheel_contents.py` 3 passed；`harness/tests/test_release_script.py` 16 passed（修脚本之前是 8 passed, 7 errors）。
