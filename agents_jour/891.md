1. 起因与做法：刷新清单（`QueryDefinition.changed_by`）是手写的，与查询实际读到的数据早对不上。做法按用户 2026-10-24 的决定：清单宁多勿漏，会改变查询结果的事件种类要么进刷新清单，要么进这个查询的「不刷新」清单并写明理由，由一条集成层的重放核对保证。核对的做法是：用假模型跑出带项目的场景得到真实事件存储，把事件按位置逐条写进一个新的事件存储，每写一条调用一次全部已登记的查询；某条事件改变了某个查询的结果而它的种类既不在刷新清单也不在不刷新清单，用例失败，失败信息写明查询、事件种类、事件位置与变化的字段。
2. 改了哪些文件：
   - `harness/app/registry.py`：`QueryDefinition` 增加 `unchanged_by`（`UnchangedEvent` 的列表，每种带一句理由），与刷新清单写在同一处登记；`Registry.__init__` 增加两项检查——其中的种类都已登记、与刷新清单不重叠（另外拒绝同一种重复登记）。`capabilities()` 不输出这份清单，所以接口合同与能力清单的形状不变。
   - `harness/app/project_queries.py`：补齐全部清单。新增两个常量：`PROJECT_EVENT_KINDS`（项目流的全部 25 种事件）与 `RUN_EVENT_KINDS`（run 流的全部 46 种事件）。读项目流版本的三个查询（`projects.list`、`project.overview`、`project.settings`）列出全部项目流种类——项目流上任何一条事件都改变项目流版本，而版本是命令的基准，所以 `project.settings` 不会因为新建事项这类事件而页面版本过期。`project.flow` 补 `delivery_accepted` 与 `spec_accepted`（流转记录吸收的种类），`project.loop` 补 `spec_accepted`、`delivery_accepted`、`qa_submitted`、`activation_finished`，`project.overview` 补 `department_activated`、`run_created` 等，`work_item.inputs` 与 `department.workspace` 补 `spec_accepted`，`project.usage` 补 `context_assembled`。`run.export` 列出全部 run 种类（导出给出这个 run 的全部事件与投影，任何一条 run 事件都改变它）。
   - `harness/app/catalog_queries.py`：`catalog.change_impact` 补进行中事项的几种（`run_created`、`run_done`、`run_failed`、`run_paused`、`work_item_created`、`work_item_start_failed`）——结果里列出进行中的事项，事项开始与结束改变这份清单。

   - `harness/tests/layers.toml`：登记新用例文件（integration）。
   - `harness/tests/test_api.py`：`catalog.change_impact` 的逐项相等断言随清单更新（分成目录查询与影响清单两份）。
3. 重放核对的实现要点：
   - 新事件存储由 `EventStore` 建立，每写一条事件就在同一个事务里保存这个流的投影与它的决定请求（按事件前缀重放得到，与写入口做的事相同），随后 `store.notify` 让读取模型吸收。
   - 查询在一个应用层替身上执行：事件日志是新写的那一份，工件、Provider、排空状态沿用源系统，读取模型写在重放用的数据目录里（不动源数据目录）。
   - 查询参数（项目、事项、run、部门、调用尝试、事件编号）从场景的事件里取，取场景里第一次出现的那个对象：请求在整个重放中保持不变，结果的变化只来自事件本身。
   - 结果比较把快照的数据拍平成「路径 → 值」（列表元素用 `*`），只比较数据的字段；快照位置本身不参与比较。
   - 不参与比较的读数逐个写在用例里，只限设计说明第 4.2 节列出的几类：`projects.list` 的 `last_activity_at`（每条事件都更新它）、`project.loop` 的 `elapsed_sec`（已用秒数随墙钟增长）、`run.recovery` 的 `last_confirmed_position` 与 `last_confirmed_event_id`（恢复页最后确认的位置与事件）、`home.away_report` 的 `range.from_at`、`range.to_position`、`range.to_at`（离开期间报告的截止位置与截止时间）、`system.status` 的 `home.disk_free_bytes`（磁盘剩余空间）。
4. 核对测出的漏项与处置（正式场景比原型多测出几处）：`project.flow` 的 `delivery_accepted` 与 `spec_accepted`；`project.loop` 的 `spec_accepted`、`delivery_accepted`、`qa_submitted`、`activation_finished`；`project.overview` 的 `department_activated`、`run_created`、`spec_accepted`；`project.settings` 的 `work_item_created` 与 `deliverable_adopted`（版本）；`projects.list` 的 `run_created`、`department_activated`、`activation_finished`、`source_directory_configured`；`work_item.inputs` 的 `spec_accepted`；`project.usage` 的 `context_assembled`；`catalog.change_impact` 的 `run_created`；`project.attempts` 与 `run.attempt` 的 `model_message`；`run.recovery` 的 `model_requested`；`run.export` 的全部 run 种类。
   - 按工单的取舍规则处置：会改变用户据此操作的状态（版本、进度结论、事项状态、计数、影响清单）进刷新清单；只改变进度读数的高频事件进不刷新清单并写明理由——`project.attempts` 与 `run.attempt` 的 `model_message`（只改变阶段与已收到的输出条数，进行中的阶段由输出片段实时显示），`run.recovery` 的 `model_requested`（只改变已用模型步数，与已用秒数同类）。
