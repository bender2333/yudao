## 设计决定

- **事件种类**：`independent_judgement_committed` 是**应用事件**，不是骨架事件——设计说明第 5.4 节第 1 条：内核写入或读取的才是骨架事件；这个事件的读法（上下文装配看它存在、放行门引用它）是应用行为，#1190 的引用校验也读它。登记进 `harness/streams.py` 的 run 流清单、`harness/app/payloads.py` 的载荷声明（登记走 `register_application_event_types`，内核文件不动）。`models.py` 的 `EventType` 接着声明。
- **载荷**（只增，全部带默认或封闭取值）：`kind: Literal["independent_judgement"]`、`product_spec_hash`、`delivery_spec_hash`、`criteria: list[QaCriterionPayload]`（#151 的形状，字段封闭由 `_qa_criteria` 复用）、`session_id` 在信封列。旧事件没有它，投影按未知种类跳过（已实测 `apply_event` 对未登记种类静默折叠）。
- **写入口**：经提案提交路径走（`submit_review` 的 `kind=independent_judgement` 变体？）——**否**。提案种类的封闭清单在 proposal_contracts.json，`qa_review` 的通用条件（绑定当前交付、质检回执、作者分离）对独立判断并不全部成立（独立判断要刻意不看解释，可以不带检查回执）。按总图第四节「裁决」缝，它是质检的一次**写入**，不是成果：走 `submit_review` 工具会撞上 `_review` 的全部检查。落地：`WatchedOutputsTightening` 增加 `independent_judgement` 种类的提交检查（结构核对复用 `_qa_criteria` 的逐条结论核对、绑定当前 ProductSpec 与当前交付），内核提案路径照常（`kinds()` 放行这个种类 → `submission()` 组装内容 → 内核通用条件只核 `no active ProductSpec/DeliverySpec`）→ `submissions.py` 写 `INDEPENDENT_JUDGEMENT_COMMITTED`（不进 git 版本、不失效任何成果）。工具 `submit_review` 的参数 schema 需要允许这种提交（`tools.json` 的 submit_review description 加一句，不新建工具）——`tools.json` 属核心文件，补记越出清单。
- **装配侧（三条通道）**：`quality_engineering_content` 的 `explanation_visible` 判据从 `any(QA_SUBMITTED ...)` 改为 `any(INDEPENDENT_JUDGEMENT_COMMITTED 或 QA_SUBMITTED ...)`（同 delivery hash）。门在事件，不在结论：放行结论提交以前，解释就可以并入——这是设计说明第 4 节时序的原意（独立判断 → 看解释 → 下结论）。
- **裁决侧（门）**：`_review` 增加一条：提交结论（qa_review）时事件日志里必须有当前交付的独立判断事件，缺失时拒绝（字段 `independent_judgement`，字段级错误写明缺什么——与验收「不写独立判断就提交结论的提案被拒绝，字段级错误写明缺什么」对齐）。
- **内核不变式**：`harness/tests/kernel/test_judge_before_explanation.py`（清单里预登记的名字）+ 清单该条 `ready: true`。不变式：对每份交付，上下文清单里含工程解释部分的验证者请求，位置都晚于这份交付的独立判断事件。两条通道：①`quality_engineering_content` 的纯函数层（同 session 不同 delivery 的解释可见性）；②真实循环层（假模型场景：交付到达 → 质检独立判断提交 → 装配的 `context_assembled` 里才出现解释字段）。反例：预测性探索期间（还没有交付）装配的请求解释不可见（既有行为，从测试断言）。
