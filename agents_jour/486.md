## 开工前的既有事实

- `evals/runner/run_yudao_eval.py` 的 `run_once` 在 147、158、159 行引用 `void_reasons`，但全文没有赋值：真实运行必然 `NameError`。Yudao 一侧现有的材料路径核对也没有调用点。本工单必须补上，否则验收二无处落地。
- 摘要原先在 evals 里不存在；场景 2 已有 `materials/manifest.json`，场景 3 只有给被测方看的 `materials/start/files/manifest.json`。
- 场景 3 的上游仓库是 `AGI-Eval-Official/PRDBench`（`docs/archive/research/evaluation-benchmarks.md` 第 42 行，MIT）；场景 2 是 `openai/openai-agents-python`。
- 材料文件在 git 索引里是 LF，本机签出是 CRLF（`core.autocrlf=true`），因此摘要必须按 LF 规范化才算，否则换机器就失效。
- `evals/tests/` 下只有 `__pycache__`，场景目录里没有 `.pyc`；一旦有进程在 `checks/` 里写过字节码，递归摘要就会失效，所以摘要的遍历跳过 `__pycache__` 与 `*.pyc`。
- Yudao 的命令文本确实进入事件日志导出：`harness/environment.py:530` 的 `meta` 带 `command`，它成为工具回执的载荷。所以在导出 JSON 上做原文子串查找是有依据的。
- 场景 2 的 `checks/tests/models/test_kwargs_functionality.py` 与上游那份差 5631 对 5808 字节，只是换行差异，不是材料被改。

## 决定

- 摘要的规范化形式：读字节 → `replace(b"\r\n", b"\n")` → SHA-256，字符串写成 `sha256:<hex>`，与 `harness/artifacts.py` 的现有约定一致（evals 不导入 harness，只沿用格式）。
- 目录条目的摘要是「相对路径 + 文件内容摘要」按序拼接后再取摘要，改名、增删文件都会改变摘要。
- 登记在 `materials/manifest.json` 的 `digests` 块里：`algorithm`、`note`（LF 规范化、递归、跳过 `__pycache__` 与 `*.pyc`）、`entries`。场景 2 沿用已有清单，场景 3 新建同形清单。键用正斜杠（`materials/requirement-table.json`），Windows 的反斜杠只出现在本机路径上。
- 摘要算在场景目录的材料原件上，不算评分目录的副本：评分目录紧接在运行之后从原件 `copytree` 出来，两者相同，而真正要防的是被测方在运行途中改掉仓库里的原件。
- 核对点放在 `run_once` 里、`score_delivery` 之前，不放进出 `score_delivery`：`evals/scenarios/scenario-2/validate.py` 把 `score_delivery` 当材料自检调用，放进去会让自检依赖摘要、循环。
- 上游访问的查找用地址的四种写法：带协议、不带协议、scp 形式（`github.com:owner/repo`）、以及各自在 JSON 文本里的转义形式。只用 `.git` 结尾的形式会漏：实测上游树里 `github.com/openai/openai-agents-python` 出现在 17 个文件（含 `pyproject.toml` 的 `Homepage` 与 `Repository`），没有 `.git` 形式。
- 场景 2 只登记 `UPSTREAM_URL`（`.git` 结尾）作为查找地址，不为它单独加裸 slug 形式：场景 2 的运行目录就是上游仓库的签出，`pyproject.toml` 里本来就有这个地址，找裸 slug 会把每次运行都判无效。
- 作废原因字符串沿用现有风格，与材料路径同一条处理：
  - `材料摘要与材料版本记录不同：<条目>`
  - `JSON 输出中出现对上游仓库的访问：<地址>`（OpenCode）／`事件日志导出中出现对上游仓库的访问：<地址>`（Yudao）
- Yudao 一侧新增纯函数 `yudao.void_reasons(text)` 汇总三项（材料路径、材料摘要、上游仓库），`run_once` 调用它；OpenCode 一侧沿用原有的内联写法，只增补两项。
