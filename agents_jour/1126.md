3. **判定：这是工具（测试辅助）写法的问题，不是产品行为的问题。** 产品代码一行不动：`harness/event_store.py` 的打开方式是对的，失败来自测试辅助在「进程刚被终止、文件还被短暂占用」的那一刻打开事件库而只对探测做了重试。证据是两条失败都停在 `process_kill.interrupted` 终止子进程之后的重新打开这一步（正文记的两个运行链接），而同一提交重跑即通过；`EventStore.__init__` 里除了 WAL 与建表之外没有可改的行为。
4. 读代码确认根因的形状：
   - 原来的 `_open_system_after_kill` 是「先 `_open_writable_after_kill` 探测到可写打开成功（含设置 WAL），关掉，再 `LoopSystem.for_testing` 打开系统」。探测与系统的打开是两次独立的打开，探测成功只说明那一刻能打开，不保证下一次也能打开；系统自己那次打开没有重试，撞上占用就抛 `OperationalError`。
   - 核对「打开事件库是不是 `LoopSystem` 启动序列里第一件有副作用的事」：`harness/runtime.py` 的 `__init__` 依次是 `data_dir.mkdir(parents=True, exist_ok=True)`（幂等）、`self.store = EventStore(...)`、`writes.rebuild_missing()`、`finish_drain_on_startup()`、`settle_pending_on_startup()`、`create_missing_revision_runs_on_startup()`、补建普通事项 run、强制升级、`resume_startup_runs()`。事件库的打开在补做结算、补建 run 与启动恢复之前，因此这一步失败时启动序列一步都还没做，整个构造可以重来。
5. 实现（只改 `harness/tests/process_kill.py`）：
   - `_open_system_after_kill` 改成对整个 `LoopSystem.for_testing` 重试：捕 `sqlite3.OperationalError`，每 0.2 秒一次，等到 `STARTUP_TIMEOUT_SEC`（300 秒）为止，超过上限照常抛出原来的错误（`raise`，不包装、不吞掉）。等待条件写清了：等的是被终止的进程留下的占用释放——Windows 上进程退出与它占着的文件真正可以再打开之间有一小段间隔（句柄回收、WAL 的 `-wal` 与 `-shm` 收尾都晚于进程退出）。重试次数逐次写进 stderr（`打开事件库失败，第 N 次重试：<原错误>`），CI 日志里能读出来试了几次。
   - 新增 `_failed_on_the_store_open`：只有「构造系统时第一次打开事件库」这一步失败才重试。判断落在调用链上——`for_testing → LoopSystem.__init__ → EventStore.__init__`，紧跟 `__init__` 的下一帧在 `event_store.py` 里就是这一步。启动序列里的某一步失败（补做结算、补建 run、启动恢复）时中间会多一层，那种情况不重试，否则这些步骤会做两次。文件名取自 `LoopSystem.__init__` 与 `EventStore.__init__` 的 code object，不写死字符串。
   - 删掉 `_open_writable_after_kill`：它的作用（等到可写打开能成功）被这次的重试完全覆盖，留着会多等一遍、而且它的假设（探测成功以后文件就不再被占用）正是本次要否掉的。文件里已没有调用者（`docs/CHANGELOG.md` 第 384 行是 #876 的历史记录，按规矩不改历史条目）。
   - 用例与断言一行没改：`interrupted`、`restarted` 的签名与行为不变，四个用它的地方（`interrupted` 的 before、after 与 `restarted` 的 before、after）都走这一个函数。

   - 场景一（占住文件）：有重试时等到占用释放、成功；把重试拿掉（`deadline` 取当前时刻，等价于只试一次）后立刻失败：`OperationalError: unable to open database file`，1.5 秒后抛出（1.5 秒是 SQLite 自己在 Windows 上的打开重试）。还原后再次成功。这一条是反向验证的主证据：同一触发手段下「拿掉重试就失败、加回重试就通过」。
