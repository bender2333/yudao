2. 根因：`harness/projection.py` 的 `apply_event` 处理 `DEPARTMENT_ACTIVATED` 时无条件执行 `state.active_department = event.department`。询问分支会话的激活（`harness/orchestrator.py` 的 `_run_ask_branch` 写入的 `DEPARTMENT_ACTIVATED`，department 是被询问部门、session_id 是分支会话）因此把 run 的「所在部门」改成了被询问部门；提问方拿到回答以后继续工作，它的主线会话不会再次写 `DEPARTMENT_ACTIVATED`，这个值就一直停在被询问部门（正文里的 67 分钟）。
3. 这不是 #557 引入的：这行赋值从 #201（`dcd742f1`）起就是这样，询问分支从 #624（`3be89ae5`）起就有了；#557 以后一个事项里同时有几个会话在跑，旁支工作的激活更容易改写所在部门，现象因此更容易被看到。
4. 取值链（三处页面与失败事件读同一份来源）：`harness/projection.py` 的 `RunProjection.active_department` → `harness/projects.py` 的 `item.department`（`project.overview` 的 `work_items[].department` 与 `project.loop` 的 `department`，事项卡与楼层页读它）、`harness/app/project_queries.py` 的 `_room_status`（部门页的「工作中」）、`harness/orchestrator.py` 的 `_fail`（`RUN_FAILED` 事件的 department）。
5. 实现：`harness/projection.py` 改一处——询问分支会话的激活不改写 `active_department`，所在部门只由主线会话的激活推出。没有改别的地方：`PRODUCT_INPUT_ASSIGNED` 仍然把所在部门写成产品（那是「这件事分给了产品」的事实），分支的激活仍然推进 `cycle_count`（轮次口径另记，见下）。
