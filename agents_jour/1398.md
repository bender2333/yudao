执行者 solo-deepseek-v4.1-flash / 2026-11-03 02:10 / 决定与自定的边界：

1. 两个字段的形状。`ActionReceipt` 加 `tree_change`（`TreeChange`：`before_digest`、`after_digest`，两个相同即没有改动公开树）与 `after_snapshot_ref`（`SnapshotRef`：`kind`、`content_hash`、`path`、`media_type`，与事件载荷的 `after_snapshot_ref` 同形）。两项都是 `| None = None`，旧回执读出来为空，字段只增。「前后差异」按设计说明与总图写成两个树摘要而不是改动清单：工单正文写的就是「动作前后的树摘要」。
2. `SnapshotRef` 与 `ArtifactRef`（`harness/models.py`）同形但不在合同里导入它：`harness/actions.py` 是内核模块，只允许导入内核文件、标准库与 pydantic（`harness/definitions/kernel-manifest.json` 的 `allowed_imports`）。`SnapshotRef.model_dump()` 可以直接给 `ArtifactRef(**…)`，读的一方按工件区域取回。
3. 快照内容由合同给出：`snapshot_payload(tree)` 放进 `harness/actions.py`，`engine.py` 的 `_tree_snapshot` 改成调用它。这样回执里的终点快照与事件 `tool_started`／`tool_called` 上的快照是**同一份内容、同一个工件**（内容寻址，同一个 run 下路径相同，`put` 幂等），读回执的一方不用再去事件载荷里找。这是「只改」清单外的 `harness/engine.py`（只改函数体与一行导入），已在工单评论里补记。
4. 取不到公开树时这两项为空，不让动作失败：工作区里有无法表示的条目（链接、重解析点、硬链接、特殊文件）时 `_tree_facts` 返回空，动作照常执行——否则能修好工作区的动作（例如删掉那个条目）会被挡住。这一条是设计没写到的边界。
5. 没有工件区域时不造引用：直接构造的 `LocalEnvironment`（测试、没有工件区域的旧用法）与没有给出工件区域的第二种实现只交回两个树摘要，`after_snapshot_ref` 为空。生产路径上 `Workspaces` 会给执行环境工件区域与 run，两个字段都有。
6. 拒绝与「取消先于动作到达」的回执不带这两项：动作没有执行，没有终点可报。动作执行了但出错（`except Exception`）时照样带上，读回执的一方据此判断工作区有没有被改动。
