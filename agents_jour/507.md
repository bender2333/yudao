## 2026-10-14 交付（第 2 轮）

### 审查意见与对应

第 1 轮审查 FAIL 的唯一未过项：`test_changed_tree_after_delivery_rejects_the_stale_release` 的迁移把验证点架空。
`checks=[]` 使拒绝原因退化成「release requires quality-run evidence bound to the current snapshot」，
与树变不变无关（审查给的两条反向证据：不改树也被拒、错误只有 `checks` 字段）。

### 新契约下为什么必须改构造方式

- #481 之后质检的检查工作区每次激活从「当前最新的封存交付」建立（`orchestrator.py:468-478`、
  `_inspection_source_tree`），提交时 `facts.digest` 就是这份快照；改运行工作区对它没有影响。
- `_accept_review` 的拒绝链：`basis_delivery_spec_hash` 不符（`validation.py:548`）、
  `code_tree_digest != facts.digest` → `code_snapshot_hash`（553-554）、
  检查回执绑定（555-575）、release 要求 `bound_checks` 非空（582-585）。
  质检激活开始时工作区已重建为最新封存，`code_snapshot_hash` 在同一次激活内不可达；真实可达的
  「过期」来源是「质检依据的那份交付已被新的封存取代」。

### 改动（`harness/tests/test_range_edit.py` 内只改这一个用例）

1. 场景换成真实协作：产品规格 → 工程交付 A → 质检退回重交付（`collaboration_request(..., action="revise_delivery")`）
   → 工程重新封存交付 B（文件内容不同，`code_tree_digest` 变）→ 工程应答 → 质检第六次激活提交放行。
2. 质检这次激活真实跑 `run_check`（`checks={"smoke": 0}`），回执绑的是新封存快照；
   放行结论却声明依据退回前面对的旧交付 A。
3. 断言改为逐字核对拒绝原因：
   `[error["field"] for error in errors] == ["basis_delivery_spec_hash"]`，
   message 含 `submitted artifact is based on {original!r}` 与新交付 hash，
   并显式断言没有 `checks` 字段错误（拒绝原因不是缺检查证据）。
4. 顺带删掉第 1 轮为 `checks=[]` 构造引入的 `prompt_part` 导入（新实现不再读请求里的当前交付），
   `delivery` 导入本来就不是本用例用的（净删除核对见下）。
