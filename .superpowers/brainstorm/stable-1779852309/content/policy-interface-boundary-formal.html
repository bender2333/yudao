Policy / Gate: v0.1 Boundary

This part stays intentionally thin: reserve interfaces, avoid deep governance design.

Principle
Do Not Over-Design

Policy/Gate is an orchestration boundary, not a business rule engine in v0.1.

The Process Orchestrator reads structured facts and autonomy mode, then decides whether to continue, ask, route, pause, or gate. It does not judge product/business content itself.

Do
  • Reserve gate interfaces
  • Store autonomy mode per loop/node
  • Record why a gate was triggered
  • Allow runtime and node outputs to request approval
  • Make routing decisions auditable as events
Do Not
  • Build enterprise approval workflow now
  • Hard-code every security policy
  • Encode business semantics in the orchestrator
  • Turn gates into manual review everywhere
  • Block the MVP on complete governance
Reserved Interfaces
Minimal v0.1 Contracts
GateRequest {
  mission_id
  loop
  node_run_id
  reason
  risk_level
  autonomy_mode
  required_decision
  recommended_action
}

GateDecision {
  approve | reject | ask | route | pause
  decided_by
  rationale
}
Where It Fits
Runtime to Orchestrator to Mission

DAG Node emits facts and route recommendation.

Process Orchestrator applies mode/policy boundary and writes the decision.

Mission Event Stream records gate requests, decisions, and routing results.
