Mission Big-loop State Model

The big loop has its own long-running state, memory, backlog, and feedback signals.

Mission State
Lifecycle graph, not a linear pipeline
exploring
  -> changing
  -> verifying
  -> operating
  -> learning
  -> exploring / changing / child_mission / archived

MissionState is separate from SpecChange state. SpecChange tracks one bounded change; MissionState tracks long-running evolution.

Long-term Context
MissionMemory
  • Goals and non-goals
  • User preferences
  • Architecture decisions
  • Failure patterns
  • Runtime lessons
  • Open and closed risks
MissionBacklog
  • Follow-up ideas
  • Deferred improvements
  • Unresolved questions
  • Tech debt
  • Operational issues
  • Child mission proposals
Feedback Signal
Operations and external world input
FeedbackSignal {
  source
  signal_type
  severity
  evidence
  related_artifact
  related_specchange
  suggested_classification
  received_at
}
Planner Usage
Why the next workflow changes

SpecChange explains bounded work.

MissionState explains where the long-running mission is.

MissionMemory explains why future workflows should be generated differently.

FeedbackSignal explains why the big loop should move again.
