EvoAgentX 借鉴地图

结论不是“拿来做底座”，而是“借鉴骨架 + 平台级重写执行、权限、审计和恢复”。

Reuse boundary for the software-dev multi-agent platform
Adopt
可直接借鉴为产品模型
  • WorkflowGraph / Node IO 契约
  • Agent / Action 双层抽象
  • Environment 轨迹留痕
  • Benchmark / Evaluator 评估闭环
Adapt
保留思想但要改造
  • 固定角色池替代动态 agent 生成
  • 确定性生命周期替代 LLM 任意调度
  • MCP / ToolKit 变成受控能力目录
  • HITL 变成异步审批系统
Rebuild
必须平台级重写
  • 持久化 run / step / artifact
  • 权限、沙箱、凭证、网络边界
  • 幂等、恢复、重试、取消
  • 审计事件和团队级记忆治理
Later
MVP 后再启用
  • TextGrad / MIPRO prompt 优化
  • SEW / AFlow 结构进化
  • 自动修改线上流程模板
  • 复杂 workflow 自生成
Product Domain
需求 -> 设计 -> 任务 -> 代码 -> PR -> 发布 -> 运维

平台保存事实、状态、权限、证据、决策。

→
Adapter
EvoAgentX-style graph adapter

把阶段和制品映射为 node inputs / outputs / actions。

→
Runtime
Codex / Claude Code / Hermes / CI / Sandbox

执行、测试、审查、提交 PR，全部产生审计事件。

建议的复用判断

A

推荐：EvoAgentX-style kernel adapter

平台不 fork 成 EvoAgentX 平台版，而是在产品领域模型和执行 runtime 中间放一层兼容其 graph/action/evaluator 思想的 adapter。

B

不推荐：直接 fork 改平台

短期快，但 HITL、app、tool、storage 都偏 demo/SDK，后面会把权限、审计、运行时和框架代码缠在一起。

C

保守：只学概念，全重写

长期最干净，但浪费 EvoAgentX 在 workflow、tool、evaluator、optimizer 上已经形成的抽象经验，MVP 验证会慢。
