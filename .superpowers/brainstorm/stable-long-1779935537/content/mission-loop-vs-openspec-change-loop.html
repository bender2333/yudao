Mission Loop vs OpenSpec Change Loop

Mission owns the long-running lifecycle. OpenSpec-style artifacts own bounded change contracts inside it.

Corrected Boundary
Mission 大循环

Long-running evolution system.

  • Mission state and history
  • Loop routing across months
  • Child missions and relations
  • Operations feedback
  • Strategic progress and learning
OpenSpec 小循环

Bounded change contract.

  • One proposal/change
  • Scenario acceptance
  • Design and tasks
  • Verification evidence
  • Archive to canonical spec
Composition
A Mission contains many bounded SpecChange loops
Mission
  MissionLoopState
  MissionEventStream
  MissionMemory / Learning
  MissionRelation

  SpecChange #1  -> OpenSpec proposal/design/tasks/specs/verify/archive
  SpecChange #2  -> OpenSpec proposal/design/tasks/specs/verify/archive
  IncidentChange -> OpenSpec proposal/design/tasks/specs/verify/archive

  DAGRun / NodeRun execute each SpecChange loop
Routing Rule
Who decides what?

OpenSpec answers: Is this bounded change clear, designed, implemented, verified, and accepted?

Mission answers: What should happen next in the long-running product evolution?

Process Orchestrator answers: Given facts from SpecChange, DAG nodes, ops signals, and policy boundary, where do we route now?

Updated Principle
SpecChange is not the Mission

OpenSpec-style artifacts are ideal for a bounded task/change.

The Mission 大循环 needs its own durable state model, roadmap/memory, feedback handling, relation graph, and evolution logic.
