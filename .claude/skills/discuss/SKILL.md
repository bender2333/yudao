# 讨论

流程的正本是[工作方式](../../../docs/agents/workflow.md)。讨论的产出是结论，不是代码，也不是设计说明。

## 何时用 / 何时不用

- 用：用户带来一个新想法；一张工单或一个帖子里的问题要先想清楚；`/triage` 认为要讨论的报告。
- 不用：总图、规则与理念（总架构师的会话）；已经有结论、只差写成设计说明（直接 `/to-design`）；方向看不清、一次会话讨论不完（`/wayfinder`）。

## 先读什么

总图里相关的那一节、`CONTEXT.md`、相关的需求记录、ADR 与设计说明。

## 步骤

1. **定位**：在总图里找到这件事属于哪一节、哪个方框或哪道缝。总图里没有位置的，停下来，开 `architecture` 工单交总架构师，不自己加方框或缝。完成：能说出总图位置。
2. **追问**：调用 `grilling` 与 `domain-modeling` 两个技能，逐项追问需求与边界；术语定下来就写进 `CONTEXT.md`，难以撤销的决定写成 ADR。先给出自己的判断，只把真正要用户定的事留给用户。完成：每个开放问题有了答案，或者明确留作设计说明的「未决问题」。
3. **查证**：答案取决于外部事实（文档、第三方接口、参考实现）的，调用 `research`；参考实现先看 OMP 与 OpenCode（共同规则「参考实现」）。完成：每个事实有出处。
4. **看效果**：要看到才能判断的，调用 `prototype`。页面原型不带画面、用假数据、能点，交给用户试用；画面只画单页草图回答设计问题。原型定稿时，改 `docs/prototypes/CHANGELOG.md` 开头的「当前定稿」一行，并把开放工单里引用旧版本的路径改成新版本。完成：用户对原型给了结论。
5. **记结论**：结论写进 `docs/decision.md` 与 `claude_jour.md`；用户的原话进需求记录，不改写。完成：结论有总图位置、定了什么、还剩什么。

## 常见借口

| 借口 | 为什么不行 |
| --- | --- |
| 「这个想法很小，不用在总图上找位置」 | 找不到位置的东西就是总图之外的东西，要先交总架构师 |
| 「用户没说，按常见做法定了」 | 先给判断，但要用户定的事要问出来 |
| 「讨论到这里顺手把设计说明也写了」 | 结论和设计分开；设计按 `/to-design` 与设计说明规范写 |
| 「能跑一下看到的，问用户就行」 | 能观察到的事实用原型或实验定，问用户的只留偏好与走向 |

## 危险信号

- 讨论里出现了函数名、字段名和枚举值。
- 术语表里的词和讨论里用的词不一样。
- 结论只在对话里，没有落进任何文件。

## 交付

结论清单：总图位置、定了的事、留给设计说明的未决问题、改了哪些文件（`CONTEXT.md`、ADR、需求记录、决策记录）。下一步是 `/to-design`。
