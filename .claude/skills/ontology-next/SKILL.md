# 该做什么了（本体）

本体在 `tools/yudao-ontology/`，方案见 `tools/yudao-ontology/reports/skill-plan.md`。这个技能只做一件事：跑 `next.py`，把它算出的结果讲给用户。推理与检查都在脚本里，技能自己不下判断。

## 何时用 / 何时不用

- 用：用户问「该做什么了」「本体看一下」「设计里哪里不一致」「哪些设计了还没实现」；或者给了一个提交，要看那一版。
- 不用：要读 GitHub 上工单与里程碑的状态、挑下一张工单（那是 `/next`）；要看缝在代码里立住没有（那是 `/seam-diff`）；要全量扫文档的写法与术语（那是 `/doc-scan`）。三者看的东西不同，可以先后用。

## 先读什么

- `tools/yudao-ontology/aligned.json`：模型最后对齐的提交。
- 上一次的结果不读。每次都从提交算，不靠会话记忆，也不靠 `reports/next/` 里的旧文件。

## 步骤

1. `git fetch origin main`，确定提交：用户给了就用用户的，没给用 `origin/main`。完成：手上有一个提交号。
2. 在 `tools/yudao-ontology/` 下运行 `python3 next.py <提交>`（要 Java 与 `rdflib pyshacl owlready2`，缺了先装）。完成：打印出结果，`reports/next/<提交>.md` 写好。
3. 先讲第一行：模型对这个提交跟不跟得上。没跟上时，明说下面的结论只到模型对齐的那一版，并列出对不上的原句与没抽的段落。完成：用户知道结论可信到哪一版。
4. 按四类讲，每类先说条数，再说最要紧的一两条；每条带原句、文档节号与提交。代码的带文件与行号。第四类只说条数和例子。完成：用户能从这一段直接回到原文。
5. 讲建议，照脚本排的先后；有工单草稿的说草稿写好了、等用户开；几种做法时列出来，标倾向与理由，不替用户选。完成：用户知道先定什么。

## 常见借口

- 「这类结果上次也有，不用再跑了。」上次的提交不是这次的提交；每次都跑。
- 「脚本没报，就说明没问题。」脚本只覆盖模型里有的；覆盖范围在结果第二行，没列的文档要照说「模型不知道」。
- 「顺手把模型改一下，结果就对上了。」这个技能只报告。原句对不上、段落没抽，报给用户，不改模型；改模型是增量更新那一步的事，还没做。

## 危险信号

- 结果里没有提交号，或者讲的时候没说模型对齐到哪一版。
- 把第三类的「定义文件里有、设计没写」讲成推理出来的必然；它是对照，推理出来的只有「推出的空位」。
- 没有出处原句就下结论。

## 交付

- 对用户：一段话的结论，四类各几条与最要紧的，按先后的建议。
- 文件：`tools/yudao-ontology/reports/next/<提交>.md` 与 `.json`，是生成的，不手改。
