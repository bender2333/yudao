# 该做什么了（本体）

本体在 `tools/yudao-ontology/`，方案见 `tools/yudao-ontology/reports/skill-plan.md` 与 `change-impact-plan.md`（第 0 节是设计前提：神经和符号互相反馈）。这个技能只做一件事：跑 `next.py`，把它算出的结果讲给用户。推理与检查都在脚本里，技能自己不下判断。

## 何时用 / 何时不用

- 用：用户问「该做什么了」「本体看一下」「设计里哪里不一致」「哪些设计了还没实现」；或者给了一个提交，要看那一版。
- 不用：要读 GitHub 上工单与里程碑的状态、挑下一张工单（那是 `/next`）；要看缝在代码里立住没有（那是 `/seam-diff`）；要全量扫文档的写法与术语（那是 `/doc-scan`）。三者看的东西不同，可以先后用。

## 先读什么

- `tools/yudao-ontology/aligned.json`：模型最后对齐的提交。
- 上一次的结果不读。每次都从提交算，不靠会话记忆，也不靠 `reports/next/` 里的旧文件。

## 步骤

1. `git fetch origin main`，确定提交：用户给了就用用户的，没给用 `origin/main`。完成：手上有一个提交号。
2. 在 `tools/yudao-ontology/` 下运行 `python3 next.py <提交>`（要 Java 与 `rdflib pyshacl owlready2`，缺了先装）。完成：打印出结果，`reports/next/<提交>.md` 写好。
3. 先讲第一行：模型对这个提交跟不跟得上。没跟上时，明说下面的结论只到模型对齐的那一版，并列出对不上的原句与没抽的段落。完成：用户知道结论可信到哪一版。
4. 按四类讲，每类先说条数，再说最要紧的一两条；每条带原句、文档节号与提交。代码的带文件与行号。第四类只说条数和例子。完成：用户能从这一段直接回到原文。
5. 对齐点不是这次的提交时，讲「零、对齐以后的变动」：自动能接上几条原句、要用户点的改名（每条一句，旧 → 新，用在模型哪里）、改写几句、删掉几句、哪里还用旧词。全文在 `reports/changes/<旧>..<新>.md`。完成：用户知道模型落后多少、哪些不用他管。
6. 讲建议，照脚本排的先后；有工单草稿的说草稿写好了、等用户开；几种做法时列出来，标倾向与理由，不替用户选。完成：用户知道先定什么。
7. 用户点了改名就记：`python3 renames.py confirm <旧> <新>`，说不是就 `reject`。用户说跟上，先跑 `python3 heal.py <提交>` 试一遍，把会改什么、三道过没过讲给他；他再点头才 `--apply`。改写的句子他判过意思没变，才加 `--accept 序号`。删掉的句子与新加的段落是意思变了，要重抽，不归 `heal.py`。完成：模型跟上，或者用户知道还差哪几句。

## 常见借口

- 「这类结果上次也有，不用再跑了。」上次的提交不是这次的提交；每次都跑。
- 「脚本没报，就说明没问题。」脚本只覆盖模型里有的；覆盖范围在结果第二行，没列的文档要照说「模型不知道」。
- 「顺手把模型改一下，结果就对上了。」没有用户点头不改模型。点头以后也只走 `heal.py`：三道检查过了才写回。
- 「这个违例惹麻烦，把那条断言删了。」原句还在的断言不删；违例照实报。删掉会把真矛盾藏起来。
- 「候选看着像改名，替他确认了。」改名要用户点；只有术语表证据的才算确定。

## 危险信号

- 结果里没有提交号，或者讲的时候没说模型对齐到哪一版。
- 把第三类的「定义文件里有、设计没写」讲成推理出来的必然；它是对照，推理出来的只有「推出的空位」。
- 没有出处原句就下结论。
- 模型没跟上就讲违例：先分清是模型过期（原句对不上）还是设计真矛盾。

## 交付

- 对用户：一段话的结论，四类各几条与最要紧的，按先后的建议。
- 文件：`tools/yudao-ontology/reports/next/<提交>.md` 与 `.json`，`reports/changes/<旧>..<新>.md`，都是生成的，不手改。
