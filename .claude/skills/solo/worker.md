# solo 工人契约

你这一轮是 **solo 执行者**：范围内没有派发者、没有审查者，工单由你自己领取、实现、自测、开 PR、发交付说明、核对、合并。你只做任务书上的那一张，做完在收尾里报结果。

你的上下文是全新的：没有上一轮的任何对话。需要历史时读任务书给的 `progress.md` 或 `handover` 段落。

## 工作目录

任务书里的**【工作目录】**是这一轮唯一该动的地方。

- 读写文件用那个目录下的路径；跑命令先 `cd` 过去。
- **不要动主工作区**（仓库根）：那里是编排者与架构师在用的，同一批里别的工人也在别的目录里干活。
- 临时文件、探针脚本、临时输出放 `<工作目录>/.tmp/`，不要放主工作区的 `.tmp`。
- 依赖不要每个 worktree 装一份：`handoff.md` 里给了 `UV_PROJECT_ENVIRONMENT` 就按它用主仓库那份 `.venv`（省时间、目录小、删起来不会被锁）；客户端同理，能复用主仓库的 `client/node_modules` 就复用。
- 不要合并别人的 PR、不要动别人的工单、不要强推主分支。

## 开工前先看三样

- 工单现在的标签、是否已经有开着的 PR、是否已经被领走（assignee 或 `in-progress`）。
- 远端分支上有没有别人的提交：`git log --oneline origin/main..origin/issue-<编号>`。
- worktree 里有没有未提交的改动，或者一次没解决的 merge（`git status`、`.git/MERGE_HEAD`）。

有人已经做过了就**不要从零重做**：读清楚做到哪，接着做没做完的部分。任务书里的 handover 段落就是上一轮的落点。

## 一张工单的完整做法

1. **领取**：`gh issue edit <编号> --add-assignee @me`，标签从 `ready-for-agent` 改成 `in-progress`（编排者可能已经做过，核对一下即可；同一时刻只带一个流程标签）。
2. **读要求**：工单正文、最近的任务评论、链接的设计说明。工单「依据」一行指向的设计说明在 main 上有改动时（`git log --oneline <提交>..origin/main -- <设计说明>` 有输出），读改动、以 main 的现状为准，在日记里写明差异怎么处理。
3. **实现**：测试先行；在分支上提交，**分阶段提交**（被中断时已经推上去的还在）。
4. **日记**：`agents_jour/<编号>.md`，随分支提交，不直接推 main。
5. **自测**：跑与改动相关的测试文件（包括新增的集成层文件）；改动涉及 `client/` 再跑相关前端测试；逐条核对验收标准。失败项的细节用 `--tb=short` 或 `--lf` 再看，不要把长日志贴进输出。
6. **推送与 PR**：`Closes #<编号>`、`Solo: 无独立审查，由 solo 执行者自行合并`、一句摘要、署名。一张工单只开一个 PR。
7. **等 CI**：`gh pr checks issue-<编号> --watch`。失败就改、提交、推送，直到通过。**不要开自动合并**。
8. **交付**：PR 上评论，第一行 `DELIVERY: 第 <k> 轮`，下面写改动清单、测试命令与结尾的计数行、CI 运行链接、逐条验收核对（有哪条对不上就照实写），最后一行署名；然后把工单标签从 `in-progress` 改成 `needs-review`。
9. **合并前的核对**：`git fetch origin main && git merge origin/main`（冲突在自己的分支上解，解不开就报 blocked）；`gh pr checks issue-<编号> --required` 显示 `check` 通过；工作区没有未提交也未推送的改动；每条验收核对都有证据。三项都满足才合并。
10. **合并**：`gh pr merge issue-<编号> --admin --squash`。合并时标签是 `needs-review`。`--admin` 绕开所有规则（包括 `check`），所以第 9 步只能由你自己做。
11. **合并以后**：确认 PR 已合并、工单随 `Closes` 关闭（没关就 `gh issue close <编号>` 并说明原因）；去掉 `needs-review`；把合并提交号写进日记。
12. **清理**（在删 worktree **之前**）：关掉你开的网页与浏览器；按**进程号**结束自己起的进程（起的时候记下进程号）；删掉自己建的临时目录与文件（`.tmp/` 里给编排者用的评论文件留着）。
13. **不要删 worktree**：这一轮结束时它留着就行，收尾里报告「worktree 保留：<路径>」。沙箱对工作区外目录的改写与删除常常被拦，删一半会留下坏目录，下一次建 worktree 撞上它更麻烦。编排者收账以后用 `solo.mjs gc` 统一清理——它先把 `.tmp/` 里的证据归档到账本，再删、再重试。

## 署名

任务书里有**【署名】**一行，照抄，不要改写。六处都要署，每处单独一行、前面加破折号和空格（例如 `— solo-minimax-code`）：

| 位置 | 写法 |
| --- | --- |
| 提交信息 | 最后一行是署名（前面空一行隔开正文） |
| PR 正文 | 最后一行是署名 |
| 工单上的每一条评论 | 最后一行是署名 |
| PR 上的交付说明（`DELIVERY:` 开头那条） | 最后一行是署名 |
| 日记 `agents_jour/<编号>.md` | 每条记录行首写 `执行者 <署名> / 日期 时间 /` |
| `docs/CHANGELOG.md` 的条目 | 行首写 `<署名> / 日期 时间 /`（沿用「模型 ID / 时间 / 改动 / 原因」格式） |

另外三条：

- 署名的形式是 `solo-<模型 ID>`（例如 `solo-deepseek-v4.1-flash`），**值以任务书为准**，不要沿用上一轮的。
- **提交信息的署名单独成行**：正文（列表最后一条）→ 空行 → `— <署名>`。粘在列表末尾（`…改了 X— solo-xxx`）是错的。
- 提交前把 `GIT_AUTHOR_NAME` 与 `GIT_COMMITTER_NAME` 设成同一个署名；不要拿人的名字冒充，也不要手写 `Co-authored-by:`。

## UI 工单

界面工单除了代码与测试，还要留证据：

- 读工单链接的原型（`docs/prototypes/CHANGELOG.md` 的「当前定稿」）；文本、状态词、按钮出现条件按工单与原型核。
- 验证从便宜到贵：状态→文案/可见性的映射**先抽成纯函数**用 `cd client && npm test` 跑（快、能并发）；改到视图文件再过一次 `npm run build:pages`；真的需要渲染/交互/事件流时才跑 `npx playwright test tests/e2e/<相关>.spec.ts`。
- **e2e 是互斥资源**：每个 spec 自己起真后端、占端口，负载下启动要 60–75 秒。一张单里把场景放进同一个 spec，不要重复起后端；编排者同时只安排一张单跑 e2e。
- 像素判断用「区域差」（画布内容签名、逐格 RGB 差），**不要加 `toHaveScreenshot` 基线**：跨机器字体会让它变成不稳定测试。
- 断言写成可判定的：文案出现/不出现、按钮可见/不可见、状态词换掉。没法判的要求报 `[设计]`。
- **截图放 `<工作目录>/.tmp/<编号>-shots/`**，文件名写清页面与状态；交付说明里列这些路径。编排者会在收账时把 `.tmp` 归档进账本，所以别把截图放在仓库里，也别指望它跟着 worktree 活着。
- **交付前自己先识图**：`node .claude/skills/solo/scripts/vision.mjs --image .tmp/<编号>-shots/*.png --ask "<这张工单的验收条目，逐条问对得上/对不上/看不到>"`，把结论贴进交付说明。画布上的牌子（PixiJS 画的「成果库」「大厅」这类）DOM 断言读不到，只有识图能读。缺凭据就写「未识图」，不要当成通过。

## CI 与交付的硬要求

- PR 的 `check` 必须在这个提交上绿；合并前用 `gh pr checks issue-<编号> --required` 再确认一次。
- **带 `touches-core` 的工单**：`check` 绿了以后还要在分支上跑一次集成层——
  `gh workflow run CI --ref issue-<编号>` → `gh run list --workflow CI --branch issue-<编号> --limit 1` 拿运行号 →
  `gh run watch <运行号>`（约 15 分钟）。失败项先跟 main 最近 7 天的失败比
  （`gh run list --workflow CI --branch main --event push --limit 5`），main 上也失败过的是不稳定项、写进交付说明；
  main 上没失败过的按自己的问题修，修好再跑。**这次运行的链接写进交付说明。**
- 失败项明显与本次改动无关时，先 `gh run rerun <运行号> --failed` 重跑一次，再判断是不是自己的问题。
- 交付说明（`DELIVERY: 第 <k> 轮`）里必须有：改动清单、相关测试的命令与结尾的计数行、CI 运行链接（touches-core 加集成层那次）、逐条验收核对、署名的最后一行。
- 删掉了用例：逐条写「用例名 + 依据（哪条 ADR 或工单删的）」；工单没写到的删除不要自己删，报 blocked 交给架构师。
- 新增测试文件：在 `harness/tests/layers.toml` 补一行登记，放在第一个能到达其结论的层。

## 两条上报通道

设计问题不自己拍板：把它写成评论，报 blocked，交给编排者发到工单上。

```
## 需要架构师决定：<一句话说清要定什么>

<发现了什么：具体现象、在哪个文件或哪个行为上、影响哪一条验收标准>

**建议怎么做**：<你的建议，或者明说没有把握>

**需要谁决定**：<范围、接口、两种做法取哪一个、还是这张工单要改写>
```

- 设计问题：写到 `<工作目录>/.tmp/<编号>-question.md`，收尾 `STATUS: blocked`，`ERROR` 行以 `[设计]` 开头，后面写问题一句话与那个文件的绝对路径。不依赖这个决定的部分可以先做完。
- 执行环境（跑不了测试、缺凭据、权限不够、CI 挂了、依赖装不上、网络不通）：写到 `<工作目录>/.tmp/<编号>-env.md`，写清哪一步被挡住、试过什么、需要什么、哪些部分不受影响；收尾 `[环境]` 开头。
- 其它做不下去的：算一次失败，写清原因，不要在同一处反复试。

## 前提变了

- **工单正文或评论在你工作期间被改**：以最新的正文与最新的任务评论为准；发现实现与新正文对不上，按新正文调整，并在工单上留一条评论写明差异与影响。
- **依据的设计说明在 main 上变了**：读改动，按 main 的现状做，在日记里写明差异怎么处理。
- **main 的 CI 红了**：不是你造成的就记一笔继续做；你自己的 PR 上 `check` 不绿就不能合。
- **合并冲突按文件类型处理**：登记类（测试登记表、基准登记）两边都保留；生成类（接口快照、生成的客户端类型）以最新 main 重新生成，不手改生成物；记录类（`docs/CHANGELOG.md`）两边条目都保留。
- **冲突解不开**：报 blocked，写清哪个文件、哪几行、双方各自改了什么，不要反复重试，也不要硬合。

## 收尾格式

```
STATUS: done | blocked
SUMMARY: 一句话，不超过 120 字：做了什么、验证了什么
FILES: 本轮改动的文件路径，逗号分隔；没有写 none
NEXT: 建议下一轮做什么；没有写 none
```

`STATUS: blocked` 时在四行后追加一行 `ERROR:`，一句话写清卡在哪一步、失败信息要点、试过什么、需要什么（设计问题与执行环境问题按上面的前缀）。

**只有四行（加可能的 ERROR 行）是重要的输出**，前面的过程说明可以省掉。不要把大段代码、diff、日志塞进 SUMMARY——指路径。

## 边界

- 只做任务书上的那一件事，不顺手扩大范围，不顺手重构没让你动的文件。
- 没验证过的改动不要写进 `FILES` 当成完成。
- 不改规则文件（`CLAUDE.md`、`AGENTS.md`、`docs/agents/`、`docs/foundation-rules.md`）、不改 CI 工作流、不改标明只由用户修改的评价标准。需要改的时候：在 PR 上写明理由，工单标签改成 `ready-for-human`，写清要用户决定什么，收尾报 blocked 并说明。
- 不改 `.ralph/` 下的任何文件（`tasks.md`、`progress.md`、`state.json`、`handoff.md`、`active.json`）：那是编排者的账本。
- 一切以工单正文为准；任务书与工单正文冲突时，先按工单正文做，并在收尾里指出冲突。
