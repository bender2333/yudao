# 试用

这份技能是一份能照做到底的运行手册：从核对环境到发出帖子，每一步都有命令、有判据、有产出文件。读它的人是架构师会话，动手的是它起的几个子代理。工具命令集中在第 13 节。

试用回答七个问题，证据与判断的人写在表里：

| 问题 | 证据 | 谁判断 |
| --- | --- | --- |
| 交付得好不好 | `evals/scorer` 的隐藏检查 | 评分器 |
| 新手能不能自己走通 | 新手段带时间戳的出声记录 | 新手段记录，专家段核对 |
| 配错凭据、中途指导、改了主意、离开再回来，还接得住吗 | 模拟用户任务的事件与页面状态 | 专家段 |
| 卡住时查得出原因吗 | 专家段把卡点追到具体一步，以及花了多久 | 专家段 |
| 画面与事实一致吗 | 关键时刻的直播截图、回放截图、页面读数与事件 | 专家段（第 5 节画面对账） |
| 这个薄片承诺用户能做到的，做得到吗 | 试用工单「用户要能做到」的每一条与证明它的事件 | 专家段（第 5 节覆盖核对） |
| 画面看起来对吗 | 每个页面第一次打开时的第一眼记录；`audit` 的画布占比读数 | 第一眼是模型的观感，只进帖子的「观察」；占比读数由专家段对着截图判断，判断为没铺满的才进问题（第 7 节） |

成本（墙钟、请求数、用量、费用）是读数，不另成维度。试用不判断交付对错，也不评论代码风格。

试用的对象是从 main 打包安装的实例，试用过程只读被测对象：不改源码与仓库工作树、不提交、不当场修缺陷、不建工单、不动规则文件与设计说明。可以改的是试用环境自己的配置（服务地址、凭据、数据目录）。

## 1. 准入与预算

开始前把这几件摆到桌面上，缺一项就按表里的来源取；来源里也没有的，停下来问，不猜、不沿用上一次：

| 要什么 | 为什么要 | 从哪来 |
| --- | --- | --- |
| 试用工单号 | 覆盖核对对照它的「用户要能做到」 | 这次推进的薄片的那张试用工单 |
| 两个模型 | model1（`wb/cn:deepseek-v4.1-flash`）给产品与工程，model2（`ag/gemini-3.8-flash-high`）给质检、找问题与看图；被试部门的毛病不会被同一双眼睛复制 | [运行配置](../../../docs/agents/autopilot-runtime.md)第 4 节 |
| 服务地址与 Key | 部门跑真实模型；演练配错凭据用的就是它；只从环境变量读 | 环境变量 `YUDAO_EVAL_BASE_URL` 与 `YUDAO_EVAL_API_KEY`，不写进文件与日记 |
| 时间窗 | 一次约 4 小时 45 分，中途不能被打断 | 有试用者在场时先问他什么时候开始；没有人在场时按下面的预算自己排 |
| 发现的问题怎么处置 | 本技能只把问题写进帖子，不建工单 | 维护者：用户在场的会话，或[架构师循环](../architect-loop/SKILL.md) |

**由架构师循环启动时**（用户不在场）：上表每一项都有来源，不再向人索取；跑之前把 main 提交、任务集版本、两个模型的名称与试用工单号写进帖子的「环境与前提」。

环境逐项查，缺项就停，不降级硬跑。命令是第 13 节那条 `preflight.ps1`，级别为「阻断」的补齐了才往下走，「警告」记进帖子的「环境与前提」。

预算（一次一轮，多轮留给以后的 benchmark 优化）：

| 部分 | 上限 | 2026-10-28 实测 |
| --- | --- | --- |
| 安装与准备 | 25 分钟 | 在 25 分钟以内（未单独计时） |
| 固定任务 F1 | 120 分钟（与评测一致） | 20 分 44 秒，撞上压缩失败提前到终态 |
| 模拟用户任务 R1 | 55 分钟 | 18 分 47 秒，撞上上游 400 提前到终态 |
| 专家段与评分 | 50 分钟（含画面对账） | 22 分钟 |
| 覆盖核对的补做 | 15 分钟 | 并入专家段 |
| 独立复现 | 30 分钟 | 28 分 49 秒，与专家段并行 |
| 成稿与发帖 | — | 6 分钟 |

合计上限约 4 小时 45 分，实测墙钟约 2 小时 30 分，另有子代理自己操作页面与记录的用量。两条规矩：

- 一段到了终态就进下一段，省下的时间给复现与覆盖，不补跑。上限是「最多等到什么时候」，不是「必须等这么久」。
- 专家段与独立复现同时进行：复现用自己的实例与新数据目录，不碰试用实例。本轮复现从 20:37 起，同一时间帖子草稿已经成型。

超预算时按这个顺序删减，删掉的部分写进帖子：

1. 覆盖核对不补做，没覆盖到的写进「没测到的部分」；
2. R1 只做「离开再回来」，不做第二句改主意；
3. 独立复现只做排在前面的问题，其余标「未经复现」，进观察。

F1 与新手段不删减。单 agent 一方不跑（第 6 节），预算里没有它。

**谁动手**。三段各起一个子代理，每个只看得到自己那一段需要的东西；会让它预先知道答案的材料不给它：

| 子代理 | 模型 | 给什么 | 不给什么 | 产出 |
| --- | --- | --- | --- | --- |
| F1 新手段 | model2 | 起始文件夹路径、输入文本路径、归档目录、[method/novice.md](method/novice.md) | 不给 `docs/`、导出、本文第 5 节以后的任何内容 | `novice.md`、`shots/`、`text/` |
| R1 新手段 | model2 | 同上，任务换成任务集 R1 的步骤与两段指导原话 | 同上 | `novice-r1.md`、`shots/`、`text/` |
| 专家段 | model2 | 两段记录、导出、`errors.log`、试用工单、[method/expert.md](method/expert.md)、[method/probes.md](method/probes.md) | 不给结论与建议，让它自己查 | `expert.md` |
| 看图（子代理，或 `vision.mjs` 脚本） | model2 | 截图的绝对路径与要回答的问题 | 不给结论，也不给「这里应该是什么样」 | 每张一段「看到什么」 |
| 独立复现 | model1 | 帖子草稿里每条问题的复现步骤、同一个 wheel、一个全新数据目录 | 不给记录、结论、`expert.md` | 每条一份「复现到 / 没复现到」 |

两个模型时做不到三处互不相同。质检本来就跑 model2，找问题与看图的也是 model2，所以质检自己的输出要靠 model1 的复现子代理去查；产品与工程的输出由 model2 的找问题子代理查。帖子的「环境与前提」里写明这条分工与两个模型的名称。

## 2. 判据先核对

## 3. 试用实例

记下已有的安装（`yudao --version`、`uv tool list`），然后从 main 构建 wheel，装进仓库外的独立虚拟环境。**用干净克隆构建**：工作区里正在写的东西不能混进包里。

`scripts/release.py` 只接受「在 main 上、已推送、且是远端最新」的提交，所以构建的提交就是克隆下来那一刻的 `origin/main`，不要 `git checkout` 到旧提交（2026-10-29 试用时这一点卡过一次：指定的提交落后于 main，脚本拒绝构建，只能在最新提交上跑）。要试的是某个旧提交时，先把这个事实写进帖子的「环境与前提」，再按脚本允许的提交构建。

```powershell
git clone --no-tags <仓库地址> $env:TEMP\yudao-trial-src
cd $env:TEMP\yudao-trial-src; git rev-parse HEAD        # 就是 origin/main 的最新提交，记进帖子
uv run python scripts/release.py                 # 输出 wheel 路径与 SHA-256，记进帖子
uv venv $env:TEMP\yudao-trial-venv
uv pip install --python $env:TEMP\yudao-trial-venv\Scripts\python.exe <wheel 路径>
$env:TEMP\yudao-trial-venv\Scripts\python.exe -m harness api --data-dir $env:TEMP\yudao-trial-data --port 8766 --no-browser
```

- 其他系统解释器在 `bin/`；不用默认数据目录。
- 起服务时把当前目录设在仓库之外（`-WorkingDirectory $env:TEMP` 或先 `cd` 出去）。在仓库根目录下运行会导入仓库里的 `harness` 包，页面文件找不到，服务只回「没有页面文件」。
- 一次试用固定一个数据目录，重启服务时用同一个，R1 第 3 步要的就是这一点。
- 不带 `--publish` 时 `release.py` 只核对工作区干净、这个提交在 main 上并已推送、`node` ≥ 22.12，然后构建并输出 wheel 的路径与 SHA-256。带 `--publish` 才打标签、推送并上传 Release，标签已存在会报错。试用一律不加 `--publish`，不改发布脚本。
- 起服务以后核对一次 `http://127.0.0.1:8766/api/capabilities` 返回 200 才继续。构建失败就停：源码直跑没有页面文件。
- 服务进程号、端口、数据目录、wheel 与 SHA-256 写进 `state.md`（第 12 节）。

### 3.1 把两个模型配进产品

页面上做（`#/sys/models`），顺序是：连接 → 凭据 → 模型测试 → 部门默认。实测过的四个坑：

- **凭据引用必须是合法键名**：大写字母、数字与下划线，例如 `MODEL1_KEY`。用连字符的名字（`trial-model-key`）勾「写入 .env」会写坏数据目录里的 `.env` 并让服务回 500，之后保存与清除都报「.env 第 N 行键名非法」。恢复办法是把 `.env` 里那一行删掉（或者整个文件删掉）再重填；这一步不在这里耗时间，这是被测对象的问题，记下来继续。
- **模型测试准入要先过**：没通过的模型不能绑给部门，页面会拒，提示「该模型访问定义尚未通过模型测试准入」。
- **准入记录写得比命令返回晚一两秒**：测完立刻保存部门默认可能被同样的话挡住，等两秒重试即过。
- **质检要图像输入**：质检绑文本模型时页面在「部门默认」下给黄色提醒，说依赖外观的验收条件无法核验。把质检绑到声明了「支持图像输入」的模型，提醒消失。
- **`base_version` 按对象各算**：连接、凭据、模型测试、部门默认各有一份版本号，不是目录级那个 revision。拿错会回 409，重读那一项再写。
- **把页面给的黄提醒读一遍**：部门默认保存以后页面会自己给出建议（例如质检绑了纯文本模型）。提醒就是产品的判断，原文记进帖子，它常指向一个真问题。

两个模型分工：产品与工程用 model1；质检用 model2（`ag/gemini-3.8-flash-high`，模型访问定义里把「支持图像输入」勾上）。地址 `https://9router.huiju.asia/v1`，Key 只填进凭据表单，不进帖子、不进日记。

## 4. 新手段

方法与记录格式见 [method/novice.md](method/novice.md)。要点四条：只读 README 与页面；每一步一行，四问都过；觉得不对的地方只记现象，不写原因；每个页面第一次打开先做「第一眼」（一张视口截图、一句固定的问话、一次 `audit`）。

等待期按 [method/probes.md](method/probes.md) 的**页面类**探针做。F1 运行中不做任何打扰；配错凭据、两段指导、停服务与改主意都集中在 R1，按任务集的原话提交，不改写、不加提示。

## 5. 专家段

方法与完成标准见 [method/expert.md](method/expert.md)。七件事：卡点归因、R1 八件过程事实、画面对账、报错对账、覆盖核对、机械扫描与接口类探针、第一眼的整理。

覆盖核对里「交付与放行」「质检给出结论」这一类条目，可以用独立复现那一单的事件当补证，帖子里注明它是复现实例、不是新手段那两单。前两单都没走到终态时，这是唯一能补到放行一条的路。

两个任务的新手段都结束以后才开始这一段，中间不回头看页面。

**看图**：用 `scripts/vision.mjs` 把截图发给 model2，要它逐张说看到什么：有没有内容、布局错位、文字被截断、颜色与对比、按钮在哪、报错长什么样。它的原话记进画面对账那一行的「截图证据」，不转述成结论。要它看图之前不给它期望的样子。

```powershell
$env:YUDAO_VISION_API_KEY = <Key>
node .claude\skills\trial\scripts\vision.mjs --image shots/models.png --prompt "页面每个区块的标题与字段逐条抄下来；有没有红黄提醒，原文是什么" --max-tokens 1500
```

三条经验：

- 一张图问一件事，问具体的：字段值、按钮是否可点、提醒原文。不问「这张图有什么问题」；唯一的例外是「第一眼」那句固定的问话（[method/novice.md](method/novice.md)），它的回答只进「观察」。
- 整页截图会到上亿像素：本轮 `shot --full` 出过 1674×223164 的图，送模型直接回 413。`browser.mjs` 现在默认 JPEG 并限制高度，`vision.mjs` 有体积与像素双闸；要更细的地方单独截那一块（`shot --css`），不要放大整页。
- 视觉这条路只有 model2，而质检也跑 model2：截图读数只当客观读数（页面上写了什么、按钮什么状态），判断交给文本模型，不把截图读数算成独立证据。

看图有两条路，都走同一个模型。开子代理看图，适合要它顺带说页面前后关系、要它自己裁出几处细节的情形；`scripts/vision.mjs` 适合只要逐张抄看到什么，或者会话里的模型没有图像输入时。2026-10-29 起本机 harness 已给 `ag/gemini-3.8-flash-high` 声明了图像输入，子代理可以直接 `read_image`。换一台机器先试一次子代理读图，回「model does not declare image input」时二选一：在 harness 的模型声明里加 `input: [text, image]`（字段名是 `input`，`inputModalities` 是另一族协议用的，写错不生效也不报错），或者直接用脚本这条。两条路都不把截图读数算成独立证据（见上一条）。

## 6. 读数与对照

先跑一次机械读数，一条命令给出每份导出的概况：

```powershell
node .claude\skills\trial\scripts\readout.mjs <run.export> <run-r1.export> <run-repro.export>
```

它打印每个导出的状态与停止原因、轮次、发生的时间与墙钟、按部门的尝试次数与用量、缓存读占比、最大单次输入与配置窗口的比、按目的的成功与失败、失败清单（错误原文、`error_type`、`request_observation_id`、耗时）、压缩记录、关键事件链。加 `--types` 列全部事件种类，加 `--json` 给机器读。省下的是逐个 grep 与手工加总：本轮这件事做了四五遍，两次把时间抄错。

两种墙钟要分开写：导出里的墙钟是 `run_created` 到最后一个事件，子代理记录里的墙钟是它接手到交回。两个数不一样（本轮 F1 是 20 分 44 秒与 22 分），帖子写了哪个就标明是哪一种。

评分要的读数用 `evals/runner/yudao_metrics.py` 的 `collect(export, outcome, replay)` 算。`outcome` 写 `{"timed_out": ..., "elapsed_seconds": ..., "hidden_failures": [评分器里失败的检查]}`，`replay` 是 `replay.check` 的返回。用量没上报的写「未知」，不算 0。

F1 的交付按评测运行器的方式取回，再交给评分器：

```bash
uv run python -c "import sys, json; sys.path.insert(0, 'evals/runner'); import yudao; e = json.load(open('<导出文件>', encoding='utf-8')); print(yudao.fetch_delivery(yudao.YudaoClient('http://127.0.0.1:8766'), yudao.last_archived_delivery(e), '<交付目录>'))"
uv run python evals/scorer/scorer.py --delivery <交付目录> --result <结果文件>
```

**单 agent 一方不跑**（用户 2026-10-28 决定）。帖子里的「交付与对照」只写 Yudao 一侧的评分与读数，并写一行「单 agent 对照本轮未运行」，不让读者以为没有差别。R1 要停服务、追加输入，单 agent 的一次性运行本来就做不了同样的操作。

**可比性**：专家段记下部门所用的模型、上下文窗口与输出上限。三样都与评测相同时，F1 的评分可以与同一提交在 `docs/evaluation/` 的场景 3 读数并排列出；有一样不同，读数只在试用之间比较。上一轮的读数与问题编号从上一篇帖子读，不凭记忆。

## 7. 问题的门槛与排序

一条问题进列表之前过三道：

1. **查重，必做且留痕**：`gh issue list --state open --limit 300 --json number,title,body`，逐条比。帖子的问题表里多写一列「与已有工单的关系」：重复、相邻、无关。相邻的写一句为什么不重复（例：本轮压缩失败与 #1202「按轮折叠与用量预算」相邻，那张工单明写「压缩这次不改」）。重复的，在原工单下评论补证据（脱敏规则同第 9 节），不进列表，在帖子里列出补了哪几张。查重结论同时写进 `state.md`，发帖前核对这一列有没有空着。本轮漏了这一列，发帖后才发现与 #1202 相邻。
2. **换路复测**：换浏览器、换新数据目录，或者改用接口做同一件事。换了路就不出现的，归为试用环境的问题，写进「环境与前提」。
3. **单独复现**：在全新实例上照复现步骤再做一次，由第 1 节表格里那个复现子代理做。复现子代理说「跑通了、没停下」也是结论：把停下的一次记成偶发，写清同一输入一共跑了几次、几次停，不写成必然。反过来，复现子代理把清单读成「应该跳转」而判「没复现到」的，先看它看到的现象是不是就是问题本身（按钮不响应、页面不动），别照抄它的结论。清单本身还有两条：会改数据目录状态的条目排在最后（例如要写坏 `.env` 的那一条），目录被写坏就换一个新目录接着做，不手工修；复现子代理每改一次实例状态，在它的记录里写一行。

每条问题写：编号 `T<提交短号>-NN`、标题、复现步骤、期望、实际、证据（run id、事件 id、截图或 `.txt` 文件名、命令与输出）、专家段的分类。复现步骤里凡是要点、要输入的地方，写清点的是哪一处：元素的选择器、可见文字或坐标，连同那一步的页面读数；只写「点决定卡片的按钮」这种话，维护者与复现子代理会各点一个地方（2026-10-29 复盘：一条端到端用例的断言与界面对不上，就是因为帖子里没说点的是哪里）。另外标三样，按这个顺序排：

- 影响：挡住目标 > 拖慢 > 只干扰；
- 能不能绕过：不能 > 能（写明代价）；
- 频率：两段、两个任务、两条路中一共出现几次。

偏好、猜测、main 上还没承诺的能力进「观察」，不进问题列表。

**第一眼与占比读数**：新手段「第一眼」的原话是模型的观感，原样放进帖子「观察」的「模型觉得有问题的地方」，不进问题列表，也不过上面三道门槛。`audit` 的 `underfilled` 读数可以用数字说清楚（画布宽、容器宽、占比），专家段对着同一页的第一眼截图判断：设计上居中的小图，写明原因后放过；画面没铺满的，记一条问题候选（类写「画面读数」），之后过三道门槛。

**本技能不建工单**：问题写在帖子里，由维护者决定转成哪几张工单。

## 8. 建议

每条建议写四样：挡住了用户的哪个目标；证据（链到问题编号）；与上一轮的同一项比是更好、更差、看不出差别还是不可比；对应路线图「进入可迭代状态」五条判据中的哪一条（有负载、能度量、改动便宜可撤回、看得见、锚点受保护）。对不上任何一条的，不写成建议。
