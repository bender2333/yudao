# 专家段：把每处卡点追到具体一步

这一段与两个任务的新手段分开做，可以换一个子代理执行。它读得到全部材料，任务是**查明原因**并且**核对画面与事件**，不是重新用一遍。

## 输入

- 两份 `novice.md`（含「第一眼」表）、`shots/`、`text/`（含每个页面的 `<页面>-audit.json`）、`errors.log`
- 导出：`run.export`、`run.attempt`、`project.attempts`、`run.asks`、`run.recovery`、`replay.check`。请求体以 `GET /openapi.json` 为准。
- 试用工单的「用户要能做到」清单
- 任务集里两个任务的判据（F1 的检查点、R1 的八件过程事实）

## 一、卡点归因

逐处卡点，按时间戳对到事件，归到一类，记下定位用了多久：

| 类 | 判据 | 去向 |
| --- | --- | --- |
| 该说的结论没说 | 状态没显示；读取失败说成没有内容；原因说错；没给下一步；结论没有范围（放行没说覆盖了哪些要求） | 问题候选 |
| 系统出错 | 事件里有错误、空转、状态讲不通 | 问题候选 |
| 试用者误解 | 页面说清楚了，是新手段看漏了 | 不进列表，写进帖子「观察」 |
| 查不出原因 | 定位不到具体一步 | 问题候选，单独一条 |

## 二、R1 的八件过程事实

任务集第 69 至 78 行列了八件，逐件写结论与支撑它的事件 id：

1. 决定请求：卡片说了什么；从出现到回答用了多久；回答以后从哪里接着做；已完成的工作与已用的量是否保留。
2. 四处歧义：产品是去问了，还是按常见做法定了并写进 PRD；用户在页面上看不看得到这些选择。
3. 给工程的指导：工程下一步有没有照做（事件、之后的动作、交付里的依赖）。
4. 给产品的指导：回答有没有回到页面上；这期间工程与质检是否照常工作。
5. 重启以后页面状态讲不讲得通；事项接着做、从头来，还是卡住（`run.recovery`）；重启前后的已用时间、用量与剩余量是否连续。
6. 追加的输入有没有进同一个事项（`work_item.inputs`）。
7. PRD 有没有新版本，新版本里分类去掉了没有、按月汇总加上了没有。
8. Excel 这处新歧义怎么处理的，与「不要装第三方的包」这段指导怎么调和。

## 三、画面对账

从导出里取这些事件**各自第一次出现**的时刻：建事项、第一次交接、第一次询问、决定请求、指导的回答、重启后的恢复、追加输入、放行或取消。没有发生的写「未发生」。

每个时刻做三件事：

1. 取该事件之后的**第一张**新手段截图，这是直播；
2. 把页面回放拖到同一个事件，截一张，这是回放；
3. 直播、回放、事件三方对照，只对照承载事实的通道（[画面与播放设计说明](../../../../docs/design/visualization.md) 第 8.1 节的视觉通道表）。小人的位置与动作不对照。

一方与另外两方不同，记一条问题候选；事件发生以后过了一次采样（2 分钟）画面还没有反映，也记一条；回放拖不到那个事件，记一条「查不出原因」。

看截图用另开的 `ag/gemini-3.8-flash-high` 子代理：一次给它一张图的路径与三个问题（画面上有哪些字、布局与位置、有没有报错或被截断的字），把它说的原话抄进那一行。自己看不了图时，用同一时刻的 `text/*.txt` 与 `browser.mjs audit` 的读数代替，并在帖子里写明这一项用的是文字通道；两边的说法不一致时以重新看那张截图为准。

完成：每个时刻都有两方证据与一行结论（一致，或者问题候选的编号）。

## 四、报错对账

`errors.log` 的每一条，对到同一时间的事件或页面操作：

- 讲得通的（例如有意的拒绝、401 的演练）写明原因；
- 讲不通的记一条问题候选；
- 网络请求 4xx、5xx 里出现内部路径、堆栈、英文原文的，单独记。

完成：每一条都有去向，没有「留着以后再看」的条目。

## 五、覆盖核对

对照试用工单的「用户要能做到」，每一条写由哪几个事件证明（事件 id）。

- F1、R1 没覆盖到的，在同一个实例上补做（可以新建事项），留下事件 id 与截图；补做总时长以预算表那一行为限。
- 补不到的写进帖子的「没测到的部分」。
- 没有试用工单的，写「没有试用工单，覆盖核对未做」。

完成：清单每一条都有证明它的事件，或者在「没测到的部分」里。

## 六、机械扫描与接口类探针

1. 把导出写到文件，搜 `key`、`token`、`password`、`Authorization`、盘符开头与 `/home/` 开头的路径。
   - 凭据的**值**（Key、token、密码、Authorization 头内容）命中就是问题。
   - 路径与本机用户名出现在部门执行的命令与输出、或用户给的起始文件夹里，不算问题：导出是原始记录，不脱敏（[应用层与接口层设计说明](../../../../docs/design/app-and-interface.md) `run.export` 一行）。
   - 出现在 Yudao 自己写的其他字段里才算。
2. 按 [probes.md](probes.md) 里标「接口类」的探针做一遍，尤其空状态、超长输入、并发提交与刷新页面这四类。
3. 服务日志 `errors.log` 之外的服务端输出，只看有没有未捕获异常与堆栈，不追代码。
4. 每个 `text/<页面>-audit.json` 里 `underfilled` 非空的条目，对着同一页的第一眼截图判断：设计上居中的小图，写明原因后放过；画面没铺满的，记一条问题候选，类写「画面读数」，带上画布宽、容器宽与占比。

## 七、第一眼的整理

把 `novice.md` 的「第一眼」表原样抄进 `expert.md` 的「第一眼」一节，每行加上同一页 `audit` 的读数：`underfilled` 有条目就写占比，其余写「无读数」。不判断、不改写原话。这一节进帖子「观察」的「模型觉得有问题的地方」，不进问题列表；其中带占比读数、又经第六节第 4 条判断为没铺满的，同时是一条问题候选。
