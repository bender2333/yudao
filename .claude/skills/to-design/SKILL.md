# 写成设计说明

流程的正本是[工作方式](../../../docs/agents/workflow.md)；写法的正本是[设计说明规范](../../../docs/agents/design-spec.md)。这一步不追问用户，只整理已经定了的东西；还有没定的，回到 `/discuss`，或写进「未决问题」。

## 何时用 / 何时不用

- 用：`/discuss` 有了结论；父工单带 `waiting`，正文「决定」一段写着「设计先写」；一份设计说明还不符合设计说明规范；`/triage` 要把设计没写到的边界定下来。
- 不用：总图本身要改（交总架构师）；只是改工单正文（`/to-children` 或 `/triage`）。

## 先读什么

设计说明规范；总图里对应的那一节；相关的需求记录、ADR、调研与已有的设计说明；有成熟做法时，OMP 与 OpenCode 的实现（共同规则「参考实现」，写它们的提交号）。

## 步骤

1. **总图位置**：文件第 3 行写 `总图位置：<哪一节、哪个方框或哪道缝>。依据：<需求记录、ADR、相关设计说明与调研，路径加小节标题>。`。完成：这一行能在总图里对上。
2. **写正文**：按规范的六节写，没有内容的节不写：功能与依据；边界与范围（常量写默认值、范围和理由）；接口（在哪道缝上、谁调用谁、交换什么，配模块图；新增或调整代码的包时配包图）；方案（流转、失败处理、取舍理由）；验收（功能层面，用方案里的词写，父工单的验收从这里取）；未决问题。完成：子架构师能直接拿它拆子工单。
3. **自查**：把每句里的代码名、字段名、路径、行号、工单号拿掉，还成立的留下，没意思了的删掉；不写状态、历史与「现有做法 → 改为」。完成：全文没有工单号、没有「已实施」这类状态词。
4. **索引与对照**：新增的设计说明加进 `docs/design/README.md`；改了小节标题的，在 `docs/CHANGELOG.md` 写「旧标题 → 新标题」；总图的词与代码名不一致的，记进对照表 `docs/design/architecture/name-map.md`。
5. **推送与放出**：推送 main，记入 `docs/CHANGELOG.md` 与 `claude_jour.md`。父工单是「设计先写」的：把「依据」改成这份设计说明加推送后的提交，去掉「设计先写」与 `waiting`，下一步是 `/to-children`。冻结中的里程碑按 `/next`「改设计时的冻结」处理。

## 常见借口

| 借口 | 为什么不行 |
| --- | --- |
| 「写上类名和字段，执行者更好懂」 | 代码名会变，设计说明会跟着过时；名字的对照写在对照表 |
| 「写一节现状，说明为什么要改」 | 设计说明只写现在的设计；现状与经过进变更记录 |
| 「验收先空着，拆单时再想」 | 父工单的验收从这一节取，空着就拆不出能验证的子工单 |
| 「总图没写到，我在设计说明里补一个模块」 | 总图里没有的方框与缝先交总架构师 |

## 危险信号

- 第 3 行的总图位置在总图里找不到。
- 「验收」一节里写的是测试名或命令，不是功能。
- 同一个常量在两份设计说明里写了数。

## 交付

设计说明的路径与推送提交；放出的父工单（如果有）；还留在「未决问题」里的事。
