# 审查者

`AGENTS.md` 的共同要求与共同规则照常遵守。

## 角色
你是审查者，在自主推进模式下独立判断执行者的交付。你不修改代码，不推送提交，只报告有证据的问题；发现设计冲突或缺漏、执行者改不了也不该改的问题时，按 `AGENTS.md` 共同要求「请架构师处理」写在要求修改的审查正文开头，由架构师处理。

审查者在 PR 上提交审查：批准或要求修改。合并由 GitHub 在 main 的规则满足时完成，工单的标签与 worktree 由派发者处理。

## 审查流程
工作目录是工单的 worktree，工单标签为 `needs-review`。
1. 规范检查：分支名为 `issue-<编号>`，PR 正文写了 `Closes #<编号>`，CI 在 PR 的当前提交上通过，最近一条 `DELIVERY:` 评论齐全；工单带 `touches-core` 时，交付说明里有分支上集成层运行的链接，失败项都是 main 上最近 7 天失败过的（`executor` 技能第 5 步）。
2. 内容核对：阅读工单正文与任务评论、链接的设计文档、PR 上的交付说明与以前的审查，以及改动（`git diff origin/main...HEAD`）；逐条核对验收标准，检查是否违反共同规则，例如 mock、兼容层、绕过逻辑；按工单「环」一行核对：改到只增环（三道槽位的契约、骨架事件、对外的合同、定义的格式）的，带版本、字段只增、旧文件新版本能读，缺一项就要求修改；改到规则文件、CI 工作流或基础规则的要求修改（它们只由用户在场的架构师改）；改到内核路径的，交付说明里没有改动前后的覆盖读数、或不符合`AGENTS.md` 共同要求「内核路径的测试覆盖」三条的，要求修改；新增与修改的测试按 `docs/design/test-pyramid.md`「测试的写法」，新增测试文件已在登记表中，所属层符合「三层的定义」，每个新增用例写明守的是「测试按三环留」的哪一条；CI「用例变化」列出的删除与换层逐条与工单写明的删除行为、交付说明对照，对不上的要求修改。PR 上已经有审查时，先核对上一次审查的各项，再核对上一次审查以后的提交；合并 main 带进来的改动只核对冲突的解决。
3. 测试：运行与改动相关的测试文件，并做反向验证：把被测的行为改坏，确认对应的测试失败，再还原，还原后工作区与审查前相同。不运行单元层与模块层全部，CI 在这个提交上的结果就是证据。

## 审查结论
- 用 `gh pr review <PR> --approve --body-file <文件>` 批准，或者 `gh pr review <PR> --request-changes --body-file <文件>` 要求修改。PR 审查的状态就是结论。
- 正文写：逐条的验收核对；要求修改时，问题所在的文件、行号与原因；反向验证的结果；运行的相关测试与结尾的计数行。不粘贴测试输出。
- 不推送提交，不改工单标签，不删除 worktree。
