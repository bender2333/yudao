# 试用接待

与 [`/trial`](../trial/SKILL.md) 的分工：`/trial` 是 agent 自己当用户跑一遍、打分、发帖；这个技能服务**用户亲自试用**，试用前把实例与导游卡备好，试用后把口语反馈变成工单。用户只给试用结论，分流与建单由你做（`CLAUDE.md`「用户的参与方式」）。

你以架构师身份做。里程碑与试用工单的关闭权在用户：试用工单上有用户确认评论以后，按[验收证据规则](../../../docs/agents/acceptance-evidence.md)第 5 节写关闭评论再关。

## 模式 A：`prep <里程碑标题> <薄片>`

用户不在场时，`prep` 的 1 至 5 步（外加一次 agent 试用）由[架构师循环](../architect-loop/SKILL.md)「薄片推进」做，导游卡写在试用工单上；`prep` 留给用户在场的会话，用来把已经备好的导游卡交给用户、或者从头把这几步走一遍。

1. 达到检查：读置顶的阶段工单里这个薄片的清单，用 `gh issue list --milestone "<标题>" --state open --json number,title,labels` 对照。这个薄片只剩试用工单与子工单已全部关闭的父工单才往下走；还有别的开着就把清单给用户，停。
2. 核对父工单：每张父工单的验收标准逐条在当前 main 上核对（`/flow` 第 6 步），过了关闭父工单；没过的补成缺口工单放进里程碑，停。
3. 复盘：读 [`/milestone-retro`](../milestone-retro/SKILL.md) 按它做，报告发到 Discussions；参数与规则句子的修改先经用户确认。
4. 发布与走查：按 `docs/design/web-interface-and-release.md`「谁在什么时候发布」「架构师的走查」与「试用的交接」。发布前的测试按 `docs/design/test-pyramid.md`「各角色运行哪一层」：`integration` 在要发布的提交上通过，真实模型冒烟与全部客户端端到端测试，`desktop` 测试在用户同意的时间跑。发布脚本在 `scripts/`，走查用临时虚拟环境、单独的数据目录与端口，不动用户安装的那一份。走查按用户的操作路径走，指南与合理预期不一致时建缺陷工单，不改指南迁就。
5. 试用工单改为 `ready-for-human`。里程碑的变化（缝的已定未定）告诉总架构师。
6. 向用户输出导游卡，**不超过 10 行**：

   ```
   导游卡：<里程碑标题> · 薄片 <…>，版本 <v…>
   启动：<一条命令，装到哪、开哪个地址>
   第一个场景：照试用任务集 R1 的步骤原样操作一遍（<docs/trial/tasks.md 在 GitHub 上的链接>），之后随意
   这次看得见的变化：
   - <变化 1> — 去 <页面或位置> 看
   - <变化 2> — 去 <…> 看
   - <变化 3，可以没有>
   立住的缝：<总图第四节的缝名，逗号分隔>；回答的问题：<路线图第 2 节这个薄片的问题>
   反馈：试完对我说，口语就行；或者写在试用工单 #<编号> 里，我用 /trial-intake feedback 收
   ```

   变化只写用户在页面或命令行里看得到的，从这个薄片里因交付关闭的工单标题里挑 2 至 3 个，不列内部重构。完成：用户拿到导游卡，试用工单带 `ready-for-human`。

## 模式 B：`feedback [原话或文件]`

1. 收集：把用户的反馈逐条编号，保留原话不改写；没给参数就从试用工单的用户评论里读。
2. 定位：每条派一个只读子代理（Explore），给它原话、试用的版本、总图与对照表路径。要它回答：这条对应哪个页面或命令，代码在哪个文件哪几行；属于总图哪一节、哪个方框或哪道缝；设计说明对这个行为怎么写的；代码与那个说法一致还是不一致。几条同时派。
3. 分流，每条归一类：
   - **A 明确缺陷**：代码与设计说明不一致，或者与用户的合理预期不一致而设计说明没写；修法落在一两个文件里。
   - **B 模块优化**：行为符合设计，但用户想要的更好的做法要动一个模块的走向。
   - **C 总图边界**：触及总图的方框或缝，或者是新想法在总图里没有位置。
4. 向用户输出分流确认表，一行一条：

   | 编号 | 原话 | 定位（文件:行） | 总图位置 | 类别 | 处理 |
   | --- | --- | --- | --- | --- | --- |

   「处理」一栏写：A 写工单标题；B 写 `/module-sync <模块>`；C 写一句话议题。等用户确认分类，改到同意为止。
5. 办理：
   - **A**：按 [`/to-children`](../to-children/SKILL.md) 的子工单模板建工单，带「依据」「环」「只改」与验收层，正文引用用户原话，标 `ready-for-agent`，挂到里程碑里对应的父工单下、放进这个里程碑（试用中发现的缺陷可以进正在派发的里程碑，`autopilot` 技能「冻结」一条）。「环」是需你批准的，按 `/module-sync` 第三步当场念「只改」清单批准。标题格式 `[桶或道] 动作与交付目标`。
   - **B**：告诉用户用 `/module-sync <模块>`，可以接着在本会话做。
   - **C**：写成一句话议题（现象、触及总图哪一节、要定什么），列给用户带去总架构师会话；不自己改总图，不在设计说明里写与总图相反的做法。
6. 完成：每条反馈在表里有类别与处理结果（工单编号、`/module-sync` 的目标，或议题一句话）。

## 收尾

- `claude_jour.md` 追加一条：里程碑、版本、建了哪些工单、转了哪些、带走的议题。
- 试用工单上用户确认以后，按验收证据规则第 5 节写关闭评论，关闭试用工单（最后一个薄片连同里程碑）；用户不在场时保持打开。
