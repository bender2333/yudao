# 复盘

复盘是一次试验的读数：上一次改了什么、预期什么、实际发生了什么，据此保留或撤回；再从这段时间的原始记录里找出时间和返工花在哪里，提出下一次的改动，并写明下一次复盘用哪个数字检验它。它是近期阶段目标「改一处，运行真实任务，看到结果，决定保留还是撤回」中看结果、做决定的那一步。

你以架构师身份复盘，以 `CLAUDE.md`、`AGENTS.md`、`docs/agents/` 为对照基准。产出是一份报告和日记；规则、参数、设计说明与工单的修改写成提议，由用户确认。

## 三条读法

- **原始记录是证据。** 交付说明、审查正文、日记、交接记录、里程碑报告里的平均数，都是某个角色对经过的转述：用它们定位该去哪里看，并当作待核对的说法。结论引用事件本身：时间线上的标签事件、运行记录里的工具调用与输出、CI 日志的失败行、提交的差异。每条证据写成能直接打开的位置（`文件:行`、运行记录文件与行号、事件时间、链接）。
- **当时的视角。** 某个角色做错一步时，找出它在那一刻读到的内容（工单正文、任务评论、规则、工具输出）。读到的内容足以做对，原因在角色；读到的内容本身有缺漏或矛盾，原因在提供内容的那一层。
- **对照顺利的工单。** 一个原因成立的条件：出问题的工单里有它，顺利的同类工单里没有它。每个归因配一张做对照的顺利工单，找不到对照时写「待定」。

## 原始记录在哪里

| 记录 | 取法 | 用来看 |
| --- | --- | --- |
| 工单、标签时间线、PR | 里程碑范围用运行配置第 3 节的导出命令（`milestone.py collect`），数据文件含每张工单的时间线与 PR；其他范围用 `gh api repos/bender2333/yudao/issues/<n>/timeline --paginate` 与 `gh pr view issue-<n> --json commits,reviews,comments,files` | 每个标签停留的时间、轮次、要求修改、合并后重开 |
| 执行者与审查者的运行记录 | 运行那台机器（运行配置第 1 节）的 omp 会话记录 `~/.omp/agent/sessions/<工作目录编码>/*.jsonl`，编码例如 `C:\project\yudao-worktrees\issue-127` 对应 `--C--project-yudao-worktrees-issue-127--`；2026-10-12 以前本机的运行输出在 `C:\project\yudao-worktrees\autopilot\runs\`（`omp-<编号><轮次>.jsonl`、`rv-…`，同名 `.err`、`.done`），同目录的 `analyze-run.py` 列出每次请求的模型、停止原因与工具调用 | 实际运行的命令与测试、结果、工具调用花在哪里、结束方式、用量 |
| 被唤醒的架构师 | 工单与 PR 上最后一行是 `— claude-架构师` 的评论、`git log --author=claude-架构师`；派发机器上另有架构师 worktree 的 `.tmp/architect-<时刻>.json` | 处理了什么、怎样结束 |
| CI | `gh run list --workflow CI --branch main --event push`、`gh run view <编号> --log-failed`、`gh run download <编号> -n integration-results` | 失败项、首次出现的提交、重新运行是否通过 |
| git 历史 | `git log --stat <起>..<止>`；每个 PR 的差异与工单「只改」清单比较；`git log --diff-filter=D -- harness/tests client/src` | 改动是否超出工单、删掉的测试是否对应删掉的行为、哪些改动后来被删掉 |
| 设计说明的改动 | 每张工单的「依据」行：`git log <依据提交>..<合并提交> -- <设计说明>` | 放出以后设计有没有变 |
| main 的豁免记录 | 运行配置第 6 节 | 绕过 CI 与审查的合并 |
| 用户的反馈 | 试用工单的评论、`docs/requirements/` 中的用户原话 | 交付是不是用户要的 |
| Yudao 自己的运行 | 评测场景与自举运行经 `run.export` 导出的事件日志，评分在 `docs/evaluation/` | 三个部门的循环是否收敛、停在哪一层 |

## 步骤

1. **定范围与对照基准。** 参数给了里程碑、编号或日期就用它；省略时，取 `docs/evaluation/milestones/` 下最近一份 `*-retro-*.md` 的截止时间到现在。读上一份复盘的「改动与预期」表；没有上一份时，从 `docs/decision.md`、`docs/CHANGELOG.md` 与 `git log -- CLAUDE.md AGENTS.md docs/agents .github/workflows` 列出范围开始以来对规则、参数、CI 与流程的修改，每项当作没有写明预期的改动。完成标准：工单清单（编号、状态、PR），加一份改动清单，每项带日期与位置。

2. **取原始记录，写覆盖表。** 按上表取记录。完成标准：覆盖表写明每类记录覆盖多少张工单、缺哪些、为什么缺。缺失本身是发现，写明它让哪些结论无法得出。

3. **逐张重建经过。** 每张工单按时间排出事件：每个标签的起止（`ready-for-agent` 只计没有未关闭阻塞方的时段，以及 `in-progress`、`needs-review`、`needs-architect`、`ready-for-human`）、每一轮的结果、CI、审查、重开。有运行记录的轮次再读：
   - 执行者：实际运行过的检查命令与结果，和交付说明里的说法逐条比对；工具调用主要花在哪里；结束方式（正常、超时、上下文用尽、报错、反复做同一件事）。
   - 审查者：自己运行了哪些测试、读了哪些差异；每条要求修改在下一轮被证实（执行者改了代码，问题消失）还是被推翻。
   - 出错的那一步：按「当时的视角」写出它读到的内容。

   没有运行记录的轮次，用 PR 上每次推送的提交与该提交上的 CI 结果（`gh pr view issue-<n> --json commits,statusCheckRollup`、`gh run list --branch issue-<n>`）重建这一轮改了什么、检查结果如何；执行者是否自己运行过检查、审查者是否自己运行过测试、结束方式与成本这几项写「无法得出」。

   工单多于 5 张时按工单分给 subagent（sonnet），同时不超过 3 个；每个边读边把摘要写进 `.tmp/retro/<编号>.md`，只交回摘要，每条附出处。完成标准：范围内每张工单都有摘要，没有运行记录的注明只依据时间线。

4. **度量。** 里程碑范围先用运行配置第 3 节的 `report` 命令生成里程碑记录，有上一个里程碑时带 `--previous`，平均轮数、架构师介入次数与修复类工单比例的比较取自它。每个数字写明分子与分母。口径沿用里程碑报告的「口径」一节，新增的口径写进报告：
   - 时间去向：全部工单在每个标签上停留时间的合计与中位数；等待（`ready-for-agent`、`needs-architect`、`ready-for-human`）与工作（`in-progress`、`needs-review`）各占多少。
   - 返工：轮数分布、要求修改、合并后重开；成果在后来被另一张工单删除或推翻的成对清单，写明推翻的原因（设计改了、要求变了、实现错了）。
   - 漏过的缺陷：每张修复类工单、main 上 `integration` 的新失败、每次合并后重开，追到引入它的 PR（`git log -S`、失败用例的历史），写出哪一道检查本该拦下（执行者自测、审查、CI、集成层、试用），按检查分组计数。这组数字直接衡量各部门的判断是否独立。
   - 审查的作用：要求修改中被证实的比例；批准以后漏过的缺陷数。
   - 范围变化：派发开始以后加入、退回 `needs-triage`、依据的设计说明被改动的工单数。
   - 成本：有运行记录的工单，每个角色的请求数与 token。
   - 和上一个里程碑比较时写出两边的样本数；差别能由一两张工单的变化解释时，写「看不出差别」。

5. **核对上一次的改动。** 改动清单的每一项写：当时的预期（没有写明的，按改动的目的推出并注明）、这一次的数字、结论（保留 / 撤回 / 证据不够，写明下一次需要什么数据）。完成标准：每一项都有结论与证据。

6. **归因。** 第 3、4 步发现的每个问题，写出从现象到原因的链条，每一环附证据，并附一张做对照的顺利工单。然后选一个改动层，改动只放在这一层：
   - **CI 与测试**：同类问题能由机械检查发现；
   - **参数**：运行配置第 7 节的数值不合适；
   - **流程规则**：规则缺失或互相矛盾；
   - **工单写法**：验收写不清、依赖漏写、范围过大；
   - **设计与架构**：边界没定、缺跨工单的长期约定；
   - **执行环境**：机器、账号、模型、模型提供方；
   - **角色能力**：角色读到了足够的内容仍然做错。

   同一原因只在一张工单出现，归工单写法或角色能力；在两张以上出现，或会在还没开工的工单里再出现，归设计与架构、流程规则或 CI 与测试。完成标准：每个问题都有原因链、对照工单与改动层；证据不足的写「待定」与缺少的证据。

7. **对照项目目标。** 按 `docs/program-roadmap.md` 第 2 节的阶段边界与第 7 节的五条判据，写这段时间每条判据的变化与证据；对照试用反馈与需求原话，写交付与用户要的有没有偏差；列出还没开工的工单中，哪些会碰上第 6 步暴露的原因。

8. **提出改动。** 选层的优先次序：能做成机械检查的进 CI 或测试，其次改运行配置第 7 节的参数表，最后才是规则句子。每项改动写四件事：
   - 改什么，改在哪里；
   - 预期：下一次复盘看哪个数字、往哪个方向、变化多少；
   - 撤回条件：数字到什么程度就撤回；
   - 证明方式：能做成检查的，写成工单提议，验收要求这项检查在出过问题的历史提交上失败、在修复以后通过；其余由下一次复盘的数字证明。

9. **独立复核。** 派一个新的 subagent（sonnet），只给它报告草稿与原始记录的位置，不给你的推理过程，要它逐条反驳：证据是否支持结论，对照工单是否真的顺利，有没有反例。按它的结果处理每条发现：成立的保留，不成立的删除，证据不够的改成「待定」。

10. **写报告与日记。** 报告写到 `docs/evaluation/milestones/<里程碑短名>-retro-<YYYY-MM-DD>.md`（范围跨几个里程碑时用正在派发的那个），顺序：覆盖表 → 上一次改动的结论 → 时间去向与度量 → 按改动层分组的问题（问题、原因链、证据、对照工单、影响的后续工单）→ 项目目标 → 改动与预期表 → 需要用户决定的事项。没有问题的层略过。改动与预期表的列：编号、改动、层、位置、预期、撤回条件、证明方式、状态（提议 / 用户确认 / 已生效及日期），下一次复盘从这张表开始。`docs/CHANGELOG.md` 与 `claude_jour.md` 各追加一行：时间到分钟、范围、报告路径、需要用户决定的事项数。在会话自己的 worktree 中提交，`git push origin HEAD:main`。回复用户：报告路径、上一次改动的结论、需要用户决定的事项。
