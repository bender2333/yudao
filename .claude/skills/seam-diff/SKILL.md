# 按缝的差异报告

用户不读代码，要看出代码现在的样子与总图要求的样子差在哪。这份报告只写**差异**，差异尽量由已有的守卫算出来：守卫跑的结果、导入方向、部门名的检索、对照表的状态。代码现状的描述已经有了（总体架构第 1 节的模块图、对照表 `docs/design/architecture/name-map.md`），报告不重写它，也不画图。

你以子架构师身份做（`CLAUDE.md`「子架构师」）：只读代码与测试，不改；不改总图。产出是一份报告、对照表第 4 节的更新、工单与架构问题登记。

## 依据

- 总图 `docs/architecture.html`：第四节十三道缝（两侧、已定或未定、规矩、交换什么）；第二节的三环与「四层」一段。
- 路线图 `docs/program-roadmap.md` 第 5 节表的「第四节十三道缝」一行：每道缝在哪个阶段结束时立住。
- 对照表第 1、2 节：按缝列出的词与代码名、一致或不一致；第 4 节：每道缝的守卫与守的规矩，是守卫清单的唯一来源。

## 六步

### 1 定提交

`git fetch origin main`，在一个干净的 worktree 里检出要核对的提交（默认 `origin/main`），记下短提交号与标题。工作区有未提交改动的检出不用：结果要能绑定到提交。

**判据**：报告状态行写得出提交号；`git status` 干净。

### 2 跑守卫

结果写进 `.tmp/seam-diff/`。

- 先装依赖：`uv sync --frozen`；`npm ci --prefix client`；在 `harness/tests/openapi` 下 `npm ci`（接口快照的类型核对要它，缺了会报 `openapi-ts 未安装`，那是环境问题，不是缝的问题）。
- Python 单元层与模块层整层跑：`uv run python -m pytest -m unit -q --junitxml=.tmp/seam-diff/unit.xml`、`-m module`（模块层的测试会建仓库并提交，要有 git 身份）。两层合起来十几分钟，放后台。
- 集成层整层要 15 到 45 分钟，只跑对照表第 4 节里标「集成」的守卫文件：`uv run python -m pytest <这些文件> -n 4 --dist loadgroup --timeout=300 --timeout-method=thread --junitxml=.tmp/seam-diff/integration.xml`，两分钟左右。
- 评测工具的两个守卫：`uv run python -m pytest evals/tests/test_no_harness_import.py evals/tests/test_no_harness_paths.py`。
- 客户端：在 `client/` 下 `node --test --test-force-exit tests/unit/<第 4 节列的文件>`；三个逐场景回放不在 CI 里，一共一分半钟，照样跑。
- 通过与失败的数从 junit 文件读（`tests`、`failures`、`errors`、`skipped` 四个属性），`-q` 的日志末尾不一定有汇总行。

结果只认这一次在这个提交上实际跑的。跑不了的（缺依赖、超时、要外部服务）写「没跑」与原因；以前的结果、CI 在别的提交上的结果都不拿来顶替。

**判据**：第 4 节列的每个守卫文件都有本次的「通过 / 失败 N 项 / 没跑（原因）」；每个文件都在本次的 junit 里出现过，按 `classname="harness.tests.<路径，斜杠换成点>` 检索（没被收集的算「守卫丢了」）。

### 3 算差异

三项机器核对，结果也写进 `.tmp/seam-diff/`：

1. **部门名检索**（四层）。取 `harness/definitions/organization.json` 里的部门标识，在对照表第 4 节「四层」一行列的文件里按整词检索：`rg -n -w -e <标识> -e <标识> <文件...>`，去掉注释行。整词命中里有同名的变量（`context.py` 里叫 `engineering` 的局部变量），逐条看过，只数按部门名分支或取值的行，报告里写文件与行号，按「事实与裁决」「循环」分开记。
2. **对照表状态**。对报告要核对的那几道缝（见第 4 步「什么时候立」），把第 1、2 节里标「不一致」「代码里还没有」的行逐行用 `rg` 在代码里查一次现在的名字。代码已经变了的行，就地改对照表那一行；仍不一致的进报告。
3. **守卫对规矩**。逐道缝把总图的规矩与交换项和第 4 节「守的规矩」比：总图写了、守卫没断言的，就是**缺守卫**。

**判据**：每道缝都有「部门名命中几处、对照表还差几行、缺守卫的规矩有哪些」三个数或清单，可以是零。

### 4 逐缝判断

每道缝、四层、三环各写一行，「怎么处理」只给一种结论，按下面的先后取第一个成立的：

| 情形 | 怎么处理 |
| --- | --- |
| 守卫失败，并且失败的断言就是这道缝的规矩 | 缺陷工单 |
| 缝在以后的阶段才立住（路线图第 5 节） | 无需处理，写「阶段 N 立」 |
| 缝标「未定」 | 无需处理；有代码依赖了它的内部细节时登记架构问题 |
| 认为总图对这道缝的要求本身不成立 | 登记 `docs/architecture-issues.md`，开头写「总图」与节号，交总架构师 |
| 该立住的缝有越界：部门名命中、交换项代码里还没有、一个名字盖住了总图分开的两样东西 | 立缝工单 |
| 该立住的缝缺守卫 | 补守卫工单（执行者写测试） |
| 只差名字 | 无需处理，名字随立缝工单改（对照表「用法」第 2 条） |
| 都没有 | 无需处理 |

「什么时候立」看路线图第 5 节的两行：「第四节十三道缝」给缝，「判据五 锚点受保护」给缝里个别规矩（例如谁能拒绝谁无环的校验在阶段五），规矩比缝晚立的按规矩的阶段算。没有守卫的缝如实写「没有守卫」，这本身是一条结论。要建的工单先查重：`gh issue list --state open --limit 300 --json number,title,milestone` 存进文件再按关键词检索；已有工单覆盖的写工单号，不重复建。

**判据**：十五行齐全；每行的结论能指回第 2、3 步的一条结果或总图的一句话。

### 5 写报告

路径 `docs/evaluation/seam-diff-<日期>-<短提交号>.md`，一页能看完，用户的语言，结构固定：

```
# 按缝的差异报告：<日期>，提交 <短提交号>
状态行：提交号与标题、跑了哪几层、通过与失败的数、没跑的
## 结论（三到五条，每条一句话，最该先处理的在前）
## 逐缝
| 缝 | 什么时候立 | 两侧在代码里 | 守卫 | 这次结果 | 差在哪 | 怎么处理 |
## 没跑的与原因
## 工单与登记（已有的写编号，新建的写编号，交总架构师的写登记位置）
```

单元格写短句；两侧与守卫写模块名、文件名，细节留在对照表。路径用反引号，不做成链接。里程碑或阶段结束时做的，在那个里程碑的阶段工单上评论一行报告路径，总架构师核对阶段结束时引用它（验收证据规则第 6 节）。

**判据**：每一格的数字与第 2、3 步的文件对得上；状态行写了提交号。

### 6 交出去

- 第 4 步定了要建的工单按 `/ticket` 建：立缝工单与补守卫工单挂在该阶段的父工单下；建好的编号回填报告。该阶段的父工单正由别的子架构师改写时，报告里写「待建」与要合并进哪张父工单，交给那位子架构师建，免得重复。
- 第 4 节的守卫有增减、改名的，改对照表第 4 节。
- 报告与对照表的改动记 `docs/CHANGELOG.md`，`claude_jour.md` 写一段：核对了哪个提交、几条结论、建了哪些工单。
- 提交前 `git pull --rebase origin main`，只 `git add` 自己改的文件。

**判据**：报告里每条「立缝工单」「补守卫工单」「缺陷工单」都有编号，或写明「待建」与交给谁；每条交总架构师的都在 `docs/architecture-issues.md` 里。
