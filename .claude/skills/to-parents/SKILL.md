# 拆成父工单

这是两级拆分的上一级：从大的范围拆到父工单，一张父工单是一个桶、一个可以交给用户试用的目标。下一级 `/to-children` 把一张父工单拆成子工单。拆分让新工作沿着现有代码往总图靠拢：不掉头，旧工单能归并的归并，不另起一套。

你以架构师身份拆分，依据三份正本：`docs/architecture.html`（总图）、`docs/program-roadmap.md`（路线图，第 1 节的走法、当前阶段与它的「结束时总图」、第 3 节十条道）、`docs/agents/ticket-spec.md`。

## 环

每个桶、每张父工单记下它在总图第二节的哪一环，子工单照抄：

- **可重写**：路由、装配、执行的实现，适配，投影，画面，观察者；
- **只增**：三道槽位契约、骨架事件、对外的合同、定义的格式，字段只增、带版本；
- **需你批准**：写入口、裁决、边界、薄驱动与插件加载、评价材料、看门狗。

「环」只用这三个词；总图第三节的外环、内环说的是一轮工作的两层循环，是另一回事。

## 阶段工单与里程碑

阶段工单（一个阶段一张）与里程碑（一个阶段一个，标题是阶段名，只建当前与下一个阶段的，`docs/agents/ticket-spec.md`）由总架构师建，时间与条件见[验收证据规则](../../../docs/agents/acceptance-evidence.md)第 6 节。范围的阶段工单或里程碑不存在时停下来告诉用户，不自己建；父工单只挂在已有的阶段工单下、放进已有的里程碑。

## 已在执行的范围

范围里的里程碑已经开始执行时，它的工单按 `/next`「改设计时的冻结」只做一致性修正。这时拆分的产出是**对桶与补缺**：把已有的父工单对到桶上，已有的多层结构（父工单下面还有父工单）原样保留；改的只是挂在哪里、属于哪个桶，不改正文与设计。不重切已放出的工单，它们挂过来时保留原标签，不改成 `needs-triage`；缺口另建工单补上。

## 步骤

### 1. 读

读参数指向的范围。**里程碑**就是阶段：读路线图第 2 节表里它那一行（要回答的问题、结束时总图、薄片）与置顶的阶段工单当终点；一个阶段有几十张打开的工单，一次会话做不完时按一个薄片跑（如阶段二的薄片 ①）。阶段读路线图那一节；缝或道读总图与路线图的对应处；阶段工单读正文与评论；没有参数时读当前对话的结论。同时读总图六节与 `docs/agents/ticket-spec.md`。完成：你能说出范围的终点，也就是做完时总图上哪些方框、哪些缝变成什么状态，用户能试用什么。

### 2. 归桶

把范围里要做的事逐项归到一个桶：结构的工作归到总图第四节的一道缝（或第一节的一个方框），内容的工作归到路线图第 3 节的一条道。同一件事既碰缝又加内容时（比如网络取回既扩「动作」的缝又是动作道上的一项）：立缝归缝，加种类归道，一张父工单只认一个桶；先立缝的父工单，再加种类的父工单。一个桶太大、一次试用验不完时，按用户能试用的发布切成几个桶。每个桶记下环。归不进任何缝或道的事项，停下来交总架构师先改总图，不自己加方框或缝。

然后反过来找**缺口**：拿第 1 步的终点（路线图该阶段的「结束时总图」）逐项对桶，列出终点要求、却没有桶或没有工单的方框与缝；要求立住的缝，查它有没有第二种实现（测试用的也行）的工单，没有也算缺口。每个缺口成为一个新桶，或者补进已有的桶。终点里「已建」的说法要在 main 上核对，不按工单关闭与否推断。

单独的缺陷（一张工单就修完、不属于要立的缝或要交付的目标）不进桶，直接挂在阶段工单下，排在队列前面。

完成：每一项都在一个桶里、是挂在阶段工单下的缺陷，或者列为交总架构师；终点的每一项都有桶，或者写明已建、在 main 上核对过。

同时看每个桶有没有设计说明。设计先于拆分：桶没有设计说明（或者设计说明没有这道缝的两侧、保证、规矩与交换什么）时，父工单照建，标 `waiting` 而不是等子工单，正文「决定」一段写「设计先写：<缺什么>」，「依据」一行只写总图位置；`/to-children` 不拆这种父工单。

### 3. 旧工单定去向

列出与范围相关的打开工单（`gh issue list --state open --search`，按缝名、道名、设计说明路径、文件名找；也看阶段工单的子工单与相关里程碑），对照当前 main 给每一张定一个去向：

| 去向 | 条件 | 发布时做的事 |
| --- | --- | --- |
| 关闭：已实现 | main 上有实现与测试 | 评论写测试名或提交，关闭 |
| 关闭：被取代 | 做法与总图相反，或内容已被别的工单覆盖 | 评论写取代它的总图位置或工单，关闭 |
| 归并 | 内容仍要做，落在某个桶里 | 挂到那个桶的父工单下，标 `needs-triage`，由 `/to-children` 改写 |
| 推迟 | 属于后面的阶段 | 那个阶段的里程碑已建的移进去，没建的放进「待排期与阶段总览」；标 `waiting`，评论写等什么 |
| 清理单 | 不回答阶段问题、要改代码或测试的维护工作（`docs/agents/ticket-spec.md`） | 归在所属的父工单下，不放进里程碑；依赖某个阶段里的工单时设工单依赖 |
| 架构师直接做 | 文档、归档与规则文件的清理（`CLAUDE.md`「文档维护与归档」） | 不开工单；用户在场的架构师直接改、推送 main，旧工单做完后关闭 |

旧的父工单正好对应一个桶时，改写它当这个桶的父工单，保留编号与讨论。「已实现」要在 main 上亲眼核对，按[验收证据规则](../../../docs/agents/acceptance-evidence.md)。完成：每张相关的打开工单都有一个去向和一句理由。

### 4. 排序

父工单之间只在一个桶用到另一个桶的结果时设依赖；同一道缝上，立住缝的桶排在用它的桶前面。把父工单放进它所在阶段的里程碑，并写进阶段工单的薄片清单；清理单的父工单不放（`docs/agents/ticket-spec.md`）。完成：每张父工单有依赖或写明可以直接开始，清理单以外的都有里程碑与薄片。

### 5. 问用户

列成三张表给用户看：父工单（标题、桶、环、终点、依赖、里程碑、有没有设计说明，标明新建、改写还是原样对上）、旧工单的去向、缺口。问三件事：桶分得对不对、终点是不是用户要试用的、旧工单的去向有没有错。改到用户同意为止。

### 6. 发布

按依赖顺序创建或改写父工单，用下面的模板；依赖用 GitHub 原生依赖，有阶段工单时挂成它的子工单，命令见 `docs/agents/issue-tracker.md`。父工单带种类标签 `parent`，状态标 `waiting`（等子工单，[工作方式](../../../docs/agents/workflow.md)第 4 节）；需你批准一环的父工单在正文写清改的是哪些内核路径，不另等批准。再按第 3 步执行旧工单的去向，把单独的缺陷挂到阶段工单下。完成：表里每一行都在 GitHub 上落实，把编号列给用户，并提示下一步对每张父工单运行 `/to-children <编号>`。

## 父工单模板

```markdown
## Parent
#<阶段工单>

## 总图位置
依据：<设计说明路径>（main <提交>）；总图：<节号与方框或缝>
桶：<缝名或道名>；环：<可重写 | 只增 | 需你批准>
里程碑：<阶段名；清理单的父工单写「无」>；薄片：<阶段工单里的薄片与它回答的问题>

## 目标
<做完时用户能试用什么；这道缝交换什么、保证什么。>

## 用户故事
1. 作为<角色>，我要<行为>，以便<好处>

## 决定
<已定的模块边界、合同、交换内容；不写文件路径。>

## 验收标准
- [ ] <用户能观察到的行为>
- [ ] 验收层：<内核 | 缝 | 真实场景>，按 docs/design/test-pyramid.md

## 归并的旧工单
- #<编号>：<一句话>

## 不在范围
<明确留给后面的。>
```
