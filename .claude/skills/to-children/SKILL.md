# 拆成子工单

这是两级拆分的下一级：一张父工单（由 `/to-parents` 产生）拆成执行者能领取的子工单。环的三个词、桶与旧工单去向的定义在 [`/to-parents`](../to-parents/SKILL.md)；这里照抄父工单上写的，不重新判断。

## 两种做法

每张子工单是下面两种之一。

- **立缝**：用薄的一层把现有实现包起来，定下总图第四节那道缝的交换内容与版本，里面的代码这次不动。立缝的验收必须有第二种实现（测试用的也行）接上这道缝并通过契约测试；接不上的只是改了名字，不算立缝。只在后面的切片需要这道缝时才立。
- **切片**：在已有或刚立的缝上交付一段用户看得到、能试用的行为，纵向穿过需要的每一层，一次执行者会话做得完、CI 全过。

宽范围的机械改动（改名、改共享类型）按「先加新、分批迁、最后删旧」排成一串，每批一张。

## 步骤

### 1. 读

父工单「决定」一段写着「设计先写」时停下来告诉用户，先按工作流程第 2 步写设计说明，不拆。读父工单的正文、评论和已有的子工单，读它「总图位置」指向的设计说明与总图那一节，读 `CLAUDE.md`「工单规范」与[运行配置](../../../docs/agents/autopilot-runtime.md)第 7 节的上限，在当前 main 上看要碰的代码。完成：你能说出现有代码里哪些模块直接复用、哪些要包一层。

### 2. 处理归并的旧工单

父工单「归并的旧工单」里的每一张，对照当前 main 决定：改写成一张立缝或切片（保留编号与讨论，更新依据），或者关闭（已实现、已被本次的子工单覆盖，评论写明）。完成：每张归并的旧工单有一个结果。

### 3. 切

把父工单的目标切成立缝与切片，写出阻塞边：一张只在用到另一张的结果时被它阻塞；立缝排在用它的切片前面。按「工单规范」核对大小，超过手写文件上限的再切。父工单的每条验收标准至少落在一张子工单里。完成：父工单的目标与验收标准都被子工单覆盖，每张有阻塞边或写明可以直接开始。

### 4. 问用户

列成一张表：子工单（标题、做法、阻塞边、交付的行为、新建还是改写旧单）。问三件事：粒度合不合适、阻塞边对不对、有没有该合并或再切的。改到用户同意为止。

### 5. 发布

按依赖顺序创建或改写子工单，用下面的模板，挂成父工单的子工单，阻塞边用 GitHub 原生依赖，命令见 `docs/agents/issue-tracker.md`，里程碑跟父工单。标签：环是可重写或只增的标 `ready-for-agent`；需你批准的标 `ready-for-human`，评论写清要用户批准什么；「只改」里有核心文件的加 `touches-core`。父工单保持 `waiting`，不改不关。完成：表里每一行都在 GitHub 上落实，把编号列给用户。

## 子工单模板

```markdown
## Parent
#<父工单>

## What to build
依据：<设计说明路径>（main <提交>）；总图：<节号与方框或缝>
环：<可重写 | 只增 | 需你批准>；做法：<立缝 | 切片>

<用户看到的行为，或这道缝交换什么、保证什么。>

现有代码：<包住或复用的现有模块；这次明确不动的部分>

## 只改
- <手写文件清单>

## Acceptance criteria
- [ ] <行为或契约的判据>
- [ ] 验收层：<内核 | 缝 | 真实场景>，<要跑的测试或命令，按 docs/design/test-pyramid.md>
```

删减功能的工单在「只改」与验收里写明删掉的行为与对应用例（测试分层第 4.4 节）。
