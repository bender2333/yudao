# 文档一致性工具

Yudao 开发用的单独工具：给文档建一份文件和小节的索引（类似 Obsidian 的元数据缓存，不往任何文档写东西），再对脚手架文件（`CLAUDE.md`、`AGENTS.md`、`docs/agents/**`、`.claude/skills/**`）做确定性的检查。不调用任何 LLM，只提醒、不拦提交。设计依据见 `docs/research/doc-consistency-concept-model.md`。

## 运行

在仓库根目录：

```
uv run --project tools/doc-consistency doc-consistency <命令>
```

## 命令

| 命令 | 做什么 |
| --- | --- |
| `build` | 重建 `.doc-index/`。文件没变时索引文件字节不变；第一次运行把现状记成「待核对」的基线 |
| `status` | 工作区和索引比，列出新增、改动、删除的节点 |
| `who <文件或小节>` | 谁引用了它，给出位置与行号。小节写成 `路径#标题 > 子标题`，同名小节后面带 `(2)` |
| `nodes <关键词>` | 按关键词列出节点名；`who`、`impact`、`confirm` 要写完整的节点名，写错时报错也会列出相近的候选 |
| `view` | 生成离线图谱 `.tmp/doc-index/graph.html`：拖动、按目录上色、点一份文档高亮它引用的（绿）和引用它的（橙）、双击展开小节、「展开总图」显示 6 个节和 13 道缝 |
| `refresh` | 用 `gh label list` 保存标签快照到 `.doc-index/labels.json`；只有这一条命令要联网，其余都离线 |
| `check` | 汇总提醒：死引用（技能、标签、文件路径）与待核对。永远以 0 退出；规则或程序自己出错（缺标签快照、规则无解、角色表对不上）才报错退出 |
| `scope [--reach]` | 每个角色的阅读范围与字符数 |
| `rules canon` | 规则事实线：把正本表格（`data/canon.json`）读成事实，列出每张表的事实、「冲突时以谁为准」表读出的 `canon_prevails`、附注、引用格、读不出的格子、一条事实两处正本、读不到正本的角色。永远以 0 退出；配置或程序出错才报错退出 |
| `rules view` | 生成离线页面 `.tmp/doc-index/rulefacts.html`：角色 × 规则矩阵（每行能展开这条事实被复述的地方，矛盾的标红）、规则图（含第 1 节的「定」「改」边）、「以谁为准」偏序图（正本的边画实线，文档里复述的边画虚线；成环或与正本相反的标红）、底部矛盾清单与引用、读不出、附注（同一份事实，不手画） |
| `rules check [--all] [--tier A\|B\|C] [--sample N]` | 规则事实线第 3 步：把脚手架文件里的复述按八种句式读成原子，和正本比；输出解析成功多少句（按句式分）、附注、矛盾（五类加三类加以谁为准与正本相反加用户走样，逐条列复述 `文件:行` 与原句、正本 `文件:行` 与值、差在哪）、读不到正本、一条事实两处正本，最后是「像在说规则但解析不了」的提醒：汇总写「基线 N 条，新 M 条」，默认只列不在基线里的前 20 条。永远以 0 退出；程序或规则自己出错才报错退出。`--all` 把提醒全部打印，基线里的也列并标「基线」；`--tier` 只留一档提醒（A 全部候选，默认；B 窄口径命中、句式形状补入、机器主语；C 只留句式形状补入）；`--sample N` 从这一档里按固定种子抽 N 条 |
| `rules baseline` | 规则事实线第 6 步：把现在「像在说规则但解析不了」的提醒记进 `.doc-index/rulefacts/baseline.jsonl`（只追加，见下面「基线」一节）。输出原有几条、新增几条、其中几条已不在现有提醒里。永远以 0 退出 |
| `rules scan [--sample N]` | 规则事实线第 2 步，粗筛与盘点：在脚手架文件里列出「像在复述规则」的候选句，分「已是引用」「解析成功」「不是规则事实」三类，打印总数、三类各多少、窄宽口径各多少、按文件的计数，再逐条列出。`--sample N` 按固定种子随机抽 N 条，用来人工核对噪音率。永远以 0 退出，只读 |
| `impact <文件或小节>` | 引用它、提到它的节点，按角色分组（必读范围内的先列，其次是只是可达的） |
| `pending` | 上游变了而下游没变、也没确认的引用。范围（`check` 里的待核对用同一套）：上下游都不是记录文档（清单在 `data/record-docs.json`：`CHANGELOG`、`decision`、日记、`adr`、`research`、`evaluation`、`archive`）；只算指向小节、表格行、总图的节或缝的引用，指向整份文件的引用只由死引用检查查文件在不在。这些边仍在索引里，`who`、`impact` 照常能查 |
| `confirm <下游> [上游]` | 记一条确认（下游看过，不用改）；追加到 `.doc-index/confirmed.jsonl` |

## 范围与索引

- 范围：git 跟踪的 `.md`、`.html`，排除 `docs/archive/`、`agents_jour/`、`.claude/worktrees/`、`docs/prototypes/` 与 `evals/scenarios/` 下的 HTML（代码）、页面模板 `assets/graph.html` 与 `assets/rulefacts.html`。
- 节点：文件，和小节（Markdown 标题、总图的节与缝）；脚手架文件里的表格每一行也是一个节点（身份是「表 + 首列」）。hash 在行尾统一以后算，只代表内容版本。
- 边：Markdown 链接、HTML href、反引号路径、`` `路径`「小节」 ``、设计说明的「总图位置」行（落到总图的节和缝）。
- 一份源文件一个索引文件：`.doc-index/files/<路径>.json`；不记行号，`who`、`impact` 查询时现算。
- 索引里的 `seen` 是下游最后认可的上游 hash，是状态，不能重建：删掉索引等于把基线重置成现状。`confirmed.jsonl` 只追加。

## 规则与数据

- `rules/*.lp`：clingo 规则（只用分层写法），Python 只负责把事实喂给 clingo 并输出结论。规则事实线的规则在 `rules/rulefacts/`。
- `data/known-external.json`：内置技能与用户级技能的白名单（检查不依赖本机的 `~/.claude`）；约定路径清单（写入时才创建的具体文件，如 `agents_jour/其他.md`，不算死引用，只写文件不写目录）；哪个表头的首列是标签或技能。
- `data/roles.json`：角色的别名（如 solo 执行者的「执行者」「工人」「实施者」，审查者的「审查子代理」；协调者、维护者、编排者不是角色表里的角色，不登记）、入口规则文件、入口技能，和合称 `groups`（规则事实线读格子时展开）。角色名取自 `docs/agents/workflow.md` 的角色表，两边对不上会报错。
- `data/canon.json`：规则事实线的正本表格、键的别名（表级 `aliases`）、载体与载体别名（见下一节）。
- `data/rulefacts-scan.json`：`rules scan` 的动作词、动作词的排除、句式动词（见下一节「粗筛与盘点」）。
- `data/rulefacts-patterns.json`：第 3 步的词表与映射：动词到事实名、交给的动词、键的专用词表、清单的键别名、用户只定与确认的事实名、在场与可否的说法、限定与副词（见下一节「句式与比对」）。
- `doc_consistency/rulefacts/grammar.lark`：八种句式的文法，终结符由词表生成后接在它后面。

## 规则事实线

与上面的图谱线分开：管给 LLM 读的规则文件里「谁做、谁加、谁写、能不能」这类事实。方案见 `docs/research/doc-consistency-rule-facts.md`，现在做到第 6 步（收尾：测试分层表与「冲突时以谁为准」表登记为正本、键别名）：第 1 步把正本表格读成事实，第 2 步粗筛盘点（`rules scan`），第 3 步句式解析与比对（`rules check`，页面给矛盾着色），第 4 步植入矛盾验收，第 5 步是写法约定进规则（`workflow.md` 第 11 节「规则事实怎么写」是正本）与工具跟上约定：引用格、机器、理由清单在句号处停、角色表只登记键、第 1 节「谁定」、载体别名扩到路径。第 6 步迁移存量（脚手架文件里用自己的话复述规则的句子改成引用或句式，剩下的记成基线，`rules baseline`）。工具只读文档，不改文档。代码在 `doc_consistency/rulefacts/`（`patterns.py` 解析，`compare.py` 比对与输出），规则在 `rules/rulefacts/canon.lp`、`compare.lp`，数据在 `data/canon.json`、`data/rulefacts-patterns.json`；与图谱线共用的只有 `scan.py` 的解析、`scaffold.solve/pick`、阅读范围的事实（`scaffold_facts`）和打包的 cytoscape。`rules canon`、`rules view` 不读 `.doc-index/`，不需要标签快照；`rules scan` 读标签快照里的标签当窄口径的键，没有快照时跳过这一来源并在输出里说明。

**正本**（现在是九张表）：`workflow.md` 的「事实放在哪」表（第 1 节，由谁定、由谁改）、角色表（第 2 节，只登记键）、状态表（第 4 节）、证据评论表（第 5 节）、出问题往哪交表（第 7 节）、用户在场与不在场的权限表（第 9 节）、「冲突时以谁为准」表（第 11 节，第二张表，见下面「以谁为准的正本」），`acceptance-evidence.md` 第 1 节的结论表、第 3 节的测试分层表（键列「层」，「谁跑」读成「由谁负责」，和结论表的「负责角色」同一个事实名，括号里的限定如 `touches-core` 合并之前进附注）。每条事实只归一张表的一列。角色表（第 2 节）也在 `canon.json` 里，但只登记键是角色（角色词表的来源、被点名的角色）；它的「做什么」「不做什么」两列是可读的摘要，不是正本，不出「做」「不做」事实，谁做什么的正本是第 1 节。

**`canon.json` 怎么声明**：`tables` 的键是 `nodes` 命令查得到的表节点名（`小节 > 表N`）。一张表写：

| 字段 | 意思 |
| --- | --- |
| `key` | 首列的表头，和文档对不上会报错（权限表首列没有表头，写 `""`） |
| `key_vocab` | 写 `"角色"`：键本身是角色（角色表）；点名的角色就是键 |
| `node` | 规则图里键的节点类型；不写，这张表只进矩阵 |
| `carrier_column` | 载体别名从哪一列取（第 1 节「位置」）：那一格里的载体名和反引号路径都是这一行的键的别名 |
| `aliases` | 表级的键别名：`{"行的键": ["别名", ...]}`。行的键要和文档首列一字不差（对不上直接报错，不猜）；别名是复述里常用的缩写（「缝的已定未定」「试用工单」「里程碑」「推送」「合并」……），句式解析认它们；`rules scan` 的键词表不含它们（「依赖」「合并」「里程碑」这类常用词一进去，粗筛就几乎句句命中）。写在表级而不写在列级，是因为别名属于一行，不属于某一个事实 |
| `columns` | 列名 → `{fact, many, vocab, edge, edge_label, open, after, key_from}`；角色表这类只登记键的表写 `{}` |

列的字段：`prevail`（只有「冲突时以谁为准」表的那一列写 `true`，见下面）；`fact` 事实名；`many` 一格是不是多值；`vocab` 值的词表，`"角色"` 取自 `roles.json`（别名与合称），写成名字的词表放在 `canon.json` 的 `vocab` 里（如 `可否`），值必须在清单里；没有词表的列（理由清单）一格按「、」「；」切开，每个短语原样当一个值，不算读不出，`open: true` 只是给页面和 `rules canon` 加一个「词表未封闭」的提示（现在的 `canon.json` 没有用它）；`edge` 在规则图里画边，`"角色→键"` 或 `"键→角色"`，`edge_label` 是边上显示的字（第 1 节的两列写「定」「改」，不写就用事实名）。两种特殊取法，都只有一个字段：

- `after`：只读格子里这段话后面的清单（状态表「意思」一格里「交回架构师：」后面是 `needs-triage` 的理由清单）。清单在第一个「。」处停：「。」后面的话（如「新报告的问题也标它」）不进事实，记成附注给人看。格子里没有这段话的行不出事实。
- `key_from`：事实的键不是首列，而是另一列反引号里的标签，且在 `tags` 清单里（找不到标签的行不出事实）。现在的 `canon.json` 没有用它（第 7 节「卡在」一格改成了引用，不再另列一份理由清单）；测试用它造「一条事实两处正本」。

**读法**：一格里用「或」「、」「与」「；」「，」或 `<br>` 分开的是多个值（词表不是角色的列只认「、」「；」）；`\|` 转义的竖线不分格。角色按 `roles.json` 的名字与别名，合称（`groups`：`架构师`、`任何角色`）展开成各个角色。括号里的话与 `canon.json` 的 `qualifiers`（「领取时」「之前」这类限定）剥成附注 `note`，不进事实；写成名字的词表（可以、不可以）只认第一个「，」前面的词，后面的话是附注。**引用**：整格只写「按第 N 节」「见第 N 节」的格子是引用（第 1 节「每次状态变化的证据」谁改：按第 5 节）：不出事实，不算读不出，`rules canon` 与页面单列一段「引用」给人看。夹在别的话里的「按第 5 节」不是引用，照旧按词表读。**机器**：词表为「角色」的列里可以写 `canon.json` 的 `vocab.机器`（CI、脚本、钩子），读成值；它们不是角色，没有阅读范围，`named` 不包含它们，矩阵里不列，规则图里没有它们的节点和边（事实仍挂在键的节点上）。读不出的值（不在词表里，如「报告的人」「独立审查者」）原样报 `unparsed`，不猜；一格里读得出的部分照读。

**规则**（`canon.lp`，只用分层写法）：`dup_canon` 同一条事实在两张表里都有；`only_in` 两处里只有这一处有的值；`unreachable` 正本点名的角色，必读范围里没有正本所在的文件（只算 `agent` 不为 false 的角色，用户不读规则文件，不算读不到；矩阵里用户一列只标「点名」）。键是角色的表（角色表）里，每个键都算被点名（表里没有事实也一样）；机器值不算被点名。

### 粗筛与盘点（`rules scan`）

范围：脚手架文件（`scan.is_scaffold`）的 `.md`。`canon.json` 九张正本表的行是正本，不扫；其余表格照扫。YAML 头（`---` 之间）跳过；标题、表头、代码围栏线不扫；代码块里的句子照扫，标「代码块」。

**切句**：按「。」「！」「？」与换行切句，每句再按「；」切成分句；列表项各自分开，表格一格一句，`<br>` 当换行。**引导句**：行尾是「：」的分句；它命中时，它下面紧跟的列表项与续行（到空行、标题、表格、代码块、同级下一项为止）一起算进这一条，缩进列在下面，不再单独成候选。引导句自己没有命中，但它和它下面的条目合起来命中（`靠引导句加条目合起来才命中`），也算。句中冒号引出「；」分开的几项（「请架构师处理：只有四种情形交回…：甲；乙；丙」），同一句里冒号后面的分句是它的条目。引导句自己没有键、角色、动作词，但本身是「（不）是…的理由」或「以…为准」的形状，也补进来，单独记数。

**粗筛**：一句话里同时有键、角色、动作词，就是候选。
- 键：`canon.json` 九张表的键（含表级 `aliases`；「冲突时以谁为准」表的首列是两个载体，不当键）；标签快照（`.doc-index/labels.json`）；脚手架文件所有表格的首列。纯 ASCII 的键两边不能紧挨字母数字。表格格子的键与角色可以靠所在行的首列补上（记数里单列）。
- 角色：`roles.json` 的角色、别名、合称（复用 `rulefacts/canon.py` 的 `role_aliases`），包括「用户」。角色名也是键（角色表的键就是角色），所以只要有角色加动作词就够；`data/rulefacts-scan.json` 的 `role_as_key` 设成 `false` 可以关掉。
- 动作词：封闭清单，在 `data/rulefacts-scan.json` 的 `actions`；`action_ignore` 列出要先抹掉的复合词（标签、规定、关于……），免得单字动作词命中它们。
- 窄口径：键来自标签快照或证据前缀（`canon.json` 里 `node` 为「证据前缀」的表）；宽口径：窄口径加其余的键，计数里「宽」含「窄」。

**三类分法**（`rulefacts/scan.py` 的 `finish`，按顺序判；第 3 步改成用真正的文法）：
1. **解析成功**：`patterns.py` 用文法（`grammar.lark`）把这一句读成了原子，类别后面写读成哪种句式。陈述加指路的句子也按解析走。
2. **已是引用**：纯指路：句子里有指向正本文件的链接、`路径`「小节」、或「见」加正本文件的标题，并且没有「由」「不」「为准」「理由」，而且解析不了。
3. **不是规则事实**：命中了词表，但既没解析成功也不是纯指路。里面有流程叙述、例子、命令行、格式说明，也有还没写成句式的规则事实（它们就是 `rules check` 末尾「像在说规则但解析不了」的那些）。

第 3 步补的两条粗筛：主语是机器（CI、脚本、钩子，`canon.json` 的 `vocab.机器`）的句子算候选（「由 CI …运行」或分句一开头就是机器、后面跟着动词），记「机器主语补入」；匹配八种句式粗形状的句子直接算候选，不再要求同时有键、角色与动作词，记「句式形状补入」。

**输出**：总数、三类各多少、窄口径与宽口径各多少（含其中的表格格子数）、按文件的计数表，然后每条候选一行 `文件:行  [类别/句式，窄|宽(，代码块)(，表格)(，形状补入)]  句子`，引导句带的条目缩进在下面（`行号: 原文`）。`--sample N` 用固定种子（20261103）从全部候选里抽 N 条，格式相同，用来人工核对噪音率；同样的输入两次输出逐字节相同。

局限：这是粗筛，不判断是不是真的矛盾。没有主语的祈使句（「不自己加方框或缝」）句式形状对不上，不会成为候选；词表里没有的动作词同理。

### 句式与比对（`rules check`）

**八种句式**（文法在 `grammar.lark`；词汇封闭：终结符从词表生成后注入文法。角色与别名、合称来自 `roles.json`；键来自 `canon.json` 九张表的首列（「冲突时以谁为准」表除外，它的首列是两个载体；首列里「：」前面的头也认，「意图只由用户定」对到「意图：目的、判据…」那一行），第 1 节「事实放在哪」表另把「位置」一格里的载体名和反引号路径（`harness/`、`docs/design/`、`CLAUDE.md`……）当那一行的键的别名，所以「总图只由总架构师改」对到「系统的形状、三环、缝」那一行，「架构师不改 `harness/` 的代码与测试」对到「代码与测试」那一行（「A 的 B」两边必须是同一行的键，否则不读），表里写了 `carrier_column`；再加表级 `aliases` 登记的别名，如「里程碑」「依赖」「推送」「合并」对到各自那一行；载体与机器来自 `canon.json` 的 `vocab.载体`、`vocab.机器`，载体的别名在顶层 `载体别名`，如「其他需求记录」读成「需求记录」）：

| 句式 | 例子 | 原子 |
| --- | --- | --- |
| 由谁 | `needs-triage` 由执行者加上；总图由总架构师改 | `says(节点,键,事实,主语)` |
| 只由谁 | 总图只由总架构师改 | `says` 加 `only` |
| 谁不 | 架构师循环不改总图；审查者不推送 | `says_not(节点,键,事实,主语)` |
| 是或不是清单一员 | 文件超上限不是 `needs-triage` 的理由；下面这些不是交回的理由：（条目） | `member` / `not_member(节点,键,条目)` |
| 以谁为准 | 设计说明与 ADR 冲突时以设计说明为准（与第 11 节「冲突时以谁为准」表比，见下）；「总图只由总架构师改，与设计说明不一致时以设计说明为准」（前一个分句的主语是载体才成立） | `prevails(节点,优先的载体,其次的载体)`，只认载体词表 |
| 在场可否 | 用户在场时总架构师可以改意图；用户不在场时架构师循环不可以改意图 | `may(节点,角色,事,在场或不在场,可以或不可以)` |
| 交给 | 执行环境的问题交给用户；设计问题交回架构师 | `handoff(节点,卡在项,角色)` |
| 穷尽清单 | 只有 A、B、C 是 `needs-triage` 的理由；只有四种情形交回：A；B；C；D | `only_members(节点,键,条目)` 每条目一条，加 `closed(节点,键)` |

解析对象是脚手架文件里正本表格行以外的全部分句（切句、表格格子、列表项、引导句带的条目、代码块都复用 `rules scan` 的）。一句先整句解析，不行再按顶层的逗号切成分句各自解析；括号里的话与限定（`canon.json` 的 `qualifiers`，加 `rulefacts-patterns.json` 的「限定」「限定正则」）剥掉当附注，不进原子；合称先展开成各个角色再出原子（「由架构师」是三条 `says`）；没有主语的句子（祈使句、「你」）、词不在词表里的句子不解析、不猜。键后面可以写几个键、动词前可以有副词（直接、统一……）。

**动词到事实名**（`data/rulefacts-patterns.json` 的「动词」，不写在代码里；一个动词写几个事实名时取这个键在正本里有的第一个）：加上、加、标、改成 → 由谁改成；写、写成 → 由谁写；改、修改 → 由谁改（键只有「由谁改成」时取它）；定 → 由谁定；建 → 由谁建（键没有时取由谁改：第 1 节「谁改」那一格写的是「建、关、改名」）；删 → 由谁删；负责、做、跑、运行 → 由谁负责；交给、交回 → 交给。无宾语的「谁不」（审查者不推送）只认「无宾语的动作」里列的几个动词，其余动词要带键。

**比对**（`rules/rulefacts/compare.lp`，和 `canon.lp`、`scope.lp` 一起 load）。矛盾的八类，加对着「冲突时以谁为准」表的一类，和方案第 3.1 节的一类：

| 类 | 意思 |
| --- | --- |
| 五类 `extra` | 复述多说了正本没有的值（说「是理由」而正本里没有的也算）；合称展开后多出来的角色也按它报 |
| `only_wrong` | 说「只由」，正本里还有别人 |
| `denied` | 说「不」，正本里有 |
| `not_member_wrong` | 说不是理由，正本里是 |
| `precedence_cycle` | 「以谁为准」方向相反或绕成一圈（成环的一组载体报一条，列组内每一句） |
| 三类 `may_wrong` | 在场可否：复述说可以，正本说不可以，或反过来 |
| `handoff_wrong` | 交给：复述交给的角色，正本没有 |
| `closed_missing` / `closed_extra` | 穷尽清单：复述说只有这些，正本还有别的；复述里有正本没有的（一句话对一个键各报一条，漏的、多的合在一起列） |
| 另 `prevails_wrong` | 以谁为准与正本相反：复述说 A 优先于 B，而正本 `canon_prevails(B,A)`；复述说的两边正本里没有的不报（见下面「以谁为准的正本」） |
| 另 `user_hands_on` | 复述里写用户改、建、删、写（`hands_on` 事实名在 `rulefacts-patterns.json`）：用户只定与确认 |

多值事实复述只说一部分不报。条目只按字面和正本比（不做同义判断），所以改写过措辞的清单会被报成又多又漏。`rules view` 的页面与 `rules check` 是同一份结论。

**输出**（`rules check`）：解析成功多少句（按句式分）、附注多少、矛盾按类逐条列（复述 `文件:行` 与原句、正本 `文件:行` 与值、差在哪）、读不到正本与一条事实两处正本（沿用第 1 步）；最后是「像在说规则但解析不了」的提醒：候选 − 解析成功 − 纯指路，分成基线里的和新的，默认只列新的前 20 条，这是以后钩子的提醒。

局限：只比词表里有的名字；键不在词表里的复述（「冒烟层由 CI 跑」）读不了（「集成层由 CI 跑」读得了：集成层是测试分层表的键；「单元层、模块层」一行的键是整格，「单元层」单写读不了）；正本里的机器值（CI）读得出，机器主语的复述照角色一样比（正本没有的机器按 `extra` 报）；角色表不再出「做」「不做」事实，没有比；「用户只定与确认」那一类矛盾对着第 1 节「谁定」里写用户的行。

**植入矛盾验收**（方案第 4、5 步，`tests/rulefacts/`）：`planted.json` 是 20 条植入句（照句式写 10、随手写 10，各写文件、锚点、句子、期望）；`test_planted.py` 在当前 HEAD 的临时副本（`git worktree`）里植入、用真实命令行跑两次 `rules check --all`，断言照句式写找回 ≥ 8/10、随手写在提醒里 ≥ 8/10、两次逐字节相同、干净副本里这些句子一条也不出现，每条的找回与否用 `pytest -s` 能看到；`plant_on.py <提交>` 是一次性脚本，在任意提交上做同一件事并打印找回表（含三档提醒各找回几条；锚点或对着的正本在那个提交里没有的单独列，不算找回也不算失败）。

### 以谁为准的正本

`workflow.md` 第 11 节「冲突时以谁为准」表（第二张表）是「以谁为准」的正本：首列「两边」，列「以谁为准」。`canon.json` 里写 `{"key": "两边", "columns": {"以谁为准": {"fact": "以谁为准", "prevail": true}}}`，这一列不走普通事实的读法，读成 `canon_prevails(优先,其次)`：

- 「两边」格按「与」切成两个载体（括号里的话，如 `（执行时）`，去掉当附注）。载体取 `vocab.载体` 和顶层 `载体别名`（`D38`、`父工单的验收`、`子工单` 在载体表里；「其他需求记录」是需求记录的别名）。有一边不是载体：整行原样进「读不出」，不猜。
- 「以谁为准」格去掉反引号和括号，必须是两边之一，那一边优先，另一边是其次，出一条 `canon_prevails`。值不是两边之一（「不定优先级：交回……」）：只记成附注，不出事实，也不算读不出。
- 这张表不出普通事实，首列不进键词表，规则图和矩阵里没有它；`rules canon` 在这张表下面逐行列「优先于」，开头一行写总条数。

比对（`compare.lp`）：复述 `prevails(N,A,B)` 而正本有 `canon_prevails(B,A)`，报「以谁为准与正本相反」（`prevails_wrong`，列复述 `文件:行` 与原句、正本那一行、差在哪）。复述说的两边正本里没有的，不报（和多值事实只说一部分同理）；正本的边不参与「方向相反或绕成一圈」，那一类仍只比复述之间，所以一句相反的复述不会再多报一条环。页面第三部分的偏序图：正本的边画实线，复述的边画虚线，成环的、与正本相反的标红，列表里每条边前面写「正本」或「复述」。

### 基线（`rules baseline`）

存量里「像在说规则但解析不了」的提醒大多不是规则事实（流程叙述、命令、例子），也有正本里没有的规则事实（孤儿，等架构师定进哪张表）。这些记成基线，`rules check` 才有可能只报新出现的。`rules baseline` 把现在的提醒记进 `.doc-index/rulefacts/baseline.jsonl`，每条一行 JSON：`file`（文件）、`hash`（句子规范化以后的 sha256 前 16 位）、`head`（句子前 60 字，给人认）。句子是引导句加它带的条目；规范化是汉字旁的空白去掉、其余空白合成一个空格、条目前的列表记号去掉，所以挪行、改缩进不变，改字就变。

- **只追加**：已有的行不动，新的接在末尾；再运行一次没有新的，文件一字不动。行尾固定 LF（`.gitattributes` 对 `.doc-index/**` 已固定）。
- **改一句就重新报**：句子改了，hash 变了，不在基线里，`rules check` 把它当新提醒列出；改回原样又回到基线里。旧记录不删，`rules baseline` 的输出会说有几条已不在现有提醒里（句子改过，或已经写成句式解析成功）。
- **`rules check`**：汇总写「基线 N 条，新 M 条」，默认只列新的；`--all` 把基线里的也列出，标签前加「基线」。没有基线文件时全部算新的。基线文件有坏行直接报错，不猜。
- 基线只是「看过、暂不处理」，不是正本：把一条孤儿规则定进正本表以后，对应的复述改成句式，基线里的旧记录留着无害。

## 阅读范围怎么算

链接可达不等于必读。入口是 `data/roles.json` 里的规则文件与入口技能。一条引用算必读，要同时满足：它的子句（两个逗号、分号、句号或表格竖线之间）里有「读、遵守、遵循、为准、正本」或「按[链接]」，或者它在技能的「先读什么」一节里；并且这个子句不是只对别的角色说的（子句里出现别的角色的别名而没有本角色的）。必读只走一步：入口文件的指令算必读，必读文件里再指向的文件是按需查阅。

局限：条件性的阅读（「某某时读」）和只读一节（`「小节」`）都按整份文件计字符；一步以外的必读不计；没有指令词的「见某某」不计。
