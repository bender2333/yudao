# 本体技能：问「该做什么了」，从仓库现状算出方向（方案草稿）

11-08 晚你给这个分支加的目标：agent 和你都是无状态的，你只看大方向，细节下一步往哪推要靠本体给方向。你用技能问「该做什么了」，本体做符号推理，给出系统内部不一致的设计、没实现的功能、照现状必然还要考虑的设计，再给建议。

这份是方案，还没建。代码只在研究分支，main 不动。

设计前提（神经和符号互相反馈，两边各缺哪一环）写在 `change-impact-plan.md` 第 0 节。

## 1. 一句话

技能每次对一个给定的 main 提交，先核对模型跟不跟得上，再跑推理与检查，最后把结果归成四类，每条都带出处原句和提交，按先后排好。它不靠会话记忆，也不靠上一次的结果：同一个提交，算出来就是同一份。

## 2. 入口

- 技能：`.claude/skills/ontology-next/SKILL.md`，放在研究分支上（理由见第 6 节）。
- 你说「该做什么了」「本体看一下」，或者在技能后面写一个提交号；不写就用 `origin/main` 最新的提交。
- 技能做的事只有一件：运行 `python3 tools/yudao-ontology/next.py <提交>`，把它写出的结果按第 3 节的格式讲给你。技能不自己推理，也不改模型；它读到的结论都出自脚本。
- `next.py` 是新加的总入口，按顺序调现有脚本：`quotecheck` → `defs` → `run` → `crosscheck` → `codecheck` → `openloop`，最后汇总。它读文档和代码都用 `git show <提交>:路径`，不切分支，所以 main 上的工作区不受影响。

## 3. 输出

先有一行「模型对这个提交跟得上吗」，再按四类列，最后是建议。

```

一、内部不一致的设计（违例）
  1. 几个角色都能交完成时，开环怎么判前后矛盾
     「指定的角色交了完成，事项结束：没有核验角色核验它，结束原因是开环完成」 · 形态与核验角色 4.3 第 3 条

  1. 先定开环的判法（一、1）：它挡着工单二，也挡着中心型小组落地
  2. ……
```

每条的硬规矩：
- 带出处：原句照抄，写文档名和节号，写的是哪个提交上的；代码带文件和行号。
- 只说模型里有的。模型没覆盖的地方不说「没问题」，在开头那一行写明覆盖范围（例如「只覆盖骨架、定义、裁决、路由、循环、组织、缝与环；三份计划中的说明还没抽」）。
- 四类和现有结果一一对应：违例 → 一，确实缺与代码检查的缺口 → 二，推出的空位 → 三，不知道 → 四。不加新判断。

建议怎么排：模型跟不上的段落排最前（结论可能已经过时）；然后是违例（矛盾会让后面的实现返工）；然后是挡着别处的确实缺；空位与不知道放最后。建议只说「先定什么、先补什么」，不替你选做法；有几种做法时列出来，标我倾向哪个和理由。

## 4. 增量更新（你说的「梯度更新」）

每次不全部重抽，只动变了的那几处。

1. 找变化：`git diff <模型对齐的提交> <这次的提交>`，只看模型读的文档与代码。有两种变化，处理不同：
   - 改了模型里引用的原句：原句核对已经能找出来（上午 `48e2158` 那一轮就是这样查出 15 条真改的）。
   - 新加的段落，模型里没有一句引它：原句核对查不出来。要加一步：把变了的段落和模型的引用对一遍，没被引用的新段落列成「未抽」。
2. 只重抽这些段落：交给一个 agent，按现有批次的格式写成断言，词表与正名表随它一起给。
3. 重抽的结果先过三道再进模型：原句核对、HermiT 一致性、埋错仍全查出。过不了的不进模型，在输出开头写「这几段没抽进来」。
4. 进了模型以后记下新的「模型对齐的提交」，写在分支的一个文件里。下一次从这里开始算差。

技能随模型一起更新：技能本身只是调用 `next.py` 与讲结果的格式，新加检查或新的一批时，改的是脚本与模型，技能文件一般不用动。

## 5. 和第二步「先统一名字」的先后

管家的意见是统一名字要在技能前面，因为抽取一致率只有 0.25 时技能的结论不可靠。我同意一半。

- 不受影响的部分：技能推理用的是参照模型，它是逐条对过原句、过了一致性与埋错的。两次独立抽取一致率低，说明的是「换一个 agent 来抽，抽出来的名字不一样」，不说明参照模型里的结论错了。所以只读现有模型、加上原句核对的第一版技能，现在就能给出可信的结果。
- 受影响的部分：第 4 节的增量更新要靠 agent 重抽。名字不统一，新抽的「中心型小组」和模型里的「工程的中心型小组」就会被当成两个东西，模型会悄悄长出重复的个体。所以统一名字必须在增量更新前面。

我建议的顺序：
1. 技能第一版：`next.py` 汇总现有检查，加上原句核对和「未抽」段落的提示，只报告，不更新模型。
2. 统一名字：抽取之前与对照之前，拿 `CONTEXT.md` 词条与 name-map 把名字归一；重算一致率，目标是回到 r2 的水平以上。
3. 增量更新：名字统一以后，再让技能在「未抽」时自动重抽那几段。

## 7. 现在做不到、要先说清楚的

- 「没实现的功能」现在只查到定义文件和少数代码事实：分层里出现职能名、name-map、开环的两种判法、检查材料目录。「验收第 5 条有没有代码」这类功能级的判断还做不到。可行的做法是把设计说明「验收」里的每一条，对到「验收层」写的测试文件和用例名，测试不存在就记「未实现」。这要新抽一批（验收条目 → 测试），算第二步以后的事。
- 只覆盖范围（A）：骨架、定义、裁决、路由、循环、组织、缝与环。产品要怎么做、页面怎么画，模型都不知道，技能也不会建议。
- 推出的空位只到你写进第 0 批的那几条公理，深度 3。公理越多，「必然还要考虑」的就越多。这部分要靠你的意图，模型自己推不出新公理。
