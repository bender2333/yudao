# 文档改了，本体怎么跟：变动记录 + 覆盖检查（方案草稿）

11-08 夜你的担心：一次改名改一大片，以前的建模、关系都要跟着改，做成一次性的、每次都得重来一遍，效果就不好。通话里你把意思说清了：改文字、改概念都是应该的，变动本身是个过程。你要的是三件事：

1. 每次变动记下来；
2. 查这次变动的覆盖范围，确认它传到了整套系统（文档、本体、定义、代码）；
3. 不必每次改都重新建模，尽量自动，又合流程。

这份是方案，还没建。研究分支 `research/ontology-step1-r4`，main 不动。

## 0. 设计前提：神经和符号互相反馈

你 11-09 说的出发点：符号主义和神经网络结合，但不是训进模型里，是两边互相反馈，让两边都做得更好。大模型擅长从大量文字里找概念和关系，但会忘、窗口有限、没有强的逻辑推理；本体能做一致性和推理，但自己读不了文档。单让模型抽、没有本体把关，会抽得一团糟；本体报的问题，又可能是模型抽错的。

模型内部是不是隐式地有一套本体：研究上能从模型内部读出一部分概念和关系的表示，但它是隐式的，读不出全貌，换个上下文就变，不能拿来做一致性检查，也会忘。外面这套符号模型的用处，就是把它变成显式的、查得了的、不会忘的。

### 0.1 两个方向，现在各有什么、缺什么

| 方向 | 环节 | 现在 |
|---|---|---|
| 神经 → 符号 | agent 抽原句与断言，符号层判（原句核对、HermiT、SHACL、埋错） | 有：第 1、2 批 |
| | 推改名，符号层判「换完新文档里真有这句」 | 有，今天做的（候选目前从 git 改动推，还没用大模型；形态名这类不在术语表的词，以后可以让模型补候选） |
| | 抽公理（含意图公理），符号层核 | **缺**。14 条「必有」公理加 3 条注解，全是我照 D38、基础规则和你 11-06 的原话手写的 |
| | 抽的时候就拿本体自校验 | **缺**。现在是抽完再查 |
| 符号 → 神经 | 违例、确实缺、不知道 → 「该做什么了」，你和 agent 照此改文档与代码，再被检查 | 有：`next.py` |
| | 变动影响清单 → 下一次只重抽哪几段 | 有，今天做的：`changes.py`、`heal.py` |
| | 推出的空位 → 照现状必然还要考虑的设计 | 机制有，**现在 0 条**：4 条推理链都已被设计填上。公理太少，推不出新东西 |
| | 结果喂给 Yudao 的上下文装配 | **缺**。现在结果只在报告里，上下文装配不读它；接进去是改 main |

最要紧的缺口是「抽公理」：它是推出的空位为 0 的原因，也是符号层自己长不出新判断的原因。

### 0.2 本体报了不一致：设计真矛盾，还是抽错了

每条违例都挂着原句，所以能分开：

1. 先查原句。原句在当前提交上对不上，是模型过期，不算矛盾，先跟上（`heal.py`）。
2. 原句在，就让一个看不到参照模型的 agent，只拿这几句原句加正名表，独立重抽相关的断言，重跑检查：
   - 重抽以后同一个冲突还在：算设计矛盾，报给你。
   - 重抽以后冲突没了：算抽取问题。参照模型里这几条换成重抽的版本（照样过三道），记一笔是哪种错。
   - 两边抽的不一样，各有各的冲突：报「不知道」，附原句，交你看。
3. 有独立证据的直接算数：代码两边按两种判法写，或者两次独立抽取都抽出同一个东西。

现有的两条站得住：开环判法前后矛盾有代码当独立证据（`orchestrator.py` 与 `direct.py` 判法不同）；「工程的中心型小组」在两次独立抽取 A、B 里都有，只是名字不同。

代价：只对报出来的违例做，每条几句原句，不是全量重抽。

### 0.3 抽的时候就把本体当工具用

抽取的 agent 手里有三样工具：原句核对（我引的这句在不在）、正名表（这个词是不是正名，`_Avoid_` 里的该换成谁）、对一批草稿跑一致性与 SHACL（比起没加之前，新冒出了哪些违例）。抽完先自查，没过的自己重抽，最多两轮，然后才交上来。交上来的要么全过，要么附上「还剩哪几条、为什么」。

要防的是反馈把错洗掉：模型为了让检查通过，删掉惹出违例的断言，真矛盾就被藏起来了。所以规矩是：原句在的断言，agent 不能删，只能改名、拆分或合并；一直过不了的违例照实报上来，不许去掉。埋错 27 条仍要全查出，这道检查管的是检查器本身不被带偏。

### 0.4 抽取不只抽概念，也抽公理

意图公理就是把「为什么必须这样」写成规则。例如「内部要协作的职能必有一份职能内的核验」，出自你 11-06 的原话；「以放行结束的成果必有一份核验声明」，出自基础规则 3。推出的空位全靠这类公理：公理说「X 必有 Y」，模型里有 X、没有 Y，就报一个空位。

做法：

1. 抽取时把带「必须、必有、不能、只有……才、一定、不得、只由」的句子单挑出来，让模型写成公理草稿，带原句。粗数总图、D38 与基础规则里这样的句子约 28 句，设计说明还没数；现在只写成了 14 条。
2. 每条草稿由符号层先核三样：和现有模型一致吗；加进去以后推出哪些新空位、冒出哪些新违例（一下冒出很多，不是公理错了，就是设计真有问题，两样都值得你看）；能不能埋一个它该抓的错、它真抓得到。
3. 公理是意图，工具判不了真假，所以每条要你点一下才进第 0 批。这是整套里最该人确认的地方。

这一环接上以后，推出的空位才会从 0 变成有东西。

### 0.5 要不要训一个专门建模的小模型

现在不值得。

- 数据不够：现在是 158 句原句、几百条断言、两次独立抽取。训一个抽取模型，起码要几千条「原句 → 断言或公理」、并且检查过、人确认过的配对，差两个数量级。
- 不是能力问题：两次独立抽取的分歧主要在起名、一句话拆不拆，正名一下就能解决，用不着训练。
- 结构还在变：今天还在改名、加「询问」、去掉外包形态。现在训出来的模型会把旧结构固定住。

什么时候值得：

1. 上面的回路跑起来，攒下几千条检查过、人确认过的配对。这些配对本身就是训练数据，所以先建回路，训不训都要这一步。
2. 类与属性连着几周不变。
3. 抽取成了瓶颈：每次提交都要重抽很多段，大模型的费用或速度扛不住。
4. 不止 Yudao 自己要建模：用 Yudao 做的项目也要长自己的领域模型（你 11-06 说的第三步），一个专门的小模型才有足够多的用处。

在那之前更便宜的做法：把检查过的配对挑几条放进提示词里当例子，按句子的相似度挑。

## 1. 先说清图谱里放的是什么

不只是「文档位置 + 本体」合成一张图。里面分三层，变动时各自的命运不一样：

| 层 | 是什么 | 谁写 | 量（r4） |
|---|---|---|---|
| 概念与公理 | 概念的稳定编号（IRI，例如 `yd:Department`）、它们之间的关系种类、你定的几条不变式（第 0 批） | 人写 | 少，几十行 |
| 带锚的事实 | 「质检 核验 工程的交付」这样的断言，每条带锚：原句、文档、节号、提交 | 人或 agent 从总图与设计说明抽（第 1、2 批） | 158 句原句 |
| 生成的事实 | 定义文件与代码里的事实 | 脚本生成（第 3、4 批），不用人动 | 改名那次变了 282 行，没人手动 |

你说的「稳定的中间层」就是第一层加上第二层的锚。锚是关键：每条事实都知道自己出自哪句话，所以文档一变，能精确算出哪些事实受影响，不用全盘重抽。

## 2. 正面回答：总图概念改了，中间层要不要跟着改

分四种改动，量用上一次真实改名（r2 `ad36dd8` → r3 `bdedcdc`，即 `ce9c6883`/`02d1d590` 部门改职能，同一天还去掉了外包形态、加了询问）来数。

| 改动 | 例子 | 中间层 | 现在的做法要人改的行 | 按本方案要人改的行 |
|---|---|---|---|---|
| 只换词 | 部门 → 职能 | 不动。IRI 没变（`yd:Department` 还在），公理和关系一行没动 | 标签 30、原句 42、其他 8，共 80 | 0：原句按推出的改名自动接上，标签按确认过的改名换 |
| 原句改写、意思没变 | 表里「成果驱动」改成「按成果」 | 不动 | 10 | 10 句列出来，人看一眼确认「意思没变」，原句由脚本换新 |
| 意思真变了 | 外包不再是形态；新加「可以询问」 | 要改，而且应该改：系统本身变了 | 删 12、加 21、结构 3 | 同样这些，一行省不了 |
| 概念拆分、合并，或不变式变了 | 例如「核验角色」拆成两种 | 公理也要改，最贵 | 这次没有 | 没有省；影响清单会列出依赖它的公理和推理链 |

合起来：那次改名，现在的做法人手改了 126 行（另有注释 22 行）；按本方案人手改约 46 行。这 46 行里 33 行是真的设计变了（外包、询问），本来就该改；剩下 13 行是「看一眼确认」。

回放核实（拿 r2 的模型直接对改名以后的 main `48e2158` 做原句核对）：
- 对不上的原句 52 条（17 句不同的话）。
- 只给两行改名（部门 → 职能；三部门 → 「产品 · 工程 · 质检」），自动接上 38 条；改成从 git 改动自动推断候选，接上 44 条（第 8 节）。
- 剩 14 条，是 7 句话：2 句是外包被删（意思真变了），其余是形态名也改了（「几个角色直做」→「产品 · 工程」，「一个角色直做」→ 只有工程一个职能）和表格措辞（「成果驱动」→「按成果」）。形态名也推出来以后，还能再少几条。

所以诚实的结论是：中间层吸收的是「换词」和「改写」，这是改动里的大头；「意思变了」永远要人改，但改的量跟改动本身一样大，不跟模型一样大。不会每次重来一遍。

## 3. 一个踩到的坑：术语表的「避免用词」不能当改名表

管家提议的做法一是「名字只当标签，术语表给别名」。我同意，但回放时发现一个问题：`CONTEXT.md` 里的 `_Avoid_` 是「在这个意思下别这么说」，不是同义词。拿它直接替换，会把「质检」换成「核验角色」、「放行」换成「开环完成」、「材料」换成「证据」，原句反而全错，52 条里只接上 14 条。只用两行明确的改名，就接上 38 条。

所以要知道「哪个词改成了哪个词」。怎么知道见第 8 节：不靠人登记，从术语表和 git 的改动里推出来。

## 4. 变动影响清单：接到「该做什么了」技能里

每次问技能，它已经会先看模型对不对得上（`aligned.json` 记着模型最后对齐的提交）。在这一步之前加一份变动影响清单，对「对齐的提交 → 这次的提交」算：

**一、记下来：这段时间改了什么**
- 只看模型读的东西：总图、六份设计说明、术语表、定义文件、代码检查读的那几个文件。
- 按句切开，每句归一类：换词（推出的改名接住了）、改写、新加段落、删掉段落、定义文件变、代码变。
- 写成 `reports/changes/<对齐提交>..<这次提交>.md`，跟分支一起留在 git 里。下一次从新的对齐提交往后算，记录一段接一段。

**二、覆盖检查：这次改动传到哪了、哪里还没跟上**
- 每句变了的话 → 模型里引它的断言 → 这些断言说的概念（IRI）。
- 每个概念再往外查一圈：别的文档里还用旧说法吗；术语表有没有新词条；定义文件、代码里对应的事实变没变。每一处标「跟上了」「没跟上」「不知道（模型没覆盖）」。
- 例子：总图把部门改成职能 → 查出六份设计说明里哪几节还写「部门」；术语表有「职能」词条，跟上了；定义文件的键名还是 `departments`，name-map 写了「代码名不改」，算有意不改，不报。
- 最后重跑推理和检查，把四类结论和上一次比：这次改动新冒出来的违例、消失的违例、新的空位，单列。

**三、不重新建模：只动受影响的那几处**
- 换词：脚本按推出的改名换原句（换完新文档里真有这句才算），标签只按确认过的改名换。没人登记。
- 改写：列出那几句和引它的断言，人或 agent 判「意思没变」还是「意思变了」。没变，脚本换原句；变了，进下一条。
- 意思变了、新加段落、删掉段落：只重抽这几段（交给 agent，带上术语表与确认过的改名），先过三道再进模型：原句核对、HermiT 一致性、27 个埋错仍全查出。过不了不进，清单里写明。
- 定义文件、代码：重新生成第 3、4 批，不用人。
- 全过了，`aligned.json` 往前挪。

**合流程的地方**：清单本身就是这次改动的核对单。谁改了文档（你或某个 agent），跑一下就知道还有哪几处没跟上。以后要放进 Yudao 自己的流程（比如改总图的事项交完成前必须跑一遍），那是改 main，等你定。

## 5. 管家四点，逐条

1. 稳定编号、名字只当标签：已经是这样（这次 IRI 没改，公理没动）。要补的是标签从术语表生成，不手写。同意。
2. 只手写几条不变式，实例从定义和代码自动生成：一半同意。定义与代码那一侧已经自动生成（第 3、4 批）。但设计那一侧（第 1、2 批）不能从定义文件生成：那样设计和定义就成了同一份东西，「设计里有中心型小组、定义文件里没有」这种缺口就永远查不出来。设计侧要留着独立抽取，只是改成按锚增量抽。
3. 用原句锚算影响范围：同意，第 4 节就是它。现在的原句核对只能查出「改了的原句」，查不出「新加的、没人引的段落」，第一版技能已经补上了这一块。
4. 回放改名、用数说话：第 2 节，126 行 → 约 46 行，其中 33 行本来就该改。

## 6. 无论怎么做都要改模型的改动

- 意思变了：一个形态没了、一种关系反了、谁能放行变了。
- 新概念：比如「询问」第一次出现。
- 新的不变式，或者旧的不变式改了。
- 概念拆开或合并。
- 抽取范围扩大：比如把三份还没抽的设计说明抽进来。

这些就是系统真的在变。工具能做的是把它们从一大片改动里挑出来、告诉你波及哪里，不能替你判断它们。

## 7. 编号挂在什么粒度上：不另造一层更抽象的概念

你担心的是：术语表和总图已经很概念了，概念层再往上抽一层，怎么描述、怎么划分。答案是不往上抽。编号就挂在文档已经在用的词上，一个词一个编号，名字照文档写。模型里的概念分两种：

| 种类 | 是什么 | 名字从哪来 | 例子 |
|---|---|---|---|
| 文档里的词 | 总图、术语表、设计说明里有名字、规则在说它的东西 | 照抄文档 | 事项、角色、职能、核验角色、上限 |
| 推出来的类 | 模型为了写规则，用几个词组合出来的 | 不要求文档里有，标签就是那句描述 | 「有核验的形态」= 有核验角色的形态 |

第二种不是新概念，是规则的写法，用不着进术语表，也不用人起名。

划分从哪来，按仓库已有的先后：总图优先（`CLAUDE.md`：总图与术语表不一致时以总图为准），然后是术语表，然后是设计说明。模型自己不拆、不并任何概念。文档里同一个词有两种用法时（例如「放行」既说事项自己那一圈，又说子组织的出口），模型报成「不知道：一个词两种用法」，由人定。谁定也是现成的：`docs/agents/workflow.md` 第 1 节，术语表由架构师改，总图由用户定、总架构师改。

所以「怎么划分」确实是最难的问题，但它不是本体带来的新问题，是文档本来就要回答的问题。本体做的只是让划分不一致的地方露出来。

## 8. 改名怎么知道，不给改文档的人加一道手工登记

你说先不加约束。比了五种做法，用上一次改名实测（`ce9c688` 的上一个提交到 `02d1d59`，模型读的六份文档加术语表；然后拿 r2 的模型对改名以后的 `48e2158` 接原句，对不上的原句一共 52 条，是 17 句不同的话）：

| 做法 | 谁出力 | 实测 | 毛病 |
|---|---|---|---|
| 一、手工登记：改名的人记一行 | 改文档的人，多是 agent | 我照决定记录手写 4 条，接上 38 条 | 加负担，会漏记；你不要 |
| 二、从 git 改动自动推断，人确认（管家的思路） | 机器出候选，人点确认 | 327 对改动行，69 种「旧 → 新」片段。出现 3 次以上的 8 对：接上 42 条；2 次以上的 15 对：接上 44 条，剩 4 句 | 候选里有杂音，例如「一个 → 独立」出现 8 次 |
| 三、读术语表的改动 | 不用人，术语表本来就在同一个提交里改（`CLAUDE.md`「一次改完」） | `ce9c688` 上消失 4 个词条、新增 5 个；「职能」的 `_Avoid_` 里写着「部门」，改名确定；「部门默认」「部门账本」「项目部门设置」三条用同一个换法都对上了 | 只管术语表里的词。形态名（「三部门」→「产品 · 工程 · 质检」）不是词条，看不到 |
| 四、不要改名，逐句模糊对原句 | 人逐句确认 | 17 句都要人看 | 换一个词就要看十几句，最累 |
| 五、读决定记录 | 机器读 `docs/decision.md` 与提交说明 | 11-08 那条写了改名和不改的地方（ADR、v19、代码名） | 是给人读的话，机器抽不稳，只能当旁证 |

推荐三加二，不要人登记：
